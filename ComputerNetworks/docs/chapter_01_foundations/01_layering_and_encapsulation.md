# 分层、封装与协议

想象这样一个稀松平常的傍晚：你的笔记本电脑连着家里的 Wi-Fi，一边开着浏览器看技术博客，一边挂着聊天软件和朋友发消息，后台还在同步网盘。网线或无线电波传进网卡的，归根结底只是一长串连续不断的 `0` 和 `1`。

这就立刻带来一个让人忍不住发问的难题：网卡收到这串冰冷的比特流后，凭什么知道它确实是发给「你这台电脑」而不是隔壁邻居的？进了你的电脑，操作系统又凭什么分清哪一段该交给浏览器、哪一段该交给聊天软件？而浏览器拿到后，又怎么读懂对方发来的究竟是网页正文，还是一条「页面不存在」的报错？

要把这些互相交织的麻烦理顺，单靠一个无所不能的超级程序是行不通的。计算机网络给出的解法是把通信规则拆解开来，各管一摊：

- 通信双方事先约定好「消息怎么写、收到后怎么回应」，这套严格规则叫作 **协议**（protocol）；
- 把庞杂的通信任务按职责切分成上下衔接的若干层，每层只操心自己的那部分问题，称为 **分层**（layering）；
- 发送数据时，每一层都在原始数据的外面贴上自己专用的「说明标签」，就像把信件一层层装进不同用途的信封，这一动作叫作 **封装**（encapsulation）。

下面我们不急着背模型，先从一句最简单的网页请求出发，亲眼看看把一句话寄到千里之外，一路上究竟需要贴几张不同的地址。

## 寄出一句话，为什么要贴三张不同的地址？

当你在浏览器里打开一个网站首页，浏览器真正想对远方服务器说的话极其朴素，核心其实就是一句 `GET /`——意思是「请把网站根目录下的首页发给我」。可这句话要从你的笔记本出发，穿过家里的无线路由器、运营商的一串机房，最终落进远方服务器里正在运行的网页服务程序，它必须依次闯过三道完全不同的「认路关」。

第一道关在「此时此刻的眼前」：你的笔记本电脑并没有拉一根直通远方服务器的专用网线，它唯一能直接对话的邻居，是客厅里那台无线路由器。于是，数据包走出电脑的第一步，必须写明「眼前这一小段路交给哪块网卡」。每块网卡出厂时通常都带有一串局域网内用于识别设备的硬件编号，叫作 **MAC 地址**（Media Access Control address）。有了它，无线信号才能准确落到客厅路由器的网卡上，而不会误交到同一局域网里的智能电视手里。

第二道关在「跨越成千上万公里的茫茫互联网」：客厅路由器收到数据后，知道终点远在千里之外，它要把数据交给运营商的下一台中转设备，后者再交给更远的一台……像这样专门负责替数据指路、决定下一站往哪送的中转设备，叫作 **路由器**（router）；数据每从一个设备传给下一个相邻设备，就叫作走了一 **跳**（hop）。沿途的每一台路由器都不认识你家客厅里的网卡，它们需要一张全网通用的「最终收件人门牌」，这就是 **IP 地址**（Internet Protocol address）。路由器拆开上一跳的外包装，看一眼目的 IP 地址，就能查出接下来该往哪个出口送，再给它换上通往下一跳的新 MAC 地址。

第三道关在「进了目标机房之后」：好不容易千山万水送到目标机器，可一台服务器上往往同时运行着网页服务、文件传输、远程登录、监控采集等几十个程序。机器本身收到了数据，还得知道应该递进哪一个程序的信箱。于是，发送方在写请求时，还会附上一个用来区分机器内部不同通信程序的数字编号，称为 **端口**（port），比如普通的网页服务常约定使用 80 或 443 号端口。

把这三关连起来看，答案便呼之欲出：并不是网络设计者闲着没事非要发明三套地址，而是因为「眼前这一跳交给谁」「全网最终去哪台机器」「进了机器交给哪个程序」压根是三个不同尺度的问题。MAC 地址负责眼前一跳，IP 地址负责跨网寻路，端口负责精准投递到具体程序——三张地址各司其职，缺一不可。

??? question "如果下一跳换了，应用请求一定要跟着重写吗？"

    完全不需要。每换一跳时，只需把当前这段链路的外包装（主要是这一跳的 MAC 地址）换掉，里面装着的 `GET /` 请求原文可以原封不动地穿过整个互联网。不过也有例外：如果路径上部署了替真正服务器接待外部流量的中间角色——也就是第 9 章会细讲的[反向代理](../chapter_09_virtual_network/02_service_discovery_proxies.md)——它有时会拆开看到应用层内容，并根据规则读取或改写请求。

既然我们直觉上已经把通信分成了几件互不干扰的事，那么在工程上，这套「分层」思想究竟带来了什么本质好处？又为什么总要小心区分「协议」「服务」和「接口」这三个词？

## 为什么一定要分层：协议、服务与接口

不妨做个思想实验：假如世界上没有分层，写浏览器的工程师必须亲自包办一切——既要懂得网页文本怎么排版，又要操心半路丢包了怎么重发、跨洋光缆断了怎么绕路、无线电波遇到微波炉干扰怎么重新调制，还要针对市场上几百种不同厂商的网卡芯片分别写驱动。那样的话，哪怕只是家里从有线网线换成新一代 Wi-Fi，你电脑上的浏览器、聊天软件、游戏客户端全都得跟着大改代码，整个软件生态根本转不起来。

分层的核心动机，就是**隔离变化、管控复杂度**：把庞大的系统切成若干相对独立的层次，每一层只关心自己份内的职责，并只依赖紧挨着它的下一层所做出的承诺，而不必打听下一层内部到底怎么实现。

在这个协作体系里，有三个经常同时出现、却含义迥异的关键词，一定要从一开始就分清：

- **协议**（protocol）：是**同一层**的通信双方（比如你的浏览器和远方网页服务器，或者两端的传输模块）共同遵守的约定——消息的字节怎么排、谁先开口谁后回答、出错了怎么办。协议是水平方向上的对话规则。
- **服务**（service）：是**下一层向紧邻的上一层**承诺提供的能力。比如网络层向上一层提供的服务是「我尽力帮你把这个包送到目标 IP，但不保证绝不丢包」，而某些传输层协议则在此基础上向上承诺「保证让你的程序按发送顺序读到完整无缺的字节流」。服务是垂直方向上看得见的能力清单。
- **接口**（interface）：是上一层具体去**调用**下一层服务的操作入口。例如，应用程序要请操作系统帮忙收发网络数据时，调用的就是操作系统暴露出来的编程入口——第 2 章会亲手操作的 [Socket（套接字）](../chapter_02_application/04_socket_and_listening.md)。

你可以把这三者对照成身边的快递系统：全国各地快递分拨中心之间约定的分拣规范和运单编码，是**协议**；快递公司对寄件人承诺的「次日达」「保价赔付」「限重 20 公斤」，是**服务**；而你走进去填单交件的那个前台柜台或手机下单界面，就是**接口**。作为寄件人，你只需要通过接口看清对方承诺什么服务，至于货车晚上走哪条高速、中间换没换新能源厢货，你完全不必操心——只要服务承诺不变，底层想怎么升级换代，都不会打扰你寄件。

清楚了「为什么要分层」之后，互联网工程师们具体把网络切成了哪几层？每一层又分别管些什么呢？

## TCP/IP 与 OSI 模型 { #tcpip-osi }

把前面已经浮出水面的几项分工串起来——应用程序写消息、按端口交给进程、按 IP 跨网寻路、按 MAC 完成眼前一跳——再加上最底下真正把 `0` 和 `1` 变成光纤里的脉冲、网线里的电压或空气里的电磁波的工作，正好自然拼出了五层。

在日常工程与互联网实践中，我们最常用这套五层的 **TCP/IP 模型**（得名于互联网里最核心的两个协议 TCP 和 IP）来梳理全局。除此之外，国际标准化组织还曾提出过一套经典的七层 **OSI 模型**（Open Systems Interconnection model）。先看五层模型如何划清边界（表中提到的具体协议会在后续章节逐一展开，可随时点击链接预览）：

| TCP/IP 五层 | 代表协议或技术 | 核心职责 | 常见数据单位 |
| --- | --- | --- | --- |
| **应用层** | [HTTP](../chapter_02_application/01_http_https.md)、[DNS](../chapter_02_application/02_dns.md) | 定义应用程序互相发什么请求、怎样应答 | **报文**（message），即应用间交流的一条完整消息 |
| **传输层** | [TCP、UDP](../chapter_03_transport/01_udp_tcp.md) | 在两端运行的进程之间交付数据，按需提供可靠传输与节奏控制 | **TCP 段**（segment）或 **UDP 数据报**（datagram） |
| **网络层** | [IPv4](../chapter_04_network/01_ip_addressing_subnetting.md)、[IPv6](../chapter_04_network/02_ipv6_nat_icmp.md) | 用 IP 地址标识网络中的主机，在多跳路由器间选路转发 | **IP 数据报**（datagram），口头上常叫 IP 包 |
| **链路层** | 以太网（Ethernet）、Wi-Fi | 在同一段物理链路上，把数据可靠地送到相邻节点的网卡 | **帧**（frame） |
| **物理层** | 光纤、双绞线、无线电 | 将比特编码为光、电或无线电信号，在物理介质上传输 | **比特**（bit） |

那么七层 OSI 模型多出来的两层在哪？它把「管理会话起止」（会话层）和「数据格式转换、压缩与加密」（表示层）从应用层里单独拎了出来，夹在应用层和传输层之间。而在真实运行的 TCP/IP 互联网里，这两类活并没有独立成专门的操作系统内核层，而是常由应用程序自己或它调用的软件库顺手办妥——比如第 7 章会深入剖析的 [TLS](../chapter_06_security/01_tls.md) 安全库，就负责在网页登录时把应用数据加密保护起来。

这里有个很重要的学习心态：**分层模型是用来帮我们厘清职责的思维地图，而不是死板的施工图纸。** 现实中的软件和硬件实现完全可以把相邻两层的工作合并在一个模块里以追求效率；但只要你心里装着这张五层地图，遇到任何网络问题都不会迷失方向。

纸上谈兵不如亲眼看一次打包全过程。接下来，我们拿一条真实的网页请求，沿着五层从上走到下，再从下拆到上。

## 最小完整例子：跟踪一条 HTTP 请求的打包与拆包

假设你在浏览器地址栏敲下 `http://example.com/index.html` 并回车。浏览器首先按 [HTTP](../chapter_02_application/01_http_https.md) 协议的格式，拼出一条非常简短的纯文本请求报文。其中 `GET /index.html` 表示「请读取这个路径对应的内容」，`HTTP/1.1` 声明所用协议版本，`Host: example.com` 指明要访问哪一个站点：

```http
GET /index.html HTTP/1.1
Host: example.com
```

接下来，这条应用报文要交给操作系统里的网络协议栈逐层向下传递。每经过一层，这一层都会在原有数据的最前面贴上一块写满自己控制信息的「说明标签」，叫作 **首部**（header）；最底层的以太网为了检测信号在网线里有没有传错，还会在整包数据的最后面补上一小段校验码，叫作 **尾部**（trailer）。

假设这里用 TCP 来可靠运送 HTTP/1.1 请求（TCP 首部里会记下用来给字节排队的「序号」和回报收货进度的「确认号」，第 3 章会细讲）。沿着发送端一路向下，这条请求就像俄罗斯套娃一样越包越厚：

```text
HTTP 报文（应用层载荷）
  -> 加 TCP 首部：源/目的端口、序号、确认号等        （封装成 TCP 段）
  -> 加 IP 首部：源/目的 IP、跳数限制、上层协议编号等   （封装成 IP 数据报）
  -> 加以太网首部与尾部：源/目的 MAC、类型、差错校验码  （封装成以太网帧）
  -> 交由网卡物理层编码成电信号或无线电波发出
```

这就是完整的 **封装** 过程。值得注意的是，每一层把上面传下来的整块东西都当成自己不加过问的「货物」（常称为**载荷**，payload），只管填好自己的首部，再整体交给下一层。

当这串信号历尽跋涉抵达目标服务器网卡后，完全对称的逆过程开始了：

1. 网卡先核对以太网尾部的校验码确认没传坏，再看目的 MAC 确实是自己，便剥掉以太网首尾部；看一眼以太网首部的「类型」字段写着 IPv4，于是把里面的内容交给操作系统的 IP 模块。
2. IP 模块核对目的 IP 正是本机，剥掉 IP 首部；看一眼首部里的「协议」字段写着 TCP，于是交给 TCP 模块。
3. TCP 模块剥掉 TCP 首部，按序号理顺数据，再看一眼「目的端口」写着 80，便把最里层的原始 HTTP 报文准确投递给正在 80 端口守候的网页服务器程序。

把外层包装一层层剥掉的动作，叫作 **解封装**（decapsulation）；而每一层根据首部里的类型字段或端口号，在众多候选的上层模块或应用程序中精准挑出正确收件人的分拣动作，叫作 **解复用**（demultiplexing）。现在回头看开篇的那个疑问——「网线传来的是一长串 0 和 1，电脑凭什么分清该交给浏览器还是聊天软件？」——答案就藏在各层首部那些精准的「上层协议号」和「端口号」里，一环扣一环，严丝合缝。

不过，套娃也是要付邮费的。在不带额外可选字段的标准情况下，IPv4 首部通常占 20 字节，TCP 首部通常占 20 字节，以太网帧首尾部还会再占 18 字节——光是「信封」就已经吃掉 58 字节。如果你在聊天软件里只敲了一个「好」字发出去，控制信息占用的字节数比真正的内容高出几十倍；而当你下载一部几 GB 的高清电影时，每个数据包里装着一千多字节的有效载荷，几十字节的首部开销占比就微不足道了。这第一次让我们摸到了网络工程的铁律：**分层换来了清晰与灵活，代价是额外的首部字节与处理成本。**

看完了出发和抵达的两端，那数据包在广袤的互联网中间穿行时，沿途的路由器也要把这五层全都拆一遍吗？

## 每一跳到底发生了什么？

如果沿途的每一台路由器都必须认识 HTTP、聊天协议、游戏协议甚至还没发明出来的新应用，那整个互联网很快就会瘫痪。

幸好，真实的网络把「端点」和「中间节点」分得清清楚楚。像你的笔记本、手机、远方服务器这样位于网络边缘、真正产生和消费应用数据的设备，叫作 **端系统**（end system）；它们内部实现了从物理层到应用层的完整协作模块，合称 **协议栈**（protocol stack）。

而路上那些兢兢业业只管指路转运的普通路由器，根本不需要碰传输层和应用层——它们通常只实现最底下的物理层、链路层和网络层。当一个数据包抵达一台路由器时，路由器利落地执行四步接力：

1. **接收与检验**：从入口链路收到比特流，组装成帧并校验信号在上一跳链路中有没有出错。
2. **拆包读地址**：剥掉入口链路的帧首尾部，露出里面的 IP 数据报，读取其中的目的 IP 地址。
3. **查表选出口**：拿着目的 IP 地址去查路由器内部维护的一张「指路目录」（**转发表**，forwarding table），决定接下来该从哪一个物理端口送出去，以及下一站的相邻设备是谁。
4. **重新换装上路**：按照出口链路的技术规范（比如入口是局域网铜线，出口换成了骨干光纤），给同一个 IP 数据报套上全新的链路层首尾部（写上本路由器出口的源 MAC 和下一跳设备的目的 MAC），然后推上出口链路。

这一套动作揭示了一个极其关键的规律：**端到端的 IP 数据报在漫长旅途中基本保持着自己原本的源 IP 与目的 IP（像贴在包裹上始终不变的最终目的地地址），但每跨越一跳，外面的链路层帧都会被彻底剥掉重包，源/目的 MAC 地址也随之换成当前这一跳的两个相邻网卡。**

现在就能解释一个初学者常困惑的现象：当你从家里电脑访问远在地球另一端的服务器时，第一跳以太网帧里填的目的 MAC 地址，为什么并不是远方服务器的 MAC？因为你的电脑根本和那台服务器不在同一段局域网上，喊破喉咙对方的网卡也听不见。要走出本网络去往外面的世界，电脑必须先把数据交给家里的路由器——这台专门负责帮本网设备把跨网流量转出去的「大门卫」，叫作 **默认网关**（default gateway）。你的电脑在发出第一跳帧时，目的 IP 写的是远方服务器，但目的 MAC 写的其实是默认网关的网卡地址；后面每一跳，都依葫芦画瓢接力下去。

## 为什么偏偏需要这么多套名字和地址？

走到这里，我们已经凑齐了网络里最常见的四套标识符。把它们并排摆在一张表里，你会发现它们绝不是重复造轮子，而是各自守着不同的作用范围，在不同层级完成解复用：

| 标识符 | 作用范围 | 它回答的核心问题 |
| --- | --- | --- |
| **域名**（如 `example.com`） | 应用层与人类视角 | 我想访问哪一个好记的服务名称？ |
| **IP 地址** | 跨整个互联网 | 目标主机所在的网络接口位于哪一片网络？ |
| **端口号** | 单台主机内部 | 数据进了这台机器，该交给哪一个进程？ |
| **MAC 地址** | 当前这一段本地链路 | 眼前这一跳，把帧交给哪一块相邻网卡？ |

既然各有各的用场，它们之间自然需要「翻译官」来衔接：人记住的是域名，可网络层只认 IP 地址，因此第 2 章会介绍全网电话簿 [DNS](../chapter_02_application/02_dns.md) 如何把域名翻译成 IP；同理，电脑知道默认网关的 IP 地址，可要封装以太网帧时却必须填对方的 MAC 地址，这就需要局域网里的「现场问路」协议（第 6 章的[以太网、Wi-Fi 与 ARP](../chapter_05_link/02_ethernet_wifi_arp.md) 会专门讲 IPv4 里的 ARP 以及 IPv6 里的邻居发现机制）来把下一跳 IP 翻译成对应的网卡硬件地址。

## 分层的收益与代价

任何伟大的工程抽象都不是免费的午餐，分层设计同样是一笔精打细算的权衡。

先看它换来的巨大**收益**：

- **底层硬件自由演进**：链路技术可以从早期同轴电缆一路升级到千兆以太网、Wi-Fi 7、5G 甚至卫星链路，上面的 HTTP 和浏览器几乎不用改一行代码。
- **把异构世界粘成一体**：不管底层是哪家厂商、哪种物理介质，只要往上都支持统一的 IP 层，全世界风格迥异的局域网就能无缝互联成真正的「网络的网络」。
- **故障可分层定位**：网站打不开时，你可以像医生分科会诊一样逐层排查——先看物理网线亮不亮灯，再看能不能拿到 IP，再看端口连不连得上，不必一上来就怀疑是不是光纤断了。
- **跨厂商开放生态**：只要守住标准协议和接口，不同公司生产的路由器、手机、服务器和操作系统就能毫无障碍地对话。

再看它不得不付出的**代价**：

- **额外开销**：每一层都要加首部、做校验，在软件栈里有时还会引发多余的内存拷贝与处理开销。
- **信息隔离带来的盲区**：严格分层有时会把对上层很有用的信息藏起来。比如视频播放软件如果完全不知道底层无线信号正在剧烈波动，就很难及时降低画质以避免卡顿。
- **边界并非铁板一块**：为了追求更低的连接耗时和更好的性能，现代协议有时会主动打破传统分层边界，把原本分散在几层的职责揉进同一个设计中。比如第 3 章会见到的 [QUIC](../chapter_03_transport/01_udp_tcp.md)，就在单一协议里同时搞定了安全加密和在一条连接上并行承载多条互不阻塞的数据流。

## 历史与直觉：为什么让核心网络保持简单？

如果你把互联网和上个世纪的传统电话网放在一起对比，会发现两者走上了截然不同的哲学道路。传统电话网把大量聪明才智和状态管理都堆在电信局的交换机里，呼叫前先为你打通一条专属线路并全程照料；而互联网的奠基者们提出了一条影响深远的 **端到端原则**（end-to-end principle）：**把复杂的可靠性保障、数据重排、安全加密尽量放到网络边缘的端系统（你的电脑和服务器）去做，让网络核心的路由器保持尽可能简单、只管高速转发。**

这个看似「把脏活留给终端」的选择，却造就了互联网惊人的生命力。因为核心路由器不关心你在传什么应用，只要有人写出全新的程序——无论是当年的万维网、后来的视频直播，还是今天的 AI 智能体——只需要在两端的电脑上装好软件就能立刻跑遍全球，压根不需要说服全世界的电信运营商去升级每一台路由器。当然，硬币的另一面是：既然核心网络只承诺「尽力转发」，端系统就必须亲自扛起丢包、乱序、拥堵和安全防御的全部重担——这正是后面几章精彩故事的由来。

!!! question "随堂自测"
    当你从家里访问异地的一台服务器时，为什么抓包看到的以太网帧里，目的 MAC 地址通常不是那台远方服务器的 MAC 地址？

    因为 MAC 地址的作用范围只局限在眼前这一段本地链路。你的电脑和远方服务器并不直连，所以源主机只能把以太网帧的目的 MAC 填成负责转发跨网流量的**默认网关**（家里的路由器）；此后每跨越一跳，路由器都会剥掉旧帧，用新一段链路相邻设备的 MAC 地址重新封装，直到最后一跳的路由器才把目的 MAC 填成目标服务器自己的网卡地址。
