# 分层、封装与协议

假设你在同一台电脑开启了网页服务和聊天软件。网络收到一段数据，先要确认送到了哪台机器，再决定由哪个程序处理，程序还要知道这段数据在请求什么。两边事先约定数据怎么写、收到后怎么处理，这套约定叫作**协议**。把这些规则分工组织起来，就是**分层**。把下一层要看的信息包在原数据外面，称为**封装**。

## 寄出一句话，要给它加几种地址？

浏览器想发送 `GET /`，意思是「请把网站首页给我」。先按应用层的约定写下这句话，再写上目标程序的编号（**端口**）、要访问的机器地址（**IP 地址**），以及这一段连接送给哪张网卡的地址（**MAC 地址**）。如果第一站是一台中转设备（**路由器**），它会拆掉当前这层包装，看 IP 地址决定接下来送给哪个相邻设备。每送到一个相邻设备，就走了一**跳**。后文会把三种标记放到同一个例子里。

??? question "如果下一跳换了，应用请求一定要跟着重写吗？"

    换下一跳时，需要为这段连接换包装，`GET /` 本身可以保留。路径上若有替服务器接请求的[反向代理](../chapter_09_virtual_network/02_service_discovery_proxies.md)，它也可能读取或改写请求内容。

## 为什么需要分层

假设浏览器必须同时知道网页请求的含义、路径上何时该减速、数据该往哪走、无线信号如何重发以及网卡如何发出信号，任何一次硬件更新都会迫使浏览器重写。分层的动机，就是把变化限制在局部：上层只依赖下层承诺的服务，不依赖其全部实现细节。

这里要区分三个词：

- **协议**：同一层的通信实体遵循的消息格式、顺序和动作规则。
- **服务**：下层向上层提供的能力，例如「尝试把这个包交过去」或「让程序按发送顺序读到连续字节」。
- **接口**：上层使用服务的具体入口，例如应用程序通过 [Socket（套接字）](../chapter_02_application/04_socket_and_listening.md)请操作系统收发数据。

协议像两家快递网点之间的作业规范，服务像它们向顾客承诺的寄送能力，接口则是下单柜台。顾客不必知道每个中转站如何排班，但必须知道服务是否保价、是否限重。

## TCP/IP 与 OSI 模型

在已经认识的三份工作之外，还要有人负责把 `0` 和 `1` 变成线缆或无线信号。下面用五层 **TCP/IP 模型**整理这些工作，名字来自互联网里常用的 TCP 和 IP 协议。另一种常见的 **OSI 模型**把相同领域的工作分成七层。这里先看每层职责，表中协议名可沿链接继续读。

| TCP/IP 五层 | 代表协议或技术 | 核心职责 | 常见数据单位 |
| --- | --- | --- | --- |
| 应用层 | [HTTP](../chapter_02_application/01_http_https.md)、[DNS](../chapter_02_application/02_dns.md) | 约定应用发什么请求、怎样回答 | 报文，也就是写给应用的一条消息 |
| 传输层 | [TCP、UDP](../chapter_03_transport/01_udp_tcp.md) | 把数据交给正确的运行中程序 | TCP 段或 UDP 数据报 |
| 网络层 | [IPv4](../chapter_04_network/01_ip_addressing_subnetting.md)、[IPv6](../chapter_04_network/02_ipv6_nat_icmp.md) | 用 IP 地址标明目的地，跨网络转发 | IP 数据报，即一个 IP 包 |
| 链路层 | Ethernet、Wi-Fi | 同一链路上的一跳交付 | 帧 |
| 物理层 | 光纤、双绞线、无线电 | 传输比特信号 | 比特 |

OSI 额外把管理会话、转换和保护数据格式等工作分到单独的层。五层模型中，这些工作经常由应用依赖的软件库完成，例如由 [TLS](../chapter_06_security/01_tls.md) 库保护网页登录时的数据。模型帮我们分辨职责，实现可以把几类工作放进同一模块。

## 最小完整例子：发送一个 HTTP 请求

浏览器准备发送下面这条 [HTTP 请求](../chapter_02_application/01_http_https.md)。`GET /index.html` 表示要读取这个路径对应的内容，`Host` 指明要访问的网站名称。

```http
GET /index.html HTTP/1.1
Host: example.com
```

用 TCP 运送 HTTP/1.1 请求时，每层会在前面写一段自己的说明（**首部**），以太网还在末尾加上校验信息（**尾部**）。TCP 首部中的序号用于给数据编号，确认用于告诉发送方收到了哪里。沿着请求看发送端加了什么：

```text
HTTP 报文
  -> 加 TCP 首部：源/目的端口、序号、确认等
  -> 加 IP 首部：源/目的 IP、跳数限制等
  -> 加以太网首尾部：源/目的 MAC、类型、校验等
  -> 编码成物理信号
```

这个过程叫**封装**。接收端根据首部中的类型字段逐层交付：以太网帧指出上层是 IPv4 或 IPv6，IP 首部指出上层是 TCP，TCP 的目的端口帮助操作系统找到服务器进程。去掉各层包装叫作**解封装**。根据包上的编号把它交给多个候选程序中的正确一个，叫作**解复用**。

若暂不考虑可选字段，IPv4 首部通常至少 20 字节，TCP 首部通常至少 20 字节。应用只发送几十字节时，控制信息占比很高；发送大文件时，这些固定开销的占比下降。这说明分层带来模块化，也带来额外字节和处理成本。

## 每一跳都会发生什么

通信两端的设备（**端系统**）通常处理从网卡到应用的全部层次，这些一起工作的协议称为**协议栈**。普通路由器只为下一站转发，主要查看链路层和网络层：

1. 路由器从入链路收到一个帧并验证链路层信息。
2. 去掉入链路帧首尾部，读取 IP 目的地址。
3. 查询转发表，选择出接口和下一跳。
4. 为出链路重新封装新的链路层帧。

因此，端到端 IP 数据报在途中原则上保持其网络层身份，但每一跳的链路层帧会变化。访问另一张网络时，第一站往往是负责把数据转出本网络的路由器，称为**默认网关**。源主机在以太网帧中填的是这台路由器的 MAC。

## 标识符为什么有多套

| 标识符 | 作用范围 | 回答的问题 |
| --- | --- | --- |
| 域名 | 应用与人类可读命名 | 想访问哪个服务名称 |
| IP 地址 | 跨网络 | 目标接口位于哪个网络 |
| 端口号 | 单台主机 | 交给哪个进程或 Socket |
| MAC 地址 | 本地链路 | 这一跳交给哪个网卡 |

它们不是重复设计，而是在不同范围内完成不同的解复用。DNS 把域名映射到 IP；ARP 或 IPv6 邻居发现把本地下一跳 IP 解析为链路层地址。

## 分层的收益与代价

收益包括：

- 可以独立替换链路技术，HTTP 不必关心底层是 Wi-Fi 还是光纤。
- 统一的 IP 层把异构网络连接成“网络的网络”。
- 故障可分层定位，应用错误不必先怀疑电气信号。
- 标准接口允许不同厂商实现互操作。

代价包括：

- 多层首部、重复校验和数据复制增加开销。
- 严格分层可能隐藏有用信息。例如应用若完全不知道网络状况，就难以自适应码率。
- 实现也可以合并一些层次的工作。[QUIC](../chapter_03_transport/01_udp_tcp.md)可以同时处理数据保护和携带多条独立的数据流，其中各条数据流可各自交付。

## 历史与直觉

电话网更强调连接建立和网络内部状态；互联网的端到端思想倾向于把复杂可靠性放在端系统，让核心网络保持相对简单。这个选择使新应用可以在不改造所有路由器的情况下部署，但也意味着端系统必须面对丢包、乱序和安全等问题。

!!! question "自测"
    访问异地服务器时，为什么以太网帧里的目的 MAC 通常不是服务器的 MAC？

    因为 MAC 地址只服务于当前链路。源主机先把帧交给本地默认网关；路由器每经过一跳都会用新链路的地址重新封装。
