# HTTP 与 HTTPS

当你在浏览器地址栏敲下一个网址并按下回车，你电脑上的浏览器和千里之外的服务器可能由完全不同的公司用不同的语言写成——一个跑在手机的移动系统上，一个跑在 Linux 机房里。它们凭什么能听懂彼此说的「请把首页给我」「找到了，这是正文」「不好意思，这个页面已经删了」？

靠的就是一套双方严格遵守的应用层对话规则——**超文本传输协议**（HTTP，HyperText Transfer Protocol）。而当这份对话不再裸奔在公共网络上，而是放进一条由第 7 章会细讲的 [TLS](../chapter_06_security/01_tls.md) 协议建立的加密通道里传输时，它就变成了我们每天在地址栏里看到的小锁标志：**HTTPS**。

HTTP 的核心思想其实非常直白，但哪怕是两个最寻常的数字——`200` 和 `404`——背后也藏着整个网络分层的排查智慧。让我们先从这个最贴近日常的现象切入。

## 同一个服务，返回 200 和 404 时，底层的路通了吗？

假设你在本机或远端运行着一个极简网页服务，然后分别请求首页 `/` 和一个压根不存在的路径 `/missing`。前者让你看到了漂亮的网页，状态码是 `200`；后者屏幕上冷冰冰地显示 `404 Not Found`。

很多人遇到 `404` 时下意识会觉得「网络出故障了」，但沿着上一章的分层视角往下一照，事实恰恰相反：**能收到 `404`，恰恰证明你的网络一路绿灯！** 无论是请求 `/` 还是 `/missing`，浏览器都顺利完成了地址解析、穿越沿途路由器、和目标服务器建立好了连接，并且把请求原封不动地递进了网页服务进程的手里。两者的唯一分歧发生在最顶层的应用逻辑里：服务进程去磁盘或路由表里翻找 `/` 时找到了内容，于是礼貌地回一个 `200` 并附上正文；翻找 `/missing` 时扑了个空，于是同样礼貌地回一个 `404` 告诉你「人我找着了，但你要的东西真没有」。

这一区分在工程排障里价值连城：看到 `404`，别去重启路由器或怀疑网线，直接查 URL 路径拼写、代理转发规则和服务器上的资源目录；反过来，如果连状态码都收不到，屏幕提示「连接被拒绝」或「超时」，说明请求压根没摸到应用层的门槛，问题出在更底下的 DNS、路由、防火墙或服务压根没启动。

??? question "发出一条提交订单的 `POST` 请求后，页面一直转圈直到超时，能放心推断「服务器一定没扣款」吗？"

    千万不能！超时只代表「客户端在规定时间内没等来回应」，至于半路出了什么事，至少有三种可能：请求根本没送到服务器、请求送到了且服务器已经完成扣款但响应半路丢了、或者服务器正在慢吞吞地处理中。如果涉及扣款、发券这类有真实副作用的操作，绝不能盲目重发，而应当先查询状态，或配合应用层设计的**幂等键**（用来唯一标记同一次业务操作的编号）安全重试。

弄清了应用层和底层的界线，我们再回到起点：浏览器发出的第一条请求里，那串看似杂乱的网址究竟在传达哪些信息？

## 动机与网址解剖：让全世界软件用同一种语言谈资源

Web 诞生之初面对的是一片高度异构的计算机世界：客户端可能是任何操作系统上的任何浏览器或脚本，服务器也可能是任何语言写的后端。为了让彼此毫不相识的双方无需共享代码就能顺畅协作，HTTP 做出了一个简洁而优雅的抽象——把网上的一切内容（网页、图片、接口数据、文件）都视作**资源**（resource），并统一规定了「怎么给资源起名」「怎么表达对资源的动作」「怎么汇报执行结果」。

拿一个完整的 URL 为例：`https://www.example.com:443/docs/index.html?lang=zh#intro`。别被它长长的外表吓到，拆成六段之后，每一段都在给不同环节递纸条：

| 组成部分 | 示例值 | 谁在看它、起什么作用 |
| --- | --- | --- |
| **协议方案**（scheme） | `https` | 告诉浏览器走什么协议、要不要启用 TLS 加密 |
| **主机名**（host） | `www.example.com` | 目标服务器的名字，通常交给下一节的 DNS 翻译成 IP 地址 |
| **端口**（port） | `443` | 机器上服务的「房间号」；不写时按默认约定（HTTP 默认 80，HTTPS 默认 443） |
| **路径**（path） | `/docs/index.html` | 指明想要访问这台服务器上的哪一份具体资源 |
| **查询参数**（query） | `lang=zh` | 附带给服务器的筛选或动作参数，例如要求返回中文版 |
| **片段标识**（fragment） | `intro` | **不会发给服务器！** 只留给浏览器在拿到网页后自动滚动到 `#intro` 那个标题位置 |

注意最后一行这个常常让人意外的细节：`#intro` 只是浏览器本地的「书签坐标」，真正的 HTTP 请求报文里根本不包含它。

那么，浏览器拆解完 URL、连上服务器之后，真正顺着连接发过去的那封「信」长什么样呢？

## 最小完整例子：一次 HTTP/1.1 的真实对话

在 HTTP/1.1 里，一次完整的请求和响应甚至可以直接用肉眼读懂。浏览器发给服务器的请求报文看起来像这样：

```http
GET /hello HTTP/1.1
Host: example.com
Accept: text/html
Connection: keep-alive
```

服务器读懂后，立刻回发一封结构高度对称的响应报文：

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 15
Cache-Control: max-age=60

<h1>Hello!</h1>
```

细看这两段纯文本，每一块都井井有条：

- **第一行（起始行）**开门见山：请求里写清「动作 + 目标路径 + 协议版本」（我要用 HTTP/1.1 获取 `/hello`）；响应里写清「协议版本 + 状态码 + 简短说明」（没问题，200 OK）。
- **中间几行（首部，headers）**是键值对形式的元数据：比如 `Host` 告诉服务器我要找托管在这台机器上的哪个网站（一台物理机往往同时挂着几十个域名）；`Content-Type` 告诉浏览器后面跟着的是 UTF-8 编码的网页源码而不是图片；`Content-Length: 15` 明确标出正文正好 15 个字节，让浏览器知道读到哪里算收完；`Cache-Control: max-age=60` 则是嘱咐浏览器「60 秒内直接用你本地存的就行，别反复来问我」。
- **一个空行**作为严格分界线，空行之后才是可选的**消息体**（body）——在这里就是那段 15 字节的 `<h1>Hello!</h1>`。

顺带一提，较新的 HTTP/2 和 HTTP/3 为了省流量和提速，在真实线路上不再传输这些纯文本，而是压缩编码成紧凑的二进制帧；但它们并没有推翻 HTTP 的灵魂——请求方法、路径、状态码和首部语义完完整整地延续了下来。

读懂了报文骨架，接下来有两个业务开发最常踩坑的核心概念：请求方法该怎么挑，以及为什么网络超时会让「重试」变得步步惊心？

## 方法、状态码与幂等性

在请求第一行里，HTTP 用不同的**方法**（method）表达意图，其中最常见的五个各有分工：

- `GET`：只读地获取资源，不该悄悄改变服务器状态；
- `HEAD`：和 `GET` 一样，但只要响应首部、不要正文（常用来探测文件存不存在、有多大、有没有更新）；
- `POST`：向服务器提交数据，常用于新建订单、发表评论、触发一项业务处理；
- `PUT`：用你发过去的完整内容去创建或整体替换某个目标资源；
- `DELETE`：请求删除指定资源。

服务器则用三位数字的**状态码**（status code）快速定性结果：首位 `2xx` 代表成功（如 `200 OK`、`201 Created`）；`3xx` 代表资源搬家了或没变化，需要重定向或读缓存（如 `301`、`302`、`304`）；`4xx` 说明问题出在客户端请求侧（如 `400` 格式错、`401/403` 没登录或没权限、`404` 找不到）；`5xx` 则说明请求本身没毛病，是服务器内部崩了或扛不住了（如 `500`、`502`、`503`）。

这些方法背后藏着一个分布式系统里极其关键的性质——**幂等性**（idempotency）：**把同一个请求执行 1 次和不小心重复执行 10 次，对服务器最终状态产生的影响是否完全一样？**

试着拿这个标准量一量上面五个方法：反复 `GET` 查余额，查十次余额也不会变；反复 `PUT` 把收货地址设为「北京海淀」，设十次结果还是「北京海淀」；反复 `DELETE` 删除同一条草稿，删完后草稿就是不存在了。所以 `GET`、`HEAD`、`PUT`、`DELETE` 在设计上都追求幂等。但 `POST` 提交一笔「给张三转 100 元」的请求呢？如果不做保护，点一次扣 100，超时后浏览器或重试框架自作聪明再重发一次，就会活生生扣掉 200 元！

正因为真实网络随时可能丢包超时、让发送方陷入「到底成没成」的盲区，现代支付与下单接口通常要求客户端为每笔业务生成一个唯一的 **幂等键**（idempotency key）放在请求首部里。万一超时重试，服务器一看还是同一个幂等键，就知道「这是刚才那笔单子的重发」，直接把上次的结果原样返回，绝不重复扣款。

聊完单次请求，下一个生活体验立刻冒了出来：HTTP 每发完一次响应就算了结，那为什么你在电商网站登录之后，点进商品页、加入购物车、去结算，网站始终记得你是谁？

## 无状态、Cookie 与会话：网站怎么记住我是谁？

HTTP 从诞生起就刻意设计成一种 **无状态**（stateless）协议：服务器处理每一个新请求时，默认把它当成一张白纸，不会仅仅因为「它来自刚才同一条 TCP 连接」就假定这是同一个人。

为什么要这么「健忘」？试想一台热门网站服务器每秒要应付几万名访客，其中大多数人扫一眼文章就关掉标签页。如果服务器在协议层被迫死记每个人的浏览历史，内存很快就会被海量半途走掉的访客撑爆，而且一旦后台部署了十台服务器分摊流量，用户下一个请求落到另一台机器上，状态全丢。无状态让服务器极其轻盈、随时可以横向扩容。

可登录态、购物车和偏好设置又是实打实的刚需。既然协议本身不记账，应用层就想出了一个巧妙的外挂——**Cookie**（曲奇饼干，常喻指服务器塞给浏览器随身带着的小凭证）。整个「认人」流程只有一来一回：

```text
1. 用户输入账号密码登录成功
2. 服务器在响应首部塞进一张凭证：
   Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Lax
3. 浏览器默默收好，此后每次再向该网站发请求，都自动在请求首部亮出它：
   Cookie: session=abc
```

服务器收到 `session=abc` 后，去后台共享的会话存储里一查，就知道「哦，这是刚才登录过的 Alice」。当然，随身带凭证也立刻招来偷窥和冒用的风险，所以那三个附加属性绝不是摆设：

- `Secure` 规定浏览器**只能**在加密的 HTTPS 连接上发送这块 Cookie，绝不许在明文 HTTP 里裸传；
- `HttpOnly` 禁止页面上的 JavaScript 脚本读取这块 Cookie，就算网页不小心中了恶意脚本注入，黑客也偷不走登录凭证；
- `SameSite` 限制从其他第三方网站跳转或发起请求时自动携带 Cookie，大幅缓解「坏网站借你的登录身份偷偷发转账请求」（跨站请求伪造）的风险。

三道门锁各有侧重、互为补充，没有哪一个是能一劳永逸的万能开关。

解决了「怎么说话」和「怎么认人」之后，随着现代网页变得越来越华丽——打开一个首页动辄要加载上百张图片、样式表和脚本——HTTP 撞上了一堵厚厚的性能高墙。于是，一场跨越三十年的版本演进拉开了大幕。

## 从 HTTP/1.0 到 HTTP/3：一场与延迟和阻塞的拉锯战

如果你把 HTTP 四个主要版本的演进串成一条因果链，就会发现每一次升级都不是为了推翻 `GET` 和 `200`，而是为了解决上一代留下的**性能痛点**：

1. **HTTP/1.0 的痛点：一图一连接，握手累死人。** 早期 HTTP/1.0 默认每拉取一个资源（HTML、每张小图标、每段脚本）就新建一条 TCP 连接，传完立刻拆掉。每次建连都要来回握手，加载一个含 50 张小图的页面得白白浪费几十个往返时延。
2. **HTTP/1.1 的改进与新痛点：持久连接撞上应用层队头阻塞。** HTTP/1.1 默认启用 **持久连接**（persistent connection，`Connection: keep-alive`），让多个请求排着队复用同一条连接。可好景不长，新麻烦冒出来了：在同一条连接上，响应必须严格按照请求的顺序依次返回。万一排在第一个的接口查询数据库卡了 2 秒，排在它后面早就准备好的十张小图片也只能死死干等——这就是臭名昭著的 **队头阻塞**（head-of-line blocking）。浏览器被逼无奈，只好对同一个域名同时硬开 6 条左右的并行 TCP 连接来「曲线救国」。
3. **HTTP/2 的改进与新痛点：二进制多路复用，却仍被 TCP 绊住脚。** HTTP/2 彻底换用二进制帧，在**同一条** TCP 连接里切出许多逻辑上独立的「流」（stream），允许不同请求和响应的帧交错穿插传输（**多路复用**，multiplexing），顺便还把重复冗长的首部做了专门压缩。应用层的队头阻塞确实消除了——慢接口不再挡住快图片的路。可别忘了，这所有流底下还是合用**同一条 TCP 字节流**！只要网络上恰好丢了某一个 TCP 数据包，按照 TCP「必须严格按顺序把字节交给上层」的铁律，就算其他流的包已经全部安然抵达，TCP 也必须把它们统统扣在缓冲区里，直到丢掉的那个包重传回来为止。队头阻塞从应用层下沉到了传输层。
4. **HTTP/3 的终极解法：换掉底座，搬到 QUIC 上。** 既然症结在 TCP 的单一有序字节流，HTTP/3 干脆把底层的 TCP 换成了基于 UDP 构建的新传输协议 [QUIC](../chapter_03_transport/01_udp_tcp.md)。QUIC 原生理解「多条独立的流」，某条流丢了一个包，只暂停那一条流等重传，其他流照常丝滑交付；同时它把连接建立和 TLS 加密握手合并在一起，进一步削减了首次访问的往返耗时。

当然，工程世界永远没有免费的午餐：从纯文本的 HTTP/1.1 一路演进到二进制加密的 HTTP/3，换来了显著的延迟下降和弱网韧性，代价则是协议实现变重、抓包调试门槛变高，而且还要克服路上一些老旧防火墙对 UDP 流量不友好的兼容性阻力。

除了把传输管道越修越顺，还有没有一种更极致的加速方式——干脆「根本不发请求，或者只确认一眼没变就不重传正文」？

## 缓存为何既快又难

答案就是 **缓存**（caching）：世界上最快的网络请求，就是根本不需要跨网发出去的那一次。

如果一张网站 Logo 或一份静态脚本已经下载过，每次刷新页面都要千里迢迢重新传一遍，既拖慢用户体验又白白烧掉服务器带宽。于是 HTTP 内置了一套精巧的缓存协商机制：

- **强缓存（新鲜期）**：服务器在响应里贴一张保质期标签，例如 `Cache-Control: max-age=60`。在 60 秒之内，浏览器连问都不用问服务器，直接从本地磁盘秒开副本。
- **协商缓存（条件验证）**：过了 60 秒保质期，内容未必真的改过。服务器当初还可以顺手附上一个代表内容版本的指纹标签 `ETag`（Entity Tag）。浏览器再次请求时，会把旧指纹捎给服务器问一句：「我手头这份还是最新版吗？」如果服务器一比对发现纹丝未动，就只回一个极其袖珍的 `304 Not Modified`（没有正文！），浏览器收到后放心地继续使用本地缓存，省去了大块数据的重复传输。

听上去美妙绝伦，可为什么老练的工程师一提到缓存总是如履薄冰？因为缓存永远伴随一个如影随形的阴影——**一致性与安全边界**。如果缓存规则没把「用户语言」「压缩编码」甚至「登录身份」算进区分缓存的钥匙（缓存键）里，就可能把英文版错塞给中文用户；更可怕的是，一旦某份包含个人隐私账单的响应被手误标成了允许中间代理共享的公共缓存，张三的敏感信息就会活生生地展示在李四的屏幕上！因此，每一份资源能不能缓存、存多久、过期怎么验证，都必须紧贴业务属性仔细拿捏。

## HTTPS 多了什么，又没藏住什么？

把上面这套明文 HTTP 装进 TLS 加密壳子里，就成了今天的默认标配 **HTTPS**。它一口气为脆弱的公共网络补齐了三根安全支柱：

1. **机密性**（confidentiality）：数据包在路上全变成密文，咖啡馆 Wi-Fi 旁边的窃听者看不懂你搜索了什么、提交了什么密码。
2. **完整性**（integrity）：哪怕中途有人偷偷改动了一个比特，接收端在校验时立刻就能识破并丢弃，杜绝「半路插广告、改转账账号」。
3. **服务器身份认证**（authentication）：浏览器通过核验数字证书链和证书里写的主机名，确认对面真的是货真价实的银行网站，而不是冒牌钓鱼站点。

但同时也要保持一份清醒：**HTTPS 不是隐身斗篷。** 它不担保对面网站本身是个良心商家（骗子网站也能轻易申请到合法的 HTTPS 证书）；此外，即便正文全加密了，沿途的观察者通常仍然能看到你连接了哪个目标 IP、什么时候发了请求、一共传了多少字节的数据，甚至在某些配置下还能从握手的明文提示里看到你访问的域名。关于 TLS 如何凭空在互不相识的两端建立起这层信任，第 7 章[ TLS 与可信连接](../chapter_06_security/01_tls.md)会带你完整推演。

## 亲手观察一次真实对话

纸上读十遍，不如在终端里亲眼看一次真实报文。打开命令行敲下这两条命令：

```bash
curl -v https://example.com/
curl -I https://example.com/
```

第一条 `-v`（verbose）会把幕后细节一览无余地摊开给你看：先解析出什么 IP 地址、TCP 连没连上、TLS 证书核验过没过、发出去的 `>` 请求首部是什么、收到的 `<` 响应状态码和首部又是什么；第二条 `-I` 则发送 `HEAD` 请求，只利落地拉取响应首部。以后再遇到「网站打不开」，别再含糊地说「挂了」，用 `curl -v` 走一遍，立刻就能精确报出是死在「解析域名」「TCP 建连」「TLS 握手」还是「HTTP 502」。

!!! question "随堂自测"
    HTTP/2 已经在单条连接里实现了多路复用，为什么说它并没有彻底消除队头阻塞？

    HTTP/2 确实彻底解决了 HTTP/1.1 中「应用层响应必须按请求顺序排队」的队头阻塞，不同资源的二进制帧可以交错发送。但它底下依然跑在**单一一条 TCP 连接**之上，而 TCP 承诺向应用层交付严格按序的字节流。一旦网络丢了某一个承载 A 流数据的 TCP 段，哪怕 B 流和 C 流的数据早就平安到达对端网卡，TCP 协议栈也必须把它们暂时扣在接收缓冲区里干等，直到丢掉的那个段重传补齐才能一并上交——队头阻塞只是从应用层转移到了传输层。

---

回头再看刚才那段 HTTP 请求里的 `Host: example.com`，或者 `curl -v` 输出的第一行——你会发现，HTTP 世界里到处都是人类友好的英文域名，可第 1 章已经告诉我们，沿途路由器只认冰冷的数字 IP 地址。那么，电脑究竟是怎样在几毫秒内把 `example.com` 翻译成一串 IP 地址的？更奇怪的是，为什么服务器明明已经搬去新 IP 了，有时候你的电脑却依然固执地连向旧地址？下一节，我们推开互联网电话簿 **DNS** 的大门。
