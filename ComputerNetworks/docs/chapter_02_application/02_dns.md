# DNS

几乎没人能顺口背出常用网站的 IP 地址，但大家都能轻松记住 `example.com`。更重要的是，服务器迟早要扩容、迁移机房甚至更换云厂商——机器背后的 IP 地址随时可能变动，而印在名片和用户脑海里的网站名字却希望十年不变。

负责在「稳定的名字」和「可变的网络地址」之间搭起桥梁的，正是互联网最基础的公共目录——**域名系统**（DNS，Domain Name System）。你只要问它一句「`example.com` 现在住在哪里？」，它就会查出一张当前可用的地址清单交给你。

听起来就像查一本在线电话簿，可实际工程里，很多开发者和运维工程师第一次亲手上线网站时，几乎都会撞上一个令人抓狂的怪现象：明明已经把服务器换到了新 IP，配置后台也保存成功了，为什么刷新浏览器，流量依然固执地往老机器上跑？我们就从这个真实困惑出发，把 DNS 的设计精髓一层层拆开。

## 服务器已经换了地址，为什么我还连到旧的？

让我们把时间轴放慢来看。假设你公司负责替大家查域名的解析器，在中午 `12:00:00` 查了一次 `api.example.test`，拿到的答案是 `192.0.2.10`。随答案一起附带的，还有一张有效期小票，上面写着「60 秒内放心直接用，不用再来问我」——这个缓存有效期就叫作 **生存时间**（TTL，Time to Live）。

过了短短 20 秒，在 `12:00:20`，运维工程师完成了服务器迁移，把权威后台里的地址改成了新机器 `192.0.2.12`。可在接下来的 40 秒里，只要有用户去问那台解析器，解析器一看自己手头的旧纸条还没到 `12:01:00` 的过期时间，根本不会大老远跑去上游核实，而是直接把缓存里的 `192.0.2.10` 报给了用户！直到 `12:01:00` 旧条目自然失效之后，下一次查询才会真正触发向上游拉取新地址。

原来如此！并不是 DNS「失灵」了，而是它在刻意做一笔划算的交易：**牺牲一小段时间的新鲜度（TTL 窗口），换取成百上千倍的查询加速，并替上游服务器挡掉海量重复请求。**

??? question "既然如此，我在切换服务器那一瞬间把后台的 TTL 改成 1 秒，能立刻清掉外面已经缓存的旧结果吗？"

    不能！世界各地已经拿到旧记录的解析器，当时记下的还是旧的 TTL（比如 3600 秒），在旧记录到期前它们压根不会回来问你，自然也看不到你刚改的「1 秒」。因此老练的运维在做计划迁移时，都会**提前**（至少早于旧 TTL 的时长）把 TTL 调小（例如降到 60 秒），耐心等全网旧缓存陆续自然过期并换上短 TTL 后，再动手切换 IP。

明白了 TTL 的时间账，我们再把镜头拉远到全球尺度：全世界有数亿个域名、几十亿台设备每天发起数万亿次查询，这本「全球电话簿」究竟是怎么存放、怎么做到既不崩又极快的？

## 动机：为什么不能把全网名单放在一台超级服务器里？

最直觉的做法，当然是找一台性能怪兽级的中央服务器，把全世界所有域名和 IP 的对照表存成一个大文件（互联网刚起步、全网只有几百台主机时，人们确实就是靠一份名为 `HOSTS.TXT` 的文本文件这么干的）。

可一旦互联网扩张到亿级规模，这种集中式方案会瞬间在四个方向上同时撞墙：

- **单点故障**：这台机器一断电或挨打，全世界的网址一秒全盲；
- **流量爆炸**：全球几十亿设备同时问它，带宽和 CPU 根本扛不住；
- **地理延迟**：无论把这台机房建在纽约还是北京，地球另一端的用户每次点链接都要先跨洋跑一个来回；
- **管理噩梦**：地球上每秒钟都有人在注册新域名、修改子域名，中央管理员根本审核不过来。

DNS 给出的解法堪称分布式系统设计的教科书：**层次化、分布式数据库，再叠加层层缓存。** 它把域名按树状结构划分领地，每一级只负责记住「下面一块领地归哪几台服务器管」，把具体管理权层层委派（delegation）给各个组织自己维护。

仔细看一个域名：`www.example.com.`。很多人没注意过，域名其实是**从右往左**由大到小展开层次的：最右边那个平时习惯省略的小点 `.` 代表整个域名树的 **根域**（root）；往左一级 `.com` 是 **顶级域**（TLD，Top-Level Domain）；再往左 `example.com` 是某个组织申请下来的权威域；最左边的 `www` 则是该组织内部划分出的具体主机或服务名。谁的地盘谁做主，彻底告别了中央大管家。

那么，当你第一次访问一个从未去过的网站时，电脑究竟怎样顺着这棵倒挂的大树把 IP 一步步找出来？

## 最小完整解析过程：谁替你跑腿，谁只管指路？

假设浏览器首次访问 `www.example.com`，而且你电脑本地和上游解析器里都碰巧没有任何缓存。一场环环相扣的「六步寻址」立刻展开：

1. **交给本地跑腿入口**：浏览器向操作系统内置的 **存根解析器**（stub resolver）发起询问。存根解析器非常轻量，自己并不懂怎么遍历全球域名树，只负责把问题转交给配置好的「专业代办」。
2. **委托专业代办**：存根解析器把查询发给运营商、公司内网或公共服务（如 `8.8.8.8`、`1.1.1.1`）提供的 **递归解析器**（recursive resolver）。对你的电脑来说，这一步是一次「甩手掌柜式」的委托——你只管等最终答案。
3. **问根服务器**：递归解析器先去问全球分布的 **根服务器**（root server）：「请问 `www.example.com` 在哪？」根服务器并不存具体网站的 IP，它只回一句转介：「`.com` 归这几台顶级域服务器管，你去问它们。」
4. **问顶级域服务器**：递归解析器转头去问 `.com` **顶级域服务器**（TLD server）。后者同样不记具体主机 IP，只给出下一级转介：「`example.com` 这个域归这几台权威服务器管，找它们去。」
5. **问权威服务器**：递归解析器最后敲开 `example.com` 的 **权威名称服务器**（authoritative name server）的大门。这里是真正掌管 `example.com` 账本的主人，它立刻查出 `www.example.com` 当前的 IP 地址记录交出来。
6. **入库缓存并返回**：递归解析器拿到最终答案，按记录附带的 TTL 存进自己的缓存里造福后续查询同一网站的其他用户，同时把结果交回给你的存根解析器和浏览器。

把第 2 步和第 3–5 步放在一起对比，你就彻底看懂了 DNS 里最常考的一对概念：
- 你的电脑发给递归解析器的是 **递归查询**（recursive query）：「帮我查到底，直接给我最终答案！」
- 递归解析器依次向根、顶级域、权威服务器发出的通常是 **迭代查询**（iterative query）：「你知道答案吗？不知道的话，告诉我下一站该问谁就行，我自己跑下一趟。」

正因为有了递归解析器集中替成千上万用户跑腿并共享缓存，全网绝大多数查询在第 2 步就直接在缓存里命中返回了，根本不用每次都去打扰远方的根服务器和权威服务器。

## 常见资源记录：DNS 不止会存 IPv4 地址

很多人以为 DNS 表里只有「域名 → IPv4 地址」这一种条目，其实它的账本里存着许多不同类别的 **资源记录**（resource record，RR），每条记录都带着名字、类型、值和 TTL：

| 记录类型 | 它回答什么问题 | 典型应用场景 |
| --- | --- | --- |
| `A` | 这个名字对应的 IPv4 地址是什么？ | 指向 Web 服务器的 IPv4 地址 |
| `AAAA` | 这个名字对应的 IPv6 地址是什么？ | 指向支持 IPv6 的服务器地址 |
| `CNAME` | 这个名字其实是哪个正式名字的「别名」？ | 把业务域名 `static.example.com` 指向 CDN 服务商的调度域名 |
| `MX` | 发给这个域名的电子邮件，该投给哪台邮件服务器（含优先级）？ | 邮件系统的投递入口 |
| `NS` | 这一片子域名具体由哪几台权威名称服务器掌管？ | 实现域名树的逐级委派 |
| `TXT` | 附带一段纯文本声明或校验串 | 配置反垃圾邮件策略（如 SPF）或证明域名所有权 |
| `PTR` | 已知一个 IP 地址，反查它对应的域名是什么？ | 运维日志排查、邮件服务器反查信誉验证 |

值得留心的是，DNS 返回给你的常常是一组记录，而不是孤零零的一个地址。权威服务器甚至可以非常聪明地「看人下菜碟」——根据查询来源的地理位置、机房实时负载和节点健康状态，给上海用户返回上海机房的 IP，给法兰克福用户返回欧洲机房的 IP；如果目标支持双栈，客户端还会同时拿到 `A` 和 `AAAA` 两条记录，然后并行或择优试连，谁快用谁。

## 缓存的收益与代价：为什么「改了记录还没生效」？

前面开篇的 TTL 故事，其实只掀开了缓存冰山的一角。在真实设备访问网站的路径上，旧的 DNS 结果可能同时藏在好几个抽屉里：

1. **浏览器自带的 DNS 缓存**（为了连点站内链接时连系统调用都省掉）；
2. **操作系统的本地解析缓存**（供本机所有进程共用）；
3. **局域网路由器或企业内网的转发缓存**；
4. **上游递归解析器的公共缓存**；
5. **某些长驻应用程序自己在内存里死死缓存下来的旧 IP**（比如某些服务端代码只在启动时解析一次域名，此后只要不重启就永远连旧机器）。

此外，DNS 甚至连「查无此人」（`NXDOMAIN`）的否定结果也会短暂缓存起来，称为 **负缓存**（negative caching）。想象如果有人拼错了一个不存在的域名、或者恶意脚本高频查询随机乱码域名，没有负缓存的话，每次都会穿透直击权威服务器把它问垮。

因此，TTL 的设定永远是一场权衡：TTL 设得长（比如几小时甚至一天），缓存命中率高、查询极快、权威服务器清闲，但突发故障切机房时恢复极慢；TTL 设得短（比如 30 秒），切流量极其敏捷，却会成倍放大解析延迟与权威查询压力。

## 传输方式与加密 DNS：为什么平时走 UDP，有时却换 TCP？

翻开协议栈往下一层看，传统的 DNS 查询默认敲开目标服务器的 **53 号端口**，并且优先选用轻巧的 **UDP** 协议：客户端发一个小数据包问一句，服务器回一个小数据包答一句，不需要像 TCP 那样先来回握手建连，一趟往返就能搞定，开销极低。

不过，UDP 并不包打天下。早年经典 DNS 报文在 UDP 上的传统上限很小，即便后来引入了扩展机制允许承载更大的 UDP 响应，但一旦响应内容塞得太满（比如带了大量记录或加密签名）容易触发底层分片和丢包，或者服务器之间需要成批同步整张域名区域表（区域传送）时，DNS 就会果断回退到可靠的 **TCP** 来传输。

另一个伴随隐私意识觉醒的新变化是**加密 DNS**。传统跑在 53 端口上的明文 DNS 查询，意味着沿途的 Wi-Fi 热点、运营商甚至同网段窃听者，一眼就能看穿你刚刚问了哪些网站的名字。为了堵上这个隐私口子，现代系统和浏览器开始广泛支持两种加密承载：

- **DoT**（DNS over TLS）：把 DNS 报文装进专用的 TLS 加密隧道（通常用 853 端口）发给解析器；
- **DoH**（DNS over HTTPS）：把 DNS 查询直接包装成标准 HTTPS 请求（走 443 端口），与普通加密网页流量融为一体。

但请务必分清边界：DoT 和 DoH 保护的是「你的电脑到递归解析器」这一段路不被偷看和篡改；它们既不能保证你选的那家递归解析器本身绝对诚实，也无法证明上游权威服务器给出的数据中途没被动过手脚。

## 安全边界：DNSSEC 与纵深防御

如果不只怕被偷看，更怕有人在路上抢答一份伪造的假 DNS 响应（把银行官网指向黑客的假服务器 IP）——即所谓的 **DNS 缓存投毒或劫持**——该怎么防？

最基础的防线是给每一次查询附带随机的查询编号并随机挑选客户端源端口，严格要求回答必须与提问字字匹配，大幅拉高盲猜伪造的门槛。而在密码学层面，**DNSSEC**（DNS Security Extensions）为域名记录引入了从根域一路向下背书的**数字签名链**：递归解析器拿到记录后，可以用公钥逐级验签，确认这份地址确实出自真正的权威域主人之手且中途一字未改。

把 **DoT/DoH** 和 **DNSSEC** 摆在一起对比，思路立刻清晰无比：前者管**传输隐私**（不让旁人知道你问了谁），后者管**数据来源认证与完整性**（验证答案是不是真货，但并不加密隐藏你问了谁）。两者互补，互不替代。

退一万步讲，就算某条路径上没开 DNSSEC、DNS 真的被人篡改指向了假 IP，当你用 **HTTPS** 访问网站时，第 7 章会细讲的 TLS 证书主机名校验依然会当场亮起红灯——因为攻击者拿不到真正银行域名的合法私钥和证书。这正是网络工程中极具美感的 **分层防御**（defense in depth）：绝不把全部身家押在单一信任点上。

## 亲手观察一次 DNS 解析

用命令行里的 `dig` 工具，你可以亲眼目睹上面所有机制的真实运转：

```bash
dig www.example.com A
dig www.example.com AAAA
dig +trace www.example.com
dig example.com MX
```

前两条命令直观展示递归解析器返回的 IPv4/IPv6 记录、当前剩余的 TTL 倒计时（连敲两次你会看到 TTL 每秒递减！）以及谁回答了你；第三条 `+trace` 极其精彩，它像慢动作回放一样，从根服务器一路追踪到顶级域再到权威服务器，把完整的委派链条摊开在你眼前；第四条则用来查该域名的邮件投递入口。排障时记住区分四种完全不同的结果：`NXDOMAIN`（域名真不存在）、超时（根本连不上解析器或半路丢包）、返回了旧/错地址（缓存或配置问题）、以及解析完全正确但连不上目标端口（问题已不在 DNS，得往下查传输层和服务器）。

!!! question "随堂自测"
    哪怕运维把某条记录的 DNS TTL 设为 `0`，为什么依然不能保证每次用户访问都立刻打到权威服务器？

    首先，许多递归解析器、操作系统或运营商缓存为了保护上游免遭查询风暴，会强制设定一个「最小缓存下限」（例如无视 0 秒，按 30 秒缓存）；其次，浏览器和客户端往往会复用已经建好的持久 TCP/HTTPS 连接，或者应用代码自己把 IP 缓存在了内存里，压根不会重新触发 DNS 查询；最后，即便递归解析器重新向权威发问，通往权威路径上的根域和顶级域委派（`NS`）记录依然可能处于缓存中。DNS 只是发起新连接之前的一道寻址环节，远非控制流量的唯一开关。
