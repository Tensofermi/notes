# 从服务名到监听中的进程

前面两节里，我们已经看着浏览器写好了 HTTP 请求，也靠 DNS 把域名翻译成了目标机器的 IP 地址。现在数据包跨越互联网敲响了目标服务器的大门——可真正的「临门一脚」才刚刚开始。

一台服务器上往往同时运行着网页服务、数据库、日志采集器等几十个进程。服务程序怎么告诉操作系统「发往这个 IP 和这个端口的数据，请统统交给我」？更让人好奇的是：当成百上千个用户在同一秒向这台服务器的同一个 8000 端口发起请求，数据包全奔着同一个门牌去，服务器究竟靠什么把它们分得清清楚楚，绝不把张三的网页误发给李四？

要弄明白这件事，只需要认清两个在操作系统内核里天天运转的核心概念：

- **Socket**（套接字）：操作系统暴露给应用程序的通信接口，你可以把它想成进程插在网络世界里的一个「插座」——程序往里写字节，操作系统就负责按协议打包送出去；外面来了数据，操作系统就通过对应的插座递进来。
- **监听**（listen）：服务进程启动后，先向操作系统登记自己要占用的本地 IP 和端口号，然后进入「开门迎客」的状态，告诉内核「如果有新客户端敲这个端口的门，请通知我接单」。

下面我们就从「同一端口如何应付两条同时到达的连接」入手，再亲手在你自己电脑上做三组极简对照实验，把服务名、IP、端口和监听 Socket 彻底串成一体。

## 四个数字怎样区分同时到达的两条连接？

假设你的电脑上启动了一个网页服务，它只占用了 `127.0.0.1` 的 `8000` 号端口。此时，两个客户端程序（比如浏览器里的两个标签页，或两个终端里的 `curl` 命令）几乎同时向 `127.0.0.1:8000` 发起访问。

看起来它们敲的是完全相同的目标地址和目标端口，操作系统怎么不会搞混呢？秘密在于客户端自己出发时也会领一个临时的「出发房间号」——**源端口**（source port）。操作系统给第一个客户端分配了临时源端口 `49152`，给第二个客户端分配了 `49153`。

于是，在内核眼里，这两条同时存在的连接其实是两份截然不同的四元组（再加上传输协议 TCP，就是完整的**五元组**）：

```text
连接 1：客户端 127.0.0.1:49152  <--->  服务器 127.0.0.1:8000
连接 2：客户端 127.0.0.1:49153  <--->  服务器 127.0.0.1:8000
```

这里还有一个非常妙的分工：服务器上守着 `8000` 端口的那个 **监听 Socket**（listening socket）就像写字楼大堂的**总机接线员**——它从不亲自和顾客长聊业务，只负责接听新来电，然后立刻拉一条全新的独立分机线路（**已建立连接 Socket**，connected socket）把通话转接过去，自己马上回到门口继续等下一通新来电。

正因为两条连接各自对应着独立的已建立连接 Socket，有着不同的四元组坐标，它们可以各自收发字节、各自等待慢响应，互不串线。

??? question "如果第一个客户端（`49152`）率先关闭连接，第二个客户端（`49153`）一定会跟着断开吗？"

    一般不会。两条连接在内核中拥有各自独立的状态和连接 Socket，关掉其中一条对另一条毫无影响，服务器的大堂总机（监听 Socket）也会继续守在 `8000` 端口接待后续新来的客户端。只有当服务器进程整个崩溃或主动退出时，它名下打开的所有连接才会一并终止。

**先修**：[HTTP 与 HTTPS](01_http_https.md)、[DNS](02_dns.md)。

**学完能做**：亲手启动一个本机服务，用可复现的实验现象清楚区分主机名解析、监听地址绑定、TCP 建连失败与 HTTP 应用层报错。

## 先让两个进程在本机对话

理论听懂了，现在花两分钟在自己电脑上亲眼验证一次。先新建并进入一个空目录，用 Python 自带的模块启动一个极简 HTTP 服务，并刻意规定它只绑定在本机 **回环地址**（loopback address）`127.0.0.1` 上：

```sh
python -m http.server 8000 --bind 127.0.0.1
```

什么是回环地址 `127.0.0.1`？它是操作系统在软件里虚拟出的一条「不出本机门」的内部专用通道：发往 `127.0.0.1` 的数据包会在本机协议栈里转一圈直接送回本机，完全不需要经过物理网卡或路由器，哪怕拔掉网线也能照常跑通。

保持上面那个终端开着，另开一个终端窗口，在浏览器打开 `http://127.0.0.1:8000/`，或者更直观地敲下命令：

```sh
curl -i http://127.0.0.1:8000/
```

命令里的 `-i` 会同时打印出响应首部和正文。你会立刻看到一串 `HTTP/1.0 200 OK` 开头的状态行以及当前目录列表，同时在第一个运行服务的终端里滚出一条访问日志！

回头复盘这短短一秒里操作系统替你干了什么：因为你直接写了 IP `127.0.0.1`，客户端跳过了 DNS 查询，直接沿本机回环接口向 `8000` 端口发起 TCP 建连；服务端的监听 Socket 接到敲门声，分出一条专属的连接 Socket 接单；随后 `curl` 顺着这条连接送出 `GET /`，服务端读取空目录并拼好 `200 OK` 网页正文回传。只要你同时开几个终端一起 `curl`，服务器会按各自不同的源端口稳稳接住所有请求。

## 三个「只改一项」的对照实验

排障功力最快的提升方式，就是**故意制造可控的失败，观察每一层报错长什么样**。保持刚才的思路，每次只改一个变量，先动脑预测结果，再敲命令验证：

| 实验改动 | 先做预测：卡在哪一层？ | 真实观察到的现象 |
| --- | --- | --- |
| 1. 把 URL 端口改成 `8001`（确认没有别的程序占着 `8001`） | 传输层：本机 `8001` 端口没有监听 Socket | `curl` 立刻报错 `Connection refused`（连接被拒绝）；服务日志一片空白——HTTP 请求连门都没摸到 |
| 2. 服务仍绑定 `127.0.0.1`，但改用本机在局域网里的 IP（例如 `192.168.x.x:8000`）访问 | 绑定地址边界：服务明确只收发往回环接口的连接 | 哪怕就在同一台电脑上敲命令，依然连接被拒绝！因为服务压根没在局域网那张网卡地址上监听 |
| 3. 恢复访问 `http://127.0.0.1:8000/not-exist` | 应用层：TCP 建连畅通无阻，HTTP 也成功递给了进程 | 终端打印出完整的 `HTTP/1.0 404 File not found`，服务端终端也明确记下了一条 404 日志 |

做完这三组对照，两个在真实开发和部署里天天绊倒新手的细节，一下子就透明了：

- **主机名双栈陷阱（`localhost` vs `127.0.0.1`）**：当你把命令里的 `127.0.0.1` 换成主机名 `localhost` 时，客户端会先查系统解析配置。很多现代操作系统会同时把 `localhost` 解析成 IPv6 回环地址 `::1` 和 IPv4 回环地址 `127.0.0.1`，甚至优先尝试 `::1`！如果你的服务像上面那样明确只绑定了 IPv4 的 `127.0.0.1`，某些只试第一个地址的客户端可能就会莫名报错。排查这类怪问题时，第一件事就是确认客户端实际连的是 IPv4 还是 IPv6。
- **监听通配地址 `0.0.0.0`**：如果你想让室友或者另一台机器也能通过局域网 IP 访问你的服务，绑定 `127.0.0.1` 是不行的——必须绑定到具体网卡 IP，或者绑定到 IPv4 的 **通配地址**（wildcard address）`0.0.0.0`，意思是告诉操作系统「凡是发往本机**任意**一块 IPv4 接口 8000 端口的连接，我都接！」。但请注意：`0.0.0.0` 只是服务端用来「挂牌监听」的写法，客户端绝不能去访问 `0.0.0.0`，客户端必须连接服务器某一个真实可达的 IP；而且即便服务端绑了 `0.0.0.0`，外部能不能连上，还要过沿途路由和系统防火墙这两关。

## 随堂自测

假设你把一个网页服务部署在了公司内网的另一台服务器上，自己电脑连过去排查时遇到两种截然不同的现象：
1. 浏览器或 `curl` 返回了 `HTTP 404`；
2. 命令卡住十几秒，最终只吐出 `Connection timed out`（连接超时）。

这两种现象分别能帮你确认什么？又该顺着哪条线索继续查？

??? note "参考思路"
    收到 **HTTP 404** 其实是个「好消息」：它证明从 DNS 解析、跨网路由、防火墙放行、TCP 建连到至少某一台 HTTP 服务或反向代理进程，整条通信管道已经完全打通！你完全不必怀疑网络不通，直接把注意力集中在应用层——查 URL 路径拼写、静态文件目录、反向代理的转发规则，以及确认是不是连错到了同一端口上的另一套后端服务。

    而 **连接超时** 提供的信息要模糊得多，只说明「在限定时间内迟迟没收到期待的回应」。它可能卡在任意一个环节：DNS 解析器没回话、数据包被中间防火墙静默丢弃（注意和直接回拒的 `Connection refused` 不同）、路由黑洞导致回程包走丢、TLS 握手卡死，或是服务器进程虽然接了连接却在忙着查数据库迟迟不吐响应。此时需要用 `curl -v`、抓包或下一章学完传输层后的连通性工具逐段切开定位。
