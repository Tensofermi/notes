# UDP 与 TCP

不妨先设想一个极简单的小程序：发送方先后调用两次发送函数，第一次发「甲」，第二次发「乙」。请问：接收方的程序调用接收函数时，应该明确看到两条彼此独立的消息（「甲」一条、「乙」一条），还是只要最终能按顺序读出「甲乙」两个字就行，至于是一次读完还是拆成两半读都无所谓？

这听起来像是吹毛求疵的文字游戏，实则是传输层两大核心协议最根本的分水岭：

- **用户数据报协议**（UDP，User Datagram Protocol）选择前者：你发几次，正常到达时对方就按独立包裹收几次，边界清清楚楚——代价是它不操心包裹会不会半路丢了、翻了顺序或者莫名其妙多出一份；
- **传输控制协议**（TCP，Transmission Control Protocol）选择后者：它像一条首尾相接的水管，保证你倒进去的每一个字节不漏、不乱、不重复地从另一头流出来——但它完全不管你当初是分两瓢倒进去的还是一瓢倒进去的，想要区分消息边界，应用程序得自己想办法。

选哪一个才顺手？我们先拿 `AB` 和 `CD` 两个极简片段放到纸上推演一遍。

## 把两次 `send` 放到纸上比一比

假设发送方先交出 `AB`，紧接着交出 `CD`。看看走两条不同传输管道时，接收方可能撞见的真实画面：

- **走 TCP**：接收方的应用进程调用一次读取，可能一口气拿到合并在一起的 `ABCD`；也可能第一次只拿到半截 `A`，第二次才拿到剩下的 `BCD`；当然也可能碰巧一次 `AB`、一次 `CD`。唯一铁板钉钉的承诺是：**只要连接没断，最终拼起来一定是严丝合缝的 `ABCD`，既不会少字母，也不会变成 `CDAB`。** 如果应用希望把 `AB` 和 `CD` 当作两条独立消息，必须在数据里自己约定长度前缀（比如 `2:AB2:CD`）或分隔符（比如 `AB\nCD\n`）。
- **走 UDP**：每次发送都被装进一个独立信封（数据报）。如果顺利送达，接收方调用读取时要么完整拿到 `AB`，要么完整拿到 `CD`，绝不会拿到半个 `A` 或粘在一起的 `ABCD`。可另一方面，由于没有任何保障，接收方完全可能只收到 `CD`（`AB` 丢了）、先收到 `CD` 后收到 `AB`（乱序），甚至在某些异常重试下收到两份 `AB`！

看到这里，你大概已经对两种性格有了画面感。

??? question "既然 UDP 既可能丢包又可能乱序，现实里为什么还有程序宁愿选 UDP，也不愿等 TCP 帮忙重传？"

    因为很多实时应用**只在乎「此时此刻的最新状态」**。想象你正在打多人联机动作游戏或开视频会议：0.5 秒前角色在左边坐标的数据包半路丢了，此时角色早就跑到右边了。如果用 TCP 死等 0.5 秒前那个过期位置重传回来、还把后面崭新的坐标包统统卡住不让上交，画面就会瞬间定格卡顿。用 UDP 的话，应用可以干脆利落地丢弃过期旧帧，直接渲染刚到的最新状态，或者只在应用层针对关键控制指令补发。

不过，不管你选 UDP 还是 TCP，在决定「怎么送」之前，传输层必须先干好一件事：把送到这台机器的流量分毫不差地递给正确的进程。

## 传输层首先解决的难题：多路复用与解复用

同一台笔记本上，你可能同时开着浏览器刷网页、挂着终端跑远程登录、后台还在发 DNS 查询。网络层里的 IP 地址只能把包裹送到「你这台电脑的网卡门口」，进了门以后交给谁，全靠传输层首部里的 **端口号**（port number，16 比特无符号整数，范围 `0`–`65535`）。

发送端把来自多个不同进程的数据统统贴上源端口和目的端口，汇流交给同一层网络协议发出，这叫 **复用**（multiplexing）；接收端操作系统根据到达报文里的信息（对 UDP 主要是目的 IP 与目的端口；对 TCP 则是完整的源 IP、源端口、目的 IP、目的端口四元组加上协议类型），把它精准递进对应的那个 Socket，就是第 1 章已经打过照面的 **解复用**（demultiplexing）。

日常通信里，服务器通常会守在一个大家熟知或提前配置好的端口上（如 `80`、`443`、`53`），而客户端发起连接时则由操作系统自动挑一个空闲的 **临时端口**（ephemeral port），例如你的浏览器可能以 `192.0.2.10:53124` 的身份去连接远方的 `198.51.100.20:443`。

这里顺手破除一个极常见的误解：**`443` 端口并不是硬件焊死给 HTTPS 的。** 它仅仅是互联网社区为了免去每次手动敲端口号而达成的默认约定。你完全可以把自己的测试网页服务开在 `8443` 端口，反过来，也有人会把远程登录或隧道流量伪装跑在 `443` 端口上。端口号是投递信箱的编号，本身并不能决定里面装的究竟是什么应用协议。

搞清楚了共同的「分拣」底座，现在分别走近 UDP 和 TCP 看看它们各自长什么样。

## UDP：轻装上阵的最小封装

如果你打开 UDP 的首部规范，会惊讶于它简陋得几乎无可再减——总共只有短短 **8 个字节**，只装了四个字段：源端口（2 字节）、目的端口（2 字节）、总长度（2 字节）和校验和（2 字节）。

正是这份极简，赋予了 UDP 鲜明的特点：

- **面向数据报**：每次发送独立封包，接收端原样保留消息边界；
- **无连接**：说发就发，发之前不需要任何握手来回，没有建连延迟，服务器也不用为每个客户端在内核里留一大堆状态内存；
- **尽力交付**：不编序号、不等确认、不自动重传，也不替你调速；
- **基础检错**：校验和能查出传输中大部分比特损坏，但一旦查出坏包，UDP 的处理方式极其干脆——**直接静默丢弃**（或带错上交，视实现而定），绝不帮忙重传。

拿个最小例子感受一下：客户端连续朝服务端发出 `A`、`B` 两个 UDP 数据报。服务端实际看到的可能是顺顺利利的 `A, B`，也可能是 `B, A`（后发先至），可能只收到 `B`（`A` 丢了），甚至可能因为客户端应用自己盲目重试而收到 `A, A, B`。只要业务接受不了这些意外，应用开发者就必须亲自动手在载荷里加上序号、确认、重试、去重，或者用冗余编码来做 **前向纠错**（FEC，Forward Error Correction，发额外纠错码让接收端丢少量包也能自己算回来）。

正因为够轻、够直接、没有强制队头等待，UDP 在四类场景里如鱼得水：一是像 DNS 这样「一问一答」的短小查询；二是实时语音、视频和联机游戏；三是局域网广播或组播；四是像 QUIC 这样想把控制权收归用户态、自己按需定制可靠性和拥塞控制的现代协议。

## TCP：把乱石路修成铁轨的可靠字节流

如果每个写网页、传文件、连数据库的开发者都要在 UDP 上自己手写一套防丢包、防乱序、防撑爆的机制，软件工程早就被拖垮了。**TCP** 站出来把这套脏活累活彻底包圆，向应用层交付一条**面向连接、全双工（双向可同时收发）、有序、可靠的连续字节流**。

可既然底层网络无状态又不可靠，TCP 通信前必须先让两端「对好表」，结束时也要体面地「道好别」。

### 为什么建立连接需要「三次握手」？

在真正互传应用字节前，TCP 客户端和服务器会先走一遍经典的 **三次握手**（three-way handshake）：

```text
客户端                                    服务器
  | ------- 1. SYN (seq = x) -----------> |  「我想建连，我的初始字节号从 x 开始」
  | <--- 2. SYN + ACK (seq = y, ack=x+1) -|  「收到你的 x！同意建连，我的初始号从 y 开始」
  | ------- 3. ACK (ack = y+1) ---------> |  「收到你的 y！双向确认完毕，开聊！」
```

很多初学者会忍不住问：「两句打招呼不就够了吗？为什么非要来回三次？」

不妨反推一下假如只有**两次握手**会发生什么灾祸：
1. **服务器心里没底**：客户端发了第 1 句 `SYN`，服务器回完第 2 句 `SYN+ACK` 就立刻认为连接建好了、分配好内存缓存等着收数据。可万一服务器回的这句 `SYN+ACK` 在半路丢了呢？客户端压根不知道服务器同意了，也没收到服务器的初始序号 `y`，而服务器却傻傻地耗着资源干等！加上第 3 句客户端的 `ACK`，双方才都亲眼证实「我发出去的你能收到，你发过来的我也能收到」（双向可达）且「彼此的初始序号与通信选项已同步」。
2. **防止迷路的旧连接诈尸**：假如一个很久以前客户端发出的 `SYN` 在网络里绕了远路、延迟了几十秒才晃晃悠悠到达服务器。若是两次握手，服务器一看有 `SYN` 就立刻开门建连并白白占着资源；而在三次握手下，服务器回完 `SYN+ACK` 后，客户端一看「我此刻根本没发起建连」，立刻回一个复位拒绝，轻松挡掉僵尸连接。

### 连接怎样关闭：半关闭、`RST` 与 `TIME_WAIT`

因为 TCP 是全双工的（你发你的、我发我的，像两条反向单行道），关闭连接时**两个方向需要各自独立告别**。一方发完所有数据后，发出一个 `FIN`（Finish）标志位，表示「我这边话说完了，不再发新数据，但你没说完的还可以继续发给我」——这就形成了合法的 **半关闭**（half-close）状态。直到另一方也发完剩余数据、回敬一个自己的 `FIN` 并得到对方 `ACK` 确认（完整的「四次挥手」，有时中间两步可合并为三步），这条连接才算功德圆满。如果遇到程序崩溃或端口压根没人监听等异常，也可以直接甩出一记干脆利落的 **`RST`**（Reset，复位）强行拆断连接。

这里还有一个工程面试和线上排障的常客：**主动发起关闭的那一方，在发完最后一个 `ACK` 后，不会立刻把连接彻底销毁，而是要在一个叫 `TIME_WAIT` 的状态里静静守候一段时间**（通常是两倍的最大报文生存时间，很多系统约 60 秒左右）。

新手常误以为 `TIME_WAIT` 是系统清理不及时造成的资源浪费，甚至想方设法暴力关掉它，其实它肩负着两份极重要的保镖职责：
1. **给最后那个 `ACK` 留反悔余地**：万一你发出的最后一个 `ACK` 半路丢了，对端没收到确认就会超时重发 `FIN`。如果你还在 `TIME_WAIT`，就能稳稳接住并再补发一次 `ACK` 让对方体面关闭；要是你早就删光记录跑路了，只能回一个冰冷的 `RST` 报错。
2. **隔离迟到的幽灵包**：如果关掉旧连接后不到一秒，立刻用一模一样的源 IP、源端口、目的 IP、目的端口新建了一条连接，旧连接里某个滞留在网络深处的迷路旧数据包突然姗姗来迟，就会神不知鬼不觉地混进新连接里污染数据！`TIME_WAIT` 强行等待足够长的时间，确保旧连接的所有残余包裹都在网里彻底消亡，才允许彻底释放这个五元组。

## TCP 到底替你干了哪五件事（以及它不管什么）？

总结一下，TCP 首部至少占 20 字节，靠一套精密机制同时为你提供五大保障：

1. **序号与确认**：给每一个字节编上号码，并通过回执回报连续收到了哪里；
2. **校验和**：检测首部和数据在传输中有没有损坏；
3. **重传**：超时或收到丢包信号时，自动把丢掉的段重新发一遍；
4. **接收缓存与流量控制**：防止发送方一口气把慢吞吞的接收端内存撑爆；
5. **拥塞控制**：密切观察网络路况，在公共线路堵车时主动降速礼让。

当然，天下没有免费的午餐。这些强大保障的代价是：每次建连要花握手往返、内核必须为每条连接维护状态内存、一旦发生丢包后续字节必须等待重传补齐（队列延迟），而且协议状态机相当复杂。

同时请一定记牢 TCP 的**能力边界**：它不保证你的业务交易「恰好扣款一次」（连接半路断了应用仍需幂等键），不保证固定不变的低时延，也不提供任何加密保密性（防窃听必须靠 TLS）。

## 实战怎么选：不是「UDP 快、TCP 慢」那么简单

网上常流传一句过于粗糙的口号——「UDP 快、TCP 慢」。真正做架构选型时，这样想很容易掉进坑里：如果你因为嫌 TCP 慢而选了裸 UDP，结果发现业务还是不能丢数据、不能把别人宽带打爆、还得加密，于是自己从头在 UDP 上手写确认、重传、窗口和拥塞控制——最终写出来的不仅复杂难维护，性能多半还比不上打磨了几十年的操作系统内核 TCP！

真正该问的是：**你的应用究竟需要哪种交付语义？**

| 典型业务需求 | 更自然的协议起点 | 选定后应用层仍需操心的事 |
| --- | --- | --- |
| 网页、文件下载、数据库查询、API 调用 | **TCP** 或基于 **QUIC** 的可靠流 | 消息分帧边界、请求超时、业务幂等、TLS 安全 |
| 短小独立的单次查询（如 DNS） | **UDP** | 应用层超时重试、防止被利用做流量放大攻击、请求响应匹配 |
| 实时语音、视频会议、高频状态同步游戏 | **UDP** 或 **QUIC 数据报** | 抗抖动缓冲、动态调码率、丢包补偿或忽略旧帧 |
| 弱网环境高并发多路复用，不愿跨流互相卡死 | **QUIC** | 用户态 CPU 成本、老旧网络/防火墙对 UDP 限速或拦截的降级策略 |

## 延伸视野：QUIC 为什么站在 UDP 的肩膀上？

前面在 HTTP/3 里打过照面的 **QUIC**，正是打破传统僵局的现代范本。既然全世界几十年来部署的路由器、家用网关和防火墙对 TCP 首部早已形成了根深蒂固的「僵化假设」（稍微改点 TCP 扩展字段，路上的老旧设备就可能把它拦截丢弃），QUIC 干脆不再去硬改操作系统内核里的 TCP，而是直接跑在人人放行的 **UDP** 之上，把全部聪明才智搬进了**用户态**（应用程序或库里，升级迭代像更新 App 一样快！）。

它一口气把可靠传输、拥塞控制、TLS 1.3 加密握手和原生多路复用整合成一体：同一条连接里可以并发跑几十条独立数据流，某一条流丢了包绝不会挡住旁边其他流的交付；而且它用独立的「连接 ID」而不是脆弱的 IP+端口四元组来识别连接——当你拿着手机走出家门、网络从 Wi-Fi 瞬间切到 5G 换了新 IP 时，视频通话或下载还能丝滑不断线（**连接迁移**）。当然，QUIC 也不是魔法：它照样受光速传播和网络拥塞规律管束，丢了的包还是得靠重传找回来。

!!! question "随堂自测"
    打开 UDP 首部规范，明明能看到一个「校验和」字段，那为什么教科书和工程师依然一口咬定 UDP 是「不可靠」传输协议？

    因为**能发现错误，和能从错误中恢复，完全是两码事**。UDP 校验和确实能帮接收端查出部分比特损坏，但查出来之后它除了把坏包随手扔掉什么也不做——它不通知发送方重传，不给数据包排序，不剔除重复包，也不回报收货确认。真正的可靠传输，需要一整套「检测 + 反馈 + 重传 + 去重 + 排序」的闭环。
