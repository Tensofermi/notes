# 可靠传输

想象这样一个让人进退两难的日常场景：你寄出一封至关重要的挂号信，嘱咐对方收到后务必立刻回寄一张收件回执。可三天过去了，信箱里依然空空如也。此刻你盯着空信箱心里犯了嘀咕——究竟是**我寄出去的信半路丢了**，还是**对方其实已经收到了，偏偏那张回执在回来的路上弄丢了**，抑或仅仅是邮车遇上暴雨晚点了一天？

网络里用来充当这张收件回执的，就是 **确认**（ACK，Acknowledgment），它专门用来向发送方回报「哪些数据已经安然抵达」。可麻烦的是，ACK 本身也是跑在同一条不可靠网络上的普通分组，同样可能迷路、迟到甚至被拥堵丢弃！

为了把这场猫鼠游戏看个透彻，这一节我们不直接扔出冰冷的协议规范，而是把目标定得极其具体：假设发送方要往接收方传送六个字节 `ABCDEF`，分成 `ABC` 和 `DEF` 两段发出去。底层网络随时可能把其中一段弄丢、弄坏，或者让 `DEF` 抢在 `ABC` 前面到达，而接收端应用程序只认一份**连续、无缺、不重复的 `ABCDEF`**。让我们跟着两端的视角，亲手把可靠传输的每一块积木一步步「发明」出来。

> **阅读建议**：第一遍读时，重点跟着画出「ACK 丢失的四步」并亲手跑一遍末尾的六字节拼接练习，先把最小闭环立住；接着再顺理成章看懂「流水线滑动窗口」「累积/选择确认」和「超时定时器」如何把这套机制打磨成高速运转的现代 TCP。

## 动机：在不可靠的乱石路上铺出一条铁轨

底层网络层（IP）提供的只是「尽力而为」服务——分组在路上可能遭遇比特损坏、队列溢出丢失、莫名其妙的重复，或者走了不同路径导致后发先至。可靠传输层（如 TCP）的使命，就是在这片混乱之上向上层应用程序撑起一把干净的保护伞：**交进去的字节绝不损坏、绝不丢失、绝不重复，且严格按发送顺序交付。**

要兑现这四个承诺，靠某一个神奇的字段远远不够，它必须是一组机制严丝合缝咬合而成的反馈闭环。下面我们从最简单的故障开始，每撞上一堵墙，就补上一块新积木。

## 从零亲手「发明」可靠传输：三步演进

### 第一步：信号传坏了怎么办？——校验和

最先想到的麻烦是比特翻转：发出的是 `ABC`，无线干扰让一个比特翻了身，对端收成了 `ABX`。怎么防？发送方出发前用数据算出一段校验码——**校验和**（checksum）——附在首部里；接收方收到后用同样算法重算一遍，只要对不上，就立刻识破「这包已经坏了」，绝不把脏数据交给上层应用。

可校验和马上暴露出局限：**知道包裹摔碎了，并不等于能凭空还原里面的东西。** 要修复损坏，接收方必须想办法让发送方重新发一份完好的副本。

### 第二步：包丢了或者坏了，怎么让对方重发？——确认与定时器

发送方并不能长出一双千里眼直接偷看接收方的内存，它唯一能获知对端收货情况的途径，是让接收方回发一条 **确认**（ACK）。发送方每送出一份数据，都在本地缓存里留好备份，并顺手按下 **重传定时器**（retransmission timer）：

- 如果在闹钟响之前收到了对应的 ACK，发送方如释重负，把备份删掉，继续发下一段；
- 如果闹钟响了还没见到 ACK，发送方就判定「多半出岔子了」，把本地备份再重发一遍并重新按下闹钟。（某些教学协议还允许接收方在发现坏包时主动发「否定确认」NAK 催促重发，但只要有超时兜底，单靠 ACK 就足以覆盖所有情况。）

然而，第二步刚建好，我们就一头撞上了开篇那个经典两难！闹钟响起时，发送方眼前看到的唯一事实就是「我没等到 ACK」——它根本无从分辨究竟是**原数据丢了**、**ACK 丢了**，还是**网太堵、ACK 正在赶来的路上**。如果发送方每次超时都硬着头皮重传，万一接收方其实早就把原数据交给了应用程序，这一重传岂不是让应用白白读了两遍 `ABCABC`？

### 第三步：怎么区分「新数据」和「重复发来的旧副本」？——序号

破解重复投递的方法简洁得令人拍案叫绝：给每份数据贴上身份编号——**序号**（sequence number）。

先看最简单的 **停止等待**（stop-and-wait）模型：发送方极其谨慎，发完一个分组就停下来干等，必须收到它的确认才肯发下一个。在旧副本不会跨过几轮长期滞留的理想信道里，发送方甚至只需要短短 **1 个比特**（`0` 和 `1` 交替使用）就够区分「这是一份全新数据」还是「刚才那份的重传」！接收方如果正在等序号 `1`，却突然又收到了序号 `0`，立刻就能心领神会：「哦，一定是刚才的 `ACK 0` 丢了，对方才急着重发！」于是它**绝不把这份重复的 `0` 再交给应用**，只是好脾气地再补发一张 `ACK 0` 安抚对方。

回头瞧瞧，短短三步，我们已经亲手凑齐了可靠传输的五件核心法宝：**校验和**识破损坏，**ACK** 传回对端状态，**定时器**打破无尽等待，**重传**修复丢失，**序号**消除重复与恢复顺序。

## 先画出 ACK 丢失的四步 { #ack }

光看文字容易发飘，让我们把这台最小机器放到慢动作镜头下演练一遍。在这个一次只允许一个分组「在途」（已发出但尚未收到确认）的教学模型里，发送方给 `ABC` 贴上序号 `0`，接收方初始正等着收序号 `0`。注意：此处教学模型里的 `ACK 0` 表示「序号 `0` 已收到」；稍后讲到真实 TCP 时，确认号会采用更巧妙的「**下一处缺的字节位置**」约定。

```text
发送方                               接收方
   ────────── DATA 0: ABC ───────────→ 校验无误，交付 ABC，改等序号 1，发出 ACK 0
   ×──────────── ACK 0 ─────────────        糟糕！这张 ACK 0 在半路丢了
   （定时器超时，重传副本）
   ────────── DATA 0: ABC ───────────→ 认出是重复序号 0！不重复交付，只再补发 ACK 0
   ←──────────── ACK 0 ─────────────
如释重负！开始发送 DATA 1: DEF
```

把每一步两端的「内心状态」拆进表格里对照看，逻辑清晰得像钟表齿轮：

| 发生事件 | 发送方当前状态 | 接收方当前状态 |
| --- | --- | --- |
| `DATA 0` 平安到达 | 拿着备份，静等 `ACK 0` | 向应用交付 `ABC`，期望序号切到 `1`，回发 `ACK 0` |
| `ACK 0` 在途中丢失 | 一无所知，继续干等 `ACK 0` | 已经交差完毕，安静等待序号 `1` |
| 发送方超时，重发 `DATA 0` | 重置定时器，继续等 `ACK 0` | 一看序号 `0` 不是正在等的 `1`，识破重复，**绝不二次交付**，再补发 `ACK 0` |
| 重发的 `ACK 0` 抵达 | 确认成功，翻篇开始发 `DATA 1` | 依然等待 `1`，应用程序自始至终只拿到一次 `ABC` |

??? question "如果把丢失的位置改成最开头那条 `DATA 0` 丢了（而不是 `ACK 0` 丢了），四步里哪一步最先出现不同？"

    从发送方的视角看，前面两步几乎一模一样——都是苦等直到定时器超时然后重传 `DATA 0`。但接收方的状态从第一步就截然不同：因为原始的 `DATA 0` 压根没送到，接收方一直停在「等待序号 `0`」的状态，什么也没交付；直到发送方超时重传的 `DATA 0` 真正抵达时，接收方才**第一次**把 `ABC` 交付给应用、切到等待 `1` 并发出 `ACK 0`。你看，发送方眼前只有「超时」这一种模糊现象，全靠序号和接收方状态机才把两种完全不同的故障收拾得服服帖帖。

这套停止等待协议虽然滴水不漏，可一拿到真实的跨城或跨洋光纤上跑，工程师看一眼速度表就会当场崩溃。为什么？

## 停止等待为何惨烈浪费带宽？

算一笔扎心的账。假设你花大价钱租了一条 100 Mb/s 的高速链路，发送一个 1250 字节的标准分组只需要：

$$
d_{trans}=\frac{1250 \times 8\ \text{bit}}{100 \times 10^6\ \text{bit/s}} = 0.1\ \text{ms}.
$$

可这条链路横跨几千公里，分组飞过去再等对方的 ACK 飞回来——也就是一个 **往返时延**（RTT，Round-Trip Time）——总共要花 $T_{wait} = 100\ \text{ms}$。

在停止等待协议下，发送方拼命工作了 `0.1 ms` 把包推上线，接下来整整 `100 ms` 只能双臂抱胸坐在那儿干瞪眼！这一轮里，发送方真正利用链路干活的比例（链路利用率 $U$）粗略只有：

$$
U\approx \frac{d_{trans}}{T_{wait}+d_{trans}} = \frac{0.1}{100 + 0.1} \approx 0.001.
$$

千分之一！你花钱买的 100 Mb/s 高速公路，99.9% 的时间空无一车，实际有效传输速率惨到只有约 100 kb/s！更讽刺的是，哪怕你把宽带再升级 10 倍变成 1 Gb/s，$d_{trans}$ 缩成 `0.01 ms`，利用率反而跌成万分之一——因为光速往返的 100 ms 一毫秒都没少！

破局的直觉呼之欲出：**千万别发一个就停下来傻等！趁着第一个包的回执还在千里之外往回飞的空当，发送方应该马不停蹄地把第 2 个、第 3 个、第 4 个包连续不断推上线缆！**

## 滑动窗口与流水线：把长长的水管彻底填满

这种允许**多个未确认分组同时在路上奔跑**的技术，叫作 **流水线**（pipelining），而管理这批在途数据的优雅数据结构，就是 **滑动窗口**（sliding window）。

先用简单的分组编号想象窗口如何滑动：假设窗口大小设为 3（意味着任意时刻最多允许 3 个分组处于「已发未确认」状态）。发送方一口气把 `0`、`1`、`2` 连续推上线缆；此时窗口被占满，发送方暂停。一旦 `ACK 0` 飞回来，序号 `0` 功成身退离开窗口，整个窗口立刻向右优雅地「滑动」一格，原本空出的名额马上放行发送方推入分组 `3`；如果中途确认迟迟不来，窗口卡在原地占满，发送方就自然停下来等待或重传。真实 TCP 的滑动窗口不是按「包个数」算，而是精细到按**字节数**计量，并且受到下一章[流量控制与拥塞控制](03_flow_congestion_control.md)的双重约束。

那么问题来了：为了不让一条高带宽、长距离的光纤闲着，发送方的窗口至少要开多大，才能保证第一个包的 ACK 刚好飞回来时，发送方手里也刚好不停歇地把整条路塞满？

答案就是网络性能工程里最具分量的乘积之一——**带宽时延积**（BDP，Bandwidth-Delay Product）：

$$
BDP=R\times RTT.
$$

你可以把一条高速跨洋链路想象成一根又粗（带宽 $R$ 大）又长（往返时间 $RTT$ 长）的透明水管——**BDP 正是这根水管从头到尾在某一瞬间所能容纳的全部水（在途比特数）的总容量！**

立刻代一组真实数字感受一下震撼：一条速率 $R = 100\ \text{Mb/s}$、往返时延 $RTT = 100\ \text{ms}$ 的跨国链路，它的带宽时延积是：

$$
100\times 10^6\ \text{bit/s} \times 0.1\ \text{s} = 10^7\ \text{bit} = 1.25\ \text{MB}.
$$

算完这个数，一个困扰很多运维的谜团迎刃而解：**如果这条连接的滑动窗口上限只有老式默认的 64 KB，哪怕线路零丢包、零拥堵，发送方每跑满 64 KB 就必须停下来苦等 100 ms，连 1.25 MB 管道容量的二十分之一都填不满，吞吐死活上不去！** 要跑满「又肥又长」的管道（俗称 Long Fat Network，LFN），在途数据窗口必须足够大以逼近 BDP。

## 累积确认与选择确认：乱序到达时，怎么拼回原样？

流水线一跑起来，新的现实考验随之而来：既然同时有好几个分段在路上飞，难免会出现前面的段丢了或绕远迟到、后面的段反而抢先抵达的**乱序**局面。真实 TCP 怎样优雅地处理乱序、又怎样给对方回确认呢？

TCP 采用了简洁的 **累积确认**（cumulative ACK）语义：**接收方在 ACK 字段里填的数字，不再是「我刚收到哪一段」，而是「我接下来期望收到的第一个字节编号」**。比如接收方回复 `ACK = 5001`，就等于一口气担保：「从连接开始直到第 5000 号字节，全都严丝合缝收齐了，请接着给我发 5001！」

回到我们开篇的六字节例子：假设 `ABC` 占据字节序号 `100, 101, 102`，`DEF` 占据 `103, 104, 105`，接收方一开始期待的下一个字节是 `100`。现在网络顽皮了一把，让 `DEF` 抢先抵达，`ABC` 晚了一步，随后甚至因为发送方误判又重传了一遍 `ABC`。只要接收缓冲区空间充足，接收方会先把乱序的 `DEF` 妥善暂存起来，全过程像这样运转：

| 到达的报文段 | 接收方的暂存与拼接动作 | 本次能向上交付给应用 | 回复的 ACK（下一期望字节） |
| --- | --- | --- | ---: |
| `DEF` 先到（序号 103–105） | 前面 100–102 还缺着口！先把 103–105 暂存在缓存里 | 无（不能跳过缺口交付） | `100` |
| `ABC` 补到（序号 100–102） | 缺口瞬间填平！先拿 `ABC`，立刻顺带连上早已暂存的 `DEF` | `ABCDEF` | `106` |
| `ABC` 重复再到一次（100–102） | 这几号字节早就小于当前期望 `106`，直接丢弃忽略 | 无 | `106` |

看懂了吗？这就是为什么接收方明明已经拿到了 103–105，回过去的 ACK 却依然死死钉在 `100`——因为 TCP 严守「只能交付从头连续无缺的字节」的铁律，缺口一天不补上，期望指针就一天不能往前挪。

不过，单靠累积确认在一次丢掉多个不连续分段时会显得有点「笨」：接收方只能一遍遍喊「我缺 100！」，发送方听完却一头雾水——「那我后面发的 103–105、109–111 你到底收到了没有？我该只重传 100–102，还是全部重新发一遍？」

为了填补这个信息盲区，现代 TCP 普遍启用了 **选择确认**（SACK，Selective Acknowledgment）扩展选项：接收方在回 `ACK 100` 的同时，顺带附上一张小纸条明确写上「顺便告诉你，103–105 这块我已经稳稳收进缓存了！」。发送方一看一目了然，精准只重传真正缺失的缺口，在多丢包场景下大幅减少无效重传；代价则是两端需要维护更复杂的已收区间表。

??? example "动手拼字节：亲手跑通乱序、补齐与去重"

    下面这短短十几行教学 Python 代码，正是 TCP 接收端「字节流重组器」最纯粹的骨架（为了聚焦核心逻辑，略去了定时器、接收窗口上限、序号回绕和真实网络连接，并假设同一序号的正确副本内容一致）。

    读代码前先看懂两个变量：`pending` 是一本字典，用来暂存提前乱序到达、还不能交付的字节；`next_byte` 是当前期待交付的第一个字节编号。`setdefault` 确保只收下尚未缓存的编号；一旦缺口填上，`while` 循环就像拉拉链一样把连续的字节一口气全部拉出来交付，遇到下一个缺口再停下。

    ```python
    pending = {}
    next_byte = 100
    for start, segment in [(103, b"DEF"), (100, b"ABC"), (100, b"ABC")]:
        for index, byte in enumerate(segment, start):
            if index >= next_byte:
                pending.setdefault(index, byte)

        delivered = bytearray()
        while next_byte in pending:
            delivered.append(pending.pop(next_byte))
            next_byte += 1
        print(next_byte, bytes(delivered))
    ```

    运行后，三轮循环会依次打印：`100 b''`、`106 b'ABCDEF'`、`106 b''`。强烈建议动手改一下输入——把第一段改成 `(104, b"EF")` 再跑一遍，亲眼看看在 103 号字节缺席时，那两个字节是怎么老老实实待在 `pending` 里等待拉链合拢的！

## 定时器怎么设？还有比傻等超时更快的办法吗？

回头再看那个触发重传的闹钟——**重传超时时间**（RTO，Retransmission Timeout）。设多少才合适，是一道极其微妙的走钢丝题：

- **闹钟设太短**（比如链路平时往返 50 ms，稍微波动到 60 ms 就急着重传）：会把明明只是排了一会儿队的正常包误判成丢包，制造大量毫无意义的重复流量，让本来就吃紧的网络雪上加霜；
- **闹钟设太长**（比如动辄等 2 秒）：真丢了一个包时，整条连接傻傻冻结两秒毫无动静，用户早就气得关掉页面了。

因此，真实 TCP 绝不会把 RTO 写死成一个常量，而是持续测量每一个正常往返的实时 RTT，算出它的平滑均值和波动方差（抖动越大，预留的安全余量就越宽），动态自适应地调整超时闹钟。

即便如此，光靠等闹钟响依然太慢了。聪明的设计者很快发现了另一个更敏捷的丢包线索：假设发送方一口气流水线发出了 1、2、3、4、5 五个分段，其中 1 号半路丢了，2、3、4、5 却相继到达对端。还记得累积确认吗？每到达一个乱序段，接收方都会焦虑地回喊一遍同一个期望编号：「我还在等 1！」「我还在等 1！」「我还在等 1！」。当发送方在极短时间内连续收到多个一模一样的**重复 ACK**（经典规则是 3 个重复 ACK，或看到 SACK 报出的明确缺口），不用傻等超时闹钟响，立刻就能断定「1 号多半真丢了！」，当机立断提前补发——这就是大名鼎鼎的 **快速重传**（fast retransmit）。

这里已经隐隐露出了下一章的伏笔：在 TCP 里，丢包信号往往身兼两职——**重传负责把丢了的数据救回来（可靠性），而紧随其后的降速则试图缓解酿成丢包的路上拥堵（拥塞控制）**。

## 细节收尾：按字节编号与序号回绕

在实际抓取的 TCP 数据包里，你会发现 TCP 首部里的序号标的是**字节位置**，而不是「第 1 个包、第 2 个包」。如果一个 TCP 段起始序号是 `1000`，里面装着 500 字节的应用数据（占据 `1000` 到 `1499`），那么下一个连续段的起始序号就是 `1500`。按字节编号的好处显而易见：哪怕因为半路 MTU 变化导致重传时把原来 500 字节拆成两块 250 字节来发，两端的字节流坐标依然丝毫不乱。

此外，上一节见过的 [TCP 建立连接的 `SYN` 和结束发送的 `FIN`](01_udp_tcp.md) 虽然不带应用数据，但也各自象征性地占用 1 个序号——这样一来，连「开聊」和「告别」本身都能无缝复用同一套 ACK 确认机制，确保绝不会在半路悄无声息地丢失！

至于 32 比特无符号序号最大只能数到约 42.9 亿（约 4 GiB），在今天动辄 10 Gb/s 的高速链路上几秒钟就会数到头并从 `0` 重新开始——即 **序号回绕**（sequence number wraparound）。协议依靠窗口大小限制、时间戳扩展以及报文最大生存时间，确保几分钟前滞留在网里的古老幽灵字节绝不会被误认成当下回绕后的新数据。

## 清醒的结尾：可靠的边界在哪？

学完这么多精妙机制，千万别产生「只要用了 TCP，业务就万无一失」的错觉。和上一章强调过的一样，传输层的可靠依然有它严格的责任边界：

- 当客户端发完「转账 100 元」后连接突然中断，TCP 只能如实向应用报错「连接断了」，绝无能力替你判断「服务器到底扣了钱还是没扣钱」——重连后防止重复扣款，必须由应用层的事务编号、幂等键或查询对账来兜底；
- 当你的代码调用 `send()` 成功返回时，仅仅意味着数据已经被拷贝进了**本机操作系统的发送缓冲区**，甚至还没离开本机网卡，更不代表对端应用程序已经把数据安全落盘写入数据库。

每一层只为自己承诺的契约负责，切忌把下层的字节确认夸大成上层的业务持久化确认。

!!! question "随堂自测"
    既然增大滑动窗口能填满带宽时延积、大幅拉高长距离链路的吞吐，那干脆把窗口设成无穷大不就好了吗？为什么绝不能无限扩大？

    窗口开到恰好能填满路径的**带宽时延积（BDP）**时，物理链路就已经满负荷运转、吞吐达到天花板了。如果此时继续盲目扩大窗口，多出来的在途数据包根本走不快，只会全部堆积在沿途瓶颈路由器的缓冲区里——先是把排队时延和抖动拉爆（缓冲膨胀），紧接着把队列彻底撑溢酿成成片丢包；除此之外，窗口大小还受限于接收方有限的可用内存缓存、序号空间防回绕约束，以及我们马上要在下一章深入拆解的拥塞控制限制。

---

至此，第 3 章彻底揭开了「从不可靠信道变出可靠字节流」的全部魔术：校验和、ACK、序号、定时器、滑动窗口、累积确认与 SACK 严丝合缝地拼成了一台精密机器。

但正如刚才那道自测题留下的巨大悬念：现在发送方已经手握流水线和滑动窗口，可以撒开腿往网里狂塞字节了。可一旦跑得太猛，两种截然不同的灾难马上就会迎面撞来——要么把慢吞吞的接收方内存活活撑爆，要么把沿途成千上万条连接共用的瓶颈路由器彻底堵死！
