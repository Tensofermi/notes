# 可靠传输

把一封邮件发出去后，你也许会想等一张回执。网络里的**确认**（Acknowledgment，缩写 ACK）也是在告诉发送方「哪些数据已经收到了」。如果等不到回执，数据和回执本身都有可能丢失。本节从这个小问题推导编号、等待和重发。

设两台电脑要传 `ABCDEF`，发送方先发 `ABC`、再发 `DEF`。网络可能先送来 `DEF`，也可能把其中一段丢掉。接收程序想看到的是「连续的 `ABCDEF`」。这一章跟着接收方手里的字节和发送方手里的确认，看看需要加哪些机制。

**第一次读**，先手推一次确认丢失，再做末尾的六字节拼接练习。第二遍可以再看一次往返期间怎样连续发数据、如何指出哪些部分到了，以及多久没回应才重发。

## 动机：不可靠信道上建立可用抽象

底层可能损坏、丢失、重复或重排分组。可靠传输希望向应用呈现更简单的结果：数据不损坏、不重复，并按预期顺序交付。这个抽象不是由单一字段实现，而是多种机制组成的闭环。

## 从最小协议逐步演进

### 第一步：检测损坏

发送方附加校验值，接收方重新计算。若不一致，接收方知道数据不可直接交付。但“知道坏了”不等于“知道正确内容”，所以还需要反馈与重传。

### 第二步：确认与重传

发送之后，发送方不能直接看到接收方的状态。让接收方发一条**确认**（ACK），才能把已收到的消息传回来。发送方在收到对应的确认前保留副本并启动计时器。若等待过久，就重传这份副本；某些教学协议还允许接收方主动发否定确认。

此时发送方看到的只是「一直没等到确认」。它无法区分数据丢了、确认证明丢了，还是这一路特别慢。如果总是重发，接收方必须能判断这是否是已交付过的数据。因此仅加确认和定时器，还要继续解决重复。

### 第三步：序号与去重

在停止等待的教学信道模型里，发送方一次只允许一个未确认分组；若旧副本不会跨过一次序号重用长期滞留，1 比特序号 0、1 交替即可区分新分组和上次重传。接收方对重复分组再次确认，但不重复交付。

这个最小例子包含可靠传输的核心思想：校验判断可用性，序号标识身份，ACK 传回接收状态，定时器处理无响应，重传修复丢失。

## 先画出 ACK 丢失的四步

先用只让一个分组在途的教学协议。这里的「在途」指已经发出、尚未收到确认。发送方给 `ABC` 标上序号 0，接收方等 0。这个模型里的 `ACK 0` 表示「序号 0 已收到」。下方 TCP 的确认号会采用另一种约定，表示**下一处缺的字节**。

```text
发送方                               接收方
   ────────── DATA 0: ABC ───────────→ 交付 ABC，开始等序号 1
   ×──────────── ACK 0 ─────────────        确认在路上丢失
   ────────── DATA 0: ABC ───────────→ 旧分组，只再发确认
   ←──────────── ACK 0 ─────────────
开始发送 DATA 1: DEF
```

| 事件 | 发送方 | 接收方 |
| --- | --- | --- |
| DATA 0 到达 | 等 ACK 0 | 向应用交付 0，改等 1，发 ACK 0 |
| ACK 0 丢失 | 仍等 ACK 0 | 仍等 1 |
| 发送方超时，重发 DATA 0 | 重置定时器 | 识别重复 0，再发 ACK 0 |
| 重发的 ACK 0 到达 | 可以开始发送 1 | 仍等 1，应用只收到一次 0 |

??? question "只把丢失的位置改成第一条 DATA 0，哪一步最先不同？"

    发送方仍然会等到超时。接收方却一直在等序号 0，因为原始数据根本没到。重传到达后，它第一次交付 `ABC`，再变成等序号 1。这两种情况下，发送方都看到超时，接收方的状态却不同。

## 停止等待为何浪费带宽

若发送一个分组只需 0.1 ms，发完后却还要大约 100 ms 才收到确认，发送方绝大多数时间都在等待。把一轮看成「发数据的时间」加「发完后的等待时间」，发送链路的粗略利用率为：

$$
U\approx \frac{d_{trans}}{T_{wait}+d_{trans}},
$$

代入后约为千分之一。RTT 指一次往返所需的时间；当分组发送时间相对很短时，可以用往返时延粗略估计这一轮的大部分等待。提高链路带宽会缩短发送本身，仍需要等待传播和确认。因此下一步是让发送方可以在等确认时先发送后续数据。

## 滑动窗口与流水线

滑动窗口允许多个分组同时在途。先用分组编号来画：窗口一次允许有 3 个未确认分组，发送方发出 0、1、2。确认 0 后，0 离开窗口，1、2 仍在等确认，此时可以发送 3。确认迟迟不来时，窗口会占满，发送方就得等。实际 TCP 的窗口会按字节计算，并受[流量与拥塞控制](03_flow_congestion_control.md)约束。

为了让高带宽长时延链路保持忙碌，在途数据量至少应接近带宽时延积：

$$
BDP=R\times RTT.
$$

例如 100 Mb/s、RTT 100 ms 的路径，带宽时延积约 10 Mb，即 1.25 MB。若窗口只有 64 KB，发送方即使没有丢包也无法跑满链路。

## 累积确认与选择确认

TCP 的确认号通常表示“下一个期望字节”，因此具有累积含义。若接收方确认 5001，表示此前连续字节均已收到。乱序到达的后续数据可暂存在接收缓存，但累积确认可能停在缺口处。

让 `ABC` 占据序号 100、101、102，`DEF` 占据 103、104、105。接收方开始时等 100。在这个例子里，假设缓存有空间，接收方会保留乱序数据：

| 到达顺序 | 暂存或拼接动作 | 本次能向上交付 | 下一期望字节，也就是 ACK |
| --- | --- | --- | ---: |
| `DEF` 先到，从 103 开始 | 暂存 103–105，前面还缺字节 | 无 | 100 |
| `ABC` 补到，从 100 开始 | 先拼 `ABC`，随后接上已暂存的 `DEF` | `ABCDEF` | 106 |
| `ABC` 再到一次 | 100–102 已经交付，忽略重复字节 | 无 | 106 |

接收方只交付从当前位置开始的连续内容。这也是为什么它看到 105 时，确认号仍可停在 100。

选择确认 SACK 可额外告诉发送方哪些不连续区间已经到达，使发送方只重传真正缺失的部分。它提高多丢包场景效率，代价是双方维护更复杂的区间状态。

??? example "动手拼字节：把丢失、乱序和重复分开"

    改这一组输入，先预测每轮的确认号。教学代码只处理收到的字节，不实现计时器、接收窗口上限、序号回绕或网络连接。假设同一序号的正确副本内容相同。

    `pending` 按编号存放还没交付的字节，`next_byte` 指着当前第一个需要交付的位置。`setdefault` 只写入此前没缓存的编号。`while` 每取出一个连续字节，就把位置往前挪一格。遇到缺口时停下来，先把缺口后面的字节留在缓存里。

    ```python
    pending = {}
    next_byte = 100
    for start, segment in [(103, b"DEF"), (100, b"ABC"), (100, b"ABC")]:
        for index, byte in enumerate(segment, start):
            if index >= next_byte:
                pending.setdefault(index, byte)

        delivered = bytearray()
        while next_byte in pending:
            delivered.append(pending.pop(next_byte))
            next_byte += 1
        print(next_byte, bytes(delivered))
    ```

    三轮分别输出 `100 b''`、`106 b'ABCDEF'` 和 `106 b''`。把第一段改为 `(104, b"EF")`，看看字节 103 没到时，后面两字节会在哪里等待。

继续练习可做 [Kurose & Ross 的 TCP 确认与重传题](https://www-net.cs.umass.edu/kurose_ross/interactive/tcp_retrans.php)，注意题面采用自己的乱序处理假设。要进一步实现带容量限制的拼接，可读 [Stanford CS144 的字节流重组实验](https://cs144.github.io/assignments/check1.pdf)。

## 定时器如何选择

重传超时太短，会把只是排队较久的数据误判为丢失，制造多余重传；太长，则真正丢失后恢复缓慢。实际协议根据测量到的 RTT 平滑估计超时时间，并为波动留余量。

仅靠超时恢复仍慢。TCP 可从重复确认或 SACK 缺口推断某段可能丢失，提前快速重传。要注意丢包信号与拥塞控制相连：重传修复可靠性，降低发送速率则试图缓解造成丢包的拥塞。

## TCP 以字节编号

TCP 序号标识字节而不是“第几个包”。若一个段从序号 1000 开始，携带 500 字节，那么下一个连续字节序号是 1500。底层分段大小可能因 MTU 和实现改变，但应用看到的仍是连续字节流。

[TCP 建立连接的 SYN 和结束发送的 FIN](01_udp_tcp.md) 也占用序号空间，便于可靠确认连接的开始与结束。序号是有限宽度字段，会回绕；协议依靠窗口和报文生存时间避免把很久以前的旧数据误认成当前数据。

## 可靠的边界

传输层可靠不等于业务可靠。客户端发送“转账 100 元”后连接断开，可能是请求没到，也可能是服务器已执行但响应丢失。TCP 重连后无法替应用判断。业务层需要事务标识、幂等键、查询接口或去重表。

同样，TCP 成功写入本机发送缓冲区不等于对端应用已经持久化数据。每层确认的只是自己的责任范围，不能把下层确认夸大为业务承诺。

!!! question "自测"
    为什么窗口扩大能提高长距离链路吞吐，却不能无限扩大？

    足够大的窗口可填满带宽时延积；继续扩大可能让队列累积、延迟上升和突发丢包，还受接收缓存、序号空间与拥塞控制约束。
