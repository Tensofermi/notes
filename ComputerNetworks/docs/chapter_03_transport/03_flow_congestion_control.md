# 流量控制与拥塞控制

上一章里，我们给可靠传输装上了「滑动窗口」这台涡轮增压引擎——发送方不再发一个包就干等一个回执，而是可以把源源不断的字节流水线般推上高速路。

可一旦踩下油门狂奔，两个截然不同的麻烦立刻会找上门来：
- **第一种祸闯在对端机器里**：你的发送服务器性能强悍，每秒往外灌 100 MB 数据，可对端那台手机或老旧设备正忙着把收到的数据解压写进慢吞吞的闪存，每秒只能消化 10 MB。你不管不顾地继续猛灌，瞬间就会把对方的接收缓存彻底撑爆，白白把好不容易送达的字节挤掉。
- **第二种祸闯在半路的公共网络里**：对端服务器其实快如闪电、内存大得很，压根不怕你发；偏偏你和成千上万个用户共享着中间那段 100 Mb/s 的瓶颈链路。大家都铆足了劲往里冲，沿途路由器出口立刻排起长龙、队列溢出、成片丢包，最后谁也别想顺畅走过去。

这两种祸外表看起来都表现为「发太快了、该减速」，但病因和保护对象完全不同，必须拆成两套独立机制来治：

- 盯着接收方还剩多少空位、防止撑爆对端缓存的调速机制，叫作 **流量控制**（flow control）；
- 盯着沿途共享路径的承载能力、防止堵垮公共网络的调速机制，叫作 **拥塞控制**（congestion control）。

上一章做[六字节拼接](02_reliable_transport.md)时，我们暂时默认「接收方总有无限大空间把乱序数据稳稳放好，路上也敞亮通畅」。这一章，我们把这两道现实约束全部加上，看看 TCP 究竟怎样同时看住两块仪表盘，在「榨干可用带宽」和「绝不闯祸」之间精准拿捏发送节奏。

## 两个名字极像、却各护其主的问题

初学者最容易把「流量控制」和「拥塞控制」混成一团浆糊。记住两个极其形象的画面，你就永远不会搞混：

- **流量控制（保护单个接收端）**：就像大水管往一只小水桶里倒水。水桶底下的排水口（接收应用程序调用 `recv` 读取数据的速度）很细，就算你把整座水库接过来，倒太快水照样溢一地。流量控制解决的是**端到端一对一的速度匹配**问题。
- **拥塞控制（保护沿途共享网络）**：就像十辆满载的大货车同时抢着过一座老旧独木桥。桥对岸的仓库（接收端）哪怕大如足球场、卸货飞快，只要货车全挤在桥头上互不相让，桥面立刻瘫痪。拥塞控制解决的是**多条独立连接公平共享公共网络资源**的全局问题。

现实中，接收端很快绝不代表网络不堵；反过来，半夜网络空荡荡也绝不代表对端应用来得及消化。两套机制缺一不可，必须同时在线。

先来拆解相对直白的那一个——发送方怎么知道对端的小水桶里还剩多少空位？

## 流量控制：接收窗口 `rwnd` 如何给发送方「报余量」

解决办法非常直接：既然只有接收方自己最清楚内存缓存还剩多大空位，那就让接收方在**每一次发回的 ACK 首部里顺便夹带一个数字**——**接收窗口**（`rwnd`，receive window），白纸黑字地告诉发送方：「我现在空闲缓存还剩这么多字节，你尚未得到确认的在途字节总量，绝不许超过这个数！」

看一个具体的数字走查：假设接收方为这条连接划出了 `64 KB` 的接收缓冲区。此时网卡已经替应用收好了 `48 KB` 字节，可接收方的应用程序正忙着做复杂计算，还没来得及把它们 `recv` 读走。那么，接收方剩下的空位就是：

$$
64\ \text{KB} - 48\ \text{KB} = 16\ \text{KB}.
$$

于是接收方在回发 ACK 时，把首部里的 `rwnd` 字段填成 `16 KB`。发送方收到后乖乖照办，确保自己发出去还没收到确认的数据不超过 16 KB。过了一会儿，接收应用忙完了，一口气从缓冲区里读走 32 KB，接收方立刻在下一个 ACK 里把 `rwnd` 更新成 `48 KB`，发送方随即放开手脚加速。

可这里藏着一个极其精巧的边界陷阱：**万一接收应用卡住了，缓冲区 64 KB 被彻底塞满，接收方通告了 `rwnd = 0` 会怎样？**

收到 `rwnd = 0` 后，发送方当然老老实实暂停发送常规数据。过了一阵，接收应用终于缓过神来读空了缓冲区，接收方于是主动发了一个「窗口更新包」告诉对方 `rwnd = 32 KB`，请继续发！**偏偏不巧，这个单独的窗口更新包在半路丢了（而且纯 ACK 本身是不触发重传的）！** 如果没有补救措施，发送方会以为对方窗口还是 0 而一直干等，接收方则以为通知已经送达而一直干等新数据——双方陷入永恒的**零窗口死锁**！

TCP 设计者用一个四两拨千斤的小招化解了死锁：**窗口探测**（window probe）。当发送方看到 `rwnd = 0` 进入暂停后，并不会真的彻底睡死，而是会启动一个持续定时器，隔一小段时间就试探性地发一个只装了 **1 字节**数据的极小探测段过去。接收方收到这 1 字节后必须礼貌地回一个 ACK，顺便把此刻最新的真实 `rwnd` 捎回来——死锁瞬间打破！

当然，流量控制能防住内存溢出，却治不了「对端应用程序彻底死锁、永远不再读数据」的病。遇到那种僵尸对端，连接会长期死死占着内核内存和文件描述符，服务端仍需借助应用层超时断开、最大并发限制和业务级背压来兜底保护自己。

搞定了「一对一不撑爆接收端」，接下来面对的是计算机网络里最迷人、也最具挑战性的难题：发送方看不见沿途几十台路由器的内部队列，究竟怎么判断「公共网络堵不堵」？

## 拥塞是怎样形成的，又为何会酿成「拥塞崩溃」？

当成百上千条流同时涌向同一条瓶颈链路，路由器出口缓冲区开始迅速拉长（排队时延陡升）；一旦涌入速率持续超过出口发送速率，队列彻底填满，路由器别无选择，只能把装不下的新分组直接丢弃。

早年的互联网（上世纪 80 年代中期）还没装上拥塞控制时，曾爆发过令整个学界震动的 **拥塞崩溃**（congestion collapse）惨剧。原因回过头来看极具讽刺意味：当路由器拥堵丢包后，当时只管可靠性的 TCP 发送方把丢包当成「偶尔线路坏包」，超时后立刻把丢掉的数据**重新发一遍**，甚至发得更起劲！结果，原本就已经塞满的瓶颈链路瞬间涌入了海量的重传副本——路由器把绝大部分宝贵带宽全耗在了运送已经重复的废包上，整条网络看似忙得热火朝天，用户真正收到的有效新数据（好吞吐）却暴跌到不足原带宽的千分之一！

惨痛的教训让工程师彻底清醒：**在无中央交警统一指挥的互联网里，每一个端系统必须具备「自觉感知路况、见堵立刻礼让」的端到端拥塞控制本领。**

可核心矛盾摆在眼前：网络不会提前给你发一张「前方限速 35 Mb/s」的通告牌。送信的人如果不试着一点点提速，就永远不知道这条路到底多宽；可要是提速太猛，又会把队列打爆、害人害己。因此，端到端拥塞控制必须像老司机看路面颠簸一样，通过 ACK 飞回来的节奏、是否出现丢包、RTT 是否突然拉长，或者沿途路由器悄悄打上的拥塞标记，动态反推出路径当前的真实容量。

## 双窗口协同：此刻到底还能新发多少字节？

为了估算「网络此刻大概能承受多少在途数据」，发送方在自己心里偷偷维护着第二个窗口——**拥塞窗口**（`cwnd`，congestion window）。

现在，发送方眼前同时亮着两盏限速牌：接收方发来的 `rwnd`（接收方能装多少）和自己算出来的 `cwnd`（网络大概能扛多少）。为了既不撑爆对端，又不堵垮网络，TCP 遵守一条铁律——**任意时刻允许处于「已发未确认」状态的在途字节总量，不得超过两者的较小值：**

$$
W_{send}=\min(rwnd,\ cwnd).
$$

- 如果 `rwnd < cwnd`，说明网络还敞亮着，是接收方读得太慢成了瓶颈；
- 如果 `cwnd < rwnd`，说明接收方胃口大得很，是发送方对前方网络容量保持谨慎成了瓶颈。
（实际操作系统里，还要受限于本机发送缓冲区大小以及应用程序往里塞数据的速度。）

这里有一个新手做题和写代码时最容易算错的坑，我们拿一组清晰的数字手把手走查一遍。假设此时：
- 接收方刚通告它还能收 `rwnd = 4 KiB`；
- 发送方估算网络当前最多扛 `cwnd = 3 KiB`；
- 而发送方此前已经推上网线、目前还在等 ACK 的数据已经有 `2 KiB`（在途数据，bytes in flight）。

请问：**此时此刻，发送方最多还能立刻新发多少字节出去？**

| 计算步骤 | 对应数值 | 背后的含义 |
| --- | ---: | --- |
| 接收方允许上限 `rwnd` | `4 KiB` | 接收缓存当前的空闲余量 |
| 发送方估计网络上限 `cwnd` | `3 KiB` | 对当前路径承载能力的保守上限 |
| 实际允许的最大在途总量 $\min(rwnd, cwnd)$ | `3 KiB` | 两根刹车里更紧的那一根生效 |
| 当前已经在途、尚未确认的字节 | `2 KiB` | 已经占用的窗口配额 |
| **此刻最多还能新发出去的数据** | **`1 KiB`** | **总上限减去已占用，绝不是直接再发 3 KiB！** |

记住这句口诀：**窗口永远管的是「在途总量上限」，不是「这一次还能新发的量」。** 接着往下推演：如果下一毫秒飞回来一个 ACK 确认了其中 `1 KiB`（假设 `rwnd` 和 `cwnd` 暂未改变），已在途数据降为 `1 KiB`，那么此刻允许新发的空间就顺势恢复成了 `3 - 1 = 2 KiB`。

而且在一条长连接的生命周期里，谁当瓶颈是动态切换的：刚开始网络拥堵可能是 `cwnd` 掐着脖子；过一会儿路通了、对端磁盘突然卡住不读数据，立刻变成 `rwnd` 猛缩接管限制。

弄懂了双窗口的算术，核心好戏登场了：一条崭新的连接刚刚握手成功，面对一无所知的陌生网络，发送方怎么从零开始动态调节 `cwnd` 呢？

## 从慢启动到拥塞避免：一场「先冲刺、再试探、撞墙急刹」的舞蹈

如果刚建连就贸然以本机千兆网卡的线速往外狂砸数据，碰上窄带宽接入网瞬间就会酿成大规模丢包。经典 TCP 发明了一套分阶段调节 `cwnd` 的优雅策略：

### 第一阶段：慢启动（Slow Start）——名义上「慢」，实则指数起飞

连接刚起步时，发送方非常谦虚地把 `cwnd` 设为一个很小的初始值（比如几个最大报文段 MSS，现代系统常从 10 个 MSS 起步）。此后，每收到一个正常的新确认，就把 `cwnd` 扩大一点——算下来，**每平安度过一个完整的往返时延（RTT），`cwnd` 就会近似翻一倍**（1 → 2 → 4 → 8 → 16 → ……）！

你可能会笑出声：「这明明是指数级狂飙，怎么起了个『慢启动』的乖巧名字？」其实它是相对于「开局直接按满线速狂喷」而言足够谨慎，既避免了一上来就把陌生小路由器冲垮，又能在短短几个 RTT 内迅速摸到高带宽链路的真实水位，不至于慢吞吞爬行半小时。

### 第二阶段：拥塞避免（Congestion Avoidance）——见好就收，走上 AIMD 锯齿路

指数翻倍固然痛快，但越往后翻一倍的增量越吓人（从 500 瞬间跳到 1000 极易一把打爆队列）。因此，发送方心里还记着一个换挡警戒线——**慢启动阈值**（`ssthresh`）。一旦 `cwnd` 冲过 `ssthresh`，或者曾经嗅到过拥塞信号，TCP 就切入稳健的 **拥塞避免** 阶段，奉行互联网最经典的 **加性增大、乘性减小**（AIMD，Additive Increase Multiplicative Decrease）法则：

```text
一路顺风、没有拥塞信号：每过一个完整 RTT，只把 cwnd 温和地加 1 个 MSS（线性小心试探剩余容量）
一旦嗅到拥塞信号：果断把 cwnd 砍掉一大截（例如直接减半），立刻腾出队列空间给所有流喘口气
```

为什么偏偏设计成「慢慢涨、狠狠砍」的不对称节奏？数学与几十年的互联网实测给出了漂亮答案：假设两条条件相似的 TCP 流共享同一条瓶颈链路，大家一起线性增长、遇堵一起按比例减半——经过几轮锯齿形的拉锯之后，原本占便宜的大流砍得绝对值更大，吃亏的小流慢慢补齐，两条流的带宽占用会自动向着 **公平平分** 的中线收敛！

不过，现实世界从来不是理想实验室。AIMD 的公平性在真实网络里会受到许多因素扰动：比如往返时延（RTT）短的连接「每 RTT 加 1」跑得比长 RTT 跨洋连接快得多，天然更占便宜；不同操作系统混用不同拥塞算法也会影响份额；更现实的是，某些下载器一口气对同一个文件开 16 条并行 TCP 连接，硬生生在单连接老实人面前抢走了十多倍带宽。

## 丢包不是唯一信号：现代拥塞控制的演进与 ECN

上面这套以「丢包 = 堵车」为核心假设的经典算法（如早期的 Reno、后来长期统治 Linux 的 CUBIC）支撑了互联网几十年，但在现代无线网络和超高速宽带时代，它逐渐暴露出两个软肋：

1. **冤枉好人**：在 Wi-Fi、4G/5G 或卫星链路上，穿墙衰减和信号干扰经常造成随机比特误码丢包——此时路由器队列其实空荡荡的，压根没堵车！传统基于丢包的算法分不清是非，一见丢包就猛砍 `cwnd`，白白把吞吐砸到地板上。
2. **非要把队列填满才肯收手**：只要路由器配了大缓冲区，基于丢包的算法为了试探上限，会一直线性涨窗口直到把缓冲区彻底灌满、逼出第一个丢包才肯降速——这恰恰亲手制造了第 1 章痛批过的 **缓冲膨胀**，把排队延迟拖得老高！

因此，现代拥塞控制正在百花齐放地引入更丰富的路况线索：
- **看时延和真实交付速率**：例如像 BBR 这类新一代算法，不再坐等队列填满丢包，而是主动估算路径的「瓶颈带宽」和「最小物理传播 RTT」，尽量把在途数据精准控制在带宽时延积（BDP）附近，既跑满带宽，又让路由器队列几乎保持清空、把延迟压到极低。
- **让路由器开口说真话——显式拥塞通知（ECN）**：与其让两端靠猜丢包来推断堵车，支持 **ECN**（Explicit Congestion Notification）的路由器在发现出口队列开始变长、**还没满到必须丢包之前**，就直接顺手在经过的 IP 分组首部里打上一个「前方快堵了」的标记位；接收方看到标记后，在回发的 ACK 里转告发送方，发送方不丢一个包就能提前优雅降速！

不同算法背后依然是工程权衡：激进探测能快速抢占空闲带宽，却容易推高队列和丢包；温和盯紧时延的算法交互极其丝滑，但在同一条路上遇上激进的传统丢包型老对手时，有时反而会被挤占份额。最后别忘了：**运行在 UDP 之上的 QUIC 绝不是法外之地**——它同样必须在用户态完整实现拥塞控制，否则成千上万个不踩刹车的 UDP 应用瞬间就能把公共互联网拖回 1986 年的拥塞崩溃。

## 最小完整诊断例子：为什么一开始下载，SSH 终端就卡成幻灯片？

学完第 1 章的缓冲膨胀和本章的拥塞控制，我们立刻就能破获一桩工程师日常最常遇到的悬案。

**现象**：你在家里的电脑上全速下载一个大镜像文件，测速一看下载速率跑得飞快，可顺手切回远程 [SSH](../chapter_06_security/03_remote_access_identity.md) 终端敲命令，却发现按一个字母要隔半秒屏幕才蹦出来，卡得令人抓狂。

**幕后真凶推演**：大文件下载是一条贪婪的长流，传统的基于丢包的拥塞控制一路推高 `cwnd`，把你家出口路由器那块偏大的缓冲区灌得满满当当。此时你敲下 SSH 终端里的一个按键，这个只有几十字节的迷你交互数据包刚进路由器，就绝望地发现自己排在了几百个庞大的 1500 字节下载数据包尾巴后面——这就是活生生的 **缓冲膨胀**！

**怎么用证据验证？** 极其简单：在开始下载前和下载全速跑起来之后，持续用 `ping` 观察到网关或目标服务器的 RTT。如果你看到下载吞吐稳在高位，而 RTT 却从空闲时的 `20 ms` 暴涨到 `400 ms`，铁证如山——问题根本不是「宽带不够快」，而是队列失控！治理手段也非常对症：在路由器上启用智能队列管理（AQM，如 FQ-CoDel）和公平排队（让小包交互流不再被大流堵死）、给大文件下载做温和限速，或排查本机上行带宽是否被同步任务占满导致连 ACK 都发不出去。

## 跳出网络看系统：TCP 窗口与分布式「应用背压」

如果你往更高的系统架构视角看一眼，会发现流量控制背后藏着一条放之四海而皆准的计算机系统思想——**背压**（backpressure）。

TCP 用 `rwnd` 实现的是**字节级的背压**：下游接收缓存快满时，立刻给上游发送端发信号要求降速。而在现代分布式后端系统里，消息队列、微服务网关、数据流处理引擎每天都在面对一模一样的挑战：当下游数据库或消费服务处理不过来时，如果上游生产者继续盲目狂塞任务，内存很快就会溢出崩溃（OOM）。因此应用层同样需要**业务级的背压**——限流、缩短预取队列、返回 `429 Too Many Requests` 让上游退避。两者灵魂相通，唯一区别是 TCP 只看得懂无差别的字节和缓冲区余量，而应用背压懂得「哪条任务更重要、哪个请求可以优先丢弃或降级」。

!!! question "随堂自测"
    抓包发现接收方在 ACK 里大方地通告了 `rwnd = 1 MB` 的超大接收窗口，但发送方发出去的在途数据却始终死死卡在 `64 KB` 上不去。这最可能是什么原因造成的？

    因为发送方的实际在途上限取决于 $\min(rwnd, cwnd)$ 而不是单看 `rwnd`！接收方通告 1 MB 只说明它内存充裕、不是瓶颈；发送方卡在 64 KB，最常见的原因是发送方自身的**拥塞窗口 `cwnd`** 此时只有 64 KB（比如刚经历过丢包降速，或仍处于慢启动/拥塞避免爬坡期）。除此之外，也可能是发送方本机操作系统配置的发送缓冲区上限（`SO_SNDBUF`）偏小，或者发送端应用程序自己往 Socket 里喂数据的速度本来就没那么快。
