# 传输层 { #3 }

上一章结束时，我们留了一个悬念：应用进程把数据塞进 Socket，底层的分组交换网络却是一条处处漏风的公共公路——分组可能排队溢出被丢弃、可能因为路径变化而后发先至、甚至可能在无线电波里发生比特翻转。

把数据勉强送到目标机器只是第一步。到了机器之后，还有两道硬骨头要啃：第一，机器上同时跑着浏览器、音乐播放器、聊天工具，这份数据到底该递给哪一个进程？第二，既然底下的路并不靠谱，上层程序到底想拿到什么样的服务——是宁可丢几帧也要飞快送达的独立包裹，还是哪怕多等半秒也要保证一个字节不差、顺序丝毫不乱的可靠通道？

负责在**两端的应用程序进程之间**扛起这两份职责的，就是 **传输层**（transport layer）。

站在应用层和网络层之间，传输层提供了截然不同的交付哲学：

- **UDP** 极其克制，只帮你贴上端口号、保留每次发送的消息边界，然后把包裹推出去便撒手不管，省去握手与重传的负担；
- **TCP** 则像一位一丝不苟的大管家，先握手建立连接，再用编号、回执、定时重传把不可靠的底层网络硬生生「魔法包装」成一条有序、可靠的连续字节流；
- 新兴的 **QUIC** 另辟蹊径，借道 UDP 穿过既有网络设备，在用户态把可靠传输、多路复用和加密握手揉成一体。

## 藏在传输层背后的两条端到端原则

读这两章时，心里揣着下面两条底层设计哲学，所有繁杂的机制都会瞬间顺理成章：

- **原则一：把复杂可靠性留在两端，别为难核心网络。** 沿途的 IP 路由器每秒要转发海量分组，根本没精力替全球几亿条 TCP 连接各自记账「哪个字节收到了、哪个该重发」。确认、缓存、重排和重传全由通信两端的端系统自己消化，核心网络才能保持简单高速。
- **原则二：可靠不等于「死等到底」。** 没有任何一种交付策略放之四海而皆准。下载软件安装包时，差一个比特程序都会崩溃，必须咬定可靠不放松；可打实时语音电话时，三秒前那半句「喂」就算重传回来也早已毫无意义，宁可丢掉继续听下一句，也不愿让整场通话卡住死等。

## 学完本章你能回答什么

1. 操作系统究竟靠哪几个字段，把到达同一块网卡的 IP 数据报精准送进正确的进程？
2. 为什么说 TCP 是「没有消息边界的字节流」，应用程序写代码时因此必须注意什么？
3. 当发送方迟迟等不到回执时，它凭什么判断「该重传了」？重传以后，接收方又凭什么确保同一批字节不会重复交给上层两次？
4. 为什么「发一个包、等一个回执」在高带宽长距离链路上会惨烈浪费带宽？滑动窗口和带宽时延积如何解决这个问题？

!!! question "出发前先热热身"
    假设发送方发出了数据 `ABC`，接收方其实已经稳稳收到并交给了应用程序，偏偏接收方发回的「我收到了」回执在半路丢了。发送方左等右等超时了，只好把 `ABC` 重新发了一遍。问题来了：接收方收到这份重传的 `ABC` 后，怎样避免把它再次塞给应用程序，导致对方屏幕上多出重复的 `ABCABC`？

    核心秘密在于**序号**：每个数据块或每个字节出门时都带着唯一编号。接收方一核对编号，立刻认出「这几号字节我早就收过并交差了！」，于是直接丢掉重复载荷、绝不二次交付，只是礼貌地再补发一张回执好让对方彻底安心。
