# IPv6、NAT 与 ICMP

上一节结束时，我们留下了一个天天在你家客厅路由器里上演的魔术：家里电脑、手机、平板、智能音箱全都拿着不能上公网的私有地址（比如 `192.168.1.x` 或 `10.0.0.x`），而运营商只给这户人家分配了**唯一一个**公网 IPv4 地址。

家庭网关之所以能让全家设备同时刷视频、查资料，靠的是把出门数据包的源地址悄悄改写成自己的公网地址，并在本子里记一笔账，等响应回来再按账本改回原主——这就是 **网络地址转换**（NAT，Network Address Translation）。

可细想一下，这套魔术马上就会撞上一个棘手冲突：**假如内网两台机器偏偏凑巧用了同一个源端口号去访问同一个远方网站，出门全被改成了同一个公网 IP，等对方的响应包飞回来时，路由器怎么分清该交给哪一台电脑？**

这一节我们就从这个「端口撞车」的现场出发，先拆解 NAT 的真实账本与副作用，再看看彻底打破地址荒的新一代协议 **IPv6**，最后认识在 IP 尽力而为的世界里负责「通风报信」和支撑 `ping`/`traceroute` 的幕后功臣——**网际控制报文协议**（ICMP，Internet Control Message Protocol）。

## 两个内网进程用了同一个端口，返回时怎样分开？

假设公司内网里的两台主机 `10.0.0.2` 和 `10.0.0.3` 正好在同一秒都挑中了临时源端口 `5000`，而且都去访问同一台外部网站服务器。两份数据报先后到达公司出口网关（它手握唯一公网 IP `203.0.113.7`）。

如果网关只傻傻地把两个源 IP 都改成 `203.0.113.7` 而保留原源端口 `5000`，那两份包在公网上就长得一模一样（源端都是 `203.0.113.7:5000`，目的端也完全相同），回包飞回来时网关当场抓瞎！

真正的做法要聪明得多：网关不仅改写 IP 地址，还顺手替它们**重新分配互不冲突的公网源端口**！比如把 `10.0.0.2:5000` 映射成 `203.0.113.7:40001`，把 `10.0.0.3:5000` 映射成 `203.0.113.7:40002`，并把两条对应关系死死记进内存的映射表里。等外部服务器的响应回到 `203.0.113.7:40001` 时，网关一查表立刻明白这是 `10.0.0.2:5000` 的快递，把目的地址和端口改回去交差；回到 `:40002` 的则精准递给 `10.0.0.3:5000`。

看明白这笔交易了吗？**多台内网机器共享一个公网 IP 之所以可行，代价是出口网关被迫从「无状态逐包转发」变成了「必须为每条连接记账并改写传输层端口」的有状态设备。**

??? question "既然如此，公网上一台陌生服务器，可以只凭我家的公网 IP `203.0.113.7` 主动连接我客厅里的某台电脑吗？"

    默认情况下根本连不进来！因为当一个陌生入站包突然敲响 `203.0.113.7` 的门时，网关的 NAT 映射表里压根没有对应的记录，它根本不知道该把这份包转给屋里的手机、笔记本还是电视。外部主动访问内网，必须依赖提前配好的**静态端口转发**、两端配合的穿透技术（打洞）、公网中继服务器或第 7 章会讲的 VPN 通道。

这种把地址和端口一起改写的机制，正是现实中最常见的 NAT 形态。不过在细究 NAT 的利弊之前，我们先看看从根本上消灭 IPv4 地址枯竭的终极方案——**IPv6**。

## IPv6 的动机，远不只是「地址不够用」

IPv4 诞生于互联网尚在实验室襁褓中的年代，32 比特约 42.9 亿个地址在当时看来已是天文数字；可谁也没想到今天连灯泡、手表、汽车和亿万个云容器都要联网。

**IPv6** 一口气把地址宽度扩充到了 **128 比特**——地址总数高达 $2^{128} \approx 3.4\times 10^{38}$ 个。这个数字大到什么程度？就算给地球表面每一平方毫米分配数以亿计的 IPv6 地址也远远用不完。

但 IPv6 的雄心远不止「扩大号段」，设计者趁着换代的机会，把 IPv4 攒了几十年的历史包袱也痛快清理了一遍：

- **固定精简的基础首部**：IPv6 把主首部规整成固定的 40 字节，删掉了极少用却拖慢硬件解析的变长选项，还砍掉了每跳都要重新计算的 IP 首部校验和，把可选功能统统挪到链式挂载的**扩展首部**里，让核心路由器转发更快；
- **禁止沿途路由器分片**：遇到超过 MTU 的大包，路由器直接退回 `Packet Too Big` 通知源主机自己调小再发；
- **告别传统广播，拥抱多播与即插即用**：重新设计了邻居发现与**无状态地址自动配置**（SLAAC），设备接入网络后甚至不需要专门的 DHCP 服务器，听一眼路由器发出的网段前缀通告就能自己拼出合法的全局 IPv6 地址。

IPv6 的宏愿是让世界重回「每台设备都有独立全局地址、端到端直接互通」的清爽架构；但现实中全球庞大的 IPv4 基础设施不可能一夜关停，因此 IPv6 必须长期与 IPv4 和平共存。

## 一分钟学会读写 IPv6 地址与压缩规则

128 比特如果像 IPv4 那样写成十进制会长得令人崩溃，所以 IPv6 规定按每 16 比特一组，写成 **8 组四位十六进制数**，用冒号 `:` 隔开。例如：

```text
2001:0db8:0000:0000:0000:ff00:0042:8329
```

为了书写方便，记住两条极其简单的合法压缩规则：
1. **每组内部可以省略开头的 `0`**（比如 `0db8` 写成 `db8`，`0042` 写成 `42`，全零组 `0000` 简写成 `0`）；
2. **连续的多组全零可以用一个双冒号 `::` 合并压缩**——但请注意，**整条地址里 `::` 最多只能出现一次！** 如果出现两次，你就再也算不出左右两边各自到底省略了几组零。

套用这两条规则，上面那串长地址瞬间变得清爽优雅：

```text
2001:db8::ff00:42:8329
```

反推还原也毫无难度：现在能看见 5 组非零项，总共应该是 8 组，所以 `::` 中间必然省略了 $8 - 5 = 3$ 组 `0000`。

日常排障还要眼熟几个最常见的 IPv6 特殊地址：
- `::1`：IPv6 的本机回环地址（对应 IPv4 的 `127.0.0.1`，第 2 章测试 `localhost` 时已经提过它！）；
- `fe80::/10`：**链路本地地址**，每块支持 IPv6 的网卡都会自动生成一个，只在眼前这段物理链路上有效，路由器绝不跨网转发；
- 标准子网划分几乎清一色采用 **`/64`**——前 64 位标明网络前缀，后 64 位作为接口标识。

最后切忌掉进一个危险误区：有人觉得「IPv6 空间这么大，黑客一辈子也扫描不完我的地址，那是不是就不用开防火墙了？」大错特错！公网日志、DNS 记录、出站连接、常见后缀规律（比如 `::1`）随时都会暴露你的 IPv6 地址。**「地址难猜」从来不是可靠的安全防线，明确的防火墙访问控制一刻也不能少。**

## IPv4 NAT（NAPT）如何工作，以及它的双面刃

回到目前依然无处不在的 IPv4 家庭与企业出口。前面那套同时改写 IP 和端口号的 NAT 变体，正式名称叫 **网络地址端口转换**（NAPT，Network Address Port Translation）。来看看它内存里那张核心映射表长什么样：

| 内网源地址 : 源端口 | 改写后的公网地址 : 公网端口 | 远端目标地址 : 目标端口 |
| --- | --- | --- |
| `192.168.1.10:53000` | `203.0.113.8:40001` | `198.51.100.20:443` |
| `192.168.1.11:53000` | `203.0.113.8:40002` | `198.51.100.20:443` |

数据出门时，路由器顺手查表（或新建条目），改写 IP 首部的源 IP 和 TCP/UDP 首部的源端口，再重新计算校验和送往公网；响应返回 `203.0.113.8:40001` 时，路由器按表精准还原成发往 `192.168.1.10:53000` 的内网包。

NAT 无疑立下了汗马功劳：它硬生生给 IPv4 续了几十年命，还让企业换宽带运营商、换公网 IP 时，内网几千台机器的私有地址纹丝不动。但它付出的代价也相当沉重：

- **打破端到端透明性**：它越权伸手改写了本不归网络层管的传输层端口号，还强迫边界网关为每条活跃连接保存状态和超时计时器（连接闲太久条目一清，长连接就莫名断了）；
- **让内网对外提供服务变得曲折**：你想在家里电脑架个网站或跑 P2P 联机，外网压根敲不开你的门，必须折腾端口转发、穿透打洞、公网中继或 VPN；
- **某些老协议「水土不服」**：如果某个应用协议傻傻地把内网 IP 写进了应用层报文正文里（比如早期 FTP 或语音信令），NAT 只改了外层 IP 首部，对方拿到正文里的 `192.168.1.10` 照样连不通，迫使路由器还要加装专门的应用层网关补丁；
- **运营商级 NAT（CGNAT）火上浇油**：如今许多宽带运营商连「一户一个公网 IPv4」都给不起了，干脆在运营商机房再叠一层超大 NAT 让几百户共享一个公网 IP！这不仅让普通用户彻底没法做家庭端口转发，还会引发高并发端口耗尽、线上封禁误伤同出口无辜用户、安全审计难以溯源等一连串烦恼。

最后顺手纠正一个广泛流传的误解：**NAT 不等于防火墙！** 诚然，没有映射表的陌生入站流量会被 NAT 顺带挡在门外，但这只是状态转换的副产品，而不是有意识的安全策略（比如它管不住你内网中了木马的电脑主动往外连黑客服务器）。真正的访问控制永远应该交给显式的防火墙规则。

聊完了地址空间和地址改写，网络层还有一块容易被忽视却在排障时救命的拼图：IP 只管埋头把包往外推，万一路断了、跳数用光了、包太大塞不进下一段链路了，谁来把噩耗带回给发送端？

## ICMP：IP 世界的「反馈电报」与诊断利器

这就是 **网际控制报文协议**（ICMP）的使命。它在架构上紧贴着 IP 协议（ICMP 报文直接封装在 IP 数据报里），专门承担两份工作：**网络故障报错**与**主动连通性探测**。

日常运维里你几乎天天打交道的四种核心 ICMP 消息：

- **`Echo Request` / `Echo Reply`（回显请求与应答）**：大名鼎鼎的 `ping` 命令发的就是它——向目标喊一声「在吗？」，对方回一句「我在！」，顺便测出往返时延（RTT）和有没有丢包。
- **`Destination Unreachable`（目的不可达）**：前面路断了，路由器或目标主机明确回信说明死因——常见细分包括「网络不可达（没路由）」「主机不可达」「协议/端口不可达（比如发给一个没人监听的 UDP 端口）」「需要分片但首部禁止分片」。
- **`Time Exceeded`（超时 / 跳数耗尽）**：为了防止路由配置失误酿成环路，让一个幽灵数据包在几台路由器之间兜圈子直到天荒地老，IPv4 首部装了 **TTL**（Time to Live，在这里不是 DNS 的秒数，而是**最大剩余跳数**！），IPv6 首部更名得极其直白，叫 **Hop Limit（跳数限制）**。数据包每经过一台路由器，这个数字就减 1；一旦减到 `0`，路由器立刻毫不留情地把它销毁，并朝源主机寄回一封 `Time Exceeded` 报信！
- **`Packet Too Big`（分组过大）**：在沿途不许分片的 IPv6（以及开启路径 MTU 探测的 IPv4）中，一旦路由器发现这个包塞不进下一段较窄链路，就把它丢掉并立刻寄回这封电报，顺便写明下一段链路的真实 MTU 上限，让源主机乖乖把包切小重发。

### 拍案叫绝的巧思：`traceroute` 究竟怎么画出沿途每一跳的？

知道 `Time Exceeded` 的规则后，你瞬间就能看穿经典排障神器 `traceroute`（Windows 下叫 `tracert`）背后的绝妙「碰瓷」手法：

1. 探测程序故意发出一批把 **TTL / Hop Limit 设成 `1`** 的探测包。包刚踏出家门走到第 1 台路由器，跳数一减立刻归 `0`！第 1 台路由器按规矩把它扔掉，并老老实实给自己发回一封 `Time Exceeded`——于是你白捡了第 1 跳路由器的 IP 地址和耗时！
2. 紧接着，它把 **TTL 设成 `2`** 再发一批。包平安穿过第 1 台（剩 1），走到第 2 台路由器刚好归 `0`，逼出第 2 跳的 IP 地址！
3. 依次设成 `3, 4, 5, ...`，一路步步逼近，直到探测包最终抵达目标主机收到回应，整条路径便跃然纸上！

当然，读 `traceroute` 输出时切忌盲信两点：第一，互联网路径可能随负载均衡或路由变化动态飘移，前后几跳测出来的未必属于同一个业务包的真实轨迹；第二，有些中间路由器出于安全或减负策略会直接静默丢弃而不回 ICMP 超时，表现为屏幕上的一行 `* * *`——这**绝不代表那台路由器断网了**，只要后面几跳照常亮着，说明业务流量依然稳稳穿过去了。

## 警钟长鸣：为什么千万别「一刀切禁掉所有 ICMP」？

不少初学安全配置的新手听说「别人能 ping 通我的服务器不安全」，手一抖就在防火墙里把所有 ICMP 协议统统拉黑。

这往往会亲手制造出全网最诡异、最难排查的故障之一——**路径 MTU 黑洞**！试想你和服务器之间有一段隧道链路 MTU 只有 1400 字节，发送端发了一个 1500 字节且禁止分片的大包。中间路由器好心寄回一封「包太大了，请改小到 1400！」的 ICMP 报错电报，结果被你的防火墙一把拦死！发送端死活收不到提示，一遍遍执着地重传 1500 字节的大包，于是呈现出令人抓狂的现象：**小文本请求、SSH 登录和 `ping` 全都秒通，偏偏一拉大网页或传大文件就彻底卡死不动！**

正确的安全姿态不是把 ICMP 当垃圾一棍子打死，而是按类型、方向和速率精细管控——放行至关重要的差错反馈（尤其是 `Packet Too Big` / 需要分片消息）与合理的诊断限速。

## 从 IPv4 走向 IPv6 的共存长跑

把全世界几十亿台设备从 IPv4 切到 IPv6，不可能按下某个总开关一夜切换，而是依靠三种过渡技术打持久战：

- **双栈**（dual-stack）：目前最主流的做法，让主机和路由器同时跑 IPv4 和 IPv6 两套协议栈，拿到 `A` 和 `AAAA` 记录后按连接质量择优使用（现代浏览器常用「Happy Eyeballs」算法，略微优先试连 IPv6，若几十毫秒没回音就立刻并行拉起 IPv4 快速回退，绝不让用户在坏掉的 IPv6 路径上傻等）；
- **隧道**（tunneling）：把 IPv6 包当成货物装进 IPv4 包里，穿越尚未升级的纯 IPv4 路段（第 8 章我们还会看到隧道在容器与虚拟网络里大显身手）；
- **协议转换**（translation，如 NAT64）：在纯 IPv6 客户端和老旧纯 IPv4 服务器之间架起一座实时翻译桥。

!!! question "随堂自测"
    等到将来全球普及 IPv6、每台设备都拥有花不完的公网地址之后，是不是就彻底告别 NAT 和任何类似转换技术了？

    为「省地址」而生的经典 NAPT 动机确实会彻底消退，端到端透明连接得以回归。但在部分复杂企业场景里（如多运营商出口切换、内网地址迁移不想重配策略），有时仍会出现前缀转换（NPTv6）或显式应用代理来满足管理策略。最重要的是再记一遍原则：**网络隔离和访问控制应当由清晰的路由规划与状态防火墙来承担，绝不要把 NAT 当成安全保护伞。**

一路走到这里，我们已经搞定了网络层的「门牌编制（IPv4/IPv6）」「出口改写（NAT）」和「故障电报（ICMP）」。最后，也是网络层最激动人心的核心引擎终于要揭幕了：

当一个写满目的 IP 地址的数据报冲进一台拥有几十个光纤接口的核心路由器时，它怎么在纳秒到微秒之间，从上百万条路由规则里挑出最精准的那一个出口？更神奇的是，全球几十万台由不同国家、不同商业公司各自掌控的路由器，到底靠什么算法彼此互通消息、协同算出整张互联网的指路地图？

下一节，我们走进 **转发与路由**！
