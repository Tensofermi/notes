# 转发与路由

还记得本章开头的邮政分拣中心吗？当一件包裹从传送带滑过来时，分拣员绝对不会停下机器去研究「今天全国哪条高速公路堵车、要不要修一条新铁路」——他只低头扫一眼面单，照着墙上早已贴好的分拣规则，一秒内把包裹拨进对应的滑槽。至于墙上那张分拣规则表究竟是怎么结合全国路网、车次和运费算出来的，那是幕后总调度室的活。

在计算机网络里，这两件经常被混为一谈的工作有着极其清晰的界线：

- **转发**（forwarding）：路由器收到单个数据报后，查自己本地的转发表、把它从正确的物理出口送出去的**局部高频动作**；
- **路由**（routing）：全网路由器之间彼此交换网络拓扑与策略信息、计算最佳路径并最终生成和更新转发表的**全局协同过程**。

下面我们先从路由器查表时最常碰到的一个实际冲突切入——当好几条指路规则同时对同一个目的 IP 举手说「我能匹配！」时，路由器究竟该听谁的？

## 三条规则都匹配时，下一跳选谁？

假设一台路由器的转发表里目前写着三条规则：
1. 默认兜底路由 `0.0.0.0/0` → 从出口 **A** 送出；
2. 宽泛网段 `10.0.0.0/8` → 从出口 **B** 送出；
3. 精细网段 `10.2.0.0/16` → 从出口 **C** 送出。

现在，一个发往 `10.2.3.4` 的数据报冲进来了。糟糕——这三条规则的门槛它全都合得上！`0.0.0.0/0` 匹配全世界所有 IPv4 地址，`10.0.0.0/8` 匹配所有 `10.*` 开头的地址，`10.2.0.0/16` 则精准框住了 `10.2.*` 这一小片。路由器该往 A、B 还是 C 送呢？

互联网的铁律极其符合人类直觉——**谁说得最具体，就听谁的！** 这就是大名鼎鼎的 **最长前缀匹配**（LPM，Longest Prefix Match）原则。`/16` 精确咬合了前 16 个比特，比 `/8` 和 `/0` 都更具体，因此 `10.2.3.4` 毫无悬念地走出口 **C**。紧接着再来一个发往 `10.3.4.5` 的数据报：它够不上 `/16`，同时匹配 `/8` 和 `/0`，自然听更具体的 `/8`，走出口 **B**。

??? question "假如因为链路调整，路由器删掉了 `10.2.0.0/16` 这条精细规则，原先发往 `10.2.3.4` 的包会立刻被丢掉吗？"

    不会立刻被丢掉！它依然能匹配剩下的 `10.0.0.0/8`（以及默认路由），于是会被顺势转往出口 **B**。至于数据包最终能不能真到达 `10.2.3.4`，那就要看出口 B 连着的下一台路由器手里有没有通往 `10.2.0.0/16` 的可达路径了。

明白了「查表怎么判胜负」，让我们站高一步，把路由器大脑里的两张工作台彻底分开。

## 数据平面与控制平面

在现代网络架构里，上面那组对比对应着两个核心术语：

- **数据平面**（data plane）：干的就是**转发**的活。它盯着每一个蜂拥而来的真实数据报，在纳秒到微秒级的时间尺度里高速查表、改写字段、排队发走，通常直接由专用硬件芯片（ASIC）扛大梁；
- **控制平面**（control plane）：干的就是**路由**的活。它运行在毫秒到秒级甚至分钟级的时间尺度里，靠路由协议（或者管理员的静态配置）感知链路断没断、哪家运营商便宜、哪条路更近，算完之后把最终结果下发、刷新进数据平面的转发表（FIB，Forwarding Information Base）里。

再借用一次身边的交通类比：**控制平面**就像城市交通指挥中心和导航大脑，综合全城修路、限行和拥堵信息算好全局方案，然后去路口把指示牌挂好；**数据平面**就像路口那个毫秒级放行的交警和匝道口，只看眼前的路牌把车导流出去，绝不拦下每辆车重新掏出全国地图现算一遍。两者相互依赖，却在速度和实现形态上泾渭分明。

## 最长前缀匹配：大网聚合与局部例外的粘合剂

再拿一张稍丰富一点的转发表亲手验算四组目的地址，巩固手感：

| 目的网络前缀 | 前缀长度 | 出接口 |
| --- | :---: | :---: |
| `10.0.0.0/8` | 8 | A |
| `10.1.0.0/16` | 16 | B |
| `10.1.2.0/24` | 24 | C |
| `0.0.0.0/0` | 0 | D |

逐个核对：
- 目的 `10.1.2.9`：前三条全中，但 `/24` 最长最具体 → 走 **C**；
- 目的 `10.1.8.9`：匹配 `/8`、`/16` 和 `/0`，`/16` 胜出 → 走 **B**；
- 目的 `10.9.8.7`：匹配 `/8` 和 `/0`，`/8` 胜出 → 走 **A**；
- 目的 `198.51.100.5`：前三条全落空，最后被默认路由 `0.0.0.0/0` 稳稳兜底 → 走 **D**。

仔细体会这套规则的工程美学：**最长前缀匹配让「粗粒度路由聚合」和「精细局部例外」完美共存。** 假如一家大公司把整个 `10.0.0.0/8` 都聚合到主出口 A，可偏偏其中一小块 `10.1.2.0/24` 搬到了新机房需要走专线 C——你完全不需要把庞大的 `/8` 拆得稀碎，只需多加一条精准的 `/24` 覆盖进去即可！不过，硬件要在每秒几亿次查表里瞬间挑出「最长匹配」绝非易事，高速路由器为此专门动用了极其昂贵的硬件查找电路（如三态内容寻址存储器 TCAM）和树形前缀压缩流水线。

## 慢动作回放：路由器转发一个 IPv4 数据报的六步

每当一个 IPv4 数据报从路由器的一张物理网卡进来，直到从另一张物理网卡飞出去，数据平面在微秒间一丝不苟地走完六步流水线：

1. **检验合法性**：剥掉入链路的帧外壳，校验 IPv4 首部校验和与基本格式，读取目的 IP 地址；
2. **跳数扣减防环**：把 IPv4 首部里的 `TTL` 字段减 `1`；一旦减到 `0`，立刻销毁这个迷路的包，并按策略回发一封 ICMP `Time Exceeded` 报错；
3. **重算 IPv4 首部校验和**：因为第 2 步改动了 `TTL` 字段，IPv4 路由器必须同步更新首部校验和；
4. **最长前缀匹配**：拿目的 IP 去查转发表，得出该走哪一个物理出接口，以及下一跳相邻设备的 IP 是谁；
5. **解析下一跳硬件地址**：如果需要把包送上以太网这类多点局域网，还要查一下「下一跳 IP 对应哪块网卡的 MAC 地址」（下一章就会细讲的 ARP 缓存）；
6. **换装重封与排队发送**：给同一个 IP 数据报套上出链路的新帧首尾部（源 MAC 换成路由器自己这个出口的 MAC，目的 MAC 换成下一跳设备的 MAC），放进出口队列推上线缆！

顺手留意一个极其优雅的演进细节：还记得上一节说 **IPv6 基础首部干脆取消了首部校验和** 吗？看看上面的第 3 步你就恍然大悟了——IPv4 每经过一台路由器，就因为 `TTL` 减 1 而被迫把整块首部重新做一次校验和计算，纯属拖慢核心转发！IPv6 认为底层链路层帧有更强的校验码、上层 TCP/UDP 也有端到端校验和，干脆把网络层首部校验和彻底砍掉，替核心路由器卸下一大块累赘。

看透了数据平面的六步转发，终极悬念浮出水面：路由器手里那张动辄几十万条记录的转发表，到底是谁算出来的？

## 路由算法的两种基本直觉：全局上帝视角 vs 邻里口口相传

如果一个小公司只有两三台路由器，管理员手工敲几条静态路由绰绰有余。但面对由几十万台路由器构成、每时每刻都有光纤被挖断或新链路接入的全球互联网，必须依靠**动态路由协议**自动算路并自愈。归根结底，教科书和工程界最经典的算路直觉分成两大流派：

### 流派一：链路状态（Link-State）——人手拼出一张完整地图

想象你在玩一款探险游戏，每个村庄（路由器）先把「我直接连着哪几个邻居、走过去分别要花多少代价」写成一张小公告，然后像传话接力一样向整个区域**泛洪**广播出去。

很快，区域里的**每一台路由器都收集齐了所有人的公告，在自己脑海里拼出了一模一样的完整全局拓扑地图**！有了全图，每台路由器只需各自安静地运行一次图论里的最短路径算法（经典如 Dijkstra 算法），算出从自己出发到全区每个目的网段的最优第一跳，写入转发表即可。

- **优点**：视野完整、故障后各路由器同步拿到断链公告，重新算路快、收敛可控，不易产生长久环路；
- **代价**：全区每台设备都要存储整张拓扑数据库，网络规模太大时泛洪和算路开销吃不消（因此大网往往要划成多个区域）。真实世界里广泛使用的 **OSPF** 和 **IS-IS** 正是这一流派的扛鼎之作。

### 流派二：距离向量（Distance-Vector）与路径向量（Path-Vector）——只听邻居报信

另一派则采取彻底的分布式「口口相传」策略：谁也不拼全局地图，每台路由器只维护一张「我到各个目的地大概有多远」的距离清单，然后定期把自己的清单念给直连邻居听。邻居收到后做一道简单的加法算术：「哦？你告诉我你离北京只要 3 步，而我离你只要 1 步，那我走你这条路去北京总共就只要 4 步，比我原来那条 7 步的近，更新！」（对应图论里的 Bellman-Ford 算法思想。）

- **优点**：极其直观轻量，路由器不用存全网地图；
- **致命软肋**：「好消息传得飞快，坏消息传得奇慢无比！」假如某条链路突然断了，邻居之间因为看不到全图，可能互相误信对方过时的旧距离，你指着我、我指着你，把距离从 2 一路加到 3、4、5……陷入臭名昭著的 **计数到无穷**（count-to-infinity）和路由环路！早期的 **RIP** 就是这一流派的经典教学案例。

为了保住「不共享全网内部细节」的好处、又彻底根治环路，互联网域间路由的核心协议 **BGP**（Border Gateway Protocol，边界网关协议）进化出了 **路径向量**（Path-Vector）机制：邻居通告的不再是一个孤零零的数字距离，而是**沿途经过的完整自治系统编号列表**（AS-PATH）！一旦路由器在邻居发来的路径列表里赫然看到「咦，我自己的编号居然已经在里面了！」，立刻识破这是兜圈子的环路，果断丢弃！

## 域内与域间：为什么数据包不总是走「地图上最短的路」？

把视野拉到整个地球：互联网并不是归某一家公司所有的一张大网，而是由成千上万个相对独立运营的网络拼起来的联邦。每一个由单一组织（如中国电信、某所大学、大型云厂商）统一管理的路由领地，叫作一个 **自治系统**（AS，Autonomous System）。

于是路由自然切分成两个截然不同的世界：

- **域内路由**（IGP，如 OSPF、IS-IS）：在自家公司或同一运营商的 AS 内部运行，大家是一家人，目标很纯粹——追求**连通性、低链路代价和故障快速收敛**。
- **域间路由**（EGP，现实里几乎唯一的主角就是 **BGP**）：在成千上万个不同商业利益的 AS 之间谈判。在这里，**商业合同和安全策略远远凌驾于「物理最短」之上！** 举个生活化的例子：A 运营商绝不愿意免费替两家竞争对手 B 和 C 中转跨国流量，哪怕从物理距离看绕经 A 最短；此外，运营商还会出于赚钱考量优先走付费客户的链路，出于合规或安全考量避开某些路径，并严格过滤防止邻居胡乱宣告别人家的 IP 前缀（BGP 路由劫持）。

这就解开了一个很反直觉的现实现象：你在上海发往北京的某个数据包，有时用 `traceroute` 一看居然绕道广州甚至海外转了一圈——它绝非路由器算术算错了，而是技术可达性、商业结算关系与路由策略共同博弈的结果。

## 收敛、短暂环路与等价多路径（ECMP）

无论算法多聪明，当某根骨干光纤被挖掘机一铲子挖断时，全网路由器不可能在同一纳秒瞬间同时切换完毕。从故障发生到全网所有路由器的转发表重新达成一致，这段过渡期叫作 **收敛**（convergence）。

在收敛的短短几百毫秒甚至几秒里，新旧视图交错，极易出现**短暂路由黑洞**（包被送进死胡同）或**短暂转发环路**（A 把包发给 B，B 还没收到更新又把包发回给 A）。此时，前面提过的 `TTL / Hop Limit` 就像一道保险丝，防止兜圈子的包把链路带宽瞬间打爆；而现代协议则靠快速链路故障检测（如 BFD）、增量更新、防抖动抑制等技巧拼命压缩收敛时间。

还有一种常见场景：从当前路由器出发去往目标网段，恰好有两条甚至八条代价完全相同的并列好路（比如数据中心机柜之间多条并联高速光纤）。只用一条太浪费，于是路由器启用 **等价多路径**（ECMP，Equal-Cost Multi-Path）把流量均匀分摊到所有等价出口上。

这里藏着一个极精妙的工程细节：**路由器能按「逐包随机轮询」把同一条 TCP 连接的第 1 个包走左路、第 2 个包走右路吗？** 千万不能！一旦左右两路排队时延略有差异，同一条 TCP 流的包就会疯狂后发先至（严重乱序），瞬间触发第 3 章学过的「3 个重复 ACK 快速重传」和第 4 章的拥塞降速，吞吐断崖暴跌！因此 ECMP 通常对每个包的**五元组做哈希计算**，确保同一条连接流始终稳稳走同一条路，把不同连接分散到不同路上。这也顺便解释了为什么在大型网络里跑 `traceroute` 有时同一跳会交替跳出好几个不同的路由器 IP——因为探测包落到了不同的等价路径上！

## 历史演进：软件定义网络（SDN）带来了什么新思路？

回顾过去几十年，传统路由器是典型的「黑盒一体机」：每台硬件盒子里既跑着转发芯片（数据平面），又自己跑着 OSPF/BGP 算路软件（控制平面），彼此靠复杂的分布式协议猜着合作。

到了云计算和超大规模数据中心时代，成千上万台服务器与虚拟网络频繁扩缩容，逐台登录路由器改配置根本玩不转。于是 **软件定义网络**（SDN，Software-Defined Networking）应运而生：它把**控制平面从一台台分散的硬件盒子里抽离出来，逻辑上集中到一套可编程的软件控制器里**；控制器掌握全网全局视图，通过标准接口把算好的流表/转发表直接下发给底下专心高速转发的交换设备，让网络像写代码一样实现自动化编排。

当然，SDN 绝不是银弹：集中控制器自身必须做成高可用集群，不能成为一挂全挂的单点故障；下发规则时还要应对分布式状态一致性、大规模性能瓶颈，以及万一底层设备暂时和控制器失联时该怎么本地降级保命。最后一定纠正一个常见误解：**控制平面「逻辑集中」，绝不意味着所有业务数据包都要绕路穿过控制器！** 绝大多数普通业务包依然在底层数据平面里以线速直奔目的地，控制器只在背后运筹帷幄、制定规则。

!!! question "随堂自测"
    既然路由表里已经配置了无所不包的默认路由 `0.0.0.0/0`，那为什么路由器表里依然要保留那么多更具体的前缀条目（如 `/24`、`/16`）？

    因为默认路由 `0.0.0.0/0` 只是「前面所有更具体规则全都没匹配上时的最后兜底出口」。路由器必须靠更具体的前缀来精确表达本机直连子网、公司内部各分支网段以及走特定专线的策略例外；而**最长前缀匹配**保证了具体规则永远优先于宽泛的默认兜底生效。

## 和算法课连起来

学到这里你会发现，计算机科学的底层脉络其实是相通的：链路状态路由（OSPF/IS-IS）在本地跑的是典型的单源最短路径，距离向量路由（RIP）则脱胎于分布式松弛迭代。不妨回头翻一眼算法笔记里的<a href="../../DataStructuresAndAlgorithms/chapter_graph/shortest_paths.html">最短路径</a>，对比纸上干净的静态图和现实中的互联网，问自己三个真正在系统工程里才冒出来的新问题：在没有上帝视角的网络里，谁最先知道某条边权变了？变化消息怎样跨越异步网络传遍全网？在消息还没传完的短暂瞬间，各节点算出的局部不一致结果会不会酿成环路？

现在，把视线紧紧盯住刚才「路由器转发六步」里的**第 5 步和第 6 步**——路由器已经决定了「下一跳是眼前这台邻居设备」，数据报即将彻底离开网络层，变成一帧物理信号踏上眼前这根网线或这片无线电频谱！

可就在这「最后一段一跳链路」里，一堆崭新的底层难题正等着我们：信号在铜线和空气里传错了比特怎么用数学方法一抓一个准？十几台手机连在同一个 Wi-Fi 频道上同时开口说话怎么不撞成一团乱码？交换机刚通电时一张表都是空的，怎么神奇地「自学成才」记住每个插口连着谁？以及那个被提过好几次的问题——只知道下一跳的 IP 地址，电脑究竟怎么问出对方的网卡 MAC 地址？
