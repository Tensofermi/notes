# TLS 与可信连接

当你坐在公共 Wi-Fi 下打开一个银行网站准备输入密码时，你和这台素未谋面的远方服务器之前从未私下碰过面、也没提前约定过暗号。偏偏中间整条网络路径上处处都有可能藏着窃听者和冒牌货。

问题来了：**两个素不相识的陌生人，如何当着全网窃听者的面，在几毫秒内既确凿验明对方的真实身份，又凭空商量出一把只有彼此知道的秘密钥匙，把后续所有对话锁进坚不可摧的密道里？**

完成这场密码学奇迹的，就是现代互联网无处不在的 **传输层安全协议**（TLS，Transport Layer Security）——HTTPS 地址栏里那把小锁，靠的就是它。在正式传送任何应用数据之前，客户端和服务器会先交换一轮专门用来核验身份、对齐加密参数的控制消息，称为 **握手**（handshake）。握手中极其关键的一步，是服务器向浏览器出示一张数字 **证书**（certificate）。

但很多初学者都有一个天真的误解：「服务器给了张证书，握手不就稳了吗？」远远不够！拿到证书的那一瞬间，浏览器其实紧盯着两个绝不能放过的致命追问。

## 服务器递来一张证书，浏览器还要追问哪两个问题？

假设你要访问 `api.example.test`，对面的服务器递过来一张数字证书。所谓证书，本质上是一张经过权威公证处（证书颁发机构，**CA**，Certificate Authority）盖章签名的「网络身份证」，上面白纸黑字写着：「`api.example.test` 这个域名，对应的公开钥匙（公钥）是 XXX。」

浏览器拿到这张证书，绝不会直接拍手叫好，它立刻连问两个核心问题：

1. **「这张身份证是真的吗？上面写的名字是我要找的人吗？」** 浏览器会沿着证书上的数字签名一路往上验，确认签名确实出自自己操作系统/浏览器预先信任的根 CA 体系，同时核对证书里写的域名列表里确确实实包含 `api.example.test`，且当前时间没过期。
2. **「证书是公开谁都能顺手复制一份的——你怎么证明你本人就是这张身份证真正的主人，而不是捡了别人身份证的冒牌货？」** 这一问一针见血！因为任何人都可以连一次真网站，把真网站的公开证书原封不动抄下来拿去糊弄受害者！要自证清白，服务器必须动用那把**绝不公开、只锁在自己机房内存里的配对私钥**，对当前这次握手的新鲜随机内容现算一份数字签名交出来。浏览器用证书里的公钥一验签，立刻水落石出——只有手握真私钥的本尊，才签得出这份独一无二的答卷！

两问全过关后，双方再联手协商出本次连接专属的对称会话密钥，正式开启加密通信。

??? question "假如一家公司省事，拿自己另一台服务器 `shop.example.test` 的完全合法有效证书，直接部署到 `api.example.test` 上，浏览器会放行吗？"

    绝对拒之门外！浏览器会立刻弹出醒目的安全警告。因为「签名链合法有效」和「证书上的名字匹配当前请求的主机名」是两项彼此独立的强制核检——就像你拿着隔壁张三货真价实的真身份证，也不能用来证明你是李四。只要任何一项不通过，身份锚点就宣告破裂。

把这场「双问验身」看懂后，我们打开 TLS 的工具箱，看看它究竟借用了哪三种密码学积木，才把「速度」与「安全」同时拉满。

## 动机与三类密码学工具的黄金搭档

裸奔的明文 HTTP 穿过 Wi-Fi 热点、运营商网关和一串路由器，任何中间环节都能像读明信片一样一览无余，甚至顺手把下载的软件悄悄替换成木马。TLS 站在传输层与应用层之间，靠精准搭配三类密码学工具各展所长：

1. **密码学哈希函数**（cryptographic hash，如 SHA-256）：把任意长度的数据瞬间榨成一段固定长度、几乎不可能碰撞的「数字指纹（摘要）」。改动原数据哪怕一个比特，摘要就会面目全非。但它自己**不含秘密密钥**，单靠哈希防不住主动把数据和摘要一起掉包的攻击者，常用来构建签名和密钥派生结构。
2. **对称加密**（symmetric encryption，如 AES-GCM、ChaCha20-Poly1305）：加解密用同一把秘密钥匙，硬件加速下速度动辄每秒数 GB，极适合大批量应用数据的实时加解密；唯一的软肋是「事先怎么在不可信网络上把这把共同钥匙安全交给对方」。
3. **公钥密码 / 非对称加密**（public-key cryptography，如 RSA、椭圆曲线 ECDHE/ECDSA）：每人配成对的「公钥（公开）」和「私钥（保密）」。它计算开销比对称加密大上百倍，不适合直接加密几个 GB 的大文件，却能干两件对称加密干不了的绝活——**数字签名验身份**，以及在陌生人之间**当众协商出共同秘密**！

TLS 的精妙之处在于绝不硬碰硬，而是让三者完美分工：**握手阶段**用公钥密码验证证书身份，并让两端用临时密钥材料现场算出一份外人无从破解的共同秘密；随后用哈希函数把这份秘密派生出本次连接专用的**对称会话密钥**；一旦进入**数据传输阶段**，立刻切换成飞快的对称加密——而且不是光加密就算完，而是采用 **带关联数据的认证加密**（AEAD，Authenticated Encryption with Associated Data），每发一小块数据同时搞定「加密防偷看」与「认证标签防篡改」。

## 证书究竟担保了什么（以及它不担保什么）？

浏览器拿到服务器证书后，会一丝不苟地执行四项硬核检查：

1. **主机名匹配**：证书里的主题备用名称（SAN）是否精准覆盖你地址栏里请求的域名；
2. **时间有效**：当前系统时钟是否落在证书的生效期与过期日之间（所以电脑主板电池没电导致系统时间跳回 1970 年时，所有 HTTPS 网站都会瞬间报证书错误！）；
3. **信任链完整**：服务器证书的签名能不能一路向上追溯验证到本机内置信任库里的某张**根证书**（Root CA），且未被吊销；
4. **用途与算法合规**：证书允许用于服务器身份认证，且签发和密钥算法未过时降级。

但请始终保持清醒：**证书只证明「某个受浏览器信任的签发体系，确认这把公钥属于这个域名」——它绝不证明这家网站是个正经良心商家！** 骗子完全可以花几十块钱注册一个长得极像银行的域名（比如 `bank-login-verify.test`），再免费申请一张完全合法的 HTTPS 证书，地址栏照样亮起一把漂亮的锁。此外，你信任谁的根证书库、以及 CA 机构签发流程是否严谨，本身也是整个信任体系的核心安全边界。

## TLS 1.3 最小握手：一次往返敲定一切

为了把延迟压到极致并彻底清除历史包袱，现代主流的 **TLS 1.3** 把繁琐的旧版两轮握手精简到了极致的 **1 个往返时延（1-RTT）**。省略可选分支后，整场握手如行云流水般简洁：

```text
客户端                                        服务器
  | --- 1. ClientHello: 支持版本、密码套件、   ---> |
  |        临时密钥份额（Key Share）、随机数         |
  | <--- 2. ServerHello: 选定参数、临时密钥份额  ---|
  |         [以下已用握手密钥加密！]                 |
  |         服务器证书、用私钥签出的握手签名、Finished |
  |                                                 |
  | （客户端校验证书与签名；双方各自独立算出对称会话密钥）|
  | --- 3. Finished（握手完成证明）             ---> |
  | <===== 双方使用 AEAD 认证加密畅快互传应用数据 ====> |
```

这里藏着一个让无数人拍案叫绝的密码学特性——**前向保密**（Forward Secrecy，常称 PFS）。

TLS 1.3 强制使用**临时** Diffie–Hellman 类密钥交换（如 ECDHE）：每次建立新连接，客户端和服务器都会现场临时生成一对「用完即焚」的短命密钥份额互相交换，在旁人全程偷听的情况下通过数论难题各自独立推导出只有双方知道的共享秘密；连接一关闭，这批临时密钥立刻从内存彻底抹掉！

为什么这如此重要？设想一位极其耐心的间谍，今天先把你访问某网站的加密流量全部原封不动录进硬盘存起来。哪怕五年之后，那家网站的服务器不幸被黑客攻破、**长期证书私钥彻底泄露**，间谍翻出五年前录下的密文试图解密——结果他依然束手无策！因为当年用来加密流量的对称会话密钥，是靠那对早已灰飞烟灭的「临时密钥」算出来的，长期私钥当年只负责签了个名证明身份，根本解不开历史密文！当然，前向保密保护的是「过去被录下的密文」，如果端点**此时此刻**已经被木马入侵，黑客直接读内存明文照样拦不住。

除此之外，TLS 1.3 大刀阔斧地砍掉了几十种早已脆弱不堪的老旧加密套件（如 RC4、SHA-1、静态 RSA 密钥交换）和繁杂的握手分支。在安全工程里，**删减复杂度、收窄出错表面积，本身就是最硬核的安全升级。**

## 记录层与 AEAD：为什么绝不要「自己手搓加密」？

握手尘埃落定，应用层源源不断塞下来的 HTTP 字节会被 TLS **记录层**（record layer）切分成一块块规整的记录。每一块记录都交由 **AEAD** 引擎处理：输入包括会话对称密钥、一个在同一密钥下**绝对不能重复使用**的序号/一次性数值（**nonce**），以及虽然明文发送但必须防止被篡改的头部关联数据；输出则是密文外加一小段防篡改的**认证标签**（authentication tag）。

接收方拿到记录后，必须先拿密钥核验认证标签。只要认证标签差了一个比特，协议栈就立刻把整条记录彻底拒收并断开警报，**绝不允许把哪怕一个未经认证的字节吐给上层应用程序**。

历史上，无数自研加密协议都倒在了两个低级坑里：一是在同一把密钥下不小心复用了同一个 `nonce`（对流式或 GCM 类加密，复用一次 `nonce` 就足以让攻击者直接反推出明文异或值甚至伪造任意认证标签！）；二是随便拿「普通加密 + 自己拼个哈希」乱凑组合，结果漏出「填充预言机」等致命侧信道漏洞。成熟标准协议如 TLS 的真正价值，就是替全行业把密钥派生、nonce 递增、错误处理和状态机严丝合缝地标准化下来。

## SNI 与 ALPN：单 IP 托管百个网站时，怎么挑对证书？

实际部署 HTTPS 时，紧接着会冒出两个极聪明的握手小插件：

- **服务器名称指示**（SNI，Server Name Indication）：早年一个公网 IP 往往对应一个网站，可如今云端一台服务器或一个反向代理 IP 后面动辄同时托管着几百个不同域名！问题来了：TLS 握手发生在 HTTP 请求发送**之前**，服务器还没看到 HTTP 里的 `Host: example.com` 首部，怎么知道此刻该掏出几百张证书里的哪一张给浏览器呢？**SNI** 化解了这个「先有鸡还是先有蛋」的困局——让客户端在第一条 `ClientHello` 里就明明白白写上「我要找的是 `example.com`」，服务器一看立刻精准奉上对应的证书。
- **应用层协议协商**（ALPN，Application-Layer Protocol Negotiation）：顺便在同一次 TLS 握手里捎带一句「咱俩一会儿是用 HTTP/2 还是 HTTP/1.1 聊？」，省去握手结束后再单独多跑一个来回的协商耗时！

不过，传统的明文 SNI 也带来了一个隐私小尾巴：虽然网页内容全加密了，但沿途旁观者扫一眼 `ClientHello` 里的明文 SNI，照样能看清你正在访问哪个域名。为此，较新的扩展（如加密客户端问候 ECH）正在探索把 SNI 等握手元数据也一起藏起来；但即便如此，通信双方的 IP 地址、连接起止时间和数据包大小分布这些流量特征，依然难以凭单层加密彻底隐身。

## 会话恢复与 0-RTT：为快这半拍，要冒什么险？

对于经常回访的老网站，每次重连都重走完整握手还是略显奢侈。TLS 允许客户端在首次成功连接后领一张服务器加密签发的「**会话恢复票据**」（session ticket），下次再连时出示票据即可大幅简化握手。

TLS 1.3 甚至把速度推向了极致——**0-RTT（零往返早期数据）**：老熟客重连时，不等服务器回第一句话，就在发出 `ClientHello` 的同一个数据包里，顺手把第一条 HTTP 请求（早期数据）直接加密塞进去发了！

快是真快，可它付出了一个极其危险的安全代价——**0-RTT 早期数据缺乏抗重放保护！** 因为此时服务器还没来得及给客户端发回本轮的新鲜随机数，沿途潜伏的攻击者完全可以把你发出的那个 0-RTT 数据包原封不动截下来复制十份、往服务器狂重发十遍！服务器收到后每一份都能合法解开！因此，**绝不能把转账、下单、修改密码这类带有副作用的非幂等操作放进 0-RTT**，只应放行天然幂等（如只读 `GET`）或应用层自带严格一次性防重放去重机制的请求。

## 亲手拆开一次 TLS 握手

在终端里用一条 `openssl` 命令，就能把远方网站握手的版本、选定的密码套件、完整证书链和校验状态看得一清二楚：

```bash
openssl s_client -connect example.com:443 -servername example.com
```

注意后面那个 `-servername example.com` 参数，它正是手动指定 **SNI**！你可以试着把 `-servername` 删掉或者故意写错，经常会亲眼撞见运维排查里的经典怪现象：「直接用 IP 拼端口明明连上了，服务器却吐出一张风马牛不相及的默认兜底证书，导致校验报错！」

## 别踩这些常见误区

- **地址栏有小锁 ≠ 网站可信**：小锁只代表「连接满足浏览器的传输加密与域名证书核验」，绝不代表网站背后不是钓鱼骗局；
- **代码里千万别顺手写 `verify=False` 跳过证书校验**：很多新手在测试环境遇到自签名证书报错，随手把校验开关一关就上线了——一旦跳过校验，中间人就能分别和你、和真服务器各自握手加密，在中间大摇大摆偷看所有明文，整套加密形同虚设！
- **看清反向代理后的那一段**：如果 HTTPS 在公司入口的反向代理处就解密终止了（TLS 终止），那从代理到内网后端服务器那一段是不是明文、需不需要额外加密保护，取决于你的内网威胁模型；
- **终端与私钥失守全盘皆输**：私钥误传公开仓库、日志不小心把明文密码打出来、或者电脑中了木马，全都能轻而易举绕开最坚固的 TLS 通道。

!!! question "随堂自测"
    假设我们设计了一套只做「临时密钥交换 + 对称加密」，但**完全省去数字证书身份认证**的加密协议。为什么它依然拦不住积极活跃的中间人攻击？

    因为没有身份认证，客户端根本不知道对面正在和自己协商密钥的究竟是真银行，还是坐在咖啡馆隔壁桌的攻击者！攻击者可以轻而易举地「两头瞒」：一边冒充银行和你完成密钥协商建立加密通道 A，另一边冒充你和真银行完成密钥协商建立加密通道 B。你的数据用通道 A 加密发给攻击者，攻击者解开偷看甚至篡改后，再用通道 B 重新加密发给真银行——两端都以为自己在加密通信，其实全程都在攻击者眼皮底下裸奔！正是数字证书把公钥和预期域名牢牢焊死，才斩断了这种冒充。
