# HTTPS、SSH 和 VPN 分别管哪段连接

无论是日常办公还是维护线上服务器，你几乎每天都在和「加密远程访问」打交道，手头最常用的不外乎三件法宝：

- 浏览器打开后台页面或调用接口时，靠 **HTTPS**；
- 在终端里远程登录到另一台 Linux 机器敲命令、传文件或做端口转发时，靠 **安全外壳协议**（SSH，Secure Shell）；
- 出差在外、想让手里的笔记本像插着网线坐在公司工位上一样访问整片内网时，靠 **虚拟专用网络**（VPN，Virtual Private Network）。

初学者极容易把这三者揉成一团：「反正都加密了，我连着公司 VPN 呢，里面的 HTTP 还需要 HTTPS 吗？SSH 登进去了，怎么还提示我没权限读文件？」

其实，HTTPS、SSH 和 VPN 保护的是完全不同层级的连接边界，各管一段、互不替代。这一节，我们就顺着一次再真实不过的远程开发工作流，把请求一路穿过的每一道身份门禁全部标出来。

## 一条远程操作，究竟穿过了几道独立的身份检查？

想象这样一个场景：你在家办公，想查看公司内网一台研发工作站上的实验报告 `/project/result.txt`。你按习惯做了三步动作——先点开客户端连上公司 **VPN**，再在终端敲 `ssh dev@workstation` 登录机器，最后执行 `cat /project/result.txt`。

看似一气呵成的一串动作，在系统眼里其实是**三道彼此完全独立、谁也不替谁担保的关卡**：

1. **第一关：网络可达边界（VPN / 私有覆盖网络）**。你在家里本来根本路由不到公司内网的私有 IP（如 `10.20.0.50`）。连上 VPN 并通过企业账号或设备证书认证后，VPN 在公网上架起一条加密隧道，给了你一张「允许进入公司内网车道的通行证」——此刻，你的数据包终于能到达那台工作站的网卡门口了。
2. **第二关：主机与登录身份边界（SSH）**。数据包到了工作站 `22` 端口，SSH 客户端先核对工作站出示的**主机密钥指纹**（防止有人在局域网里冒充这台工作站！），紧接着工作站核验你出示的 **SSH 私钥签名或口令**，确认你确实有权以 `dev` 用户的身份开启一个远程终端会话。
3. **第三关：操作系统进程与文件权限边界（OS 内核授权）**。终于拿到了远端命令行，你敲下 `cat /project/result.txt`。此时网络协议早已退居幕后，工作站的操作系统内核接管安检：它检查当前 `shell` 进程所属的用户 `dev`、所在的属组，以及 `/project` 目录和 `result.txt` 文件的读权限位（或访问控制列表 ACL），决定放行还是当场拒之门外。

把这三道门画在同一张图上，一个极容易犯的认知错误瞬间烟消云散：**换一种更高级的网络接入方式（比如从普通网换成公司 VPN），并不会也不应该自动让你在目标主机上多出任何文件读写权限！** 每一层只认自己那把钥匙，清清爽爽。

??? question "如果 VPN 已经顺利连上且能 ping 通工作站、SSH 也成功登录拿到了命令行提示符，但在读取 `/project/result.txt` 时却提示 `Permission denied`（拒绝访问），应该先查什么？"

    千万别去重启 VPN 或折腾 SSH 密钥配置！既然你已经稳稳拿到了远端命令行，说明第一关（VPN 网络路由）和第二关（SSH 身份登录）早已 100% 通关！此刻拒绝你的是第三关——工作站的操作系统内核。应当直接运行 `id` 核对当前登录的实际用户和属组，再运行 `ls -ld /project /project/result.txt` 检查目录的执行进入权限与文件的读权限（以及挂载选项或安全模块限制）。

**先修**：[TLS 与可信连接](01_tls.md)、[基本威胁与分层防御](02_threats_defenses.md)。

**读完能做**：面对任何一次跨网远程访问，都能迅速画出路径上每一段加密隧道的起止点，以及各段分别由谁做身份认证与权限裁决。

## 同一台工作站，三种入口的精准对比

把 **HTTPS**、**SSH** 和 **VPN** 并排摆在桌面上，看清它们各自站在哪一层、守护哪一段路、又留下了哪些必须由别处核对的盲区：

| 访问入口 | 典型作用层级 | 它保护的范围（起止点） | 通过这一关后，**仍然必须**核对的事 |
| --- | --- | --- | --- |
| **HTTPS** | 应用 / 传输安全（TLS） | 浏览器或 API 客户端 ↔ **TLS 终止点**（服务器或反向代理）之间的单条应用连接 | 服务器域名与证书链、登录后的应用级身份与权限，以及反向代理之后到真实后端的那一段链路 |
| **SSH** | 应用层加密会话 | 本机 SSH 客户端 ↔ 目标主机 SSH 服务进程之间的交互终端、文件传输（SFTP/SCP）或端口转发通道 | 目标主机密钥是否可信（防首次连接被中间人调包）、登录账号权限、以及在主机上实际能执行哪些命令和读写哪些文件 |
| **VPN / 私有覆盖网络** | 网络层 / 隧道封装 | 本机虚拟网卡 ↔ VPN 网关或对等节点之间的加密 IP 隧道 | 设备接入后究竟获准访问内网哪些子网与端口（防火墙策略），以及目标服务自己的应用认证与授权 |

再细品一个极其重要的运维安全准则——**凭据按用途严格隔离**。

假设你是运维人员，通过 VPN + 个人 SSH 密钥登录工作站排查问题；与此同时，这台工作站上还跑着一个自动化后台任务，需要定时拉取某份数据集或调用上游 API。**千万不要图省事，把运维人员用来登录整台机器的个人 SSH 私钥（或者万能管理员账号）直接塞进自动化业务进程里！** 应当为工作进程签发权限严格收敛、只够读那一个任务目录或那一个接口的独立短期凭据。这样一来，哪怕业务进程代码出漏洞被攻破，攻击者也拿不到运维登录凭据去接管整台工作站；反过来，运维人员离职吊销个人 SSH 密钥时，也不会莫名其妙把线上自动化任务一并弄崩。

## 排障与架构的必答题：先认清 TLS 到底终止在哪里！

在现代网站与云端后端架构里，浏览器往往并不是直接连到写满业务代码的后端应用服务器上，中间常常站着一层专门接待外部流量的入口——第 9 章会细讲的 **反向代理** 或负载均衡器（比如 Nginx、云网关）：

```text
浏览器  =====[ HTTPS / TLS 加密段 ]=====>  反向代理  -----[ 内部转发段 ]----->  后端应用服务
                                           ▲
                                      TLS 终止点
```

这里藏着一个架构评审时必问的关键问题：**HTTPS 的加密保护到底是在哪一台机器上解开的？**

在上面这张图里，客户端校验的证书、协商的对称会话密钥，终点都在**反向代理**处——这个把加密流量解开还原成明文 HTTP 的位置，叫作 **TLS 终止点**（TLS termination point）。

看清这个终点，两个实践要点立刻浮现：

1. **反向代理之后不是自动加密的「安全真空」**：客户端只能证实自己到反向代理这一段安全无虞；至于反向代理转发给后端应用服务的那一段，究竟是跑在严密隔离的私有机房网段里，还是穿过共享多租户云网络需要再补一段新的 TLS（甚至双方互相验明证书的**双向 TLS**，mTLS），必须根据你的内网威胁模型显式决定，绝不能糊里糊涂假定「对外配了 HTTPS 就全线加密了」。
2. **审计日志的「该记」与「绝不该记」**：反向代理和后端服务通常会为每条请求分配全局唯一的请求编号（Request ID），并把「谁发起的（身份主体）、访问了什么资源、执行结果是什么」记进审计日志，方便事后串联整条链路追责。但切记严守底线——密码、会话 Cookie、API Token、SSH 私钥和敏感业务输入，必须严格过滤脱敏，绝不允许大摇大摆写进明文日志文件里。

## 随堂自测

你出差在酒店里连上了公司的 VPN，接着用 SSH 登录进了研发工作站，可运行脚本读取 `/project/result.txt` 时，操作系统却返回了 `Permission denied`（没有权限读取文件）。请分层次指出：这条路径上哪些关卡已经顺利通过，究竟是哪一层拒绝了这次请求？如果要安全地放行这个任务，应该怎么改？

??? note "参考思路"
    在这条链路上，**VPN 隧道（网络可达与设备接入）** 和 **SSH 会话（主机身份校验与用户登录认证）** 都已经完全通过——连接早已建立成功。拒绝请求的是最末端工作站的**操作系统内核授权层**，它在检查当前运行进程的用户身份（UID/GID）、挂载属性以及目标目录与文件的访问权限后判定越权。

    要安全地给这个任务开通权限，切忌一把梭把整个目录改成 `chmod 777` 或直接给该用户开 `root` 管理员权限！遵循**最小权限原则**，应当只为执行该任务的专用账号或属组开放 `/project/result.txt`（及沿途目录的进入权限）所需的最小**只读**权限。
