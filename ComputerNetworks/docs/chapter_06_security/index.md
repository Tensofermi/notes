# 网络安全 { #6 }

想象这样一个再平常不过的午后：你坐在街角咖啡馆里，连上店里的公共免费 Wi-Fi，准备打开浏览器登录网上银行转一笔账。

经过前六章的历练，你此刻的脑海里已经能清晰看见数据包离开笔记本后的凶险处境：同一片无线电波覆盖范围内的任意一台陌生电脑都能静静「旁听」你的信号；局域网里有人可以发伪造 ARP 抢走默认网关的位置；沿途十几个素未谋面的运营商路由器和中间节点，随时可以偷看、篡改甚至冒名顶替。

面对这样一条步步漏风的公共信道，哪怕完全不懂密码学，你也一定会本能地提出三个最朴素的底线要求：

1. **别让人偷看**：我敲下的账号、密码和转账金额，旁观者哪怕全抓走也必须像看天书一样读不懂；
2. **别认错对象**：对面收走我密码的，必须确确实实是那家真银行，而不是坐在咖啡馆角落里搭了个假热点的骗子；
3. **别被人冒用**：登录进去之后，每一个查账和转账指令都必须确凿无疑是我本人发出的，既不能被半路篡改数字，也不能被复制重放扣两次款。

**网络安全**（network security）这一章，就是要把这三个朴素的愿望，一步步落到真实运转的协议与系统边界上。

## 先立规矩：安全不是按下一个「加密开关」

互联网诞生之初的首要目标是「把全世界连起来」，早年的许多基础协议（HTTP、DNS、ARP、BGP）在设计时几乎默认「路上的同行都是好人」。安全工程则把视角彻底倒转：**默认整条通信路径随时可能被偷窥、拦截、篡改与伪装。**

更重要的是，安全从来不是买一款神秘产品或者点一下「开启加密」就能一劳永逸的。它是一整套各司其职的防线协同作战：密码学算法保护传输字节，数字证书把公钥和真实身份绑在一起，随机挑战与序号防止旧报文被重放，防火墙和最小权限原则限制越权访问，日志监控帮我们在失守后第一时间察觉异常——而最顶层的应用程序自己，照样必须把好输入校验和会话管理的大门。

## 问「安不安全」之前，先画好威胁模型

在安全工程里，脱口而出问「这个系统安全吗？」其实是一个没法回答的空洞问题。专业做法是先定好 **威胁模型**（threat model），把四件事摆上台面说清：

- **要保护什么资产？**（是用户的登录态、银行交易，还是服务器上的源码？）
- **假设对手有多大本事？**（是咖啡馆里只能被动旁听的普通黑客，是能主动拦截改包的局域网中间人，还是已经攻破了某台服务器的内鬼？）
- **哪些组件是必须信任的锚点？**（比如操作系统的根证书库、本地终端硬件没有中木马。）
- **万一这道防线失守，爆炸半径有多大？**

举个一目了然的例子：公共 Wi-Fi 上的旁观者可以肆无忌惮地抓包、注入伪造 ARP/DNS，却通常篡改不了你浏览器内置的根证书库——因此 HTTPS 能把他牢牢挡在门外；可如果你的电脑本身中了恶意插件，或者远方服务器已经被黑客攻陷，攻击者就站在加密通道的终点直接坐看明文，此时再强的 TLS 也回天乏术。

围绕威胁模型，安全工程通常权衡五大核心目标：

- **机密性**（confidentiality）：未经授权的旁观者看不懂通信内容；
- **完整性**（integrity）：传输或存储中的数据只要被改动哪怕一个比特，接收方就能立刻察觉；
- **认证**（authentication）：确凿核验通信对端（以及发起操作的主体）到底是不是它自称的那个人；
- **可用性**（availability）：即便遭遇突发故障或恶意流量洪泛，合法用户依然能正常获得服务；
- **授权与审计**（authorization & auditing）：确认身份后只放行其被允许的操作，并留下可供事后追责溯源的证据链。

现实中，这五个目标经常互相拉扯：为了强审计把所有请求细节全写进日志，万一日志库泄漏反而成了新的泄密重灾区；把认证门禁卡得死紧固然安全，可一旦紧急故障时连值班运维都被锁在门外，又会重创可用性。

!!! warning "永远看清保护边界"
    TLS 保护的是「数据在网络传输途中」这一段通道，它**治不了**用户设的弱密码、后端代码里的 SQL 注入漏洞、居心不良的钓鱼服务器，也挡不住潜伏在你电脑里的木马病毒。做任何安全结论时，永远要加上那句定语：「在什么假设下，保护了哪一段边界」。
