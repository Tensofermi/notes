# 综合练习：从远程请求到 Agent 沙箱

上一篇的网页访问属于典型的「同步短交互」：发出请求，几百毫秒后网页正文就回来了，整个生命周期紧绑在一次 HTTP 往返里。

可今天越来越常见的一类云端架构，彻底打破了这种「一手交钱一手交货」的简单节奏——比如把一个能自主读文件、跑代码、调工具的 **Agent（智能体）** 部署在云端远程工作站上。为了防止这个自动化程序手抖删掉宿主机重要文件或者乱连内网敏感接口，系统通常会把它关进一个资源和文件视野都严格受限的 **沙箱**（sandbox，常见如容器或轻量虚拟机）里运行。

这时候，一个让无数开发者抓狂的新现象出现了：**你在网页控制台点击提交任务，页面立刻笑眯眯地弹出一句「任务已接受（任务号 `J7`）」，可苦等了足足五分钟，任务进度条却纹丝不动，压根还没开始执行！**

这正是异步分布式系统与传统 Web 最本质的分水岭——**HTTP 返回「已接受」，只证明提交受理这一半走通了，后面真正的队列、工作进程和沙箱还没经受考验！** 这一节，我们就把前面十章学过的网络入口、TLS 代理、私有覆盖网络、容器沙箱以及操作系统保护机制全部拧成一根绳，顺着任务号 `J7` 一路追进执行现场。

**先修**：[从虚拟网卡到隧道](../chapter_09_virtual_network/01_interfaces_bridges_tunnels.md)、[服务发现、代理与负载均衡](../chapter_09_virtual_network/02_service_discovery_proxies.md)、<a href="../../OperatingSystems/chapter_06_protection_virtualization/01_protection_security.html">操作系统的保护机制</a>。

**本节目标**：能够把一条跨网提交的异步远程任务，从浏览器入口一路追到宿主机沙箱里的具体执行进程，清楚切分网络层、代理层、任务队列与操作系统权限各自的故障证据。

## 页面说任务已接受，为什么几分钟后还没开始？

当你在网页上点下「运行」，入口 API 校验完参数后，并没有让你的浏览器傻等五分钟算完，而是把任务写进持久队列、飞快返回一个 `202 Accepted` 和唯一任务编号 `J7` 就结束了这次 HTTP 往返。

几分钟过去 `J7` 却毫无动静，可能卡在至少三个完全不同的闸口：
- **卡在排队**：后台工作进程（Worker）数量有限，此刻正满负荷忙着跑前面提交的 `J1`–`J6`，`J7` 只能老老实实待在队列里轮候；
- **卡在沙箱准备**：工作进程其实早就领走了 `J7`，但拉起隔离沙箱时卡在了拉取镜像、准备挂载目录、申请临时只读凭据，或网络插件配置虚拟网卡这一步；
- **卡在静默失败或权限拒之门外**：沙箱进程已经启动，却因为没有读权限或出网被拒而瞬间报错退出，而状态回写没同步到前端。

要像侦探一样把这三个嫌疑人一眼分开，核心法宝就是**把入口生成的「请求 ID（Request ID）」和后台流转的「任务 ID（`J7`）」绑定记录下来**，顺着 **`API 受理 → 入队 → 工作进程领取 → 沙箱启动 → 实际执行`** 这五个里程碑逐一核对事件日志——只有带着同一个任务编号 `J7` 的日志，才能确凿证明它们讲的是同一次执行尝试！

??? question "既然提交完立刻拿到了任务号 `J7`，那如果用户此刻直接关掉浏览器甚至合上笔记本断网，云端任务还能继续跑下去吗？"

    完全可以继续！因为 HTTP 提交连接只是「把任务单递进窗口」的那几百毫秒，任务一旦安全落入队列并由云端独立的后台工作进程接手，它的生命周期就和你的浏览器彻底解耦了。不过，如果半途不幸遇到**云端工作进程崩溃或整台宿主机虚拟机重启**，任务能不能接着跑或重试恢复，就完全取决于任务状态、输入文件和检查点有没有老老实实持久化到可靠存储（磁盘卷或外部数据库）里——只存在内存里的状态一重启就会灰飞烟灭。

## 先把整座工作站的两类入口和一条执行链画出来

设想一台跑在云上的虚拟机（VM）工作站，上面部署着任务 API、状态存储、工作进程和沙箱运行时。平时会从两条截然不同的入口走进这台工作站：

- **业务任务入口**：用户通过浏览器 Dashboard 或聊天机器人接口，走公网 **HTTPS → 反向代理（TLS 终止与鉴权）→ 任务 API** 提交任务；
- **运维开发入口**：工程师通过第 7–8 章学过的 **私有覆盖网络 / VPN** 接入管理网段，再用 **SSH** 或远程编辑器直连工作站排查问题。

两条入口各守各的身份边界（切忌混用凭据！），而真正干活的业务执行链则沿着下面这张架构图展开：

```text
用户 ──→ Web / 消息入口 ──→ TLS 反向代理 ──→ 任务 API ──→ 有限任务队列 ──→ 工作进程 ──→ 沙箱进程
                                               │                                         │
                                               ▼                                         ▼
                                      任务状态与提交者身份                     挂载工作目录、产出结果与日志
```

细看这张图里三个绝不能混为一谈的生命周期：**运维的 SSH 登录会话**、**常驻后台拉单的工作进程**，以及**随单个任务 `J7` 创建又销毁的短命沙箱进程**。用户在提交后可以随时通过任务状态查询接口轮询 `J7` 的最新进度；一旦需要排查异常，必须沿着「哪个用户提交 → 请求 ID 是什么 → 落成了哪个任务 ID → 第几次重试尝试（Attempt ID）→ 跑在哪个沙箱容器里」的完整血缘一追到底。

## 逐层取证对照表：出了事，先翻哪一份证据？

面对复杂系统，最忌讳一团浆糊瞎重启。按照从外向内、由网络入系统的顺序，每一种表面现象都对应着最有区分力的「第一份铁证」：

| 观察到的异常现象 | 最该第一时间调取的核心证据 |
| --- | --- |
| 服务名压根无法解析 | 客户端实际拼出的完整域名、`dig` 解析结果与本机/容器 DNS 配置 |
| 解析出正确地址，但 TCP 建连超时或被拒 | 客户端路由表、目标代理或宿主端口监听地址（是否误绑 `127.0.0.1`）、云安全组与防火墙规则 |
| 反向代理吐出报错（如 `401`/`502`/`503`），任务根本没创建 | HTTP 完整响应码、响应头里的请求 ID，以及反向代理与任务 API 双边的对应日志 |
| 页面提示已接受（拿到 `J7`），但迟迟不见开工 | 队列当前积压长度、队头等待时长、后台工作进程健康与并发槽位占用情况 |
| 沙箱跑起来了，却报找不到输入文件或权限被拒 | 沙箱进程的运行用户 UID/GID、宿主机到容器的目录挂载路径、文件读权限位与注入的短期凭据 |
| 宿主机或工作进程重启后，任务结果凭空消失 | 任务尝试编号（Attempt ID）、持久卷目录内容，以及状态库里最后一次落盘的检查点记录 |

### 现代可观测性三支柱：日志、指标与追踪如何配合？

在排障这张复杂的异步链路时，光靠 `tcpdump` 抓包早就远远不够了（数据包送到 API 之后，后面的排队和沙箱全在应用与内核内部发生！）。工程界普遍把三类观测数据搭配使用：

- **日志（Logs）**：记录某一个具体时刻发生的离散事件（比如「`14:02:11` 请求 `req-99` 创建了任务 `J7`」「`14:02:15` 沙箱读取 `/workspace/in.csv` 触发 `EACCES`」），最适合查单次失败的精确现场；
- **指标（Metrics）**：按时间窗口聚合出的数值走势（如接口错误率、队列等待时长、P95/P99 尾部延迟分位数），一眼看出系统是不是正在整体变慢或积压雪崩。**一条血泪禁忌**：千万别把每次都不一样的「任务 ID / 用户 ID」塞进指标标签里——百万级标签瞬间就能把监控时序数据库撑爆（高基数灾难）！
- **追踪（Traces）**：靠一路透传的追踪标识（Trace ID / Request ID 与 Task ID 关联），把跨反向代理、任务 API、消息队列和沙箱进程的零散片段拼成一条完整的火焰瀑布图，一眼看穿时间到底耗在哪一环。当然，别忘第 7 章红线：密码、API 密钥和隐私 Token 绝不允许随手打进日志或追踪属性里！

## 动手实验与纸面推演练习

合上上面的答案，试着独立完成这四道从本机直通云端架构的硬核推演，把全书前十章的任督二脉彻底打通：

1. **回归本机基线**：重温第 2 章的[本机 HTTP 服务实验](../chapter_02_application/04_socket_and_listening.md)，依次访问「正常路径」「无人监听的空端口」「服务上不存在的文件路径」，亲手把「传输层连接失败」和「应用层返回 HTTP 404」的终端现象对照写下来。
2. **双层取证推演**：设想反向代理顺利把创建任务请求转给了任务 API，任务成功入队，但工作进程启动沙箱时不小心漏掉了宿主机工作目录的挂载配置。请分别写出**请求接入层（代理与 API）**和**后台执行层（工作进程与沙箱）**各自会留下什么看似矛盾、实则严丝合缝的日志证据？
3. **重启灾难演练**：假如工作进程跑了一半突然遭遇宿主机断电重启。请画一张三列恢复表，把下面三类数据分别归类并标出重启后是否丢失：
   - 仅存放在工作进程内存变量里的临时进度；
   - 仅写在容器默认可写层里的中间产出文件；
   - 已经明确刷盘写进挂载持久目录或外部数据库的任务状态与结果。
4. **给 Agent 沙箱画一道最小权限安全笼**：假设你要让一个自动化 Agent 沙箱分析一份代码仓库并生成一份 Markdown 报告。请为它设计最小可运行权限边界——只读挂载哪些输入目录？只写挂载哪个输出目录？是否需要彻底禁止外网出站（或仅放行指定白名单 API）？应该给它签发怎样有效期受限的短期凭据，而不是把开发者的个人 SSH 私钥塞进去？最后，怎么用任务 ID 把全过程审计记录串起来？

若想进一步系统了解日志、指标与分布式追踪的统一标准，推荐阅读 [OpenTelemetry 可观测性入门](https://opentelemetry.io/docs/concepts/observability-primer/)。
