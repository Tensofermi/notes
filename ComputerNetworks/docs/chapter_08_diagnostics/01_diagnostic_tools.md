# 诊断工具与排障路径

打开终端准备排障之前，先挑一个你有权合法测试的目标站点，把三条纪律贴在屏幕边上：**记下敲的每一条命令、记下在哪个网络位置运行、记下原始输出结果；每次只动一个变量再复测。**

初学者看 `ip`、`dig`、`ping`、`traceroute`、`nc`、`openssl`、`curl`、`tcpdump` 这一长串命令时常觉得眼花缭乱。其实它们一点也不零散——**每件工具天生只负责回答某一层的一个具体问题**：本机路怎么指？域名查到了啥？路通不通？端口开没开？证书对不对？HTTP 回了什么？线上到底飞过了哪些真实字节？

这一节绝不枯燥地背命令参数手册，而是严格按照真实排障的「剥洋葱」顺序，用**四步法**把漫无边际的故障精准压缩到唯一一层。

## 核心心法：用四条记录，一眼把故障钉死在哪一层

面对任何一条「网站或接口访问失败」，先按自顶向下或自底向上的清晰顺序，依次记下四项客观结果：

1. **DNS**：域名到底解析出了哪个具体 IP？
2. **TCP**：到这个 `IP:端口` 的传输层三次握手通没通？
3. **TLS**：安全握手、证书链和主机名核验过没过？
4. **HTTP**：最终吐回来的应用层状态码是什么（`200`、`302`、`404`、`503`）？

这四条记录一摆出来，方向瞬间水落石出：如果前三步一路绿灯，唯独最后吐出一个 `503`，别去折腾网线、路由器和证书，直奔入口代理后端清单和应用服务；反过来，如果连第 2 步 TCP 都根本建不起来，就别急着怀疑证书过期，老老实实回头核对 IP、端口号、服务监听和防火墙策略！

**千万留神一个极隐蔽的取证陷阱**：务必把每一步测试实际命中的**具体 IP 地址**记下来！如果 `dig` 解析出 3 个 IP，你测 `ping` 碰巧打中了健康的 IP 1，而浏览器偏偏连向了故障的 IP 2，你拿 IP 1 的成功替 IP 2 作伪证，就会把整个排查带进沟里。

??? question "如果我发请求收到了 `HTTP 404 Not Found`，就能百分百断定「我预期那台后端业务服务器收到了请求」吗？"

    不一定！收到 `404` 只能铁板钉钉地证明「路径上有**某一个** HTTP 服务实体收到了请求并回了话」。但在真实架构里，这个 `404` 很可能是前面的 CDN、七层反向代理（比如路径路由规则配错了，根本没转发给后端！），甚至是被错指到的另一台完全无关的服务返回的。要验明正身，必须比对响应头里的自定义标识、查询代理与后端双边日志，或者用全局请求 ID 把两头日志串起来核实。

## 第一步：先把飘忽的「问题」钉死在桌面上

动手敲诊断命令前，花一分钟记牢五个基础锚点：

- **精确失败对象**：完整的 URL、域名、解析后的 IP、端口与协议（HTTP/2 还是 HTTP/3、IPv4 还是 IPv6）；
- **时间与频次**：从几点几分开始？是 100% 必现、偶发抽风，还是只在晚高峰出现？
- **影响范围**：仅限某一个浏览器/进程、单台电脑、同一片局域网，还是全网大面积报错？
- **最近变更**：过去几小时有没有更新过证书、改过 DNS、切过路由、发过新代码或升级过系统？
- **对照组**：切手机热点（换网络）、换一台电脑（换设备）或绕过代理直连源站，现象还一模一样吗？

紧接着，立刻用一个极简的命令行请求（比如 `curl -v`）替代背后藏着海量插件、缓存和代理规则的图形界面浏览器——只有最小复现，才能把干扰降到零。

## 第二步：查本机配置、路由表与监听端口

先扫清自己家门口的盲区：网卡到底有没有拿到合法 IP？默认路由指对了出口吗？发往目标 IP 的数据包到底会从哪一块网卡走出去？本机进程究竟绑在了 `127.0.0.1` 还是 `0.0.0.0`？

在 **Linux** 上最顺手的四件套：

```bash
ip address
ip route
ip route get 203.0.113.5
ss -lntup
```

在 **macOS** 上的对应组合：

```bash
ifconfig
route -n get 203.0.113.5
networksetup -getinfo Wi-Fi
lsof -nP -iTCP -sTCP:LISTEN
```

其中 `ip route get <目标IP>`（macOS 下为 `route -n get <目标IP>`）极其好用——你不用自己拿肉眼在几十条路由表里心算最长前缀匹配，直接让内核亲口告诉你：「发往 `203.0.113.5` 时，我最终决定走哪张网卡、从哪个源 IP 发、交给哪个下一跳网关！」而 `ss -lntup` 和 `lsof` 则直接摊开本机所有正在监听的端口和对应进程，一眼揪出「服务只监听在 `127.0.0.1` 回环地址，导致外部机器死活连不进来」的经典低级错。

## 第三步：查 DNS——名字有没有翻成你以为的那个地址？

确认本机网络底座正常后，用 `dig` 核验域名解析：

```bash
dig api.example.com A
dig api.example.com AAAA
dig @1.1.1.1 api.example.com A
dig +trace api.example.com
```

把系统默认解析器的结果和显式指定公共解析器（如 `@1.1.1.1`）的结果并排一比，立刻能看出是不是本地缓存过期太慢，或者公司内网/运营商 DNS 返回了不同视图（注意：公司内部私有域名本来就只能由内网 DNS 解析，公共解析器查不到是正常的）。紧盯四个输出字段：响应状态码（`NOERROR` 还是 `NXDOMAIN`）、记录类型、剩余 `TTL` 倒计时以及最终 IP 列表。

还要提防一个常见盲点：**`dig` 查对了，不代表你的浏览器或应用进程一定连的是同一个 IP！** 因为 `dig` 直接向 DNS 服务器发问，通常会绕过本机 `/etc/hosts` 静态文件、系统搜索域、应用自带的内存缓存以及浏览器内置的加密 DNS（DoH）。怀疑解析分叉时，一定要核查应用日志或抓包里真正连出去的目标 IP。

## 第四步：查基础可达性与沿途路径（`ping` 与 `traceroute`）

拿到具体目标 IP 后，先轻敲一下路况：

```bash
ping -c 4 203.0.113.5
traceroute 203.0.113.5
```

（Linux 与 macOS 上部分参数略有差别，如指定探测次数、协议或等待超时。）

读懂这两条输出，必须时刻保持两份清醒，绝不被表象忽悠：
1. **`ping` 通 ≠ 服务通；`ping` 不通 ≠ 服务挂！** `ping` 走的是 ICMP 回显报文。服务器完全可能放行了 `ping` 但网页 443 端口进程已经崩了；反过来，很多云厂商和安全组默认禁用了 `ping`（丢弃 ICMP）却照常敞开 443 端口提供满血 HTTPS 服务！
2. **`traceroute` 中间出现一排 `* * *` 别惊慌！** 只要后面几跳和最终目标照常亮起并正常回复，那一行星号仅仅说明「那台中间路由器配置了不回发 ICMP 超时消息或对 ICMP 限速」，业务数据包其实稳稳穿过去了。同理，判断有没有真实丢包要看**终点和业务流本身**，绝不要被中间某台限速 ICMP 的路由器表象误导。

## 第五步：查真实端口与传输层握手

直接敲业务真正要用的目标端口，才是最有含金量的试金石：

```bash
nc -vz api.example.com 443
curl --connect-timeout 5 -v https://api.example.com/
```

面对传输层吐出的四种典型反应，对照这张表立刻锁定下一步：

| 终端看到的现象 | 底层最可能的含义 | 最有价值的下一步动作 |
| --- | --- | --- |
| 瞬间弹回 **`Connection refused`** | 网络一路畅通到达目标（或中间设备主动发了 `RST`），但目标端口没人监听或被主动拒绝 | 登录服务端查 `ss -lntup` 核实监听地址与端口，确认进程有没有崩溃 |
| 死死卡住直到 **连接超时** | 数据包被防火墙静默丢弃、缺少去程/回程路由，或严重丢包 | 核查沿途安全组/防火墙、检查回程路由，必要时两端同时抓包看 `SYN` 到了没 |
| TCP 握手刚成功，瞬间被对端关闭 | 端口通了，但应用协议不匹配、IP 黑白名单拦截或服务端瞬崩 | 直奔服务端与代理错误日志 |
| 时好时坏、**偶发成功/偶发超时** | 背后挂着多个 IP / 负载均衡后端（其中一台坏了）、等价多路径某条有问题，或连接数耗尽 | 拆开每个独立 IP 或后端分别固定测试，把「偶发」变成「必现」！ |

如果服务端就在你掌控之下，别忘同时检查三件容易被忽略的本机状态：进程是不是只监听了 IPv6 或 `127.0.0.1`、半连接/全连接队列有没有打满、进程打开的文件描述符（FD）上限是不是耗尽了。

## 第六步：查 TLS 握手与数字证书

TCP 端口确认畅通后，接着剥开加密安全层：

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com
```

重点扫视返回结果里的五项硬指标：协商出的 TLS 版本（如 TLSv1.3）、完整证书链、证书里的域名（SAN）是否匹配、生效与过期时间，以及最终的 `Verify return code`（`0 (ok)` 才算完全通过）。特别注意 `-servername` 用来传递 **SNI**——忘了加它，托管多站点的服务器可能会塞给你一张风马牛不相及的默认兜底证书！另外，一旦遇到莫名其妙的「证书尚未生效或已过期」，顺手敲一句 `date` 检查本机系统时钟是不是歪了。

如果命令行 `openssl`/`curl` 全绿，唯独浏览器报错，重点对比两者的差异点：浏览器是不是挂了系统代理或扩展插件、用的信任根证书库是否不同、是否命中了旧的 HSTS 缓存，或者需要客户端双向证书。最后切记：**千万不要在代码或脚本里加一个 `curl -k`（跳过证书校验）就把故障当「修好了」**——那等于为了不听火警铃声直接剪断了报警器电线！

## 第七步：查 HTTP 应用层与定向测试神技 `--resolve`

穿过 TLS，最后核验应用层对话：

```bash
curl -v https://api.example.com/health
curl -I https://api.example.com/static/app.js
curl -L -v https://example.com/
```

（`-I` 只取响应首部，`-L` 自动跟踪 `301/302` 重定向。）盯紧状态码、`Location` 重定向目标、`Host` 首部、缓存字段（`Cache-Control`、`ETag`、CDN 命中标记）和各阶段耗时。请留神：`200 OK` 的正文里照样可能写着业务级报错；`503` 多半指向反向代理找不到健康上游或后端过载；而无限 `301/302` 重定向死循环，常因为反向代理终止 TLS 后忘了把 `X-Forwarded-Proto: https` 透传给后端，导致后端误以为用户走的是明文 HTTP 而一遍遍把它踢回 HTTPS！

这里隆重介绍一个运维封神级参数——**`curl --resolve`**：

```bash
curl --resolve api.example.com:443:203.0.113.5 \
  https://api.example.com/
```

它有多妙？假设 `api.example.com` 背后挂着三个 IP，你想绕开随机 DNS 轮询，精准单挑其中一台 `203.0.113.5` 测 HTTPS。如果你傻傻地直接敲 `curl https://203.0.113.5/`，TLS 的 **SNI** 和 HTTP 的 **`Host` 首部**全都会变成裸 IP，当场报证书不匹配！而 `--resolve` 既强行把连接打向你指定的 `203.0.113.5`，又完整保留了域名 `api.example.com` 用于 SNI、证书校验和 `Host` 首部——一把手术刀，精准剥离「DNS 调度问题」和「单个后端故障」！（测完即止，绝不要把它当永久配置写死绕过服务发现。）

## 第八步：终极实锤——用 `tcpdump` 亲眼看线路上飞过的包

当上面七步依然无法分出胜负（比如「客户端喊发了、服务端喊没收到」，或者怀疑诡异的丢包、零窗口、MTU 黑洞），就祭出网络世界最诚实的裁判——**抓包**！

```bash
sudo tcpdump -i any -nn 'host 203.0.113.5 and port 443'
sudo tcpdump -i any -nn -w capture.pcap 'host 203.0.113.5'
```

（`-nn` 禁止把 IP 和端口反查成域名/服务名，既加速又防干扰；`-w` 保存原始数据包文件，方便拖进图形界面 Wireshark 慢慢深度剖析；Linux 用 `-i any` 可同时盯所有接口，macOS 通常明确指定具体网卡如 `-i en0`。）

面对满屏滚出的抓包记录，直奔五个最关键的信号：
1. **DNS**：问出去了吗？回包里到底给的哪一个 IP？
2. **TCP 建连**：`SYN` 发出去没有？对面回 `SYN+ACK` 还是立刻甩了 `RST`，还是客户端隔 1s、2s、4s 绝望地重传 `SYN`？
3. **TLS 警报**：握手在哪一步蹦出了 `TLS Alert`？
4. **TCP 异常**：有没有密集的重复 ACK、超时重传、通告 `win 0`（接收零窗口卡死）或突然的 `RST`？
5. **ICMP 报错**：半路有没有弹回来 `Destination Unreachable` 或 `Fragmentation Needed / Packet Too Big`？

务必牢记一条抓包几何常识：**在客户端抓包看到「发出了 `SYN`」，只证明包平安抵达了客户端本机的抓包点，绝不代表它穿过了中间防火墙到达了服务器！** 遇到「单向失踪」悬案时，最干脆的做法是在客户端、服务端（乃至关键中间网关）**同时开启抓包**，两边时间戳一对照，包究竟在哪一跳凭空消失立刻铁证如山！而且即便 TLS 把 HTTP 内容全加密了，抓包依然能清清楚楚还原出整场 TCP 握手、重传、窗口变化、TLS 协商与精确时序。

## 实战破案回放：怎么把「偶发超时」变成「铁证如山」？

把刚才所有工具串成一场教科书级别的线上 6 步破案：

**报警现象**：用户反馈访问 `https://api.example.com/` 偶尔正常秒开、偶尔死死卡住直到超时。

1. **查 DNS 拆多址**：敲 `dig api.example.com A`，发现这个域名通过轮询同时返回了 **3 个不同的 IP**！怀疑三台入口里混进了一颗坏果子。
2. **用 `--resolve` 逐个点名**：对 3 个 IP 分别跑 `curl --resolve ...`，结果 IP-1 和 IP-2 次次毫秒级 `200 OK`，唯独 IP-3 **100% 必现连接超时**！至此，最讨厌的「随机偶发玄学」瞬间被锁定为「固定目标必现故障」。
3. **客户端抓包取证**：在客户端抓向 IP-3 的包，清楚看到 `SYN` 稳稳发了出去、每隔几秒重传，却始终等不到半个 `SYN+ACK` 或 `RST`。
4. **服务端双端比对**：分别登录正常后端和 IP-3 故障后端同步抓包——正常后端清晰收到 `SYN`，而 IP-3 故障后端网卡上一片死寂，压根没见到客户端的 `SYN`！结论锁定：**数据包死在了「客户端离开之后、到达 IP-3 网卡之前」的半路上！**
5. **比对路由与防火墙**：对比正常节点和 IP-3 节点的网络策略，一眼抓出真凶——公司刚扩容的新客户端出口网段，忘了同步加进 IP-3 所在机房入口的 **访问控制列表（ACL）** 白名单，入口防火墙把 `SYN` 静默丢弃了！
6. **修复并闭环验证**：补齐 ACL 规则后，先用 `--resolve` 逐一验证 3 个 IP 全部 200 绿灯，再撤掉 `--resolve` 走正常 DNS 轮询反复压测确认彻底恢复。

回味一下这场漂亮的排障：自始至终没有慌乱重启任何一台服务器，靠「拆地址把偶发变必现 + 双端抓包把路径切半」，十分钟之内精准挖出根因。

## 清醒认识工具的盲区

工具极其强大，但记住：**任何一条命令吐出来的都只是「此时此地的一次局部观测」，不是上帝视角的全部真相。** 缓存可能掩盖最新变更，负载均衡可能让两次连续命令落到不同机器，防火墙会对 ICMP 和 TCP 采取截然不同的态度，甚至网卡硬件卸载（TSO/GRO）还会让本机 `tcpdump` 抓到表面上比 MTU 还大的「超级大帧」（其实网卡发出前会在硬件里切好）。扎实的排障结论，永远由多条彼此印证的硬证据共同筑成。

!!! tip "贴在工位上的最短排障运行手册"
    1. 先 `dig` 确认解析出了哪些精确 IP；
    2. 再 `ip route get` / `route -n get` 确认本机发包走哪张网卡、哪个下一跳；
    3. 再用 `nc -vz` 或 `curl --connect-timeout 5 -v` 实测真实业务端口；
    4. 接着用 `openssl s_client` 验 TLS 证书与 SNI，用 `curl -v` / `--resolve` 查 HTTP 与单后端；
    5. 只有现有证据实在区分不开两个假设时，再上 `tcpdump` 双端抓包一锤定音。
    每一步都顺手记下时间戳和真实目标 IP！

## 从「排查一条连接」迈向「排查一次分布式请求」

上面这整套网络工具箱能把「数据包到底送到哪一台机器、哪一个端口」查得水落石出；但正如上一篇[Agent 工作站案例](../chapter_07_case_study/02_agent_workstation.md)所展示的，在现代微服务与异步云系统里，网络连接畅通仅仅是故事的上半场。一旦请求穿过入口代理进入业务集群，你必须自然接上应用层的可观测性武器：用全局请求 ID（和异步任务 ID）把代理、任务 API、消息队列与沙箱日志串成一条线，用错误率、队列深度和 P99 延迟分位数盯住全局健康，再用分布式追踪还原单次慢请求的完整火焰图。
