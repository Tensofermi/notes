## 热身：先画出自己的故障排查路径，再看参考答案

**实战热身题**：你在云服务器上用容器跑起了一个网页服务。登录到宿主机本机用 `curl` 访问一切正常，可换到你办公室的电脑上通过服务域名去访问，请求却一直卡住转圈等待。你该按什么顺序一步步排查？

试着把每一步写成一句**「能验证、能证伪」的清晰假设**：
1. 先查办公室电脑把域名解析成了哪个 IP（是不是指错了旧地址或根本是内网私网地址？）；
2. 再登录宿主机查端口发布究竟绑定在了 `127.0.0.1` 回环地址，还是对外可达的 `0.0.0.0`/外部网卡 IP（以及容器内部是否错绑了容器回环地址？）；
3. 接着顺着网络路径核对宿主机防火墙、云安全组与沿途路由是否把入站包静默拦截了。

顺便想一想：为什么「宿主机本机能访问成功」，远远不足以证明外部路径也是通的？（因为本机直连完全绕过了公网 DNS、跨网路由、云安全组以及外部网卡的绑定监听边界！）

??? question "如果按上面查完、放行外部入口和防火墙之后，办公室电脑访问不再卡住超时，而是立刻返回了 `HTTP 404 Not Found`，请问故障性质发生质变了吗？"

    发生了彻底的质变！从「超时无回音」变成「秒回 `HTTP 404`」，意味着从 DNS 解析、跨网路由、安全组防火墙、宿主机端口发布到某个 HTTP 监听进程的整条网络与传输管道已经**全线打通**！此刻请立刻收起网络排障工具，把全部精力聚焦到应用层：核对请求的 URL 路径拼写、静态文件目录、反向代理是否选对了后端，以及这个 `404` 究竟是代理吐出来的还是真正后端服务吐出来的。

## 一、分层、封装与网络性能

### 1. 为什么同一个 IP 数据报在互联网里每经过一台以太网路由器，外层的 MAC 地址都会变一次，而里面的目的 IP 却保持不变？

??? answer "答案"
    因为两张地址承担的作用范围完全不同：**目的 IP 地址**负责跨越整张互联网的「端到端寻址」，标明最终收件主机属于哪片网络，因此沿途原则上保持不变（除非经过 NAT 改写）；而 **MAC 地址** 只服务于「眼前这一段本地链路的一跳交付」。路由器收到帧后，剥掉上一跳的链路外壳，靠目的 IP 查转发表选出下一跳出口，再把源 MAC 换成自己这个出口网卡的地址、目的 MAC 换成下一跳相邻设备的地址重新封装发送。

### 2. 把一个 1500 字节的分组推上一条速率为 10 Mb/s 的链路，发送时延是多少？

??? answer "答案"
    先把字节换算成比特：$1500 \times 8 = 12000\ \text{bit}$；链路速率 $R = 10 \times 10^6\ \text{bit/s}$。套用发送时延公式：

    $$
    d_{trans}=\frac{L}{R}=\frac{12000}{10\times 10^6}=0.0012\ \text{s}=1.2\ \text{ms}.
    $$

    请牢记：这 `1.2 ms` 仅仅是「把分组所有比特全部推上线缆」花的时间，完全不包含信号在物理介质中飞行的传播时延、沿途路由器里的排队时延和处理时延。

### 3. 为什么把宽带带宽升级十倍（比如从 100 Mb/s 升到 1 Gb/s），小型 API 请求的端到端延迟却远远下降不了十倍？

??? answer "答案"
    因为小型 API 请求和响应的字节数本来就很小，在 100 Mb/s 链路上把它们推上线缆的发送时延本来就只有零点零几毫秒，在总耗时里微不足道。真正占大头的，是信号跨越物理距离的光速**传播时延**、DNS 查询与 TCP/TLS 建连的**多次往返（RTT）**、沿途路由器里的**排队等待**，以及后端服务器的**业务计算与查库时间**。带宽提速只能压扁发送时延，却动摇不了物理距离和协议往返次数。

### 4. 路由器出口的缓冲区是不是配得越大越好？为什么？

??? answer "答案"
    绝不是越大越好！适度的缓冲区能吸收短暂的突发流量、减少无谓丢包；但如果缓冲区大得离谱，基于丢包的拥塞控制算法会不断提速直到把整个超大队列彻底塞满才肯刹车，酿成严重的 **缓冲膨胀**（bufferbloat）。结果虽然下载吞吐看似漂亮，但每一个新发出的鼠标点击、SSH 按键或语音包都得排在几百毫秒甚至几秒的长队尾巴后面干等！好的队列设计必须在吞吐、丢包与交互时延之间求平衡，并配合主动队列管理（AQM）与公平排队来护住小包交互流。

## 二、应用层（HTTP、DNS、CDN）

### 5. DNSSEC 与加密 DNS（DoT / DoH）都是保护 DNS 安全的，它们分别解决了什么不同的问题？能互相替代吗？

??? answer "答案"
    两者解决的是完全不同的威胁，**互不替代、而是互补**：
    - **DNSSEC** 靠数字签名链保障**权威数据的来源认证与完整性**——证明查回来的 IP 确实出自真正域名主人且中途没被伪造篡改，但它**不加密**，旁观者依然看得见你查询了哪个域名；
    - **DoT / DoH** 把「客户端到递归解析器」这一段查询装进 TLS/HTTPS 密道，保护**传输隐私**不被局域网或运营商沿途偷看与篡改，但它既不能自动证明上游权威记录绝对真实，也要求你信任你选用的那家递归解析器本身。

### 6. HTTP 天生是「无状态」协议，为什么电商和社交网站依然能稳稳记住我的登录身份和购物车？

??? answer "答案"
    「无状态」说的是 HTTP 协议核心本身不在两次请求之间自动记忆业务上下文（服务器不会仅凭「来自同一条 TCP 连接」就认出你是谁），从而让服务器轻盈易扩容。实际业务状态是由**应用层显式外挂**管理的：登录成功后，服务器通过响应头 `Set-Cookie` 把一个会话标识（或签名令牌）交给浏览器存好；浏览器后续每次请求自动在 `Cookie` 首部里亮出凭证，服务器据此去共享会话存储里恢复你的身份和购物车。

### 7. 调用提交订单或扣款的 `POST` 接口遭遇超时后，客户端为什么绝不能简单粗暴地直接重试？

??? answer "答案"
    因为「超时」只代表客户端在限定时间内没收到回应，你根本无从区分究竟是**请求半路丢了压根没送到服务器**，还是**服务器其实早就扣款成功、偏偏回执响应在回来的路上丢了**！如果盲目重发普通 `POST`，极易酿成重复扣款或创建两笔重复订单的事故。安全做法是让客户端为每笔业务预先生成全局唯一的 **幂等键**（idempotency key），并配合服务端去重表和结果查询接口，确保哪怕重复提交十次，最终业务效果也只生效一次。

### 8. CDN 把内容缓存到用户家门口确实快如闪电，但它引入的最核心工程代价是什么？

??? answer "答案"
    最核心的代价是 **数据新鲜度与一致性管理**，以及潜在的**缓存安全边界风险**。一旦资源在全世界几百个边缘节点留下副本，源站更新后旧副本在过期前可能继续被看到，必须精心组合 TTL、条件验证（`ETag`/`304`）、主动刷新或内容哈希版本化 URL（如 `app.a1b2.js`）来治理；更危险的是，如果缓存键遗漏了语言、压缩格式甚至用户认证身份，就可能把错误版本甚至张三的私密敏感响应直接缓存泄漏给李四。

## 三、传输层（UDP、TCP、流量与拥塞控制）

### 9. UDP 首部明明同时包含端口号和校验和，为什么依然被称为「不可靠」传输协议？

??? answer "答案"
    因为端口号只负责把数据报解复用交给目标进程，校验和只负责**发现**比特损坏——查出坏包后 UDP 除了随手丢弃外什么也不做。它不编序号、不等确认（ACK）、不自动重传、不恢复乱序，也不剔除重复包。「能发现出错」与「能从出错中自动恢复并保证有序完整」是两回事；业务若需要可靠性，必须自己上移到应用层实现或直接选用 TCP / QUIC。

### 10. TCP 建立连接时为什么要费劲走「三次握手」，而不是更省事的「两次握手」？

??? answer "答案"
    三次握手同时完成三件事：确认通信双方**双向可达**、同步彼此的**初始字节序号**并协商通信选项（如 MSS、窗口扩大、SACK）。假如只有两次握手，服务器在发出 `SYN+ACK` 后就单方面认定连接成立并分配资源，却根本无法确认客户端到底收没收到自己的初始序号与参数；更糟的是，如果网络深处某个很久以前迷路迟到的旧 `SYN` 突然到达，两次握手会让服务器白白建起一条僵尸半开连接。加上客户端发出的第三条 `ACK`，双方才彻底对齐状态，消除了旧报文歧义。

### 11. 在 TCP 编程中，发送方调用了一次 `send` 写出一条完整消息，接收方调用一次 `recv` 一定会恰好读出这一条完整消息吗？

??? answer "答案"
    **绝对不保证！** TCP 提供的是没有应用消息边界的连续**字节流**（byte stream）。底层协议栈随时可能把你两次 `send` 合并进同一个 TCP 段里发出（粘包），也可能把你一次大的 `send` 拆成好几个小段分批到达（拆包）。应用程序如果关心「一条消息到哪里结束」，必须自己在载荷里约定显式分帧规则，例如固定长度、明确的长度前缀（类似 HTTP 的 `Content-Length`）或特定分隔符。

### 12. 一条带宽 100 Mb/s、往返时延（RTT）80 ms 的长距离路径，它的带宽时延积（BDP）大约是多少？这个数字有什么工程意义？

??? answer "答案"
    直接按带宽乘以 RTT 计算：

    $$
    BDP=R\times RTT=100\times 10^6\ \text{bit/s}\times 0.08\ \text{s}=8\times 10^6\ \text{bit}=1\ \text{MB}.
    $$

    它的工程意义极其直白：这根高速长管道在某一瞬间整整能装下 **1 MB** 的在途数据。如果单条 TCP 连接的滑动窗口上限远小于 1 MB（比如默认只有 64 KB），那么哪怕线路零丢包、零拥堵，发送方每发满 64 KB 就必须停下来干等回执，单条流永远跑不满这条 100 Mb/s 的昂贵链路。

### 13. 接收窗口 `rwnd` 与拥塞窗口 `cwnd` 名字很像，它们分别保护谁、由谁维护、又怎样共同决定发送速度？

??? answer "答案"
    - **`rwnd`（接收窗口）** 属于**流量控制**，由**接收方**根据自己剩余接收缓存空间计算并在 ACK 里通告，目的是**保护接收端不被撑爆**；
    - **`cwnd`（拥塞窗口）** 属于**拥塞控制**，由**发送方**根据丢包、RTT 变化或 ECN 等网络反馈动态推算维护，目的是**保护沿途共享网络不被堵垮**并试探可用容量。

    发送方任意时刻允许的已发未确认在途数据总量，严格受两者的较小值约束：$W_{send}=\min(rwnd, cwnd)$（同时受本机发送缓存与应用供数速度限制）。

### 14. 既然 TCP 保证可靠交付，是不是说「用 TCP 把一笔转账请求发出去，只要没报错，就保证恰好扣款一次」？

??? answer "答案"
    不是！TCP 的可靠承诺严格局限在**单条连接存活期间的端到端字节搬运**，它对业务事务一无所知。你的代码调用 `send()` 返回只表示数据进了本机内核缓冲区；就算字节送到了服务器内核，万一服务端进程刚读出来还没写入数据库就断电重启，或者扣完款回执路上断了线，TCP 重连后也无法替应用裁决到底扣没扣钱。真正的业务「恰好执行一次」语义，必须由应用层的数据库事务、幂等键、去重记录与对账查询来保证。

## 四、网络层（IPv4/IPv6、NAT、路由与转发）

### 15. 给定带前缀的地址 `192.0.2.200/27`，它所在传统 IPv4 子网的网络地址和定向广播地址分别是什么？

??? answer "答案"
    `/27` 意味着剩下的主机位是 $32 - 27 = 5$ 比特，每一段子网正好包含 $2^5 = 32$ 个地址！把最后一段按每 32 个一刀切开，各段起点依次是：`0, 32, 64, 96, 128, 160, 192, 224`。

    题目中的 `.200` 稳稳落在 `192` 到 `223` 这一段中，因此：
    - **网络地址**：`192.0.2.192`
    - **定向广播地址**：`192.0.2.223`
    - （顺带一提，常规可分配主机范围是 `.193` 到 `.222`，共 30 个。）

### 16. 很多人觉得「家里和公司出口已经装了 NAT，外网连不进来，所以 NAT 就等于防火墙了」——为什么这种看法很危险？

??? answer "答案"
    NAT 的本质使命是**改写地址与端口以缓解 IPv4 地址枯竭**，维护连接映射表只是为了把回包还原给正确内网主机；而防火墙的使命是**显式表达并强制执行允许与拒绝的安全访问控制策略**。NAT 固然顺带挡住了没有映射记录的陌生入站包，但它既不检查内网被攻陷主机主动往外连黑客控制服务器的行为，也不对允许放行的流量做身份认证、精细策略隔离或应用层安检——绝不能拿 NAT 替代明确的状态防火墙与端到端认证。

### 17. 网络层里常并提「路由」和「转发」，这两个动作到底有什么本质区别？

??? answer "答案"
    两者分属完全不同的两个平面与时间尺度：
    - **路由（控制平面）**：是在后台以毫秒到秒级尺度运行的全局协同过程，路由器之间交换拓扑和商业策略（如 OSPF、BGP），算路并生成转发表；
    - **转发（数据平面）**：是对每一个到达网卡的数据报在纳秒到微秒级执行的高速局部动作——查转发表做最长前缀匹配，把包从选中的物理出口送往下一跳。

### 18. 路由表里同时存在 `10.1.2.0/24` 和 `10.0.0.0/8`，发往 `10.1.2.9` 的数据包为什么优先匹配 `/24`？这样设计有什么好处？

??? answer "答案"
    两条规则都与 `10.1.2.9` 匹配，而路由器执行的是 **最长前缀匹配**（LPM）原则——谁匹配的比特位数更多、描述的集合更具体，就优先听谁的（24 > 8）。这套规则的巨大好处是让**大范围路由聚合**（一条 `/8` 或默认路由 `0.0.0.0/0` 兜住全局）与**局部精细例外**（其中某一个小 `/24` 子网走专线或搬了新机房）能够毫不冲突地完美共存，极大压缩了全球路由表规模。

### 19. 运行 `traceroute` 时，发现第 5 跳显示成一行 `* * *`，但第 6 跳到终点却全都正常响应。能断定第 5 跳路由器把我的业务流量丢掉了吗？

??? answer "答案"
    绝对不能！第 6 跳和终点都照常亮着，恰恰反证了探测包和业务流量稳稳穿过了第 5 跳！那一排星号通常仅仅意味着第 5 跳路由器出于安全加固或保护 CPU 的策略，配置了「静默忽略探测包、不回复 ICMP 超时消息」或对 ICMP 回包做了极低限速。此外，遇到多路径负载均衡或不同探测协议（ICMP/UDP/TCP）时，读 `traceroute` 也要结合终点实际业务流判断。

## 五、链路层与网络安全

### 20. 以太网帧尾的 CRC-32 校验顺利通过了，这能证明该数据帧一定来自合法的发送者且中途没被黑客篡改吗？

??? answer "答案"
    不能！CRC 是一种公开、**无密钥**的差错检测算法，只用来对抗物理介质里的随机噪声和偶然比特翻转。任何截获数据帧的主动攻击者，把内容篡改得面目全非之后，随手就能用同一个公开生成多项式算出一个崭新的合法 CRC 贴回去，轻松骗过网卡检错。防伪装和防主动篡改必须依靠带秘密密钥的密码学消息认证码（MAC）、AEAD 认证加密或数字签名。

### 21. 你的主机处于 `192.168.1.10/24`，要访问远在公网的服务器 `198.51.100.20`，发包前局域网里的 ARP 广播究竟在问谁的 MAC 地址？

??? answer "答案"
    问的是**本地下一跳（即默认网关，如 `192.168.1.1`）的 MAC 地址**，绝不是远方服务器 `198.51.100.20` 的 MAC！因为 MAC 地址和 ARP 广播只在当前这片局域网里有效。主机发出的第一跳数据包里，内层目的 IP 写着远方服务器，外层帧目的 MAC 写着家里默认网关；此后每经过一台路由器，外层链路帧都会被剥掉换上新一段链路相邻设备的 MAC。

### 22. 为什么 Wi-Fi 采用「碰撞避免（CSMA/CA）」，而不能像早期有线总线以太网那样简单地「边发边检碰撞（CSMA/CD）」？

??? answer "答案"
    背后有两大冷酷的无线物理限制：第一，**强自干扰**——无线终端发射信号时，自己天线发出的功率比远端微弱信号强出成百上千万倍，根本听不见别人是不是也在同时发；第二，**隐藏终端问题**——隔着墙的两台手机彼此听不见对方的信号，却都能同时干扰中间的无线接入点。因此 Wi-Fi 只能改走碰撞避免路线：发前先听、引入随机退避、发送整帧后靠接收方回发链路层 ACK 确认没撞车，必要时用 `RTS/CTS` 提前清场预约。

### 23. 总结一下：TLS 究竟为你提供了哪三项核心安全保证？又明确「不提供」哪些保障？

??? answer "答案"
    - **TLS 提供的三大保障**：传输中应用内容的**机密性**（防偷看）、**完整性**（防篡改），以及基于数字证书与私钥签名的**对端身份认证**（防冒充，且现代 TLS 1.3 还标配前向保密）。
    - **TLS 不提供的保障**：它不证明对面网站是个良心商家（钓鱼站也能领合法证书）；不修复网站后端的 SQL 注入、越权等应用漏洞；无法彻底隐藏通信双方 IP、连接时间、数据包大小等流量元数据；也保护不了已经被木马攻陷的终端或服务器内存里的明文。

### 24. TLS 1.3 的 0-RTT 能让老熟客重连飞快，为什么却绝不能把任意 HTTP 请求都放进 0-RTT 里发？

??? answer "答案"
    因为 0-RTT 早期数据在服务器尚未返回本轮新鲜随机数之前就发出去了，**天生缺乏抗重放保护**！路径上的攻击者可以把截获的 0-RTT 密文原封不动复制发给服务器十遍，服务器全都能合法解密执行。因此，0-RTT 只适合承载天然幂等的只读请求（或应用层具备严格防重放去重机制的操作）；转账、下单、扣费这类有副作用的非幂等操作绝不能为了省这一个往返而贸然塞进 0-RTT。

## 六、综合排障实战

### 25. 域名解析完全正确、`ping` 目标 IP 也延迟极低零丢包，可浏览器访问 `https://` 却始终超时——你接下来该怎么查？

??? answer "答案"
    `ping` 通只证明 ICMP 回显报文可达，完全不保证业务真正要走的 **TCP 443**（或 UDP 443）畅通！紧接着按四步缩小范围：
    1. 用 `nc -vz host 443` 或 `curl --connect-timeout 5 -v https://host/` 实测真实业务端口，一眼区分是「秒拒 `Connection refused`」「TCP `SYN` 死等超时」「卡在 TLS 握手」还是「HTTP 响应超时」；
    2. 若卡在 TCP 超时，核查客户端路由、云安全组与防火墙是否放行 443、目标主机服务监听地址（是否错绑 `127.0.0.1`）以及回程路由；
    3. 悬而未决时，在客户端和服务端同时用 `tcpdump` 抓 443 端口的 `SYN`，一眼切出数据包究竟死在半路还是死在服务端内部。

### 26. 同一个域名时而秒开、时而连接超时（偶发故障），最立竿见影的第一轮缩小范围动作是什么？

??? answer "答案"
    第一时间破除「随机玄学」，把偶发变成**固定目标必现**！先用 `dig` 查看该域名是不是返回了多个 IP（或查看背后是否挂着多台负载均衡后端），然后用 `curl --resolve 域名:443:单个IP https://域名/` 挨个点名压测每一个独立 IP。只要发现其中某一个特定 IP 100% 必现超时而其他 IP 次次秒通，问题瞬间就从飘忽不定的偶发故障，精准锁死在了那一台特定后端的路由、健康检查、监听或入口 ACL 防火墙策略上！

### 27. 抓包和开发者工具都显示网页的主 HTML 文档几十毫秒就快速返回 `200 OK` 了，但用户屏幕却持续白屏好几秒——这一定说明网络层带宽不够吗？

??? answer "答案"
    绝不一定！拿到 HTML 仅仅是浏览器渲染流水线的起跑线。白屏很可能是因为页面引用的同步 JavaScript 脚本或庞大 CSS 阻塞了解析与渲染树构建、某些挂在慢速第三方域名下的字体/子资源迟迟不归（新域名还要重新做 DNS + TCP + TLS！），或者是繁重的前端脚本把浏览器主线程彻底卡死。打开浏览器开发者工具的 Network 资源瀑布流、Console 报错面板和 Performance 主线程火焰图，立刻就能分清究竟卡在子资源网络拉取还是前端本地执行。

### 28. 线上突发网络故障时，为什么经验丰富的工程师强烈反对「上来啥也不看，先重启所有服务器和路由器试试」？

??? answer "答案"
    因为盲目重启会在一瞬间同时洗掉内存里的连接表、ARP/DNS 缓存、拥塞队列、进程句柄和临时路由状态——**彻底销毁破案现场**！哪怕侥幸重启后服务暂时恢复了，你也完全不知道刚才的根因是什么，隐患原封不动埋在那里，半夜随时卷土重来。专业做法是「先保留现场核心证据（日志、连接状态、`dig`/`curl`/必要抓包），再用一次只动一个变量的最小对照实验锁死根因，最后实施精准且可验证的修复」。
