# 从虚拟网卡到隧道：一条容器网络路径

**先修**：[监听地址和端口](../chapter_02_application/04_socket_and_listening.md)、[地址和子网](../chapter_04_network/01_ip_addressing_subnetting.md)、[地址转换（NAT）](../chapter_04_network/02_ipv6_nat_icmp.md)、[从 IP 地址找到网卡地址（ARP）](../chapter_05_link/02_ethernet_wifi_arp.md)。

**读完能做**：完整画出两个容器从「同宿主机互访」到「访问外网/发布端口」再到「跨物理机隧道互访」的每一段路径，准确标出哪里发生了地址改写、哪里套上了外层隧道包装，以及为什么跨机大响应可能莫名超时。

---

试着在同一台普通 Linux 电脑上启动两个都要监听 `0.0.0.0:8000` 的网页服务——第二个程序几乎立刻会抛出 `Address already in use` 退出，因为同一套协议栈里一个端口只能归一个监听 Socket 独占。

可当你把这两份服务分别装进两个 **容器**（container）里，它们却能舒舒服服地各自占有 `8000` 端口和平共处！背后的魔术不是什么黑科技，而是 Linux 内核提供的一项隔离能力——**网络命名空间**（network namespace）。你可以把它想象成内核凭空变出的多间「独立网络单间」：每个命名空间里都有自己专属的一套网卡列表、独立 IP 地址、独立路由表、独立端口号空间和防火墙规则。于是，容器 A 里的程序往外看，觉得自己独占整台机器的 `8000` 端口；容器 B 里的程序也同样觉得自己独占 `8000` 端口。

可关进各自的小单间以后，麻烦来了：**A 和 B 隔墙相望，连一根网线都没接，容器 A 究竟怎样把第一个 HTTP 请求送到容器 B 手里？** 我们先在同一台物理机器上用软件帮它们拉通网线，再一步步走出宿主机、跨越两台物理机器。

## 给隔离的进程接网线：veth 对与软件网桥

承载这些容器运行的底层物理机或虚拟机，称为 **宿主机**（host）。如果把容器 A 看成一台独立小电脑，那它需要一张网卡插上一根网线，另一头连进一台交换机；容器 B 也一样。Linux 用两件极其精巧的内核虚拟设备，在纯软件里完美复刻了这套硬件拓扑：

1. **`veth` 对**（virtual Ethernet pair）：它永远成双成对出现，就像一根**两端自带虚拟网卡接口的软件网线**——你从这一头塞进去一个以太网帧，它瞬间毫发无损地从另一头钻出来！创建容器时，内核把 `veth` 对的一端塞进容器的网络命名空间里（通常改名为容器熟悉的 `eth0`），把另一端留在宿主机的默认网络命名空间里。
2. **Linux 软件网桥**（bridge，如 `br0` 或 `docker0`）：它在软件内核里完整扮演一台我们在第 6 章学过的二层[交换机](../chapter_05_link/02_ethernet_wifi_arp.md#switch-learning)！把容器 A、B 留在宿主机上的那两根 `veth` 线头统统「插」进同一座网桥 `br0`，A 和 B 就仿佛用两根真实网线插进了同一台局域网交换机——网桥同样按以太网帧头的目的 MAC 地址做自学习与转发。

来看一个具体走查：假设容器 A 的地址是 `10.20.0.2/24`，容器 B 是 `10.20.0.3/24`，两者同属同一台宿主机上的 `10.20.0.0/24` 子网（前 24 位网络前缀相同），各自通过一对 `veth` 接入网桥 `br0`：

```text
容器 A                        宿主机                         容器 B
eth0 ── veth 对 ── 宿主端口 a ── br0 ── 宿主端口 b ── veth 对 ── eth0
10.20.0.2/24                                             10.20.0.3/24
```

现在，容器 A 里的客户端从临时端口 `49152` 向容器 B 的 `10.20.0.3:8000` 发起第一个 TCP 连接请求。慢动作回放这五步，你会惊喜地发现——每一步都是你前六章的老熟人！

| 执行步骤 | 负责决策的组件 | 这一步究竟查了什么、做了什么 |
| --- | --- | --- |
| 1. 查路由 | 容器 A 的独立路由表 | 比较 `/24` 前缀，发现 `10.20.0.3` 就在同一本地子网，无需走网关，下一跳直接就是 B |
| 2. 找 MAC | 容器 A 的 ARP 模块 | 若本地 ARP 缓存为空，A 发出广播帧大喊「谁拥有 `10.20.0.3`？」；B 收到后单播回复自己的虚拟 MAC |
| 3. 穿软件网线 | A 的 `veth` 对 | A 封装好目的 IP 为 B、目的 MAC 为 B 的以太网帧送进 `eth0`，帧瞬间从宿主机端口 `a` 钻出来 |
| 4. 过软件交换机 | 宿主机网桥 `br0` | `br0` 从入帧的源 MAC 学会「A 在端口 `a`」；若已记住 B 在端口 `b` 就精准单播，否则向其他端口泛洪 |
| 5. 交付进程 | 容器 B 的协议栈 | 帧穿过 B 的 `veth` 抵达 B 的 `eth0`，剥包校验后，把发往 `10.20.0.3:8000` 的请求递进 B 的监听 Socket |

请特别留心这条同子网路径上的两个细节：第一，自始至终 A 和 B 的 IP 地址丝毫没变；第二，第 2 章提过的 **回环地址 `127.0.0.1`** 是**按网络命名空间各自独立的**！如果容器 B 里的网页程序只偷懒监听在 `127.0.0.1:8000`，哪怕上面的以太网帧一路绿灯送到了容器 B 的 `eth0`（`10.20.0.3`），内核一看目的 IP 对不上 `127.0.0.1`，照样会冷冰冰地拒收连接——这也是容器部署里新手踩过最多次的坑之一（容器内服务若要被外部或其他容器访问，通常应监听 `0.0.0.0:8000` 或明确绑定的容器网卡地址）。

搞定了同宿主机里两个容器互相串门，接下来两个反方向的实际问题立刻找上门来：容器 A 怎么访问外面的公网网站？外面的用户又怎么连进宿主机里那个藏在私网的容器 B？

## 容器出网与宿主机端口发布：两个方向的不同机制

### 方向一：容器访问外部网络（出站源 NAT）

当容器 A 想访问公网上的某个网站（比如 `198.51.100.20`），它查路由表发现不在 `10.20.0.0/24` 本地子网，于是把包发给自己的**默认网关**——通常正是宿主机网桥 `br0` 上配置好的那个网关 IP（例如 `10.20.0.1`）。

包到达宿主机内核后，宿主机查自己的路由表准备从物理网卡送往外部网络。可麻烦在于：**外面的路由器和目标网站根本不认识你宿主机里私自划的 `10.20.0.2`！** 如果直接原样发出去，回程响应永远找不到回家的路。

于是宿主机借用了我们在第 5 章熟悉的绝招——**源地址转换**（SNAT / 源 NAT，也称 Masquerade 伪装）：数据包离开宿主机物理网卡前，宿主机把源 IP 从 `10.20.0.2` 悄悄改写成宿主机自己外部可达的网卡地址，并把改写前后的五元组记进内核的 **连接跟踪**（conntrack）状态表里；等外网响应飞回宿主机时，连接跟踪表精准查出原主，把目的地址改回 `10.20.0.2` 再送回容器 A。（当然，Docker 或企业网络也可以选择另一种路子：在全网路由器里显式配好去往容器子网的路由，让外网直接认识容器 IP，省去 NAT。）

### 方向二：外部访问容器服务（端口发布）

反过来，现在容器 B 里跑着好用的网页服务（监听在 `10.20.0.3:8000`），你想在宿主机浏览器里打开 `http://127.0.0.1:18000` 访问它，甚至让同一局域网里的同事也能连进来。

这就需要给容器配置 **端口发布**（port publishing，如 Docker 的 `-p 127.0.0.1:18000:8000`）：它在宿主机指定的入口地址与端口（`127.0.0.1:18000`）和容器内部监听点（`10.20.0.3:8000`）之间架起一条入站转发通道（底层常靠目的地址转换 DNAT 或用户态代理进程实现）。这样一来，容器 A 和容器 B 在各自命名空间里可以同时霸占 `8000` 端口，只要发布到同一个宿主机 IP 时挑不同的宿主机端口（比如 `18000` 和 `18001`）就毫不打架。记住：**容器出站走源 NAT，宿主机端口发布管入站转发，两者解决的是相反方向的问题。**

??? question "明明同宿主机上的两个容器 A 和 B 可以顺畅互访，为什么通过宿主机发布的端口去访问 B 却还是连不通？"

    同机容器互访成功，只证明了「容器 A ↔ 网桥 ↔ 容器 B」这条内部走廊没坏，完全没测到宿主机的入口路径！排障时顺着客户端发出的包逐一核对三道关口：
    1. **入口绑在了哪块地址上？** 上面的例子把端口只发布到了宿主机的回环地址 `127.0.0.1:18000`。如果你在**另一台电脑**上访问 `127.0.0.1`，请求压根不会离开你那台电脑；就算你改用宿主机的局域网 IP 去连，也对不上只绑在回环的发布规则！
    2. **后端转发目标与容器监听对得上吗？** 确认发布规则确实指向 `B:8000`，且容器 B 里的程序没有错误地只监听在容器自己的 `127.0.0.1:8000` 上。
    3. **沿途防火墙与转发规则放行了吗？** Linux 上 Docker 的桥接转发和端口发布深度依赖内核包过滤（如 `iptables`/`nftables`）与路由转发开关，需要核实实际命中的规则链是否拦截了入站或跨接口转发。

    老练的排障套路是**分段做三组对照测试**：先记下「容器间互访」、再记下「宿主机本机连发布端口」、最后记下「另一台机器连宿主机发布端口」的结果，立刻就能把故障框死在哪一截。延伸阅读：[网桥与防火墙讨论](https://www.bilibili.com/video/BV1Aj411r71b/#reply178725159776) · [Docker 包过滤文档](https://docs.docker.com/engine/network/packet-filtering-firewalls/)

单台宿主机已经玩得滚瓜烂熟了。可真实生产环境里，单台机器迟早装不下，必须扩展成几台、几百台宿主机组成的集群。现在把容器 B 搬到隔壁物理宿主机上——新的难题立刻迎面砸来！

## 从一台宿主机扩展到两台：隧道、覆盖网络与 MTU 算账

假设现在有两台物理宿主机：宿主机 1 的外网/机房物理地址是 `192.0.2.10`（上面跑着容器 A：`10.20.0.2`），宿主机 2 的物理地址是 `192.0.2.20`（上面跑着容器 B：`10.20.0.3`）。

两台宿主机之间物理网络早已畅通无阻，可机房里的物理路由器压根不认识你软件里捏出来的 `10.20.0.0/24` 容器私网！如果宿主机 1 直接把目的 IP 为 `10.20.0.3` 的包扔进机房交换机，机房路由器一看查无此网段，当场就会把它丢弃！

怎么在不去折腾全机房物理路由器配置的前提下，让两边的容器以为自己还插在同一台交换机上？网络世界再次祭出了最经典的万能招式——**再套一层信封！**

宿主机 1 把容器 A 发出来的整份原始以太网帧原封不动当成「货物」，外面再套上一个全新的数据包，外层目的 IP 稳稳写上宿主机 2 的物理地址 `192.0.2.20`！机房里的物理路由器只看外层包，毫不费力地把它送到了宿主机 2；宿主机 2 拆掉外层信封，取出里面原汁原味的内部帧，按内层目的地址精准交给容器 B：

```text
外层（机房物理网络看得见）：192.0.2.10 ── 物理路由器按外层转发 ──→ 192.0.2.20
  内层（只有两台宿主机拆开看）：10.20.0.2 ── 拆封后按内层交 B ──→ 10.20.0.3
```

像这样「把一种协议包整包塞进另一种协议包里穿越中间网络」的逻辑管道，叫作 **隧道**（tunnel）；架设在既有底层物理网络之上、由隧道编织出的整套虚拟逻辑网络，叫作 **覆盖网络**（overlay network）。如果在套外层包前顺手把内层加密，沿途机房设备连里面的明文都偷看不着，这就成了**加密隧道**（正是 WireGuard、IPsec 等现代 VPN 与安全覆盖网络的核心原理）。

### 一定要算清的账：VXLAN 封装如何「偷偷吃掉」你的 MTU？

在云原生与数据中心里，最经典的覆盖网络封装格式之一是 **VXLAN**（Virtual Extensible LAN）——它专门把完整的二层以太网帧装进外层 UDP 数据报里跨三层网络运送，并在 8 字节的 VXLAN 首部里写上一个 24 位的虚拟网络编号（VNI），让接收方宿主机精准分辨拆出来的内层帧属于哪一套隔离的虚拟网络。

但「俄罗斯套娃」是要扣空间的！还记得第 1 章讲过的[最大传输单元（MTU）](../chapter_01_foundations/02_packet_switching_and_performance.md#mtu)吗？假设底层物理机房链路的 MTU 是标准的 `1500` 字节。在没有额外 IPv4 选项和内层 VLAN 标签的常规配置下，让我们从外到内把新套上的「信封厚度」一笔一笔加出来：

- 外层 IPv4 首部：**20 字节**
- 外层 UDP 首部：**8 字节**
- VXLAN 隧道首部：**8 字节**
- 被装在里面的内层以太网首部：**14 字节**

四层一加，外包装足足吃掉了 $20 + 8 + 8 + 14 = 50$ 字节！于是，留给容器内部 IP 数据报的真正安全可用空间只剩下了：

$$
1500 - 50 = 1450\ \text{字节}.
$$

这一步算术直接揭开了一桩云上运维最经典的诡异故障：**如果底层路径禁止分片（或 ICMP 反馈被挡），而两头容器里的虚拟网卡还傻傻地以为自己的 MTU 是默认的 1500 字节——结果小请求（如 `ping`、SSH 敲几个字、小 JSON）全都畅通无阻，偏偏一拉大网页、一传大文件或者 TLS 握手发大证书链就彻底超时卡死！** 实际工程里必须根据具体封装格式（如 IPv6 外层、IPsec 加密填充等）把容器网卡 MTU 调小到安全值，或者干脆换一种思路——放弃隧道封装，把容器子网直接宣告进底层物理路由器里做 **直接路由**（underlay routing，零封装开销、保住完整 1500 MTU，但代价是必须让底层网络基础设施认识并接纳这些容器子网）。

把这一路遇见的虚拟网络积木收进一张速查表，你会发现逻辑无比清晰：

| 想解决的实际问题 | 对应的核心机制 |
| --- | --- |
| 让多个容器各自拥有独立的网卡、端口空间和路由表 | **网络命名空间**（network namespace） |
| 在两个隔离的网络命名空间之间拉一根软件网线 | **`veth` 对** |
| 在同一台宿主机的二层范围内按 MAC 转发帧 | **软件网桥**（bridge） |
| 跨越不同子网按最长前缀匹配选路 | **路由** |
| 改写地址/端口出网或发布端口，并按连接状态还原回包 | **NAT 与连接跟踪** |
| 跨物理机在既有底层网上架设独立逻辑网络 | **隧道与覆盖网络**（如 VXLAN） |
| 防止沿途中间节点偷看隧道里的通信明文 | **加密隧道协议** |

顺带一提，这套「覆盖网络 + 加密隧道」思路不仅用来连云端容器，也极其适合远程访问你放在实验室或家里的个人工作站！当你的笔记本和远方工作站都躲在各自的家庭/运营商 NAT 后面、谁也没有公网固定 IP 可以直接连入时，像 **Tailscale**（底层基于 WireGuard）这样的组网工具会替你建起一张私有覆盖网络：能打通 NAT 穿透就让两端直连加密互访；万一遇上严苛的对称 NAT 实在直连不通，双方就借道一个彼此都连得上的第三方节点来转发密文——这个兜底角色叫作 **中继**（relay，当然多绕一站也会受到中继延迟与带宽制约）。同时别忘第 7 章的忠告：覆盖网络只负责打通安全可达管道，目标机器上的应用与操作系统照样要做好自己的认证和权限把关！

## 把整张图无缝落到 Kubernetes 上

在真实生产集群里，成百上千台宿主机上的海量容器通常由 **Kubernetes** 统一调度编排。对照刚才的积木，Kubernetes 的网络抽象瞬间秒懂：

- **Pod**：Kubernetes 最小的调度单元，由一个或多个紧密协作的容器组成。在经典模型里，**每个 Pod 拥有自己独立的网络命名空间和专属 IP 地址**。如果把 A 和 B 放进两个不同的 Pod，它们各自都能监听 `8000` 端口互不冲突；而装在**同一个 Pod 内部**的多个容器则共享同一个网络命名空间，彼此直接用 `localhost` 就能极速对话（但也因此绝不能抢同一个端口号）。
- **节点与 CNI 插件**：运行 Pod 的每台宿主机叫作 **节点**（node）。节点本身并不把某一种具体的虚拟网络方案写死，而是定义了一套标准插槽规范——**容器网络接口**（CNI，Container Network Interface，详见 [CNI 规范](https://www.cni.dev/docs/spec/)）。每当新 Pod 创建时，节点调用你选装的 CNI 网络插件（如 Flannel、Calico、Cilium 等）自动帮它插好 `veth`、分好 IP、接上网桥或隧道/路由；Pod 销毁时再利落回收。不同 CNI 插件的拿手绝活各异——有的走 VXLAN 覆盖隧道开箱即用，有的走 BGP 直接路由榨干性能，有的还能用内核可编程技术在内核入口高速执行精细的网络放行策略（NetworkPolicy）。

可就在所有节点上的 Pod 都畅快互通的那一刻，一个致命的新痛点立刻浮出水面：

**在 Kubernetes 里，Pod 就像随时可能更换的易耗品！假如容器 B 所在的 Pod 崩溃重启了，调度器在另一台机器上拉起了一个崭新的替身，它的 IP 从 `10.20.0.3` 变成了 `10.20.0.4`！** 如果容器 A 的代码里死死写着旧 IP `10.20.0.3`，请求瞬间就会全线报错！

怎么办？聪明的解法是引入一层永不改变的「稳定门牌」——Kubernetes 称之为 **Service**——把背后动态漂移的 Pod 地址统统藏在稳定入口后面。这正是紧接着的 **第 9 章**：[服务发现、代理与负载均衡](02_service_discovery_proxies.md) 要带你彻底攻克的主题！排查集群通信故障时，也要养成顺藤摸瓜的习惯：先分清是「Pod 自己没监听好」「Pod 之间跨节点路由/隧道不通」，还是「Service 背后根本没有就绪的后端」，同时别忘了核查集群的网络放行策略与应用自身授权。

## 随堂自测

集群上线后，运维发现同一台宿主机上的两个容器互访飞快，但跨不同物理节点的两个容器通信时，却出现了诡异现象：发几十字的小请求每次都成功，可一旦接口返回几 KB 的大响应就直接卡住超时！你会优先重点检查哪两项？

??? note "参考思路"
    首先，立刻把目光锁定在跨节点链路与隧道封装上：
    1. **核对实际路径与封装后的有效 MTU**：检查跨节点流量走的是哪种覆盖隧道（例如 VXLAN 吃掉 50 字节），对照底层物理链路 MTU 核验容器网卡的 MTU 是否设置过大，同时检查沿途防火墙有没有把用来做路径 MTU 发现的 ICMP `Fragmentation Needed` / `Packet Too Big` 消息误拦掉了。
    2. **在路径两端抓包核实 TCP 重传证据**：不要光凭「小包通、大包断」就直接下定论！分别在源宿主机虚拟口、物理口和对端宿主机抓包，亲眼确认究竟是超大帧在物理出口被静默丢弃、还是中途防火墙按包大小或连接状态拦截、抑或是后端应用自己生成大响应时慢超时了。
