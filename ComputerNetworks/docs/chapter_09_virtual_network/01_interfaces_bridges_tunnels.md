# 从虚拟网卡到隧道：一条容器网络路径

**先修**：[地址和子网](../chapter_04_network/01_ip_addressing_subnetting.md)、[NAT](../chapter_04_network/02_ipv6_nat_icmp.md)、[以太网和 ARP](../chapter_05_link/02_ethernet_wifi_arp.md)。

**读完能做**：区分虚拟网卡、网桥、路由、NAT、隧道与加密分别改变了什么。

为了在同一台机器上部署两份服务，我们让两个容器各自监听 `8000`。如果它们使用同一个网络视图，两个进程在同一地址上占用同一端口就会冲突。给它们分开网络视图以后，问题又变了：既然各有一套接口和路由，A 怎样才能把请求送到 B？我们先解决一台机器上的问题，再把 B 搬到另一台机器上。

## 给隔离的进程接网线

网络 namespace 可以有自己的接口、路由表和端口空间。Linux 的 veth 是成对的虚拟以太网设备，一端发出的帧能从另一端收到。把一端交给容器，另一端接到宿主机，就得到一段可观察的虚拟连接。把多个宿主机端口接入同一网桥，可以像用二层交换机那样转发帧。

假设 A 地址为 `10.20.0.2`，B 为 `10.20.0.3`，两者都在同一台宿主机上。A 和 B 各有一对 veth，一端留给容器当网卡，另一端接到宿主机的虚拟网桥 `br0`。

```text
容器 A                        宿主机                         容器 B
eth0 ── veth 对 ── 宿主端口 a ── br0 ── 宿主端口 b ── veth 对 ── eth0
10.20.0.2/24                                             10.20.0.3/24
```

现在 A 从本地临时端口 `49152` 连接 B 的 `8000`。沿着第一个 TCP 连接请求看一遍：

| 步骤 | 谁在做决定 | 这一步用的地址或状态 |
| --- | --- | --- |
| 查路由 | A 的网络视图 | 目标 `10.20.0.3` 属于本地 `/24` 子网，下一跳就是 B |
| 找链路地址 | A 的 ARP | 若没有缓存，先问「谁拥有 `10.20.0.3`」，B 回复自己的 MAC 地址 |
| 过虚拟网线 | A 的 veth | A 把包装进以 B 的 MAC 为目的的以太网帧，帧从宿主端口 a 出来 |
| 过网桥 | `br0` | 用 MAC 找所在端口；尚未学到时可在这一网桥内泛洪 |
| 找应用 | B 的网络视图 | B 收到发往 `10.20.0.3:8000` 的连接请求，交给监听该地址和端口的程序 |

这条同子网路径上，A 和 B 的 IP 不需要改变。如果 B 只监听自己的 `127.0.0.1:8000`，帧仍可能成功到达 B 的网卡，但这次访问的目的地址是 `10.20.0.3`，找不到相应的监听者。容器里的 `127.0.0.1` 只指它自己的回环接口。

## 访问外网和访问宿主机入口

目标换成子网之外的地址时，A 把包交给默认网关。在常见的 Docker IPv4 桥接配置中，宿主继续路由，并可用**源 NAT**把出站源地址改成宿主地址。返回时宿主利用连接跟踪，把目标对应回 A。具体网络也可以让外部可路由到容器子网，按配置决定是否需要转换地址。

反过来，若希望用宿主机上的 `127.0.0.1:18000` 访问 B 的 `8000`，就要发布这个端口。它为宿主地址和容器的监听点建立一条转发路径，后端可由地址转换或代理等方式实现。两个容器各自可以用内部的 `8000`，只要发布到同一个宿主 IP 时选择不同的宿主端口即可。这个例子只绑定宿主回环，适合在本机练习。端口发布和容器出站 NAT 解决的是两个方向上的问题。

## 从一台宿主机扩展到两台

两台宿主机可能只有底层 IP 网络连通。隧道把内部包封装进外部包，外层地址用于到达隧道对端，解封装后继续处理内部地址。逻辑网络建立在现有网络之上，称为覆盖网络。封装增加头部开销，因而需要考虑有效 MTU、网络诊断位置和额外的数据路径。隧道可以配合加密，也可以只封装。

保留 A、B 的内部地址，把它们分别放到外部地址为 `192.0.2.10` 和 `192.0.2.20` 的两台宿主机上。假设这套覆盖网络延伸了同一个二层网段，第一台宿主把内部帧放进发往第二台宿主的外层包。底层路由只需把外层包送到 `192.0.2.20`；第二台宿主拆掉外层，再把内部帧送给 B。

```text
内部地址：  10.20.0.2  ────── 容器之间 ──────→ 10.20.0.3
外层地址：  192.0.2.10 ────── 宿主之间 ──────→ 192.0.2.20
```

假设底层链路最多承载 1500 字节的 IP 包，采用没有额外选项的 IPv4/UDP/VXLAN，外层 IP、UDP、VXLAN 头加上隧道里的以太网头共占 50 字节。内层 IP 包就只剩约 `1500 − 50 = 1450` 字节的空间。不能分片、两端还都认为可以发 1500 时，就可能出现小请求成功、大响应失败。实际值要按封装、链路及额外头部计算。另一种设计是为容器子网提供直接路由，省去封装，同时需要让底层网络认识这些子网。

| 要解决的问题 | 对应机制 |
| --- | --- |
| 容器各自有接口、端口和路由表 | 网络 namespace |
| 连接两个虚拟接口 | veth 对 |
| 同一二层网络内转发帧 | 网桥 |
| 跨子网按目标前缀转发 | 路由 |
| 变更地址或端口并在返回时匹配 | NAT |
| 在现有网络上传输另一套逻辑网络的数据 | 隧道与覆盖网络 |
| 要求链路上的中间节点看不到明文 | 加密协议 |

远程访问工作站时，若节点都没有可直接接收入站连接的公网地址，可以考虑受控的覆盖网络。NAT 状态、连接发起方向和网络策略决定直连是否可行；必要时经中继可达，代价是路径更长且吞吐受中继限制。Tailscale 是一个应用例子。能经虚拟网络到达服务，应用端仍需按自己的规则认证与授权。

## 把这张图用到 Kubernetes

如果把 A、B 运行在两个普通 Pod 中，它们通常各有一个 Pod IP，可以都监听 `8000`。同一个 Pod 里的容器共享网络视图和端口空间，放在一起的程序便能通过 `localhost` 互访，也要避免争用同一监听地址。节点上的网络实现负责连接 Pod；可能用网桥和隧道，也可能使用直接路由等数据路径。

Pod 重建后，地址可能变化。希望客户端继续用同一个名字时，可以在这些地址之上加一层 [Service 与服务发现](02_service_discovery_proxies.md)。排查时先分清问题出在 Pod 自己的监听、Pod 之间的送达，还是 Service 没有可用后端。能路由到目标也不代表所有应用都能访问它，具体放行还要看应用授权及网络插件所执行的策略。

## 自测

如果同一宿主机上的两个容器可以互访，但不同节点的容器间只有小请求成功，大响应超时，你会检查哪两项？

??? note "参考思路"
    检查跨节点流量实际走哪条路径，以及封装后有效 MTU 和相关反馈是否正常。也要结合抓包位置与 TCP 重传判断，避免直接把所有超时归因于 MTU。

桥接和端口发布的实际选项见 [Docker 网桥文档](https://docs.docker.com/engine/network/drivers/bridge/)。封装格式见 [RFC 7348](https://www.rfc-editor.org/rfc/rfc7348)。Pod、Service 和网络插件的分工可对照 [Kubernetes 网络概念](https://kubernetes.io/docs/concepts/services-networking/)。
