# 服务发现、代理与负载均衡

上一章里，我们亲手用虚拟网卡、网桥和 VXLAN 隧道把跨越不同物理机的容器连成了一张顺畅的大网。可刚刚松了一口气，一个在真实生产系统里天天上演的难题就砸在了眼前：

容器天生不是永久不变的宠物，而是随时可能崩溃重启、发版替换、按流量潮汐自动扩缩容的易耗品。今天后端容器 B 的地址是 `10.20.0.3`，十分钟后发个新版本重启一下，它就变成了 `10.20.0.4`——如果上游客户端代码里死死写着旧 IP，整套系统每次发版都会瞬间瘫痪！

面对朝生暮死、数量随时增减的后端实例，客户端却只有一个朴素愿望：**「我只想永远敲同一个稳定的服务名字（比如 `api.example.test` 或 `web`），别让我操心后面换了几台机器！」**

这一章，我们就把这层稳定入口彻底拆开，看清 **服务发现**、**反向代理** 与 **负载均衡** 是怎样联手在动态变化的云端世界里撑起「稳如泰山」的访问体验。

## 后台从 A 悄悄换成 B，客户端为什么毫无察觉？

设想你的客户端一直连着 `api.example.test`。如果这个域名在 DNS 里直接硬指着后端服务器 A 的 IP，当你把业务从 A 升级替换成新机器 B 时，麻烦就会一串串冒出来：全球各地还把 A 的旧 IP 攥在 DNS 缓存里的客户端会继续傻傻地往死掉的 A 上撞；正在 A 上跑了一半的长请求更会被粗暴掐断！

工程界的解法直击要害——**在客户端和真实后端之间，竖起一道地址永不轻易改变的「稳定接待大厅」**。这类站在服务端前面替真实应用接住请求、再按规则转交给后面真正干活的机器的中间角色，叫作 **反向代理**（reverse proxy）；躲在它后面实际干活的 A 和 B，则统称为 **后端**（backend / upstream）。

有了这道稳定门面，一场丝滑的「零中断发布（滚动替换）」就能像换岗哨兵一样从容上演：

1. 启动新实例 B，但先不急着分流，耐心等它把模型、缓存和数据库连接彻底加载妥当；
2. 确认 B 真正准备好接客了，把它加入反向代理的可用后端清单；
3. 把老实例 A 标成「不再接新单」，同时宽限它几十秒把手上已经接下的旧请求体面处理完；
4. 等旧请求清零后，再安安静静关掉 A。

整个切换过程中，大厅的门牌号（`api.example.test` 对应的入口 IP）纹丝未动，客户端压根不需要改一行配置，甚至察觉不到背后已经换了一轮兵马！

??? question "新部署的后端进程 B 明明已经启动成功、端口也监听上了，为什么反向代理还不急着立刻把线上流量切给它？"

    「进程活着」和「能正常干活」往往隔着好几秒甚至几分钟的鸿沟！比如一个图像识别或大语言模型推理服务，进程一秒就拉起来了，可它后台还得花二十秒把几个 GB 的权重文件加载进显存、预热本地缓存并连上数据库。如果进程一启动就把海量线上请求灌过去，瞬间全变成报错和超时！因此代理会持续向 B 发专门的小探测请求，专门核实「你现在真的具备接待业务的条件了吗？」——这就是 **就绪检查**（readiness probe）。切换后同样要给老实例 A 留出收尾窗口，不能一刀切死旧连接。

**先修**：[从服务名到监听中的进程](../chapter_02_application/04_socket_and_listening.md)、[DNS](../chapter_02_application/02_dns.md)、[TLS 与可信连接](../chapter_06_security/01_tls.md)。

**读完能做**：沿着一个稳定服务名一直追到最终处理请求的那个后端进程，说清当后端扩缩容或故障替换时，控制平面、数据平面、健康检查与连接排空各自负责哪一环。

## 从一个固定地址到一组动态端点：服务发现与双平面分工

当后端从孤零零的一台变成随时在增减的十台甚至一百台，代理（或者直接连后端的客户端）必须实时知道「此刻到底有哪些健康、就绪的后端可以连」——把稳定服务名动态映射到这组当前可用后端列表的机制，叫作 **服务发现**（service discovery）。

清单里的每一条具体可连目标，称为一个 **端点**（Endpoint），它通常精确到 `IP:端口`（例如 `10.20.0.3:8000`），并且附带着「是否就绪」的实时状态标记。

这里你可能又会想起老朋友 DNS：「干脆直接用 DNS 返回所有后端的 IP 列表，坏了我就改 DNS 记录，不就省了反向代理吗？」直接用 DNS 做后端发现确实简单，但它会立刻撞上第 2 章讲过的 **TTL 缓存墙**：哪怕你 1 秒内把坏掉的后端 A 从权威 DNS 里删了，下游各级递归解析器和客户端只要旧缓存还没过期，就会继续往死掉的 A 上发请求；可要是把 TTL 压得极短，又会成倍放大查询延迟和 DNS 服务器压力。

更现代、更敏捷的架构把「处理真实业务流量」和「维护后端花名册」干净地拆成了我们在第 5 章路由器里已经见过的**两个平面**：

- **控制平面**（control plane）：由专门监控全局状态的**控制器**（如 Kubernetes 控制面）或**服务注册中心**负责——每当有新后端上线通过就绪检查、或者某台机器宕机失联，控制平面立刻刷新花名册，在毫秒到秒级主动推送给所有入口代理；
- **数据平面**（data plane）：反向代理和负载均衡器握着这份最新花名册，全速接住客户端发来的真实 TCP/TLS 连接与 HTTP 请求，按规则分发给健康的后端进程。

```text
客户端 ──→ DNS 解析 ──→ 稳定服务入口地址
客户端 ──→ TCP/TLS ──→ 反向代理（数据平面）──→ 选定健康后端 A 或 B ──→ 应用进程
                              ▲
控制平面（控制器 / 服务注册表）──┘ 实时推送可用端点列表与就绪状态
```

不过，控制平面把老后端 A 从花名册里划掉之后，别漏掉一个极其隐蔽的现场细节：**那些在切换前就已经和 A 建好持久 TCP/HTTP 长连接的客户端，并不会因为花名册改了就自动神奇地瞬移到 B！** 如果直接拔掉 A 的电源，这些老连接上的在途请求会瞬间全线报错。

优雅的做法叫作 **连接排空**（connection draining / graceful shutdown）：先把 A 从新流量列表里摘除，让代理不再把任何新请求分给 A，同时给正在 A 上跑的已有连接留出一段宽限时间把未完成的响应送回客户端，再发送礼貌关闭信号；万一超过宽限上限还有赖着不走的超长连接，才强制断开，并由客户端优雅重连到新后端 B。

## 四层负载均衡 vs 七层反向代理：它们分别看得见什么？

当门面后面站着十台健康后端，按照轮询、最少连接数或一致性哈希等规则把蜂拥而来的连接或请求均匀分给其中一台，就是 **负载均衡**（load balancing）。

在工程对话里，你几乎天天会听到「四层负载均衡（L4）」和「七层反向代理（L7）」这两个行话。这里的「四」和「七」，正是借用了第 1 章讲过的 [OSI 七层模型](../chapter_01_foundations/01_layering_and_encapsulation.md#tcpip-osi) 编号——**第四层是传输层（TCP/UDP）**，**第七层是应用层（HTTP 等）**。它们的根本差别就一句话：**站得越高，拆开的包越深，看得越清，干的活越精细，付出的算力与配置复杂度也越高！**

- **四层负载均衡（L4）**：只拆到网络层和传输层首部，靠五元组（源/目的 IP、源/目的端口、协议）做决定，把整条 TCP 连接直接转发或 NAT 给选中的某一台后端。它压根不管里面跑的是 HTTP、MySQL 数据库协议还是自定义二进制游戏协议，也**不需要解密 HTTPS**——性能极高、通用性极强，代价是对应用内容一无所知（比如它看不出请求路径是 `/images` 还是 `/pay`，也无法在同一条 HTTP/2 长连接里把不同请求分摊到不同后端）。
- **七层反向代理（L7）**：必须先自己和客户端完成完整建连、拆到应用层读懂完整的 HTTP 报文！因此它能做出极其精细的业务级分流——例如把 `Host: blog.example.test` 交给博客集群，把路径 `/images/*` 交给专门的对象存储网关，把 `/api/v2` 灰度分流 5% 给新版本，甚至顺手做压缩、鉴权、限流和精细的请求级日志审计。

可一旦碰上加密的 HTTPS，七层代理立刻面临一个物理现实：**密文不解开，代理根本看不见里面的 `/images`！** 因此，要让七层反向代理按 HTTP 路径分流 HTTPS 流量，加密连接就必须在代理处终止解开——这就是第 7 章已经见过的 **TLS 终止点**（TLS termination point）。随后，代理再按需要决定用明文还是开启一段崭新的内部加密连接把请求转发给后端。

| 对比维度 | 四层负载均衡（L4） | 七层反向代理（L7） |
| --- | --- | --- |
| **核心决策依据** | 连接的 IP 地址、端口号与传输协议 | HTTP 的 `Host` 站点名、URL 路径、请求方法、首部甚至 Cookie |
| **加密 HTTPS 处理** | 可直接透传密文给后端（无需持有网站证书私钥） | 必须作为 **TLS 终止点** 先解密才能读懂路径与首部（需托管证书） |
| **性能与适用场景** | 吞吐极高、开销小，通吃所有 TCP/UDP 协议（数据库、SSH、游戏等） | 业务路由极其灵活、支持丰富网关治理，但需承担协议解析与加解密开销 |

### 健康检查的三把尺子与超时防护

为了让负载均衡器不把流量送进黑洞，系统会持续对每个后端做 **健康检查**（health check）。现代容器编排和代理体系非常讲究把后端的「健康」拆成三种截然不同的状态来问：

1. **启动检查**（startup）：慢启动的大服务还在漫长初始化阶段，先别误杀它；
2. **存活检查**（liveness）：进程是不是彻底卡死或陷入死锁了？只有确认真「死透」了才重启它；
3. **就绪检查**（readiness）：进程虽活着，但此刻准备好接线上流量了吗？（比如本地缓存刚清空或依赖数据库短暂抖动时，只需暂时从负载均衡名单里摘掉歇一歇，绝不能贸然把所有实例全重启——否则一波下游小抖动会被错误的重启风暴放大成全站雪崩！）

同样地，稳健的反向代理必须把**连接建立超时**、**单次请求总超时**和**长连接空闲超时**分别清清楚楚设好，绝不让某几个卡死的慢后端把整个代理的连接池全部拖干。

## 回到实战：把上一章的两个容器接到 Kubernetes 稳定入口

让我们顺手把上一章留下的悬念彻底闭环！在上一章末尾，容器 A 想访问容器 B，可 B 重建后 IP 从 `10.20.0.3` 变成了 `10.20.0.4`。

现在，我们在 Kubernetes 集群里为 B 这一组后端创建一个名为 `web` 的 **ClusterIP Service**（集群内部默认类型的稳定虚拟入口），系统会给 `web` 分配一个**生命周期内永不改变的虚拟集群 IP**，例如 `10.96.0.10:80`。

看看全过程怎样丝滑运转：

1. **初始阶段**：集群内置 DNS 自动把 `web` 解析为稳定入口 `10.96.0.10`。控制平面看着 B 的 Pod（`10.20.0.3:8000`）通过了就绪检查，于是把它登记进 `web` 的端点列表，并把转发规则同步到集群各个节点的网络数据平面（例如通过内核规则或代理）。容器 A 访问 `http://web`，流量经稳定入口丝滑落到 `10.20.0.3:8000`。
2. **无缝替换**：现在运维升级重建 B。新 Pod 拿到崭新 IP `10.20.0.4` 并监听 `8000`；等它通过就绪检查后，控制平面第一时间把 `web` 的后端端点更新成 `10.20.0.4:8000`，同时把旧的 `10.20.0.3:8000` 移出新流量列表并让它排空收尾。
3. **客户端毫无察觉**：容器 A 发起新连接时，依然只认 `web`（`10.96.0.10:80`），请求瞬间自动流向了新地址 `10.20.0.4:8000`！至于切换前就已经连在旧 Pod 上的长连接，则会随旧进程优雅排空结束，必要时由客户端自动发起重连切换至新后端。（详见 [Kubernetes Service 文档](https://kubernetes.io/docs/concepts/services-networking/service/)。）

## 实战排障练习

设想线上突然告警：客户端访问 `https://api.example.test/tasks` 时，域名解析完全正常，TLS 握手也顺利通过，可入口反向代理却冷冰冰地吐回了一个 **`503 Service Unavailable`**（服务暂时不可用）。

1. 请顺着分层路径指出：到目前为止哪几段已经确认畅通？你接下来的**头两个排查动作**是什么？
2. 紧接着换一个场景：请求已经顺着代理送进了后端，结果客户端干等 30 秒只等来一次**超时**——此时客户端敢不敢直接自动重试？满足什么条件才算安全重试？

??? note "参考思路"
    **第一问（面对 `503 Service Unavailable`）**：
    收到代理返回的 `503`，说明从客户端的 DNS 解析、公网路由、TCP 建连到代理的 TLS 终止点全部畅通无阻！问题出在「代理往后端找人」这一截。紧接着最直接的两个排查动作：
    1. **查控制平面与健康检查状态**：看代理手里的可用后端清单是不是空了（比如所有后端实例刚发版全都没过就绪检查，或被健康检查全部摘除）；
    2. **查代理到后端的网络连通与后端监听**：若花名册里明明有后端，立刻从代理节点测试到后端 `IP:端口` 的连通性、检查后端进程是否真的监听在正确地址以及中间安全组/网络策略是否放行。

    **第二问（面对响应超时后的重试）**：
    超时绝不等于「后端没执行」！特别是像提交任务、创建订单、扣款这类有副作用的非幂等写操作，请求很可能已经落库成功，只是回执丢在半路。只有在**业务操作天然幂等**（如只读查询），或者客户端在首次请求时就生成并附带了全局唯一的 **幂等键**（idempotency key）、且服务器能凭它识别重复提交并返回同一份结果时，才可以安全重试！此外，任何重试机制都必须配好最大重试次数、指数退避等待和总超时预算，防止把本就濒临崩溃的后端活活重试垮掉（重试风暴）。

至此，第 8 章和第 9 章已经把现代云端微服务世界的「虚拟组网」和「服务发现与负载均衡」彻底打通。无论前面有多庞大的用户流量，还是后面有几百个朝生暮死的容器，这套「客户端 ↔ 稳定入口 ↔ 弹性后端」的范式都能稳稳接住。

然而，如果你走进今天最炙手可热的大型数据中心内部——特别是那些塞满成百上千张 GPU、日夜训练大语言模型的 AI 集群——你会震惊地发现，这里的网络游戏规则彻底变了天！

在这里，主角不再是成千上万个互不相干的浏览器去访问网页，而是几百上千个并肩作战的计算进程：每一轮计算短短十几毫秒，所有机器算完自己手头那一份后，必须**齐刷刷地交换几百 MB 的梯度参数、算出总和再一起迈向下一步**。只要其中有一台慢了 5 毫秒，或者交换机里撞了一下车，全场几百张昂贵的芯片就得一起干瞪眼空转！
