# 服务发现、代理与负载均衡

## 后台从 A 换到 B，客户端为什么还能用同一个名字？

设客户端一直连接 `api.example.test`，这个名字指向代理。代理最初只把请求交给 A。部署 B 时，先启动 B、等待就绪，再把它加入后端列表；最后让 A 完成在途请求。客户端使用的名字可保持不变，代理调整的是从入口到后端的连接。

??? question "为什么 B 进程已经启动，还不急着把流量切给它？"

    例如模型还没装入显存，启动成功但暂时不能服务。就绪检查应覆盖能接收请求的前置条件，切换还要给旧连接留出结束的机会。

**先修**：[本机服务](../chapter_02_application/04_socket_and_listening.md)、[DNS](../chapter_02_application/02_dns.md)、[TLS](../chapter_06_security/01_tls.md)。

**读完能做**：从一个服务名追到一个实际后端，解释后端替换时每一层负责更新什么。

## 从一个地址变成一组地址

假设客户端调用 `api.example.test`，后端 A 重启后地址变了，B 新加入。客户端需要一个比较稳定的服务入口；代理或客户端需要发现可以用的后端地址、端口以及就绪状态。一个后端 Endpoint 可以描述「哪里可连」；是否当前可以接收业务，还要看健康和就绪信息。DNS 缓存会延迟客户端看到某些地址变化，短 TTL 则会增加解析请求。

```text
客户端 → DNS 解析 → 服务入口地址
客户端 → TCP/TLS → 反向代理 → 选后端 A 或 B → 应用进程
控制器或服务注册信息 ──────────────────→ 后端地址和就绪状态
```

数据平面搬运请求与响应，控制平面维护规则和后端集合。只更新后端列表，已有的长连接也可能继续使用原连接，需要考虑连接排空和长连接重连。

## 四层和七层分别看得见什么

| 方式 | 常见决策依据 | 适用与代价 |
| --- | --- | --- |
| 四层负载均衡 | 连接的地址、端口和协议等 | 可以处理多种传输层服务；通常看不到加密后的应用内容 |
| 七层反向代理 | Host、路径、方法等应用信息 | 可按业务路由和记录请求；需要处理应用协议，分析 HTTPS 请求内容时需合适的 TLS 终止位置 |

健康检查有不同目标。「进程还活着」「已完成启动」「可以接收请求」是三种状态。只有就绪后才发流量，避免请求落到还没加载好模型的进程；短暂下游抖动时，贸然重启所有实例反而会削弱服务容量。连接超时、总请求超时和空闲超时也要分别设定。

## 练习

假设服务名能解析，TLS 正常，但代理返回 503。画出已经成功的路径，列出两个下一步动作。再设想客户端请求已经送到后端，但响应超时。什么时候可以安全重试？

??? note "参考思路"
    先看代理是否有就绪的入口，以及代理到后端的网络和应用监听。超时后要根据操作语义判断，读操作通常更容易重试，创建任务等有副作用的调用可用幂等键约束重复。还要给重试次数和总时间留出预算。
