# 虚拟网络与服务发现 { #9 }

读完前七章，你已经对「一台物理机器、一块物理网卡、连着一台物理交换机」的经典网络世界了如指掌。但只要你今天打开任意一台云端服务器，或者在自己的笔记本上敲下一行 `docker run`，眼前就会出现一幕看似违背常识的景象：

**明明只有一台机器、一块物理网卡，却同时跑起了两个都监听 `8000` 端口的网页服务，彼此不仅没有报错冲突，还各自拥有一块 `eth0` 网卡和专属的 IP 地址！** 更神奇的是，它们明明同住在一块主板的内存里，连一根铜线都没接，却能像隔着交换机的两台独立电脑一样互发以太网帧；甚至把其中一个搬到千里之外的另一台宿主机上，它们依然能以为自己还在同一个局域网里畅快对话！

这正是现代云原生基础设施的基石——把物理世界里的网卡、网线、交换机和路由器全部搬进操作系统内核，用软件虚拟出来。

## 从「两个 8000 端口和平共处」开始

把一个应用连同它的文件系统、进程空间和独立网络视图打包进一个轻量隔离环境，就是我们今天无处不在的 **容器**（container）。既然容器 A 和容器 B 各自拥有互不干扰的网络视图，它们当然可以各自安稳地监听 `8000` 端口。

可隔离带来了一个立刻要解决的新问题：**彻底隔开之后，A 该怎么把请求送到 B 手里？**

为了把现代虚拟网络看得清清楚楚，我们把这一整段云端演进拆成紧密衔接的两章：

1. **第 8 章（本章）：[从虚拟网卡到隧道](01_interfaces_bridges_tunnels.md)**
   - 先在同一台宿主机上，给隔离的容器 A 和 B 接上软件网线（`veth` 对）和虚拟交换机（软件网桥），亲眼看第一个请求怎样走过 ARP、MAC 学习和回环边界；
   - 再让容器连出公网、让外部流量连进宿主发布端口，看源 NAT、连接跟踪与包过滤如何协作；
   - 最后把容器 B 搬到另一台物理宿主机上，用 **隧道** 与 **覆盖网络**（如 VXLAN）把两地连成一体，亲手算清多层封装吃掉多少 MTU，并把整张图自然落到 Kubernetes 的 Pod 与网络插件（CNI）上。
2. **第 9 章（紧随其后）：[服务发现、代理与负载均衡](02_service_discovery_proxies.md)**
   - 容器天生「朝生暮死」，B 随时可能崩溃重建、换一个崭新的 IP。客户端总不能每次都改代码追着新 IP 跑！下一章将顺势解开「如何把变动不居的后端藏在一个稳定服务名背后」，打通服务发现、反向代理、四层/七层负载均衡与 Kubernetes Service。

## 与前七章的汇流点
