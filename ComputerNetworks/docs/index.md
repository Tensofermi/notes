# 计算机网络

不妨从一个再熟悉不过的场景开始：你在手机或电脑上点开一张照片，发给远在千里之外的朋友。照片动辄几兆字节，不可能像倒水一样一股脑从这头直接泼到那头。为了不让一张大照片把公共线路彻底堵死，网络会先把它切成许多规整的小块，每一小块叫作一个 **分组**（packet）；接着，这些小块要接力穿过家里的无线信号、运营商的机房光纤、海底光缆等许许多多段物理通道，每一段直连的通道叫作一条 **链路**（link）。

一路上，麻烦远不止「把一串 `0` 和 `1` 送到对端」这么简单。同一段链路可能有成千上万人在同时争抢，分组可能走散、迟到、甚至在拥堵的路口被直接丢弃；远处的接收方可能一时处理不过来；沿途经过的中间设备也未必完全可信。因此，计算机网络真正要解决的核心问题是：**如何让彼此独立、相隔甚远、硬件和速度各不相同的设备，依然能够稳定、可靠、安全地交换信息，仿佛置身于同一个系统之中。**

## 贯穿全书的主线问题

为了避免把网络学成一堆互不关联的缩写名词，这套笔记用一条完整的主线把所有知识串起来：

> 在浏览器地址栏里输入一个网址（**URL**，Uniform Resource Locator），按下回车之后，屏幕上的网页究竟是如何一步步出现的？

这看似轻描淡写的一次点击，背后其实是整个网络栈的精密协作：

- 首先，浏览器只拿到了人类好记的网站名字，得先找一套全网「电话簿」系统（**DNS**）查出目标机器的数字地址；
- 拿到地址后，浏览器要按照一套事先约定的问答格式（**HTTP**）写下「请把首页给我」，并在需要保密时先用加密握手（**TLS**）把这条信道锁起来，防止窃听和篡改；
- 写好的请求交到底层去运送，传输层协议（如 **TCP** 或较新的 **QUIC**）负责把数据可靠地交给目标机器上正确的程序，还得小心翼翼地控制发送节奏，既别把对方撑爆，也别把公共道路堵死；
- 跨越大半个地球时，网络层协议（**IP**）负责给每个分组指明方向，让沿途的每一台中转设备都能挑出正确的下一站；
- 真正踏出每一步时，局域网里的有线以太网（Ethernet）或无线 Wi-Fi 负责把数据变成物理信号，送到眼前这根线缆或这片空域的下一台设备手里。

分层设计让我们在学习时可以逐层拆解、各个击破；但到了真实世界里，网页能不能打开、快不快、安不安全，永远是所有层次端到端通力合作的结果。

## 动手先行：先建立手感

如果你是第一次系统学习计算机网络，不必等到背完所有协议再动手。建议先趁热打铁做三个迷你小实验，先把直觉立起来：

1. 先[在自己电脑上启动一个极简服务并发出请求](chapter_02_application/04_socket_and_listening.md)，亲眼对比「收到网页找不到（HTTP 404）」和「压根连不上（Connection refused）」这两种完全不同的失败方式——前者说明网络通了、程序也在工作，后者说明门都没敲开；
2. 接着试着[把六个乱序抵达的字节重新拼回原样](chapter_03_transport/02_reliable_transport.md)，体会底层信道不可靠时，两端到底靠什么保证数据不丢不乱；
3. 再思考[发送方明明有数据，为什么有时必须停下来等](chapter_03_transport/03_flow_congestion_control.md)，感受网络里的「礼让」与拥堵控制。

哪怕此刻还不认识其中的协议细节，亲手走完这三个例子，后面读到对应章节时也会有一种「原来如此」的踏实感。

## 一个先行的直觉：跨国物流与互联网

在接触正式术语之前，不妨先把互联网想象成一套极其高效的跨国物流系统。你要把一件礼物寄给海外某栋写字楼里特定办公室的朋友，整个流程里的各个角色几乎都能在网络中找到对应的影子：

| 网络概念 | 物流类比 | 回到真实网络时的关键区别 |
| --- | --- | --- |
| 应用报文 | 箱子里的礼物与附带的说明信 | 信怎么写、对方怎么回，完全由应用协议的严格格式约定 |
| 传输层端口 | 写字楼里的房间号 | 用于把送到这台机器的数据精准交给对应的进程 |
| IP 地址 | 国家、城市与街道门牌 | 并非随机编号，而是带有网络拓扑结构，方便沿途指路 |
| 路由器 | 各级物流分拨中转站 | 每站只查表决定「下一站发往哪个方向」，不替你规划全程细节 |
| 链路层帧 | 某一段运输专门换上的周转箱或集装箱 | 每换一种交通工具（如卡车换货轮），外包装就会拆掉重打 |

这个类比能帮你迅速抓住「各管一段、逐层嵌套」的大局观，但千万别把它当成全部真相。在真实网络里，拆成多份寄出的包裹完全可能后发先至（乱序），甚至半路凭空消失，靠两端主机上的传输协议默默补发和重排；更关键的是，物流分拨靠人眼扫面单，而网络设备必须在纳秒到微秒间吞吐海量流量，一切都依赖毫厘不差的二进制首部格式和硬件查表。

## 读懂任何协议的六个问题

后面十章里，我们会陆续遇到 HTTP、DNS、TCP、IP、ARP、TLS、BGP、VXLAN 等几十个名字。死记字段位数既痛苦又容易忘，更聪明的做法是每学一个协议，都拿出下面这把「六问标尺」去量一量它：

1. **它要对抗什么失败模式？**（是线路会丢包、地址会变化，还是中间有人窃听？）
2. **它向上一层做出了什么承诺？**（是「尽力而为送过去」，还是「保证一个字节不差且严格有序」？）
3. **报文里具体是哪些字段支撑了这个承诺？**（没有序号就谈不上排序，没有校验和就谈不上检错。）
4. **状态保存在哪里？**（由通信两端的机器自己记着，还是沿途的每台路由器都得记一笔？）
5. **它付出了什么代价，换来了什么性质？**（可靠性换来了重传延迟，安全换来了握手往返与算力开销。）
6. **真出问题时，抓包能看到什么证据？**（能不能把抽象概念和屏幕上真实流动的数据帧一一对上号？）

学计算机网络，从来不是为了背诵一本协议名词词典。真正的掌握，是当一个请求变慢、超时或失败时，你能在脑海里迅速回放数据穿过每一层的画面，并从眼前的现象反推出问题究竟出在哪一环。
