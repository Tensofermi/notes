# 抽象层次与接口契约

## 同一行加法，在每一层分别看见什么？

假设你在代码里写下了一行再普通不过的语句：`total = count + 1`。

站在高级语言的视角里，这行代码干净得像一道小学算术题：拿到变量 `count` 的值，加上 1，再存进 `total`。你既不需要操心 `count` 躺在主板哪一根内存条的哪一排单元里，也不需要操心电压怎样在硅片上跳变。

可芯片并不认识 `total`、`count` 或 `+` 号。为了让这行代码真正跑起来，编译器必须先把它翻译成处理器听得懂的底层命令——一条条由 0 和 1 编码而成的**机器指令**（machine instruction）。落到这一层，画面立刻变了样：原来的一行加法，往往要拆成「先从内存把 `count` 读进某个寄存器」「再给这个寄存器里的数加 1」「必要时把新值写回内存」这样一串明确的步骤。

如果再把镜头往下推一层，钻进处理器芯片内部，景象又完全不同了。电路设计者看到的甚至不再是「指令」，而是一串串高低电平信号，它们沿着铜线涌进加法器，在时钟节拍的催促下翻转开关，把结果锁存进寄存器。

更有意思的事情就在这里发生了：同一条加法机器指令，交给十年前的老芯片和今年刚出厂的新芯片，两块芯片内部的电路排布天差地别，完成这条指令所花的步骤数量也可能完全不同——然而只要程序能观察到的结果分毫不差，软件就浑然不觉。为什么底层的实现可以翻天覆地，上层的代码却能稳坐钓鱼台？这正是「分层与接口契约」要回答的核心问题。

??? question "如果给处理器换上一块更大、更快的缓存，原先编译好的机器指令需要重写吗？"

    不需要。缓存是处理器内部用来暂存常用数据的快速存储，属于底层实现细节。只要新处理器依然遵守同一套指令规则，对同一条指令给出完全相同的运算与访存结果，原先编译好的二进制程序就可以原封不动地继续运行——唯一的变化是它跑得更快了。

## 动机：复杂性无法消灭，只能切开

一颗现代处理器里集成着数十亿甚至上百亿个晶体管。就算把全世界最聪明的程序员集中起来，也不可能直接去指挥每一颗晶体管在哪一纳秒导通、在哪一纳秒关断。面对这种量级的复杂性，工程界唯一的出路不是试图消灭它，而是用一道道清晰的边界把它**切开**。

切开复杂性的核心手段叫**抽象**（abstraction）：我们人为划定若干层次，让每一层都只对正上方暴露简洁、稳定的规则，而把自己内部盘根错节的细节藏在边界之后。上层只需要信任下层承诺的行为，下层则可以在不违背承诺的前提下，放心大胆地改进内部实现。

在整台计算机的分层体系中，最关键的一道分界线把软件世界和硬件世界隔开：

- 分界线本身，就是我们在概述里提到过的**指令集架构**（ISA）——它像一份白纸黑字的法律条文，规定了处理器认识哪些指令、有哪些寄存器可供读写、内存怎样按地址访问。
- 紧贴在分界线之下的具体电路组织方式，则称为**微体系结构**（microarchitecture）——它回答的是「怎么用电路把这份条文又快又省电地做出来」。

正因为有了这道分界线，微体系结构层才获得了施展拳脚的空间。比如，芯片设计师可以把一条指令的执行拆成取指、译码、计算等几个阶段，像汽车装配车间一样让多条指令前后衔接、重叠推进——这就是第 6 章要深入剖析的**流水线**（pipeline）；他们也可以在处理器身边布置多级缓存，把程序刚用过的数据留手边，免得每次都去跑慢吞吞的主内存。无论加不加流水线、缓存做成多大，只要对外呈现的指令执行结果与 ISA 条文丝毫不差，上层软件就无需修改一行代码。

把整台机器从上到下摊开，大致呈现为下面这六层：

```text
应用与算法
  ↓
高级语言、编译器、操作系统
  ↓
指令系统结构（ISA）            ← 软硬件之间的契约边界
  ↓
微体系结构：数据通路、控制、流水线、cache
  ↓
数字逻辑：逻辑门、组合电路、时序电路
  ↓
器件与工艺：晶体管、连线、存储单元
```

值得注意的是，信息并不只是单向地「自顶向下」流动，下层在必要时也会「自底向上」敲门汇报。举个例子，如果某条指令试图去读写一块压根不存在或者无权触碰的内存地址，硬件不能装作无事发生，而会立刻叫停当前指令，把控制权转交给操作系统，并附上出事的原因。这类由指令执行触发、迫使处理器暂停当前流程并转入专门处理程序的事件，叫做**异常**（exception）。

除了报错，硬件还常常把自己的运行状态如实向上汇报。现代处理器内部埋设了大量**性能计数器**（performance counter），默默统计诸如「执行了多少条指令」「发生了多少次缓存未命中」之类的底层事件。软件层感受到的「程序变慢了」，很多时候正是靠读取这些硬件计数器才真相大白的。

## 接口与实现：自由的代价

把上面的想法再往前推一步，就能提炼出一对贯穿整个计算机科学的概念：**接口**（interface）规定使用者可以依赖什么承诺，**实现**（implementation）则说明提供者打算怎样兑现这些承诺。

拿一条普通的加法指令来说，ISA 这份接口契约会清清楚楚地写明：两个加数从哪几个寄存器取、结果保留多少位宽、结果写回哪个寄存器，以及专门用来记住「下一条该执行哪条指令」的**程序计数器**（program counter，简称 **PC**）应该前进多少字节。

但 ISA 通常**绝口不提**芯片内部该花几个时钟节拍算完这条加法，也不规定是老老实实一条接一条算，还是在确保最终结果等价的前提下，让排在后面但数据已经齐备的指令抢先执行——后者就是现代高性能处理器常用的**乱序执行**（out-of-order execution）。换句话说，ISA 管的是「最终账本对不对」，微体系结构管的是「背后怎么算得最快」。

把接口和实现解耦，换来了两笔极其丰厚的工程红利：

- **软件生态得以跨代长青**：几十年前针对同一 ISA 编译出的程序，无需修改就能在最新一代芯片上流畅运行，用户和开发者的历史投入不会随着换代清零。
- **硬件设计得以百花齐放**：面对同一份 ISA 契约，手机芯片可以优先追求省电与小面积，服务器芯片可以不惜代价堆叠缓存与乱序执行部件，大家在面积、功耗和性能的三角之间各取所需。

当然，天下没有免费的午餐。接口一旦广泛流行、上面长出了庞大的软件生态，就几乎变成了「只能往里加、极难往外删」的石头。哪怕几十年前设计出的某条冷门指令或寻址模式在今天看来既笨重又碍事，为了不让老软件崩溃，新一代处理器也往往不得不继续花宝贵的芯片面积去兼容它。

那么，这份听起来有些抽象的「ISA 契约」，落到一条真实可见的程序片段上究竟长什么样？让我们拿一个最小、却完整的例子，从头到尾剖开看看。

## 最小完整例子：`z = x + 1`

设想内存里紧挨着放了两个 32 位整数变量 `x` 和 `z`。此时，寄存器 `x10` 里存着 `x` 在内存中的起始地址；因为一个 32 位整数占 4 个字节，所以紧跟在 `x` 后面的 `z`，它的地址正好是 `x10 + 4`。

在 RISC-V 指令集里，要完成 `z = x + 1`，编译器通常会生成下面这三条简短的汇编指令（其中 `lw` 表示从内存读取一个 32 位字，`addi` 表示把寄存器里的数加上指令自带的常数，`sw` 表示把一个 32 位字写回内存）：

```asm
lw   x5, 0(x10)   # 从地址 x10 + 0 读出 x，放进寄存器 x5
addi x5, x5, 1    # 把 x5 里的数加 1，结果仍放回 x5
sw   x5, 4(x10)   # 把 x5 的新值写回地址 x10 + 4，即变量 z
```

盯着这短短三行代码，让我们沿着前面画出的六层阶梯，一层一层数清楚每一层究竟在干什么：

| 层次 | 面对 `z = x + 1` 时这一层的职责 |
| --- | --- |
| 高级语言 | 规定 `x` 与 `z` 的数据类型、加法语义以及数值超出表示范围时的行为 |
| 编译器 | 把高级语句拆成 `lw`、`addi`、`sw` 三条指令，并安排好 `x5`、`x10` 这些寄存器 |
| ISA | 规定三条指令各自的 32 位二进制编码、寄存器读写效果以及 PC 的更新规则 |
| 微体系结构 | 把每条指令送入取指、译码、地址计算、访问缓存、写回结果等硬件步骤 |
| 数字逻辑 | 用加法器、多路选择器、寄存器电路和状态机，把上述步骤变成实实在在的数据流 |
| 器件与工艺 | 在特定电压、时序和散热约束下，用晶体管开关忠实维持每一个 0 和 1 |

顺着这三条指令的因果关系看过去，你马上就会察觉到一个藏在字面之下的紧箍咒：第二条 `addi` 必须等第一条 `lw` 把 `x` 真正从内存搬进 `x5` 之后，才能动手加 1；第三条 `sw` 又必须等 `addi` 算出新值，才能把它写回 `z`。如果第一条 `lw` 运气不好，刚好撞上缓存未命中，得慢悠悠地去主内存跑一趟，那么后面两条指令就只能眼巴巴地干等。到了全书收官的[一条 load/add/store 如何贯穿机器](../chapter_08_case_study/load_add_store_walkthrough.md)，我们会把放大镜调到最高倍，按时钟节拍一拍一拍地看这三条指令如何唤醒整台机器。

读到这里，一个很自然的问题会浮上心头：前面说处理器内部为了提速可以「抢先执行」「乱序执行」，可如果它抢着算了一半，突然发现前面那条指令触发了异常或者走向了别的分支，那岂不是把寄存器和内存都弄脏了吗？

## 架构状态与瞬时状态：正式账本与草稿纸

芯片设计师化解这个难题的办法既巧妙又克制：在硬件内部严格区分「软件看得见的正式账本」和「硬件自己用的临时草稿纸」。

- **架构状态**（architectural state）就是那本正式账本——凡是 ISA 契约规定软件能够直接观察到的值，比如通用寄存器（`x5`、`x10` 等）里的内容、主存里变量 `z` 更新后的值，以及程序计数器 PC，统统属于架构状态。
- 而在处理器内部，为了加速执行而临时寄存的中间结果、流水线各阶段之间传递的暂存数据、猜出来的分支方向等等，全都属于软件看不见的**微体系结构状态**（也常称为瞬时状态）。

打个比方，这就像你在考场上做一道有条件的计算题：还没彻底确认走哪条分支之前，你先在草稿纸上把最可能走的那条路算出来。如果后来证实你猜对了，直接把草稿纸上的答案誊抄到答题卡上，省下大把时间；如果发现猜错了，二话不说把草稿纸撕掉重算，答题卡上依然干干净净，阅卷老师（也就是软件）根本看不出你曾经走过弯路。

在处理器里，把草稿纸上的临时结果正式「誊抄到答题卡」、确认为程序可见进展的这一步，叫做**提交**（commit）。只要处理器保证所有指令严格按程序原本的顺序依次提交，那么在提交之前无论内部怎样提前猜测、乱序计算，对外呈现的架构状态就永远一丝不苟。

不过，再好的类比也有边界。草稿纸并不是免费白写的——猜对的时候，提前算出的结果确实帮你赢回了宝贵的时钟周期；可一旦猜错，撕掉草稿纸、清空已经涌进流水线的错误指令，不仅白白消耗了电力，还会耽误好几个甚至十几个时钟节拍。这笔「猜对赚多少、猜错赔多少」的账，我们会在第 6 章的分支预测里仔细清算。

## 抽象为什么会泄漏？

既然分层把软硬件隔得如此严实，是不是意味着写程序的人只要守着高级语言这一层，就可以把底下的硬件抛到九霄云外了？

回想概述里提过的那个二维数组遍历实验。用 C 语言把一个 $4096 \times 4096$ 的二维数组所有元素相加，先按行遍历（`a[i][j]` 中内层循环改变 `j`），和先按列遍历（内层循环改变 `i`），两段代码在高级语言层面的功能语义完全等价——哪怕你拿着放大镜一行行核对结果，也找不出半点差别。

然而一跑起来，按行遍历往往比按列遍历快出几倍甚至一个数量级。原因在于，二维数组在内存中通常是按行连续排布的。当你读取 `a[i][0]` 时，硬件并不会小气地只搬这一个数进缓存，而是顺手把紧挨着它的 `a[i][1]`、`a[i][2]` 等一整块相邻数据一起装进缓存。这种「刚访问过一个地址，紧邻它的地址很快也会被用到」的规律，叫做**空间局部性**（spatial locality）。按行遍历恰好顺着硬件的脾气走，后面连续多次读取都能直接从缓存里秒取；按列遍历却每次大步跨过一整行，把刚辛苦搬进来的整块缓存白白浪费，步步都在触发缓存未命中。在第 7 章的[局部性、Cache 与主存](../chapter_06_memory/hierarchy_cache.md)中，我们会用具体地址算例逐次验算哪些读取能撞上同一块缓存。

这给了我们一条极其清醒的认知：**抽象建立的是「功能上可依赖的最低契约」，而不是把下层永远封印在黑盒里。** 在判断程序「算得对不对」时，你可以放心地相信抽象，假装下层不存在；可一旦追问程序「为什么跑得慢」，抽象就会发生泄漏——下层的缓存、流水线和内存带宽会透过性能曲线清清楚楚地显出原形。

## 这门课怎样串起整个计算机体系

站在这张分层地图上往四周看，你也会发现计算机专业的几门核心课其实都在同一张图纸上接力配合：

- **数据结构与算法**关注操作次数与内存访问模式，组成原理解释为什么同样是 $O(n)$ 的访问模式，连续数组往往把链表甩开几条街；
- **编译原理**负责把高级语言翻译成 ISA 指令，并结合微体系结构特征做寄存器分配和指令调度；
- **操作系统**负责管理进程、异常、虚拟内存和各类外设，但它离不开硬件提供的中断机制、地址翻译部件和特权级支持；
- **数字电路**教会你如何用逻辑门搭出加法器和触发器，组成原理则把这些孤立的部件装配成一台能自己取指、译码、执行的可编程机器。

现在我们已经看清了一台计算机在「空间」上是怎样层层切分的。但还有一个让人忍不住好奇的问题：今天的计算机为什么偏偏长成了「存储程序 + 缓存 + 流水线 + 多核 + GPU」这副模样？它是某个天才拍脑袋发明的，还是几十年来一步步被物理瓶颈逼出来的？下一节，我们把镜头切到时间维度，看看体系结构是怎样在一堵又一堵「墙」面前演进到今天的。

## 自测

1. `x86` 是一族广泛使用的指令集架构名称。仅凭「这是一颗 x86 处理器」这句话，你能不能断定它配备了多大的缓存，或者内部把指令拆成了多少步执行？为什么？
2. 现代处理器猜错分支方向后，通常只会让程序变慢一点，却不会让程序算错结果。硬件是靠什么机制守住正确性底线的？
3. 除了按行与按列遍历二维数组，你还能想到另一个「功能抽象没有泄漏，但性能抽象明显泄漏」的编程例子吗？
