# 体系结构的历史演进

## 两台主频相同的电脑，为什么速度能差出一倍？

挑电脑时，很多人习惯先盯参数表里的「主频」——比如 3.0 GHz。可如果你真拿一台十年前的 3.0 GHz 老机器，和一台今天的 3.0 GHz 新机器跑同一份程序，结果往往令人大跌眼镜：两台机器每秒钟跳动的节拍数完全一样，新机器却常常能快出一倍甚至更多。

这是怎么回事？要解开这个谜，得先看清处理器是怎样踩着节拍干活的。处理器内部有一个类似节拍器的电子时钟，用来协调各个电路部件整齐划一地同步动作。每秒钟敲响多少下节拍，就是**时钟频率**（clock frequency），比如 3.0 GHz 意味着每秒敲响 30 亿下；每两下节拍之间的时间间隔，就是**时钟周期**（clock period），3.0 GHz 对应的一个时钟周期只有短短 $0.33$ 纳秒。

但敲得快，不等于干完活就快。假设一段程序总共包含 10 亿条机器指令：老机器每完成一条指令平均要花 4 个时钟周期，新机器得益于更好的内部设计，每条指令平均只需要 2 个时钟周期。哪怕两者的时钟频率分毫不差，新机器用掉的总周期数也只有老机器的一半，最终运行时间自然减半！

所以，评估一台机器有多快，光盯着时钟频率远远不够，必须把三笔账放在一起算：**一共要执行多少条指令**、**每条指令平均耗费几个时钟周期**、以及**每个时钟周期有多长**。至于更精确的性能公式，我们会在第 6 章正式展开；此刻更值得追问的是——是什么驱动着硬件设计者一代又一代地压缩周期数、拉高频率，后来又为什么突然转头去堆多核和专用加速器？

??? question "如果新机器为了把每条指令做简单、让每条指令的平均周期减半，结果却让完成同一任务所需的指令总数翻了一倍，速度会变快吗？"

    不会，两者恰好相互抵消。假设时钟频率不变，指令数翻倍、每条指令平均周期减半，总时钟周期数和总耗时保持不变。这也是为什么比较不同架构的处理器时，绝不能只看单项指标，而必须用真实程序的端到端运行时间说话。

如果把计算机七十多年的发展史当成一串型号年表去背，既枯燥又毫无用处；但如果换个眼光，把它看成一部**「瓶颈如何不断迁移」**的工程实验记录，整段历史立刻就活了过来。每一代架构师都在拼尽全力拆掉眼前最昂贵的那堵墙，而每当一堵墙倒下，墙后立刻又会露出一堵更棘手的新墙。

## 第一道跃迁：从拔插电线到存储程序

在 20 世纪 40 年代最早的电子计算机（如 ENIAC）上，「换一个程序跑」绝不是双击鼠标那么轻松的事。那时候的计算逻辑直接硬连在机器的电路里，想把算弹道的机器改去算另一组方程，工程师得花上几天时间，在密密麻麻的插线板上拔插成百上千根电缆、拨动成排的开关。换句话说，早期「编程」本质上是在给硬件动外科手术。

真正把计算机从专用计算器解放成通用平台的，是**存储程序**（stored-program）思想。它的核心洞察简单得近乎惊人：**指令本身也是信息，完全可以像数字和文字一样编码成 0 和 1，和普通数据一起存进同一块内存里。** 处理器只需要按顺序从内存里取出一条指令、读懂它、执行它，再去取下一条。想换一个程序？不用再碰一根电线，只要往内存里装入另一串 0 和 1 就行了。从此，程序可以被保存、复制、传输，甚至可以由另一个程序（比如编译器）自动生成，现代软件世界的大门就此推开。

然而，这项把指令和数据统一放进内存的经典设计——也就是人们常说的**冯·诺依曼结构**（von Neumann architecture）——在解决灵活性的同时，也立刻埋下了计算机史上最长寿的一个麻烦：指令和数据要共用同一条通往内存的通道。

随着电子器件不断提速，处理器的运算速度突飞猛进，内存的读写速度却增长缓慢。通道每秒能运送的字节数有限，CPU 算得再快，也常常只能停下来苦等指令和数据从内存慢慢爬过来。这道卡住计算咽喉的窄门，后来被称为**冯·诺依曼瓶颈**（von Neumann bottleneck）。

为了绕开它，几代架构师想尽了办法：把最近刚用过的数据留在芯片身边的缓存里，避免反复去跑主内存；观察程序的访问规律，猜到稍后大概率要用的数据就悄悄提前搬过来——这叫**预取**（prefetch）；或者干脆加宽数据通道、把芯片内部的指令缓存和数据缓存分开。你会发现，这道瓶颈从未真正消失，只是被一层层巧妙的机制一再推远。这个「问题不会消失、只会转移」的规律，很快就会在历史的下几幕里反复重演。

## 黄金红利期：晶体管、集成电路与双定律

早期的电子计算机用玻璃真空管充当开关，不仅体积庞大得占满整间屋子，还动不动就发热烧毁。1947 年晶体管的发明改写了一切：它体积更小、开关更快、可靠性高出几个数量级。紧接着，**集成电路**（integrated circuit，简称 **IC**）技术把成千上万个晶体管和连线一起蚀刻在同一块指甲盖大小的硅片上；到了 20 世纪 70 年代，**微处理器**（microprocessor）更是把整颗 CPU 浓缩进了单颗芯片，彻底引爆了个人电脑和嵌入式设备的浪潮。

随后整整三十多年，计算机行业享受了一场史无前例的「物理红利期」，支撑这场盛宴的是两条著名的经验规律：

- **摩尔定律**（Moore's law）：芯片上可经济集成的晶体管数量大约每两年翻一番。每隔一代工艺，设计师手里可支配的晶体管预算就会暴增。
- **Dennard 缩放**（Dennard scaling）：当晶体管尺寸按比例缩小时，它的工作电压和电流也能同步降低，结果是**单位面积的功耗大致保持不变**。

这两条规律叠加在一起，产生了近乎魔幻的效果：芯片越做越小、晶体管越塞越多、时钟频率一路飙升，而整颗芯片却不会因此烧熔！在这个黄金时代里，架构师只需要把多出来的晶体管拿去加深流水线、增加更聪明的预测器、放进更复杂的执行单元，同时不断提高频率，单线程程序的性能就能每隔一年半自动翻倍。那时候软件工程师甚至流传着一句玩笑：「代码跑得慢？别急着优化，睡一觉等明年的新 CPU 出来就行了。」

可是，物理定律从来不会永远慷慨。如果有一天，这场免费的午餐突然结束了，该怎么办？

## 两条路线之争：RISC 与 CISC

就在晶体管预算还相当紧张的 20 世纪 70 到 80 年代，架构师们围绕「指令集该怎么设计」爆发了一场影响深远的路线之争。

在内存极其昂贵、编译器还很稚嫩的年代，工程师们很自然地想到：不如让硬件多扛一点活儿，设计出功能强大、一条指令就能干完一整串动作的指令集——比如一条指令既能从内存取数、又能顺便做算术、还能把结果写回内存。这样做出来的程序体积更小（省下宝贵的内存空间），写汇编的人也省心。这就是**复杂指令集计算机**（Complex Instruction Set Computer，简称 **CISC**）的出发点，x86 架构正是其中的代表。

但随着研究人员拿真实程序做统计，一个出人意料的事实浮出了水面：尽管 CISC 提供了成百上千条花哨的复杂指令，程序在 80% 以上的时间里真正高频执行的，却只是寥寥十几条最简单的读取、写入、加法和跳转指令！更糟糕的是，那些花哨复杂、长度参差不齐的指令，让硬件电路变得异常臃肿，严重阻碍了流水线的提速。

于是，另一派学者提出了针锋相对的主张：干脆给指令集做彻底的「瘦身」！所有指令采用规整统一的长度，算术运算只允许在寄存器之间进行，只有专门的 `load` 和 `store` 指令才能碰内存。硬件电路一下子变得简单规整、极易流水化，腾出来的芯片面积可以拿去做更多的寄存器和更大的缓存；至于把复杂操作拆解成简单指令序列的苦差事，就放心交给越来越聪明的编译器去办。这就是**精简指令集计算机**（Reduced Instruction Set Computer，简称 **RISC**），ARM 和我们全站采用的 RISC-V 都属于这一脉。

有意思的是，争论了几十年后，两条路线在今天竟悄然走向了融合。像 x86 这样的现代 CISC 处理器，对外依然严守古老复杂的接口契约，但在芯片内部却安排了专门的「翻译官」，在执行前把复杂指令实时拆解成一串规整简单的内部微操作，交给一颗骨子里很像 RISC 的高速核心去跑；反过来，像 RISC-V 这样的精简指令集，也会为最高频的常用操作补充压缩版短指令，以节省宝贵的指令缓存空间。到了第 4 章探讨[最小汇编程序与 RISC/CISC](../chapter_03_isa/assembly_risc_cisc.md)时，我们还会从真实指令序列的角度，仔细比较「编译器提前拆」和「硬件现场拆」各自付出的代价。

## 撞上功耗墙：从拼频率转向拼多核

时间来到 2005 年前后，享受了三十年的免费午餐戛然而止。

处理器的动态功耗——也就是晶体管在 0 和 1 之间高速翻转所消耗的电功率——大致服从下面这条物理关系：

$$
P_{\text{dynamic}} \approx \alpha C V^2 f.
$$

式子里的四个量各有直观含义：$\alpha$ 代表每个周期实际发生翻转的电路比例（活动因子），$C$ 是电路的等效电容，$V$ 是供电电压，$f$ 是时钟频率。

注意公式里那个触目惊心的平方项 $V^2$。以前靠 Dennard 缩放，晶体管缩小后可以顺手调低电压 $V$，正好把频率 $f$ 升高带来的功耗抵消掉。可当晶体管小到几十纳米级时，漏电流开始失控——电压再往下压，开关就关不严实了！电压降不下去，如果还硬着头皮把频率往上拉（甚至为了跑得更稳还得微微抬高一点电压），芯片功耗就会像脱缰野马一样暴涨，散热片根本压不住这团火炉。

这就是芯片发展史上著名的**功耗墙**（power wall）。你大概也注意到了：从 2000 年代中期到现在，主流 CPU 的基础主频长期徘徊在 3 到 5 GHz 左右，再也没能像九十年代那样一路狂飙到 20 GHz、50 GHz。

既然「把一颗核心拧得越来越快」的路撞上了散热极限，可摩尔定律在一段时间内依然在源源不断地送来更多晶体管，架构师们于是转向了另一条出路：与其冒着烧毁的风险拉高单核频率，不如在一块芯片上并排放进两颗、四颗、甚至上百颗工作在温和频率下的核心，同时把更多晶体管投向更大的缓存和向量运算单元。

这是一次深刻的历史转向，它直接改写了软件开发的规则。过去硬件免费替软件提速的好日子结束了——两颗核心并不会自动让一份单线程程序快上一倍。想要榨干多核芯片的算力，程序员必须亲自把任务切分成能并发执行的子任务，还要头疼数据怎么划分、核心之间怎么同步、共享缓存里的数据怎么保持一致。硬件把「并行」这副重担，正式递到了软件手里。

## 从通用到专用：GPU 与领域加速器的崛起

即便走上了多核之路，通用 CPU 依然背着沉重的包袱。为了让各种充满复杂分支、难以预测的普通程序都能跑得飞快，一颗现代 CPU 核心把大片珍贵的硅片面积花在了分支预测、乱序调度、庞大缓存等「管理与控制」电路上，真正用来做加减乘除的算术电路反而只占一小块角落。

现在换一个场景想想：如果你要给一张 4K 高清照片里的几百万个像素做完全相同的滤镜变换，或者要对深度学习模型里动辄几千维的矩阵做大规模乘加运算，所有数据走的都是整齐划一的同一套算术流程，几乎没有七拐八绕的条件分支——把这么规整的体力活交给昂贵、精密的通用 CPU 核心去干，岂不是杀鸡用牛刀？

正是沿着这条思路，硬件开始从「一专多能的通用计算」大步迈向「术业有专攻的领域专用架构」：

- **图形处理器**（GPU）削减了复杂的单线程控制逻辑，把海量晶体管直接铺成成千上万个相对简单的算术单元，天生擅长同时对大批数据施加相同的运算；
- **张量处理器**（Tensor Processing Unit，简称 **TPU**）则更进一步，干脆在硅片上直接焊出专门吞吐矩阵乘加的专用阵列；手机芯片里的视频编解码模块、图像信号处理器也无一不是如此。

不过，专用加速器同样不是包治百病的银弹。它成立的前提非常苛刻：工作负载必须足够稳定、并行结构高度规整，而且数据能及时喂到算术单元嘴边。如果面对的是业务逻辑瞬息万变、指针跳来跳去、条件分支密密麻麻的任务，专用芯片就会瞬间英雄无用武之地，高昂的研发成本和惨淡的硬件利用率反而会把它拖垮。因此，今天的现代计算机并不是「GPU 取代 CPU」，而是「CPU 掌管复杂控制与调度 + 各类加速器专攻密集计算」的协同体。

## 贯穿七十年的底层规律

回望这一整条演进曲线，你会发现一条比任何具体型号都更有生命力的底层规律：**体系结构的每一次重大进步，从来都不是凭空消灭成本，而是在移动成本。**

- 存储程序解放了编程灵活性，却带来了冯·诺依曼瓶颈；
- 流水线成倍提升了指令吞吐率，却引入了指令相互牵绊的冒险问题；
- 缓存藏住了主存的漫长延迟，却带来了多核一致性与访问时间不可预测的麻烦；
- 多核绕开了单核功耗墙，却把并行拆分、通信与同步的复杂度推给了软件；
- 领域专用加速器换来了惊人的能效比，却牺牲了面对未知任务的通用性。

记住这条规律，今后无论看到多炫酷的新硬件发布，你都能保持冷静，顺手追问一句：「它确实解决了一个旧瓶颈，那它把新代价挪到哪儿去了？」

至此，我们已经从「空间分层」和「时间演进」两个维度，看清了整台机器的骨架。可落到最底层的硬件世界里，一个最朴素的问题还没解开：芯片里的电路只认得高电压和低电压——也就是 1 和 0。那我们在程序里习以为常的负数、小数、甚至汉字，究竟是怎样被塞进一串干巴巴的 0 和 1 里的？翻开第 2 章，我们立刻去一探究竟。
