# 最小汇编程序与 RISC/CISC

## 从三行汇编里，怎样一眼看出「谁必须等谁」？

看下面这短短三行代码——假设 `x10` 存着一个整数数组的起始地址：

```asm
lw  x5, 0(x10)
lw  x6, 4(x10)
add x7, x5, x6
```

初学者盯着满屏 `x5`、`x6`、`x10`，常常觉得像在看天书。其实读汇编有一个立竿见影的窍门：**先拿笔圈出哪些寄存器里装的是「地址」，哪些装的是「数据」，再把每一条指令的「写出口」连到后面指令的「读入口」。**

在这个小片段里，`x10` 是地址；第 1 条从数组首地址读出第 0 项放进 `x5`，第 2 条往后挪 4 字节读出第 1 项放进 `x6`，第 3 条再把 `x5` 和 `x6` 相加写进 `x7`。一眼就能看出：前两条 `lw` 彼此井水不犯河水，谁先读、谁后读（甚至一起读）都无所谓；可第 3 条 `add` 却死死攥着前两条的命脉——必须等 `x5` 和 `x6` 都就位后才能动工。这种「后一条指令必须消费前一条指令产出的结果」的先后约束，叫做**数据相关**（data dependence）。别小看这个简单概念，到了第 6 章的流水线里，它正是把硬件设计师逼出满头大汗的核心矛盾之一。

??? question "如果把第二条指令的偏移从 `4` 改成 `8`（即 `lw x6, 8(x10)`），它会读出数组的第几项？"

    因为每个 32 位整数占 4 个字节，偏移 0 对应下标 0（第一项），偏移 4 对应下标 1（第二项），所以偏移 8 对应下标 2（第三项）。硬件只管按 `x10 + 8` 去内存取数，绝不会帮你检查数组有没有越界——保证下标合法是软件自己的责任。

顺便理清一个名词层次：处理器真正在硅片上吞吐的是由 0 和 1 构成的机器码，人眼根本没法直接写。为了让人类也能驾驭机器指令，人们为每种操作起了容易记的英文缩写——比如 `lw`（load word）、`add`——称为**助记符**（mnemonic）；给跳转目的地起上 `loop`、`done` 这样有意义的名字，称为**标签**（label）。用助记符和标签写出来的可读文本就是**汇编语言**（assembly language），再由专门的翻译工具——**汇编器**（assembler）——把助记符编成二进制操作码、把标签换算成精确的跳转偏移量，最终产出机器码。

## 最小完整程序：手工走查 `c = a + b`

现在回到贯穿全站的那个老朋友：`c = a + b`。假设三个 32 位整数变量 `a`、`b`、`c` 在内存里紧挨着排成一排，每个占 4 字节，寄存器 `x10` 保存着 `a` 的首地址。下面四条指令就构成了一段完整的计算程序：

```asm
lw  x5, 0(x10)    # x5 <- Mem[x10 + 0]（变量 a）
lw  x6, 4(x10)    # x6 <- Mem[x10 + 4]（变量 b）
add x7, x5, x6    # x7 <- x5 + x6
sw  x7, 8(x10)    # Mem[x10 + 8]（变量 c）<- x7
```

不妨扮演一回「人肉 CPU」，给定初始状态：

```text
x10 = 0x1000
Mem[0x1000] = 20
Mem[0x1004] = 22
```

逐条跟踪架构可见状态的变化：

| 执行节点 | `x5` | `x6` | `x7` | `Mem[0x1008]` |
| --- | ---: | ---: | ---: | ---: |
| 初始状态 | 未指定 | 未指定 | 未指定 | 未指定 |
| 执行第 1 条 `lw` 后 | `20` | 未指定 | 未指定 | 未指定 |
| 执行第 2 条 `lw` 后 | `20` | `22` | 未指定 | 未指定 |
| 执行第 3 条 `add` 后 | `20` | `22` | `42` | 未指定 |
| 执行第 4 条 `sw` 后 | `20` | `22` | `42` | `42` |

这张表格所描绘的，就是 ISA 对外承诺的**架构语义**：四条指令、四次清晰可追踪的状态跃迁。真实的现代 CPU 在幕后可以大显神通——比如把前两条 `lw` 同时发出去，甚至提前把后面的指令取进来译码——但它必须死守两条底线：绝不能让 `add` 误用了尚未更新的旧 `x5` 或旧 `x6`，也绝不能在某条指令意外触发异常时留下半拉子写坏的架构状态。

直线往下走的代码已经难不倒我们了，但真实程序里到处都是判断与循环——如果没有 `for` 和 `while` 关键字，光靠几条干巴巴的汇编指令，机器怎么才能反复绕圈？

## 把循环写进汇编：数组求和完整剖析

设想一个最经典的循环任务：内存里放着一个 32 位整数数组，寄存器 `x10` 指向首元素，寄存器 `x11` 装着数组的元素个数 `n`，我们要把所有元素加总到寄存器 `x5` 里。

在 RISC-V 里，整段循环只需下面这八行汇编就能漂亮收工（其中 `beq rs1, rs2, label` 表示当两个寄存器相等时跳往 `label`，`jal x0, loop` 则丢弃返回地址、直接无条件跳回 `loop`）：

```asm
    addi x5, x0, 0      # sum = 0（利用恒零寄存器 x0 清零）
loop:
    beq  x11, x0, done  # 如果剩余元素个数 n == 0，跳出循环去往 done
    lw   x6, 0(x10)     # 读出当前元素 *p 到 x6
    add  x5, x5, x6     # sum += *p
    addi x10, x10, 4    # 指针 p 向后移动 4 字节，指向下一个 32 位整数
    addi x11, x11, -1   # 剩余元素计数 n -= 1
    jal  x0, loop       # 无条件跳回 loop，开始下一轮迭代
done:
```

这短短八行代码堪称「麻雀虽小、五脏俱全」，里面埋着四处极其值得品味的硬件细节：

1. **硬连线零寄存器 `x0`**：RISC-V 特意把 0 号寄存器做成永远读出 `0`、写入直接丢弃的常数源。于是清零 `x5` 不需要专门的清零指令，判断 `x11 == 0` 也不用先花一条指令把 `0` 装进某个寄存器，一举简化了大量常见操作。
2. **指针步长是 `4` 而不是 `1`**：在 C 语言里写 `p++`，编译器会自动帮你按元素大小挪动地址；落到汇编层，内存是按字节编址的，一个 32 位整数占 4 字节，所以每次挪向下一个元素必须老老实实 `addi x10, x10, 4`。
3. **紧贴的 `load-use` 数据相关**：盯住循环体里的第 2 行 `lw x6, 0(x10)` 和第 3 行 `add x5, x5, x6`——加法指令紧挨在读内存指令之后，立刻要消费刚刚取出来的 `x6`！这种「刚读完就马上要用」的紧密依赖叫做**读取后立即使用**（load-use）。顺便留个思考：既然 `addi x10, x10, 4` 和 `x6` 毫无关系，如果编译器把它插到 `lw` 和 `add` 中间，会不会帮流水线省下一次干等？第 6 章会给出响亮的答案！
4. **条件分支与控制流**：`beq x11, x0, done` 属于**条件分支**（conditional branch）——它决定了下一拍究竟是顺着进循环体，还是直接跳到 `done` 结束。在真正把 `x11` 和 `0` 比出结果之前，后面的指令到底该不该提前取进来执行，形成了所谓的控制相关。

顺序、访存、算术、判断、循环——撑起几乎所有通用计算的基石，竟然全被浓缩在了这短短八行里。也正是在如何让这类日常代码跑得最快、芯片做得最省的权衡中，体系结构历史上爆发了著名的 RISC 与 CISC 之争。

## RISC 的设计哲学：把简单做到极致

回看上面那段数组求和，你会发现每条 RISC-V 指令干的活都非常克制：`lw` 只管搬数据，`add` 只管做寄存器加法，`addi` 只管给指针或计数器加常数。这就是**精简指令集**（RISC）一以贯之的设计哲学：

- **指令格式高度规整、定长对齐**，译码电路小巧快速；
- **坚持 `load/store` 架构**，只有读写指令能碰内存，所有算术和逻辑运算一律在寄存器之间完成；
- **只保留少量清晰的寻址方式**，绝不为冷门场景堆砌复杂地址计算电路；
- **让 80% 最高频的简单操作走最快的硬件通道**，把复杂功能交给编译器用简单指令拼接组合。

这条路线的红利非常可观：硬件数据通路干净利落，极易切分成高主频的深流水线，电路验证成本和译码能耗都显著降低。它付出的代价则是：完成同一个高层语义有时需要写出更多条指令（例如把内存里的数加 1 必须拆成 `lw`、`addi`、`sw` 三条），程序二进制体积可能偏大，从而给指令缓存与取指带宽带来额外压力。

## CISC 的设计哲学：单条指令一步到位

把时钟拨回 20 世纪 70 年代，内存贵如黄金，编译器还远谈不上智能，许多核心软件甚至是程序员手写汇编拼出来的。站在当时的约束下，**复杂指令集**（CISC）的选择再合情合理不过：干脆让一条机器指令干完一整串活儿——比如一条指令既能直接从内存取数、加上一个常数、再写回内存，甚至直接内建字符串拷贝或循环递减跳转指令！

这样做的好处立竿见影：程序占用的字节数大大缩小（代码密度极高），手写汇编也舒心不少。但硬币的另一面是硬件复杂度急剧膨胀：指令长度从 1 字节到十几字节参差不齐，寻址模式眼花缭乱，一条指令中途出了内存页错误时，如何把已经修改了一半的状态干干净净地回滚，成了极其棘手的异常边界难题。

不过，千万别陷入「凡是复杂指令就一定很慢」的刻板印象。在真实的 CISC 芯片设计中，工程师同样会区分冷热：把最高频的复杂指令做成高速硬连线通路，而把那些百年难得一遇的冷门复杂指令交给芯片内部一小段专用程序来一步步解释执行——这种藏在处理器内部、用微小控制步骤实现复杂指令的技术，叫做**微码**（microcode）。

## 为什么今天再谈「RISC vs CISC」不能简单二选一？

几十年风风雨雨走下来，两大阵营并没有谁消灭谁，反而在工程现实的倒逼下悄悄互相抄起了作业，走出了一条「外貌各异、内里趋同」的融合之路。

一方面，现代高性能 x86（CISC）处理器在前端安排了极其强大的译码器，会在执行之前把外部变长、复杂的 x86 指令，动态拆解成一条条长度规整、只面向内部寄存器的细粒度小动作，叫做**微操作**（micro-operation，简称 **$\mu\text{op}$**），随后交给一个骨子里彻底像 RISC 一样干净高效的乱序流水线后端去狂奔！外表是兼容四十年的 CISC 契约，内脏却是彻头彻尾的 RISC 引擎。

另一方面，以 RISC-V 和 ARM 为代表的现代 RISC 阵营，也早就不止「精简」那么简单：为了弥补代码密度短板，它们引入了 16 位压缩短指令；为了加速多媒体和 AI，它们加入了庞大的向量扩展、密码学加速和矩阵指令——指令总数同样洋洋洒洒达数百条之多。

因此，今天再评判一套指令集，绝不能偷懒贴个「指令多就慢、指令少就快」的标签，而要分别盯住两个维度：**软件层生成的机器码占了多少字节**，以及**硬件层译码执行时要花多少能耗与微操作**。

| 权衡维度 | 偏向规则指令（RISC 倾向） | 偏向复杂指令（CISC 倾向） |
| --- | --- | --- |
| 取指与译码能耗 | 边界规整，并行译码开销与能耗较低 | 变长边界探测复杂，常需额外配备译码后缓存（$\mu\text{op}$ cache） |
| 代码密度 | 基础定长版本偏低，常借压缩扩展补齐 | 往往较高，节省指令缓存与内存带宽 |
| 软硬件分工 | 更多优化与指令排布责任落在编译器肩上 | 部分常见复合操作下沉到硬件译码或微码 |
| 历史兼容负担 | 新兴 ISA（如 RISC-V）模块化设计，包袱较轻 | 成熟老牌生态（如 x86）必须长期背负历史指令兼容 |

顺带一提，一条高级语言语句和机器指令之间，从来不是死板的一一对应关系。同一个 C 语言循环，开 `-O0` 和开 `-O3` 编译优化、换一种结构体对齐布局、或者开启向量指令扩展，编译器产出的汇编可能判若两人；反过来，ISA 里有没有顺手的原子操作或条件传送指令，也直接决定了编译器能施展多少优化魔法。软硬件接口不是一堵死墙，而是编译器与芯片架构师双向奔赴的协同设计点。

现在，我们的最小汇编程序已经会算术、会访存、会判断、也会循环了。但还缺一样让现代大型软件得以模块化搭建的关键结构——**函数**。用一条跳转指令从 `main` 跳进 `foo` 很容易，可 `foo` 算完怎么精准跳回 `main`？要是 `foo` 里面又嵌套调用了 `bar`，返回地址会不会被冲掉？`bar` 用了寄存器之后，`foo` 原本存在里面的局部变量还算不算数？下一节，我们马上揭开[从汇编跳转到函数调用](calling_convention.md)的秘密。
