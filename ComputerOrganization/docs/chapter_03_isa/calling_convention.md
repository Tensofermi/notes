# 从汇编跳转到函数调用

## 函数 `f()` 自己又调用了 `g()`，原来的「回家路线」去哪儿了？

写高级语言时，我们随手就能让 `main()` 调用 `f()`，`f()` 再调用 `g()`，甚至让一个递归函数自己一层层调用自己几十遍。等最里层算完，程序总能像系着一根看不见的线一样，原路精准退回外层继续往下走。

可落到硬件层面，处理器并没有什么天生自带的「函数概念」，它手里只有跳转指令和几十个通用寄存器。在 RISC-V 里，发起函数调用时，硬件会把「调用指令紧挨着的下一条指令地址」顺手存进一个专门的寄存器——**返回地址**（return address）寄存器 `ra`，然后把 PC 改写成被调函数的入口地址。

现在，麻烦来了：

1. `main()` 调用 `f()`，硬件把「回到 `main` 的门牌号」写进 `ra`；
2. 还没等 `f()` 干完活，`f()` 内部又发起了一次调用去执行 `g()`——硬件照章办事，立刻把「回到 `f` 的门牌号」也写进了同一个寄存器 `ra`！

惨案就在这一瞬间发生了：`main` 的回家路线被硬生生覆盖抹掉了！哪怕 `g()` 顺顺利利回到了 `f()`，等 `f()` 自己执行返回指令跳往 `ra` 时，它跳到的根本不是 `main()`，而是 `f()` 自己刚才的下一行——程序瞬间陷入死循环或彻底跑飞！

怎么化解这个僵局？既然只有一个 `ra` 寄存器，而函数调用又天然呈现出「最后被调用的函数最先返回」（后进先出）的整齐规律，那最稳妥的办法就是在内存里划出一块按后进先出规律伸缩的专用区域——**调用栈**（call stack），用一个专门的**栈指针**（stack pointer，简称 `sp`）寄存器始终指向栈顶。每当一个函数（比如 `f()`）准备再调用别的函数之前，先从栈顶划出一小块属于自己的临时储物柜——称为**栈帧**（stack frame）——把旧的 `ra` 妥帖存进去；等 `g()` 凯旋归来，`f()` 再从储物柜里把旧 `ra` 原封不动取回来，释放栈帧，就能稳稳回到 `main()`！

??? question "如果一个短小的函数从头到尾都不会再调用任何其他函数，它一定还要费劲在内存里建栈帧吗？"

    不一定。这种不调用其他函数的「叶子函数」不会触发下一次对 `ra` 的覆盖；如果它只动用调用约定允许随意修改的临时寄存器、又没有需要溢到内存里的局部变量，就完全可以零内存读写、零栈帧地极速跑完并返回。具体是否建栈帧取决于函数体内容与编译器优化。

## 光有硬件跳转远远不够：ABI 调用约定的诞生

设想调用方想计算 `y = inc(41)`，算完后拿结果继续往下跑。仔细想想，硬件的跳转指令（例如 `jal`）本身非常「单纯」：它只负责记下返回点并改写 PC，压根不管参数 `41` 该塞在哪儿、结果 `42` 该放回哪儿、被调函数干活时能不能随便改写 `x5` 或 `x18`。

更现实的问题是：你写的 `main.c` 可能是用 GCC 编译的，而它调用的数学库可能是另一家公司几年前用 Clang 编译好的二进制文件。两段素未谋面的机器码之所以能在同一颗 CPU 上默契配合、无缝衔接，全靠双方共同遵守了一份高于 ISA、面向已编译二进制代码的「江湖规矩」——**应用二进制接口**（Application Binary Interface，简称 **ABI**）。

函数调用约定正是 ABI 里最核心的一章，它白纸黑字地敲定了四件大事：

1. **参数怎么传**：在 RISC-V 标准整数调用约定中，前 8 个整数参数依次装在寄存器 `a0`–`a7` 里传递（如果参数多于 8 个，多出来的部分才放到栈上）；
2. **结果放哪儿**：返回值放回 `a0`（双字结果可用 `a0`–`a1`）；
3. **怎么回家**：返回地址放进 `ra`；
4. **剩下的寄存器谁来保护？** 这是最容易踩坑、也最见工程智慧的一条规矩。32 个寄存器总共就这么多，总不能每次调个小函数就把全部 32 个寄存器统统存进内存吧？于是 ABI 把剩余通用寄存器干脆一分为二：
   - **调用者保存寄存器**（caller-saved，如临时寄存器 `t0`–`t6` 和参数寄存器 `a0`–`a7`）：被调用函数可以放开手脚随便改写，不必替外头操心；如果调用方自己在函数返回后还指望用到它们原来的值，就必须在发起调用**之前**自己把它们存进栈帧。
   - **被调用者保存寄存器**（callee-saved，如保存寄存器 `s0`–`s11` 以及栈指针 `sp`）：调用方可以放心把跨调用存活的重要变量放在这里；被调用函数如果压根不用它们，就零成本省事；一旦想借用某个 `s` 寄存器，就必须「有借有还」——进门先把原值存进自己的栈帧，出门返回前原样恢复！

这套分工妙在哪儿？叶子函数优先挑 `t` 寄存器用，压根不用碰内存；而大函数里需要跨越多次子调用存活的循环变量，放进 `s` 寄存器就能省掉来回保存恢复的折腾。

### 看两个真刀真枪的 RISC-V 汇编例子

先看最轻巧的叶子函数 `inc(41)`：

```asm
    li   a0, 41        # 把参数 41 装进约定好的参数寄存器 a0
    call inc           # 保存下一条指令地址到 ra，并跳转到 inc
    # 函数返回后，a0 里稳稳装着 42

inc:
    addi a0, a0, 1     # 直接把 a0 加 1（结果恰好也在返回值寄存器 a0 里）
    ret                # 跳回 ra 指向的返回地址
```

代码里的 `li`、`call`、`ret` 并不是独立的底层硬件指令，而是汇编器贴心提供的**伪指令**（pseudo-instruction）——写起来清爽直白，汇编器会自动把它们展开成底层的真实指令序列（例如 `ret` 展开为 `jalr x0, 0(ra)`）。因为 `inc` 没有再调用任何函数、也没碰任何 `s` 寄存器，它连栈帧都没建，三条指令干脆利落收工。

现在换成一个会嵌套调用的函数 `add_two(x)`，它内部要调用 `inc(x)` 再把结果加 1。这时 `add_two` 必须保护自己的 `ra`，于是栈帧登场了（栈通常从高地址向低地址生长，因此申请 16 字节空间是把 `sp` 减 16）：

```asm
add_two:
    addi sp, sp, -16   # 在调用栈顶开辟 16 字节栈帧
    sw   ra, 12(sp)    # 把「回到外层调用方」的旧 ra 存入栈帧（32 位环境）
    call inc           # 调用 inc(a0)；这一步会覆盖 ra，但旧值已安全躺进栈里
    addi a0, a0, 1     # 对 inc 的返回值再加 1
    lw   ra, 12(sp)    # 从栈帧里把旧 ra 原封不动取回来
    addi sp, sp, 16    # 归还 16 字节栈帧，sp 恢复原位
    ret                # 稳稳跳回外层调用方
```

看着这七行代码，嵌套调用的迷雾一扫而空：`ra` 负责承载最近一层的极速返回，而随着调用层数加深，每一层未结束的函数都在调用栈上按顺序压入自己的栈帧，把旧 `ra`、被借用的 `s` 寄存器和放不进寄存器的局部变量统统妥善封存，待返回时逆序逐层弹回——无论函数嵌套十层还是递归一千层，都能有去有回、分毫不乱。

## 从普通函数调用到系统调用：三层契约全景

把视线再拉高一点，你会发现「用寄存器传参、靠约定交接控制权」这套设计思想，不仅统治了用户态里的函数调用，还一路延伸到了应用程序与操作系统之间：

| 契约层次 | 典型例子 | 这份契约究竟规定了什么 |
| --- | --- | --- |
| **ISA（指令集架构）** | `addi`、`jalr`、`ecall` | 每条机器指令的二进制编码，以及执行后如何改变寄存器、PC 与内存状态 |
| **ABI（应用二进制接口）** | 用 `a0` 传第一个整数参数、用 `ra` 存返回地址、`s0`–`s11` 由被调者保存 | 编译后的函数之间如何交换参数、返回值并划分寄存器保护与栈帧对齐规则 |
| **操作系统系统调用接口** | 把系统调用号放进 `a7`、参数放进 `a0`–`a5`，再执行 `ecall` | 用户程序如何请求内核代为执行文件读写、进程创建等特权服务，以及如何取回错误码 |

普通函数调用是在同一权限级别下，直接从程序里的一段代码跳去另一段代码；可当你的程序想打开硬盘上的文件、向网卡发一个数据包，或者向系统申请一块新内存时，处于低权限的用户代码绝不能直接去拨弄硬件寄存器。这时，程序必须按约定把「想办什么事的编号」和参数装进指定寄存器，然后执行一条特殊的陷入指令（如 RISC-V 的 `ecall`），发起一次**系统调用**（system call）。

硬件接到 `ecall` 后，立刻提升处理器特权级，沿着预先设好的安全入口把控制权移交给操作系统的核心——**内核**（kernel）。内核先核查参数是否合法、当前进程有没有权限，替用户把事办妥后，再把结果放回约定寄存器、降回低权限并返回用户程序继续执行。如果好奇硬件与操作系统在跨越这道特权边界时还发生了哪些惊心动魄的状态保存与切换，强烈建议搭配阅读<a href="../../OperatingSystems/chapter_01_foundations/02_kernel_user_syscalls_interrupts.html">内核态、系统调用、中断与异常</a>。

至此，第 4 章画上了圆满的句号——站在软件视角仰望指令集，从单条指令的位段排布、数组循环的汇编流转，到支撑起庞大软件大厦的函数栈帧与系统调用，整张蓝图已经严丝合缝。

## 自测

假设函数 `A` 调用了函数 `B`，而 `B` 在执行途中又调用了函数 `C`：
1. `B` 要采取什么措施，才不至于在 `C` 返回之后忘了怎么回到 `A`？
2. 如果 `B` 在干活期间修改了临时寄存器 `t0` 和保存寄存器 `s0`，那么 `A` 在 `B` 返回后想继续信任自己先前存的值，分别应该依赖谁的保障？

??? note "参考思路"
    1. `B` 在调用 `C` 之前，必须在自己的栈帧中把原先保存在 `ra` 里（指向 `A`）的返回地址写入内存备份；等 `C` 返回后、自己执行 `ret` 之前，再从栈帧把旧 `ra` 读回寄存器并恢复 `sp`。
    2. 依据 ABI 寄存器分工：`t0` 属于调用者保存寄存器，`B` 可以随意改写它，因此如果 `A` 在调用 `B` 之后还要用到 `t0` 的旧值，必须由 **`A` 自己在调用前保存、返回后恢复**；而 `s0` 属于被调用者保存寄存器，因此 `A` 可以放心期待它在调用前后保持不变，保护与恢复原值的责任落在 **`B` 自己**（`B` 使用 `s0` 前先压栈，返回前弹栈复原）。

若想查阅 RISC-V 全部寄存器的 ABI 别名、浮点调用规则与栈对齐细节，可参阅官方规范 [RISC-V psABI](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/)。
