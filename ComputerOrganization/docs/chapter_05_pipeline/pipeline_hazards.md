# 流水线、冒险、转发与停顿

## 后一句紧接着要用前一句的结果，来得及吗？

把目光落到下面两段看起来几乎一模一样的两行 RISC-V 汇编上——它们都是「第一条指令写寄存器 `x5`，紧跟着的第二条指令立刻读 `x5`」：

```asm
# 片段 A                          # 片段 B
add x5, x1, x2                    lw  x5, 0(x10)
sub x6, x5, x3                    add x6, x5, x7
```

回忆[第 5 章指令执行的五个阶段](../chapter_04_cpu/datapath_instruction_cycle.md)，一件棘手的事立刻浮现：不管是片段 A 还是片段 B，第一条指令都要等到**第 5 拍（WB）**才把新值正式写回寄存器堆，而第二条指令在**第 2 拍（ID）**就已经去读寄存器堆了——按照朴素的读写流程，第二条指令一定会读到过时的旧 `x5`！

但有意思的是，在经典的五级流水线处理器上，这两段代码的命运却截然不同：

- 片段 A 里，`add` 在**第 3 拍（EX）**结束时其实已经把和值算出来了，而 `sub` 要到**第 4 拍（EX）**开头才真正需要这个数进 ALU！硬件只需拉一根抄近路的导线，直接把第 3 拍算好的新鲜结果递到第 4 拍 `sub` 的 ALU 入口，根本不必苦等写回寄存器堆——这项绕过寄存器堆、直接把半成品送到下游的技术叫做**转发**（forwarding，又称旁路），片段 A 于是**零停顿**全速过关！
- 可换成片段 B 就不灵了：`lw` 在第 3 拍算出来的只是内存地址，真正的数据要等到**第 4 拍（MEM）末尾**才能从内存返回；而 `add` 在**第 4 拍（EX）开头**就已经伸手要数了！导线跑得再快，也无法逆转时间去拿一个还没从内存里取出来的数！经典流水线别无他法，只能让 `add` 原地多等一拍——这种主动按住下游等待一拍的做法叫做**停顿**（stall）。

同样是「后一句立刻用前一句的结果」，为什么一个畅通无阻、一个被迫刹车？把五级流水线按拍画进时空表，所有因果都会瞬间水落石出。

??? question "既然加了转发线路，为什么还是无法彻底消灭所有数据等待引起的停顿？"

    转发只是一条空间上的「抄近路」——它只能把**此刻已经产生出来**的值第一时间送往需要它的工位，却变不出尚未诞生的值。只要消费者需要数据的时刻早于生产者算出数据的时刻（典型如 `lw` 紧跟 `add`），单靠硬件转发就回天乏术，只能插入停顿或由编译器重新排布指令顺序。

## 五级流水线：让五条指令并肩同行

把单周期数据通路沿着 IF（取指）、ID（译码）、EX（执行）、MEM（访存）、WB（写回）五个逻辑边界切开，在相邻阶段之间各安放一排**流水寄存器**（依次命名为 `IF/ID`、`ID/EX`、`EX/MEM`、`MEM/WB`）。它们好比流水线工位之间的「传送托盘」：每个时钟上升沿一响，上一个工位刚加工好的数据和伴随它的控制信号就被锁存进托盘，下一拍稳稳交到下一个工位手里。

这么一来，每个阶段只需专注伺候自己手头那一条指令，五条指令便可以在同一拍里各司其职、齐头并进：

```text
时钟拍:  1    2    3    4    5    6    7
I1:     IF   ID   EX   MEM  WB
I2:          IF   ID   EX   MEM  WB
I3:               IF   ID   EX   MEM  WB
```

仔细看第 3 拍：此刻 `I1` 正占着 ALU 做计算，`I2` 正占着寄存器堆译码取数，`I3` 正占着指令存储器取新指令——三座工位火力全开，互不干扰！等到第 5 拍填满整条流水线后，理想情况下每一拍都能有一条指令走出 WB 完工。

当然，天下没有免费的流水线：那四排宽度动辄上百比特的流水寄存器不仅占据额外的芯片面积、消耗可观的时钟翻转功耗，还会给每一拍增加触发器的建立与输出延迟。更麻烦的是，一旦指令之间发生资源争抢或先后依赖，三大**冒险**（hazard）便接踵而至。

## 第一关：结构冒险（抢同一件工具）

当处于不同阶段的两条指令，在**同一个时钟周期**里伸手去抢同一个物理硬件部件时，就爆发了**结构冒险**（structural hazard）。

设想一台朴素的冯·诺依曼机器，指令和数据共用同一块只有一个读写端口的存储器。看看五级流水线的第 4 拍会发生什么惨剧：第 1 条 `lw` 指令刚好走到 **MEM** 阶段，要进存储器读数据；偏偏同一拍里，第 4 条指令刚好走到 **IF** 阶段，也要进同一块存储器取指令！一扇门挤不进两个人，撞车在所难免。

面对结构冒险，工程师手里有三张牌：

- **复制硬件资源**：干脆把指令通路和数据通路拆开，配备独立的指令缓存（I-Cache）和数据缓存（D-Cache）——这正是现代 CPU 芯片内部普遍采用「哈佛式分离一级缓存」的根本原因；
- **增加访问端口**：例如寄存器堆天然配备 2 个读端口和 1 个写端口，甚至允许同一拍前半拍写、后半拍读，让第 1 条指令的 WB 和第 4 条指令的 ID 和平共处；
- **实在抢不过就停顿一方**：如果某部件极其昂贵（如巨型浮点除法器），复制多份太费面积，就干脆让后来的指令排队等待。

复制资源换来高吞吐，代价是面积与功耗；停顿最省钱，代价是丢性能。好在 RISC 指令集非常规整，只要分开了指令和数据缓存、配齐了读写端口，基础五级流水线几乎可以彻底消除结构冒险。真正棘手的是第二关——指令之间剪不断理还乱的数据依赖。

## 第二关：数据冒险（结果还没到手）

当一条指令需要用到前面某条尚未走完流水线的指令的结果时，就触发了**数据冒险**（data hazard）。最核心、最不可回避的一类叫做**写后读**（Read After Write，简称 **RAW**）——后一条指令真的要消费前一条指令算出的值：

```asm
add x5, x1, x2   # 写 x5
sub x6, x5, x3   # 紧接着读 x5（RAW 真依赖）
```

在顺序推进的简单五级流水线里，所有指令一律在 ID 读寄存器、一律在 WB 写寄存器，因此只会撞上 RAW 这一种数据冒险。

不过，如果把视野放宽到后文会遇到的现代**乱序执行**或**多发射**处理器（允许后面的指令超车先算完），还会冒出另外两种看似奇怪的冲突：

- **写后写**（Write After Write，**WAW**）：两条指令先后都要写同一个寄存器 `x5`。如果后一条算得快、抢先写完，随后前一条慢吞吞地把旧结果盖上去，`x5` 最终留下的反而是过期旧值！
- **读后写**（Write After Read，**WAR**）：前一条指令还没来得及读走 `x5` 的旧值，后一条指令就抢先跑去把新值写进了 `x5`，导致前一条指令误读了「来自未来」的新值！

仔细琢磨一下你会发现：WAW 和 WAR 根本不是真正的数据传递，而是两条毫无瓜葛的指令**凑巧复用了同一个架构寄存器名字 `x5`** 惹的祸（因此称为「假依赖」或「名依赖」）。就像两位厨师其实在做两道毫无关系的菜，只因为菜谱上都写着「用 1 号锅」而大打出手。现代乱序处理器破解它们的绝招极其优雅——在芯片内部准备比 32 个架构寄存器多得多的物理寄存器，译码时悄悄把每次新写入的 `x5` 映射到一只全新的空物理锅里，并记好映射台账，这就是**寄存器重命名**（register renaming）！假依赖瞬间烟消云散。

至于躲不掉的真依赖 RAW，在经典五级流水线里则要靠「转发」和「停顿」这对搭档来化解。

### 化解之道一：转发（抄近路救急）

回到片段 A，把时间轴仔细对齐看看：

- 第 3 拍末尾：`add` 在 EX 阶段已经算出新 `x5`，顺着时钟沿落进了 `EX/MEM` 流水寄存器；
- 第 4 拍开头：`sub` 恰好踏进 EX 阶段，准备把 `x5` 送进 ALU！

虽然寄存器堆里的 `x5` 要等到第 5 拍 WB 才会更新，但新值明明已经热气腾腾地躺在 `EX/MEM` 托盘里了！于是硬件设计者在 ALU 的两个输入口前各加了一枚多路选择器，并从 `EX/MEM` 和 `MEM/WB` 两个托盘拉出两条回头导线直接连回 ALU 入口：

```text
add 的 EX 产出（存于 EX/MEM 托盘） ─────────> 直接送入 sub 的 EX（ALU 入口）
```

这便是**转发**。转发检测单元每拍都在暗暗比对：「正在 EX 里的指令要读的源寄存器号，和正在 MEM 或 WB 里准备写回的目的寄存器号是不是撞上了？」只要撞上（且目的寄存器不是恒零的 `x0`，且对应指令确实要写寄存器），立刻拨动多路选择器把最新值抢先塞进 ALU！

转发省下了大把停顿，但它并非零成本：额外的寄存器编号比较器、更宽的 ALU 入口多路选择器以及长距离回头导线，都会给原本就紧张的 EX 阶段平添延迟，一不小心就会拉长关键路径。

### 化解之道二：`load-use` 冒险不得不停顿一拍

现在再把目光转向片段 B——读取后立即使用（`load-use`）：

```asm
lw  x5, 0(x10)
add x6, x5, x7
```

对照时空表，你会一眼看到那条跨不过去的「时间鸿沟」：

```text
时钟拍:  1    2    3    4    5    6    7
lw:     IF   ID   EX   MEM  WB
add:         IF   ID   --   EX   MEM  WB
```

看清了吗？第 3 拍末尾，`lw` 才刚算出内存地址；真正的新 `x5` 要等到**第 4 拍 MEM 结束**才落进 `MEM/WB` 托盘！如果硬让 `add` 在第 4 拍就冲进 EX，哪怕转发导线铺得再密，此时 `MEM/WB` 里压根还没有这个数！

硬件检测单元在 `add` 刚走到 ID（第 3 拍）时，就提前嗅到了这场迫在眉睫的灾难（上一条正处在 EX 的指令是 `lw`，且它的目的寄存器恰好是当前 ID 指令的源寄存器）。于是冒险检测单元果断拉响急刹，在第 4 拍干了三件事：

1. **锁死 PC**：保持程序计数器不变，别急着往下取新指令；
2. **冻结 `IF/ID` 流水寄存器**：让后面的指令先在原地踏步一拍，把 `add` 留在 ID 阶段再待一拍；
3. **往 `ID/EX` 里塞入一个空操作**：把送往 EX 阶段的所有写使能控制信号（`RegWrite`、`MemWrite`）全部清零，在时空表第 4 拍的 EX 工位上打出一个既不改寄存器也不改内存的空白占位符——形象地称为**气泡**（bubble），等价于插入了一条**空操作**（no-operation，简称 **nop**）。

熬过这短短一拍的等待后，第 5 拍降临：`lw` 的数据已经稳稳躺在 `MEM/WB` 托盘里，`add` 终于踏进 EX 阶段——此时转发通路火力全开，直接把 `MEM/WB` 里的新鲜数据递进 `add` 的 ALU，整条流水线恢复满速狂奔！

你看，片段 A 和片段 B 命运分岔的谜底彻彻底底摊在了眼前：`add` 的结果在 EX 末尾就已出炉，转发赶得上；`lw` 的结果拖到 MEM 末尾才从内存归来，时间上晚了一拍，再快的导线也不能穿越回过去，只能靠一颗气泡换来一拍喘息。

## 编译器伸出援手：静态调度填平气泡

硬件自动插入气泡虽然保住了正确性，但那一拍空转终究是白白浪费了。其实，根本不必把所有担子都压给硬件——聪明的编译器站在全局代码的高度，常常能不花一颗晶体管就把气泡变废为宝！

回头看看片段 B，假如紧跟在 `add` 后头还有一条与 `x5`、`x6` 毫无关系的独立指令（比如循环计数器加 1：`addi x11, x11, 1`），编译器只需轻轻挪动一下位置，把它塞进 `lw` 和 `add` 之间：

```asm
lw   x5, 0(x10)      # 第 4 拍 MEM 拿到 x5
addi x11, x11, 1     # 第 4 拍 EX 干自己的活，完美填满原本空转的气泡！
add  x6, x5, x7      # 第 5 拍 EX 稳稳接住从 MEM/WB 转发来的 x5，零停顿！
```

这种由编译器在生成机器码阶段预先重排指令顺序、错开数据等待的技巧，叫做**静态调度**（static scheduling）。它零硬件成本、零功耗增加，威力极大；局限在于编译器看不到运行时的动态变数（比如某条 `lw` 到底有没有命中缓存，或者指针有没有别名冲突）。因此，现代高性能计算系统普遍采用「软硬合璧」：编译器先用静态调度把肉眼可见的 `load-use` 气泡清理干净，硬件再靠转发和动态调度兜底运行时突发的变数。

## 第三关：控制冒险（前方路口还没亮灯）

除了抢硬件（结构冒险）和等数据（数据冒险），五级流水线还会撞上第三座、也是现代超深流水处理器最头疼的大山——**控制冒险**（control hazard）。

当一条条件分支指令（如 `beq x5, x6, target`）刚进入流水线的 IF 阶段时，它要等到 ID 甚至 EX 阶段把两个寄存器比完，才知道到底跳不跳、该跳去哪儿。可取指部件每一拍都必须往流水线里喂一条新指令！在答案揭晓前，前端已经顺着 `PC + 4` 把紧跟在后面的指令取进来甚至开始译码了——万一分支最终决定跳转，刚才抢跑进来的指令全都是不该执行的错误路径，必须当机立断把它们统统冲刷清空！

面对控制冒险，是乖乖停顿干等、把分支比较尽量往前挪，还是干脆大着胆子「先猜再说」？下一节[控制冒险与分支预测](branch_prediction.md)会专门展开这场惊心动魄的博弈。

## 流水线平衡：木桶效应与切分的极限

最后，再从全局视角审视一下流水线的时钟周期。把一条路径切成 $k$ 级流水，并插入流水寄存器后，新的时钟周期受制于最慢的那一级加上流水寄存器的固定开销 $T_{\text{reg}}$：

$$
T_{\text{clk}} \ge \max_i(T_i) + T_{\text{reg}}.
$$

这揭示了一条极其直观的「木桶效应」：假如五级之中，EX 已经压缩到 $150\text{ ps}$，但 MEM 访问缓存依然需要 $300\text{ ps}$，那么无论你再怎么拼命优化和拆分 ALU，整颗芯片的时钟周期依然被 MEM 死死卡在 $300\text{ ps}$ 以上！

不仅如此，哪怕把各阶段切得无比均衡，级数也不可能无限加深：第一，每多切一刀就会多出一排流水寄存器的固定延迟 $T_{\text{reg}}$ 和功耗，切到最后有效计算时间反而不如寄存器开销本身；第二，流水线越深，转发旁路网越呈爆炸式复杂，而且每次遇到无法预测的分支，被冲刷报废的指令数量也成倍增长。

数据冒险已经用转发、气泡和静态调度稳稳按住了，可面对动辄每五六条指令就冒出来一次的条件分支，总不能每次都插两三颗气泡干等吧？下一节，我们看看处理器如何化身「预言家」，靠分支预测把前端的空转压缩到极致。
