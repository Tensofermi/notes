# 虚拟存储的硬件支持

## 两个程序都读写地址 `13000`，凭什么各读各的、井水不犯河水？

打开你的电脑，浏览器、代码编辑器和音乐播放器正在同时运行——在操作系统眼里，每个正在运行的程序都是一个独立的**进程**（process）。现在设想一个再寻常不过的场景：进程 A 往地址 `13000` 写入了你的密码，同一秒钟，进程 B 也往地址 `13000` 写入了一首歌曲的采样数据。

如果这两个 `13000` 都是内存条上同一个物理门牌号，世界立刻就会大乱——不仅进程 B 会把进程 A 的数据盖得面目全非，任何恶意软件还能轻而易举地偷窥其他程序乃至操作系统内核的私密内存！

现代计算机化解这一难题的魔术，就是给程序看到的地址和内存条上的真实地址之间插入一层「地址翻译」：

- 程序指令里使用的门牌号叫做**虚拟地址**（virtual address）；
- 内存控制器用来真正定位 DRAM 芯片格子的真实门牌号叫做**物理地址**（physical address）。

操作系统把庞大的地址空间按固定大小切成一片一片的**页**（page），让每个进程都活在自己专属的虚拟地址世界里：在进程 A 的登记簿（**页表**）里，虚拟地址 `13000` 所在的页被翻译到了物理内存的第 20 号格子；而在进程 B 的页表里，同样是 `13000` 所在的页，却被翻译到了物理内存的第 87 号格子！这种为每个进程提供独立虚拟地址、按页灵活映射到真实物理内存的整套机制，就是**虚拟存储**（virtual memory）。

这一层看似「多此一举」的翻译，一举为现代操作系统换来了四大基石能力：

- **强隔离与安全保护**：每张页表记录都附带读、写、执行以及用户/内核权限位，进程既摸不到别人家的物理内存，也改不了只读代码段；
- **高效共享**：打开十个相同的浏览器标签页或共享标准库时，只需让十个进程的页表把各自的虚拟代码页指向**同一份只读物理页**，立省九份内存；
- **按需调页与容量扩展**：暂时用不着的冷门页面可以安安静静躺在磁盘或 SSD 上，等程序真正碰触它时再临时搬进主存，程序总规模可以轻松超出物理内存条的实际大小；
- **化零为整的连续幻觉**：程序看到的虚拟数组完全连续，而底下真实的物理页框可以东一块西一块地散落在内存条任意空位上，彻底消除外部碎片烦恼。

**阅读建议**：如果你是第一次接触虚拟内存，先跟着下面 `13000` 和 `13004` 的两次读取，牢牢分清机器什么时候在「找地址翻译」、什么时候在「找数据本身」，再亲手推演 `13000` 的三种访存命运。若想先拿更小的数字热身，不妨同步对照<a href="../../OperatingSystems/chapter_04_memory/01_address_space_paging.html">操作系统里的 16 字节分页例子</a>。

操作系统制定映射规则，硬件则扛起了最艰巨的性能重担——在**每一次**指令取指和内存读写的短短几纳秒内，极速完成地址翻译并检查权限。可一个尖锐的矛盾立刻冒了出来：**既然页表本身也存放在主内存里，那每次读数据之前岂不是都要先跑一趟主存查页表？「为了访存，先要访存」，速度岂不是直接腰斩甚至更惨？**

## 连续读 `13000` 和 `13004`，凭什么能复用同一条翻译？

要打破「每次访存都要翻查主存页表」的魔咒，我们再次请出了第 7 章的老朋友——局部性原理！

按现代系统最常见的设定，把每页大小定为 **4096 字节（4 KiB）**。程序视角里的每一片叫**虚拟页**（virtual page），物理内存条上同样大小的对应槽位叫**物理页框**（physical page frame）。把一个虚拟地址除以 $4096$，得到的商就是**虚拟页号**（VPN），余数就是在这张页内部的位置——**页内偏移**（page offset）。

来看看连续读取相邻两个 4 字节整数 `13000` 和 `13004` 时发生了什么：

- $13000 = 3 \times 4096 + 712$ → 虚拟页号 **3**，页内偏移 **712**；
- $13004 = 3 \times 4096 + 716$ → 虚拟页号 **3**，页内偏移 **716**。

看出来了吗？只要两次访问落在同一个 4096 字节的大页面里，它们共享**完全相同的虚拟页号 `3`**！一旦查明页表把「虚拟页 `3` → 物理页框 `20`」，那么 `13000` 对应的物理地址就是 $20 \times 4096 + 712 = 82632$，紧接着读 `13004` 时根本无需再去翻页表，直接沿用「页 `3` → 页框 `20`」，瞬间拼出物理地址 $20 \times 4096 + 716 = 82636$！

顺着这个洞察，芯片设计师在处理器核心紧贴着数据通路的地方，修了一块极小、极快的专属高速缓存——**地址翻译后备缓冲区**（**TLB**，俗称快表），专门用来记住最近刚查过的几十到上千条「虚拟页号 → 物理页框号 + 权限」翻译记录！

把一次读取 `13004` 的完整旅程画成流水图，你就能一眼看清 **TLB** 和 **数据 Cache** 各管哪一摊：

```text
虚拟地址 13004
    │
    ▼ 拆成：虚拟页号 3  +  页内偏移 716
    │
    ▼ 【找地址】查 TLB（未命中才查主存页表）→ 得到物理页框 20，并核验读权限
    │
    ▼ 拼接：物理页框 20 × 4096 + 原偏移 716 = 物理地址 82636
    │
    ▼ 【找数据】拿物理地址 82636 查数据 Cache（未命中才去下级缓存或 DRAM）
    │
    ▼ 返回地址 82636 处的 4 字节整数
```

请务必记住这两套缓存的**管理单位完全不同**：

- **TLB 管的是「翻译」**，最小粒度是一整张 **4096 字节的页**；
- **数据 Cache 管的是「数据副本」**，最小粒度是一条 **64 字节的缓存行**。

举个极好的辨析例子：如果程序先读 `13000`，接着读 `13064`（相距 64 字节）：它们俩依然稳稳落在同一张虚拟页 `3` 里，因此 **TLB 翻译完美命中复用**；可翻出来的物理地址 `82632` 和 `82696` 已经跨进了不同的 64 字节数据缓存块，因此在数据 Cache 里是**两块独立的数据**！当然，复用的前提是映射与权限未被修改；一旦操作系统改动了页表，必须同步让受影响的旧 TLB 表项失效。

## 页、页表项与「为什么不用做除法」

把上面的除法换回二进制视角，硬件的简洁之美会立刻显现出来。一个虚拟地址天然切分为高位和低位两段：

```text
| 虚拟页号 (VPN) | 页内偏移 (page offset) |
```

页表里的每一条记录叫做**页表项**（Page Table Entry，简称 **PTE**）。除了保存对应的**物理页框号**（Physical Page Number，简称 **PPN**）之外，PTE 还携带一排关键标志位：

- **有效位（Valid / Present）**：这张虚拟页眼下到底在不在物理主存里；
- **权限位（R / W / X / U）**：允许读、允许写、允许当指令执行吗？普通用户态程序有权碰它吗？
- **访问位与脏位（Accessed / Dirty bit）**：最近有没有被用过、内容有没有被改写过（决定将来如果把这页换回磁盘时，要不要先写盘保存）。

翻译过程极其干脆：**只把高位的 VPN 换成 PTE 里给出的 PPN，低位的页内偏移原封不动照抄过去！**

```text
| 物理页框号 (PPN) | 完全相同的页内偏移 (same page offset) |
```

为什么 4 KiB 的页恰好对应 **12 位**页内偏移？因为 $4\text{ KiB} = 4096 = 2^{12}$ 字节！在二进制世界里，除以 $2^{12}$ 求商和余数根本不需要造一台昂贵的除法器——**直接把地址最低的 12 根导线原样连过去当页内偏移，剩下的高位导线就是虚拟页号 VPN！** 零延迟、零电路代价，这就是为什么页面大小总是 $2$ 的整数次幂。

## 为什么必须使用多级页表？

如果用一张扁平的一维大数组把所有虚拟页的 PTE 统统排开，会发生什么灾难？

来算一笔吓人的空间账：哪怕是在古老的 32 位系统里，4 KiB 一页共有 $2^{20} \approx 100$ 万个虚拟页，每条 PTE 占 4 字节，光一个进程的页表就要固定吃掉 $4\text{ MB}$ 连续内存；而换到现代 64 位处理器（假设有效虚拟地址为 48 位），总页数暴涨到 $2^{36} \approx 687$ 亿页！每条 PTE 占 8 字节，**单是一个刚写完 `Hello World` 的小进程，一张扁平页表就要吃掉整整 $512\text{ GB}$ 内存**——根本装不下！

可真实进程用掉的虚拟地址空间其实是极其**稀疏**的（比如只用了开头一小段代码堆、和末尾一小段栈，中间几百万亿个地址全是空的）。**多级页表**（multi-level page table）正是为稀疏性量身定制的目录树：它把长长的 VPN 切成三段或四段（如 x86-64 的 4 级页表），最高级页表只占区区 4 KiB；查表时先拿 VPN 最高段去顶级目录找下一级页表的地址，层层往下钻——**只要某一大片虚拟地址区间压根没分配内存，整棵对应的下级页表子树就完全不用创建！** 进程真正只为自己实际用到的内存付页表空间费。

当然，体系结构的成本守恒定律再次显灵：多级页表省下了海量内存空间，付出的代价则是**一旦 TLB 未命中，走完 4 级页表可能需要连续发起 4 次额外的内存访问**！页表级数越深，空间越省，TLB 扑空时的代价就越沉重——这让 TLB 的高命中率变得更加生死攸关。

## TLB 性能与「TLB 未命中 ≠ 缺页异常」

和第 7 章的 AMAT 如出一辙，TLB 本质上就是把缓存思想再一次应用在「地址翻译」上。假设每次查 TLB 花费 $T_{\text{TLB}}$，命中率为 $h$，未命中时由专门的**硬件页表遍历器**（page table walker，部分精简架构由软件异常完成）去内存走完多级页表并回填 TLB，额外耗时 $P$。在串行简化模型下，平均地址翻译时间为：

$$
T_{\text{translate}} = T_{\text{TLB}} + (1 - h) P.
$$

由于每个页面高达 4096 字节，程序哪怕在数组里连续跑几百次读写，也都在同一页里打转，因此 TLB 的命中率常常轻松高达 **99% 以上**。

到这里，我们再郑重把一对初学者最常张冠李戴的概念彻底钉死：

- **TLB 未命中（TLB miss）**：只是说「你这张页的翻译小抄眼下没塞进那张容量很小的 TLB 里」，但主存里的页表清清楚楚地记着这条合法映射！硬件页表遍历器自己默默跑几趟内存（通常只花十几到几十纳秒）查出 PTE、塞进 TLB 就大功告成，**既不需要惊动操作系统内核，也完全不需要碰磁盘**。
- **缺页异常（page fault）**：硬件走完页表后，发现那条 PTE 的有效位居然是 `0`（说明这页的数据压根不在物理主存里），或者程序试图往只读页面强行写入数据！这时硬件束手无策，必须精确暂停这条指令，触发异常把控制权交给操作系统内核。如果是合法的「按需调页」（比如刚映射进来的文件页还没从 SSD 读入内存），内核会找一块空闲物理页框（若内存已满，还要先挑一页换出，若那页脏位为 1 还得先写盘保存）、花数万纳秒到数毫秒从 SSD 把数据读进来、填好页表，最后返回用户态**重新执行刚才被暂停的那条指令**；可如果程序是解引用空指针或越界乱写，内核则会直接发信号终止进程（比如大家熟悉的 `Segmentation fault`）。

## 端到端走查：虚拟地址 `13000` 的完整路径与三种命运

把前面的所有环节合龙，来看一条真实的 `lw x5, 8(x10)`：CPU 的 ALU 先把 `x10` 加 `8` 算出目标虚拟地址，紧接着踏上五步访存之旅：

1. 拆分虚拟地址，拿高位的 VPN 去查 TLB；
2. 若 TLB 命中，立刻拿到物理页框号 PPN，并核对当前指令是否具备读权限；
3. 将 PPN 与原封不动的页内偏移拼成完整物理地址；
4. 拿物理地址去查离核心最近的一级数据缓存（L1 D-Cache）；
5. 若 L1 命中，立刻吐出 4 字节数据并写回目的寄存器 `x5`。

现在，借用<a href="../../OperatingSystems/chapter_04_memory/01_address_space_paging.html">操作系统的分页算例</a>里的同一个数字——虚拟地址 `13000`（虚拟页 3，页内偏移 712；合法映射指向物理页框 20，物理地址为 $20 \times 4096 + 712 = 82632$）——推演在三种不同现场条件下，这条一模一样的 `lw` 指令会走出怎样截然不同的命运：

| 访存前的系统现场 | 机器里究竟发生了什么 | 性能剖析时去哪找铁证 |
| --- | --- | --- |
| **场景 1**：TLB 里没有页 3，但主存页表已映射且可读 | 触发 **TLB miss** → 硬件遍历器查页表拿到页框 20 并回填 TLB → 拼出 `82632` 继续查数据 Cache | 硬件计数器的 TLB 未命中与页表遍历周期 |
| **场景 2**：地址合法，但页表显示页 3 尚未载入主存 | 触发 **page fault** → 暂停指令陷入内核 → 内核分配物理页框并从文件/SSD 读入数据（或清零匿名页）、更新页表 → 返回重跑该条 `lw` | 操作系统的缺页计数（minor/major page fault）与磁盘 I/O 记录 |
| **场景 3**：TLB 命中直接得到 `82632`，但该数据块不在 L1 里 | 地址翻译瞬间成功，随后触发 **L1 数据 Cache miss** → 逐级去 L2/L3 或 DRAM 搬回包含 `82632` 的 64 字节缓存块并填进 L1 | 硬件计数器的 L1/L2/LLC 缓存未命中计数 |

牢记这三件事彼此独立：**翻译缓存存的是页映射，数据缓存存的是字节块，页表存的是页面是否在内存与权限合法性**——三者各自可以独立命中或未命中。

??? question "动手推演：固定上述映射，只改动下面任意一个条件，哪个环节会随之变化？"

    设数据缓存块大小为 $64$ 字节，物理地址 `82632` 落在起点为 `82624`（`82624`–`82687`）的缓存块内：
    - **改读虚拟地址 `13004`**：仍在虚拟页 `3`（偏移 `716`），翻译得 `82636`，既复用同一条 TLB 项，又落在同一块 `82624`–`82687` 里——**TLB 与 L1 双双命中**！
    - **只把缓存块 `82624`–`82687` 替换出去**：再次读 `13000` 时，**TLB 依然命中**，但会触发一次 **L1 数据 Cache 未命中**。
    - **只清掉 TLB 里的页 3 项，不动数据 Cache**：再次读 `13000` 时，先触发一次 **TLB 未命中**、遍历页表算回 `82632`，随后去查 L1 时数据块还在，竟然能直接 **L1 命中**！
    - **把 `lw` 改成 `sw` 去写一张只读页**：哪怕这条翻译就稳稳躺在 TLB 里（**TLB 命中**），硬件权限检查立刻发现「无写权限」，照样当场触发 **page fault** 交给内核裁决（可能是合法的写时复制 Copy-on-Write，也可能是直接报错终止）。

## 大页与 TLB 覆盖范围：如何用小快表罩住大内存？

随着现代服务器内存飙升到几百 GB 甚至 TB 级，经典的 4 KiB 小页面暴露出了一个新瓶颈。把一块 TLB 里所有表项能同时映射的物理内存总量称为 **TLB 覆盖范围**（TLB reach）：

$$
\text{Reach} = N_{\text{entries}} \times \text{PageSize}.
$$

算一算就心凉半截：假设一颗 CPU 的 L1 数据 TLB 有 $64$ 条表项，每页 $4\text{ KiB}$，它最多只能同时罩住 $64 \times 4\text{ KiB} = 256\text{ KiB}$ 的内存！面对动辄占用几十 GB 内存的大型数据库、内存缓存或 AI 推理张量，随机访问一下几乎步步都是 TLB miss，花在走 4 级页表上的时间甚至能吞掉百分之十几的总性能！

怎么把 TLB 覆盖范围一下子撑大成百上千倍？与其把昂贵耗电的 TLB 硬扩几百倍，不如增大单页尺寸——现代处理器普遍支持 **2 MiB 甚至 1 GiB 的大页（huge page）**！同样区区 64 条 TLB 表项，换成 2 MiB 大页后，覆盖范围瞬间从 $256\text{ KiB}$ 暴涨到 **$128\text{ MiB}$**，顺带还少走了一两级页表！

当然，大页也有它的代价：如果一个小对象只占了几十 KiB 却领走了一整张 2 MiB 大页，白白空置的尾巴再也分不给别人，这叫**内部碎片**（internal fragmentation）；同时，操作系统更难在碎片化的物理内存里凑出连续 2 MiB 的大块空间，单次调页和清零的粒度也随之变重。

## 芯片级巧思：怎么让 TLB 和 L1 缓存「同时起跑」？

回头再看刚才的五步访存路径，眼尖的读者一定会追问一句：按顺序先查 TLB、等拿到物理地址再去查 L1 缓存，岂不是把两段延迟串行加在一起、白白拉长了每条 `load` 的关键路径？

能不能在拿到虚拟地址的同一拍，**一边查 TLB 翻高位页号，一边同步去 L1 缓存挑组**？

这正是现代高速 CPU 普遍采用的经典设计——**虚索引、实标记（VIPT，Virtually Indexed, Physically Tagged）**！回忆第 7 章那个 32 KiB、8 路组相联、64 B 块的 L1 缓存：它的块内偏移占低 **6 位**，组索引占接下来的 **6 位**，两者加起来恰好是最低的 **12 位**！

奇迹就在这里发生了：对于 4 KiB 页面，**地址最低的 12 位正好是翻译前后纹丝不动的页内偏移！** 这意味着，在地址翻译结果出炉之前，L1 缓存拿虚拟地址的低 12 位去挑出的那个组，和用物理地址挑出的组**百分之百是同一个组**！于是硬件放心地让 TLB 查表和 L1 读出该组 8 路数据与标记**同时起跑**；半拍之后，TLB 吐出物理页框号 PPN，L1 顺手拿它和刚读出来的 8 个物理 tag 一比对——既省掉了一整段串行等待，又因为最终比对的是物理 tag 而彻底避免了不同进程同名虚拟地址互相撞车（别名冲突）的麻烦！

## 权限、上下文切换与安全边界

最后，别忘了虚拟存储不只是性能与内存管理机制，它更是整台机器最核心的**硬件安全防线**。

当操作系统把 CPU 从进程 A 切换到进程 B（上下文切换）时，页表基址寄存器随之切向进程 B 的页表。此时留在 TLB 里的旧翻译全都属于进程 A——如果放任进程 B 误用它们，进程 B 就能瞬间读穿进程 A 的机密内存！早期处理器在每次切换进程时只能一刀切地把整张 TLB 全部清空（导致新进程刚恢复就遭遇一波惨烈的 TLB 冷未命中风暴）；现代处理器则给每条 TLB 项贴上了一张「身份证」——**地址空间标识符**（ASID，在 x86 上称 PCID），标明这条翻译归哪个进程所有，从而允许多个进程的翻译在 TLB 里和平共处、大幅减轻切换开销。

而正如第 6 章讲投机执行时见识过的那样，部分激进的处理器甚至会在权限位核验彻底完成之前，先沿着猜测路径投机读取受保护数据，虽然最后发现越权并撤销提交、触发异常，但投机读取留下的缓存状态却可能通过侧信道把内核机密泄漏出去（经典的 Meltdown 漏洞正是踩穿了这道硬件权限边界）。因此，现代地址翻译与权限检查不仅要快，更必须严防任何微体系结构侧漏。

走到这里，第 7 章与第 8 章关于 CPU 内部访存的全部链路已经打通——从寄存器到多级缓存、从 TLB 到多级页表、从 DRAM 行缓冲一直到缺页时惊动操作系统和硬盘。顺着最后那一环往下追问：**当系统真的需要从固态硬盘读入一整页数据，或者从高速网卡收进成千上万个数据包时，外设和主内存之间究竟是怎样把海量字节搬来搬去的？难道要让昂贵的 CPU 像搬砖工一样一个字一个字地亲手搬运吗？**

翻开**第 9 章**，让我们把视野从 CPU 和内存扩展到整块主板，走进 I/O 总线、中断、DMA 与高速设备数据通路的世界！
