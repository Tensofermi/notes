# PCIe、网卡和 NVMe 的数据路径

## 两块各跑 4 GB/s 的固态硬盘同时开读，总速度能直接加出 8 GB/s 吗？

机房采购了两块最新款的高速固态硬盘，单盘拿出来测顺序读取，每一块都能稳稳飙出 **$4\text{ GB/s}$** 的惊艳成绩。你满心欢喜地把两块盘并排插上主板，准备同时开读，期待总吞吐翻倍直冲 $8\text{ GB/s}$。

可压测一跑起来，总速度竟然死死卡在了 **$6\text{ GB/s}$** 左右——两块盘各自掉到了 $3\text{ GB/s}$！硬盘没坏，CPU 占用率也低得可怜，那消失的 $2\text{ GB/s}$ 去哪儿了？

画一眼主板底下的真实布线图，谜底瞬间揭晓：这两块盘并没有各自独享直连 CPU 的高速通道，而是先插在同一颗主板芯片组（或 PCIe 交换芯片）上，再共同挤进一条实际有效吞吐只有 $6\text{ GB/s}$ 的**共享上行通道**通往 CPU 和内存！就像两条限速宽阔的四车道支路，最后全都汇进了一座只有六车道宽的大桥——每条支路单独通车时畅通无阻，一旦两路同时放行，总车流量就被大桥的宽度死死封顶！

哪怕驱动程序把队列塞得再满，让两块盘马力全开，整条端到端吞吐也绝不可能突破共享通道的物理天花板。记住一条系统工程师的铁律：**产品说明书上的标称速度，只是单个设备的承诺，从来不是整条系统路径的承诺。**

??? question "在真实实验里，怎样一眼分清「硬盘本身慢了」还是「几块盘挤爆了共享通道」？"

    用对照变量法跑三组测试：先单独测盘 A，再单独测盘 B，最后同时并发测盘 A 与盘 B，同时记录单盘吞吐、合计总吞吐与单请求等待延迟。如果单测时各跑 $4\text{ GB/s}$、一并发总和就撞上 $6\text{ GB/s}$ 天花板，立刻去查机器的物理连接结构图——即**设备拓扑**（device topology，例如在 Linux 下用 `lspci -tv` 查看 PCIe 树），十有八九能揪出那一段被两块设备共用的咽喉链路！

**先修**：[总线、中断、DMA 与存储设备](io_interrupt_dma_storage.md)。

**读完本节你能做到**：从应用程序发起 `read()` 一路追踪到固态硬盘回传数据，清晰剥离互联道路（PCIe）、命令协议（NVMe）和底层存储介质（NAND）三个层次，并用带宽与延迟算出任何读取任务的物理下界。

## 跟着一次文件读取，走穿整条数据路径

当用户程序调用 `read()` 去读硬盘上的一段数据时，请求并不会像魔法一样瞬间把字节变进变量里，而是要沿着「软件栈 → 互连道路 → 设备控制器 → 存储介质」整整跑完一趟接力赛：

```text
应用程序 read()
    │
    ▼ 1. 操作系统先查主存里的【页缓存 (page cache)】
    │    （若命中，直接内存拷贝返回，根本不碰硬盘！）
    │
    ▼ 2. 页缓存未命中 → 文件系统把「文件偏移」翻译成「磁盘逻辑块号」
    │
    ▼ 3. 块设备层合并/调度请求 → NVMe 驱动把读命令写入主存里的【提交队列】
    │    → 通过 MMIO 写设备「门铃寄存器」，通知 SSD 控制器来取单
    │
    ▼ 4. 命令经由【PCIe】通道抵达 SSD 控制器 → FTL 查映射表
    │    → 从底层【NAND 闪存介质】读出对应物理页
    │
    ▼ 5. SSD 控制器通过【PCIe】发起【DMA】，把数据直写入主存页缓存
    │    → 写入【完成队列】并触发中断（或由驱动轮询发现）
    │
    ▼ 6. 驱动唤醒等待中的应用程序，读取大功告成！
```

先留意第 1 步那个大功臣——**页缓存**（page cache）：操作系统会把刚从磁盘读出来的热文件页悄悄留在空闲的 DRAM 主内存里当缓存；如果程序反复读同一个文件，后续读取压根不会触发任何磁盘 I/O，直接从几百倍快的 DRAM 里秒回！

而一旦页缓存未命中、必须真刀真枪去硬盘搬数据时，就会碰上三个在行业里天天被混为一谈的缩写——**PCIe**、**NVMe** 和 **SSD**。把它们放进上面这条路径里，三者的分工清晰得像高速公路、快递单规则和仓库货架：

| 层次与术语 | 在数据路径里扮演的角色 | 好比现实世界里的什么 |
| --- | --- | --- |
| **PCIe**（Peripheral Component Interconnect Express） | 主板内部连接 CPU、显卡、网卡和固态硬盘的高速点对点串行互连通道；交换芯片可将多段通道连通 | **高速公路与立交桥**（决定几车道、每车道限速多少） |
| **NVMe**（Non-Volatile Memory Express） | 专为高速闪存打造的主机-设备命令协议，约定如何通过成千上万个多队列提交读写命令并回报完成 | **高效的订单与派单规程**（允许成百上千个窗口同时收单派单，取代老式单队列的 SATA/AHCI） |
| **SSD 与 NAND 介质** | 固态硬盘整机，内部真正存电荷、锁 0 和 1 的芯片颗粒则是 NAND 闪存介质（配主控与 FTL） | **仓库里的立体货架与拣货员** |
| **高速网卡（NIC）** | 另一类挂载在 PCIe 上的高速外设，同样配有多组发送/接收描述符队列，经 DMA 在光纤和主机内存间高速倒腾网络包 | **连向外部城市的货运港口** |

分清这三层之后，排查「为什么读盘不够快」立刻有了手术刀般的精准度：

- 如果盘本身很快、单测达标、一并发就掉速，问题往往出在**道路层（PCIe 通道版本太老、通道数太窄如只有 x2、或者多设备共用交换机上行链路）**；
- 如果单核提交 I/O 满载、多核扩展上不去，要看**协议与队列层（NVMe 队列配置、中断亲和性与队列深度是否合理）**；
- 如果顺序读很快、持续写满半盘后突然断崖式暴跌，问题则藏在**介质与主控层（NAND 缓存写满、后台 FTL 垃圾回收引发的写放大）**。

## 队列深度的两面性：喂饱通道 vs 排队变长

现代高速 NVMe 固态硬盘和万兆/百兆网卡内部都藏着大量并行通道与处理流水线。如果软件死板地采取「发 1 个读请求 → 苦等它彻底完成 → 再发第 2 个请求」（即**队列深度 = 1**），那么硬盘内部 8 条甚至 16 条闪存通道里，每一瞬间有 7 条都在闲着拍苍蝇，吞吐根本起不来！

提高**队列深度**（允许同时有几十甚至上百个在途请求并发排队）能把所有闪存通道和 PCIe 流水线喂得饱饱的，把总吞吐推向物理极限。但同样逃不开排队论的铁律：队列越深，后来排进队伍的每一个单个请求就得在队尾等更久——**高队列深度换来极致吞吐，却会推高单请求的平均延迟与 P99 尾延迟**。调优存储与网络系统，本质上就是在「把通道吃满」和「别把队排太长」之间拿捏平衡点。

## 动手算两个物理下界：带宽下界与延迟下界

面对任何一次真实的 I/O 任务，动手写优化代码之前，先花十秒钟拿纸笔算出两个不可逾越的物理下界，能帮你省下无数无用功：

1. **带宽下界（大块顺序读主导）**：假设整条路径（受限于最窄一环）的持续有效读取带宽是 $4\text{ GB/s}$。现在你要把一个 $2\text{ GB}$ 的数据集从盘里搬进主存，那么无论你的代码写得多巧、操作系统调度多神，至少需要：

$$
T_{\min,\text{bandwidth}} = \frac{2\text{ GB}}{4\text{ GB/s}} = 0.5\text{ s}.
$$

如果实测跑了 $0.55\text{ s}$，说明硬件带宽已经被你榨到了 90% 以上，再在软件代码里抠指令几乎毫无收益；只有实测跑了 $5\text{ s}$，才值得深挖哪里卡住了！

2. **延迟下界（小块串行同步读主导）**：还是这块 $4\text{ GB/s}$ 的神盘，现在换一种糟糕的读法——程序每次只读 **$4\text{ KiB}$**，并且老老实实同步等这一笔彻底返回后再发下一笔（队列深度 = 1）。假设单次随机读穿过软件栈、PCIe 和 NAND 介质的端到端延迟是 $50\ \mu\text{s}$（$0.00005\text{ s}$），那么一秒钟最多只能跑完 $\frac{1}{50\ \mu\text{s}} = 20000$ 次请求，折算出来的有效带宽只有区区：

$$
20000 \times 4\text{ KiB/s} \approx 80\text{ MB/s} \text{！}
$$

标称 $4000\text{ MB/s}$ 的高速 NVMe 盘，生生被同步小块读拖成了 $80\text{ MB/s}$——**连设计带宽的 2% 都没用到**，读完同样的 $2\text{ GB}$ 竟然要花足足 $25$ 秒！这正是为什么评估存储性能时，绝不能只盯着总字节数，必须同时记录**单次请求大小、总请求次数、完成延迟和队列深度**，并通过大块预读或异步并发 I/O（如 Linux `io_uring`）把同步延迟隐藏起来。

## 自测

一台服务器装了两块性能完全相同的 NVMe 固态硬盘。单独读取其中任意一块时，吞吐都能跑满标称速度；可一旦两块盘同时并发读取，各自的读取速率双双明显下降，此时监控显示 CPU 占用率却非常低。请列出至少两种合理、且可以用实验验证的底层解释。

??? note "参考思路"
    CPU 占用率低只能说明计算资源并不吃紧，瓶颈多半卡在数据搬运路径的共享环节上。至少可以从两个方向排查：
    1. **共享 PCIe 链路或交换芯片瓶颈**：两块盘挂载在同一个 PCIe Switch 或主板芯片组下，共用了一条带宽小于双盘之和的上行链路。验证方法：用拓扑工具（如 `lspci -tv`）核对 PCIe 树与链路速率/通道数，或者把其中一块盘改插到直连 CPU 的另一组 PCIe 插槽再复测。
    2. **系统内存带宽或 NUMA 跨节点通道争用**：两块盘并发 DMA 写入同一片主存通道（或跨 CPU 插槽互连写入远端内存），导致内存控制器带宽饱和或总线仲裁排队加剧。验证方法：监控内存带宽计数器与 I/O 队列等待延迟，并将两块盘的缓冲区绑定到各自直连的本地 NUMA 节点内存上对比测试。
