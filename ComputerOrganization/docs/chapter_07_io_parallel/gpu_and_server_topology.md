# GPU、显存和服务器拓扑

## 只把四个数各乘以 2，值得搬出一块顶级 GPU 吗？

面对一个只有 4 个元素的小数组 `[3, 7, 2, 5]`，想把每个元素都乘以 2 得到 `[6, 14, 4, 10]`。你可以让一颗 CPU 核心轮流算四次，也可以交给四个并行的执行单元一人领一个下标同时算——前提是每一项只读自己的输入、只写自己的输出，彼此互不依赖（如果第 $i$ 项要依赖第 $i-1$ 项刚算出的结果，这种循环携载依赖就没法直接平铺拆分，必须先换并行前缀和等算法）。

现在有个极其现实的工程问题：手边恰好插着一块价值不菲、每秒能算上百万亿次的顶级 **GPU**——把这四个数发给 GPU 算，会不会快得像闪电？

答案恰恰相反：**不仅不会更快，反而可能比 CPU 慢上几千倍！**

原因一点都不玄乎：这四个数最初安安静静地躺在 CPU 主存里。想让独立 GPU 帮着算，CPU 得先花几微秒打包发起一次传输，经由 PCIe 总线把数据搬进 GPU 专属的独立内存——**显存**（Video Memory，简称 **VRAM**）；再花几微秒向 GPU 下发启动命令唤醒计算阵列；等 GPU 用不到一纳秒算完那四次乘法后，还得再穿一趟 PCIe 把四个结果搬回 CPU 主存！光花在路费和热身启动上的固定开销，就够 CPU 自己把这四个数来回算上几万遍了！

可如果把问题规模从 4 个数放大到**一亿个数**，甚至让整个深度学习模型几百层的前向与反向计算**全部驻留在显存里接力完成、算完一整批才把极小的损失值送回 CPU**，局势就会彻底逆转：区区微秒级的启动和路费被庞大的计算量摊薄得微乎其微，GPU 恐怖的并发算力与显存带宽瞬间把 CPU 甩开一两个数量级！

这一节，我们就顺着「GPU 怎么并行干活 → 数据究竟住在哪一层 → 多卡服务器怎样连成一张拓扑网 → 如何手算端到端带宽下界」的脉络，看懂现代异构计算机器的全貌。

**先修**：[总线、中断、DMA 与存储设备](io_interrupt_dma_storage.md)、[SIMD、多核与缓存一致性](parallelism_consistency.md)。

**读完本节你能做到**：拿到一个 GPU 计算任务，立刻说清数据此刻躺在主存、显存还是片上高速存储，判断拖慢速度的元凶是算力、显存带宽还是跨设备搬运，并算出双缓冲流水下的吞吐下界。

## GPU 的并行哲学：SIMT、线程束与分支分化

同样是做并行计算，CPU 和 GPU 把硅片面积押在了截然不同的赌注上：

- **CPU 是「少数几位全能教授」**：把大片晶体管砸在巨型缓存、复杂分支预测器和超深乱序执行引擎上，拼命压低**单条复杂线程的延迟**；
- **GPU 则是「成千上万名整齐列队的算术兵」**：大幅削减单线程的控制逻辑，腾出大片芯片铺满成百上千个精简算术单元、超大容量寄存器堆和极宽的显存通道，不追求单条线程跑得多快，而是靠海量并发线程轮换掩盖访存延迟，把**整体计算吞吐量**拉到极致！

要在 GPU 上把一百万个数组元素同时乘以 2，程序员会编写一段面向单个元素的小程序，叫做**计算核**（kernel），然后一口气启动一百万条执行同一份代码的逻辑**线程**（thread），每条线程通过自己的唯一编号领走一个下标干活。

但硬件绝不会为那一百万条线程各配一套昂贵的取指和译码控制器！以最经典的 NVIDIA GPU 架构为例，硬件会把连续的 32 条线程编成一个齐步走的小分队，称为**线程束**（warp）。同一个线程束里的 32 条线程**共享同一套取指译码前端，每一拍同时发射完全相同的指令**，各自对自己的寄存器和下标数据执行运算——这种介于 SIMD 与多线程之间的执行模型，叫做**单指令多线程**（Single Instruction Multiple Threads，简称 **SIMT**）。

理解了 SIMT，GPU 编程里两条最著名的性能铁律立刻不言自明：

1. **警惕「线程束分化」（Warp Divergence）**：假设我们对 `[3, 7, 2, 5]` 执行一段带 `if/else` 的代码——「偶数乘 2，奇数加 1」。因为这四个元素由同一个线程束里的 4 条线程同频执行，它们没法在同一拍既做乘法又做加法！硬件只好先掩码激活处理偶数 `2` 的那条线程做乘法，此时处理 `3, 7, 5` 的三条线程全都原地干等；下一拍再反过来激活那三条奇数线程做加法，让处理 `2` 的线程干等！分支越碎，原本 1 拍的活被串行拆成越多拍，有效算力直线腰斩；
2. **善用「合并访存」（Memory Coalescing）**：当同一个线程束里的 32 条相邻线程同时访问**连续相邻**的显存地址（比如线程 `k` 读 `A[k]`）时，GPU 内存控制器会把这 32 次零散请求神奇地自动合并成区区一两次整块宽带宽显存突发事务，瞬间跑满每秒数 TB 的显存带宽！反之，如果 32 条线程随机跳着读天南地北的地址，就会拆成几十次碎事务，带宽利用率暴跌。

## 分清每一份数据住在哪一层：容量 vs 带宽

评估 GPU 性能时，拿到显存参数表千万别只看一个数，必须紧盯两把不同的尺子：**容量**（最多能同时装下多少 GB 的模型权重和激活值）和**带宽**（一秒钟能把多少 TB 数据从显存搬进算术核心）。许多大语言模型推理的逐字生成阶段，显存容量绰绰有余，算术单元却一大半时间在闲着——因为每生成一个新词都要把几十 GB 参数完整从显存里重读一遍，死死卡在了**显存带宽**上！

把一台典型 GPU 服务器里的数据落脚点从远到近排成一张地图，定位瓶颈立刻一目了然：

| 数据所在层次 | 典型存放内容 | 排查性能时该盯紧什么 |
| --- | --- | --- |
| **CPU 主存（Host DRAM）** | 刚从硬盘或网络加载、经 CPU 预处理拼装好的一批训练样本 | 主存带宽，以及这块内存是否和搬运数据的 CPU 核心、PCIe 槽落在同一个 [NUMA 节点](parallelism_consistency.md) |
| **主机与设备互连（PCIe / 专用高速互连）** | 在 CPU 与 GPU 之间、或不同 GPU 之间来回搬运的批次输入、梯度与激活张量 | 真实物理路径、是否支持卡间直传（P2P）、是否与网卡/SSD 共用同一条 PCIe 交换链路 |
| **GPU 显存（VRAM / HBM）** | 神经网络模型参数、优化器状态、大尺寸输入输出多维数组（张量） | 显存总容量是否装得下（避免 OOM）、持续带宽利用率以及计算核的合并访存模式 |
| **GPU 片上存储（寄存器 / 共享内存 / 缓存）** | 线程私有的累加中间值、同一线程块内多条线程协作复用的分块小矩阵 | 能否把高频复用的数据留在片上反复算，大幅减少来回跑显存的次数（这正是 FlashAttention 等算法的灵魂） |

## 服务器物理拓扑与多卡集合通信

当单块 GPU 装不下庞大的模型或算得不够快，一台现代 AI 服务器往往会同时插上 4 块、8 块 GPU，再配上多颗 CPU 和多张高速网卡，甚至把上千台这样的服务器连成超级集群。

把这台机器里所有 CPU 插槽、内存通道、PCIe 交换芯片、GPU、高速卡间直连（如 NVLink 交换矩阵）以及网卡之间的真实连线画成一张结构图，就是整机的**拓扑**（topology）。

拓扑直接决定通信速度的天壤之别：

- **同一颗 PCIe 交换芯片下（或有专用 NVLink 高速直连）的两块 GPU**：彼此可以点对点直接传输张量，既快又不挤占 CPU 主存带宽；
- **分别插在 CPU 0 和 CPU 1 两侧、又没有专用直连的两块 GPU**：数据可能必须先走一段 PCIe 到 CPU 0，跨过相对较窄的跨 CPU 互连链路（甚至绕道主存中转）去到 CPU 1，再走 PCIe 进目标 GPU，带宽骤降、延迟飙升！

等规模跨出单台机器、走向多机分布式训练时，拓扑图还要进一步延伸到高速网卡（如支持远程直接内存访问 RDMA 的 InfiniBand / RoCE 网卡）和顶层网络交换机。在数据并行训练中，每台机器上的每块 GPU 各自算完一份局部梯度后，必须通过网络按固定算法把所有卡的梯度汇总求平均、再同步回每块卡——这种由所有参与者按规则协同交换并合并中间结果的通信模式，叫做**集合通信**（collective communication，如经典的 `All-Reduce`、`All-Gather`）。一旦网络带宽或拓扑设计不合理，上千块昂贵的 GPU 就会花掉一大半时间互相等梯度同步。

## 手算端到端下界与双缓冲流水线

让我们做一道极其贴近实战的端到端算术题，把第 6 章的流水线直觉和本章的搬运成本结合起来！

假设一个推理或训练任务，每一批输入数据大小是 **$480\text{ MB}$**，从主机主存经 PCIe 传进 GPU 显存的实际有效带宽是 **$12\text{ GB/s}$**（按十进制 $1\text{ GB} = 1000\text{ MB}$ 算），而 GPU 算完这一批数据只需 **$10\text{ ms}$**。

1. **先算传输带宽下界**：

$$
T_{\text{transfer}} = \frac{480\text{ MB}}{12000\text{ MB/s}} = 0.04\text{ s} = 40\text{ ms}.
$$

2. **朴素串行执行（传一批 → 算一批 → 再传下一批）**：每一批端到端耗时 $40 + 10 = 50\text{ ms}$。注意此时 PCIe 通道在 GPU 计算那 $10\text{ ms}$ 里闲着，而 GPU 计算核心在传输那 $40\text{ ms}$ 里全在晒太阳！
3. **启用双缓冲流水线**：在显存里开辟两块交替使用的输入缓冲区，叫做**双缓冲**（double buffering，类似流水线中的两份托盘）——当 GPU 正在埋头计算缓冲区 A 里的第 $k$ 批数据时，DMA 引擎同步把第 $k+1$ 批数据经 PCIe 悄悄搬进缓冲区 B；下一轮两者互换角色！

```text
时间(ms):   0        40   50       80   90      120  130
PCIe 传输:  [  批次 1  ][  批次 2  ][  批次 3  ]
GPU 计算:             [批1]        [批2]        [批3]
```

看清了吗？第一批依然要走完 $40 + 10 = 50\text{ ms}$ 的首批延迟；可一旦进入稳态，连续完成两批的时间间隔从 $50\text{ ms}$ 压低到了较慢那一阶段的耗时——**$40\text{ ms}$**！这和第 6 章 CPU 流水线的规律如出一辙：**稳态吞吐永远由最慢的那一级主导！**

更宝贵的是，一眼就能从这张时间线揪出头号瓶颈：就算开了双缓冲，GPU 计算核心每 $40\text{ ms}$ 也只忙了区区 $10\text{ ms}$（利用率最高只有 **25%**），剩下 $30\text{ ms}$ 都在苦等 PCIe 送货！此时哪怕花大价钱把 GPU 升级成算力快两倍的新款（计算从 $10\text{ ms}$ 缩到 $5\text{ ms}$），稳态间隔依然纹丝不动卡死在 $40\text{ ms}$！真正该下的药方是压缩输入格式（比如第 2 章的 FP16/BF16）、升级互连带宽、或者把更多预处理挪到 GPU 侧减少主机搬运。当然，双缓冲能真正重叠生效的前提是：硬件和驱动支持异步传输与计算引擎并发（例如 CUDA 独立流 + 锁页内存），且后一批数据的输入不依赖前一批的计算结果。

顺带给出一份务实的硬件选型习惯：面对诸如 H100、H200、B300 这类迭代飞快的 GPU 型号，千万不要被宣传海报上单一的「峰值算力」迷花了眼，而应先拿自己的真实工作负载定好衡量维度，把候选型号放进同一张对照表里逐列核对——**支持的计算格式与原生吞吐、显存容量与显存带宽、卡间与主机互连接口（PCIe / 专用直连）、单卡热设计功耗，以及机房实际部署拓扑**——哪一列撞上了你的任务短板，哪一列才是一票否决的关键。

至此，全书从晶体管和 0/1 编码出发，一路穿过数字逻辑、指令集与汇编、CPU 数据通路与控制、流水线与分支预测、多级缓存与虚拟内存、I/O 与 NVMe/PCIe 数据路径，直至多核一致性与多卡 GPU 服务器拓扑，所有核心机制已经全部集齐！

## 自测

性能监控面板显示：一块 GPU 的显存占用率高达 95%，但计算单元（SM / 核心）的活跃利用率却长期徘徊在 15% 左右。仅凭这两条数据，能不能直接断定「这块 GPU 算力不足」或「模型太小」？为什么？

??? note "参考思路"
    完全不能！**显存占用率 95%** 只说明模型权重、激活或缓存占用了大量显存**容量**，它既不代表计算任务重，也不代表数据搬运顺畅。而**计算单元利用率极低（15%）**恰恰说明核心大部分时间在「挨饿等待」，可能的原因包括：
    1. **显存带宽瓶颈**：每个计算核搬运的数据量极大、算术密度极低，核心大部分时间在等 HBM 显存把字节送过来；
    2. **主机到设备传输或数据加载瓶颈**：CPU 预处理或 PCIe 拷贝太慢，GPU 算完一批只能干等下一批（如正文里的 `40 ms` 传 vs `10 ms` 算）；
    3. **多卡同步或小核启动开销**：频繁等待跨机集合通信同步，或者计算被拆成成千上万个微小的 kernel 导致启动开销主导。
    正确做法是用时间线剖析工具（如 Nsight Systems）把数据加载、PCIe 传输、通信等待和各计算核的耗时按时间轴展开，精准揪出空白期究竟在等谁。

关于线程分组、SIMT 执行模型与主存到显存异步传输的完整编程细节，可进一步参阅 [CUDA Programming Guide 的编程模型](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)。
