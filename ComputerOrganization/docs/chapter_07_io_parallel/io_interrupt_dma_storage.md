# 总线、中断、DMA 与存储设备

## 等一张网卡收齐数据包，CPU 该死盯着问，还是先忙别的？

想象你点了一份外卖，正在书桌前写一篇重要的代码。面对不知何时才会敲门的外卖小哥，你手里有三种截然不同的等法：

1. **每隔一秒起身趴门缝看一眼**：「到了吗？没到……到了吗？没到……」外卖一到你确实第一时间就能拿到，可在这之前你一行代码也别想写。搬到计算机里，这种由处理器循环不断查询设备状态的做法，叫做**轮询**（polling）。
2. **安心坐回桌前写代码，等外卖小哥按门铃**。门铃一响，你随手夹张书签记下写到哪一行，起身开门取走外卖，回来翻开书签继续干活。在硬件里，这种由设备办妥后主动发信号打断处理器的机制，叫做**中断**（interrupt）。
3. **如果你订的不是一份盒饭，而是一整车家具呢？** 就算搬家公司按了门铃，总不能让你这位大科学家自己一件一件往屋里扛吧！最聪明的办法是提前给搬家公司一张清单，写明「把这 100 件家具直接卸进 302 房间的空地」，然后你继续埋头工作，等搬家公司全部卸完货再按一下门铃通知你验收！在计算机里，这种把大块数据搬运彻底外包给设备、不经 CPU 倒手直接读写内存的机制，叫做**直接内存访问**（Direct Memory Access，简称 **DMA**）。

轮询、中断、DMA，恰恰构成了外设与 CPU 协作的三级阶梯。究竟何时该用哪一招？设备搬完数据后，底层的机械硬盘和固态硬盘又藏着什么截然不同的物理脾气？这一节我们一层层拆解清楚。

??? question "既然中断能解放 CPU，为什么超高速网卡或超低延迟 NVMe 固态硬盘在高负载下有时反而「倒退」回轮询？"

    回到门铃类比：如果楼下每秒钟有**五十万个**快递小哥接连狂按门铃，你光是不停夹书签、起身开门、关门、找书签，整个人就会彻底瘫痪，根本干不了正事！当设备事件极度密集、每次等待极短时，频繁触发中断带来的保存现场、切换内核态、冲刷流水线与污染缓存的固定开销，甚至超过了等一下的成本。此时直接由专门的核心采用轮询（或「先中断唤醒、再批量轮询收割」的混合策略，如 Linux 网络栈的 NAPI），反而能换来更低延迟和更高吞吐。

## 输入与输出的根本难题

**输入与输出**（input/output，简称 **I/O**）之所以让系统设计师格外头疼，是因为外部世界远比 CPU 内部狂野得多：

- **种类千奇百怪**：键盘、鼠标、显示器、网卡、固态硬盘、音频芯片、传感器，协议各异；
- **速度横跨六七个数量级**：键盘敲击间隔几百毫秒，机械硬盘几毫秒，NVMe SSD 几十微秒，高速内存却只有几十纳秒；
- **到达时刻完全不可预测**：人类什么时候按键、远程服务器什么时候发来数据包，绝不听从 CPU 时钟的节拍。

处理器不可能为每一种新设备都专门在 ISA 里焊死一套新指令，更不能用纳秒级的宝贵算力去苦等毫秒级的慢设备。因此，I/O 天生需要**异步**（asynchronous）协作——CPU 发出请求后转身去干别的活，外设自己在后台慢慢把事办完，再通知 CPU。而在一切协作开始之前，先得解决最基本的问题：**处理器到底怎么和五花八门的设备「说话」？**

## 设备控制器与内存映射 I/O：借用 `load`/`store` 给设备发号施令

CPU 并不会直接去拨弄硬盘里的马达线圈或网卡里的光纤激光器。每台外设内部都藏着一块专属的「小管家」电路——**设备控制器**（device controller），由它包办底层的物理细节，只对 CPU 暴露出寥寥几个可读写的接口格，叫做**设备寄存器**（device register），常见分三类：

- **状态寄存器**：告诉 CPU「我眼下正忙着、已经就绪，还是出错了」；
- **命令寄存器**：CPU 往里面写下指令码（比如「去读第 500 号扇区」）；
- **数据寄存器**：用来递交或取回少量数据。

怎样读写这些设备寄存器？现代主流架构（包括 RISC-V 与 ARM）最优雅的统一方案是**内存映射 I/O**（Memory-Mapped I/O，简称 **MMIO**）：从庞大的物理地址空间里专门划出一小片门牌号，不连到 DRAM 内存条上，而是直接连到各个设备控制器的寄存器上！

这样一来，ISA 连一条额外的 I/O 专用指令都不用加——驱动程序只需像读写普通内存一样，用现成的 `lw` 读设备状态、用 `sw` 往设备发命令！

但切记一条生死攸关的警告：**虽然借用了内存地址，MMIO 绝不能被当成普通内存来优化！**

- **不能被缓存**：如果把设备状态寄存器缓存在 L1 Cache 里，CPU 循环读它时永远看到的是缓存里的旧值「设备正忙」，永远不知道外设其实早就把硬件寄存器改成了「已就绪」；
- **读操作可能有副作用，写顺序不可乱序**：向设备发命令时，「先写目标地址寄存器、再写长度寄存器、最后写启动开关寄存器」的先后顺序必须铁板钉钉，一旦被编译器或乱序 CPU 重排，设备就会拿垃圾地址直接开工！某些状态寄存器甚至「读一次就自动清零」，绝不能被编译器随意合并或删掉。因此，MMIO 区域必须在页表里明确标记为「不可缓存、强顺序」。

## 总线与点对点互连：主板上的交通网

CPU、主存和众多设备控制器之间，靠什么把地址和数据送来送去？

早期计算机采用共享**总线**（bus）——好比一条贯穿全城的主干道，所有设备挂在同一束地址线、数据线和控制线上。谁想发话，必须先举手向**仲裁器**（arbiter）申请通行权，拿到许可才能独占路面传输。共享总线布线简单、成本低，但随着设备越挂越多、频率越飙越高，共享导线的电气负载和争抢冲突成了严重瓶颈。

于是现代计算机普遍进化成了**点对点高速串行互连**（例如下一节主角 PCIe）：不再让几十个设备挤在同一根铜线上互相干扰，而是用一对对专属的点对点高速通道通过交换芯片连成树状立交桥！只要两笔传输走的是互不重叠的支路，就能彻底并行不悖；只有在多路汇入同一条主干道时，交换芯片才会介入仲裁排队，并在接收端来不及消化时用流量控制信号要求发送端暂缓发包。

路修好了、对话方式定好了，现在把开头那三种等设备的招式逐一放上解剖台。

## 第一招：轮询（最朴素的同步等待）

**轮询**的逻辑直白得只需三行伪代码：

```text
while device_status_is_busy():
    read_status_register()   # 反复查状态，直到就绪
transfer_one_item()          # 读写一个数据项
```

它的优点是极其简单、零中断切换开销、事件一旦到达立刻在几纳秒内响应；致命伤则是在等待慢设备时把整颗 CPU 核心 100% 绑死在空转循环里。所以工程上它只适合事件极其频繁、等待极短，或干脆由内核与中断配合做「高负载批量轮询」的场景。

## 第二招：中断（让设备办完了按门铃）

换成**中断**后，CPU 给设备下完命令就立刻切去跑其他线程或干脆休眠省电。等设备真的准备就绪，控制器拉高一根中断请求线（或发出一则消息信号中断 MSI），通知 CPU。处理器在当前指令边界干净利落地停下，按五步走完中断响应：

1. **保存现场**：把当前程序计数器 PC 和关键处理器状态存好，好比往书里夹上书签；
2. **查向量表**：根据中断号查表定位对应的服务程序入口；
3. **调整优先级屏蔽**：暂时屏蔽同级或更低优先级的不重要打扰，防止嵌套失控；
4. **运行中断处理程序**（interrupt handler）：读取设备数据、清理设备状态标志、唤醒等待该数据的应用程序；
5. **恢复现场**：取出书签，无缝回到被打断的原程序继续执行。

请顺手分清一对极易混淆的概念：**中断**和第 5 章讲过的**异常**都会迫使处理器暂停当前流程、转入内核处理程序，但**异常是当前指令自己惹的祸**（同步触发，如除零、缺页、非法指令），**中断则是外部世界随时敲门的结果**（异步触发，和此刻正在执行的那条指令毫无关系）。

中断虽然解放了等待时间，但每次进出中断都要保存恢复寄存器、冲刷流水线并挤占缓存。为了避免高速网卡或 SSD 每秒敲响几十万次门铃把 CPU 敲崩，现代设备支持**中断合并**（interrupt coalescing）：攒够比如 16 个包、或者等满 50 微秒，再统一按一次门铃汇报！合并大幅降低了 CPU 中断开销、提升了吞吐量，代价则是第一个到达的数据包得多等那一小会儿延迟。

## 第三招：DMA（把大块搬运彻底外包）

中断解决了「不用傻等」，却没解决「搬运太累」。设想从固态硬盘读入一个 4 MB 的文件——就算不用轮询，难道要让 CPU 每读 4 字节就被中断叫醒一次、亲手 `lw` 再 `sw` 整整一百万遍吗？

于是 **DMA** 闪亮登场！真正的工业级数据搬运流程清爽极了：

1. CPU 先在主存里划出一块用于收发数据的**缓冲区**（buffer），把「源位置、内存目标地址、总共搬多少字节」写进设备控制器的 DMA 寄存器（或内存描述符表），然后拍一下启动开关，转身去忙别的计算；
2. 设备自带的 DMA 引擎化身自主搬运工，直接向内存控制器发起一连串高速突发读写，一口气把整整 4 MB 数据从设备直灌进主存缓冲区——整个过程 **CPU 一条搬运指令都不用执行**；
3. 全部搬运完毕（或中途出错），DMA 引擎最后只轻轻按**一次中断门铃**，通知 CPU「货已卸完，请验收！」

你看，DMA 和中断从来不是互相替代的对手，而是天衣无缝的黄金搭档：**DMA 负责闷头搬砖，中断负责完工汇报！**

不过，放手让外设绕开 CPU 直接往主内存里写数据，立刻会引出三件必须严防死守的工程麻烦：

- **争夺内存带宽**：DMA 虽然省下了 CPU 指令，但它依然要占用主存总线和 DRAM 通道——大块 DMA 狂飙时，正在运行的 CPU 核心可能会感觉到内存变拥挤；
- **DMA 与缓存一致性**：如果 DMA 刚刚悄悄往物理内存 `0x8000` 写入了新收到的网络包，而 CPU 的 L1 缓存里还攥着 `0x8000` 昨天的旧副本，CPU 一读就会读到过期垃圾！现代高端 x86 服务器通常靠硬件总线嗅探自动保持 DMA 缓存一致；而在许多嵌入式或精简平台上，驱动程序必须手动执行「发送前把脏缓存刷回内存、接收后把对应缓存行作废」的同步操作；
- **安全越权风险与 IOMMU**：既然外设可以直接读写物理内存，万一某块劣质网卡的驱动写错了目标地址、或者虚拟机里直通的恶意设备故意往宿主机内核内存里乱写怎么办？现代平台在设备通往内存的咽喉要道上设立了一道硬件安全网关——**输入输出内存管理单元**（Input-Output Memory Management Unit，简称 **IOMMU**）。它就像给外设专配的「页表 + TLB」，把设备提交的地址翻译成授权的物理缓冲区地址，任何越界企图都会当场拦截！

搬运机制彻底打通了，可数据本身终究要落到持久化存储设备上。为什么同样是「读 4 KiB」，老式机械硬盘要花十几毫秒，现代固态硬盘却只要几十微秒，而且固态硬盘有时还会莫名其妙突然卡顿一下？

## 机械硬盘（HDD）：被旋转金属盘片锁死的毫秒级延迟

**机械硬盘**（Hard Disk Drive，简称 **HDD**）内部是一叠高速旋转（如每分钟 7200 转）的磁性金属盘片，配上一条像老式留声机唱臂一样的机械磁头臂。想读出盘片深处的一小块数据，必须熬过实实在在的机械运动：

1. **寻道时间 $T_{\text{seek}}$**：驱动马达把磁头臂精准挪到目标磁道那一圈（通常耗时 $4\text{–}10\text{ ms}$）；
2. **旋转延迟 $T_{\text{rotation}}$**：磁头到位后，还得干等目标扇区跟着盘片转到磁头正下方——7200 RPM 硬盘转一整圈需 $8.33\text{ ms}$，平均等半圈就要 $4.17\text{ ms}$；
3. **传输时间 $T_{\text{transfer}}$ 与控制器开销 $T_{\text{controller}}$**：扇区扫过磁头下方时真正读写字节的时间。

一次完整磁盘访问的总耗时为：

$$
T_{\text{disk}} = T_{\text{seek}} + T_{\text{rotation}} + T_{\text{transfer}} + T_{\text{controller}}.
$$

拿这串数字和 CPU 对比一下，你会倒吸一口凉气：一次随机读盘轻松吃掉 **$10\text{ ms}$**，在 3 GHz CPU 上足足等于 **3000 万个时钟周期**！如果程序满盘随机读小文件，99% 的时间全浪费在磁头来回甩臂和等盘片转圈上；唯独大块顺序读写能把那一次寻道旋转摊薄到几十 MB 数据上，跑出不错的持续带宽。这也是为什么操作系统专门配有磁盘电梯调度算法，尽量把零散请求按磁道排序合并——不过过度排序又可能让边缘磁道的请求久等挨饿。

## 固态硬盘（SSD）：摆脱了马达，却躲不开闪存的物理脾气

**固态硬盘**（SSD）彻底扔掉了旋转盘片和机械臂，改用纯电子芯片——**NAND 闪存**（NAND flash）——靠浮栅或电荷陷阱锁住电子来永久保存 0 和 1。没有了机械寻道，随机读取延迟骤降到短短几十微秒，比 HDD 快了上百倍！

但千万别天真地把 SSD 当成「掉电不丢、处处等速的超大内存」。NAND 闪存有着一条极其古怪的物理铁律：**它可以按较小的「页」（例如 4 KiB–16 KiB）读取或写入，却只能按包含几百个页的巨大「擦除块」（例如几 MiB）整块擦除；而且已经写过数据的页，必须先整块擦空才能重新写入！**

为了把这条古怪的物理脾气藏在标准块设备接口背后，SSD 内部塞进了一颗不亚于微型 CPU 的主控芯片，运行着一套精巧的固件——**闪存转换层**（Flash Translation Layer，简称 **FTL**）。它维护一张动态映射表，把操作系统看到的「逻辑块号」灵活映射到闪存芯片上真实的「物理页位置」：

- 当操作系统要改写第 100 号逻辑块时，FTL 绝不傻傻地原地擦除整块几 MiB，而是直接把新数据写到一个**全新的空白物理页**里，把原来的旧物理页标记为「过时无效」，再悄悄更新映射表（异地更新）！
- 随着不断写入，许多擦除块里堆满了过时无效页，空闲块越来越少。此时 SSD 后台必须启动**垃圾回收**（garbage collection，简称 **GC**）：挑出一个包含大量无效页的擦除块，把里面**仍然有效的少数页**先搬迁复制到别的新块里，再把这座腾空的旧擦除块整块擦除回收！
- 此外，每个闪存单元能承受的擦写次数是有物理寿命上限的。为了防止某个热点块被反复擦写提前报废，FTL 还会刻意把写入均匀摊派到整块盘的各个物理块上，这叫**磨损均衡**（wear leveling）。

看懂了 FTL 和垃圾回收，SSD 身上所有看似玄学的性能现象瞬间全部迎刃而解：

- **读快、写慢、擦除最慢**；
- **写放大**（write amplification）：因为垃圾回收需要搬迁有效页，随机零散小写入会导致闪存芯片内部实际写入的物理字节数，远远大于应用程序提交的逻辑写入量，既拖慢速度又折损寿命；
- **TRIM 指令**：以前删文件时，操作系统只改文件系统目录、根本不通知硬盘，导致 SSD 的垃圾回收傻傻地把早被用户删除的废数据当成「有效页」来回搬运！现代系统通过 **TRIM** 命令主动告知 SSD「这些逻辑块已经作废了」，让 GC 可以直接跳过它们、干脆整块擦除；
- **多通道与队列深度**（queue depth）：一块现代 SSD 内部并联着好几条独立的闪存通道，允许同时存在几十上百个在途读写请求并发推进，提高并发吞吐；
- **突如其来的尾延迟抖动**：平时读盘风驰电掣，可一旦写满触发后台大面积垃圾回收，当前台请求撞上正在擦除搬迁的通道时，响应时间会突然飙升几十倍——正好精准砸在第 6 章讲过的[P99 尾延迟](performance_amdahl.md)上！

## 把所有零件连成活画：一张网卡收包的完整旅程

最后，让我们把 **驱动**（driver，内核里操控特定硬件的代码）、**DMA**、**缓冲区**和**中断**放进一张高速网卡收包的真实场景里，看它们怎样丝丝入扣地合奏一曲：

1. **提前备好空位**：系统启动时，网卡驱动在主存里分配一批空闲缓冲区，并填好一张环形登记表——每一条记录叫做**描述符**（descriptor），写清对应缓冲区的物理地址和大小——把这张表的地址交给网卡控制器；
2. **数据不请自来**：一根网线传来一个以太网**帧**（frame）。网卡硬件毫不打扰 CPU，自己查环形描述符表领走下一块空缓冲区，用 **DMA** 直接把整帧字节灌进主存；
3. **写回凭证并敲门**：DMA 写完后，网卡改写对应描述符的状态位（标明「已填满、实际长度多少字节」），然后向 CPU 发出一次**中断**（高负载下合并多帧只敲一次门铃）；
4. **驱动接力并补货**：CPU 跳进中断处理程序唤醒网卡驱动；驱动扫一眼环形表里标着「已完成」的描述符，把装满数据的缓冲区移交给内核网络协议栈向上解析，同时赶紧把新的空闲缓冲区填回描述符环，准备迎接下一波数据洪流！

到这里，CPU 与外设之间的对话协议、搬运机制和底层存储介质都已经清晰呈现。可数据从一块 NVMe 固态硬盘或高速网卡出发，穿过主板走上内存条，沿途究竟经过了哪些物理通道与协议层次？为什么两块各跑 4 GB/s 的硬盘插在一起，实测总速度却可能连 6 GB/s 都上不去？下一节，我们沿着主板连线，走完[PCIe、网卡与 NVMe](device_data_paths.md)的真实数据路径。
