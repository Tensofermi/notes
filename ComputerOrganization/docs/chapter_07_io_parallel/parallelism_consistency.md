# SIMD、多核与缓存一致性

## 两条线程各改各的变量、没加一把锁，为什么并发跑反而慢了十倍？

看下面这个让无数并发程序员抓狂的真实案例：你在 C 语言里定义了一个结构体，里面紧挨着放了两个独立的计数器 `counter_A` 和 `counter_B`。然后启动两条线程，分别绑在核心 A 和核心 B 上：

- 线程 A 只管埋头把 `counter_A` 累加一亿次，绝不碰 `counter_B`；
- 线程 B 只管埋头把 `counter_B` 累加一亿次，绝不碰 `counter_A`。

两条线程逻辑上井水不犯河水，压根没有共享任何数据，连一把锁都没加！按理说，两颗核心各自狂奔，耗时应该和单核跑一亿次差不多。可一跑实测，时间竟然暴涨了**五倍甚至十倍**——比单核顺着跑完两亿次还要慢得多！

再做一个匪夷所思的小改动：你只在 `counter_A` 和 `counter_B` 中间硬塞进 64 个毫无用处的空字节（`char pad[64]`），逻辑一丝没变，再跑一遍——程序瞬间快了十倍！

这究竟是什么妖法？罪魁祸首叫做**伪共享**（false sharing）：程序逻辑上确实没有共享变量，但 `counter_A` 和 `counter_B` 挨得太近，**偏偏落进了同一条 64 字节的缓存行里**！核心 A 每次想改自己的 `counter_A`，硬件都必须先夺过**整条 64 字节缓存行**的独占写入权，并把核心 B 缓存里的那份副本强行作废；眨眼间核心 B 又要改 `counter_B`，于是又把整条缓存行夺回自己手里、把核心 A 的副本作废！两个毫无关系的变量，竟让同一条缓存行在两颗核心之间像乒乓球一样疯狂来回飞弹！

为什么多核硬件非得以「整条缓存行」为单位互相争抢写入权？当芯片从单核迈向 SIMD、多核乃至上百核的庞大阵列，硬件究竟是靠什么在背后苦苦维持「所有核心仿佛共享同一片整齐内存」的幻觉？这一节，我们把并行计算与多核一致性的底层机制彻底讲透。

??? question "如果给 `counter_A` 和 `counter_B` 各自配一把独立的互斥锁，能消除伪共享吗？"

    不能。锁解决的是对同一共享变量的互斥访问顺序，却改变不了两个变量在物理内存里的排布位置。只要 `counter_A` 和 `counter_B` 依然住在同一条 64 字节缓存行里，两颗核心每次拿到各自的锁去执行写入时，底层硬件依然要以整条缓存行为单位来回夺权失效。根治伪共享的药方是调整内存布局（填充对齐到独立缓存行）或改用线程局部累加。

## 并行的四个层次：从一条指令到整座机房

在第 1 章撞上功耗墙之后，芯片性能的增长引擎全面转向了**并行**。其实，同一份程序里潜伏着四个不同粒度的并行机会，分别由不同层次的硬件收割：

1. **指令级并行**（Instruction-Level Parallelism，简称 **ILP**）：在一颗核心内部，借由流水线、多发射和乱序执行，让同一条指令流里互不依赖的几条指令同时推进（第 6 章主角）；
2. **数据级并行 / 单指令多数据**（Single Instruction Multiple Data，简称 **SIMD**）：只需取指译码**一条指令**，同时对打包在一起的 4 组、8 组甚至 16 组数据执行一模一样的算术运算；
3. **线程级并行 / 多核**（multicore）：在一块硅片上集成多颗完整的处理器核心，让多个独立线程真正齐头并进地执行各自的代码流；
4. **集群级多机并行**：通过高速网络把成百上千台服务器联手，协同攻克单机装不下的海量任务。

不过切记：并行绝不只是在硅片上「把 ALU 复制十份」这么简单。算力翻倍之后，怎样及时把十倍的数据喂进运算单元、怎样公平拆分任务、又怎样协调多方对共享内存的读写，才是真正决定成败的硬仗。我们先从一颗核心内部最轻巧的并行武器——SIMD——说起。

## SIMD 与向量计算：一条号令，全排齐动

普通的一条 `add` 指令一次只能把一对数相加，这叫**标量**（scalar）运算。可遇到图像处理、音频滤波、物理仿真或矩阵乘法时，成百万个数组元素都要做一模一样的加乘动作——一个个标量循环既消耗海量取指译码能耗，又白白浪费了硅片面积。

**SIMD** 的思路极度干脆：把宽达 128 位、256 位甚至 512 位的**向量寄存器**切分成若干个并排的算术格子，每个格子负责一对数据，称为一条**通道**（lane）。下面这幅图展示了一条 4 通道 SIMD 加法指令如何一拍算出四对和：

```text
向量寄存器 A: [ a0 | a1 | a2 | a3 ]
                  +    +    +    +
向量寄存器 B: [ b0 | b1 | b2 | b3 ]
                  ↓    ↓    ↓    ↓
向量寄存器 C: [ c0 | c1 | c2 | c3 ]
```

取指一次、译码一次，指令数直接降为原来的四分之一，吞吐率瞬间翻了四倍！

不过，SIMD 在真实代码里并非一马平川，常常会撞上四道现实路障：

- **尾部余数与对齐**：数组长度是 `103` 而不是 `4` 的倍数，最后剩下 3 个零头必须额外走收尾处理；非对齐向量加载也可能跨缓存行减速；
- **条件分支引发的通道空转**：如果循环体里夹着一句 `if (a[i] > 0) c[i] = a[i] * 2;`，同一组 4 个元素里可能只有 2 个满足条件！SIMD 硬件会用一组比特——**掩码**（mask）——标出哪些通道本次生效、哪些通道屏蔽写入；被屏蔽的通道虽然占着算术单元却白白空转，拉低硬件利用率；
- **不连续访存的痛点**：连续排在内存里的 `[a0, a1, a2, a3]` 一次缓存读取就能整包拽进向量寄存器；可如果这 4 个数东一个西一个散落在不同地址（比如按索引表间接查表 `a[idx[i]]`），就必须动用昂贵的**聚集读取**（gather）把分散字节拼成向量、算完再**分散写回**（scatter），效率大打折扣；
- **带宽天花板**：像向量加法这样每读 12 字节才做 1 次浮点的「轻量计算」，往往还没把 SIMD 算力喂饱，主存带宽就已经先撞墙了。

顺便一提，早期的固定宽度 SIMD 扩展（如 x86 的 SSE 128 位 → AVX2 256 位 → AVX-512 512 位）每逢宽度翻倍就得推出一整套全新指令、逼着软件重新编译；而以 RISC-V 向量扩展（RVV）和 ARM SVE 为代表的现代**可变长向量 ISA**，把向量长度抽象成硬件运行时查询的参数，同一份编译好的二进制代码放到 128 位小芯片和 1024 位超算芯片上都能自动按实际通道数全速狂奔！

## 多核的「共享内存幻觉」与缓存一致性

走出单核，把视线投向拥有 8 颗、32 颗甚至上百颗核心的多核芯片。

为了降低延迟、避免所有核心天天挤爆同一块片上总线，每一颗核心都配备了自己私有的高速 L1（通常还有 L2）缓存，大家只在最底层的 L3 共享缓存和 DRAM 主存处汇合。

麻烦立刻来了！设想共享变量 `x` 最初等于 `0`，核心 A 和核心 B 先后读取了 `x`，各自把一份 `x = 0` 的副本稳稳装进了自己的私有 L1 缓存。下一拍，核心 A 执行了 `x = 1`（采用了第 7 章的写回缓存策略，只改了自己的 L1）。此刻如果核心 B 再去读 `x`，它从自己私有 L1 里命中读出来的依然是过时的 `0`！**同一个内存地址 `x`，两颗核心眼里竟然同时存在两个自相矛盾的值！**

如果不加管束，多线程编程赖以生存的「大家共享同一片内存」的直觉瞬间崩塌。为了在各自私有缓存的物理现实之上，牢牢维持「同一内存地址永远有单一一致视图」的幻觉，硬件必须运行一套严格的**缓存一致性**（cache coherence）协议。

### MESI 协议：用四种状态给每条缓存行管好「产权」

绝大多数现代多核 CPU 采用**写失效**（write-invalidate）思路：**允许多个核心同时持有同一缓存行的只读副本；但只要有任何一颗核心想写入，必须先通知其他所有核心把它们手里的旧副本统统标成失效（Invalid），确保写的那一刻全芯片唯独自己手握唯一有效副本！**

而且，出于控制开销的考量，硬件不可能给内存里的每一个字节都单独记一套产权状态——它把管理粒度直接对齐到了整条**缓存行**（cache line，通常 64 字节）！最经典的 **MESI** 协议给每条缓存行贴上四种产权标签之一：

- **M（Modified，已修改）**：全芯片**只有我这一份副本**，且我改过它（是脏的，比主存新）；将来被替换出去或别核来要时，必须负责写回或转交最新数据；
- **E（Exclusive，独占干净）**：全芯片**只有我这一份副本**，且和主存一致。好处是如果我等会儿想改它，不用通知任何人，直接默默升格为 `M` 就行！
- **S（Shared，共享只读）**：主存和其他核心里**可能也有**完全相同的干净副本。我可以痛快地读，但绝不能直接写——想写之前，必须先向别核发失效通知、拿齐独占权！
- **I（Invalid，无效）**：我手里这份副本已经过期作废，下次访问当作缓存未命中处理。

现在，把核心数量考虑进去，看看「通知其他核心作废副本」这条消息怎么传：

- **核心较少时（比如 4–16 核）用总线嗅探（bus snooping）**：所有核心挂在共享广播通道上，时刻竖着耳朵「偷听」通道上的所有访存请求。核心 A 想写一条处于 `S` 状态的缓存行时，只需在通道上大喊一声「我要独占写地址 `0x1000`！」，核心 B 听见后立刻低头检查自己缓存，把 `0x1000` 标成 `I` 并回复确认。简单高效，但核心涨到上百颗时，全员广播的流量会把芯片内部互连瞬间堵死；
- **核心很多时用目录协议（directory）**：在共享末级缓存或内存控制器旁建一本「产权花名册」（目录），精准记录每一条缓存行当前被哪几颗核心借走了。核心 A 要写时，目录一查花名册，只给真正持有副本的那一两颗核心发点对点定向失效私信！扩展性极佳，代价是存储目录表需要额外面积，且点对点绕一趟目录会多出一跳通信延迟。

### 回头破案：伪共享的真相

现在再回看开头那个离奇的十倍减速，一切瞬间大白于天下！

因为一致性协议是以 **64 字节整条缓存行**为最小产权单位的，当 `counter_A`（4 字节）和 `counter_B`（4 字节）紧挨着住进同一条缓存行时：

```text
同一条 64 字节缓存行: | counter_A (4B) | counter_B (4B) | ... 其余 56 字节 ... |
                     ↑ 核 A 改 A → 整行变 M，核 B 变 I
                                      ↑ 核 B 改 B → 整行抢回 M，核 A 变 I
```

每一次简单的加 1，原本只需 1 纳秒命中本地 L1，现在却被迫触发一次漫长的跨核失效广播、数据转交和重新拉取（耗时几十纳秒）！你在两者中间塞入 64 字节空白填充（或用 `alignas(64)` 强制缓存行对齐）后，两个计数器终于分家住进了两条互不相干的缓存行——核心 A 永久稳稳握着第一条的 `M` 状态，核心 B 永久稳稳握着第二条的 `M` 状态，跨核流量瞬间归零，程序立刻飞起来！代价只是多占了几十字节微不足道的内存。

## 千万别混淆：缓存一致性（Coherence） ≠ 内存一致性（Consistency）

搞懂了 MESI，千万别以为多线程内存问题就万事大吉了——下面这对英文长得很像、中文翻译甚至常撞车的概念，坑倒过无数资深工程师：

- **缓存一致性（cache coherence）**只管**「同一个内存地址」**：保证所有核心对变量 `x` 看到的修改历史自洽，且写入终将被其他核心看见；
- **内存一致性（memory consistency，又称内存顺序模型）**管的是**「多个不同内存地址之间的先后顺序」**！

看一个再经典不过的生产者-消费者握手场景（初始 `data = 0`，`ready = 0`）：

```text
核心 1（写数据后举旗通知）          核心 2（见旗后取数据）
data  = 42;                       while (ready == 0) { }
ready = 1;                        print(data);  // 一定打印 42 吗？
```

直觉会脱口而出：「核心 1 明明先写 `data = 42` 再写 `ready = 1`，核心 2 既然看见了 `ready == 1`，打印出来肯定是 `42` 呀！」

可真相足以惊掉下巴：**在现代多核 CPU（包括 ARM、RISC-V，甚至加上编译器优化后的 x86）上，这段不加同步的代码完全可能打印出 `0`！** 为什么？因为 `data` 和 `ready` 是两个**毫不相干的地址**！核心 1 的写缓冲或乱序引擎为了性能，完全可能把 `ready = 1` 抢先刷进共享缓存让核心 2 看见，而把 `data = 42` 晚半拍才送出去；或者核心 2 投机提前读走了旧的 `data = 0`！注意，这里 `data` 自己满足缓存一致性、`ready` 自己也满足缓存一致性——出事的是**跨两个地址的先后顺序被重排了**！

为了驯服编译器和硬件的激进重排、让多核之间能够可靠通信，软件必须显式使用**同步**（synchronization）原语：

- **内存屏障**（memory barrier / fence）：在代码里竖起一道红线，命令编译器和处理器「红线之前的所有写操作（如 `data = 42`）必须全部对外可见后，才允许越过红线去执行红线之后的写操作（如 `ready = 1`）」；
- **原子操作**（atomic operation）：把读改写捆成不可分割的一步，并且通常自带清晰的顺序语义（如 C++ / Rust 里的 `release` 与 `acquire`）。

内存顺序模型本身是一场经典的软硬权衡：**强顺序模型**（如顺序一致性 SC）写起并发代码最符合人类直觉，却把硬件的写缓冲和乱序访存手脚捆死；**弱顺序模型**（如 ARM、RISC-V）给硬件留足了极致提速空间，但要求高级语言内存模型、编译器和 ISA 三层严密配合，由程序员通过标准原子库或锁明确标注同步点。

## 原子读改写与并发归约：别让全局计数器毁了多核加速

再看一个常见并发事故：全局变量 `count` 当前为 `5`，核心 A 和核心 B 同时执行 `count++`。

在普通 RISC-V 汇编里，`count++` 会被拆成 `lw`（读出 5）→ `addi`（算出 6）→ `sw`（写回 6）三步。如果两颗核心恰好同时执行完 `lw` 都读到了 `5`，然后各自算出 `6` 依次写回——**明明加了两次，结果却只变成了 `6`，凭空丢了一次更新！**

破解的武器是硬件原生支持的**原子读改写**（atomic read-modify-write）指令（例如 RISC-V 的 `amoadd` 原子加或 `LR/SC` 链接加载/条件存储）：硬件在缓存一致性层面死死锁住这条缓存行的独占权，把「读旧值、加 1、写新值」揉成一个**不可被任何其他核心插队的原子步骤**，于是两颗核心依次精准得出 `6` 和 `7`。所有的互斥锁、信号量和无锁队列，归根结底都建在原子指令的地基之上。

但是，**「正确」不代表「快」**！设想你要把一个包含一亿个整数的大数组分给 16 颗核心求和：

- **灾难写法**：16 颗核心每读一个元素，就用原子加往同一个全局变量 `global_sum` 上累加——结果 16 颗核心每一拍都在疯狂争抢 `global_sum` 所在的那一条缓存行，所有并行算力瞬间退化成惨烈的跨核串行排队！
- **正确写法（局部累加 + 归约）**：把长度为 $N$ 的数组切成 $P$ 份，每颗核心只在自己私有的寄存器里闷头算出自己的局部小计（全程零跨核通信！）；等所有核心算完自己的 $N / P$ 个元素后，最后只需把这 $P$ 个小计合并成一个总和——这种由多份局部结果汇总出最终结果的模式叫做**归约**（reduction）。一亿次全局竞争骤降成了区区 16 次合并！

## 迈向大型多插槽服务器：NUMA 拓扑

当单颗芯片核心数不够用时，大型服务器会在同一块主板上装上 2 颗、4 颗甚至 8 颗独立的 CPU 插槽（Socket），每颗 CPU 插槽各自直连着属于自己的那几根 DRAM 内存条，CPU 插槽之间则通过高速互连总线相连。

这立刻打破了「访问所有主存地址延迟都一样」的古老假设：核心访问自己所在插槽直连的**本地内存**时，一步直达、延迟最低、带宽最高；可一旦访问另一颗插槽连着的**远端内存**，请求就必须多跨过一段插槽间互连、借道邻居的内存控制器，延迟明显拉长、带宽随之缩水。这种因物理距离远近而导致访存速度不均的架构，叫做**非一致内存访问**（Non-Uniform Memory Access，简称 **NUMA**）。在 NUMA 服务器上跑高性能程序时，把工作线程和它高频访问的数据尽量绑在同一个 NUMA 节点上，往往能白白捡回两位数的性能提升。

到这里，我们见识了从 4 通道 SIMD 到上百核 NUMA 服务器的通用并行世界。然而，面对深度学习动辄千亿次矩阵乘加、图形渲染每秒数十亿像素着色的恐怖吞吐需求，通用多核 CPU 依然显得力不从心——于是另一类截然不同的并行巨兽登上了历史舞台：把成千上万条精简执行通道和超宽显存塞进一块卡里的 **GPU**！把任务交给 GPU 什么时候赚翻、什么时候反而血亏？多块 GPU 之间又靠什么互联协作？下一节，我们走进[GPU、显存和服务器拓扑](gpu_and_server_topology.md)。

1. 什么样的程序最容易吃满 SIMD 向量单元的吞吐红利？一旦循环内部出现数据相关的 `if/else` 分支或非连续指针跳转，为什么通道（lane）利用率会大幅滑坡？
2. 伪共享（false sharing）丝毫不会让程序算错结果，为什么却常常把多核程序拖慢好几倍？请结合 MESI 缓存行产权迁移的过程说明。
3. 请用自己的话划清「缓存一致性（cache coherence）」和「内存一致性（memory consistency）」各自管辖的问题边界，并举例说明为什么满足前者并不自动保证后者。
