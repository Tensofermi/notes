# 综合案例 { #8 }

## 给同一条路径做功能检查和性能检查

先用[指令案例](load_add_store_walkthrough.md)检查结果能否写到正确位置，再把同样的方法用到[磁盘到 GPU 的数据路径](storage_to_gpu.md)。遇到速度问题，用[分段测量](bottleneck_diagnosis.md)找最可能限制整体的阶段。

前面几章分别研究了信息表示、指令、处理器、存储和输入输出——各章的知识在各自的边界内都讲得通，可真实程序从不按章节运行。综合案例把它们接在一起，沿先读取（`load`）、再相加（`add`）、最后写入（`store`）这条路径走一遍；某一步变慢时，再沿同一条路按段排查。

## 本章内容

- [一条 load/add/store 如何贯穿机器](load_add_store_walkthrough.md)：逐层、逐状态追踪取指、地址翻译、cache、流水线和写回。
- [跨层性能诊断与设计权衡](bottleneck_diagnosis.md)：用测量排除猜测，把优化收益和代价放回全系统。
- [一批数据怎样从磁盘进入 GPU](storage_to_gpu.md)：把追踪方法推广到设备、主机与显存之间的数据流。

## 为什么需要综合案例

孤立记忆容易制造错觉：知道 cache 的定义，却说不出它在 load 的哪一步介入；知道流水线转发，却不知 cache miss 会冻结哪些阶段；知道虚拟地址，却误以为 ALU 的加法直接得到物理地址。综合追踪就是针对这类错觉的解药。

综合追踪要求每一步回答四件事：

1. 当前输入是什么；
2. 读取了哪些状态；
3. 哪个部件产生结果；
4. 何时才能安全提交。

## 本章自测

理解单条指令以后，可以把同样的因果追踪方法用在[一批数据从磁盘进入 GPU](storage_to_gpu.md)的练习里。分别画出设备 I/O、主机解码和显存传输，再比较首批延迟与稳态吞吐。

1. load 的地址加法、地址翻译和 cache 查找分别处理什么？
2. 写内存指令为什么能先进入临时的[写入队列](load_add_store_walkthrough.md)，又需要在确认指令能正常完成后才更新共享内存？
3. 若程序慢，应先改代码还是先换硬件？需要什么证据？
