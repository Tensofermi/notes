# 一条 load/add/store 如何贯穿机器

## 先拿笔写下终局答案，再掀开机器盖子看全景

在开始这场横跨全书十章的「微观全景之旅」之前，先做一次小热身——如果你对某个环节还有些模糊，随时可以回头瞄一眼[第 5 章的单条读取数据通路](../chapter_04_cpu/datapath_instruction_cycle.md)和[第 8 章的三个访存等待点](../chapter_06_memory/virtual_memory_hardware.md)。

设想内存地址 `100` 存着 `7`，寄存器 `x6` 存着 `3`。现在顺次做三件事：「把地址 `100` 的值读进 `x5`」「把 `x5` 和 `x6` 相加存进 `x7`」「把 `x7` 写到地址 `104`」。不用想硬件，凭直觉就能写下终局账本：`x5 = 7`、`x7 = 10`、`Mem[104] = 10`。

接下来，我们把这组极简动作放进一台拥有**五级流水线、转发网络、虚拟内存（I-TLB / D-TLB）、多级写回缓存、写缓冲和多核一致性**的真实 RISC-V 机器里，换上一组贴近全站主题的数字，看看一行短短的 `c = a + b` 究竟惊动了多少硬件部件！

??? question "相比 `lw`，为什么 `sw`（写内存）指令必须同时集齐「地址」和「数据」两样东西？"

    `lw` 只要算出内存门牌号就能去取货；而 `sw` 既要知道「往哪个门牌号写（有效地址）」，又要手里攥着「具体要写进去的数值（待写数据）」。这两样东西往往来自两个不同的源寄存器，而且待写数据常常正是紧挨着的前一条算术指令刚刚才算出来的，因此不仅要走地址计算，还可能依赖专门的数据转发通路。

## 现场设定：一行 `c = a + b` 与它的初始状态

我们的主角，正是全站第一页立下的那行 C 代码：

```c
c = a + b;
```

编译器约定寄存器 `x10` 指向内存中紧挨着存放的三个 32 位整数 `a`、`b`、`c`，生成四条干净利落的 RISC-V 32 位基础整数（RV32I）汇编指令：

```asm
lw  x5, 0(x10)    # 读 a
lw  x6, 4(x10)    # 读 b
add x7, x5, x6    # 算 a + b
sw  x7, 8(x10)    # 写回 c
```

给定初始运行现场：

```text
指令集：RV32I（通用寄存器 32 位，地址与整数均为 32 位）
寄存器：x10 = 0x1000（指向变量 a 的虚拟地址）
主存内容：a = Mem[0x1000] = 20，b = Mem[0x1004] = 22
虚拟内存：页表映射有效，且拥有读/写权限，页面已经驻留在物理主存中
缓存冷热：这四条指令已经稳稳躺在 L1 指令缓存（L1 I-Cache）里；
          但 a、b、c 所在的那条 64 字节数据缓存行尚未进入 L1/L2/L3 缓存！
```

我们的终局架构目标非常明确：四条指令全部提交后，`x5 = 20`、`x6 = 22`、`x7 = 42`，且 `Mem[0x1008] = 42`。无论芯片内部接下来上演多少预测、停顿、未命中和缓冲，交到软件手里的这份账本必须分毫不差。

## 第 1 站：从源代码落地成内存里的机器码

在 CPU 取到第一条指令之前，软件工具链已经默默完成了四棒交接：

- **编译器**把 `c = a + b` 翻译成上面四条汇编，并替变量挑好了寄存器 `x5`、`x6`、`x7`；
- **汇编器**把助记符和字段编成四个 32 位二进制机器字；
- 如果程序由多个源文件拼成，**链接器**（linker）会把各个目标文件合在一起，解析跨文件符号并敲定代码与数据的最终布局地址；
- 等你敲下回车运行程序时，操作系统的**装载器**（loader）为新进程创建虚拟地址空间与页表，把可执行文件映射进内存，再把程序计数器 `PC` 指向入口。

请留意这一刻的分界线：四条指令的 **ISA 架构语义**已经彻底锁死，但底层 CPU 究竟是 5 级还是 15 级流水、缓存多大、有没有乱序执行，依然完全隐藏在微体系结构边界之下。

## 第 2 站：取指（IF）——I-TLB 与 L1 指令缓存联手出马

时钟上升沿响起，取指前端把当前 `PC`（一个**虚拟地址**）送出去：

1. 首先用 `PC` 的高位虚拟页号查询专门服务取指的**指令地址翻译快表**（**I-TLB**），拿到物理页框号并确认该页具有「可执行（X）」权限；
2. 拼出物理指令地址，查询离前端最近的**一级指令缓存（L1 I-Cache）**。按设定完美命中！32 位的 `lw x5, 0(x10)` 瞬间流入 `IF/ID` 流水寄存器，同时 `PC` 加法器顺手把下一拍的地址推到 `PC + 4`。

如果前方存在分支，分支预测器与 BTB 会在这一拍同步预测下一地址；本例四条指令笔直向前，前端一拍接一拍把四条指令依次送进流水线。

## 第 3 站：译码与读寄存器（ID）——把信号放上传送托盘

下一拍，第一条 `lw x5, 0(x10)` 步入译码阶段：

- 主译码器盯着低 7 位 `opcode`，一眼认出 I 型读字指令，提取源寄存器 `rs1 = x10`、目的寄存器 `rd = x5` 以及 12 位立即数 `0`；
- 寄存器堆从读端口吐出基址：$R[x10] = \text{0x1000}$；
- 控制器配齐一整组控制信号：`ALUSrc = 1`（选立即数）、`MemRead = 1`、`ResultSrc = 内存`、`RegWrite = 1`。

特别注意：`RegWrite = 1` 此刻绝不会立刻生效去改写 `x5`！它像一张随行工单一样被装进 `ID/EX` 流水寄存器，跟着这条 `lw` 一站一站漂流，直到最后一拍确认万无一失，才获准拉开寄存器堆的写入闸门。

## 第 4 站：执行（EX）——ALU 算出的还只是「虚拟地址」

进入 EX 阶段，立即数生成器把 12 位偏移 `0` 符号扩展为 32 位，ALU 将基址与偏移相加：

$$
\text{VA} = R[x10] + \operatorname{signext}(0) = \text{0x1000}.
$$

这是初学者最容易卡壳的节点：**ALU 算出来的 `0x1000` 依然只是一个虚拟有效地址（VA），不是物理内存条上的真实地址！** 同时硬件顺手核对对齐条件：`0x1000` 恰好是 4 的倍数，满足 32 位字的自然对齐要求，没有触发对齐异常。下一步，必须先过地址翻译这一关！

## 第 5 站：访存（MEM）——D-TLB 翻译 + L1 未命中惊动整座内存金字塔

带着虚拟地址 `0x1000`，第一条 `lw` 跨进 MEM 阶段，连闯两道大关：

1. **地址翻译关**：虚拟页号送入专门服务数据访存的**数据地址翻译快表**（**D-TLB**）。按设定映射有效且可读，D-TLB 迅速吐出物理页框号（PPN），与翻译前后不变的 12 位页内偏移拼成完整物理地址；
2. **数据查找关**：物理地址按「标记（tag）+ 组索引（set index）+ 块内偏移（block offset）」切开，查 **L1 数据缓存（L1 D-Cache）**。按现场设定，数据块此刻尚未缓存——**砰！触发 L1 数据缓存未命中！**

瞬间，整座存储层次被唤醒了：

- 缓存控制器在未决请求缓冲（MSHR）里登记一条临时追踪记录，防止遗忘这笔正在路上的请求；
- 请求依次扑空 L2 和末级缓存（LLC），一路抵达芯片边缘的**内存控制器**（memory controller）；
- 内存控制器选中目标 DRAM 通道和 bank，打开包含 `a`、`b`、`c` 的那一整行进 DRAM **行缓冲**，把对齐后的整条 **64 字节缓存行**（覆盖 `0x1000` 到 `0x103F`！）一口气沿数据总线送回 L3 → L2 → L1 D-Cache；
- 最后，L1 按块内偏移 `0` 从这 64 字节里精准挑出开头的 4 个字节——整数 `20`！

这一趟来回轻轻松松吃掉了几十到上百个时钟周期，远比 1 拍的 ALU 加法漫长得多！在简单按序流水线里，整个前端与后续指令只能暂停冻结干等；而在现代高性能处理器里，缓存往往采用**非阻塞缓存**（non-blocking cache）设计，允许在这笔未命中在途等待期间，继续放行后面不依赖 `x5` 的独立指令先行推进。

## 第 6 站：第一条 `lw` 写回，第二条 `lw` 坐享「空间局部性」红利

数据 `20` 回到核心，控制器核实前面所有阶段——取指、对齐、D-TLB 权限与内存读取——均无异常，这才在时钟上升沿拉高 `RegWrite`，把 `20` 正式写入 `x5`！这完美兑现了[第 5 章的精确异常契约](../chapter_04_cpu/control_unit.md)。

紧接着，第二条 `lw x6, 4(x10)` 走到了 MEM 阶段，算出的虚拟地址是 `0x1004`。惊喜的一幕上演了：

- `0x1004` 和 `0x1000` 稳稳落在**同一张 4 KiB 虚拟页**里 → **D-TLB 直接命中**，零页表遍历！
- 翻译后的物理地址恰好紧挨在刚才那条 **64 字节缓存行**的第 4–7 字节处 → **L1 D-Cache 直接命中**！

第一条 `lw` 辛苦等了上百拍搬回来的整条 64 字节缓存行，让紧跟着的 `b` 仅仅花了 3–4 拍（约 1 纳秒）就秒速落袋——这正是第 7 章**空间局部性**在真实流水线里交出的最漂亮成绩单！

## 第 7 站：`add` 撞上 `load-use` 停顿与转发

现在轮到第三条指令 `add x7, x5, x6` 上场了。它同时依赖前两条 `lw` 产出的 `x5` 和 `x6`：

- 等 `add` 走到 EX 阶段时，第一条 `lw` 早已写回 `x5 = 20`，顺畅无阻；
- 可第二条 `lw` 紧贴在 `add` 前头，它的结果 `22` 要到 MEM 阶段末尾才从 L1 出来！这就正好踩中了[第 6 章的读取后立即使用（load-use）数据冒险](../chapter_05_pipeline/pipeline_hazards.md)！

冒险检测单元果断往流水线里塞进 **1 颗气泡**让 `add` 原地等 1 拍；紧接着在下一拍，`MEM/WB` 流水寄存器里热腾腾的 `22` 经由**转发通路**抄近路直递 ALU 入口，根本不必等 `lw` 写回寄存器堆！

ALU 里的 32 位补码加法器瞬间传播进位，算出：

$$
R[x7] = 20 + 22 = 42.
$$

顺带记一笔 ISA 细节：在 RV32I 里，整数加法严格执行模 $2^{32}$ 补码运算，哪怕结果超出有符号范围也**不会**触发算术异常，只默默保留低 32 位；而像 Python 这样的高级语言或某些其他 ISA 则会规定完全不同的溢出语义。

## 第 8 站：`sw` 集齐地址与数据，写回缓存标为「脏行」

最后一条指令 `sw x7, 8(x10)` 登场。正如开场问答点出的，它必须两手准备：

- 一手拿 `x10` 加立即数 `8`，在 EX 阶段算出目标虚拟地址 `0x1008`；
- 另一手拿 `x7` 的值 `42`——根本不用等 `add` 慢吞吞走到 WB 写进寄存器堆，硬件通过专设的 **store-data 转发通路**直接把刚算好的 `42` 递给 `sw`！

走到 MEM 阶段，`0x1008` 与前两条一样落在同一虚拟页、同一条 64 字节缓存行里——D-TLB 命中、核验「可写（W）」权限通过、L1 D-Cache 再次精准命中！采用[写回 + 写分配策略](../chapter_06_memory/hierarchy_cache.md)的 L1 缓存把 `42` 写入该行偏移 `8` 处，并顺手把这条缓存行的**脏位（dirty bit）置为 `1`**。请注意：此时此刻，主板 DRAM 内存条上对应地址里存的很可能还是旧值！ISA 并不要求 DRAM 立刻同步变成 `42`，它只承诺「以后任何合法的 `load` 来读 `0x1008`，都必须读到 `42`」。

## 第 9 站：写入缓冲区（Store Buffer）与多核可见性

在真实的现代高性能处理器里，`sw` 甚至不会死等 L1 缓存写完才放行后面的指令。为了不让写内存拖住流水线，硬件在核心与 L1 缓存之间安放了一个小小的临时队列——**写入缓冲区**（store buffer）：

1. 当 `sw` 算出地址 `0x1008` 和数据 `42`、并通过了权限检查后，先把 `(0x1008, 42)` 这条待写记录写进写入缓冲区，核心就可以轻装上阵继续执行后面的独立指令；
2. 直到 `sw` 在重排序缓冲区（ROB）队头正式按序**提交**（确认前面所有分支都猜对了、没有任何异常会撤销它），写入缓冲区才真正获准把 `42` 排入 L1 D-Cache！
3. 这中间藏着一个极其精妙的细节：假如在 `42` 还躺在写入缓冲区、尚未排入 L1 的那几拍里，**本核自己**紧接着又执行了一条 `lw x8, 8(x10)` 去读刚写下去的 `c`，怎么办？如果只傻傻去查 L1 缓存，就会读到过时的旧值！因此硬件必须同时检索写入缓冲区，直接把新鲜的 `42` 转发给本核的后续 `load`（称为 store-to-load forwarding）！
4. 在多核机器上，当这条 `sw` 真正排入 L1 缓存时，还要走完第 10 章的 MESI 缓存一致性协议：向其他核心广播写失效、把整条缓存行升格为独占的 `Modified` 状态；至于其他核心何时能按序观察到这笔写入，则严格受处理器内存一致性模型与内存屏障约束。

## 第 10 站：退后一步，看见硅片底层的交响乐

把镜头拉回最底层的硅片物理世界：刚才所有华丽的动作，最终都落在第 3 章的基本元件上——通用寄存器和流水寄存器里每一个比特都是 D 触发器；ALU 的 `20 + 22` 是几百个逻辑门在几十皮秒内飞速传播进位；L1 的 8 路标记比对是八组硬件比较器同时点亮；每一根写使能都在时钟上升沿那一声令下整齐翻转；而晶体管的电容、供电电压 $V$ 和金属连线延迟，则在物理最底层默默划定了最高主频和功耗墙。

而这正是学习计算机组成原理最迷人的价值：**我们不必拿显微镜去数几十亿颗晶体管，却能凭借这套严密的分层模型，清清楚楚地看见每一步状态怎样交接——从最初 `x10 = 0x1000` 到最终 `Mem[0x1008] = 42`，每一纳秒的进展与等待都有迹可循！**

## 别忘了暗礁：所有可能触发的失败路径

上面走完的是阳光明媚的「幸运路径」，但任何一台可靠的处理器都必须把所有「失败暗礁」一起纳入设计：

- `x10` 指向了未对齐地址（如 `0x1001`）或无权访问的内核地址 → 触发对齐异常或段错误；
- D-TLB 未命中 → 硬件页表遍历器走多级页表；若 PTE 有效位为 0 → 触发缺页异常陷入操作系统调页；
- L1 未命中回填新行时，目标组里所有路都满，选中的牺牲行恰好是脏行 → 必须先把旧脏行写回下层腾地儿；
- 多核下其他核心正独占着这条缓存行 → 必须等待一致性协议把所有权转移过来；
- 服务器内存条的宇宙射线翻转了某个比特 → 内存控制器靠额外的校验比特——**纠错码**（Error-Correcting Code，简称 **ECC**）——实时检测并自动纠正单比特错误，若发现无法修复的双比特错误则上报机器检查异常。

无论哪一条暗礁中途爆炸，**精确异常**都要求处理器像手术刀一样利落收场：出错指令之前的修改全部安稳生效，出错指令自己以及之后抢跑的投机指令统统作废、零痕迹。

至此，我们用一行 `c = a + b` 把全书所有硬件机制的功能路径完整串联了一遍。但实战里最磨人的往往不是「算错了」，而是「算得完全正确，却慢得让人抓狂」——当一段代码跑慢了，怎样像经验老到的急诊医生一样，不靠拍脑袋瞎猜，而是用实测数据一步步锁定真正卡死整台机器的病灶？下一节，我们进入[跨层性能诊断与设计权衡](bottleneck_diagnosis.md)。
