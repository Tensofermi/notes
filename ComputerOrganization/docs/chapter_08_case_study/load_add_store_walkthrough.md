# 一条 load/add/store 如何贯穿机器

## 先写下这三条指令应该得到的结果

第一次读综合案例，可以先回看[一条读指令的数据通路](../chapter_04_cpu/datapath_instruction_cycle.md)和[地址翻译与缓存的三个等待点](../chapter_06_memory/virtual_memory_hardware.md)。

设内存地址 100 存着 7，寄存器 `x6` 存着 3。顺序做「读地址 100 到 `x5`」「把 `x5` 和 `x6` 相加到 `x7`」「把 `x7` 写到地址 104」，最后要得到 `x5 = 7`、`x7 = 10`，地址 104 的值为 10。下面的完整实例数字不同，追踪时同样可以先写最终状态，再检查每一步是否为下一步准备好了值。

??? question "为什么 store 要同时知道地址和数据？"

    地址指明更新哪里，数据决定写入什么。两者可能来自不同寄存器，而且数据也可能仍在等待前一条指令产生。

## 场景与初始状态

源程序为：

```c
c = a + b;
```

编译器约定 `x10` 指向三个连续 32 位整数，生成：

```asm
lw  x5, 0(x10)
lw  x6, 4(x10)
add x7, x5, x6
sw  x7, 8(x10)
```

假设：

```text
使用 RISC-V 的 32 位基础整数指令（RV32I），通用寄存器每个存 32 位
x10 = 0x1000
a = 20, b = 22
页表映射有效
指令已在最快查到的一级指令缓存（L1 I-cache）
目标数据块还未缓存在处理器附近，但页面已在主存
```

最终可观察目标是 `Mem[0x1008] = 42`。下面所有预测、停顿和缓冲都必须保持这个架构结果。

## 1. 从源代码到机器码

编译器先决定用哪些指令、把哪些值放进寄存器；汇编器把 `lw` 这样的指令名变成处理器实际读取的位串。若程序分几个文件编译，**链接器（linker）**会把各部分拼起来并确定它们之间的地址；运行时，系统的**装载器（loader）**为进程安排能访问的虚拟地址和初始内容。

此时 `lw` 的语义已经固定，但“有几级流水、cache 多大、是否乱序”仍未决定，这正是 ISA 与微体系结构的边界。

## 2. 取第一条 `lw`

程序计数器（PC）给出虚拟指令地址。负责读指令的部件先查**指令翻译缓存（指令 TLB，I-TLB）**，得到物理页框号，再读一级指令缓存（L1 I-cache）。因为假设命中，指令位进入译码器，PC 同时准备顺序增加 4。

若有分支预测器，它此时提供后续取指方向；本例没有分支，前端连续取四条指令。

## 3. 译码与读寄存器

译码器识别 load 格式，提取 `rs1=x10`、`rd=x5` 和立即数 0。寄存器堆读出：

$$
R[x10]=0x1000.
$$

控制器设置 ALU 输入选择为立即数、存储读有效、写回来源为内存、寄存器写有效。写使能还不会立刻提交，它随指令沿流水线向后传递。

## 4. EX 计算虚拟有效地址

在执行（EX）阶段，算术逻辑单元（ALU）把寄存器里的基地址和指令写明的偏移相加。式中的 `signext` 表示先把较短的有符号偏移扩展到寄存器宽度，保留原值。

$$
VA=R[x10]+\operatorname{signext}(0)=0x1000.
$$

这一步只得到虚拟地址，不是最终的物理位置——cache 和主存只认物理地址。还要检查对齐：32 位 load 通常要求地址是 4 的倍数。翻译和取数据，是下一步的两道关。

## 5. 地址翻译与 L1 miss

查**数据地址翻译缓存（数据 TLB，D-TLB）**时，输入虚拟页号，取回物理页框号和权限，再与页内偏移组合。**一级数据缓存（L1 D-cache）**用组索引选组，用标记（tag）找这组内有没有要读的数据块。这里假设未命中，读取会继续往下走。

1. 用一条临时记录跟踪这个尚未返回数据的请求。
2. 请求发往 L2、末级 cache（最靠下的那一级缓存），最终到**内存控制器（memory controller）**；
3. 主存打开相应存储阵列中的目标行，并把请求的整块数据返回给缓存。
4. cache line 填入 L1，目标 4 B 由块内偏移选出。

第一次 miss 的等待可能远长于一次 ALU 加法。有的缓存会继续为其他不依赖这份数据的指令提供服务，称为**非阻塞缓存（non-blocking cache）**；简单的顺序处理器则可能先暂停相关阶段等结果。

## 6. 第一条 load 写回

数据 20 沿写回通路进入 `x5`。[精确异常](../chapter_04_cpu/control_unit.md)的要求是：软件看到的错误发生在明确的指令边界。只有确认翻译、权限和访存都成功后，寄存器更新才算入可见结果。

第二条 `lw` 访问 `0x1004`。因为与 `a` 常位于同一 cache line，第一次 miss 带回的相邻数据让它很可能 L1 命中。这就是空间局部性带来的实际收益。

## 7. `add` 的数据相关

`add x7, x5, x6` 依赖两条 load。若第二条 load 的数据直到 MEM 末尾才可用，紧随其后的 `add` 就可能碰上[读取后立即使用（load-use）](../chapter_05_pipeline/pipeline_hazards.md)造成的等待。`add` 要等这一拍，等值准备好后可绕过寄存器，从中间结果直接送到 ALU，这叫转发。

ALU 最终计算：

$$
R[x7]=20+22=42.
$$

补码加法器执行模 $2^{32}$ 运算。本例没有溢出；在 RV32I 中，整数 `add` 即使溢出也不触发算术异常，只保留结果的低 32 位。其他 ISA 或语言运行时可以规定不同的溢出处理。

## 8. `sw` 的地址与数据路径

store 同时需要：

- `x10` 与立即数 8 计算地址 `0x1008`；
- `x7` 提供数据 42。

`x7` 可通过 store-data 转发直接送来，不必等它先写回再读。地址翻译检查写权限，D-cache 定位目标行。

若缓存采用[写回与写分配](../chapter_06_memory/hierarchy_cache.md)，遇到有需要时会先把整块取进缓存。更新后的缓存行标为已修改（dirty），下层内存可能暂时仍是旧值。ISA 关注的是之后合法 load 应观察到正确结果，而不是要求 DRAM 立刻写成 42。

## 9. store buffer 与提交

高性能处理器可以先把「地址 `0x1008`，待写值 42」存入**写入缓冲区（store buffer）**。这像一条等待写入缓存的记录，处理器能先准备好它，再接着做能并行的工作。只有检查完成且按序确认指令后，这条记录才可以更新缓存并让其他核心观察到。后续对同地址的 load 必须从尚未排空的 store buffer 转发最新值，避免读到旧的 cache 数据。

在多核系统中，store 获得该 cache 行所有权并使其他核心副本失效。何时对其他核心可见还受内存一致性模型约束。

## 10. 从晶体管角度看

上述每个寄存器位由存储单元保持；ALU 加法由门网络传播进位；tag 比较由并行比较器完成；控制信号驱动多路选择器和写使能；时钟边沿让流水寄存器同步采样。更底层的晶体管尺寸、电压和连线延迟共同限制频率与功耗。

组成原理的价值就在这里：不必逐管分析，也能知道某次等待发生在 ALU、翻译、cache、DRAM 还是一致性协议。开头的预测也该兑现了：`x5 = 7` 的场景换成 20 与 22，最终 `Mem[0x1008] = 42`，每一步的值都来自上一步准备好的状态。

## 失败路径

这组指令还可能遇到：

- 非法或未对齐地址；
- TLB miss 或 page fault；
- cache 替换需要写回 dirty 行；
- 多核所有权请求等待；
- 内存用额外的校验位检测到错误。用于发现并修复某些位错误的编码叫**纠错码（ECC）**。

精确异常要求更早指令已完成，出错指令和更晚指令不留下架构副作用。正常路径和失败路径必须共同设计。

三条指令的功能路径走完了。但「正确」之外还有「快」：如果这段程序慢，慢在哪一站？下一节[跨层性能诊断](bottleneck_diagnosis.md)给出按段排查的方法。
