# 综合练习：一批数据怎样从磁盘进入 GPU

## 把 GPU 换快一倍，这批图像训练真的会变快吗？

设想你正在跑一个经典的计算机视觉训练任务。每一批（batch）训练图像要从固态硬盘出发，一路过关斩将冲进 GPU 算完前向和反向传播，整条链路分成四站，单批耗时清清楚楚：

1. **读文件（NVMe 磁盘 → 主存）**：`12 ms`
2. **CPU 解码并组批（把压缩 JPEG 解压成浮点像素张量）**：`30 ms`
3. **主机到设备传输（主存 → PCIe → GPU 显存）**：`8 ms`
4. **GPU 计算（前向 + 反向计算核）**：`20 ms`

如果四站老老实实串行接力，算完第 1 批图像足足要花 $12 + 30 + 8 + 20 = 70\text{ ms}$。

现在把第 6 章的流水线魔法搬到整台服务器上：只要第 1 批文件刚读完、交棒给 CPU 解码，磁盘立刻转身去读第 2 批文件；等第 1 批开始经 PCIe 往显存搬运、甚至开始在 GPU 里开算时，CPU 已经在马不停蹄地解码第 2 批了！

停下来先在心里默算两道题：

- 流水线全速运转后，**第 1 批图像从头到尾的耗时（首批延迟）**会不会缩短？**连续交付两批的时间间隔（稳态吞吐）**又能压低到多少毫秒？
- 此时老板大笔一挥，花重金把 GPU 换成了算力快一倍的旗舰卡，把第 4 站 GPU 计算耗时从 `20 ms` 硬生生砍半到了 `10 ms`——猜猜看，在流水线稳态下，整套训练的每秒处理批次数能提升多少？

别急着拍板，先把整条数据路径画透、再把前三批的时间线亲手排开，答案会震撼得让你过目难忘！

??? question "既然想让四站重叠，如果把磁盘和解码之间、解码和 GPU 之间的预取缓冲区无限加大，稳态吞吐能突破限制变得更快吗？"

    不能。加大缓冲区好比在车间工位之间多摆几排传送架：它非常擅长吸收偶尔的抖动（例如某几张超高分辨率图片解码突然慢了一点，或者 SSD 刚好碰上后台垃圾回收），防止上下游互相饿死；可如果最慢的那一站（这里是 `30 ms` 的 CPU 解码）本来就已经 100% 满负荷连轴转，多摆再多架子也没法让 CPU 把每批解码从 `30 ms` 变短一毫秒！更糟的是，过大的缓冲区还会疯狂吞噬宝贵的 CPU 主存，甚至挤掉操作系统的页缓存，反而引发更多慢速冷读。

**读完本节你能做到**：从磁盘扇区到 GPU 计算核完整画出一条现代 AI 训练数据路径，分清控制流与数据流、冷读与热读、异步提交测量陷阱，并为每一站写出可动手证伪的瓶颈假设。

## 把「发号施令的控制动作」和「真刀真枪的数据路径」剥开看

看清一整批图像如何在整台服务器里旅行，最清爽的画法是把**数据实体在哪里流转**和**谁在幕后发号施令**上下对照着画：

```text
数据实体流向:
  NVMe 闪存颗粒 ──(DMA/PCIe)──▶ CPU 主存页缓存 ──(CPU 解码/组批)──▶ 主存锁页缓冲区 ──(DMA/PCIe)──▶ GPU 显存 ──▶ GPU 计算核
                                     ▲                                    ▲                            ▲
幕后控制推手:               文件系统 + 块 I/O 提交队列              用户态 DataLoader 多线程        GPU 运行时异步流提交
```

沿着这条横跨硬件与操作系统的长龙，有四个关键环节绝不能看走眼：

1. **块 I/O 与冷热读之分**：当程序请求读取图像文件时，操作系统先翻主存里的**页缓存**。如果这份数据集在上一轮 epoch 刚读过、而且整套数据小到能全部留在空闲主存里，读取直接命中页缓存——这叫**热读**（hot read），连 NVMe 盘的门都不用敲！可如果数据集动辄几 TB 装不下内存，或者这是开跑后的第一轮，页缓存扑空，操作系统必须发起底层的**块 I/O**（block I/O），按存储设备块号穿过 NVMe 提交队列和 PCIe 从真实闪存把字节搬上来——这叫**冷读**（cold read）。测性能时绝不能把热读当成冷读来汇报！
2. **CPU 解码与主存带宽**：磁盘里存的是高压缩比的 JPEG/WebP 字节流，GPU 没法直接拿来做矩阵乘法。用户态的数据加载器（DataLoader）派生多条工作线程，把压缩字节解压成规整的 RGB 像素、裁剪增强，再拼成一整块连续的大张量写回主存缓冲区。这一步不仅吃 CPU 算力，还大量消耗主存读写带宽。
3. **运行时发起主机到设备传输**：负责替应用程序调度 GPU 的底层软件框架——**运行时**（runtime，如 CUDA Runtime）——把装满像素张量的主存区域（通常需锁页 pinned memory 防止操作系统把页面换出导致物理地址变化）交给 GPU 的 DMA 拷贝引擎，经由 PCIe 通道直灌进 GPU 显存。
4. **计算核上阵**：数据稳稳落入显存后，运行时向 GPU 命令队列发射一连串前向、反向和优化器更新**计算核**，成千上万条线程束轰鸣启动，吃进显存里的批次张量和模型权重，算出新梯度！

## 亲手画一张四级流水线时间线

现在回到开头的数字，把四站的耗时和排查抓手摆成一张作战图：

| 流水站 | 单批耗时 | 如果卡在这一站，该看哪项证据？ |
| --- | ---: | --- |
| **第 1 站：读文件** | `12 ms` | 区分冷读与热读；核对 NVMe 队列深度、单盘吞吐与共享 PCIe 链路 |
| **第 2 站：CPU 解码与组批** | `30 ms` | 检查 DataLoader 工作线程的 CPU 占用、线程就绪排队与 NUMA 跨节点访存 |
| **第 3 站：主机 → GPU 传输** | `8 ms` | 核对 PCIe 实际拷贝速率、是否使用锁页内存、有无与网卡/SSD 争用交换机 |
| **第 4 站：GPU 计算** | `20 ms` | 查看计算核纯执行时间，更要盯紧**相邻计算核之间的空白间隙**（是否在干等数据） |

把前三批数据在理想四级流水线（假设各站互不争抢同一瓶颈资源）上的推进过程画到时间轴上（单位 `ms`）：

```text
时间(ms):   0    12        42  50        70  72  80        100 102 110       130
读文件:     [批1 ]          [批2 ]            [批3 ]
CPU 解码:        [   批 1 (30ms)   ][   批 2 (30ms)   ][   批 3 (30ms)   ]
PCIe 拷贝:                         [批1]             [批2]             [批3]
GPU 计算:                              [  批 1 (20ms)  ]     [  批 2 (20ms)  ]     [  批 3 (20ms)  ]
                                                       ▲                     ▲                     ▲
                                                  批1完工(70ms)         批2完工(100ms)        批3完工(130ms)
```

盯着底部的三个完工箭头，所有悬念瞬间水落石出：

- **首批延迟一毫秒也没少**：第 1 批图像依然老老实实穿过了全部四站，耗时 $12 + 30 + 8 + 20 = 70\text{ ms}$；
- **稳态吞吐大幅跃升**：从第 1 批完工（`70 ms`）到第 2 批完工（`100 ms`），再到第 3 批完工（`130 ms`），稳态批次间隔从串行的 `70 ms` 骤降到了 **`30 ms`**——恰好等于最慢那一站（**CPU 解码**）的耗时！
- **换快一倍的 GPU 为什么血亏？** 看一看最下面那行「GPU 计算」：在每 `30 ms` 的稳态节拍里，原本 `20 ms` 的 GPU 已经有 `10 ms` 在空转晒太阳了！如果此时花大价钱把 GPU 计算缩到 `10 ms`，**稳态批次间隔依然纹丝不动地卡死在 `30 ms`（整体加速比 = $1.00\times$！）**，唯一的变化是昂贵的旗舰 GPU 从闲着 33% 变成了闲着整整 67%！

真正的破局药方再清楚不过：**把火力集中到 `30 ms` 的 CPU 解码站！** 增加 DataLoader 解码进程数、换用 SIMD 加速解码库、把 JPEG 解码直接卸载到 GPU 自带的硬件图像解码引擎（如 NVDEC / DALI），或者干脆提前离线转存成免解码格式——直到把解码压低到 `20 ms` 以下，GPU 的 `20 ms` 计算才会重新夺回主导权，成为真正值得吃满的主角！

当然，现实总比理想模型多几分波折：如果读文件和主存拷贝共用同一条 PCIe 上行链路，或者解码线程和主内存带宽激烈互抢，实际稳态间隔还会略高于理想下界 `30 ms`，必须用真机剖析时间线核对。

## 四项可立刻上手的实战小实验

纸上算得再溜，不如亲手跑出一次曲线。即便手边只有一台普通笔记本，你也能亲身验证整套诊断思想：

1. **手画对照时间线**：在草稿纸上分别画出前三批在「完全串行」和「四级流水重叠」下的甘特图，标出第 1 批完成时刻和稳态批次间隔，再试着把 CPU 解码改成 `15 ms`，看看新的主导瓶颈跳到了哪一站。
2. **用普通电脑直击冷热读差异**：写一段简短的脚本，循环测三段耗时——「从磁盘读一个几百 MB 的文件」「在 CPU 上对数据做解析转换」「跑一段矩阵或向量计算」。紧接着不清空页缓存再跑第二遍，亲眼看看「读文件」这一站从冷读变成热读后耗时的断崖式变化（注意严谨记录现象，绝不闭眼瞎猜数据具体命中了哪一级缓存）。
3. **避开 GPU 计时的头号坑——异步提交**：如果你手边有 GPU，分别测量主机到设备拷贝和计算核的耗时，务必高度警惕**异步提交**（asynchronous submission）！现代 GPU 运行时为了让 CPU 不必傻等，在 CPU 调用 `launch_kernel()` 时只是把命令飞快塞进驱动队列就立刻返回了——此时 GPU 甚至还没开始算第一个像素！如果你天真地在 CPU 侧拿普通时钟包住 `launch_kernel()`，量出来的往往只有短短 5 微秒的「下发命令耗时」而不是真实的 `20 ms` 计算耗时！要测出真实耗时，必须在结尾显式调用设备同步屏障等待 GPU 真正完工，或者直接在 GPU 流里插入硬件事件时间戳（GPU Event）来记录真实的起止时刻。
4. **多任务干扰归因演练**：设想此时同一台服务器上又启动了第二个训练任务，与当前任务共用了同一块 NVMe 固态硬盘或同一张高速网卡。请列出四项互不重叠的实测指标，分别用来一剑区分争用究竟爆发在「NVMe 磁盘排队」「CPU 解码核抢占」「共享 PCIe 传输通道」还是「外部网络带宽」。

当单机装不下更大的模型、数据必须跨过多台服务器在集群间高速奔涌时，这条路径就会自然延伸到另外两门核心姊妹课程：跨机数据包如何穿过交换机与协议栈、拥塞如何控制，可以继续精读<a href="../../ComputerNetworks/index.html">计算机网络</a>；操作系统内核如何调度成百上千条线程、管理页缓存、处理缺页与故障恢复，可以对照精读<a href="../../OperatingSystems/index.html">操作系统</a>。
