# 计算机组成原理

在编辑器里写下一行 `c = a + b`，前后不过一秒钟。对程序来说，它只是一次平平无奇的加法；可对静静躺在主板上的硅片来说，这一行代码却要掀起一整套精密协作：芯片必须先把 `a` 和 `b` 从内存里找到、搬运到离运算电路最近的临时位置，再让成千上万个微小的电子开关在短短十亿分之一秒内翻转出和值，最后把结果妥帖地送回内存，好让后面的代码找得到它。

这一行代码从写出来到真正算完，中间究竟发生了什么？这门课正是从这些触手可及的小问题出发，一层一层揭开计算机的黑箱：从 0 和 1 怎样编码数字与文字，到逻辑门怎样搭出能记住状态的电路，再到一条指令怎样在处理器里步步推进，直到内存、磁盘、网卡和图形处理器怎样在整台机器里默契配合。

## 为什么写软件的人也需要往下看一层？

设想这样一个让许多程序员都措手不及的场景：你写了两层循环，把一个很大的二维数组里的所有元素加起来。后来，你只是把外层循环和内层循环的顺序对调了一下。从数学上看，加法满足交换律，两段代码访问的元素一个不多、一个不少，算出来的结果分毫不差——可一跑基准测试，其中一个版本竟然比另一个版本快上好几倍！

如果你只站在高级语言的视角里打转，这件事几乎无法解释：两段代码做的明明是「同一件事」，凭什么快慢悬殊？

答案藏在硬件的工作方式里。真正负责算术和控制的芯片叫**中央处理器**（Central Processing Unit，简称 **CPU**），它的运算速度极快，而存放程序和大量数据的主内存却远远跟不上它的脚步。为了不让 CPU 整天干等内存，硬件设计者在 CPU 身边安排了一小块容量不大、但读写极快的近身存储，这就是**缓存**（cache）。每次 CPU 要读一个数据，都会先在缓存里找：如果恰好就在手边，片刻就能取出；如果扑了个空，就只能停下来去更远、更慢的下一级存储里搬运，这种扑空就叫**缓存未命中**（cache miss）。你调换循环顺序时，虽然没有改变计算量，却彻底改变了数据恰好留在缓存里的比例——程序于是从「顺手拿取」变成了「来回跑腿」。

这正是学习计算机组成原理的最大收获：许多在软件层看起来像玄学一样的现象——为什么换个循环顺序就快几倍、为什么加了锁程序反而不如单线程、为什么显存带宽比算力更容易拖垮训练任务——只要往下看一两层，就会变成清清楚楚的物理事实。

为了把整套知识拧成一股绳，我们会用一个极其简单、却贯穿全站的例子作为向导：

```c
c = a + b;
```

当 `a` 和 `b` 都住在内存里时，CPU 并不能直接把内存里的两个数拿来相加。它通常先用两条读取指令（`load`），把两个数搬进芯片内部少量、速度最快、可以直接参与运算的「工作台」——**寄存器**（register）；再用一条加法指令（`add`）把两个寄存器里的数加起来；最后用一条写入指令（`store`），把结果放回内存。全书末尾的[一条 load/add/store 如何贯穿机器](chapter_08_case_study/load_add_store_walkthrough.md)，会把这短短四步在整台机器里激起的每一圈涟漪完整走查一遍。

如果你是第一次接触这门课，不妨把下面三个具体算例当作路标：先跟着[数据通路与指令周期](chapter_04_cpu/datapath_instruction_cycle.md)里的一条读取指令，分清「寄存器里保存的地址」和「按这个地址从内存里取出的值」；接着通过[局部性、Cache 与主存](chapter_06_memory/hierarchy_cache.md)里的三次相邻读取，亲眼看看缓存为什么会自动帮你省下大半趟跑腿；最后再走完[页表、TLB 和一次访存](chapter_06_memory/virtual_memory_hardware.md)里「同一个地址的三种命运」。走过这三座桥，再回头看全站末尾的综合案例，整台计算机就会在你脑海里立起来。

## 全站知识地图

一台现代计算机包含几十亿甚至上百亿个晶体管。如果把所有细节一股脑摊在桌上，没人能同时装进脑子里。工程师驯服复杂性的办法是**分层**：把整台机器切成几个职责清晰的层次，每一层只向正上方给出明确、稳定的承诺，至于底层用什么电路和技巧来兑现承诺，则留给本层内部自由发挥。

| 层次 | 这一层要回答的核心问题 | 对上一层提供什么 |
| --- | --- | --- |
| 信息表示与数字逻辑 | 0 和 1 怎样表达数与文字？电路怎样做运算、怎样记住状态？ | 可靠的二进制计算与存储部件 |
| 指令集架构（ISA） | 软件和硬件之间约定哪些指令、哪些寄存器和内存模型？ | 稳定、可跨代沿用的机器接口 |
| 微体系结构 | 处理器内部怎样用数据通路、控制器和流水线把指令执行出来？ | 语义相同、但速度与功耗各异的芯片实现 |
| 存储与输入输出（I/O） | 怎样在速度与容量之间架起存储金字塔？CPU 怎样和磁盘、网卡交换数据？ | 看起来既大又快的内存，以及可编程的设备接口 |
| 并行系统与整机拓扑 | 多颗核心、图形处理器和高速互联怎样协作，又不把数据弄乱？ | 更高的吞吐量与可扩展的算力平台 |

这张表最适合自底向上读。在整张地图的腰部，立着一个全站最关键的界碑——**指令集架构**（Instruction Set Architecture，简称 **ISA**）。它就像一份写在软硬件之间的正式契约：往上看，编译器和操作系统只需要面向这份契约生成代码，不必操心底下的晶体管怎么排列；往下看，芯片架构师只要严守这份契约对外承诺的结果，就可以放手在内部更换电路、加深流水线或扩大缓存。后面每一章，我们都会反复回到这道分界线。

## 建议学习路线

按导航栏的 11 章顺序从头读到尾是最顺滑的路线。不过，组成原理的细节很容易越看越密，为了不让知识散成一堆孤立的器件名词，第一次学习时建议始终攥紧三条主线：

1. **状态存在哪里？**（此刻的数据在寄存器里、缓存里、主存里，还是在磁盘和显存里？）
2. **数据往哪里走？**（它沿着哪条通路、经过哪些部件被搬运和加工？）
3. **谁决定下一步？**（是哪条控制信号、哪条指令或哪次硬件事件，决定了下一拍做什么？）

每当遇到一个陌生机制，顺手拿这三条主线去套一下，它的位置和作用立刻就会清晰起来。全站 11 章大致分为三个递进阶段：

| 阶段 | 覆盖章节与核心内容 | 学完后的检验方式 |
| --- | --- | --- |
| 第 1–4 章 | 抽象层次与历史演进、信息表示与浮点数、数字逻辑、指令集与[函数调用约定](chapter_03_isa/calling_convention.md) | 能手工画出一条简单汇编执行前后寄存器与栈的变化，读懂最小汇编程序 |
| 第 5–8 章 | CPU 数据通路与控制、流水线与性能公式、缓存与局部性、[虚拟内存的硬件支持](chapter_06_memory/virtual_memory_hardware.md) | 能一步步跟踪一条 `load` 指令，解释流水线停顿以及同一地址的三种访存结果 |
| 第 9–11 章 | [设备怎样往内存搬数据](chapter_07_io_parallel/io_interrupt_dma_storage.md)、多核一致性、[GPU 与服务器拓扑](chapter_07_io_parallel/gpu_and_server_topology.md)与综合案例 | 能画出[一批数据从磁盘进入 GPU](chapter_08_case_study/storage_to_gpu.md) 的完整数据路径，并定位限制速度的瓶颈环节 |

读每一节的例子时，别急着往下翻答案——先在纸上或心里写下自己的预测，再对照推导过程或[综合自测](self_assessment.md)验证。等读到第 8 章的页表与地址翻译时，还可以和<a href="../OperatingSystems/chapter_04_memory/01_address_space_paging.html">操作系统的分页</a>对照着看，同一份虚拟地址在硬件视角和内核视角下会拼成完整拼图。如果想进一步动手实践或补看图解，[Berkeley CS 61C](https://notes.cs61c.org/) 与 [Nand to Tetris](https://www.nand2tetris.org/course) 都是极佳的配套资源。

## 示例约定与阅读边界

为了不被陈旧指令集的历史包袱分散注意力，全站的核心汇编与硬件示例统一采用 **RISC-V**——一套公开、规整、免费开放的指令集规范。它的指令编码极其干净，既适合教学时一眼看穿本质，也已经在工业界的嵌入式芯片、处理器和加速器中广泛落地。

随着现代计算越来越依赖异构硬件，后几章除了剖析经典的 CPU 与主存之外，还会把视野延伸到高速外设通道、**图形处理器**（Graphics Processing Unit，简称 **GPU**）自带的独立显存，以及多机多卡的服务器互联拓扑。不过也要记住：教材里的模型总是为了抓住核心矛盾而做的提炼；真到了调优某台具体服务器时，还是要先查清它的真实拓扑与硬件配置，再用实测数据去检验模型里的每一条推论。
