# 操作系统的角色、结构与启动

## 电脑开机后，谁先把程序放进内存？

试着想象一下按下电源键那一刻的机箱内部：刚刚通电的内存条里是一片空白（或者满是毫无意义的随机电信号），你费心装好的操作系统，此刻还老老实实躺在硬盘里一动不动。这就冒出了一个有点绕脑筋的困境——操作系统自己也是程序，要运行就得先被装进内存；可机器里还没跑操作系统，谁来认识硬盘、谁来把操作系统搬进内存呢？

答案是一场环环相扣的接力赛，而不是靠某个神奇部件一步到位。通电复位后，CPU 会死板地去一个硬件预先定死的地址取第一条指令。那里并不是你的硬盘，而是出厂时就焊死在主板芯片里的一小段代码，叫作**固件**（firmware）。固件的本事很有限，不懂复杂的应用程序，但足以给主板、内存和关键外设做个基本体检，然后按照启动顺序挑出一块启动磁盘，把接力棒交给磁盘上负责“找系统、搬系统”的小程序——**引导程序**（bootloader）。引导程序顺着约定好的位置找到磁盘上的内核文件，把它装进内存，再把 CPU 的控制权交出去。直到内核接手、把内存和设备理顺，第一个用户程序才终于被拉起来。你在屏幕上看到熟悉的登录框时，这场接力赛其实已经跑完了前半程最惊险的几棒。

??? question "硬盘里明明躺着完好的内核，为什么开机还是会卡在“找不到启动项”？"

    因为内核自己没法跳进内存，必须依赖前面每一棒顺利交接。只要固件里记录的启动顺序丢了、选错了磁盘、引导分区损坏，或者引导程序在安全策略校验时被拦下，整条接力链就会在内核拿到控制权之前当场断掉。

回头看计算机的发展史，你会发现操作系统最初根本不是为了做出好看的桌面窗口，而是为了心疼那台贵得惊人的机器。上世纪五十年代的大型机每小时机时费高昂，早期做法是人工把穿孔卡片一叠叠喂进机器，一次只跑一个作业；换作业时，昂贵的 CPU 就干晾在旁边什么也不干。为了榨干空闲时间，工程师发明了**批处理系统**，让机器把一摞作业排成队自动连续跑；紧接着大家又发现，哪怕作业连续跑，每当程序去读磁带或等打印机，CPU 照样在发呆——于是**多道程序系统**登场了，内存里同时驻留好几个作业，一个等 I/O，CPU 立马扭头去算另一个；再往后，人机交互成了刚需，**分时系统**干脆把 CPU 切成极短的小段轮流分给大家，让坐在不同终端前的几十个用户都觉得自己独自霸占着整台电脑。

从接力启动到分时共享，这段演化悄悄点出了操作系统一辈子都要面对的根本张力：底层的物理硬件永远是共享且有限的，可跑在上面的每个程序、坐在屏幕前的每个用户，都渴望拥有一个简单、安稳、仿佛为自己独享的运行环境。共享硬件到底会惹出多大的乱子？不妨把操作系统撤掉，直接看一眼失控的现场。

## 没有仲裁者的世界：为什么需要操作系统

假设我们关掉所有操作系统保护，让两段普通程序直接往磁盘控制器发命令：

```text
程序 A：把账本数据写到扇区 100
程序 B：把临时日志写到扇区 100
```

没人居中协调时，最终留在扇区 100 里的可能是 A 的数据、B 的数据，甚至是两份字节交错掺在一起的废品。更糟糕的是，程序 A 不必怀有任何恶意——哪怕只是程序员少写了一个循环终止条件，或者算错了一个内存下标，失控的指令就能顺手把磁盘上的关键结构改写得面目全非，甚至霸占 CPU 让整台机器彻底失联。

要想让许多互不信任的程序和平共处在同一块铁疙瘩上，操作系统必须稳稳扛起三项职责：

1. **抽象（Abstraction）**：把裸露、琐碎、型号千差万别的硬件，包装成干净统一的概念——硬盘上冰冷的扇区号变成按名存取的“文件”，CPU 上不断跳动的寄存器现场变成可生可灭的“进程”，杂乱的物理内存条变成每个程序独享的“虚拟地址空间”。程序员从此不必为换了一块新硬盘就重写代码。
2. **复用（Multiplexing）**：让有限的硬件在时间和空间上被安全地切分共享。CPU 靠时间片轮换实现“时间复用”，内存和磁盘靠分区、分页与块分配实现“空间复用”，设备请求则在队列里有条不紊地排队发车。
3. **保护（Protection）**：给每个程序划出红线，检查每一次越界企图。即便某个程序崩溃或存心捣乱，也能尽量把破坏关在它自己的牢笼里，不连累内核与其他程序。

值得留意的是，“抽象”远不只是为了让程序员写代码更省事，它更是“保护”和“复用”的抓手。正因为应用不能直接操作磁盘扇区，而必须通过 `open` 这样的统一接口按名字请求打开文件，内核才有了插手的机会：在真正碰硬件之前，先沿着目录解析路径、核对访问权限、检查配额，再决定放行还是拒绝。没有抽象这层统一关卡，仲裁也就无从谈起。

## 机制与策略：把“能做什么”和“该怎么选”拆开

拿同一块硬件定时器来说，为什么在讲究跟手交互的桌面系统里，它会每隔几毫秒就打断正在算数的程序去照顾鼠标和窗口，而在跑科学计算的批处理服务器上，却可能让一个计算任务连续跑很久才切换一次？硬件本身并没有变，变的是系统做决定的方式。

操作系统设计里有一条极有生命力的原则，就是把**机制**（mechanism）与**策略**（policy）尽量分开：

- **机制**回答“能不能做到”，它提供底层的基础能力。比如，硬件定时器能按时触发中断把控制权交回内核，内核也能把当前程序的寄存器保存下来换上另一个程序。
- **策略**回答“应该怎么选”，它基于工作负载和业务目标做权衡。比如，究竟该给谁分配更高的优先级、时间片定 2 毫秒还是 20 毫秒、什么时候该把忙不过来的任务搬到另一颗空闲核心上。

为什么要费劲把两者拆开？因为一旦把具体策略写死在底层机制里，系统就会立刻僵化——今天针对单核桌面调好的规则，明天放到多核服务器上可能直接拖垮性能，想改策略却发现牵一发而动全身。反过来，如果底层机制完全不管束、把太多原始自由度直接暴露给上层策略，接口又会变得复杂脆弱，甚至留出安全漏洞。优秀的操作系统往往会在中间画出一条清晰的界线：机制保持精干、稳定、安全，策略则留出可调整、可演化的空间。

| 领域 | 机制（提供什么能力） | 策略（做什么选择） |
| --- | --- | --- |
| CPU | 定时器中断、保存与恢复寄存器现场 | 优先级规则、时间片长短、多核负载均衡 |
| 内存 | 页表映射、缺页异常触发与修复 | 内存满时置换哪一页、何时启动后台回收 |
| 存储 | 把读写请求送入设备队列并等待完成 | 哪些相邻请求先合并、哪类请求插队先做 |
| 保护 | 硬件特权级、每次访问的权限检查 | 哪个用户或服务应当被授予哪些具体权限 |

理清了“要做什么”以及“如何拆解能力与选择”，一个更现实的工程问题摆在了操作系统架构师面前：把进程、内存、文件系统、网络协议栈、成百上千种设备驱动全都写出来，代码量轻轻松松上千万行。这么多代码，在内核里到底该怎么摆放？

## 内核组织方式：装进一个大盒子，还是拆成许多小盒子？

给上千万行高权限代码规划结构，本质上是在“办事快”和“出事不连坐”之间做博弈。围绕这条分歧，历史上长出了几种极具代表性的内核架构。

### 单体内核：全装进一个大盒子

**单体内核**（monolithic kernel）的选择非常干脆：把进程调度、虚拟内存、文件系统、网络协议栈以及绝大多数设备驱动，全都放进同一个高权限的内核地址空间里。

这么做最大的甜头是快、而且顺手。文件系统想向块设备层要一块数据，或者网络栈想从内存池里拿一块缓冲区，直接就是一次普通的内核内部函数调用，既不用跨保护边界，也不用把数据来回拷贝。各个子系统可以毫无隔阂地共享同一份缓存与数据结构，跨模块做性能优化也极其直接。

可“同住一个屋檐下”的代价同样刺眼：屋里只要有一个角落着火，整栋楼都可能跟着塌掉。哪怕只是一块冷门打印机驱动里写错了一个空指针，或者做了一次数组越界写，它踩坏的也是整个内核共享的内存——轻则数据静默损坏，重则全机死机重启。我们把“一旦出错就足以危及整个系统安全与稳定”的代码集合，称为**可信计算基**（trusted computing base，TCB）。单体内核的 TCB 极其庞大，子系统之间耦合紧密，缺少天然的故障防火墙。

现实中广为使用的 Linux 通常被归类为“模块化单体内核”：它的核心服务依然运行在同一个内核地址空间，但允许在系统运行时动态加载或卸载驱动模块（比如插上一块新网卡再装对应驱动），省去了每次改配置都要重新编译重启的麻烦。但要清醒地记住：**模块化改善的是部署和扩展的灵活性，并不提供强隔离**——模块一旦加载进内核，拿到的就是和核心代码一样的最高特权，写坏了照样能把整台机器拉下水。

### 微内核：把内核削到只剩骨架

既然大盒子一炸全炸，架构师自然会反问：能不能把内核削得极小，只把非留在高权限里不可的那一小撮核心机制留下，其余全都赶出内核？

沿着这个思路诞生的就是**微内核**（microkernel）。它尽量只在内核态保留地址空间管理、最基础的线程调度、中断转发，以及让不同进程安全传递消息的**进程间通信**（inter-process communication，IPC）机制；至于文件系统、网络协议栈、各种设备驱动，统统作为普通的用户态服务进程各自隔离运行：

```text
应用程序
  -> 通过 IPC 向“文件服务进程”发请求
  -> 文件服务进程再通过 IPC 向“块设备服务进程”要数据
  -> 微内核居间完成消息搬运、权限校验与调度切换
```

这么拆开的好处一目了然：可信计算基大大缩小，故障被关进了小盒子。就算网卡驱动或者文件系统服务崩了，内核依然稳如泰山，把出问题的服务进程单独重启拉起来就行，不必整台机器重启。

但天下没有免费的隔离。原来在单体内核里只需一次几十纳秒的函数调用，拆成微内核后，可能要跨越好几次地址空间边界——每次发消息都要进出内核、校验权限、切换上下文，甚至伴随数据搬运和缓存变冷。早期的微内核就曾因为 IPC 开销过高而在性能上吃尽苦头；后来的现代微内核（如 L4 系列、seL4）通过极度精简的快速 IPC 路径、直接用共享内存传大块数据以及精细的接口设计，把这部分成本压低了许多，并在航空航天、汽车电子、安全隔离底座等领域大放异彩。

### 混合内核与外内核思想

既然单体内核快、微内核稳，很多商业操作系统（如 Windows NT、macOS 的 XNU）在演化中吸收了两边的思路，常被称作“混合内核”——结构上讲究分层和消息抽象，但为了把延迟压下来，还是把不少关键服务和驱动放进了内核态运行。需要注意，“混合内核”并不是一个严格统一的学术定义；评价某个系统时，别光看名字怎么叫，要看哪些代码实际拥有最高硬件特权、垮了会拖累谁。

学术界还探索过一条更激进的路——**外内核**（exokernel）。它的批评直击传统内核的痛点：不管单体还是微内核，都替应用程序定死了“文件”“虚拟内存页”这些固定抽象，可像高性能数据库或专业网络引擎这类应用，往往比内核更懂自己的数据访问规律，固定抽象反而成了束缚。于是外内核干脆只负责一件事：安全地把物理磁盘块、物理内存页、CPU 时间片等原始硬件资源分给不同应用，确保彼此不越界；至于要不要文件抽象、怎么组织缓存，统统交给随应用一起编译的“库操作系统”自己决定。这样做换来了极致的性能定制空间，代价则是应用与库的开发复杂度陡增。

### 用一个极简式子看懂架构取舍

不需要复杂的公式，用一行算术就能摸到结构选择的脉搏。假设完成一次逻辑上的文件操作，需要跨越 $k$ 次保护域边界（比如进出内核或在不同服务进程间切换），每次跨越平均要付出的固定开销是 $c$，在不计其他成本的前提下，光“过门”花掉的时间就是：

$$
T_{boundary}=kc.
$$

这个式子当然代替不了真实基准测试，但它把核心矛盾写得一清二楚：把系统切得越碎，故障边界越干净、单独升级越从容，可一次普通请求要跨的门 $k$ 往往也会变多；反过来，把大家揉在一个盒子里可以把 $k$ 压到最小，却要承担牵一发而动全身的脆弱性。没有哪一种架构绝对“更高级”，一切取决于你最怕慢，还是最怕崩。

## 回到开机现场：把启动接力链一棒一棒拆开

聊完了内核的角色与内部骨架，让我们重新回到文章开头按下电源键的那一幕。现在我们已经知道内核自己长什么样，也就更有底气把“开机启动”这条接力链走一遍，看清信任与执行环境是怎样一步步从无到有建立起来的。

### 第一棒：复位与固件

通电瞬间，CPU 内部所有状态被硬件清空（复位），指令指针强制指向体系结构规定的“复位向量”地址。这个地址被主板电路映射到只读或闪存芯片里的固件代码。固件醒来后，立刻接手一团原始硬件：检测内存条能不能正常工作、扫描总线上插着哪些硬盘和设备、按配置决定从哪块盘或网络启动。

固件与后续启动程序之间需要一套清晰约定好的接口。早期 PC 长期使用的是 **BIOS**（基本输入输出系统），受历史包袱限制，启动流程偏老旧、对大容量磁盘和新式硬件支持捉襟见肘；现代机器则普遍采用 **UEFI**（统一可扩展固件接口），它本身更像一个微型操作系统，能直接识别分区表和文件系统，启动流程也更规范。

固件运行在极高的硬件权限下。如果机器开启了安全启动（Secure Boot），固件在交棒前还会用内置的公钥验证下一阶段引导程序的数字签名——签名对不上就拒绝加载，防止恶意代码抢在操作系统之前悄悄潜伏进机器底层。

### 第二棒：引导程序

固件完成交接后，**引导程序**（例如 Linux 上常见的 GRUB 或 systemd-boot）接过舞台。它的任务很聚焦：找到硬盘上存放内核代码的映像文件，顺手再加载一份供内核早期落脚用的临时微型文件包（在 Linux 上叫 `initramfs`，里面放着认出真正根磁盘所需的驱动和工具），把它们稳妥地放进内存，并把管理员配置的启动参数一并备好。

如果你在电脑上装了双系统，开机时看到的那个选单就是引导程序画出来的。不过，引导程序只负责“把内核搬进内存并交给它”，它自己既不懂多任务调度，也不打算建立完整的用户权限和文件系统抽象——那都是下一棒的活。

### 第三棒：内核早期初始化

CPU 终于跳进了内核的入口函数。可别以为这时内核已经无所不能了——刚进门的那一刻，连最基本的内存管理、中断响应都还没搭好，内核只能小心翼翼地在极其简陋的环境中先给自己搭架子：

- 建立[页表](../chapter_04_memory/01_address_space_paging.md)，规定内核使用的逻辑地址如何换算成内存条上的真实物理地址；
- 登记[异常与中断入口](02_kernel_user_syscalls_interrupts.md)，让 CPU 一旦遇到算错指令或收到外部设备来电，知道该往哪段处理代码跳；
- 探查机器上到底有几颗 CPU 核心、多大物理内存以及挂着哪些关键硬件；
- 拉起内存分配器、调度器和核心对象管理器，让内核具备分配内存、管理任务的日常能力；
- 挂载临时或真正的根文件系统，从此能按路径读取硬盘上的程序和配置。

在多核机器上，通常先由一颗“引导处理器”独自跑完这一连串初始化，等全局数据结构都准备停当，再逐一唤醒其余的核心，让它们一起跳进调度循环待命。

### 第四棒：第一个用户空间进程

当内核终于能够创建进程、并从根文件系统里读出可执行文件时，它会亲手拉起整台机器的第一个用户空间进程（在类 Unix 系统里，这个进程编号通常是 `1`，传统叫 `init`，现代 Linux 发行版上常见的是 `systemd`）。

从这一刻起，内核退居幕后当起裁判和管家，真正“把机器布置成可用状态”的杂活都由这个 1 号进程接手：挂载其余数据分区、拉起网络配置和日志守护进程、启动音频和图形服务，最后把登录提示符或桌面环境呈现在你眼前。

```text
通电复位（复位向量）
  -> 固件自检与签名校验（BIOS / UEFI）
  -> 引导程序装载内核映像与临时启动文件
  -> 内核入口建立页表、异常表与核心子系统
  -> 挂载根文件系统，拉起 1 号用户进程
  -> 系统服务逐一就绪，呈现登录或图形界面
```

### 启动失败时，如何按阶段精准定位？

把这条接力链刻在脑子里，绝不只是为了应付考试——下次遇到服务器或个人电脑死活起不来时，它能立刻帮你缩小九成盲猜范围：

| 看到的现象 | 最值得怀疑的接力棒 |
| --- | --- |
| 按下电源黑屏、风扇狂转或卡在硬件报错声，连主板徽标都没出现 | 电源、主板、内存条或固件阶段 |
| 能看到引导菜单、能选内核，但一回车就报错找不到文件或签名失败 | 引导程序配置、启动分区损坏或内核映像缺失 |
| 屏幕上滚出一屏内核日志后突然死机（Kernel Panic），抱怨找不到根分区 | 内核本身、关键磁盘驱动、启动参数或临时启动文件 `initramfs` |
| 内核顺利跑完初始化，却卡在某个服务启动超时或进不了登录界面 | 用户空间的 1 号进程、文件系统配置或具体系统服务 |

排查启动故障的秘诀，永远是先找到“最后一个成功跑完的阶段”，然后盯着紧挨着它的下一棒交接处。

## 操作系统里没有免费的午餐

读到这里，你或许已经隐隐感觉到一种贯穿操作系统的底层气质：**没有任何一个设计能同时把极致隔离、零开销抽象、绝对公平和最高吞吐全都收入囊中。**每往前跨一步，背后几乎都藏着一笔需要权衡的账：

- 让多个任务共享硬件缓存能大幅提速，却也放大了彼此争抢和通过计时偷窥信息的侧信道风险；
- 把写磁盘的数据先攒在内存里稍后落盘能把吞吐拉满，可一旦突然断电，还没来得及写进硬盘的数据就会丢得更多；
- 把功能全塞进单体内核省掉了跨域开销，代价是可信计算基膨胀，一个小 bug 就能掀翻全机；
- 把大锁拆成更细粒度的锁能让多核跑得更欢，却让程序员推演并发正确性、排查死锁的难度成倍上升。

因此，以后无论看到哪一种操作系统机制，别急着给它贴“先进”或“过时”的标签，先追问两句：它假设了什么样的工作负载？它最想防住哪类故障、又愿意为此付出哪类代价？

现在，内核已经稳稳落脚在内存里，第一个用户进程也跑起来了。可紧接着，一个悬念立刻浮上了水面：既然普通程序被牢牢关在权限受限的环境里，它既不能自己碰硬盘，也不能直接调用内核里的函数，那当它真的想读键盘、写文件时，到底该怎么敲开内核的门？而内核又该怎样守住这道门，不让恶意程序趁机闯进来？这正是[下一篇](02_kernel_user_syscalls_interrupts.md)要亲手拆解的核心。

## 与其他学科的呼应

- **计算机组成原理**：操作系统不是凭空变出特权级、异常入口和地址翻译的，这些能力全都依赖 CPU 硬件提供的底层电路支持。
- **数据结构与算法**：调度里的运行队列、内存里的页表、文件系统里的目录检索、定时器用的时间轮或最小堆，选什么数据结构直接决定了内核在成千上万个任务下的真实开销。
- **计算机网络**：协议栈同样是一个由状态机、缓冲区队列和异步事件驱动的系统，分层解耦与跨域拷贝开销的思想如出一辙。
- **分布式系统**：微内核里隔着进程边界传递消息，和分布式集群里跨机器发起远程过程调用（RPC），面对的都是接口边界、数据打包、故障隔离与命名查找——只是延迟尺度从微秒放大到了毫秒，故障模型也从本机崩盘扩展到了网络丢包与分区。

## 自测

1. 把所有设备驱动都搬到用户态运行，为什么往往能提升系统可靠性，却不一定能提升性能？
2. Linux 被称为“模块化单体内核”，这里的“模块化”是否意味着内核模块之间拥有强故障隔离？
3. 在开机启动流程中，为什么页表和中断/异常入口必须在拉起普通用户进程之前就先建好？
4. 试着自己举出一个例子，说明如果把“机制”和“策略”混在一起写死，会让系统在面对新场景时变得多僵硬。

??? note "参考思路"

    1. 用户态驱动与内核隔离在各自的地址空间里，驱动崩溃通常不会直接写坏内核内存，还可以单独重启；但原本内核内的函数调用变成了跨进程的消息传递与上下文切换，数据搬运和调度成本往往会拖慢热路径。
    2. 不意味着强隔离。内核模块虽然支持动态装卸，但加载后依然运行在高权限的内核地址空间里，和核心代码共用内存，一旦越界照样能破坏整个内核。
    3. 普通用户进程一跑起来，就要靠虚拟地址隔离内存、靠系统调用与异常入口请求内核服务、靠时钟中断交出 CPU 接受调度；如果这些基础设施尚未就位，用户进程既无法安全运行，内核也无法在它失控时收回控制权。
    4. 例如，若硬件定时器和中断机制被写死为“固定每 50 毫秒强制轮转一次、且只能按先来先服务排队”，那么一旦机器要兼顾低延迟音频播放或实时控制任务，内核就无法在不改底层硬件/入口的前提下调整优先级与时间片策略。
