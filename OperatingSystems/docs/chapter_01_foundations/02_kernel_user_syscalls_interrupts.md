# 内核态、系统调用、中断与异常

## 读一次键盘，内核居然从三扇不同的门走了进来

假设你写了一个最简单的终端程序，让它等待用户从键盘敲入一行字。这么一件日常小事的背后，CPU 其实可能会以三种截然不同的方式从普通程序切进内核：

1. 程序调用 `read` 向系统要键盘数据——这是程序自己**主动开口请求服务**，走的是**系统调用**这道门；
2. 此时用户还没按键，程序里这条独立推进的执行流（我们在第 2 章会正式展开认识它，叫作**线程**，thread）干脆暂停休息，把 CPU 让给别的程序；几秒钟后，用户终于按下了回车键，键盘控制器立刻给 CPU 发来一条电信号通知“数据到了”，这种由外部硬件随时打断当前工作的机制叫作**中断**（interrupt），内核借此醒来收下按键、把刚才睡着的程序叫醒；
3. 假如程序拿到数据后，准备把它抄进一块自己以为可用、但实际还没映射到物理内存的地址里，CPU 在执行这条写内存指令的瞬间就会发现不对劲，当场停下来向内核报告——这种由当前指令自己闯祸或触发特殊条件引起的事件，叫作**异常**（exception）。

看出来了吗？这三次进入内核，敲门的分别是**当前正在运行的程序**、**机箱里外的硬件设备**，以及**处理器自己对当前指令的检查**。

??? question "刚才那个等键盘的线程明明已经睡着、不在 CPU 上跑了，按键按下时它还能被叫醒吗？"

    当然能。收到键盘中断时，CPU 上正在跑的可能是浏览器、音乐播放器，甚至什么都没跑。没关系——硬件中断直接由内核接手处理，并不要求当初发起读取的那个线程此刻正占着 CPU。内核把读到的按键字符放进缓冲区，顺着等待队列找到那个睡着的线程，把它的状态改成“可以运行”；接下来调度器挑中它时，它就会从当初停下的地方接着往下跑。

这一页要帮你建立操作系统最核心的一道心智防线，请先把它刻在脑子里：**“进入内核态”描述的是 CPU 权限级别的变化，而“切换进程”描述的是执行主体的变化。这两件事有时恰好一起发生，但更多时候彼此独立、绝不能画等号。**只要把这两个维度彻底分清，后面很多令人抓狂的问题（比如“时钟中断到来时，当前程序是不是一定会被换掉？”）都会迎刃而解。

## 用户态与内核态：硬件焊死的权限围墙

为什么不能靠程序员自觉，大家约定好“谁也别乱改别人的内存、谁也别随便关中断”呢？道理很简单：软件里的君子协定挡不住一个写错指针的 bug，更挡不住存心捣乱的恶意程序。只要 CPU 允许普通程序执行修改内存映射或直接操作硬盘的指令，系统就毫无安全性可言。

因此，这道边界必须由处理器硬件亲自把守。不同的 CPU 架构给权限档位起了不同名字（例如 x86 里的 Ring 0 到 Ring 3，ARM 里的 EL0 到 EL1），但在操作系统视角里，先抓住最关键的两档就够了：

- **用户态**（user mode）：权限受限的日常档位。应用程序和普通函数库都在这里运行，只能算普通算术逻辑、只能读写内核明确划给自己的那片内存。
- **内核态**（kernel mode）：握有最高权限的管理档位。内核代码和内核态驱动运行在这里，可以改写地址映射表、配置硬件中断、直接向磁盘和网卡发命令。

| 运行模式 | 允许做的事 | 典型代码 |
| --- | --- | --- |
| 用户态 | 普通运算，仅能访问获准映射的内存区域 | 应用程序、标准库函数 |
| 内核态 | 执行特权指令，配置内存映射、中断控制器与外设 | 操作系统内核、内核态驱动 |

硬件的监督是“每条指令都不放过”的：用户态程序一旦试图执行特权指令，或者伸手去碰一块没有权限的内存，CPU 不会客气地返回一个 `-1` 让你自己处理，而是当场触发硬件异常，强行把控制权夺走并交给内核。至于这究竟是一次可以悄悄补救的合法缺页，还是必须立刻枪毙的越界访问，全由内核说了算。

## 为什么普通函数调用替代不了系统调用？

写 C 语言时，调用 `write(...)` 写文件和调用自己写的 `add(a, b)` 在语法上长得一模一样。初学时很容易产生一个直觉：内核不也躺在内存里吗？我直接用一条普通的函数调用指令（`call`），跳到内核写文件的函数入口不就行了？

真要这么干，会撞上两堵死墙。第一，普通函数调用只在当前权限级里挪动指令指针、压个栈帧，根本**无法把 CPU 从用户态提拔到内核态**；你就算真跳过去了，第一条特权指令就会因为权限不够当场报错。第二，就算允许跳，要是用户程序能随便跳到内核代码中间的任意一行，它就可以故意跳过开头的权限检查，直接落到“写磁盘”那一行里为所欲为！

所以，硬件专门为系统调用设计了一套“唯一受控门禁”——特殊的**陷入（trap）/ 系统调用指令**（如 x86-64 上的 `syscall`、RISC-V 上的 `ecall`）。它把“提高权限”和“跳转到内核事先登记好的唯一总入口”捆成了一个不可拆分的硬件动作：

1. 用户态代码先把“我要办哪项业务”（系统调用号）和具体参数放进约定好的寄存器里；
2. 执行体系结构规定的系统调用指令；
3. CPU 硬件瞬间切到内核态，同时不由分说地把指令指针跳向内核预先配置好的统一入口，并切到内核专用栈；
4. 内核入口代码先把用户程序刚才跑到哪条指令、寄存器里都是什么值妥善存好，搭出安全运行内核 C 代码的环境；
5. 内核拿出系统调用号查表，找到对应的处理函数，把用户传来的参数小心翼翼地复制并验证一遍，再去真正干活；
6. 活干完了，把结果或错误码放回约定好的返回值寄存器；
7. 执行专用返回指令，一次性恢复用户现场、把权限降回用户态，继续执行刚才系统调用后面的下一条用户指令。

```text
用户库封装（按约定装填寄存器）
  -> 执行系统调用指令（硬件提权 + 跳至唯一入口）
  -> 内核通用入口（保存现场、切换内核栈）
  -> 参数拷贝与合法性核查
  -> 分派给具体内核服务执行
  -> 专用返回指令（恢复现场 + 降回用户态）
```

### 拆开一个最小例子：`write` 背后的约定

在类 Unix 系统上，向屏幕输出一行 `hello`，最简短的代码长这样：

```c
#include <unistd.h>

int main(void) {
    const char msg[] = "hello\n";
    ssize_t n = write(STDOUT_FILENO, msg, sizeof(msg) - 1);
    return n < 0;
}
```

这里很容易混淆两个同名概念：C 代码里写的 `write(...)` 其实只是标准 C 库替你写好的普通包装函数，真正过门的那一脚，藏在包装函数内部那条汇编级系统调用指令里。C 库干的活，是把“写操作对应的编号”、`STDOUT_FILENO`、`msg` 的地址和长度，严丝合缝地塞进操作系统与 CPU 共同约定的那几个寄存器里——就像寄快递时，寄件人和快递站必须事先说好哪一栏填电话、哪一栏填地址一样。这种二进制程序与内核之间关于寄存器怎么放参数、怎么拿返回值的硬性规范，叫作**应用二进制接口**（application binary interface，ABI）。

## 内核为什么绝不敢轻信用户传来的指针？

回到我们最熟悉的 `read(fd, buf, 4096)`：应用程序把一块内存地址 `buf` 交到内核手里，让内核把读到的 4096 字节写进去。

看起来挺顺理成章，对吧？可站在内核的角度想一想，这其实暗藏杀机——因为此时 CPU 运行在**拥有至高权限的内核态**！假设一个恶意程序故意不传自己的缓冲区地址，而是传了一个**内核自己核心数据结构所在的地址**（比如存放当前进程权限标志的内存地址），同时把文件里提前准备好的恶意字节喂给 `read`。如果内核傻乎乎地直接把 `buf` 当普通指针往里写，等于内核亲手拿着最高权限的手术刀，替攻击者改写了自己的大脑！

就算程序没有恶意，用户传来的指针依然处处是坑：

- 这段地址可能根本还没映射到物理内存，或者只允许读、不允许写；
- 这块区域跨了边界，前半截在用户空间，后半截伸进了内核空间；
- 哪怕内核刚检查完“地址合法”，同一个进程里的另一个线程可能就在检查完的下一微秒，把那块内存解除映射或换成了只读页；
- 这块内存虽然合法，但数据暂时被换出了物理内存，访问它时会触发缺页，必须走正常的补页流程而不是让内核当场崩溃。

正因如此，内核绝不能像写普通 C 程序那样直接对用户指针解引用，必须通过专门的“安全跨界拷贝”例程（例如 Linux 里的 `copy_to_user` / `copy_from_user`）来搬运数据：先核查整段地址范围是否完全落在用户空间，再用带有硬件异常兜底的指令去拷贝——万一拷贝中途踩到非法页，硬件捕获异常后安全地给用户返回错误码（如 `EFAULT`），而不是让整个内核死机。简单粗暴地写一句 `if (buf < KERNEL_BASE)` 远远不够，因为安全性取决于实际页表映射、长度范围、访问方向和并发修改的完整组合。

## 三条进内核的路：系统调用、异常与硬件中断

现在我们已经把最主动的一条路——系统调用——摸透了。把另外两条路摆在旁边一对照，整张“事件入核”的地图就清晰无比了：

### 1. 系统调用（主动、同步）

由当前正在运行的程序主动发起，用来向内核申请服务。它是同步的：程序执行到系统调用指令这一刻才进内核，办完事返回后，通常顺着系统调用的**下一条指令**接着跑（除非这个调用是 `exit` 让进程退出了，或者中途阻塞等 I/O 期间被信号打断）。

### 2. 异常（被动、同步）

由 CPU 执行**当前这条指令**时同步触发，意味着这条指令自己出了状况，必须立刻停下来让内核裁决。常见情形包括：

- **缺页**：要访问的虚拟地址还没对应到物理页框；
- **算术或指令错误**：比如整数除以零、撞上一条 CPU 不认识的非法指令；
- **越权访问**：往只读代码段里写数据，或在用户态硬跑特权指令；
- **调试陷阱**：调试器埋下的断点指令或单步执行标记。

面对异常，内核有两种截然不同的结局：像按需分页的缺页这类“可修复异常”，内核把物理页补好、改好映射后，返回用户态时会**重新执行刚才那条出错的指令**，程序浑然不觉；而像非法地址访问、除零这类程序本身的硬伤，内核无法替它擦屁股，只能通知进程出错甚至直接终止它。

### 3. 硬件中断（外部、异步）

由 CPU 外部的硬件设备随时发出——网卡收到了一个数据包、硬盘把请求的数据搬进了内存、硬件定时器滴答到期。它和 CPU 此刻正在算的那条指令**毫无因果关系**，因此叫作异步事件。CPU 只要执行完手里这条不可拆分的指令，就会在允许的边界暂停当前程序，存好现场跳进中断处理程序；处理完毕后，如果没发生调度切换，就原封不动回到被打断的那条指令继续跑。

| 事件类型 | 谁敲响了门 | 与当前指令的关系 | 典型场景 | 返回时通常去哪儿 |
| --- | --- | --- | --- | --- |
| 系统调用 | 当前程序 | 主动、同步 | 读写文件、创建进程、发网络包 | 系统调用的下一条指令 |
| 异常 | 当前指令与 CPU 检查 | 被动、同步 | 缺页、除零、非法指令、调试断点 | 修复后重试当前指令，或转交错误处理 |
| 硬件中断 | 外部设备 / 定时器 | 异步、与当前指令无关 | 磁盘完工、网卡来包、时钟滴答 | 回到被打断的位置（若未切换任务） |

## 急诊室为什么要分诊：中断处理为什么分层？

硬件中断说来就来，而且经常扎堆来——想想一台忙着收发大流量的服务器，网卡每秒可能产生几万次通知，与此同时硬盘和定时器也在不停响铃。

设想一下：如果每次网卡一来中断，内核就在高优先级、甚至屏蔽了其他中断的环境下，一口气把网络包拆封、走完复杂的 TCP 协议校验、唤醒上层应用、顺手再写条日志……会发生什么？急诊室唯一的医生被一个慢病患者占着看半小时，后面送来的时钟中断、硬盘中断全都堵在门外进不来，整个系统的响应延迟瞬间失控，甚至连硬件缓冲区溢出了都来不及救火。

因此，现代操作系统普遍像医院急诊一样，把中断处理拆成快慢两层：

1. **快速部分（急诊分诊）**：尽可能短小精悍。一进来立刻确认是哪个设备响了铃，把转瞬即逝的硬件状态读出来、向设备应答“我收到了”，把待办数据塞进内存队列，然后迅速撤出高优先级中断现场，让别的硬件中断能顺利进来。
2. **延后部分（专科细看）**：等到安全、允许被打断甚至允许调度的普通环境里，再从队列里取出待办工作，从容地跑协议栈、做数据校验、唤醒等待线程。

不同操作系统给这两层起了各种名字——“上半部 / 下半部”“软中断”“线程化中断”“工作队列”——各自的调度约束略有差别，但背后都是同一个朴素道理：**绝不把耗时、可推迟的繁重工作堵在抢占一切的急诊室里。**

## 一次时钟中断，到底会不会切换进程？

回到本篇开头立下的那条铁律。很多人学到“分时系统靠时钟中断实现切换”，脑子里就会自动画一个等号：“时钟中断 = 切换进程”。其实不是这样。

时钟中断真正做的事，只是**准时把控制权从用户态拉回内核态**，给调度器递一次“看一眼表、检查一下局势”的机会。内核顺手更新了系统时间和当前线程的已用配额后，可能做出三种截然不同的决定：

- 当前线程的时间片还没用完，也没冒出更紧急的任务——内核直接返回，继续让它跑；
- 刚好有一个高优先级的交互线程醒了过来——调度器果断换人，切去跑那个更紧急的线程；
- 当前线程的时间片恰好用光了——调度器把它放回队列末尾，另挑一位上台。

你看，两条坐标轴清清楚楚：

```text
用户态 -> 内核态：只要中断到达，权限转换 100% 发生
线程 A -> 线程 B：是否更换执行主体，全看调度器当下的裁决，并不必然发生
```

反过来也成立：内核自己内部也有干后台杂活的内核线程（比如负责定时把脏数据刷回磁盘的线程），它们之间可以在**全程不离开内核态**的情况下互相切换。把“换权限”和“换任务”彻底拆开看，以后读调度和虚拟化代码时就不会再绕晕了。

## 跨过这道门，到底要花多少钱？

既然系统调用比普通函数调用安全得多，那写程序时是不是每读写 1 个字节就调一次 `read` 也无所谓？动手测一下你就会大吃一惊：同样读 1 兆字节的数据，每次读 1 字节调一百万次 `read`，可能比每次读 4096 字节调 256 次慢上几十甚至上百倍！

这笔开销远不止那一条陷入指令本身，每一次过门都在悄悄结账：

- 硬件切换特权级、切换内核栈，保存并随后恢复一大把寄存器；
- 校验参数合法性、在用户空间与内核空间之间拷贝数据；
- 现代 CPU 为了防住侧信道攻击（如熔断、幽灵等硬件漏洞），在进出内核时还得额外执行安全缓解隔离指令；
- 更隐蔽的成本在于“把缓存搅浑”：内核代码跑了一圈，顺手把用户程序原本捂得热乎的 CPU 缓存、分支预测记录，甚至[地址翻译缓存（TLB）](../chapter_04_memory/02_page_tables_tlb_faults.md)挤掉了一部分，等回到用户态还得慢慢重新热身；
- 这还没算上内核服务内部可能遇到的锁竞争、睡眠调度和真正等硬件的时间。

不妨算一笔直白的小账。假设每次进出系统调用的固定过门费是 $t_s$，实际处理一项数据花的功夫是 $t_w$。如果你傻傻地一项一项发系统调用，处理 $n$ 项总共要花：

$$
T_{single}=n(t_s+t_w).
$$

要是把 $n$ 项攒在一起，只敲一次门交给内核批量处理，忽略攒批本身的额外整理成本，总时间就降到了：

$$
T_{batch}=t_s+nt_w.
$$

把 $n$ 份过门费 $t_s$ 省成了 1 份，这就是标准 I/O 库要做缓冲、现代接口（如批量提交异步请求队列）热衷于批处理的根本原因。不过老规矩——便宜不会白占：批攒得越大，内存占用越高，排在最前面那条数据干等发车的延迟越长，而且万一这一批里第 37 项失败了、前 36 项已经成功，错误处理也会立刻棘手起来。

## 异常善后与“信号”：给用户进程的通知机制

前面提到，有些同步异常内核没法悄悄修好——比如程序解引用了一个空指针，或者做了整数除零。内核总不能因为一个普通应用写坏了代码，就跟着一起死机吧？

这时，内核会把硬件异常翻译成一种用户空间能听懂的通知抽象，叫作**信号**（signal，例如非法访问内存对应的 `SIGSEGV`）。默认情况下，收到致命信号的进程会被内核直接终止并清理掉；如果程序提前登记了自己的信号处理函数，内核会在返回用户态之前，悄悄在用户栈上搭出一个临时现场，让 CPU 先去跑那段用户处理函数，跑完再通过受控路径恢复原来的执行位置。

初学者常常把信号和硬件中断混为一谈，因为它们看起来都是“突然打断当前代码去跑一段处理程序”。其实两者隔着整整一个层次：**硬件中断是外设发给 CPU 和内核的底层硬件事件，而信号是内核加工出来、投递给用户进程的软件抽象。**

## 安全边界上最容易翻车的五类漏洞

系统调用入口面向机器上的每一个普通程序敞开，天然是操作系统最受攻击者青睐的薄弱地带。接口越复杂、分支越多，内核工程师在这道边界上就越容易踩中下面五类经典雷区：

- **长度检查疏漏引发整数溢出**：比如先算 `len + header_size` 用来申请缓冲区，结果攻击者故意传一个极大值让加法回绕成一个极小的数，内核只申请了很小一块内存，随后却按原本巨大的 `len` 往里拷贝，瞬间踩穿内核内存。
- **检查与使用脱节**：内核先检查了一遍用户内存里的参数觉得没问题，隔了几微秒真正要用时又去用户内存读了一遍，结果攻击者的另一个线程就在这几微秒间隙里悄悄把内容掉包了。
- **出错返回忘了收拾残局**：正常路径干完活记得解锁、释放内存，可偏偏在某个冷门的错误分支里直接 `return -EINVAL`，结果把锁一直占着死锁全机，或者慢慢漏光内核内存。
- **把用户可控数据当成可信指令或指针**：信任用户提供的偏移、索引或格式字符串，最终让内核去读写了本不该碰的位置。
- **返回路径泄漏特权状态**：回到用户态时没把标志寄存器里的特权位清干净，或者把未初始化的内核栈字节顺手带回了用户空间，泄露了内核机密地址。

正因为每一个系统调用都意味着一片需要死守的防线，现代内核在新增系统调用接口时才格外谨慎。

到这里，我们已经亲手打通了第 1 章的全部脉络：机器怎样靠固件、引导程序和内核接力启动；内核怎样用硬件特权级筑起用户态与内核态的围墙；以及系统调用、异常和硬件中断这三条受控通道怎样把控制权送进内核，处理完毕后再稳妥返回——或者，顺势换上另一个程序来运行。

等等，“换上另一个程序来运行”听起来只是轻飘飘的一句话，可同一颗 CPU 上到底怎样才能在几十个程序之间来回切换，还让每个程序都深信自己从未被打断？这背后隐藏的现场保存、独立执行流与进程间协作，正是[第 2 章：进程、线程与进程间通信](../chapter_02_processes/index.md)要揭开的秘密。

## 与后续章节的呼应

- **进程管理（第 2 章）**：创建新进程、替换程序映像、等待子进程结束（`fork`、`exec`、`wait`），全部通过系统调用完成。
- **并发与同步（第 4 章）**：当程序在系统调用里试图获取一把已被占用的内核锁时，可能被迫让出 CPU 进入睡眠，等别人解锁后再由内核唤醒。
- **虚拟内存（第 5 章）**：程序第一次触碰按需分配的内存时，正是靠缺页异常敲开内核大门，补齐映射后再回去重试原指令。
- **文件与 I/O（第 6 章）**：一次普通的 `read` 系统调用，幸运的话直接在内存副本里拿走数据；不走运的话就要向磁盘发请求、让出 CPU，直到磁盘完工发来硬件中断才把线程叫醒。
- **容器与沙箱（第 8–10 章）**：容器里的进程没有自己独立的内核，它们的系统调用照样直通宿主机内核，因此过滤和收紧可用的系统调用清单，是容器安全防线里极关键的一环。

## 自测

1. 既然内核代码也在内存里，为什么不能直接用普通跳转或函数调用指令进入内核？
2. 缺页异常和磁盘完成中断都会让 CPU 进入内核，它们在触发来源、与当前指令的关系以及返回位置上有什么本质区别？
3. 为什么时钟中断到来时，CPU 虽然一定切进了内核态，却不一定发生进程切换？
4. 如果允许一个普通用户态驱动直接读写设备硬件寄存器，会破坏操作系统的哪些保护边界？
5. 把多次小请求合并成一次批量系统调用，省掉了什么成本？同时又可能带来哪些新麻烦？

??? note "参考思路"

    1. 普通跳转或函数调用既无法可靠提升 CPU 特权级，也无法阻止用户程序跳过开头的参数与权限检查直接跳入内核函数内部；必须借助硬件陷入指令，原子地完成“提权 + 跳至唯一受控入口”。
    2. 缺页异常由 CPU 执行当前访存指令时同步触发，内核修复映射后会返回并重试刚才那条指令；磁盘中断由外部硬盘异步触发，与当前正在执行的指令无关，处理后若无调度切换则回到被打断处继续执行。
    3. 时钟中断只是给内核提供了一次例行检查时间片和调度队列的入口；如果当前线程时间片尚未耗尽且没有更高优先级任务抢占，调度器会直接返回原线程继续运行。
    4. 直接操作设备寄存器可能绕过内核的权限检查与资源仲裁，让该程序得以通过设备直接读写不属于自己的物理内存、干扰其他进程的 I/O 请求，甚至伪造或堵塞硬件中断。
    5. 批量系统调用把多次进出内核的固定开销（保存恢复现场、特权切换、缓存扰动等）摊薄成了一次；但它会增加缓冲内存占用、拉长先到达请求的等待延迟，也会让“一批里部分成功、部分失败”的错误处理变得更复杂。
