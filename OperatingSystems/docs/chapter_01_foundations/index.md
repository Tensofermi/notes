# 操作系统基础 { #1 }

## 开机键按下之后，秩序是从哪儿冒出来的？

按下电源键的那一瞬间，内存条里其实空空如也。你电脑里的操作系统——无论多么庞大复杂——此时也只是安静躺在硬盘上的一堆字节，自己同样是一段等待被加载的程序。这就碰上了第一个“先有鸡还是先有蛋”的难题：既然操作系统还没跑起来，[到底是谁先把内核装进内存、并让它接管整台机器的？](01_os_roles_architecture_boot.md)

等内核好不容易站稳脚跟、拉起了你的第一个应用程序，第二个难题紧跟着就冒了出来：普通程序不允许直接去碰硬盘控制器，也不许随便改写系统里的内存记录，可它偏偏需要读文件、敲键盘、发数据。既然不能让它长驱直入，[程序究竟该怎么安全地跨进内核、请内核替自己办事？](02_kernel_user_syscalls_interrupts.md)

本章的两篇文章，就沿着这两个问题一前一后铺开：第一篇把机器从冰冷的通电一路护送到内核站稳脚跟，并看看内核内部究竟该怎样组织自己那上千万行代码；第二篇则专门拆解普通程序与内核之间那道最关键的“门禁”，看清系统调用、硬件通知和指令出错各自怎样敲响内核的大门。

## 为什么必须先把“边界”和“入口”讲透？

翻开目录你会发现，后面有进程、有调度、有虚拟内存、有文件系统，看起来像是各自独立的大模块。可只要往深处看，它们全都被钉在同一条地基上：普通程序只能在权限受限的环境下运行，绝不能绕开监督去执行危险指令或翻看内核账本；每当需要特权服务，或者时钟响了、设备干完活了、某条指令踩到了未准备好的内存，硬件就必须把控制权稳稳地移交给内核。

如果没有先把这套“边界 + 入口”的共同舞台搭稳，后面几乎每学一章都会觉得隔着一层雾：你会把 `read()` 误以为是普通 C 函数调用，会把外部设备的来电通知和程序自己算错数混为一谈，甚至会觉得“CPU 怎么突然就自己换了个程序去跑？”显得像魔术一样。先把谁有特权、门开在哪里、敲门之后发生什么搞清楚，后面所有机制就都有了扎实落脚的地方。

## 本章主线

沿着时间线，本章串起的是机器从上电到步入日常运转的完整闭环：

```text
硬件通电复位
  -> 芯片里的固件完成自检，交棒给引导程序
  -> 引导程序把磁盘上的内核装进内存
  -> 内核建立页表、异常入口与核心数据结构
  -> 拉起第一个用户程序，机器进入日常运转
  -> 程序在受限环境中运行，遇到请求、设备通知或指令异常时受控切入内核
  -> 内核处理完毕，返回原程序或顺势换上另一个任务继续运行
```

## 读完本章，试着自己回答

- 内核为什么不能只做成一组普通的静态库，直接链接进每个应用程序里？
- 单体内核和微内核各自把哪些代码放进了高权限边界里？这么分分别赚到了什么、又付出了什么代价？
- 系统调用、硬件中断和同步异常分别由谁触发？处理完之后它们各自会回到哪一条指令？
- 从按下电源键到屏幕上亮起登录界面，控制权至少经过了哪几棒接力？
- 为什么说“CPU 切进了内核态”，并不意味着“当前运行的进程就一定被换掉了”？

## 通往后续章节的接口

别把本章当成一次性的入门铺垫——后面每一章的看家本领，都是插在本章这套入口机制上的：第 2、3 章的抢占式调度靠时钟中断定时把 CPU 拉回内核；第 5 章的虚拟内存靠缺页异常把还没加载的数据补进内存；第 6 章的异步 I/O 靠设备中断告诉内核数据已经搬好；而文件、网络、进程和容器相关的几乎所有操作，统统要从系统调用这道门排着队走进内核。站稳了这一章，后面的路就顺畅多了。
