# 进程、线程与上下文切换

## 同一段代码，跑出两个互不干扰的世界

先别急着背定义，打开两个终端窗口，在两边各运行下面这一行命令。先在第一个终端输入 `3` 并回车，第二个终端先别按回车，让它停在 `n = ` 的提示处；等第一个终端打完结果退出后，再在第二个终端输入 `9` 并回车：

```sh
python -c 'import os; n = input("n = "); print(os.getpid(), int(n) + 1)'
```

仔细看屏幕上的变化。两个终端启动的是硬盘上完全相同的那一份可执行文件——这段安静躺着、还没跑起来的静态指令和数据，我们称为**程序**（program）。可运行起来后，你会看到它们打印出两个不同的编号，一个输出 `4`，一个输出 `10`；更关键的是，第一个窗口早就算完退出了，第二个窗口依然稳稳地停在 `input` 那里等你敲键盘，丝毫不受影响。

为什么同一套代码能活出两份互不相干的“人生”？因为每次启动它，操作系统都为这次运行单独辟出了一块独立的内存视图，记下了它打开了哪些文件、代码走到了哪一行、变量 `n` 里装的是 `3` 还是 `9`。这样一份正在运转的动态实例，就是**进程**（process）；屏幕打印出来的那个独一无二的编号，就是它的身份证号——**进程标识符**（process ID，PID）。

现在把镜头再往进程内部拉近一点。第二个终端停在 `input` 等待键盘输入的那一刻，停住的其实是进程里那条独立推进的指令执行路线——这就是**线程**（thread）。一个最简单的进程里只有一条线程，它把“下一条该执行哪条指令、寄存器里存着什么值、函数一层层调用到哪里了”串成一条连续的执行流。

如果一个下载软件想一边和服务器传数据、一边刷新进度条、一边响应你点下的暂停按钮，它可以在**同一个进程内部**创建多条线程：这些线程抬头低头都能直接看到同一份任务队列和进度变量，但各自停在不同的函数位置上，手里攥着各自私有的调用栈。相比之下，上面那两个终端里的进程各自守着互相看不见的内存领地，真要合作就必须请内核出面搭桥（比如管道或共享内存）。线程之间共享内存用起来固然痛快，可两条线程同时伸手改同一个变量时，一不小心就会撞车——这正是[第 4 章竞态与锁](../chapter_03_concurrency/01_races_atomicity_locks.md)要收拾的烂摊子。

## 为什么非要发明“进程”这个抽象？

不妨顺着直觉反问一句：不要进程行不行？让所有程序直接共用整台机器的寄存器和物理内存，谁想跑就上去跑一会儿，跑累了自己让出来，多省事！

稍微推演两步就知道这主意根本行不通。首先，程序之间毫无防备，程序 B 稍微算错一个数组下标，就能把程序 A 存在内存里的中间结果抹得一干二净；其次，只要某个程序写了个死循环忘了主动让位，或者下台时漏存了两个寄存器，整台机器就会当场瘫痪。

为了在混乱的裸硬件上圈出秩序，操作系统发明了**进程**，把“运行一段程序所需的全部家当”整齐地打包成内核统一看管的对象：

```text
进程（资源与隔离的基本容器）
  ├─ 独立的虚拟地址空间（代码、全局变量、堆、栈）
  ├─ 打开的文件与其他系统资源的引用表
  ├─ 用户身份、访问权限与待处理的信号状态
  ├─ 一条或多条负责实际跑代码的线程
  └─ 统计账本、资源配额上限与父子血缘关系
```

请扭转一个常见误解：进程并不是“此刻正焊在 CPU 上跑的东西”。在任意瞬间，机器上可能同时存在几百个进程，而 CPU 核心只有 8 颗——绝大多数进程此刻要么正排着队等 CPU，要么正在安安静静地等磁盘或网络数据，甚至已经执行完毕、只剩下一行退出档案等着父进程来领走。

## 程序、进程与线程：一张表划清边界

把这三个最容易混用的概念摆在一起对照，角色分工一目了然：

| 概念 | 本质定位 | 谁管它 / 生命周期 |
| --- | --- | --- |
| 程序 | 硬盘上的静态指令与初始数据蓝图 | 只要文件还在磁盘上就一直存在 |
| 进程 | 占有资源的隔离容器（内存视图、文件表、权限） | 从被创建到退出并被回收 |
| 线程 | 进程内部可被 CPU 独立调度的执行流 | 从被创建到执行结束退出 |

一句话总结就是：**进程是装资源的房子，线程是在房子里干活的工人。**同一份程序蓝图可以盖出好几栋彼此隔离的房子（多进程）；同一栋房子里也可以住进好几位工人（多线程）。

同住一屋的线程共享进程的地址空间、打开的文件、工作目录和用户权限，但为了各自干活互不绊脚，每条线程必须独享下面几样私人物品：

- **程序计数器（PC）与通用寄存器**：记录“我自己正跑到哪条指令、手里算到哪一步了”；
- **独立的调用栈**：工人 A 正在调用 `foo()`，工人 B 正在调用 `bar()`，各自的局部变量和返回地址绝不能混在一个栈里；
- **调度状态**：工人 A 可以因为等硬盘去睡觉，与此同时工人 B 照样可以在 CPU 上算得热火朝天；
- **线程局部存储**（thread-local storage，TLS）：给每条线程辟出的一小块私有变量区（比如每条线程各自独立的错误码 `errno`），同名变量在不同线程里互不干扰；
- 部分与信号掩码、单步调试相关的独立状态。

共享屋子里的全部家具，让线程之间传数据只需读写一个普通变量，快得惊人；但也正因没了墙的阻隔，一个工人要是把公共内存写坏了，整栋房子里的所有线程都会跟着一起崩溃。

## 内核凭什么记住几百个任务的进度？

CPU 核心就那么几颗，机器上却同时挂着几百个进程和上千条线程，有的在跑、有的在等键盘、有的刚被暂停。内核到底靠什么做到过目不忘，下次挑中谁都能精准续上？

秘密在于内核在自己内存里为每个任务建了一张档案卡，教材里统称为**进程控制块**（process control block，PCB；当线程独立调度时，也常对应到**线程控制块** TCB）。不同操作系统给它的结构名和拆分方式各不相同（比如 Linux 把进程和线程统一抽象成 `task_struct`），但想把一条线程稳妥地停下来再恢复，档案卡里至少得记清这几栏：

- 当前所处的状态（运行、就绪还是阻塞）以及它正挂在哪条队列里；
- 暂停时保存下来的硬件寄存器快照，以及它进入内核态时专用的内核栈位置；
- 调度账本：优先级、已经消耗的 CPU 时间、偏爱哪颗核心；
- 所属进程的资源指针：指向它的页表（虚拟地址映射）、打开文件表与身份权限；
- 如果正在等待某件事，它究竟在等哪块磁盘、哪把锁或哪个定时器。

注意别把“档案卡”当成“整个人”：进程的程序代码、大块堆内存和用户栈依然安安稳稳待在虚拟地址空间里，PCB/TCB 里存的只是管理用的元数据和指针索引。换人时，内核只需要切换指针和档案，绝不会傻乎乎地把几百兆内存搬来搬去。

## 线程为什么常说比进程更“轻”？

工程师嘴里常说“开线程比开进程轻量”，这份轻巧实实在在省在了两笔账上：

1. **创建与销毁更省事**：在已有进程里再拉起一条线程，不必重新分配一套地址空间，也不用拷贝打开文件表，只需分一块栈内存、填一张新的线程控制块就行。
2. **协作与切换更顺手**：同进程线程之间传数据直接读共享内存，不用经由内核来回拷贝；切换同进程的两条线程时，地址空间没变，页表根指针往往可以原封不动。

不过，“轻”绝不等于“免费”——很多高并发服务踩过的坑，正是把线程当成了可以随便挥霍的空气：

- 每条线程依然要吃掉自己的用户栈、内核栈和控制块内存（成千上万条线程光栈就能吃掉好几个 GB）；
- 线程切换照样要进内核保存寄存器、跑调度逻辑；
- 线程越多，争抢同一把锁的概率越飙升，多出来的线程往往都在排队等锁，反把并行收益抵消殆尽；
- 过长的运行队列还会把 CPU 缓存洗刷得支离破碎。

## 线程一定要由内核来管吗？用户级线程、内核级线程与协程

既然进一次内核切换线程总要花点过门费，一个很自然的念头冒了出来：能不能干脆不惊动内核，由应用程序自己在用户态写个小调度器，在自己的内存里切栈、切寄存器，实现超轻量的线程？

按“谁看得见线程、谁负责调度线程”，线程模型演化出了三条经典路线。

### 用户级线程：内核蒙在鼓里的极速切换

**用户级线程**（user-level thread）完全由用户态的运行库包办：创建、销毁、切换全在用户态改改栈指针和几个寄存器，连系统调用的门都不用敲，快到几十纳秒就能切一次。

可它有一块硬伤——**内核压根不知道屋里藏了这么多工人**，在内核眼里，这个进程自始至终只有一条执行流。后果非常尴尬：只要其中一条用户级线程调用了阻塞的 `read` 去等磁盘，内核就会把这“唯一”的执行流直接挂起睡觉，屋里另外九十九条本来可以继续算数的用户级线程统统跟着干瞪眼！而且，由于内核只分给它一个内核执行实体，无论你机器上有多少颗 CPU 核心，这些用户级线程也用不上真正的多核并行。

### 内核级线程：内核亲自点名调度

为了补上这两块短板，现代主流操作系统（如 Linux 的 NPTL、Windows 线程）普遍默认提供**内核级线程**（kernel-level thread）：每创建一条线程，内核里都有一张对应的档案卡。一条线程等磁盘阻塞了，内核立刻切去跑同进程的另一条线程；机器有 16 颗核心，内核可以把同一进程的 16 条线程同时摊在 16 颗核心上火力全开。付出的代价很直白：创建、切换和阻塞唤醒都得走内核机制，数量涨到几十万级别时内存和调度开销就吃不消了。

### 多对多模型与现代协程运行时

有没有办法既享受到多核并行和单条阻塞不连坐，又能像用户态那样轻松养活几十万条并发任务？现代编程语言运行时（如 Go 的 goroutine、Erlang 进程、各类异步框架中的**协程**，coroutine）给出了经典的“多对多”折中方案：

```text
成千上万条轻量协程（用户态极小栈、微秒级切换）
  -> 语言运行时的用户态调度器（遇到 I/O 主动让出，改走非阻塞事件通知）
  -> 少量内核级线程（通常与 CPU 核心数相当）
  -> 多颗物理 CPU 核心并行推进
```

当一条协程需要等网络数据时，运行时并不让底层的内核线程傻傻阻塞，而是把这条协程挂到网络事件监听器上，顺手在用户态把同一条内核线程切给另一条就绪的协程继续跑。这套设计极大地压低了高并发 I/O 任务的内存和切换开销，但它并没有“消灭”调度——它只是在操作系统调度器之上又叠了一层用户态调度器，随之而来的是运行时必须自己操心抢占公平性、动态扩缩栈、防止某条协程长时间占着内核线程不放，以及让调试器和性能分析工具看懂这两层映射。

??? question "Go 语言里的 goroutine 和常见的线程池有什么区别与联系？"

    两者的抽象层次并不一样。**线程池**是一种任务派发模式：提前养好固定数量的一组工作线程，任务源源不断丢进队列，空闲工人反复领活干，避免频繁创建销毁线程。而 **goroutine** 是 Go 运行时管理的一条可随时暂停、恢复的轻量级执行流，大量 goroutine 会被运行时动态复用到少量操作系统内核线程上。

    打个比方：假设 goroutine G1 正在等网络回包，G2 还有计算要做，Go 运行时会在用户态把 G1 挂起、立刻让底层内核线程去跑 G2；等网络数据到了，G1 再次变回可运行状态，从停下的那一行继续。你在业务逻辑里完全可以再用一组 goroutine 搭出一个“工作池”，用来限制同一时刻最多并发处理多少个外部请求——前者讲的是**执行流怎样被调度**，后者讲的是**并发度怎样被限流组织**。[B 站讨论](https://www.bilibili.com/video/BV1dVRdBpEze/#reply298964422961) · [Go 官方 FAQ](https://go.dev/doc/faq#goroutines)

## 什么是 CPU 上下文？

前面反复说“暂停当前线程，稍后再原样续上”，可到底要存下多少信息，才能保证一条线程醒来后完全察觉不到自己曾经被人请下过台？

这份让执行流能够原地复活的最小硬件与内核档案，就叫作 **CPU 上下文**（context），它通常涵盖：

- **程序计数器（PC）**：下一条要取的指令地址；
- **栈指针（SP）**：当前函数调用栈顶停在哪儿；
- **通用寄存器与标志寄存器**：刚刚算到一半的临时数值、上一次比较留下的进位或零标志；
- **浮点、向量（SIMD）等扩展寄存器**：如果线程用到了小数运算或向量加速，这些宽大的寄存器也得留档；
- **内核栈指针与线程控制信息**：支撑它在内核态运行的那段现场；
- **地址空间标识（页表根寄存器等）**：如果即将切去另一个进程，还得告诉 CPU 换用哪一张地址翻译表。

细心的硬件和内核设计师在这里也动过不少省力的脑筋：比如不是每个程序都在算向量矩阵，很多系统会采取“惰性保存”策略或借助硬件标志位——只有线程真的动用了浮点/向量寄存器，才在切换时花力气把它们存盘恢复，既保证语义百分百正确，又省下白白搬运的开销。

## 慢镜头回放：一次上下文切换究竟经历了什么？

回到文章开头那两个终端的小实验。为了把过程看清，假设你的机器此刻只给这两个进程分配了**一颗** CPU 核心。

进程 A 正在跑，执行到 `input()` 发起读键盘的系统调用；键盘还没被按下，A 没法往下走，于是内核把 A 挪进等待队列，保存它的现场，把一直排在旁边的 B 换上 CPU。过了一会儿你敲下回车键，键盘中断把数据送进内核，内核把 A 从等待队列捞回就绪队列；注意，A 此时还没立刻抢回 CPU，它得等调度器在合适时机选中它、把现场填回寄存器，才从 `input()` 返回并打印出 `4`。

对照一下 A 在这三个阶段里截然不同的处境：

| A 所处的状态 | 真实含义 | 谁来推动它进入下一步 |
| --- | --- | --- |
| **运行（Running）** | 此刻正握着 CPU 执行指令 | 主动发起阻塞等待，或者时间片到了被抢占 |
| **等待 / 阻塞（Blocked）** | 缺的不是 CPU，是键盘/磁盘等外部条件 | 外部事件到来（如键盘中断），内核唤醒它 |
| **就绪（Ready）** | 万事俱备，只欠一颗空闲 CPU | 调度器点名选中它，恢复现场送上台 |

这里再次强调：**切换现场只保存和恢复极小的寄存器与指针状态**，进程那几百兆的代码、堆数据和打开的文件内容都留在原地一动不动，绝不会逐字复制。（想亲手算一算两个任务在一颗 CPU 上来回切换的时间账，可以先翻看第 3 章的[调度实验](03_cpu_scheduler_lab.md)。）

把时钟中断触发“从线程 A 切换到线程 B”的动作放慢到每一步，全过程就像一场默契的换班交接：

1. 时钟中断到来，CPU 硬件自动提权进入内核入口，并把 A 的最小用户态现场（程序计数器、栈指针、状态字等）压入 A 的内核栈；
2. 内核执行中断处理，更新计时，随后调用调度器，决定让 A 下台、换 B 上场；
3. 内核把 A 剩下的内核态寄存器保存到 A 的内核栈或控制块中；
4. 把 A 的状态从“运行”改成“就绪”，放回就绪队列；
5. 选定 B，把 CPU 的栈指针切到 B 的内核栈；若 B 与 A 属于不同进程，还需更换页表根指针以切换地址空间；
6. 从 B 的内核栈/控制块里把 B 当初下台时存好的寄存器一一恢复回来；
7. 执行中断返回指令，降回用户态，CPU 顺着 B 当初被打断的那条指令无缝接着跑。

```text
线程 A（用户态）
  -> 时钟中断进入内核，压入 A 的用户现场
  -> 处于 A 的内核上下文，调用调度器
  -> 切换内核栈（及必要时的页表），跨入 B 的内核上下文
  -> 恢复 B 的寄存器与用户现场
  -> 返回线程 B（用户态），仿佛从未暂停过
```

顺着第 5 步再多看一眼：**同进程内的线程切换**不需要更换页表，因为大家共用同一套地址映射；而**跨进程切换**不仅要换页表，还得让 CPU 里专门缓存近期地址翻译结果的硬件——[TLB（后备转换缓冲器）](../chapter_04_memory/02_page_tables_tlb_faults.md)——能够区分新旧两套地址空间，不能把 A 的翻译结果错拿给 B 用。

## 上下文切换的隐蔽账单：不只是保存几个寄存器

很多人跑完基准测试会纳闷：“保存恢复几十个寄存器才花几百纳秒，怎么一到高并发频繁切换，程序整体性能就掉了一大截？”

因为看得见的“显式开销”（进出内核、跑调度函数、读写控制块）只是冰山一角，真正伤筋动骨的往往是换人之后爆发的**隐式开销**：

- **缓存变冷**：A 刚才辛辛苦苦把常用数据搬进了速度飞快的 L1/L2 CPU 缓存，B 一上来立刻把这些缓存行全挤了出去；等一会儿 A 再切回来，又得重新从慢吞吞的主存里一趟趟把数据搬回来；
- **分支预测失灵**：CPU 硬件记住了 A 循环里的跳转习惯，换成 B 后预测频频猜错，流水线反复冲刷重来；
- **TLB 未命中**：跨进程切换后，B 的地址翻译大多不在高速缓存里，不得不反复去查内存里的页表；
- **跨核缓存一致性风暴**：如果 A 下次被调度到了另一颗核心上，它在旧核心里写过的脏缓存还得通过片上总线千里迢迢同步过来。

不妨把一笔切换总成本拆成两项来看：显式过门与换班耗时记作 $t_d$，新线程上台后因为缓存、预测器和 TLB 变冷而多付出的额外变慢记作 $t_c$，那么真实代价更接近：

$$
t_{switch}=t_d+t_c.
$$

其中 $t_c$ 往往比 $t_d$ 大出一个数量级，而且它强烈依赖程序的工作集大小、核心拓扑以及是否跨进程，绝不是一个能背下来的固定常数。

## 动手验证：在代码里亲眼看清进程与线程的身份

下面这段不到二十行的 Python 脚本会启动两条线程。跑一遍，亲眼核对两件事：它们打印出的进程号 `pid` 完全一样，但线程号 `thread` 截然不同；而且两者操作的是同一个全局列表 `shared`：

```python
import os
import threading

shared = []


def worker(name: str) -> None:
    shared.append(name)
    print("pid=", os.getpid(), "thread=", threading.get_ident(), "shared=", shared)


threads = [threading.Thread(target=worker, args=(str(i),)) for i in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
```

多跑几次你可能会发现，两条 `print` 的先后顺序、甚至 `shared` 打印出来时里面是一个元素还是两个元素，并不总是固定不变的——因为调度器随时可能切换它们。这个脚本故意用了最简单的 `append` 来展示“共享”，一旦你把这里换成“先读出来、算一下、再写回去”的复合步骤，立刻就会亲手撞上第 4 章的并发竞态。

## 多核、亲和性与非一致内存访问 { #numa }

当机器从单核变成 8 核、64 核甚至上百核，调度器迎来了新的头疼事。如果所有核心共用同一条全局就绪队列，每次选任务大家都得抢同一把队列大锁，核心越多堵得越惨；于是现代内核普遍给**每颗核心各配一条本地就绪队列**，平时各管各的，锁竞争几乎消失，而且线程尽量留在老核心上还能享受热乎的本地缓存。

可新麻烦随之而来：万一 0 号核心排了十个重活，7 号核心却闲得发慌，怎么办？调度器必须周期性地做**负载均衡**，把忙核心上的任务“偷”到空闲核心上去跑。这就成了一场拉锯战：迁得太勤，缓存局部性全毁；迁得太懒，算力白白浪费。

某些对延迟极度敏感的应用（比如高频交易引擎、音视频实时管线）或性能基准测试，不希望调度器把自己的线程传来传去，就可以利用 **CPU 亲和性**（CPU affinity）把线程钉在指定的几颗核心上。但这把双刃剑必须慎用：一旦人为绑得不合理，很容易造成绑定的那几颗核跑冒烟，旁边空闲的核却被规则拦在门外帮不上忙。

在多路服务器里，硬件还藏着另一层地形落差：内存条并不是到所有 CPU 核心都一样近，而是分成几组分别直连到不同的处理器插槽。处理器读写自己脚边那组“本地内存”飞快，要跨过主板互联通道去读另一颗处理器脚边的“远端内存”则会明显变慢，吞吐也更低。这种内存访问速度因位置而异的硬件组织，叫作**非一致内存访问**（Non-Uniform Memory Access，NUMA）。

在 NUMA 机器上，如果负载均衡器只看“那边有颗核心空着”，二话不说把线程迁到了远端插槽，却把它的几百兆内存留在原地没动，线程接下来每一次访存都要跨节点绕远路，性能反而可能断崖式下跌。这也解释了为什么在现代大型服务器上，CPU 调度和内存放置早已无法各自为政。

## 进程隔离不是铁板一块的孤岛

前面我们强调每个进程都有自己独立的虚拟地址空间，普通指针绝不可能凭空指到另一个进程的内存里去。但隔离的真正含义并不是“老死不相往来”，而是**所有跨界接触都必须走操作系统承认的受控渠道，并接受严格的权限核验**：

- 父进程可以把自己已经打开的文件描述符有选择地传给子进程；
- 两个进程可以向内核申请，把同一块物理内存映射进各自的地址空间实现共享；
- 进程可以通过管道、套接字或消息队列安全地收发字节与消息；
- 经由授权，进程还可以发送信号，或借助调试接口（如 `ptrace`）观察另一个进程。

没有受控通道，操作系统里就没有合作；没有权限边界，合作就会沦为入侵。

## 演进回头看：从进程、线程到协程

沿着时间轴往回看，计算执行抽象经历了一条清晰的瘦身轨迹：早期系统只有重量级的进程，一个地址空间绑定一条执行流；为了在一份共享数据上充分利用多核、降低协作门槛，操作系统把“资源容器”和“执行流”拆开，诞生了线程；到了互联网高并发时代，面对几十万条大多时间都在安静等网络回包的连接，连内核级线程的栈和切换开销都嫌重，于是各种语言运行时又在内核线程之上叠出了更细粒度的协程与异步任务。

请千万不要落入“协程已经彻底淘汰线程”的片面论调。每一次抽象演化，都是在用**增加一层调度复杂度与排错可见性成本**，去换取特定场景下固定开销的大幅下降。无论上层协程多么轻盈，落到硬件上它终究要靠底层的内核线程去占用 CPU 核心，要靠操作系统的系统调用去监听外部事件。

现在我们已经认识了进程与线程的骨架，也亲眼看清了上下文切换如何在幕后偷梁换柱。接下来，让我们沿着时间线走完一个进程从诞生、排队、协作到离场的完整一生——去[下一篇](02_scheduling_ipc.md)看看 Unix 奇特的“造人术”、同场竞技的调度策略，以及彼此隔绝的进程怎样重新开口对话。

## 自测

1. 同一个进程里的两条线程，究竟共享哪些资源，又必须各自独享哪些状态？
2. 同一进程内的两个线程发生上下文切换，虽然不用换页表，为什么依然会对性能产生隐式开销？
3. 纯用户级线程库面对“其中一条线程发起阻塞 I/O 会拖死全进程”的难题，现代运行时通常怎样破解？
4. 给关键线程设置 CPU 亲和性绑定核心，为什么既可能提速，也可能反而把整体吞吐拉低？
5. 用自己的话说清：“进入内核态”和“发生上下文切换”各自描述的是什么变化？

??? note "参考思路"

    1. 共享进程的虚拟地址空间（代码段、堆、全局变量）、打开文件表、工作目录和用户权限；各自独享程序计数器、通用寄存器、调用栈、线程局部存储（TLS）以及独立的调度状态。
    2. 虽然省去了更换页表和冲刷地址空间翻译的成本，但两条线程访问的代码与数据工作集不同，依然会挤占彼此的 L1/L2 缓存、扰乱 CPU 分支预测历史，跨核切换时还会带来缓存一致性迁移流量。
    3. 现代运行时通常把普通阻塞调用改写为底层的非阻塞 I/O + 事件多路复用（如 `epoll` / `kqueue`），把等待中的协程挂起并立刻切去跑其他就绪协程；对于实在没法异步化的阻塞系统调用，则交给专门的辅助内核线程池去接管，避免堵死主调度线程。
    4. 绑定核心能把线程稳留在热缓存与本地 NUMA 节点上，减少迁移抖动；但如果多个忙线程挤在少数被绑定的核心上，而其他未绑定的核心却空闲着无法分担负载，就会造成排队加剧和整体算力浪费。
    5. “进入内核态”是 CPU 权限级别从用户态切到内核态（可能只是替当前线程办一件系统调用或处理一次中断，办完照旧返回它）；“上下文切换”则是 CPU 执行的主体从一条线程换成了另一条线程，涉及保存与恢复线程现场。
