# 生命周期、调度与进程间通信

## 两个互不相见的世界，如何靠一根管道握手？

设想这样一个日常流水线：程序 A 一行行扫描日志、筛出用户名，程序 B 负责统计每个名字出现了多少次。在前一篇里我们已经知道，操作系统给 A 和 B 各自划出了互不相通的虚拟地址空间——A 的指针够不着 B 的内存，B 也看不到 A 的变量。既然隔离得这么严实，它们怎样才能接力干活？

Unix 给出的经典工具朴素得令人拍案叫绝：由内核在内存里辟出一小块有上限的环形缓冲区，把 A 的标准输出接到一头，把 B 的标准输入接到另一头。这条由内核托管的字节传送带，就叫作**管道**（pipe）。A 不断往里写字节，B 不断从另一头取走：只要缓冲区里还有货，B 就顺畅地读下去；一旦缓冲区空了、但 A 还没关闭写端，阻塞模式下的 B 就乖乖停下来睡觉等新数据；直到所有写端彻底关闭、缓冲区里最后一滴字节也被取光，B 才会读到“文件结束（EOF）”并安心收工。

??? question "如果 B 处理得越来越慢，而 A 却一刻不停地狂写，管道会不会把整台机器的内存撑爆？"

    不会。内核给管道配的缓冲区容量是有限的（例如 Linux 上默认往往只有几十 KB）。一旦 B 来不及消费，缓冲区很快就会被塞满：此时阻塞写模式下的 A 会被内核暂停，直到 B 腾出空位才被唤醒继续写；若是非阻塞写，内核则会立刻返回“暂时写不进去了”的错误码。这种由慢下游反过来顶住快上游、防止系统崩溃的节流力量，就是分布式与操作系统里反复出现的**背压**（backpressure）。

你看，就在这短短几秒的流水线里，一个进程已经悄悄切换了好几次身份：正在算数据时占用着 CPU，缓冲区满了就进入等待，空位腾出来了又重新排队抢 CPU。本篇就沿着这条主线，把进程从诞生到退出的**生命周期**、争夺 CPU 的**调度策略**，以及跨越隔离边界的**进程间通信（IPC）**揉进同一张大图里讲透。

## 进程状态机：先分清它在“等 CPU”还是在“等事件”

线上排查卡顿时，新手最容易说的一句话是：“这个进程半天没动静，肯定是 CPU 不够用了！”可真相往往截然相反——CPU 空闲率高达 90%，那个进程只是死死卡在等一块慢吞吞的硬盘或一把别人没放开的锁上。

为了不再把两种截然不同的“没动静”混为一谈，我们用一张最精炼的状态迁移图盯紧任务的处境：

```text
新建 -> 就绪（Ready） <======> 运行（Running） -> 退出（Terminated）
          ^                       |
          |  事件就绪（唤醒）       |  等待 I/O、锁或定时器（阻塞）
          +----- 等待/阻塞 <------+
                  (Blocked)
```

三个核心状态泾渭分明：

- **运行（Running）**：此刻正稳稳握着一颗 CPU 核心，一条条执行自己的指令；
- **就绪（Ready）**：万事俱备、代码随时能跑，唯一缺的就是一颗空闲的 CPU；
- **等待 / 阻塞（Blocked）**：缺的根本不是 CPU——它在等网卡回包、等磁盘读完、等管道腾出空位，或是等另一条线程释放锁。就算你现在把整台机器的 CPU 全送给它，它也一步都迈不出去。

如果一个任务正在运行，却因为时间片用完、或者来了更紧急的任务而被调度器硬请回就绪队列，这个动作叫作**抢占**（preemption）；而如果它是因为要等外部条件主动交出 CPU 睡去，则叫作**阻塞**。分清一个慢任务是困在“就绪队列”还是困在“阻塞队列”，是性能优化的第一把钥匙：前者该加核、调优先级或减 CPU 负载，后者加再多 CPU 也无济于事，得去查 I/O、锁或对端服务。

## 进程从哪儿来？奇特而精妙的 `fork` 与 `exec`

你在终端里敲下 `ls` 并回车，屏幕上瞬间列出了文件清单。有没有想过，操作系统究竟是怎么把这个新进程“变”出来的？

大多数人按直觉会猜：系统提供一个 `create_process("ls", args)` 接口，直接新建一个空壳进程、把 `ls` 的程序代码塞进去跑不就完事了？Unix 的先驱们却走出了一步极其出人意料的棋——他们把“生出一个新进程”硬生生拆成了两步：**先克隆自己，再脱胎换骨换装新程序**。

1. **`fork()`（分叉克隆）**：当前进程（父进程）调用 `fork`，内核瞬间复制出一个几乎一模一样的子进程。奇妙的是，这次调用会**返回两次**——在父进程里返回新子进程的 PID，在子进程里返回 `0`，两兄弟从此各走各的分支。
2. **中场改装**：在真正运行新程序前的这短短几行代码里，子进程还是自己人，它可以从容地改掉自己的标准输入/输出（比如接上刚才讲的管道、重定向到文件）、切换工作目录、调整环境变量或收紧权限，而丝毫不影响父进程。
3. **`exec()`（换壳重生）**：改装完毕，子进程调用 `exec` 家族系统调用。内核清空它原有的代码、堆和栈，把磁盘上新程序（如 `ls`）的指令和数据装进这具躯壳里，从新程序的 `main` 函数重新起步。注意：PID 没变，刚才接好的管道和文件描述符也原封不动留了下来！
4. **`wait()`（收尾领尸）**：父进程调用 `wait` 或 `waitpid`，等待子进程跑完，顺手领走它的退出码，通知内核彻底清理它的档案。

看到这里，你大概会忍不住惊呼：“太聪明了！正是因为把 `fork` 和 `exec` 拆开，Shell 才能在中间无缝插入输入输出重定向和管道，而新程序自己压根不需要操心！”

可紧接着第二个疑问就会砸过来：如果一个占了 4 GB 内存的大进程调用 `fork`，紧接着下一微秒子进程就调 `exec` 把整片内存扔掉换新程序，那 `fork` 时傻傻地拷贝 4 GB 内存岂不是冤大头？

现代操作系统用一个极其漂亮的戏法彻底化解了这个浪费，叫作**写时复制**（copy-on-write，COW）。调用 `fork` 的那一刻，内核压根不拷贝那 4 GB 物理内存，而是让父子进程的地址翻译表指向**同一批物理内存页**，顺手把这些共享页统统标成“只读”。如果子进程立刻 `exec`，几乎一字节内存都没白拷；只有当父子任何一方真的试图改写其中某一页时，硬件才会触发一次只读异常，内核趁机把**被改写的那一页**单独复制一份给写者，其余未改动的页照旧共享。[第 5 章虚拟内存](../chapter_04_memory/01_address_space_paging.md)会带你亲眼看清页表怎样施展这个戏法。

### 一个五脏俱全的最小例子

```c
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        execlp("printf", "printf", "child process\n", (char *)0);
        _exit(127);
    }
    if (pid > 0) {
        int status;
        waitpid(pid, &status, 0);
    }
    return pid < 0;
}
```

留意第 9 行的一个精妙细节：`execlp` 一旦成功，子进程原来的代码已经被彻底换掉，绝不会再返回到下一行；只有当找不到程序或权限不足导致 `exec` 失败时，才会落到 `_exit(127)`。之所以用 `_exit` 而不是 C 库的 `exit`，是为了防止子进程在仓促退出时，把从父进程那里一并继承来的未刷新输出缓冲区再替父进程多打印一遍。

## 僵尸进程与孤儿进程：善终为什么这么讲究？

顺着刚才的 `wait` 往深处追一句：如果子进程早就跑完 `exit` 退出了，父进程却忙着干别的、一直忘了调用 `wait`，内核能不能直接把子进程的记录删干净？

不能！万一父进程五秒钟后突然想起来问一句“我那个孩子是正常退出还是报错退出的？”，如果档案早就烧了，内核就答不上来了。于是，内核只能把子进程占的大块内存、打开的文件全都释放掉，唯独在进程表里死死留着它那一小行骨架记录（存着 PID、退出状态和资源统计），直到父进程来 `wait` 把它领走。这种“已经停止执行、但档案还没被回收”的状态，被形象地称作**僵尸**（zombie）进程。偶尔冒出一两个僵尸无伤大雅，但如果一个长寿服务源源不断地 `fork` 子进程却从不 `wait`，成千上万具僵尸最终会把系统的 PID 配额占满，导致整台机器再也起不来任何新进程。

与它经常成对出现、却完全是另一回事的是**孤儿**（orphan）进程：父进程自己先退出了，子进程还在活蹦乱跳地跑着。这下谁将来给子进程收尸呢？别担心，内核会立刻把这些没了爹的孤儿过继给指定的“收养者”（通常是 1 号初始化进程或容器里指定的回收进程），等孤儿将来退出时由收养者负责 `wait` 善后。记住这句顺口溜绝不会再混：**僵尸是“死了没人收”，孤儿是“活着没了爹”。**

## 怎么评判一个调度算法好不好？先造几把尺子

机器上同时排着几十个就绪任务，调度器每次只能挑一个上 CPU。凭什么说算法 A 比算法 B 高明？空口争论没意义，先拿出定量标尺。

假设一个任务在时刻 $a$ 到达就绪队列，在时刻 $s$ 第一次摸到 CPU，总共需要消耗 CPU 干活的时间是 $b$，最终在时刻 $f$ 彻底完工。由此立刻可以量出三个最关键的指标：

$$
T_{turnaround}=f-a,
$$

$$
T_{response}=s-a,
$$

$$
T_{waiting}=T_{turnaround}-b.
$$

- **周转时间**（turnaround time，$T_{turnaround}$）：从提交到彻底干完总共熬了多久，批处理后台作业最看重它；
- **响应时间**（response time，$T_{response}$）：从提交到**第一次**得到反馈等了多久，敲键盘、点按钮、打开网页的交互体验全系于此；
- **等待时间**（waiting time，$T_{waiting}$）：任务明明已经就绪、却干耗在队伍里没拿到 CPU 的总冤枉时间；
- 除此之外，系统层面还要盯着**吞吐量**（单位时间干完几票活）、**公平性**（有没有人一直挨饿）以及某些特定场景下的**截止期限**。

实战中切忌只看平均值：如果 99 次请求都在 2 毫秒内返回，唯独 1 次卡了 3 秒钟，平均延迟看起来依然很漂亮，可用户的抱怨早已炸开了锅。因此交互式服务往往紧盯着 P95、P99 这类**高分位长尾延迟**。

## 经典调度策略同台竞技

有了量尺，我们让几大经典调度策略依次登场，看看每一次改进是为了堵住前一位的什么漏洞，又意外挖出了什么新坑。

### 1. 先来先服务（FCFS）：最老实，却怕大块头挡道

**先来先服务**（first-come, first-served，FCFS）就像超市只有一个收银台：谁先排队，就一路算完再轮下一位。它实现简单、毫无切换折腾，但有一个致命毛病——想象你手里只拿了一瓶矿泉水，前面却刚好排着一位推着两满车年货的顾客。在操作系统里，只要一个耗时 10 秒的纯计算长作业抢先一步上了 CPU，后面紧跟着的十个只需 1 毫秒的交互短任务全得跟着干等 10 秒！这种“一个慢大个堵死一长串小快艇”的现象，叫作**护航效应**（convoy effect）。

### 2. 最短作业优先（SJF）：数学上最优，现实里犯难

既然大块头挡道让平均等待时间飙升，反过来想：如果我能一眼看穿谁干活最快，永远先放最短的作业插队，会怎样？可以严格证明，当所有作业同时到达且不允许抢占时，**最短作业优先**（shortest job first，SJF；若允许新来的更短作业打断正在跑的长作业，则演进为“最短剩余时间优先”）能够把平均等待时间和平均周转时间压到理论最低。

可惜，它撞上了两堵现实高墙。第一，**调度器没有水晶球**——程序刚启动时，操作系统根本不知道它究竟要跑 2 毫秒还是 2 小时，最多只能靠历史表现去猜；第二，如果短作业源源不断地涌进来，排在后面的长作业可能永远轮不到自己，陷入漫长的**饥饿**（starvation）。

### 3. 时间片轮转（RR）：人人有份，但切多细最头疼

既然猜不准未来谁短谁长，交互系统干脆祭出“雨露均沾”大法——**时间片轮转**（round robin，RR）。调度器规定一个固定长度的时间片 $q$（比如几毫秒）：每个人上台最多跑满 $q$，时钟中断一响，不管你干没干完，立刻被请回队尾排队，换下一位上场。

这么一来，就算前面排着个十小时的巨无霸，新来的短任务最多等上一圈时间片就能摸到 CPU，响应时间大幅改善。但 $q$ 该设多大？设得太大（比如 10 秒），轮转就退化成了笨拙的 FCFS；设得太小（比如 10 微秒），响应似乎飞快，可 CPU 几乎全忙着保存恢复现场去了。如果每次上下文切换要耗掉 $c$，忽略其他因素，CPU 真正用来算有效业务的时间占比上限大约是：

$$
U=\frac{q}{q+c}.
$$

增大 $q$，有效利用率 $U$ 贴近 1，却拉长了响应延迟；缩小 $q$，响应变得轻快，切换损耗却节节攀升。这就是教科书级的吞吐—延迟权衡。

### 4. 优先级调度与多级反馈队列（MLFQ）：用历史猜性格

现实里的任务并不生而平等：音频播放不能破音，系统守护进程不能卡死，后台索引任务晚两秒没人介意。于是系统引入**优先级**：高优先级先跑。为了防止低优先级任务永远被压在底层饿死，调度器还会配合**老化**（aging）机制——一个任务在队列里干等得越久，系统就悄悄给它涨一点优先级，保证它迟早能浮出水面。

更聪明的做法是把“优先级”和“动态观察”合二为一，诞生了大名鼎鼎的**多级反馈队列**（multi-level feedback queue，MLFQ）。它不要求程序提前坦白自己要跑多久，而是边跑边看行为画像：
- 新来的任务先放进最高优先级队列，给个较短的时间片试跑；
- 如果它在时间片用完之前就主动去等键盘、等网络了，说明它很可能是个“短平快”的交互型任务，下次醒来继续留在高优先级享福；
- 如果它一口气把整片时间片吃干抹净还不撒手，说明它是个计算密集型大块头，调度器就把它降一级队列，给更长的时间片但让它在空闲时再跑；
- 每隔一段较长时间，再把所有任务统一拉回顶层队列“洗一次牌”，既防饥饿，也照顾到那些突然从纯计算转入交互阶段的任务。

MLFQ 的直觉极富美感，代价则是调参颇为考究（几级队列、每级时间片多大、多久洗一次牌），而且如果恶意程序摸清了规则——故意在时间片快耗尽前假装发一个无意义的 I/O 骗取留在高优先级——还可能钻它的空子。

### 5. 公平调度：不再只靠固定队列，而是记一笔“欠账”

现代通用操作系统（比如 Linux 上沿用多年的完全公平调度器 CFS 及其演进版本 EEVDF）换了一种更统一的视角：既然要兼顾多任务公平与交互流畅，不如给每个任务记一本“虚拟运行时间”账本。按权重折算，谁目前拿到的 CPU 时间最少（欠它的服务最多），调度器就优先挑谁上台。一个刚从睡眠里醒来的交互任务，因为睡着期间账本没涨，天然就是“被欠得最多”的那个，于是不用硬编码一堆复杂队列，自然而然就获得了极快的唤醒响应。当然，落地到真实内核时，权重分配、最小切换粒度防止抖动、以及多核之间的账本平衡，依然充满了精细的工程打磨。

## 当“慢一毫秒就是事故”：实时调度

普通桌面和服务器关心的是“平均快、别太卡”，可换成工厂机械臂控制、汽车刹车系统或飞行控制计算机，规则瞬间变了味：算出来的结果就算分毫不差，只要晚到 1 毫秒，机械臂就已经撞毁了。

这类系统叫作**实时**（real-time）系统。请牢记：**“实时”的核心不是“跑得飞快”，而是“可预测地按时兑现截止期限”。**
- **硬实时（Hard Real-Time）**：错过一次截止期限就是系统性失败甚至灾难（如安全气囊触发）；
- **软实时（Soft Real-Time）**：偶尔晚一点只会让体验降级（如视频会议掉一帧、音频咔哒一声），但还不至于酿成大祸。

拿一组周期性任务来算笔底账：如果第 $i$ 个任务每隔周期 $T_i$ 就要来一次，每次需要占用 CPU 时间 $C_i$，那么这组任务在单核上的总 CPU 利用率就是：

$$
U=\sum_i\frac{C_i}{T_i}.
$$

直觉上，$U \le 1$ 是单颗 CPU 有希望按时干完所有活的必要门槛——要是总需求都超过 100% 了，神仙调度器也变不出时间来。但切记：$U \le 1$ 只是入门的必要条件，并不自动保证任何调度策略都能百分百守住截止期限；具体的调度算法（如单调速率调度 RMS 或最早截止期限优先 EDF）、锁阻塞时长、不可抢占区和切换开销，都必须一并纳入严格的可调度性分析。

## 走出单核：多核调度牵出的联动难题

把调度放进真实的多核大机器里，事情就远不只是挑一个队列头那么简单了：

- **本地队列与跨核迁移的博弈**：每核维护本地运行队列确实避开了全局锁拥堵，可一旦某些核闲下来就得跨核偷任务。把线程迁去空闲核能立刻让它跑起来，却要付出新核缓存全冷的代价；在[非一致内存访问（NUMA）机器](01_process_thread_context.md#numa)上，新核隔着插槽去够原节点的内存，延迟甚至可能翻倍。
- **逻辑核心不等于完整物理核心**：开启同时多线程（如 Intel 超线程）时，一颗物理核心伪装成两个逻辑 CPU，它们依然共用着底层的执行单元和缓存；把两个吃满浮点运算的重线程塞到同一颗物理核的两个逻辑核上，远不如把它们摊到两颗独立物理核上跑得快。
- **优先级反转（Priority Inversion）**：设想高优先级任务 H 想拿一把锁，偏偏这把锁正攥在低优先级任务 L 手里；更倒霉的是，中等优先级任务 M 根本不要这把锁，却凭着优先级比 L 高，一路抢占着 CPU 不让 L 运行！结果 L 永远没机会跑到解锁那一行，最高优先级的 H 反而被不相干的 M 活活拖死。这就是经典的**优先级反转**（当年火星探路者号探测器就曾栽在这上面）。经典解药之一是**优先级继承**（priority inheritance）：只要 H 卡在 L 拿着的锁上，内核就临时把 L 的优先级拔高到和 H 一样，让 L 赶紧跑完解锁，随后恢复原状。

可见，调度从来不是一座孤岛，它与锁机制、内存拓扑、芯片功耗甚至温度降频紧紧纠缠在一起。

## 跨过隔离墙：五花八门的进程间通信（IPC）

既然操作系统费尽心思把每个进程关进了各自独立的虚拟地址空间，那需要协同作业的多个进程，究竟该怎样安全地交换数据与步调？这就是**进程间通信**（IPC）大显身手的舞台。不同 IPC 机制本质上是在“速度”“消息结构”“跨机器能力”和“使用复杂度”之间做了不同的取舍。

### 1. 管道（Pipe）

开篇已经见识过它的魅力：由内核维护的一段单向字节流缓冲区，天然自带背压，最擅长把一组命令首尾相连（就像你在 Shell 里敲下 `cat log.txt | grep ERROR | wc -l`）：

```text
producer stdout -> 内核 pipe 缓冲区 -> consumer stdin
```

它极度简单可靠，但也有明确边界：它只认连续的字节流、不替你保留“两条消息从哪儿切开”的边界，单向流动，也不支持像读文件那样跳来跳去随机定位。

### 2. 消息队列与套接字（Socket）

如果两个无关进程需要双向对话、发送结构清晰的请求与应答，或者干脆隔着网络跑在两台不同的机器上，管道就不够用了。**消息队列**保留了每条消息的边界；**Unix 域套接字**专为同一台机器上的进程打造，免去了复杂的网络协议栈打包却提供双向全双工通道和权限核验；而**网络套接字**把这套接口无缝延伸到了局域网与互联网。这类机制由内核帮你打理缓冲、流控和身份校验，代价是数据通常要经由内核做拷贝、序列化与协议处理。

### 3. 共享内存（Shared Memory）

如果要在本机两个进程间每秒搬运几个 GB 的高清视频帧或机器学习张量，数据先从进程 A 拷进内核、再从内核拷进进程 B，光内存带宽就耗不起。这时最快的办法是直接请内核把**同一批物理内存页同时映射进 A 和 B 两个进程的地址空间**——这就是**共享内存**（shared memory）。A 往里写完，B 抬头立刻就看见了，零额外数据拷贝！

但千万别把它想得太省心：共享内存只解决了“大家都能看见同一片字节”，压根不操心“A 写到一半 B 就抢着读了怎么办”“读完之后谁负责回收这块空间”。因此，实战中它永远要配上一整套外围纪律：

```text
共享内存数据区 + 互斥锁/原子操作/信号量同步协议 + 清晰的读写所有权约定
```

没有同步协议护航的共享内存，只不过是帮你以最高速度制造并发崩溃而已。

### 4. 信号与轻量事件通知

有时候进程间根本不需要传大块数据，只需要隔空拍一下肩膀说“配置改了，重读一下”或者“赶紧优雅退出”。**信号**（以及 Linux 上的 `eventfd` 等轻量事件通知对象）就最适合这种小巧的异步打招呼。但切记，信号处理函数执行时机极其突然，里面能安全调用的库函数寥寥无几，最佳实践是只在信号处理器里改一个原子标记或往管道写一个字节，把真正的业务逻辑留回主循环从容处理。

### 一张速查表帮你做选型

| 协作场景 | 优先考虑的 IPC 方式 | 必须接住的主要代价 |
| --- | --- | --- |
| Shell 风格的单向流式拼接 | 管道（匿名/命名） | 单向字节流，无天然消息边界与随机访问 |
| 本机结构化的请求/响应服务 | Unix 域套接字、消息队列 | 内核拷贝、序列化与自定义协议解析 |
| 跨机器分布式协作 | 网络套接字（TCP/UDP） | 网络延迟、丢包、乱序与局部故障 |
| 本机超大吞吐量数据交换 | 共享内存 | 必须自己设计严格的同步、边界与生命周期协议 |
| 极简的异步状态提醒 | 信号、事件通知对象 | 承载信息极少，异步处理上下文受限 |

## 有界通道的宿命：背压与部分失败

无论你选了管道、消息队列还是网络套接字，只要通信链路中间有缓冲区，迟早都要面对一个灵魂拷问：**下游处理不过来、缓冲区塞满的那一刻，系统该怎么办？**

可供选择的策略无非五种：让上游**阻塞**等待、直接**丢弃**新消息、**覆盖**掉最老的旧数据、临时**扩容**，或者立刻报错把压力向上游传导。无论选哪一种，都必须是有意为之的设计——假装用“无限大缓冲”回避背压，只不过是把局部拥堵拖延成整个进程内存耗尽的雪崩。

而一旦通信跨越进程甚至跨越机器，失败的方式也会骤然翻倍：对端可能毫无征兆地崩溃退出，连接可能只关了一半，消息可能超时重发导致重复送达。在跨机器通信里尤其残酷：当你等了三秒没收到回包时，你根本无法仅凭“沉默”分辨请求究竟是**半路丢了压根没执行**、**对方正在慢吞吞执行**，还是**对方早就执行完但回包在路上丢了**——这道阴影，我们会在第 12 章聊集群任务重试与幂等时再次正面交锋。

到这里，进程的生死流转、调度器的策略博弈以及 IPC 的协作手段都已铺陈完毕。纸上谈兵终觉浅——FCFS 和时间片轮转的响应时间到底差出多少？等 CPU 和等磁盘在时间线上究竟长什么样？不妨拿起纸笔、打开终端，直接进入下一章的[调度实验：就绪、运行与等待](03_cpu_scheduler_lab.md)亲手算一算、看一看。

## 自测

1. 发现线上服务慢得异常时，为什么先查清楚线程处于“就绪”还是“阻塞”，会直接决定截然不同的优化方向？
2. 当一个占用大量内存的父进程 `fork()` 后立刻在子进程里调用 `exec()`，写时复制（COW）到底帮系统省下了什么？
3. 有人说“为了追求极致响应，把时间片轮转的 $q$ 调得越小越好”，这句话错在哪里？
4. 既然共享内存免去了内核拷贝、速度快到飞起，为什么还说“单靠共享内存本身算不上完整的通信方案”？
5. 用一句话区分僵尸进程和孤儿进程，并说说哪一种如果放任不管更容易引发系统故障？

??? note "参考思路"

    1. 处于“就绪”说明任务有活可干却排不上 CPU，瓶颈在计算算力竞争，优化方向是减负、提算法效率或加核；处于“阻塞”说明它在等 I/O、锁或外部响应，加再多 CPU 也帮不上忙，必须去查慢磁盘、慢网络或锁竞争。
    2. 省去了在 `fork()` 时把父进程整片物理内存逐页复制一份的巨大时间与空间开销——反正紧接着的 `exec()` 马上就会丢弃这整片地址空间，有了写时复制，父子只在短短间隙里共享只读页表映射，几乎零拷贝。
    3. 根据 $U = q / (q + c)$，时间片 $q$ 过小时，上下文切换的显式开销与缓存变冷的隐式损耗会占据绝大部分 CPU 时间，真正用于推进有效计算的比例暴跌，最终吞吐量和响应时间可能双双恶化。
    4. 共享内存只让两个进程看到了同一批物理页里的字节，既没有规定消息边界和读写顺序，也不提供互斥与唤醒机制；若缺少配套的同步协议与所有权约定，并发读写会立刻酿成数据损坏和竞态。
    5. 僵尸是“子进程已退出但父进程还没 `wait` 回收其档案”，孤儿是“父进程先退出、活着的的子进程被系统过继收养”。放任不管时，大量僵尸持续堆积会耗尽进程号与进程表槽位，更容易引发系统无法创建新进程的故障。
