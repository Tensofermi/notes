# 调度实验：就绪、运行与等待

## 先分清谁在等 CPU，谁在等输入

设 A、B 都在时刻 0 就绪，A 先拿到 CPU，运行 2 个单位后去等磁盘。A 阻塞的这段时间，B 可以继续跑。若 A 的磁盘操作在时刻 5 结束，它会回到就绪队列；但如果 CPU 正给 B 用，A 还得排队，不能马上继续。注意这里有两种完全不同的“等”：等磁盘时 A 没有工作可做，等 CPU 时 A 明明可以跑却排不上号。动手画时间线时，建议把这两种等待涂成两种颜色——后文的自测就藏在这个区别里。

??? question "A 从 2 等磁盘到 5，从 5 排到 6。它的就绪等待多了多少？"

    从 5 到 6 的 1 个单位计入就绪等待。磁盘等待的 3 个单位会增加周转时间，但那时 A 没有可立即执行的工作。

**先修**：[进程与上下文切换](01_process_thread_context.md)、[调度与进程间通信](02_scheduling_ipc.md)。

**读完能做**：画出调度时间线，并分清响应时间、等待时间和周转时间。

## 同一颗 CPU，两种选择

上一篇把调度策略讲了个遍，它们到底差多少？用两个任务、一颗 CPU 算一笔账就明白了。在时刻 0，任务 A 先进入队列，需要 6 个时间单位，任务 B 紧接着到达，需要 2 个单位。假设它们始终可运行，切换开销先记为零。

| 策略 | 时间线 | A 第一次运行 | B 第一次运行 | B 完成 |
| --- | --- | ---: | ---: | ---: |
| FIFO | A 0–6，B 6–8 | 0 | 6 | 8 |
| 轮转，时间片为 2 | A 0–2，B 2–4，A 4–8 | 0 | 2 | 4 |

B 在轮转里更早得到响应。更频繁切换会增加实际开销，可能破坏缓存局部性。周转时间从到达到完成计算；等待时间累计任务处于可运行但没占到 CPU 的时段。若 B 等待磁盘，它会进入阻塞状态，磁盘等待影响周转时间，但不计作就绪队列等待。

## 在自己的终端观察

纸上的状态图能不能在真实系统里看到？完全可以。在 Linux 上，先打开一个终端并运行：

```sh
sleep 20
```

在另一个终端运行 `ps -C sleep -o pid,stat,time,comm`。这条命令选出名为 `sleep` 的进程，显示编号（`pid`）、当前状态（`stat`）、累计 CPU 时间（`time`）和命令名（`comm`）。例如 `S` 通常表示可被唤醒的睡眠，实际经过了多少秒也可以用钟表另记。再运行一个短小的 CPU 循环，并比较系统监视器中的 CPU 时间和墙钟时间。采样可能错过短促状态，实验重点是区分等待原因和使用量。进程频繁切换、等待内存或 I/O 时，单个百分比只能提示下一步查什么。

## 到集群后哪里变了

到目前为止，故事都发生在一台机器里。内核在本机可运行线程中选择接下来占用 CPU 的线程。多台机器一起接任务时，还得先问「这项任务能不能用这些资源、应该在哪台机器运行」。真正启动后，线程仍要轮流取得这台机器的 CPU 时间。继续用[两台机器和一项双卡任务](../chapter_08_workload_platform/01_jobs_and_admission.md)推演它的额外等待。

## 自测

如果 A 每运行 1 ms 就阻塞等待磁盘，B 一直可运行，看到 B 消耗了更多 CPU 时间意味着什么？

??? note "参考思路"
    至少说明 B 得到更多 CPU 执行时间。A 可能主要在等待 I/O；需要检查 A 完成了多少工作、阻塞了多久，才能判断调度是否公平或是否存在 I/O 瓶颈。
