# 调度实验：就绪、运行与等待

**先修**：[进程与上下文切换](01_process_thread_context.md)、[调度与进程间通信](02_scheduling_ipc.md)。

**读完能做**：画出调度时间线，并分清响应时间、等待时间和周转时间。

## 同一颗 CPU，两种选择

在时刻 0，任务 A 先进入队列，需要 6 个时间单位，任务 B 紧接着到达，需要 2 个单位。假设它们始终可运行，切换开销先记为零。

| 策略 | 时间线 | A 第一次运行 | B 第一次运行 | B 完成 |
| --- | --- | ---: | ---: | ---: |
| FIFO | A 0–6，B 6–8 | 0 | 6 | 8 |
| 轮转，时间片为 2 | A 0–2，B 2–4，A 4–8 | 0 | 2 | 4 |

B 在轮转里更早得到响应。更频繁切换会增加实际开销，可能破坏缓存局部性。周转时间从到达到完成计算；等待时间累计任务处于可运行但没占到 CPU 的时段。若 B 等待磁盘，它会进入阻塞状态，磁盘等待影响周转时间，但不计作就绪队列等待。

## 在自己的终端观察

在 Linux 上，先打开一个终端并运行：

```sh
sleep 20
```

在另一个终端运行 `ps -C sleep -o pid,stat,time,comm`，观察进程状态与累计 CPU 时间。再运行一个短小的 CPU 循环，并比较系统监视器中的 CPU 时间和墙钟时间。采样可能错过短促状态，实验重点是区分等待原因和使用量。进程频繁切换、等待内存或 I/O 时，单个百分比只能提示下一步查什么。

## 到集群后哪里变了

内核在本机可运行线程中选择接下来占用 CPU 的线程。集群还要先判断任务占用的资源是否获准，并决定 Pod 放在哪个节点。到节点实际执行时，进程仍要接受本机的调度与 cgroup 约束。继续读[集群编排](../chapter_08_workload_platform/01_jobs_and_admission.md)。

## 自测

如果 A 每运行 1 ms 就阻塞等待磁盘，B 一直可运行，看到 B 消耗了更多 CPU 时间意味着什么？

??? note "参考思路"
    至少说明 B 得到更多 CPU 执行时间。A 可能主要在等待 I/O；需要检查 A 完成了多少工作、阻塞了多久，才能判断调度是否公平或是否存在 I/O 瓶颈。
