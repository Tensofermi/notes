# 进程、线程与调度 { #2 }

## 先在两个终端跑一次

在两个窗口[运行同一段代码](01_process_thread_context.md)，对照进程号和输出。接下来用[管道](02_scheduling_ipc.md)让两个进程合作，再用[调度练习](03_cpu_scheduler_lab.md)区分正在运行、等 CPU 和等输入。

先用一个简化的模型：一个 CPU 核心同一时刻只能执行一条指令流。可明明只有这一条指令流，编辑器和浏览器却看上去在同时运行——秘密在于它们轮流使用处理器，切换得快到让你察觉不到。这里需要三个本章反复使用的词：程序的一次运行叫**进程**（process），进程中的一条执行流叫**线程**（thread），决定“接下来运行哪条线程”的内核部件叫**调度器**（scheduler）。

## 本章的核心矛盾

编辑器希望尽快响应按键，而后台转换任务希望每秒处理更多文件。它们一起排队时，先运行谁就成了一个无法两全的取舍：让编辑器优先，吞吐量受损；让转换任务跑个够，按键就卡顿。切换本身也不是免费的：换一条线程上来之前，要记住原来那条接下来执行哪条指令、寄存器里都是什么，这一整套状态叫 **CPU 上下文**（context）。还有两个描述线程处境的词：线程因等待输入而主动暂停叫**阻塞**（blocking）；线程明明还能跑，调度器却硬把它换下去，叫**抢占**（preemption）。

```text
可运行任务集合
  -> 调度策略选择一个任务
  -> 恢复它的 CPU 上下文
  -> 运行至阻塞、退出或被抢占
  -> 更新状态与队列
  -> 再次调度
```

- 程序、进程、线程分别是什么？

- `fork`、`exec`、`wait` 在进程生命周期中各做什么？
- 管道、共享内存和消息传递分别适合什么情形？

## 与并发章节的连接

调度器可能在几乎任意可抢占点切换线程，所以一段“看起来连续”的源代码并不一定原子地执行完。两条线程的操作一旦交错，计数器就能莫名其妙地少加一次——这个看似不可思议的 bug，正是[并发章节](../chapter_03_concurrency/index.md)要用竞态、锁和条件变量驯服的猛兽。
