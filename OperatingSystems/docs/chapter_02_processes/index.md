# 进程、线程与进程间通信 { #2 }

## 一颗 CPU，怎么让人觉得几十个程序在同时跑？

先按一个最朴素的画面去想：一颗 CPU 核心在同一瞬间其实只能沿着一条指令流往下走，根本分身乏术。可你的电脑上明明同时开着编辑器、音乐播放器和十几个浏览器标签页，敲键盘跟手，放歌不卡顿，后台还在刷刷地下载文件。

魔法并不存在，秘密全在“极快地轮流上台”：操作系统把正在运行的程序打包成可以随时暂停、稍后无缝续上的运行实体，再安排一位挑剔的裁判在毫秒级别把它们轮流换上 CPU。只要切得足够快，人类肉眼就会被骗过去，仿佛每个程序都独自霸占着一颗处理器。

如果想亲手戳破这层“同时运行”的幻觉，本章准备了三条循序渐进的路：先在两个终端里[同时跑起同一段小代码](01_process_thread_context.md)，看看操作系统怎样给它们发不同的身份证、让它们各自停在不同进度上；接着[拿一根管道把两个彼此隔绝的程序连起来](02_scheduling_ipc.md)，顺着一个程序从生到死的完整生命周期，看清系统怎么安排它们排队与对话；等机制摸透了，紧随其后的第 3 章还有一份[手算与终端观测的调度实验](03_cpu_scheduler_lab.md)，让你亲眼分辨“在等 CPU”和“在等磁盘”究竟差在哪里。

## 贯穿本章的核心矛盾

把多个任务放到同一颗 CPU 上轮流跑，立刻会撞上两重避不开的取舍。

第一重取舍在**目标冲突**。你敲下编辑器里的一个字母，巴不得 10 毫秒内屏幕上就蹦出来——这追求的是极低的响应延迟；与此同时，后台的编译或视频转码程序却希望别老被打断，一口气把活干完最划算——这追求的是更高的吞吐量。两类性格截然不同的任务挤在同一条队伍里，先宠着谁、委屈谁，永远没有完美答案。

第二重取舍在**切换本身的代价**。把台上的任务请下去、换另一个任务上来，绝不是喊一声“换人”那么轻巧：你得把刚下台那个任务跑到哪条指令、寄存器里攒了什么中间结果一一抄录下来，再把新上台那个任务的档案原样填回硬件，顺带还可能把 CPU 原本捂热的缓存搅凉。切得太勤，大家好像都很公平，可 CPU 一大半力气都花在了“换人”的折腾上；切得太懒，系统虽然干活卖力，鼠标和键盘却卡得像幻灯片。

```text
等待上台的任务集合
  -> 调度策略挑出下一位
  -> 恢复它的执行现场，送上 CPU
  -> 跑一段，直到主动等 I/O、干完退出，或时间到了被强行换下
  -> 抄录现场、更新状态并放回对应队列
  -> 开启下一轮挑选
```

这套循环往复的节奏，就是现代多任务操作系统的心跳。

## 通往后续章节的悬念

学完进程、线程和调度，你会意识到一个让人脊背发凉的事实：既然调度器可以在几乎任何指令间隙，神不知鬼不觉地把一条线程换下去、换另一条同进程线程上来，那么源码里看似顺理成章的一句 `count++`，在多条线程同时执行时完全可能被从中间劈成两半、互相踩踏，导致最终计数莫名其妙少了一大截。这种看不见摸不着、有时灵有时不灵的幽灵故障，正是[第 4 章 并发、同步与死锁](../chapter_03_concurrency/index.md)要正面迎战的难题。
