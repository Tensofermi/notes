# 竞态、原子性与锁

## 两张便签，重演一次诡异的计数蒸发

假设办公室的白板上写着一个共享数字 `0`。员工 A 走过来瞅了一眼，在自己的便签上记下 `0`；还没等他把新数写回白板，员工 B 也走过来瞅了一眼，同样在便签上记下 `0`。接着 A 在心里算出 `0 + 1 = 1`，走回去把白板改成 `1`；几秒钟后 B 也算出 `0 + 1 = 1`，照样把白板擦掉写成 `1`。

两个勤恳的员工明明各自执行了一次“加 1”，白板上的最终结果却只有 `1`——一次加法凭空蒸发了！没有谁算错了加法，白板也没坏，祸根完全出在**“看白板 -> 心里算 -> 写白板”这三步被两个人穿插交错在了一起**。要想堵住这个漏洞，最朴素的规矩就是给白板配一支唯一的白板笔：谁想改数，必须先拿到笔；拿不到笔的就在旁边等着，直到前一个人写完放回笔，再重新看一眼最新的数字。

??? question "如果偷懒只在最后“写回白板”那一步加锁，把“读取”留在锁外，能把 bug 修好吗？"

    完全修不好。员工 A 和 B 照样会在抢笔之前同时读到旧值 `0`，随后排着队先后把算出来的 `1` 写回去，更新照样丢失。锁保护的绝不只是孤零零的一条写指令，而是**整个“依赖旧值算出新值并写回”的完整变更过程**。

这就是并发 bug 让所有程序员头疼的根源：它不光取决于你的输入数据，更取决于调度器什么时候切线程、硬件缓存什么时候同步。搞懂并发的第一步，就是抛掉“一行源代码一口气跑完”的错觉，学会用显微镜把代码拆成一条条可能被随时劈开的底层动作。

## 最小事故现场：丢失更新

这种“两次修改撞车，后写者覆盖了前写者的成果”的经典故障，叫作**丢失更新**（lost update）。让两条线程共享 `counter = 0`，各自执行一次看起来无辜得不能再无辜的 C 语句：

```c
counter++;
```

编译成机器指令后，它至少被拆成“加载到寄存器 -> 寄存器加一 -> 存回内存”三步。只要时钟中断或双核并行让两者的节拍按下面这样错开半拍，事故就百分百爆发：

| 时刻 | 线程 A | 线程 B | 内存中的 `counter` |
| --- | --- | --- | --- |
| 1 | 从内存读到 `0` | | `0` |
| 2 | | 从内存读到 `0` | `0` |
| 3 | 在寄存器里算出 `1` | | `0` |
| 4 | | 在寄存器里算出 `1` | `0` |
| 5 | 把 `1` 写回内存 | | `1` |
| 6 | | 把 `1` 写回内存 | `1` |

每条线程在自己看来都干得天衣无缝，可合在一起就把 `2` 算成了 `1`。更要命的是，在单次运行里，如果 A 刚好顺顺利利跑完 1-3-5 再轮到 B，结果又会恰好等于 `2`——这就让并发 bug 极其狡猾，平时在本地开发机上怎么测都正常，偏偏到了高并发生产环境才偶发露头。

## 分清三个容易混为一谈的词

聊并发错误时，大家常常随口把所有问题都喊成“竞态”。其实在严格讨论和排查时，有三个层次截然不同的概念必须掰开：

- **数据竞态**（data race）：最底层的语言/内存层面违规——两条以上执行流并发访问同一个内存地址，其中至少一个是写入操作，而且彼此之间缺少语言或硬件规定的同步约束。在 C/C++ 等语言里，出现数据竞态甚至直接属于未定义行为。
- **竞态条件**（race condition）：更高一层的逻辑与业务缺陷——程序最终结果依赖事件发生的先后时序，而某些可能出现的时序会违反业务预期。
- **原子性违反**（atomicity violation）：原本应该作为一个不可分割的整体呈现给外界的一组操作，在半途中被其他执行流插队观察或修改了。

特别要打破一个危险的迷思：**“消除了所有数据竞态”绝不等于“程序就并发正确了”！**举个银行扣款的例子：假设“查余额”和“扣款”各自都加了锁（或者都是硬件原子操作），因此完全不存在底层的数据竞态。可如果你的代码先调一次 `balance = get_balance()` 看到余额还有 100 元，觉得够扣，接着再调一次 `withdraw(100)`——两条线程照样可以双双先查到 100 元，再双双把 100 元扣走，让账户变成 `-100` 元！单步没错，但“先检查再扣款”这个复合动作的原子性已经被破坏了。

## 临界区与不变量：别先找代码，先写不变量

既然交错是祸根，直觉对策就是圈出一段“同一时刻只允许一条线程踏入”的代码区域——这就是**临界区**（critical section）。

可新手写并发代码最常犯的错，是盯着代码一行行猜“这里要不要加把锁？那里要不要加把锁？”。老手的做法恰恰相反：**先忘掉锁，把数据结构的“不变量”白纸黑字写出来，再反推哪些操作必须一起放进临界区才能守住它。**

比如一个有界数组队列，它最核心的不变量不仅是元素数量守住边界：

$$
0\le count\le capacity,
$$

还要求“数组槽位里的内容、队头下标、队尾下标和 `count` 计数”始终彼此自洽。如果你只把 `count++` 放进锁里，却忘了把往数组写数据和挪动队尾下标一起包进来，另一条线程完全可能看到 `count` 已经变成 `1` 了，兴冲冲地去读队头，结果读到一片还没写完的垃圾数据！

一个靠谱的临界区互斥方案，理论上应当追求三条标准：

1. **互斥**（mutual exclusion）：任意时刻，最多只能有一条线程身处临界区；
2. **进展（Progress）**：如果临界区此刻空着、而且外面有人想进，就必须尽快放一位进去，绝不能让在临界区外干活的无关线程挡住大家；
3. **有界等待（Bounded Waiting）**：任何一条发出请求的线程，都不该被别人无限次插队而活活饿死。

当然，具体到不同操作系统的锁实现，第 1 条是死底线，第 2、3 条则常常在“极致吞吐”和“严格公平”之间做现实妥协。

## 锁自己怎么不撞车？硬件原子指令与 CAS { #atomic-cas }

读到这里，爱钻牛角尖的读者一定会拍案发问：“等等！你说用锁保护共享变量，可**锁本身不也是内存里的一个共享变量吗？**”

试着自己用普通 C 代码写一把锁，你立刻会撞上一堵墙：
```c
while (lock == 1) ;  // 等锁空闲
lock = 1;            // 占住锁
```
看出来死穴在哪儿了吗？线程 A 刚执行完 `while` 看到 `lock == 0`，还没来得及执行下一行 `lock = 1`，调度器切走了 A；线程 B 也看到 `lock == 0`，顺手把 `lock` 设成了 `1` 并大摇大摆走进临界区；紧接着 A 恢复执行，一头也把 `lock` 设成 `1` 走了进去——**锁自己先发生了丢失更新，两条线程同时闯进了临界区！**

怎么打破这个“用锁来保护锁”的无限套娃？答案是向底层硬件求助：CPU 在电路层面专门设计了一类**不可分割的“读—改—写”原子指令**，在多核缓存一致性协议的护航下，保证同一时刻只有一颗核心能完成对那个内存地址的检查与修改。

现代处理器上最核心、最通用的硬件原子指令之一，就是**比较并交换**（compare-and-swap，CAS）。它接收三个参数——内存地址、心里预期的旧值、打算换上的新值——并在硬件层一口气原子地完成检查与替换：

```text
CAS(address, expected, desired):
    atomically:
        if *address == expected:
            *address = desired
            return success
        return failure
```

有了 CAS 这块基石，我们终于能造出一把真正不会漏风的简易自旋锁：抢锁时反复尝试把 `lock` 从 `0` 原子地改成 `1`，谁成功把 `0` 变成了 `1`，谁就独享临界区；其他同时来抢的线程都会看到值已经变成 `1` 而失败，只能在循环里继续等待，直到持锁者干完活把 `lock` 改回 `0`：

```c
while (!compare_exchange(&lock, 0, 1)) {
    cpu_relax();
}

/* critical section */

store_release(&lock, 0);
```

当然，上面这段只是揭示本质的概念代码。真正放到生产内核里的锁，还要操心缓存行在多核间疯狂乒乓、队列公平性、内存屏障顺序，以及“如果持锁的线程半路被调度器切走了怎么办”等一连串棘手问题。

## 拿不到锁时该怎么办？自旋锁与可睡眠互斥锁

当线程 A 试图抢一把已经被线程 B 拿走的锁时，它面临一个很现实的抉择：**是站在门口原地一遍遍敲门问“你出来没”，还是干脆去休息室睡一觉、等 B 出来时拍醒自己？** 这两种截然不同的等待姿势，分出了操作系统里最常见的两类锁。

### 自旋锁：原地空转，绝不让出 CPU

**自旋锁**（spinlock）采取第一种姿势：拿不到锁就在 `while` 循环里一直占着 CPU 死等，绝不触发上下文切换。它在下面三种场合如鱼得水：

- 临界区极短（比如只改几个指针，几十纳秒就完事），等你费劲睡下去再醒来，人家早就解锁走了八百回；
- 机器有多颗核心，而且持锁者此刻正稳稳地在**另一颗核心**上飞奔；
- 当前身处不能睡眠的特殊上下文（比如内核的硬件中断上半部）。

但千万别把它用错地方！如果临界区里夹着慢吞吞的磁盘读取，或者在单核机器上持锁者被抢占下台了，等待者原地死旋纯属烧电空转——不仅自己白费 CPU，还把真正干活的持锁者挤在就绪队列里上不来！此外，在几十颗核心同时疯狂 `CAS` 同一把自旋锁时，CPU 缓存行会在多核之间来回横跳引发“缓存一致性风暴”，所以成熟的内核自旋锁往往会先只读轮询，或者干脆改用按队排号的票据锁（Ticket Lock）/ 队列锁（MCS Lock）。

### 可睡眠互斥锁：先睡一觉，把 CPU 让给有用的人

**互斥锁**（mutex）走的是第二种路线：抢不到锁时，请求内核把自己挂进这把锁的等待队列里进入阻塞睡眠，立刻把 CPU 让给其他就绪线程；等到持锁者解锁时，内核再顺手从等待队列里挑一位叫醒。

什么时候该自旋、什么时候该睡眠？拿一笔直观的算术账一比就清清楚楚。设预计还要等锁释放的时间是 $t_w$，而“阻塞睡下去 + 被唤醒重新切回来”一整套上下文切换的成本是 $t_b$：

- 当 $t_w \ll t_b$ 时，原地等几百纳秒比折腾一趟睡眠唤醒便宜得多，自旋胜出；
- 当 $t_w \gg t_b$ 时，原地空转是在浪费宝贵的算力，乖乖让出 CPU 睡眠才划算。

现实里的许多现代互斥锁（如 Linux 里的自适应互斥锁 / 基于 `futex` 的混合锁）干脆把两者结合起来：抢不到锁时先象征性地自旋一小会儿赌持锁者马上放手，赌赢了省下一趟进内核的大开销；赌输了就老老实实进内核睡觉，绝不死磕。

### 一个干净标准的互斥锁例子

用 POSIX 线程库的互斥锁护住开头的计数器，代码简洁有力：

```c
#include <pthread.h>

static long counter = 0;
static pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

void increment(void) {
    pthread_mutex_lock(&mutex);
    counter += 1;
    pthread_mutex_unlock(&mutex);
}
```

请留意一个经常被忽视的前提：**互斥锁不是贴在变量上的防弹玻璃，而是一份君子协议。** 上面这段代码之所以安全，不仅因为 `increment` 加了锁，更因为程序里**所有读写 `counter` 的代码**都老老实实去抢同一把 `mutex`。只要有另一条线程图省事，不拿锁就偷偷读了一眼 `counter`，整个同步契约依然会被撕破。

## 加了锁，别人就一定立刻看得见我写的新值吗？锁与内存可见性

在单线程世界里，代码写在第 1 行就一定在第 2 行之前生效。可到了多核并发世界，有一个反直觉的事实常常让新手怀疑人生：**就算你在代码里先写了 `data = 42`，再写了 `ready = 1`，另一颗核心上的线程依然可能先看到 `ready == 1`，却读出旧的 `data == 0`！**

这不是魔法，而是现代编译器和 CPU 为了提速联手干的好事：编译器在保证单线程结果不变的前提下会大胆重排指令顺序；CPU 也会做乱序执行，并且每颗核心手里都攒着私有写缓冲和各级缓存，写进去的新值不会在零纳秒内魔术般同步到所有核心的视野里。

因此，一把合格的互斥锁或原子同步原语，在幕后其实同时扛着两副担子：

1. **互斥与原子性**：挡住其他线程同时进临界区；
2. **内存可见性与顺序建立（Memory Ordering）**：在多核之间立起一道清晰的先后边界。最经典的语义叫作 **release—acquire** 同步对——线程 A 在解锁（release）之前写下的所有共享数据，保证对随后成功抢到同一把锁（acquire）的线程 B 全部清晰可见，绝不会出现“锁拿到了、数据还在半路上”的灵异现象。

顺手扫除一个流传甚广的 C/C++ 误区：**千万别把 `volatile` 当成线程同步工具！** 在 C/C++ 里，`volatile` 只是告诉编译器“别把对这个地址的读写优化掉或缓存进寄存器”（典型用途是读写映射在内存里的硬件设备寄存器），它既不保证 `counter++` 的原子性，也不一定在多核 CPU 间插入必要的内存屏障。跨线程共享状态，请老老实实用语言标准定义的互斥锁或原子类型（如 C11/C++11 的 `atomic`）。

## 锁粒度：一把大锁保平安，还是千把小锁冲并行？

给一个大型哈希表或整个内核子系统加锁时，架构师立刻会面对一道经典分叉路：是省事配一把全局大锁，还是把锁拆细到每个桶、甚至每个节点？

- **粗粒度锁（Coarse-Grained Locking）**：一把大锁罩住整块数据结构。它的美德常常被低估——协议极其简单，跨字段不变量一眼望穿，而且因为总共就一把锁，**根本不可能死锁**！缺点则在高并发多核下暴露无遗：线程 A 在查第 1 号桶，线程 B 在改第 999 号桶，明明八竿子打不着，却全堵在门口排成一队，32 颗核心活生生跑出了单核的速度。
- **细粒度锁（Fine-Grained Locking）**：拆成每个哈希桶甚至每个对象各自持锁，多核并行度瞬间起飞。可复杂度的账单也紧跟着寄来了：
  - 一旦某个操作需要同时锁住两个对象（比如把元素从 A 桶挪到 B 桶），加锁顺序稍不统一就会酿成死锁；
  - 对象销毁与引用计数变得极其棘手——线程 A 正准备锁住对象 X，线程 B 抢先一步把 X 释放回收了怎么办？
  - 维护跨多个对象的全局不变量（比如瞬间算出全表总元素数）变得异常别扭；
  - 成千上万把小锁本身也要占内存、占缓存行，甚至因为相邻小锁挤在同一个 CPU 缓存行里引发**伪共享（false sharing）**而互相拖慢。

工程界有一条血泪经验：**永远别迷信“锁越细越快”。** 先用干净的粗粒度锁把正确性立稳，用性能分析工具实测确认“锁竞争确实成了瓶颈”以后，再精准拆分热点锁。

## 写锁最常踩的四个深坑

就算背熟了互斥锁 API，真实项目里下面四类翻车依然屡见不鲜：

### 1. 拆碎了的“先检查，再执行”

```c
if (!queue_empty()) {
    item = queue_pop();
}
```

哪怕 `queue_empty()` 和 `queue_pop()` 内部各自都加了锁，合在一起照样是错的！线程 A 查完看到非空、解锁刚跨出第一步，线程 B 抢先一步把最后一个元素取走了；A 再进 `queue_pop()` 时，队列早已空空如也。必须把“检查是否非空”与“取出元素”合并在**同一把锁的同一次持有期内**完成（或者提供原子的 `try_pop(&item)` 接口）。

### 2. 错误分支忘了把锁解开

一个函数中间有五处 `if (err) return -1;` 提前返回，程序员在前四处都记得 `unlock`，偏偏漏掉了最冷门的第五处。某天线上罕见错误触发了一次，这把锁就永远没人释放了，随后整个服务一条接一条线程全挂死在锁门口。善用 C++ 的 RAII 作用域锁（`lock_guard`）、Python 的 `with lock:`、Go 的 `defer mu.Unlock()`，或在 C 里统一 `goto out_unlock;`，能从语法上根治这类低级失误。

### 3. 抱着锁去调用来路不明的外部代码

手里攥着内部互斥锁，顺手调了一个用户注册的回调函数、发了一次阻塞网络请求，或者写了一行可能触发日志锁的代码——这等于亲手把临界区吹成了一个随时会炸的气球。外部回调里要是拐弯抹角又来请求你手里这把锁，当场**自我重入死锁**；要是去等磁盘 I/O，整条系统的并发线程全都陪着干等。稳妥做法是：在锁内把需要的数据拷贝出来（或增加引用计数确保对象活着），**先解锁，再执行回调或 I/O**。

### 4. 半吊子的“双重检查锁定”

为了省去每次读单例都加锁的开销，有人爱写“先无锁看一眼指针是不是空，空了再加锁、再检查一遍然后初始化”。这招在没有严格内存顺序保障时暗藏杀机：CPU 和编译器可能把“把新地址赋给全局指针”重排到“填完对象内部字段”之前！另一条线程无锁看到指针非空，欢天喜地拿去用，结果读到的是一个只初始化了一半的残次品。除非你彻底吃透了语言内存模型的 release—acquire 发布语义，否则请毫不犹豫地改用标准库自带的一次性初始化原语（如 `pthread_once`、`std::call_once`、`sync.Once`）。

## 既然硬件有原子指令，能不能彻底抛弃锁？

面对锁带来的阻塞、上下文切换和死锁风险，你可能会动心：“CAS 这么厉害，干脆把所有数据结构都写成无锁的吧！”

对于单一的统计计数器、简单状态标志或无复杂联动关系的原子指针，直接用硬件原子操作确实轻快漂亮。可一旦涉及多个字段联动的不变量，或者需要等待条件成立，老老实实上锁往往不仅更易证明正确，实测也未必比复杂无锁结构慢。

真正工业级的**无锁**（lock-free）算法门槛极高。它确实保证了“哪怕某条线程半路被抢占睡死，也不会挡住其他线程继续取得进展”，但这不等于“每条线程都一定很快结束”，高竞争下反复 `CAS` 失败重试反而可能比排队互斥锁更慢。更让人防不胜防的是无锁世界特有的两大怪兽：

- **ABA 问题**：线程 1 从共享栈顶读到节点地址 `A`，刚准备做 `CAS(top, A, next)` 时被切走了；期间线程 2 把 `A` 弹出、又把 `B` 弹出、随后内存分配器恰好把刚回收的 `A` 原地复用又压回了栈顶！线程 1 醒来执行 `CAS`，发现栈顶依然是 `A`，以为沧海桑田什么都没变就高兴地换上旧 `next`，结果把整条链表指飞到已经被释放的野内存里去了！
- **安全内存回收难题**：没有锁拦着，线程 1 把节点从无锁链表摘下来准备 `free` 时，怎么知道另一颗核心上的线程 2 此刻手里是不是正攥着指向这个节点的指针？解决它往往要引入版本号标记、风险指针（Hazard Pointer）或基于纪元的内存回收（Epoch-Based Reclamation）等重型武器。

所以，选无锁结构一定要基于真实的压测数据和明确的进展需求，千万别仅仅因为“无锁”两个字听起来酷炫就往业务代码里硬塞。

## 一点历史回望

并发同步的演化，像极了一场软硬件的双向奔赴。上世纪六十年代，计算机先驱（如 Dijkstra、Peterson）试图只靠普通内存读写写出不依赖特殊硬件的纯软件互斥算法；随着多处理器时代到来，软件算法不仅在多核乱序执行下难以为继，开销也太大，硬件架构师于是推出了测试并设置（Test-and-Set）、CAS、LL/SC 等原子指令；进入大规模多核与 NUMA 时代后，锁的实现又从朴素自旋演化出指数退避、排队锁与分层锁；与此同时，为了终结“编译器优化和乱序硬件让并发代码变成玄学”的混乱，现代编程语言和芯片架构联手确立了严格的**内存模型**（memory model），用清晰的数学规则划定了跨线程可见性的边界。

到现在为止，我们已经学会了用锁和原子操作守护临界区，拦住了“两个人同时乱动共享数据”的惨剧。可并发协作的另一半难题紧跟着冒了出来：如果队列此刻是空的，消费者抢到锁看了一眼发现没货，它总不能死抱着锁不放吧？可松开锁之后，它又怎么知道生产者什么时候把新货放了进来、该在何时醒来接着干活？这种“等某个条件成立再继续”的难题，正是[下一篇：信号量与条件变量](02_semaphores_condition_variables.md)的主场。

## 自测

1. 为什么在 C 或 Python 里看起来只有一行字的 `counter++`，在多线程环境下不是原子操作？
2. 一个经过严格检测、确认“零数据竞态”的程序，是不是就一定不会出现并发逻辑错误（竞态条件）？请举一反例。
3. 在单核机器上，或者持锁线程正被操作系统抢占换下 CPU 时，盲目使用自旋锁会发生什么灾难性后果？
4. 为什么说互斥锁需要“所有读写该共享数据的线程共同遵守”，哪怕有一个只读线程偷懒不加锁也会出事？
5. 什么时候直接用原子变量就够了，什么时候应该果断上互斥锁？

??? note "参考思路"

    1. `counter++` 在底层由“读取旧值到寄存器、寄存器加 1、将新值写回内存”多步组成，多条线程的这些步骤完全可能交错执行，导致丢失更新。
    2. 不一定。例如“先原子查询余额、判断足够后再原子扣款”，单步操作各自安全、无数据竞态，但两步组合起来仍可能被另一条线程插队扣空，形成竞态条件与原子性违反。
    3. 持锁线程此刻根本不在 CPU 上运行，不可能释放锁；而等待者还在用自旋锁死占着 CPU 空转，白白烧光整个时间片，甚至拖慢持锁线程重新获得调度的时机。
    4. 没有共同同步协议时，无锁读取既可能读到修改到一半的撕裂/不一致状态，在语言内存模型里还构成数据竞态，根本无法保证可见性与顺序性。
    5. 单个独立计数器、状态标志或引用计数适合用原子操作；一旦不变量涉及多个联动字段，或线程需要在条件不满足时进入等待睡眠，就应该使用互斥锁（配合条件变量）。
