# 信号量与条件变量

## 醒来以后，队列里真的还有东西吗？

设想一家只有一张出餐台的小餐馆：后厨有一位不停做菜的**生产者**（producer）线程，前厅有两位盯着出餐台端菜的**消费者**（consumer）线程，三个人共用这同一个任务队列。

某天出餐台空了，消费者 1 过来一看没菜，只好先靠边打个盹；过了一会儿，厨师做好一份菜放到台上，大喊一声“有菜了！”把消费者 1 喊醒。就在消费者 1 揉着眼睛走过去、还没摸到出餐台锁的那半秒钟里，恰好路过的消费者 2 眼疾手快，一把抢先拿到锁、把台上唯一那份菜端走了！等消费者 1 终于拿到锁凑到台前，盘子早就空空如也。如果消费者 1 盲目相信“刚才厨师喊过我，台上肯定有菜”，一伸手就去取，程序当场就会崩溃或取出垃圾数据。

这个画面藏着等待类并发工具最核心的真谛：**唤醒通知只是拍了拍你的肩膀说“情况可能有变，快起来重新看一眼”，至于盘子里此刻究竟还有没有菜，必须由你在重新拿到锁之后亲眼再确认一遍。**

??? question "为什么条件变量的等待代码几乎永远要写在 `while` 循环里，而不能写成 `if`？"

    因为从你被唤醒到真正重新抢回互斥锁之间，总有一段微小的时间窗口——其他线程完全可能捷足先登，把你盼着的条件再次改回不成立（甚至系统底层还可能偶尔发生“虚假唤醒”）。用 `while` 循环，醒来拿到锁后发现盘子又空了，就老老实实继续睡回去，绝不会稀里糊涂往下冲。

上一篇的互斥锁只回答了一半问题——“怎样防止大家同时乱动共享数据”。可真实世界里另一半高频需求是——**“如果现在条件还不成熟（队列空了、缓冲区满了、依赖任务还没算完），我该怎样安稳睡去，又怎样在条件成熟的第一时间被叫醒？”** 操作系统与并发库为此提供了两套风格迥异的利器：**信号量**（semaphore）和**条件变量**（condition variable）。这一篇，我们就把它们放进同一个有界缓冲区场景里掰开揉碎地比个明白。

## 为什么光靠一把互斥锁根本不够用？

不妨先试着硬扛——只用上一篇学过的互斥锁，来写那位等待出餐的消费者。你很快会发现自己左右为难：

- **笨办法一（抱着锁死等）**：消费者抢到锁，一看队列为空，就在锁里面写个 `while (empty) ;` 死等。后果立竿见影——厨师要想往队列里放菜，也得拿这把锁！你抱着锁不撒手，厨师永远进不来，全馆立刻死锁。
- **笨办法二（解锁后疯狂轮询）**：那每次发现队列为空就先解锁，转一圈再加锁重看呢？虽然不会死锁了，可万一厨师十分钟才做一道菜，消费者就在这十分钟里把 CPU 跑成 100%，每秒加锁解锁几百万次，既烧电又拖慢别人；要是自作聪明中间塞个 `sleep(100ms)`，菜做好了又得白白干等几十毫秒，延迟惨不忍睹。
- **笨办法三（先解锁，再自己去睡觉）**：看似完美，实则埋着一颗隐形炸弹——就在消费者刚刚松开锁、还没来得及把自己挂进睡眠队列的那一微秒缝隙里，厨师闪电般抢锁放菜、喊了一声“有菜了”（此时压根还没人在睡！），然后消费者才安心闭眼睡下……从此再也没人喊它，**一睡不起！**

绕了这一大圈，正确协议的轮廓终于被逼了出来：

```text
持有互斥锁，检查共享条件
  -> 条件不满足时：原子地“释放锁 + 进入等待队列睡眠”
  -> 状态改变者在持有同一把锁时修改状态，并发出唤醒通知
  -> 被唤醒后：重新抢回互斥锁，再次检查条件是否真的成立
```

盯着第二步那两个字——**原子地**。正因为“松开锁”和“躺进等待队列”被内核捆成了一个不可拆分的动作，厨师绝无可能插在两者中间偷偷把唤醒喊丢。

## 路线一：把等待变成一本“数量账”——信号量

解决等待问题有两种截然不同的哲学。第一种由计算机科学大师 Dijkstra 在上世纪六十年代提出，思路直观得像游乐园发门票：很多时候我们苦苦等待的，本质上不过是“某样东西的剩余数量目前是 0”——比如队列里剩余空槽为 0、数据库连接池剩余可用连接为 0。

于是他设计了**信号量**（semaphore）：它内部只维护一个整数计数器和一条等待队列，对外只暴露两个原子操作（历史上常叫 `P` / `V`，现代接口常叫 `wait` / `post` 或 `acquire` / `release`）：

```text
wait(S):
    原子地检查计数器 S：
    若 S > 0，则把 S 减 1，领走一张“入场券”立刻继续；
    若 S == 0，则把自己挂入等待队列阻塞睡眠，直到有人 post 补票后完成减 1。

post(S):
    原子地把计数器 S 加 1（补回一张票）；
    若等待队列里有人在睡，唤醒其中一位。
```

你看，信号量非常奇妙：如果初值设为 $N$，它就天然代表 **$N$ 份可并发使用的同类资源**；就算 `post` 先发生、`wait` 后到来，那张多出来的“票”也会稳稳记在计数器里，绝不会凭空消失！

### 最小实战：限制并发连接数

假设数据库最多承受 3 条并发连接，把计数信号量初值设为 `3`：

```python
from threading import Semaphore

slots = Semaphore(3)


def handle_request() -> None:
    with slots:
        use_one_database_connection()
```

第 1、2、3 个进来的请求顺利把计数从 `3` 减到 `0` 并开始查库；第 4 个请求进来撞见 `0`，立刻乖乖阻塞睡眠，直到前面任意一位离开 `with` 块把计数加回 `1` 并唤醒它。不过要清醒一点：这里的信号量只负责**限流（控制同时进门的人数不超过 3）**，至于把哪一条具体连接分给谁、连接池内部数组怎么安全增删，依然需要单独的锁协议保护。

### 二元信号量能直接当互斥锁用吗？

既然计数信号量初值设为 `1`（所谓二元信号量）时，同时也就只允许 1 个人通过 `wait`，它和上一篇的互斥锁是不是一回事？

表面上看很像，但**工程语义上差着一大截**：
- **所有权概念不同**：互斥锁讲究“谁加锁、谁解锁”，如果线程 A 加的锁由线程 B 来解，在严格实现里属于非法错误；而信号量根本不管谁 `wait`、谁 `post`——事实上它最经典的用法正是线程 A 在这头 `wait` 等事件，线程 B 在那头干完活调用 `post` 放行！
- **调试与调度支持不同**：正因为互斥锁明确知道“此刻锁在谁手里”，操作系统才能为它提供**优先级继承**（防止优先级反转）、死锁环路检测以及错误解锁报错；信号量没有固定所有者，内核很难替你做这些防护。

因此记住一条好习惯：**保护临界区互斥，优先用互斥锁；表达资源配额或跨线程的“一头等、另一头通知”，再用信号量。**

## 路线二：直接等一个业务条件——条件变量

不是所有等待都能轻易换算成一个简单整数。比如你想等“队列非空 **或者** 系统收到关闭指令”，或者想等“某个任务的状态从 `PENDING` 变成 `READY` 且余额大于本次扣款额”。硬把复杂谓词塞进信号量计数，代码很快就会晦涩难懂。

第二种哲学干脆把分工划得干干净净：共享状态和复杂业务条件继续留在普通变量里、由一把互斥锁严密保护；另外引入一个专门负责“排队睡觉”和“拍肩叫醒”的传声筒——**条件变量**（condition variable）。

记住它最黄金的一句心法：**条件变量自己不存任何业务状态，也不存历史通知次数，它只提供“原子释放锁并睡眠”和“唤醒等待者”的队列机制。**

翻开任何一本用 POSIX 线程写的 C 程序，你都会看到这段千锤百炼的标准范式：

```c
pthread_mutex_lock(&mutex);
while (!predicate()) {
    pthread_cond_wait(&condition, &mutex);
}
use_state();
pthread_mutex_unlock(&mutex);
```

盯紧第 3 行的 `pthread_cond_wait(&condition, &mutex)`，这一个调用内部替你原子地包办了三件事：**释放 `mutex` -> 挂入 `condition` 的等待队列睡眠 -> 等被唤醒后重新抢回 `mutex`**。所以只要从 `wait` 返回，你就一定再次稳稳握着互斥锁。

### 再强调一遍：为什么把 `while` 写成 `if` 就是埋雷？

回到开头餐馆抢菜的一幕，如果把上面的 `while (!predicate())` 偷懒改成了 `if (!predicate())`：

```c
if (!predicate()) {
    pthread_cond_wait(&condition, &mutex);
}
```

哪怕只改了这一个关键字，代码就会同时暴露在三重风险下：
1. **被半路截胡**：通知发出后、你重新抢回锁之前，另一条刚进门的消费者抢先拿到了锁并把队列里的最后一项端走了；
2. **虚假唤醒**（spurious wakeup）：出于底层多核实现与信号中断的效率权衡，POSIX 和各大语言标准明确允许 `wait` 在**根本没人调用通知**的情况下偶尔提前醒来返回；
3. **广播后条件对你不成立**：如果通知者用广播叫醒了所有等待者，其中也许只有一部分人的条件真正满足。

所以请彻底记住条件变量的真实契约：

> 从条件变量醒来，绝不代表“条件已经永久对你成立”，只代表“你拿到了一个重新检查条件的机会”。

## 把条件变量落到实处：有界缓冲区完整实现

把互斥锁和条件变量合体，我们写出并发教材里最经典、最优雅的有界队列实现。留意它用了**一把锁**（保护同一个 `items` 队列），配**两个条件变量**（生产者在 `not_full` 上等空位，消费者在 `not_empty` 上等数据）：

```python
from collections import deque
from threading import Condition, Lock


class BoundedQueue:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.items = deque()
        self.lock = Lock()
        self.not_empty = Condition(self.lock)
        self.not_full = Condition(self.lock)

    def put(self, item) -> None:
        with self.not_full:
            while len(self.items) == self.capacity:
                self.not_full.wait()
            self.items.append(item)
            self.not_empty.notify()

    def get(self):
        with self.not_empty:
            while not self.items:
                self.not_empty.wait()
            item = self.items.popleft()
            self.not_full.notify()
            return item
```

它严丝合缝地守住了队列的不变量：

$$
0\le |items|\le capacity.
$$

看看这套配合多么赏心悦目：生产者只在队列满时睡在 `not_full` 上，一旦塞进新元素，顺手敲响 `not_empty` 唤醒可能饿着的消费者；消费者只在队列空时睡在 `not_empty` 上，一旦取走元素腾出空位，顺手敲响 `not_full` 唤醒可能堵着的生产者。

### 顺手辨析：`notify` 还是 `notify_all`？

细心的你一定会问：这里用的是只叫醒一个人的 `notify()`，那什么时候必须用把所有人全喊醒的 `notify_all()`？

- **`notify()`（单播唤醒）**省开销，避免把一百个睡着的线程一起喊起来抢一把锁（这种“一喊全醒、结果 99 个白跑一趟又睡回去”的浪费叫**惊群效应**）。但它有个前提：**你能确信这次状态变化只需要叫醒任意一个同类型等待者就够了**——上面的 `BoundedQueue` 之所以敢用 `notify()`，正是因为我们特意把“等非满的生产者”和“等非空的消费者”拆在了两个独立的条件变量上！试想如果偷懒把它们混在同一个条件变量里，消费者取出一个元素后调用 `notify()`，万一叫醒的是另一个消费者而不是生产者，醒来的消费者一看还是空又睡回去，系统就彻底死寂了！
- **`notify_all()`（广播唤醒）**最稳妥保守：当一次状态变更可能让多个等待者同时受益（比如“系统即将关闭”或“大块内存释放，多个不同大小需求的线程都可以试着重查”），或者不同等待者等的是不同谓词时，果断用广播，让大家在各自的 `while` 循环里重新自检。

## 换信号量来写同一个有界缓冲区：顺序错一行就死锁！

刚才用“1 把锁 + 2 个条件变量”写出的有界队列，换成信号量会是什么画风？我们准备两本资源账加一把锁：
- `empty`：初值为容量 $C$，记录还剩几个空槽；
- `full`：初值为 `0`，记录里头已有几个可取元素；
- `mutex`：保护队列底层的指针和数组操作。

```text
producer:
    wait(empty)        // 先领一张“空槽票”
    lock(mutex)        // 再拿锁改队列
    enqueue(item)
    unlock(mutex)
    post(full)         // 补一张“有货票”给消费者

consumer:
    wait(full)         // 先领一张“有货票”
    lock(mutex)        // 再拿锁改队列
    item = dequeue()
    unlock(mutex)
    post(empty)        // 补一张“空槽票”给生产者
```

请盯住开头两行的先后次序，做一个致命的思想实验：**如果手抖把 `lock(mutex)` 挪到了 `wait(empty)` 前面，会怎么样？**

设想队列刚好满了（`empty == 0`）。生产者先抢走了 `mutex`，紧接着走到 `wait(empty)` 发现没空槽，于是**怀里死死抱着 `mutex` 睡着了**！这时消费者兴冲冲赶来打算取走元素腾出空槽，顺利通过 `wait(full)` 后，一头撞在 `lock(mutex)` 上——拿不到锁！生产者在等消费者腾槽，消费者在等生产者松锁，双方当场锁死。这个经典反例再一次印证了铁律：**绝对不要抱着别人需要的锁去阻塞等资源！**

## 丢失唤醒：为什么通知会凭空蒸发？

前面我们在“笨办法三”里已经惊鸿一瞥地见过了**丢失唤醒**（lost wakeup）的惨剧。再把它的成因彻底钉死：条件变量的通知就像站在空房间里喊一声“开饭了”，声音不会自动录在磁带上等后来进屋的人听。

如果等待者无锁看了一眼条件不成立，正准备去睡，通知者刚好在这个微秒缝隙里把状态改好并喊了 `notify`——当时房间里空无一人，通知直接消散在空气里；下一微秒等待者走进房间安心躺平，从此永远错过了那声召唤。

只要严格遵守两条纪律，这个窗口就能被彻底封死：
1. **等待者**必须在持锁状态下检查谓词，并用 `wait` 原子地释放锁并进入等待队列；
2. **通知者**也必须在持有**同一把互斥锁**的前提下修改共享状态（即便某些实现允许在解锁后再调 `notify` 以减少被唤醒者立刻撞锁，修改状态这一步也绝不能离开锁保护）。

## 两个常见衍生同步模式：屏障与一次性事件

在互斥锁、条件变量与信号量之上，工程里还会高频碰到两个顺手的组合模式。

### 屏障（Barrier）：人到齐了一起迈步

并行科学计算或分布式训练常常分阶段推进：8 条工作线程必须全部算完第 1 轮，才能一起进入第 2 轮。这种“约好所有人到齐再统一放行”的同步点叫作**屏障**（barrier）。

实现起来很直观：设总人数为 $N$，前 $N - 1$ 位先到的线程把 `arrived` 加 1 后在条件变量上乖乖等待；第 $N$ 位最后到达时，把计数器复位、把轮次号加 1，然后广播唤醒所有人。这里暗藏一个极容易栽跟头的细节——**可重用屏障必须维护一个“当前轮次号（generation）”**。否则第 1 轮最后一人广播完，某个飞快的线程瞬间跑完第 2 轮又冲回屏障，把 `arrived` 改乱了，把上一轮还没来得及完全醒透的慢线程直接搅进下一轮里。

### 一次性事件（One-Shot Event）

有时我们需要“等配置加载完成，一旦加载好了，以后任何人来查都直接通过，绝不再等”。注意这和瞬时的条件变量通知不同：条件变量自己不记账，但把一个受锁保护的布尔标志 `ready = true` 和条件变量捆在一起，就造出了一张永久生效的通行证——早来的人在 `while (!ready)` 里等，晚来的人一看 `ready` 已经是 `true`，连睡都不用睡直接通关。

## 真实工程的深水区：超时、取消与优雅关闭

教科书里的 `BoundedQueue` 假设程序永远跑下去，可真实线上服务终究要重启、请求终究会超时、用户终究会点“取消”。当你给 `wait` 加上超时或给队列加上 `close()` 时，真正考验功力的边界问题才刚刚露头：

- **超时临界点**：`wait_for(5s)` 超时返回的那一刹那，恰好有一条数据放进来了——你应该算它超时失败，还是顺手把数据收下？
- **关闭广播**：关闭队列时，必须在锁内设好 `closed = true`，并调用 `notify_all()` 把所有睡着的**生产者和消费者统统叫醒**，让它们在各自的 `while` 条件里检查到 `closed` 后体面退出（而不是只喊 `notify()` 留下一群线程永远睡死）；
- **销毁竞态**：怎么保证你销毁条件变量和互斥锁的那一刻，队列里再也没有一条迷路的线程正准备醒来访问它？

实战经验告诉我们：同步对象本身的**关闭协议与生命周期管理**，常常比核心算法本身更难写对。

## 权衡与收束：怎么选原语，怎么看待高层封装？

回头对照今天出场的两位主角：
- **信号量**表达“资源份数”和“一头生产一头消费的计数通知”极为紧凑利落，可一旦业务条件变得复杂（比如多条件组合、关闭状态），纯靠几个整数计数很快就会变成谁也看不懂的天书；
- **条件变量**把业务谓词明明白白摊在受锁保护的共享变量里，推理不变量极其清晰，代价则是写起来稍显啰嗦，而且要求每个参与者都一丝不苟地守住“同一把锁 + `while` 重检”的纪律。

在现代工程里，像 Go 的 Channel、Java 的 `BlockingQueue`、Rust 的异步通道，往往已经把底层的锁与条件变量妥帖地包在了易用的高层抽象里。日常业务优先用成熟的高层抽象当然明智，但只要出了背压堵死、关闭卡死或超时泄漏的疑难杂症，最终能帮你一针见血揪出病根的，依然是今天这套底层同步直觉。

手里已经握齐了锁、原子指令、信号量和条件变量全套工具，是时候拉上实战沙盘演练一番了！[下一篇：经典同步问题](03_classic_synchronization.md)会把生产者—消费者、读者—写者、哲学家就餐与睡眠理发师摆上桌面，训练你面对陌生并发需求时的通用建模手法——而且，那五位围桌而坐的哲学家，还会把我们直接引向本章最凶险的暗礁：死锁。

## 自测

1. 为什么条件变量必须和一把互斥锁成对使用，而不能单独调用 `wait()`？
2. 如果通知者在没有任何线程等待时调用了 `notify()`，之后才到来的等待线程还能收到这次通知吗？为什么？
3. 在有界缓冲区的条件变量实现里，为什么最好把 `not_empty` 和 `not_full` 拆成两个条件变量，而不是共用一个？
4. 一个初值为 `5` 的计数信号量，在实际系统里通常代表什么含义？
5. 在信号量版本的有界缓冲区中，如果生产者先 `lock(mutex)` 再 `wait(empty)`，什么情况下会发生死锁？

??? note "参考思路"

    1. 互斥锁保护共享状态（业务谓词）免受并发破坏，更重要的是让“检查谓词不成立 -> 释放锁并进入等待队列”成为一个原子动作，堵住丢失唤醒的窗口。
    2. 收不到。条件变量不保存历史通知次数；状态必须保存在受互斥锁保护的共享变量中，后来者会先检查共享状态，确认条件已经满足就不会再睡眠。
    3. 生产者和消费者等待的方向截然相反。拆成两个条件变量后，生产完可以精准 `notify` 消费者、消费完精准 `notify` 生产者；若混在一起用单播 `notify`，可能错喊醒同类线程而导致真正该醒的一方永远睡死。
    4. 通常表示最多允许 5 份同类稀缺资源被同时并发占用（例如 5 个数据库连接或 5 个槽位），第 6 个请求到来时会阻塞直到有人归还。
    5. 当缓冲区已满（`empty == 0`）时，生产者先拿走了 `mutex`，紧接着在 `wait(empty)` 处持锁阻塞；此时消费者需要拿到同一把 `mutex` 才能取出元素并 `post(empty)`，双方互相卡死。
