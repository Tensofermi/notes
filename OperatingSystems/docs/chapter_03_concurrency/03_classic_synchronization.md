# 经典同步问题

## 一个只有一格的缓冲区，能教会我们什么？

把上一篇的有界队列缩到最极端——它现在只有一个格子，一次最多放一件物品。刚开始格子是空的：空位数 `empty = 1`，可读元素数 `full = 0`。

生产者想把数据 A 放进去，得先确认空位数大于 0，随后占住锁把 A 放进格子，再通知消费者“有货了”；此时空位数变成 `0`，如果生产者立刻想放下一件数据 B，就只能乖乖停下来，直到消费者抢到锁取走 A、把空位数恢复成 `1` 并反过来通知它。

??? question "在这个单格缓冲区里，如果生产者贪省事，先拿着缓冲区的互斥锁、再在锁里面干等空位，会发生什么？"

    只要格子此刻刚好是满的，生产者就抱着互斥锁一睡不起了。而唯一能制造空位的消费者偏偏也需要这把互斥锁才能把 A 取出来——双方隔着这把锁大眼瞪小眼，瞬间死锁。正确的节奏永远是：先通过信号量在锁外等空位（或用条件变量在等的时候原子释放锁），确认有空位后再进临界区改格子。

教科书里反复出现的这几个经典同步问题——生产者—消费者、读者—写者、哲学家就餐、睡眠理发师——价值绝不在让你死记硬背几段伪代码应付面试，而在于它们每一道都把一类极其真实的工程矛盾剥离了业务噪音，压缩到寥寥几个角色里。拿它们反复练手，你就能攒出一套面对任何陌生并发系统都管用的肌肉记忆。

## 面对任何陌生并发需求的“八步建模法”

别急着一上来就敲 `lock` 和 `cond`。拿到一个全新的并发协作需求时，按下面八个问题逐条填完一张纸，九成隐患在写第一行代码前就会自己跳出来：

1. **参与者是谁？** 有哪几类线程或进程会同时进来？
2. **共享可变状态是什么？** 哪些内存变量或数据结构会被多方共同读写？
3. **不变量是什么？** 无论指令怎么交错，哪些硬约束必须时刻成立？
4. **哪些复合动作必须原子化？** 哪几步拆开就会破坏不变量？
5. **谁在什么条件下必须等待？** 写出精准的业务谓词。
6. **谁会改变这个谓词，改完后该通知谁？** 单播 `notify` 够不够，还是必须广播？
7. **会不会踩中四大坑？** 死锁、饥饿、活锁、惊群，逐一过筛。
8. **收尾怎么体面退场？** 超时、取消、出错和系统关闭时，睡着的线程怎么醒、持有的资源怎么放？

只要这八个问题里还有哪条模模糊糊，哪怕程序在测试机上跑了一夜没报错，也绝不代表协议已经写对了。下面我们就拿着这把尺子，挨个拆解五大经典模型。

## 经典一：生产者—消费者（有界缓冲区）

### 场景与不变量

一群生产者源源不断地往容量为 $C$ 的缓冲区塞数据，一群消费者从另一头往外取数据。整套系统要死守的核心不变量是：

$$
0\le count\le C.
$$

套用建模法立刻能看出，这里缠着两件截然不同的事：
- **互斥**：队列底层的数组、读写指针和元素计数不能被两个线程同时改坏；
- **条件同步**：队列满时生产者必须让出 CPU 等空位，队列空时消费者必须让出 CPU 等数据。

### 信号量方案回看

用两个计数信号量管资源配额，一把互斥锁管队列内部操作：

```text
empty = C    // 剩余空槽数
full = 0     // 已有元素数
mutex = 1    // 保护队列结构的互斥锁

producer:
    wait(empty)
    wait(mutex)
    enqueue(item)
    post(mutex)
    post(full)

consumer:
    wait(full)
    wait(mutex)
    item = dequeue()
    post(mutex)
    post(empty)
```

把两个计数加起来，`empty + full` 在没有线程正处于临界区操作时恒等于总容量 $C$，清清楚楚地刻画了有限空间守恒。

### 工程直觉：扩大缓冲区救不了入不敷出

新手遇到队列频频堵满，第一反应往往是：“把容量 $C$ 从 100 改成 100000 吧！”

这其实误解了缓冲区的真正使命。**缓冲区的价值是“削峰填谷”——吸收短时间的突发流量波峰，而不是对抗长期的产能失衡。** 如果生产者的长期平均速率 $\lambda_p$ 持续高于消费者的处理速率 $\lambda_c$，那么不管你把缓冲区扩得多大，积压最终都必然一路涨爆上限：

$$
\lambda_p>\lambda_c\quad\Longrightarrow\quad\text{backlog grows}.
$$

无限扩容只会把系统拖进内存耗尽和延迟飙升的深渊。真正健壮的生产者—消费者系统，必须在缓冲区触顶时果断通过**背压**让上游慢下来，或者按业务规则做限流、降级与有控丢弃。

## 经典二：读者—写者（共享读，独占写）

### 场景与不变量

设想一份放在内存里的全局路由表或配置字典：99% 的请求只是进来查一眼（**读操作**），偶尔才会有管理员进来更新它（**写操作**）。

如果粗暴地用一把普通互斥锁罩住它，结果就是一百个同时来查路由的读者全被拦在门外排长队——可大家明明只看不改，互相之间根本不会打架！我们真正想守住的不变量其实是“读读并发、读写互斥、写写互斥”：

```text
writer_active == true  ->  reader_count == 0
reader_count > 0       ->  writer_active == false
```

围绕“读者和写者撞在一起时到底该偏向谁”，演化出了三种经典策略。

### 1. 读者优先

只要屋里已经有一个读者在看书，后面新赶来的读者可以直接免排队鱼贯而入；写者必须等到屋里最后一个读者也离开、人数归零后才能进场。这套策略把读吞吐拉到了极致，但隐患也显而易见：只要读者源源不断接力进来，屋里永远不断人，可怜的写者可能被活活**饿死**在门外，配置迟迟更新不上去。

### 2. 写者优先

为了救写者，规则掉转枪头：只要有写者在门外登记排队，立刻拉起警戒线拦住所有**新来的读者**；等屋里原本已在读的那几位看完退出后，立刻放写者进场改完。写者的等待延迟立刻漂亮了许多，可一旦写入变得频繁，新读者又反过来面临饥饿。

### 3. 公平排队方案

两头都不偏袒：把读者和写者统一按到达先后排进同一条队列（或分阶段轮流放行一批读者、再放行一位写者）。虽然两边都不会被彻底饿死，但为了维护额外排队状态，实现变复杂了，纯读高峰期的极限吞吐往往也会略低于读者优先。

### 反直觉的工程忠告：读写锁不一定比普通互斥锁更快！

很多人一看业务“读多写少”，就条件反射地把互斥锁全换成读写锁（`rwlock`）。但在高并发多核机器上实测，有时反而越换越慢！原因很隐蔽：**每来一个读者，都必须原子地把共享的 `reader_count` 加 1，读完再减 1。** 如果临界区本身极短（比如几十纳秒查一个指针），几十颗核心上的读者为了抢着写同一个 `reader_count` 缓存行，会在硬件总线上掀起惨烈的缓存行争抢风暴，开销甚至远超直接排一把简单互斥锁！

因此，读写锁真正大放异彩的甜区必须同时满足三条：
- 读操作确实占压倒性多数；
- 读临界区**足够长**，并发读赚回来的时间远大于维护读写锁状态的开销；
- 你已经确认过所用读写锁实现的偏向策略，不会在你的负载下把写者或读者饿死。

## 经典三：哲学家就餐（多锁顺序的试金石）

接下来这道题听起来像餐桌趣闻，却是并发系统里演练“多把锁怎么不死锁”的头号沙盘——**哲学家就餐问题**（dining philosophers problem）。

五位哲学家围坐在一张圆桌旁，每个人左右手边各摆着一把叉子（整张桌子一共只有 5 把叉子）。哲学家平时思考，饿了就必须**同时拿起左右两把叉子**才能吃面，吃完放下两把叉子继续思考。

### 朴素做法为何瞬间僵死？

最直觉的代码是让每位哲学家按相同套路行动：“先拿左手边的叉子，再拿右手边的叉子”。大多数时候大家错峰吃饭相安无事，可只要赶上某个倒霉瞬间，五位哲学家恰好同时喊饿、同时伸手抄起了各自的左叉——这下桌上再也没有空闲叉子了！每个人都死攥着左手里的叉子，扭头等着右边邻居把叉子放下来：

```text
P0 等 P1 手里的叉子
P1 等 P2 手里的叉子
P2 等 P3 手里的叉子
P3 等 P4 手里的叉子
P4 等 P0 手里的叉子  -> 闭合成环，全桌饿死！
```

怎么破局？三条经典解法分别对应了三种截然不同的系统架构思想：

### 破局一：全局资源编号（最常用）

给桌上的 5 把叉子编上号 `0, 1, 2, 3, 4`，立一条死规矩：**任何人拿两把叉子时，必须先拿编号小的，再拿编号大的。** 仔细看 0 到 3 号哲学家依然是先左后右，唯独 4 号哲学家手边是 4 号和 0 号叉子，按规矩他必须先抢 0 号叉子！这一改，等待关系永远只能沿着编号单调递增，**数学上彻底不可能再围成环**。

这套思想直接照进了 Linux 等大型内核的锁设计：给不同子系统的锁排好全局层级，凡是要同时持多把锁的操作，一律按层级从小到大加锁。

### 破局二：限制同时入座的竞争人数

既然 5 个人抢 5 把叉子才会卡死，干脆在餐桌外配一个初值为 `4` 的计数信号量——同一时刻最多只允许 4 位哲学家伸手拿叉子。抽屉原理保证，4 个人去分 5 把叉子，至少有一个人能稳稳凑齐一双吃完放下，环路永远凑不齐。

### 破局三：请一位服务员集中审批

哲学家不自己一把一把去摸叉子，而是统一向桌边的服务员申请：“请给我左右两把叉子。”服务员在自己的一把大锁下检查两把叉子是否都空闲，只有**两把全空时才一次性批给哲学家**，否则让他干等。这就消除了“手里攥着一把、干等另一把”的局面，代价比很清晰——服务员成了全桌唯一的集中调度瓶颈。

### 重要提醒：打破死锁 != 杜绝饥饿

哪怕用了全局编号确保整张桌子永远不会死锁，可依然可能出现极不公平的一幕：2 号哲学家左右两边的 1 号和 3 号配合得天衣无缝，交替霸占着他两侧的叉子，结果大家吃得热火朝天，唯独 2 号哲学家一次都没抢到过双叉，活活饿晕在座位上！想要既无死锁又无饥饿，还必须额外引入排队公平机制。

## 经典四：睡眠理发师（持久状态不能靠瞬时通知替代）

再来一道专治“事件先后顺序错位”的名题——**睡眠理发师问题**（sleeping barber problem）。一家小理发店里有 1 位理发师、1 张理发椅和 $N$ 张候客椅：
- 店里没客人时，理发师坐在理发椅上打盹；
- 客人推门进来，先看候客椅有没有空位：有空位就坐下等，并把打盹的理发师叫醒；如果 $N$ 张椅子全满了，客人扭头就走（拒绝服务）。

这道题最精妙的陷阱在于：**“客人在等”是一个需要持久记账的状态，绝不能只靠一次一闪而过的唤醒信号来表达。** 设想理发师刚剪完一个客人，正低头扫地还没来得及躺下睡觉，新客人刚好推门坐下大喊了一声“剪头！”——如果只靠瞬时通知，理发师扫完地一回头直接睡着了，新客人就在候客椅上干坐到天黑。

用信号量加一把保护空椅计数的互斥锁，就能把状态账算得滴水不漏：
- `customers`（初值 `0`）：记录店里已经坐好等待的顾客数（理发师 `wait(customers)`，没客人就睡，有客人就扣减一位开始服务）；
- `barber_ready`（初值 `0`）：表示理发师腾出手来招呼下一位顾客坐上理发椅；
- `mutex`：严密保护“剩余空候客椅数”的检查与扣减，确保满员时客人直接离开，绝不超卖座位。

## 经典五：可重用屏障（为什么必须给每一轮贴“代号”？）

在并行矩阵计算或分布式训练里，工作线程经常一轮接一轮地推进：必须等全部 $N$ 条线程都算完第 $g$ 轮，大家才能一起跨入第 $g+1$ 轮。

新手写可重用屏障时，常常只放一个计数器 `arrived` 和一个条件变量：先到的前 $N-1$ 条线程 `arrived++` 后睡在 `while (arrived < N)` 上，最后到达的第 $N$ 条把 `arrived` 清零并广播唤醒大家。

**跑两轮试试看，立刻就会出鬼！** 最后一人把 `arrived` 清零并广播后，如果其中一条醒得极快的线程瞬间跑完下一轮、抢先冲回屏障把 `arrived` 加成了 `1`，而上一轮里某条慢吞吞的线程此时才刚刚被唤醒、拿回锁重新检查 `while (arrived < N)`——它一看 `arrived == 1 < N`，以为自己还在上一轮没凑齐人，居然又安心睡回去了，全队直接卡死！

破局的妙招只需多加一个单调递增的整数 **`generation`（轮次号）**：每个线程进入屏障时，先把当前的 `my_gen = generation` 抄在自己的局部变量里，然后睡在 `while (my_gen == generation)` 上。最后到达的第 $N$ 条线程把 `arrived` 清零、**把 `generation` 加 1** 再广播。哪怕快线程一转眼跑进了下一轮，慢线程醒来比对自己的 `my_gen` 和全局 `generation` 早已不等，立刻就能干脆利落地放行通过，绝不串轮。

## 回望一个老熟人：锁与调度交织的优先级反转

第 2 章聊多核调度时我们见过一个诡异现象，如今学完锁再回头看会更有共鸣：低优先级线程 L 拿着锁，高优先级线程 H 卡在这把锁外头干等，偏偏中优先级线程 M 压根不要锁，却凭着优先级比 L 高把 CPU 死死占住，导致 L 永远跑不到解锁那一行，最高优先级的 H 反被不相干的 M 无限拖延。

解药**优先级继承**让 L 在持锁期间临时借用 H 的高优先级，一口气跑完临界区解锁再还回原优先级。不过在真实内核里落地它远比听起来复杂——如果 L 在持有锁 A 期间又去等更低优先级线程 K 手里的锁 B，高优先级还必须沿着整条锁等待链一路传递继承下去，否则依然会出现断层。

## 把纸上的经典题翻译回真实工程

学完这五个模型，合上书环顾真实系统，你会发现到处都是它们的影子：

| 经典并发模型 | 真实系统里的化身 |
| --- | --- |
| 生产者—消费者 | 异步日志管线、网络收发包队列、微服务线程池任务队列 |
| 读者—写者 | 内存路由表、热加载配置快照、内核元数据缓存 |
| 哲学家就餐 | 内核跨目录重命名双锁、银行账户双向转账、数据库多行事务锁 |
| 睡眠理发师 | 有界连接池、Web 服务器接听队列满时的过载拒绝与限流 |
| 屏障同步 | 多核科学计算迭代步、深度学习分布式训练的梯度聚合同步点 |

当然，真实工程在这些纯净模型之外，还会叠加上超时、取消、网络抖动、节点动态增删和崩溃恢复。但在上线前，养成对着下面这张七条自检清单扫一遍代码的习惯，能帮你提前拦截绝大多数深夜告警：

- 等待条件之前，是不是确实稳稳握着保护该谓词的互斥锁？
- 条件变量的等待，是不是写在 `while` 循环里重新检查，而不是 `if`？
- 修改共享状态后，是不是精准通知了等这个方向的等待者（或者稳妥地用了广播）？
- 同时获取多把锁时，是不是全代码库都遵守了统一的全局加锁顺序？
- 有没有哪条代码路径在持有锁的情况下，傻傻地去等另一个需要这把锁的人？
- 服务关闭时，是不是把所有方向睡着的线程全叫醒并让它们看到了关闭标志？
- 业务上除了“不死锁”，是不是还需要考虑公平性以防有人长期饥饿？

那五位围坐在圆桌旁的哲学家已经给了我们最直白的警告：只要几条线程的等待关系不小心围成一个圈，整套系统就会彻底定格、再也迈不开一步。这种让所有参与者永远卡死的僵局，到底在什么条件下必然诞生？除了提前规定加锁顺序，操作系统还有没有别的办法检测甚至把死锁活生生解开？带着这些问题，进入本章的收官之战——[死锁、检测与恢复](04_deadlock.md)。

## 自测

1. 生产者—消费者问题里，既然已经有了保护队列的互斥锁，为什么还必须额外引入条件同步（信号量或条件变量）？
2. 读者优先的读写锁在高并发读取场景下，可能会让哪一方陷入饥饿？
3. 在哲学家就餐问题中，为什么“给叉子统一编号，所有人先拿小号再拿大号”就能从数学上保证绝不死锁？
4. 如果实现一个只用一次的一次性屏障，不需要 `generation`；为什么一旦做成可重复使用的循环屏障，少了 `generation` 就会出错？
5. 优先级继承机制真正解决的是死锁、饥饿，还是优先级反转？

??? note "参考思路"

    1. 互斥锁只能防止生产者和消费者同时改坏队列指针与计数，却无法解决“队列满时生产者该去哪儿睡、队列空时消费者该去哪儿睡以及何时醒来”的协作等待问题。
    2. 可能会让**写者**陷入饥饿——只要不断有新读者接力进来，屋里的读者数永远归不了零，写者就一直拿不到独占写权。
    3. 规定先拿编号小的资源再拿编号大的，意味着资源等待图里的每一条有向边都只能指向编号严格更大的资源；沿着递增顺序永远不可能走回起点，因此等待图中不可能出现环路，打破了死锁的环形等待必要条件。
    4. 没有 `generation` 区分轮次时，上一轮最后到达者重置计数并唤醒大家后，跑得快的线程可能立刻冲进下一轮并修改计数，导致上一轮刚醒来的慢线程重新检查计数时误以为还在等上一轮，从而错误地再次睡眠卡死。
    5. 解决的是**优先级反转**——让持有高优先级任务所需锁的低优先级线程临时提权尽快跑完并释放锁，避免被无关的中优先级任务长期抢占而连累高优先级任务。
