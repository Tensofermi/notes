# 死锁、检测与恢复

## 两把锁，怎样把两条活蹦乱跳的线程彻底定格？

设想文件系统里正在并发执行两个看似平常的操作：线程 A 需要先锁住**文件锁**，再去拿**目录锁**；同一瞬间，线程 B 刚好反过来，先锁住了**目录锁**，接着伸手去拿**文件锁**。

平时两人错开几微秒，相安无事。直到某天运气耗尽，A 刚刚拿到文件锁，B 也刚好拿到目录锁——接下来 A 站在目录锁门口等 B 放手，B 站在文件锁门口等 A 放手。在纸上画下两条箭头：$A \rightarrow B$（A 在等 B），$B \rightarrow A$（B 在等 A）。箭头首尾相接，围成了一个死结：谁都没法走到自己后面的解锁代码，于是两条线程就这么定格在原地，直到天荒地老。

这种一群执行流永久互相等待彼此手里的资源、没有任何外部干预就再也无法推进的僵局，叫作**死锁**（deadlock）。反过来想，只要我们立一条铁律——“全系统任何代码，必须一律先拿目录锁，再拿文件锁”——那么 A 和 B 在第一步就一起去抢目录锁：没抢到的那个此刻两手空空，什么锁也没拿着，自然谁也不需要等他，那个致命的等待环就彻底无从诞生。

??? question "既然死锁是无限期等下去，那我给每次加锁都加一个 3 秒超时，是不是就能高枕无忧、保证业务结果一定正确了？"

    超时确实能把线程从永久卡死里救出来，让你获得一次“放弃等待”的机会，但它**绝不自动保证业务正确**。触发超时退出时，你必须把已经拿在手里的锁稳妥释放，还要仔细收拾残局——把做到一半的状态干净回滚或记录清楚，才能安全重试；否则半成品数据留在内存里，只会把死锁变成更可怕的数据损坏。

准确辨认死锁，要把它和“程序算得慢”以及“单个线程傻等一个永远不回包的外部网络请求”区分开来：死锁的核心特征是**系统内部多方之间形成了一个无法靠自己解开的等待闭环**。

## 拆解最小死锁现场

把上面那幕浓缩成两行伪代码，死锁的骨架一眼就能看穿：

```text
线程 A：lock(L1) -> lock(L2) -> ... -> unlock(L2) -> unlock(L1)
线程 B：lock(L2) -> lock(L1) -> ... -> unlock(L1) -> unlock(L2)
```

一旦 A 稳稳攥住 `L1`、B 稳稳攥住 `L2`，双方就会同时卡死在各自的第二步。因为解锁指令全都躺在第二次加锁的后面，谁也到不了自己的释放点，僵局就此焊死。

## 死锁诞生的四个必要条件

上世纪七十年代，Coffman 等人把死锁发生的根源提炼成了四条著名条件。**只有当这四个条件同时成立时，经典资源模型里的死锁才可能发生**：

1. **互斥（Mutual Exclusion）**：资源同一时刻只能由一个参与者独占（比如一把互斥锁，或者一台不能同时印两份文件的打印机）。
2. **占有并等待（Hold and Wait）**：参与者手里已经攥着至少一份资源不撒手，同时还伸手去等另一份被别人占着的资源。
3. **不可剥夺（No Preemption）**：系统不能强行把别人手里正在用的资源一把夺过来——只有等持有人自己干完活主动归还才行。
4. **环形等待（Circular Wait）**：存在一条首尾相连的等待链条 $P_1 \rightarrow P_2 \rightarrow \cdots \rightarrow P_k \rightarrow P_1$，环上的每一个人都在等下一个人手里的资源。

这四条条件既是诊断书，也是处方笺：**只要从设计上干掉其中任意一条，死锁就从数学上不可能出现。** 只不过，每一条被打破时，背后都标着实打实的工程价签——比如让资源变得可剥夺往往意味着要引入复杂的事务回滚，而禁止“占有并等待”（要求一次性把未来可能用到的所有资源全申请齐）又会把系统并发度和资源利用率压得很低。

## 把“谁等谁”画成图：资源分配图与等待图

当系统里有几十个线程、上百把锁时，光靠脑子想很容易绕晕。把它画成一张有向图，死锁往往瞬间原形毕露。

**资源分配图**（resource allocation graph）包含“进程/线程”和“资源”两类节点，用两种方向的箭头记账：
- **请求边（进程 $\rightarrow$ 资源）**：表示该进程正在等待这份资源；
- **分配边（资源 $\rightarrow$ 进程）**：表示这份资源此刻正握在该进程手里。

看图判死锁有一条特别容易考糊涂的细微边界：
- 如果**每类资源都只有 1 个实例**（比如每把独立的互斥锁），那么图里只要出现一个环，**就百分百已经死锁了**（充要条件）；
- 如果**某些资源有多个同类实例**（比如有 2 台一模一样的打印机），图里出现环只是“可能死锁”的必要条件！因为环外也许正有一个没被卡住的进程握着第 2 台打印机，等它几秒钟后用完一归还，环里等打印机的那个进程拿到机器就能跑通，整张环随之自动瓦解。

如果我们只盯着互斥锁这类单实例资源，还可以把中间的资源节点消掉，画成更干净的**等待图**（wait-for graph）：节点全是线程，$A \rightarrow B$ 直接代表“A 在等 B 手里的锁”。在这张图里，发现一个稳定的环，基本就抓到了死锁的现行。

## 面对死锁的四条工程路线

既然摸清了死锁的脾气，不同操作系统和数据库给出了四种画风迥异的对策：装看不见、从源头杜绝、每次放贷前精打细算，或者干脆先放行、真卡死了再动手术。

### 路线一：忽略（鸵鸟策略）

这听起来有点不负责任，却是绝大多数通用桌面操作系统（包括 Linux、Windows、macOS 对用户态应用锁死锁的态度）最务实的选择：如果死锁在普通日常使用里发生概率极低，而为了在内核里替所有应用防死锁所付出的性能损耗和接口限制却极高，那干脆不管——真碰上某个软件卡死了，让用户按强制退出或重启服务解决。这不是学术上的投降，而是赤裸裸的概率与成本权衡。

### 路线二：死锁预防（设计期打破四个条件之一）

直接在规则层面把四个必要条件里挑一个连根拔起：
- **打破互斥**：能做成无锁只读快照或独立副本的资源，就别让大家挤在一起抢独占锁；
- **打破占有并等待**：规定必须一次性把所需的全部资源都申请齐，只要缺一样就干脆一个也不拿；
- **打破不可剥夺**：如果申请第二份资源失败，就主动把自己已经攥着的第一份资源退还回去（或者允许系统强制回滚抢占）；
- **打破环形等待**：给全系统所有锁排好全局顺序，所有人一律按顺序申请。

在操作系统内核和大型基础软件里，**锁层级排序**（打破环形等待）是实战中用得最广、性价比最高的一招，许多内核甚至内置了运行期验证器（如 Linux 的 `lockdep`），专门在测试阶段自动揪出任何“曾先 A 后 B、又在别处先 B 后 A”的反向加锁隐患。

### 路线三：死锁避免（运行期精打细算——银行家算法）

预防的规矩有时太死板，能不能在运行过程中动态放行资源，但**每一次放行前都先在草稿纸上推演一遍：把这份资源借给你之后，系统会不会陷入万劫不复的境地？**

这就是 Dijkstra 提出的**安全状态**（safe state）概念：只要系统里至少存在**某一种**让所有进程依次借够剩余所需资源、跑完并全部归还的先后序列，当前状态就是安全的；一旦某次分配会导致再也找不到这样的安全序列，哪怕此刻手里还有空余资源，系统也宁可先拒绝这次请求，让申请者等等再说。

实现这一思想的经典算法叫**银行家算法**（banker's algorithm）——像一位极度谨慎的银行家，放贷款前先算清楚每个客户的最大信用额度 $Max_i$、已经贷走多少 $Allocation_i$，从而得出他最多还可能需要再贷多少：

$$
Need_i=Max_i-Allocation_i.
$$

接着银行家拿着金库里当前可用的现金 $Work$ 开始沙盘演练：能不能找到一个还没算完的客户 $i$，他剩余最大需求满足 $Need_i \le Work$？如果能，就假想把钱借给他让他顺利做成生意、连本带利把之前借走的钱也全部还回金库：

$$
Work\leftarrow Work+Allocation_i.
$$

只要能这样滚雪球般把所有客户挨个顺利盘活，这笔贷款就敢批！

银行家算法思想极其优美，可为什么真实通用操作系统几乎不用它呢？因为它的前提在现实里太奢侈了：**进程必须在一出生就提前申报自己这一生最多会申请哪些资源、各要多少**，而且进程数固定、每次分配都得跑一遍安全性检查。普通应用程序压根不知道用户待会儿会点开几个文件、申请多少内存，于是银行家算法更多停留在理论启发和特定受控资源池里。

### 路线四：检测与恢复（先放手跑，真卡死再救火）

数据库管理系统走的是另一条爽快的路子：平时完全不限制事务的加锁顺序，最大限度榨干并发度；但在后台周期性地构造等待图（或检查锁超时），一旦揪出等待环，立刻启动**恢复手术**：
- 挑出环里的一个或多个“受害者”，强行中止它们或把它们的事务干净回滚，把占着的锁释放出来，环上其他卡住的事务立刻如获大赦继续飞奔；
- 如果涉及可安全剥夺的资源，则强制回收并稍后重做。

挑选“受害者”本身也是门艺术：通常优先牺牲刚起步、已做功最少、回滚代价小或者优先级较低的那个事务。还要留心防一手**重复倒霉的饥饿问题**——别每次撞死锁都把同一个可怜的任务挑出来枪毙，导致它重试十遍还是永远完不成。

## 工程界最爱用的护身符：全局锁顺序

把四条路线比过一轮，你会发现写多线程代码时，最靠得住的护身符依然是开头那招——**为所有锁定义严格的全序关系 $L_1 < L_2 < \cdots < L_n$，要求任何代码在需要同时持多把锁时，一律按编号从小到大加锁。**

为什么它绝对可靠？两行反证法就能钉死：假设遵守了这条规矩还是形成了死锁环 $P_1 \rightarrow P_2 \rightarrow \cdots \rightarrow P_k \rightarrow P_1$，那么沿环每走一步，等待的锁编号都必须严格大于手里已持有的锁编号——顺着环转一圈回到起点，就会推出 $L_{start} < L_{start}$ 的荒谬矛盾！因此环路绝无可能存在。

道理简单，落到百万行工程代码里却有四个真实拦路虎：
- **动态对象怎么排序？** 比如银行转账函数 `transfer(from, to, amount)` 需要同时锁住两个动态创建的账户对象，如果同时有人把钱从 A 转给 B、另一人把钱从 B 转给 A，直接“先锁 `from` 再锁 `to`”必死锁！破法很巧妙：**按账户唯一的 ID（或内存地址）比大小**，永远先锁 ID 小的账户、再锁 ID 大的账户；
- **隐藏的回调函数**：你的代码按顺序拿了 `L1`，顺手调了一个外部回调，结果回调里拐弯抹角去拿了编号更小的 `L0`，悄悄违背了全局顺序；
- **跨子系统层级冲突**：文件系统层和内存管理层各自定了一套锁规则，交汇处极易撞车；
- **数据结构反向遍历**：比如双向链表有时必须从后往前同时锁相邻节点。

工程上的常见拆弹技巧包括：按唯一 ID/地址排序、把一步大操作拆成释放旧锁再拿新锁的两阶段操作、缩小同时持多把锁的临界区，或者借助 `try_lock` 退避重试。

## 用 `try_lock` 退避，会不会掉进另一个坑？认识活锁

既然“拿不到第二把锁就死等”会死锁，一个机灵的点子立刻冒了出来：拿到 `L1` 后，我用非阻塞的 `try_lock(L2)` 试探一下——如果 `L2` 正忙，我就礼貌地立刻把 `L1` 也放掉，过一会儿从头再来！

这一招确实彻底打破了“占有并等待”，死锁消失了。可设想一下你在狭长走廊里迎面撞见一个陌生人：你礼貌地往左跨一步让路，他也刚好往你的左边（他的右边）跨了一步；两人对视一笑，又同时往另一边跨了一步……两个人忙得满头大汗，谁也没停下来，可谁也没能向前走过一寸！

并发世界里的这种僵局叫作**活锁**（livelock）：线程 A 拿到 `L1`、`try_lock(L2)` 失败立刻释放 `L1`；同一节拍上线程 B 拿到 `L2`、`try_lock(L1)` 失败立刻释放 `L2`；下一微秒两人齐刷刷重新开始，CPU 占用飙到 100%，有用进展却是零！

破解活锁的思路就像过走廊时“打破对称性”：引入**随机退避时间**（比如失败后随机等一小段不同时长再重试）、让某一方优先排队，或者干脆老老实实用全局锁顺序。

## 一张表分清三兄弟：死锁、活锁与饥饿

它们在用户眼里都表现为“请求卡着完不成”，但翻开监控证据，三者长相迥异：

| 现象 | 线程还在消耗 CPU 吗 | 系统有有用进展吗 | 背后的典型病根 |
| --- | --- | --- | --- |
| **死锁（Deadlock）** | 否（全员安静阻塞） | 否（环内全员定格） | 形成无法自行打破的环形等待 |
| **活锁（Livelock）** | 是（往往 CPU 居高不下） | 否（原地白忙活） | 彼此同步礼让、反复重试撞车 |
| **饥饿（Starvation）** | 系统其他线程在忙 | 系统整体在推进，唯独某个倒霉蛋停滞 | 调度或锁竞争长期不公平、总被插队 |

## 别只盯着 `mutex`：逻辑死锁与分布式死锁

排查卡死时，一个经典盲区是满世界只搜 `pthread_mutex_lock`。其实，**任何需要等待的条件和资源都能织出死锁环**！

哪怕你的每一段代码都在条件变量等待时乖乖释放了互斥锁，只要线程 A 在等“线程 B 把状态 X 改成就绪”，而线程 B 又在等“线程 A 把状态 Y 改成完成”，或者两个微服务之间各自把对方的同步 RPC 管道塞满、谁也不先读对方的响应——这种**逻辑死锁**照样能让整套系统彻底停摆。因此，脑子里的等待图节点必须把锁、条件变量、有界队列空位、进程间管道和外部任务依赖统统算进去。

把视野再拉远到跨机器的**分布式死锁**，麻烦更是指数级上升：
- 整张等待图散落在几十台独立服务器上，没人能一眼看清全局快照；
- 网络传输有延迟，等你把各节点的等待边收集齐，半秒前的状态可能早就过时了；
- 节点宕机和网络抖动让人真假难辨——对方半天没放锁，究竟是陷入死锁了、机器断电了，还是单纯网速慢？

因此分布式系统极少能靠完美的全局预防杜绝死锁，更多依赖**事务日志回滚、带有效期的租约（Lease）与超时中断**来保底。只是心里要有数：**超时能打破僵局，却不是死锁的铁证**——盲目把超时设得太短，反而可能把正常但稍慢的合法请求误杀，甚至诱发雪崩式的重试风暴。

## 线上遭遇疑似死锁，怎么六步破案？

真遇上服务彻底卡死、既不报错也不吐日志时，按这六个步骤抽丝剥茧：

1. **先判状态**：用 `ps`、`top` 或线程快照确认卡住的线程处于阻塞睡眠（`S`/`D`）还是满载空转（`R`），先把死锁、活锁和纯慢计算拆开；
2. **拉全员堆栈**：死锁是**群体关系属性**，只盯着某一个线程的调用栈永远破不了案！把进程内所有线程的堆栈（如 `gdb`、`pstack`、JVM `jstack`、Go `SIGQUIT` dump）一次性全抓出来；
3. **画等待图找环**：逐个记录“线程 X 正在等哪把锁/哪个队列，而这把锁此刻握在线程 Y 手里”，连线寻找首尾闭合的环；
4. **顺藤摸瓜查反序与回调**：检查环上各处加锁顺序是否违反了全局层级，尤其留意持锁期间不小心触发的隐藏回调或日志/内存钩子；
5. **扩大搜索面**：没找到锁环时，立刻检查有界队列是否满死、线程池是不是出现“父任务占满全部工作线程、却又在同步等待子任务被同一线程池执行”的经典**线程池饥饿死锁**；
6. **最小复现与回归防护**：写个刻意加随机延迟扰动的并发压力测试，把修好的锁顺序焊进自动化检查（如 ThreadSanitizer 或锁序审计工具）里。

## 设计权衡：没有一招鲜的银弹

回头盘点全篇，防死锁的每一种选择都逃不开工程取舍：
- 粗粒度大锁让加锁顺序的烦恼烟消云散，却把多核并行压成单车道；
- 一次性申请齐所有资源干掉了死锁，却让大量本来能并发的短任务闲等；
- 允许死锁发生再靠检测与回滚兜底，能把平时并发吞吐拉到最高，前提是你的业务操作具备可撤销回滚的能力——这正是为什么拥有完善日志回滚的**数据库**偏爱死锁检测，而面对一旦发出就收不回来的硬件设备控制，**操作系统内核**却不得不老老实实死守严格的锁顺序与预防纪律。

至此，第 4 章的硬仗圆满打完。我们驯服了并发交错的猛兽：用锁与原子操作守住临界区，用条件变量和信号量优雅等待，用全局顺序和检测手段化解了死锁僵局。

不过，把视线从“谁在什么时候改数据”稍微往旁边移一寸，一个同样神奇的谜题一直在脚下等着我们揭晓：同一台电脑只有 16 GB 物理内存，可打开任务管理器一看，几十个进程各自都宣称自己独占着一整片从 `0` 开始、庞大连续的地址空间，彼此互不打架，甚至所有进程宣称占用的地址加起来远远超过了内存条的真实容量！操作系统和硬件究竟施展了什么障眼法，才变出了这套“人人独占内存”的宏大幻觉？让我们迈进下一章——[第 5 章 虚拟内存与内存压力](../chapter_04_memory/index.md)。

## 自测

1. 死锁的四个必要条件中，工程上最常用的“全局锁编号按序加锁”破坏的是哪一个？
2. 为什么在资源分配图里，如果某些资源拥有多个相同实例，图中出现一个环并不意味着系统就一定已经死锁？
3. 用 `try_lock` 在拿不到第二把锁时立刻释放第一把并重试，避开了死锁，却可能引出什么新问题？该如何缓解？
4. 银行家算法里的“安全状态”，是不是要求系统此刻手头的空闲资源足以同时满足所有进程的最大需求？
5. 为什么说“加锁等待 5 秒超时”只能作为打破卡死的手段，而不能当作“系统一定发生了死锁”的充分证据？

??? note "参考思路"

    1. 破坏的是**环形等待**——沿等待链锁编号严格递增，数学上不可能围成首尾相接的环。
    2. 因为环外可能还有未被卡住的进程持有该类资源的另一个空闲实例；一旦它执行完毕归还该实例，环里等待该类资源的进程就能拿到资源继续推进，从而自然解开整个环。
    3. 可能引发**活锁**（多条线程以完全相同的节奏同时拿第一把锁、同时试探失败、同时释放再同时重试，忙个不停却毫无进展）。可通过随机退避时间、打破对称规则或改用全局锁顺序来缓解。
    4. 不是。安全状态只要求存在**至少一种先后完成顺序**，让进程一个接一个拿到剩余所需资源并全部归还，就像滚雪球一样依次盘活，而不需要同时把所有人的最大需求一次性全拿出来。
    5. 超时只能证明“这 5 秒内没拿到锁”，它完全可能只是因为持锁者恰好在执行一次极慢的正常操作或遭遇磁盘/网络拥堵；要确诊死锁，必须看到多方互相依赖形成的稳定等待环。
