# 并发、同步与死锁 { #3 }

## 当“一行代码”在半空中被劈成两半

在前两章里，我们见识了调度器如何神不知鬼不觉地在多个任务间切来切去：一个任务等键盘或磁盘时，另一个任务立刻接棒跑起来；就算在多核机器上，好几条线程也能同时火力全开。多项工作在同一段时间内交替推进、或由多个核心同时推进，这种运行方式叫作**并发**（concurrency）。

并发本身是现代计算机榨干性能的利器，可只要两条线程开始触碰**同一份共享数据**，一头极难捉摸的猛兽就会被放出来。最诡异的地方在于：每个线程自己的代码单独看都天衣无缝，可一旦指令在半空中交错执行，程序的最终结果就会随每次运行不同的调度时序而飘忽不定——测试跑一百遍全绿，上线第一天就在深夜悄无声息地把账算错。

本章的四篇文章，就是沿着“见识事故 -> 造出工具 -> 实战建模 -> 避开死锁”的路线一步步驯服这头猛兽：先从[一个凭空少加了一次的计数器](01_races_atomicity_locks.md)看清指令交错如何酿祸、又该如何用硬件原子指令与锁圈出安全领地；接着把目光转向“等条件”的难题，在[信号量与条件变量](02_semaphores_condition_variables.md)里学会如何让线程优雅睡眠而不是原地空转；随后用生产者—消费者、读者—写者、哲学家就餐等[经典同步问题](03_classic_synchronization.md)把建模套路刻进肌肉记忆；最后正面拆解并发世界最凶险的僵局——[死锁、检测与恢复](04_deadlock.md)。

## 理解并发的两把钥匙：不变量与原子性

面对千变万化的线程交错，凭脑子去穷举“每条指令谁先谁后”很快就会崩溃。真正老练的系统工程师，手里紧紧攥着两个锚点。

第一把钥匙是**不变量**（invariant）——不管线程怎么交错，在每一次完整操作前后，系统状态都必须始终守住的底线规律。比如“银行转完账，两个账户的总金额不变”“有界队列里的元素个数永远在 `0` 和容量之间”“完成了两次自增，计数器就必须比原先多 `2`”。

第二把钥匙是**原子性**（atomicity）。拿最不起眼的 `counter++` 来说，在 C 或 Python 源码里它只占半行，落到 CPU 眼里却是“从内存读旧值 -> 在寄存器里加 1 -> 写回内存”三步曲。只要两条线程同时执行它，彼此都读到旧值再各自写回，就会有一份加一悄无声息地蒸发。为了保卫不变量，我们需要让这三步对其他线程表现为一个**不可分割的整体动作**——要么还没开始，要么已经彻底干完，谁也别想在半道上插进来偷看或改写。这就是原子性。

说到底，本章接下来要认识的所有同步工具，本质上都是在用不同手法保卫不变量、重建原子性，并在条件尚未成熟时有序协调各方的节奏。

## 工具选型的一眼直觉

初学同步原语最容易陷入“名词太多、不知道该掏哪一件”的迷茫。其实先问清楚自己想表达哪种语义，工具自然就会对号入座：

| 你想解决什么具体问题 | 最称手的工具 |
| --- | --- |
| 同一时刻只许一条线程动手修改某块共享状态 | 互斥锁（Mutex） |
| 临界区极短（几十纳秒）、且所处上下文绝不能睡眠 | 自旋锁（Spinlock）或硬件原子操作 |
| 线程需要休眠，直到“队列非空”“任务完成”等条件成立 | 条件变量（配合互斥锁） |
| 给 $N$ 份同类稀缺资源发“入场券”，或做跨线程到达计数 | 计数信号量（Semaphore） |
| 某份全局配置只想初始化一次，其他线程等着它准备好 | 语言提供的一次性初始化原语 |

记住：原语的名字从来不是重点。真正决定并发代码生死的，是你有没有先白纸黑字写清楚——**哪些状态是共享的、必须守住什么不变量、谁来改状态、谁在等条件，以及等待和通知是否遵守了同一套同步协议。**
