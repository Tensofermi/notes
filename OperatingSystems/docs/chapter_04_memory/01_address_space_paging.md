# 地址空间与分页

打开电脑上的编辑器、浏览器和终端，几十个程序挤在同一根内存条里，每个程序的代码里却都在自由自在地使用着相似的内存地址，既不打架、也看不见彼此的私密数据。操作系统和硬件究竟靠什么给每个程序各自变出了一片专属天地？

**阅读建议**：第一遍读时，先顺手把下面那个 16 字节迷你算例拿纸笔算通，再连着读完“4096 字节页翻译例子”和“按需分页”，先把核心直觉立住；第二遍再细品大页、共享页面、写时复制与 `mmap` 的巧妙配合。

## 两个程序都去读“26 号地址”，怎么能拿到两份不同数据？

假设机器里正同时跑着两个互不相干的进程 A 和 B，它们各自发出指令：“读地址 `26`。”我们当然希望 A 读到的是 A 的数据，B 读到的是 B 的数据。

实现它的核心办法，是在“程序看到的地址”和“内存条上的真实地址”之间插一层翻译：程序眼里使用的 `26` 叫作**虚拟地址**（virtual address），内存条硬件认的真实编号叫作**物理地址**（physical address）。操作系统为每个进程规划出的那整套可用的虚拟地址视野，就是它的**地址空间**（address space）；每个进程各配一张私有的地址对照表，CPU 跑谁的指令，就自动翻谁的表来翻译。

为了能拿口算一眼看穿本质，我们先造一个迷你玩具系统：规定每 **16 字节**切为一整块。虚拟地址空间里切出来的 16 字节小块叫**虚拟页**（virtual page，简称**页**，page）；物理内存条里对应切出来的 16 字节格子叫**物理页框**（page frame，简称**页框**）。记录“哪一页住进了哪个页框”的对照表，就是大名鼎鼎的**页表**（page table）。下面分别列出进程 A 和进程 B 各自页表里的前几行：

| 虚拟页号 | 覆盖的虚拟地址范围 | A 的页表（去哪个页框） | B 的页表（去哪个页框） |
| --- | --- | --- | --- |
| 0 | `0` 到 `15` | 页框 3 | 页框 4 |
| 1 | `16` 到 `31` | 页框 5 | 页框 2 |
| 2 | `32` 到 `47` | 页框 1 | （当前无有效映射） |

现在，亲手把虚拟地址 `26` 翻译成物理地址！只需两步：先看 `26` 落在第几页，再看它在这一页里排第几格。用小学除法一算：$26 = 1 \times 16 + 10$，也就是说它是**第 1 号虚拟页里的第 10 号偏移位置**。
- 轮到进程 A 运行时，硬件查 A 的页表：第 1 页对应**页框 5**。页框 5 的物理起点是 $5 \times 16 = 80$，往后数 10 格，物理地址稳稳落在 $80 + 10 = 90$。
- 轮到进程 B 运行时，硬件查 B 的页表：第 1 页对应**页框 2**。页框 2 的物理起点是 $2 \times 16 = 32$，往后数 10 格，物理地址落在了 $32 + 10 = 42$。

```text
虚拟地址 26  ==拆解==>  虚拟页号 1  +  页内偏移 10
                                         │
          查 A 的页表：页 1 -> 页框 5    物理地址 = 5×16 + 10 = 90
          查 B 的页表：页 1 -> 页框 2    物理地址 = 2×16 + 10 = 42
```

留意一个极其舒爽的规律：**页内偏移（这里是 10）在翻译前后纹丝不动！** 就像把一整本 16 页的小册子搬到书架另一个格子里，书里的第 10 页照样排在册子的第 10 位。正因为每页大小固定统一，程序眼里紧挨着的相邻虚拟页，完全可以打散塞进物理内存条里毫不相干的任意空闲页框中，只需在页表里各自记清去向即可。

??? question "趁热打铁算一题：进程 A 连续读取虚拟地址 `31` 和 `32`，它们在物理内存里也会紧挨着差 1 吗？"

    不会！让我们算一遍：`31 = 1 × 16 + 15`，落在虚拟页 1，查 A 的页表对应页框 5，物理地址是 `5 × 16 + 15 = 95`；紧接着下一个字节 `32 = 2 × 16 + 0`，已经跨进了虚拟页 2，查 A 的页表对应页框 1，物理地址猛地跳到了 `1 × 16 + 0 = 16`！**虚拟地址的连续性，绝不要求物理页框也连续**——这正是分页解放物理内存的最大魔力。

??? example "用 10 行 Python 验证你的手算结果"

    下面这段迷你脚本模拟了上面的页表查表逻辑；返回 `None` 代表该虚拟页在页表里目前没有有效映射。

    ```python
    def translate(address, page_table, page_size=16):
        page, offset = divmod(address, page_size)
        frame = page_table.get(page)
        if frame is None:
            return None
        return frame * page_size + offset

    table_a = {0: 3, 1: 5, 2: 1}
    table_b = {0: 4, 1: 2}

    print(translate(26, table_a), translate(26, table_b))  # 90 42
    print(translate(31, table_a), translate(32, table_a))  # 95 16
    print(translate(32, table_b))                         # None
    ```

## 为什么不干脆直接用物理地址？

回头想想早年简陋的计算机：那时候程序里写的地址直接就是物理内存条上的真实地址。这套做法一遇到多任务就处处撞墙：

- **地址冲突**：编译器给程序 A 和程序 B 都安排从物理地址 `0x1000` 启动，两个程序根本没法同时装进内存；
- **搬家困难**：哪怕硬把程序 B 挪到 `0x8000` 去装，代码里所有跳转指令和全局变量地址全得重新修正一遍——这种繁琐的改地址工程叫作**重定位**（relocation）；
- **毫无隔离**：程序 B 只要把指针往低处一减，就能轻轻松松读走程序 A 的密码，甚至一把抹掉内核代码；
- **装不下大程序**：要是物理内存只有 4 GB，而你同时开了十个宣称需要 1 GB 内存的程序，直接用物理地址根本没法做到“只把眼下正在用的那一小撮数据留在内存里”。

引入虚拟地址空间后，上述四个难题一举化解：每个进程都活在从低地址到高地址、整洁统一的虚拟视图里，物理内存的分配、挪动与隔离全被操作系统悄悄收进幕后。

## 一张进程地址空间的“户型图”

在现代操作系统里，一个普通进程的虚拟地址空间概念上常排布成这样：

```text
高地址
  ┌──────────────────────────┐
  │ 内核保留区 / 用户不可访问  │
  ├──────────────────────────┤
  │ 用户栈（通常向低地址增长） │
  │            ↓             │
  │      （广阔的未映射空洞）   │
  │    共享库与内存映射区      │
  │      （广阔的未映射空洞）   │
  │            ↑             │
  │ 堆（通常向高地址增长）     │
  ├──────────────────────────┤
  │ 全局与静态数据段           │
  ├──────────────────────────┤
  │ 只读程序代码段             │
  └──────────────────────────┘
低地址
```

请一定打破一个直觉误区：图里堆和栈之间那片动辄几百上千 GB 的“未映射空洞”，**一丁点真实的物理内存都不占！** 虚拟地址空间只是一张极度宽敞的蓝图，操作系统只在程序真正用到某段区域时，才按需给它分配背后对应的物理页框。另外，出于安全考虑，现代系统还会随机打乱栈、堆和共享库的起始落点，实际布局并不像教材简图那样年年固定不变。

## 历史演进：从“基址—界限”到“分段”，为何最终走向“分页”？

分页并不是天才拍脑袋一步想出来的，而是工程师踩过两代前辈的坑之后逼出来的优雅答案。

### 第一代：基址与界限（整块连续搬迁）

最朴素的虚拟化硬件只在 CPU 里加两个寄存器：起始位置 `base` 和允许长度 `limit`。进程发出逻辑地址 $x$，硬件瞬间检查 $0 \le x < limit$（越界就报警），通过后简单一加就算出物理地址：

$$
physical=base+x.
$$

它虽然便宜又快，却有两个致命硬伤。首先，为了给堆和栈留出各自向上向下生长的余地，整块连续空间中间不得不白白预留大片空荡荡的物理内存；更糟的是，随着一批批大小不一的程序不断启动和退出，物理内存条会被切得像一块千疮百孔的奶酪——明明剩下两块各 8 MB 的空闲缝隙，加起来足足 16 MB，可新来的一个 12 MB 程序因为要求**物理连续**，偏偏哪块都塞不进去！这种“总空闲够大、却碎成小渣用不上”的毛病，叫作**外部碎片**（external fragmentation）。

### 第二代：分段（按逻辑切块）

为了不再为堆和栈中间的空白浪费物理内存，第二代设计推出了**分段**（segmentation）：把进程拆成代码段、数据段、堆段、栈段等逻辑区域，每段各自拥有独立的基址、界限和读写权限。这样既省掉了中间空洞，又能方便地让多个进程共享同一份只读代码段。

可惜，因为不同程序的代码段和数据段大小依然千差万别，段长大时还得整段搬家，**外部碎片这个幽灵依然阴魂不散**。现代主流通用系统大多不再靠硬件分段做主内存分配，但“按代码、数据、栈等逻辑区域分别管理权限”的思想，完整保留在了内核的虚拟内存区域（VMA）管理里。

### 第三代：分页（统一规格，终结外部碎片）

**分页**（paging）的灵光一闪极其彻底：**既然大小不一的块才会留下凑不齐的零碎缝隙，那就干脆把所有虚拟空间和物理内存全都按同一个固定尺寸切成方块！** 只要物理内存里还有任何一个空闲页框，就能立刻分给任何需要一页的进程，外部碎片就此从页框分配层面彻底绝迹。

在二进制计算机里，只要把页大小定为 2 的幂次 $P = 2^p$ 字节（例如现代最常见的 $4096 = 2^{12}$ 字节，即 4 KiB），连除法和取余都不需要算——硬件只需直接把虚拟地址的高位截出来当作虚拟页号（VPN），低 $p$ 位原封不动当作页内偏移：

```text
+-----------------------+------------------+
|     虚拟页号（VPN）    |  页内偏移（p 位）  |
+-----------------------+------------------+
```

地址翻译要做的全部事情，就是把左半边的“虚拟页号”查表换成“物理页框号”，右半边的偏移原样拼接！

## 真实尺寸热身：4096 字节页的最小翻译算例

把前面 16 字节的玩具放大到真实电脑最常见的 **4096 字节（4 KiB）页**。假设进程访问虚拟地址 `13,000`，跟着老规矩走三步：

1. 用除法算出它落在哪一页（虚拟页号 VPN）：
$$
VPN=\left\lfloor\frac{13000}{4096}\right\rfloor=3.
$$
2. 用取余算出它在这一页里的位置（页内偏移）：
$$
offset=13000\bmod4096=712.
$$
3. 查当前进程的页表：假设第 3 号虚拟页映射到物理页框 20，拼出最终物理地址：
$$
physical=20\times4096+712=82632.
$$

程序代码从头到尾只知道自己在读写 `13,000`，底层硬件和内核悄无声息地把它送到了内存条的 `82,632` 号字节。

借这组具体数字，正好可以和组成原理里的硬件路径对上暗号：如果页框 20 已经在物理内存里，但 CPU 的高速翻译缓存里还没记下页号 3，硬件就会先去遍历页表；如果页表里标着“这一页还没装进内存”，就会触发缺页进入内核；而一旦算出了物理地址 `82,632`，接下来还要查 CPU 的数据 Cache 命没命中。这三条硬件路径的完整对照，可以延伸阅读<a href="../../ComputerOrganization/chapter_06_memory/virtual_memory_hardware.html">组成原理的访存算例</a>。

只要你能在草稿纸上顺手写出这三步——**除法找页、余数找偏移、查当前进程页表换页框**——分页最核心的骨架你就已经完全拿下了。

## 页表里的一行，除了“页框号”还藏着哪些机关？

既然硬件每次翻译都要看一眼页表项（Page Table Entry，PTE），设计师顺手往这一行里塞进了一排威力巨大的标志位，让页表同时扛起了**权限保护**和**活跃度追踪**两副重担：

- **有效位（Present / Valid）**：这一页此刻到底在不在物理内存里？如果为 0，硬件当场触发缺页异常交由内核裁决；
- **读写执行权限（R / W / X）**：精确到每一页控制能不能读、能不能写、能不能当指令执行；
- **用户/内核位（User / Supervisor）**：标记这一页是不是内核禁地——用户态程序伸手一碰就立刻触发保护异常；
- **访问位（Accessed / Reference）**：只要最近有人读过或写过这一页，硬件自动把它置 1，帮页面置换算法判断哪页是“热页”；
- **脏位（Dirty）**：只要有人改写过这一页，硬件自动把它置 1，告诉内核“将来踢出这一页时别忘了先写回磁盘”；
- 还有缓存策略位、全局映射位，以及留给软件记录“写时复制”等语义的保留位。

有了页级 `R / W / X` 权限，操作系统能轻松筑起一道经典的防线——**W^X（Write XOR Execute，写与执行互斥）**：代码页只读可执行、不准篡改；堆栈和数据页可读写、却**禁止当机器指令执行**。这样就算攻击者靠缓冲区溢出把恶意机器码塞进了栈数组里，CPU 一跳过去执行也会因为缺少 `X` 权限当场毙命。（像浏览器 JavaScript 引擎这类需要运行期动态生成机器码的 JIT 编译器，则必须走受控的权限切换流程：先写完，再把权限从“可写不可执行”切到“只读可执行”。）

## 分页消灭了外部碎片，却留下了“内部碎片”

天下没有免费的午餐。固定页大小干掉了页框之间的外部碎片，却带来了另一种浪费：假设你的程序只需要 `4097` 字节，因为分配最小单位是一整页（`4096` 字节），系统不得不分给你 2 页，第二页里整整 `4095` 字节就这么空在里头、没法再借给别人用。这种浪在已分配页内部的空余空间，叫作**内部碎片**（internal fragmentation）。

如果大略假设对象的末尾大小均匀随机分布，每个独立区域最后一页平均会浪费大约半页：

$$
E[waste]\approx\frac{P}{2}.
$$

这就给“页尺寸 $P$ 该定多大”画出了第一道紧箍咒：页定得太大，小映射的末尾浪费会非常肉疼；可页定得太小，页表自己又会暴涨成庞然大物（下一篇马上算这笔账）。真实世界里 4 KiB 之所以统治了几十年，正是当年在两者之间反复称量出来的折中甜点。

## 按需分页：不到真用那一刻，绝不提前掏物理内存

打开一个几百兆的大型程序，操作系统真的在双击图标那一秒就把几百兆代码全从硬盘搬进内存了吗？并没有——如果你只是打开它改了两行字就关掉，90% 的冷门功能代码这辈子都没执行过，提前全搬进来纯属白白耽误启动时间和糟蹋内存。

于是现代系统普遍采用**按需分页**（demand paging）：进程启动或申请大片内存时，内核只在账本上圈出这块合法的虚拟区域，顺手把对应页表项统统标为“暂不在内存”（有效位为 0），一页物理内存都不急着给！

直到程序第一次真正去读写其中某个地址，硬件一查页表发现有效位是 0，立刻触发**缺页异常**（page fault）把控制权交给内核。

回头看看开篇迷你表里 **进程 B 访问地址 `32`** 的情景：B 的页表里第 2 页目前没有有效页框，硬件一报警，内核立刻翻开 B 的虚拟内存区域账本甄别两种截然不同的真相：
- **合法的首次访问**：如果地址 `32` 确实落在刚申请的堆空间或已映射的文件范围内，内核就从容地从空闲池里拨一个新页框——若是堆/栈等空白内存就先清零防泄密，若是文件就从磁盘读入对应内容，若是之前换出去的页就从磁盘的**交换区**（swap space）读回来——填好页表后返回用户态，**重新执行刚才那条访存指令**，进程甚至浑然不觉自己刚进过一趟内核！
- **真正的非法越界**：如果地址 `32` 压根不属于任何合法区域（比如解引用了空指针 `NULL`），或者企图往只读代码页里写数据，内核就会果断拒绝补页，直接给进程送上一记致命信号（如 `SIGSEGV` 段错误）。

按需分页让程序启动飞快、让稀疏地址空间零浪费，还能把宝贵的物理内存集中留给程序眼下正频繁访问的那一小撮热点页面——我们把这组热点页面称为当前程序的**工作集**（working set）。记住这个词，到了[页面置换一篇](03_replacement_allocation.md)，你会看到一旦所有活跃进程的工作集加起来撑爆了物理内存，系统就会坠入可怕的抖动深渊。当然，按需分页的代价也很直白：首次触碰页面时的延迟难以预测，对极端讲究确定性低延迟的实时任务，往往需要提前锁页预热。

## 页表的三大绝活：共享页面、写时复制与 `mmap`

一旦在虚拟页和物理页框之间插进了页表这层间接映射，许多原本听起来像魔术的高级功能瞬间水到渠成。

### 绝活一：共享页面（多张页表指向同一个页框）

谁规定不同的页表不能指向同一个物理页框？一台服务器上跑着 50 个都用到了标准 C 库（`libc`）的进程，难道要在物理内存里存 50 份一模一样的库代码吗？完全不用！内核只在物理内存里装入**一份**只读的 `libc` 代码页，然后让 50 个进程的页表各自指向这同一批物理页框——瞬间省下 49 倍物理内存！

除了共享只读库代码，共享页也是第 2 章**进程间共享内存**、同一文件被多进程同时映射，以及下面写时复制的共同底座。当然，如果共享页面允许写入，各进程之间就必须像多线程一样遵守严格的同步协议。

### 绝活二：彻底拆解 `fork` 的写时复制（COW）

在[第 2 章讲 `fork`](../chapter_02_processes/02_scheduling_ipc.md) 时，我们预告过现代操作系统靠写时复制让 `fork` 几乎零拷贝。现在有了页表权限位，整个机关一目了然：
1. 父进程调用 `fork` 时，内核复制一份页表给子进程，让父子双方的虚拟页指向**同一批物理页框**，但偷偷把原本可写的页面在双方页表里**统统改标成只读**，并打上“写时复制（COW）”标记；
2. 如果双方只读不写（或子进程立刻 `exec` 换装新程序），一字节数据都不用拷贝；
3. 一旦父子任何一方试图往其中某一页写数据，硬件立刻因为“违反只读权限”触发写保护缺页异常；
4. 内核接手后一看 COW 标记便心领神会：悄悄分配一个新页框，把原页内容拷过去，把写入方的页表项改成指向新页框并恢复可写权限；
5. 返回用户态重新执行那条写指令，写入顺利完成，另一方看到的原页丝毫不受污染！

不过也别神话 `fork`：对于占用上百 GB 内存的超大型进程，光复制页表结构本身、把几千万条页表项改成只读并触发后续大量写时复制缺页，依然会带来不可忽视的延迟毛刺。

### 绝活三：`mmap`——把磁盘文件当成内存数组来读写

既然按需分页本来就能在缺页时“从磁盘文件读一页塞进页框”，操作系统设计师顺水推舟推出了**内存映射**（memory mapping，即 `mmap` 系统调用）：直接把磁盘上的一段文件映射到进程的虚拟地址空间里，从此应用程序连 `read`/`write` 都不用调，像操作普通字节数组指针一样直接读写文件！

```c
void *p = mmap(NULL, length, PROT_READ, MAP_PRIVATE, fd, 0);
```

首次摸到 `p[i]` 时触发缺页，内核自动把文件对应块读入内存页框并挂上映射。`mmap` 区分两种常见口味：`MAP_PRIVATE` 走私有写时复制，你的修改只留在自己进程副本里，绝不回写污染原文件；`MAP_SHARED` 则直接与内核里的文件页缓存联动，写进去的改动其他共享映射者立刻可见，并按系统策略刷回磁盘——但务必清醒：**写完内存指针返回成功，绝不等于数据已经安全落盘**，真要抗断电还得老老实实调用同步刷盘（如 `msync` / `fsync`）。

## 放大尺码：大页（Huge Page）的得与失

前面提到常规页是 4 KiB。可如今一台服务器动辄插着几百 GB 内存，一个数据库进程随随便便占用上百 GB——全用 4 KiB 切，光页数就高达几千万页，CPU 芯片里那点寸土寸金的[地址翻译缓存（TLB）](02_page_tables_tlb_faults.md)根本兜不住！

于是现代架构允许混用更大的页尺寸（如 x86-64 上的 2 MiB 甚至 1 GiB **大页**）。如果 TLB 里有 $N_{entries}$ 条槽位，每页大小为 $P$，那么整个 TLB 一瞬间能兜住的总内存范围——即 **TLB 覆盖率**——就是：

$$
TLB\ coverage=N_{entries}\times P.
$$

把 $P$ 从 4 KiB 换成 2 MiB，同样一条 TLB 记录能罩住的面积瞬间暴涨 **512 倍**，页表体积和查表次数双双骤降！代价也如影随形：内部碎片可能变大、一次缺页或写时复制要搬整整 2 MiB、保护权限也只能按 2 MiB 粗粒度划定，内存紧张时还更难凑出连续的物理大块。因此大页最受大型数据库、科学计算这类拥有巨型连续热内存的应用偏爱，对大量零碎小对象却未必讨好。

## 给黑客蒙上眼睛：ASLR 地址空间布局随机化

如果每次启动程序，栈永远长在 `0x7fff0000`，标准库永远躺在 `0x7f001000`，攻击者一旦找到一个缓冲区溢出漏洞，就能照着背下来的固定地址精准跳转到恶意代码或库函数里接管进程。

为了打乱攻击者的坐标图，现代系统普遍开启了**地址空间布局随机化**（address space layout randomization，ASLR）：每次进程启动时，内核故意给栈、堆、共享库甚至主程序代码加上不同的随机偏移量。这样攻击者连目标函数住在哪儿都猜不准，盲跳大概率直接撞上未映射空洞把进程撞崩。但请记住：**ASLR 只是增加利用难度的纵深防线，绝不等于治好了内存安全漏洞**——只要程序还有信息泄漏漏洞把某个指针值吐了出去，随机化布局就会被顺藤摸瓜算个底朝天。

## 厘清最后一层迷雾：`malloc` 和操作系统的页分配是一回事吗？

写 C 语言时，我们天天调 `malloc(32)` 申请 32 字节。既然操作系统最小只按 4096 字节分整页，难道每次 `malloc(32)` 都要进内核敲一次门、拿走一整页 4096 字节吗？

当然不是！`malloc` 根本不是系统调用，而是**跑在用户态的内存批发商（分配器）**：
1. 它先通过 `brk` 或 `mmap` 向内核一次性“批发”一大块虚拟地址区域（称为 arena，比如几百 KB 或几 MB）；
2. 当你的代码频繁申请 32 字节、64 字节的小对象时，`malloc` 直接在用户态自己的仓库里切零头递给你，连内核的门都不用敲；
3. 只有手头存货不够、或者你一口气申请了一个超大块时，它才再向内核进货。

同理，内核自己内部也分层：底层物理页框分配器按整页批发，上层 slab 分配器再把整页切成几十字节的小对象供内核数据结构复用。名字都叫“内存分配”，但所处层次、面对的碎片问题和加锁开销截然不同。

到这里，我们已经亲手算通了一页的翻译，也见识了页表撑起的共享、COW 与 `mmap`。可把视线抬高到真实的 64 位计算机，两个庞然大物立刻挡住了去路：第一，48 位虚拟地址全按 4 KiB 切，一张扁平大页表算下来竟要吃掉整整 **512 GiB** 内存——比整台电脑的内存条还大！第二，如果每次执行一条访存指令都要先去内存里查几遍页表，程序岂不是要慢上好几倍？操作系统和 CPU 究竟如何靠**多级页表**压缩空间、靠 **TLB** 挽救速度？让我们接着走进[下一篇：页表、TLB 与缺页](02_page_tables_tlb_faults.md)。

## 自测

如果现在你已经能闭着眼讲清虚拟地址 `26` 在进程 A 和 B 里各自是怎么算出 `90` 和 `42` 的，强烈建议顺手延伸阅读 [OSTEP 的分页章节](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-paging.pdf) 和 [MIT xv6 教材的页表章](https://pdos.csail.mit.edu/6.1810/2025/xv6/book-riscv-rev5.pdf#page=31)——前者深入剖析分页开销，后者则带你直接看真实教学内核里的页表 C 代码。

1. 为什么两个毫无关系的进程可以同时使用完全相同的虚拟地址（例如 `0x401000`），却各自保存互不干扰的数据？
2. 与早期的“基址—界限”和“分段”相比，分页彻底消除了哪类碎片，又不可避免地引入了哪类碎片？
3. 在 `fork` 的写时复制（COW）机制里，内核为什么要先把父子共享的可写页在页表里故意标成“只读”？
4. 使用 2 MiB 大页怎样大幅改善 TLB 覆盖率？它又带来了哪些新的工程代价？
5. 当程序通过 `MAP_SHARED` 的 `mmap` 把数据写入映射内存区并顺利返回后，是不是就意味着数据已经安全保存到硬盘上了？

??? note "参考思路"

    1. 每个进程拥有各自独立的页表，CPU 切换进程时会换用对应的页表根指针，因此相同的虚拟页号在两张页表里会被翻译成两个不同的物理页框。
    2. 分页以固定页框为单位分配，消除了可变大小连续分配导致的**外部碎片**；但对象大小不是页大小的整数倍时，最后一页里用不满的余量无法再分给他人，引入了**内部碎片**。
    3. 标成只读是为了借硬件之力“设伏”——只要父子双方都不写就相安无事；一旦任一方尝试写入，CPU 硬件会立刻捕获权限冲突并触发缺页异常，内核由此精准介入，只复制被写入的那一页。
    4. TLB 覆盖率等于槽位数乘以单页大小，把页从 4 KiB 放大到 2 MiB 让单条缓存覆盖面积扩大 512 倍，显著降低 TLB 未命中率；代价是内部碎片变大、缺页与 COW 搬运粒度变粗、内存保护粒度变粗且更难凑出连续物理大块。
    5. 不是。写入 `mmap` 区域只是修改了内存中的页缓存，何时真正刷写到非易失磁盘取决于操作系统的回写策略或显式同步调用（如 `msync` / `fsync`），突然断电前未落盘的改动仍可能丢失。
