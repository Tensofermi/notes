# 页表、TLB 与缺页

## 一张大表，为什么要拆成好几张小表套着查？

上一篇我们用 16 字节迷你页把分页算通了，可真要把这套办法搬进真实电脑，立刻就会撞上两堵吓人的墙：**空间墙**和**时间墙**。

先拿一个稍微放大一点的玩具感受一下空间墙：假设系统一共有 16 个虚拟页，而当前这个小进程只用到了第 0 页和第 1 页。如果你老老实实建一张 16 行的平面数组页表，哪怕后面 14 页全空着，照样得占满 16 个槽位。换个思路呢？把每 4 页打成一个包——顶层只留一张 **4 行的目录表**，每行指向一组 4 页的下级小表。既然进程只用了第 0 组里的页 0 和页 1，那就**只给第 0 组分配一张 4 行的小表**，另外三组在顶层目录里直接打个“无效”叉号，连下级小表的影子都不用建！

原本 16 行，如今只需顶层 4 行 + 第 0 组 4 行 = 8 行。放到 64 位真实计算机里，这个省空间的比例甚至高达百万倍！可天下没有白赚的便宜：拆成多级目录后，每次翻译地址不能只查一次内存，而要顺着目录一级一级往下翻——程序跑起来岂不是要慢成蜗牛？为了堵上这道时间墙，CPU 在芯片核心旁边修了一块极快的小型速查缓存，专门记着最近刚查过的几十到几千条“虚拟页 -> 物理页框”翻译，这就是大名鼎鼎的**地址翻译后备缓冲器**（translation lookaside buffer，**TLB**）。

??? question "如果某个进程真的把所有分组里的虚拟页全都映射满了，多级页表还能省内存吗？"

    省不了，甚至反而会比平面页表**多占一点内存**——因为每一张下级表全都得老老实实分配出来，顶层和中层的目录表就成了额外开销。多级页表赌的是现实世界里绝大多数进程的地址空间都极其**稀疏**（中间躺着大片用不到的空洞），它用一点点多级目录的查表代价，换来了稀疏布局下惊人的内存节省。

整篇笔记，就围绕**多级页表（治空间）**、**TLB（治时间）**和**缺页处理（治未就绪与保护）**这三根支柱逐一拆解。

## 算一笔惊人的账：平面页表为什么大到塞不进内存？

不亲手算一遍，你很难体会 64 位地址空间有多辽阔。设虚拟地址有效宽度为 $V$ 位，页内偏移占 $p$ 位（即每页 $2^p$ 字节），那么一个进程理论上的虚拟页总数就是：

$$
N_{pages}=2^{V-p}.
$$

如果每条页表项占 $E$ 字节，一张覆盖所有虚拟页的平面数组页表总大小是：

$$
S=2^{V-p}E.
$$

把现代常见的 64 位服务器参数代进去——有效虚拟地址通常用 $V = 48$ 位，标准页大小 4 KiB（$p = 12$ 位），每条页表项占 $E = 8$ 字节：

$$
S=2^{48-12}\times8=2^{36}\times 8\ \text{字节}=512\ \text{GiB}!
$$

看清那个数字了吗？**仅仅是一个进程**的一张平面页表，就要吃掉整整 **512 GiB** 连续物理内存！哪怕你的电脑上只跑着一个打印 `hello world` 的小程序，整台机器的内存条都装不下它自己的一张页表——平面页表在 64 位时代彻底宣告出局。

## 多级页表：像图书馆分册目录一样按需分配

怎么把 512 GiB 压回几十 KiB？奥秘在于观察一个事实：一个普通进程虽然名义上坐拥 256 TiB（$2^{48}$ 字节）的虚拟地址空间，但实际用到的无非是低地址的代码和堆、高地址的栈，以及中间零星几块共享库，其余 99.9999% 全是空洞。

**多级页表**（multi-level page table）把虚拟页号切成好几段索引，织成一棵树（例如主流 x86-64 常用的四级页表）：

```text
虚拟地址（48 位有效位）
  ├─ level-1 索引（9 位，查顶层目录）
  ├─ level-2 索引（9 位，查二级目录）
  ├─ level-3 索引（9 位，查三级目录）
  ├─ level-4 索引（9 位，查最底层的页表项，拿到物理页框号）
  └─ page offset （12 位，页内偏移原样拼接）
```

硬件手里握着当前进程的“顶层页表物理根地址”（存放在 CPU 的专用控制寄存器里，如 x86 的 `CR3`）。翻译地址时，硬件从根出发一级一级往下查——这个逐层顺藤摸瓜的过程叫作**页表遍历**（page walk）。

只要某大片虚拟区域压根没映射过，顶层或中层对应的目录项直接标为“无效”，底下整棵子树里的成千上万张下级小表连分配都不用分配！结果，那个只用几兆内存的小程序，整套四级页表加起来往往只要几张 4 KiB 小页（总共十几 KiB）就搞定了。

### 拿 32 位两级页表做一次精准位拆分

为了把“索引位刚好凑成一页”的美感看得更透，看看经典的 32 位系统（4 KiB 页，每条页表项 4 字节，两级页表）：

```text
31          22 21          12 11           0
+--------------+--------------+--------------+
| directory 10 | page table 10| offset 12    |
+--------------+--------------+--------------+
```

算一笔恰到好处的巧合：下级索引占 10 位，意味着一张下级页表恰好有 $2^{10} = 1024$ 项；每项 4 字节，整张下级表正好 $1024 \times 4 = 4096$ 字节——**不多不少正好塞满一个 4 KiB 物理页框！**（上面 64 位四级页表每级切 9 位也是同样的巧算：$2^9 \times 8\text{ 字节} = 4096\text{ 字节}$。）一张 4 KiB 下级表覆盖 $1024 \times 4\text{ KiB} = 4\text{ MiB}$ 的虚拟地址范围，没用到的 4 MiB 区域一丁点下级表都不占。

不过，空间墙翻过去了，时间墙立刻砸在眼前：四级页表意味着每次查表要跑 **4 趟慢吞吞的主存**，再加上最后取数据那 1 趟，**程序每读一个字节竟然要访问 5 次内存！** 速度直接跌成原来的五分之一——这绝对不可接受。救世主登场了。

## TLB：把翻译速度救回来的片上快查表 { #tlb }

程序运行时有着极强的时间和空间局部性：一个循环在同一个 4 KiB 页面里来回读写几千次数组元素，难道每次都要傻傻地把同一条四级页表走上几千遍吗？

当然不！处理器在核心内部集成了一块由高速相联电路打造的极小缓存——**TLB**（translation lookaside buffer），专门记住最近刚翻译过的“虚拟页号 -> 物理页框号 + 读写权限”。每当 CPU 发出一个虚拟地址，硬件第一时间并行查 TLB：

- **TLB 命中（Hit）**：几乎在 1 个时钟周期内直接拿到物理页框号并核对权限，拼接偏移直奔数据，四级页表一步都不用走！
- **TLB 未命中（Miss）**：速查表里没记录，只好由硬件页表遍历器（或某些架构上的内核软件）去内存里跑一趟页表遍历。只要查到有效映射且权限合法，硬件就顺手把这条新翻译塞进 TLB（若 TLB 满了就按替换策略踢掉一条旧记录），再继续取数据。
- **映射无效或越权**：无论 TLB 里还是页表里都找不到合法权限映射，立刻触发缺页或保护异常交给内核。

请务必分清一件事：**TLB 缓存的是“地址翻译关系”，不是用户数据本身**（缓存用户数据本身的是 L1/L2/L3 Data Cache）。

### 用公式感受 TLB 命中率有多值钱

借一个最简化的单级页表模型来算算账：设查一次 TLB 只需 $t_T$，读一次主存要花 $t_M$，TLB 命中率为 $h$。那么一次访存的**有效访问时间（EAT）**大约是：

$$
EAT=h(t_T+t_M)+(1-h)(t_T+2t_M).
$$

命中时只需 1 次主存访问（取数据）；未命中就多出 1 次主存访问（查页表；在真实四级页表上未命中最多可能多出 4 次查表访存！）。虽然现代 CPU 还会把页表项顺手缓存进 L1/L2 Cache、并用并行预测掩盖部分延迟，但核心结论稳如磐石：**只要 TLB 命中率从 99% 掉到 90%（比如在几十 GB 内存上做完全随机的指针跳跃），程序性能立刻会出现肉眼可见的滑坡。**

### 上下文切换与多核下的 TLB 麻烦：ASID 与 TLB Shootdown

TLB 是片上公共快查表，可上一篇我们刚说过——进程 A 和进程 B 都可以把虚拟页 1 映射到完全不同的物理页框！如果刚刚切走进程 A、换上进程 B，TLB 里还留着 A 的旧条目“页 1 -> 页框 5”，B 一查命中了，岂不是直接读走了 A 的机密内存？

硬件和操作系统联手用三招堵死了这个漏洞：
1. **暴力清空（早年做法）**：每次切换进程页表时，把整张 TLB 统统刷空。绝对安全，代价是新进程刚一上台前几百次访存全都会遭遇惨烈的 TLB 未命中；
2. **给每条记录贴进程标签——ASID**：现代处理器给每条 TLB 项贴上一枚**地址空间标识**（address space ID，RISC-V/ARM 叫 ASID，x86 叫 PCID）。切换进程时不用冲刷 TLB，硬件自动只匹配“虚拟页号和当前进程 ASID 同时吻合”的条目，多个进程的翻译从此在 TLB 里和平共处；
3. **内核全局项（Global Bit）**：内核空间在所有进程里往往映射到同一份物理地址，打上全局标记后，切换用户进程时根本不用动它。

而在**多核 CPU** 上，还有一笔隐蔽却极其昂贵的开销：**TLB Shootdown（跨核 TLB 击落）**。设想进程有 16 条线程正同时跑在 16 颗核心上，此时 0 号核心调用 `munmap` 撤掉了一页映射，或者把一页写权限收回。0 号核心改完内存里的页表、刷掉自己本地的 TLB 远远不够——另外 15 颗核心各自的私有 TLB 里依然留着那条允许读写的旧翻译！为了堵住安全漏洞，0 号核心必须向那 15 颗核心发送**处理器间中断（IPI）**，强行打断它们正在跑的活儿、命令它们各自刷掉那条旧 TLB 记录，并且 0 号核心还得原地干等到所有核心全部回复“已刷完”才敢把那页物理内存释放给别人。在高并发频繁 `mmap`/`munmap` 或回收内存的服务器上，TLB Shootdown 常常是吞掉大量 CPU 的隐形杀手。

## 终结最常见混淆：TLB Miss $\neq$ 缺页 $\neq$ 读磁盘

初学虚拟内存，最容易把这三个概念搅成一锅粥。现在把它们彻底劈开摆在桌面上：

```text
TLB miss（翻译缓存未命中）
  -> 只是片上快查表里暂时没这条记录；硬件默默查一遍内存页表，有效就直接过关，
     压根不用进内核，更不会碰磁盘！

次要缺页（Minor Page Fault）
  -> 页表里确实没有直接可用的映射，触发异常进了内核；
     但内核在纯内存里就能搞定（比如分一页清零内存、处理写时复制、或直接挂上已在页缓存里的文件页），
     全程依然零磁盘 I/O！

主要缺页（Major Page Fault）
  -> 触发异常进了内核，而且目标数据压根不在内存里，
     内核必须向硬盘发起真实的存储读取（从文件或交换区搬回来），线程被迫阻塞睡眠等磁盘中断！
```

三者的耗时跨度惊人：一次 TLB 未命中大概花几十纳秒，一次次要缺页大约几微秒，而一次需要等机械硬盘或繁忙 SSD 的主要缺页可能高达几百微秒到几毫秒——彼此之间差着上千倍到上十万倍！

## 四种缺页异常，内核怎样见招拆招？

“缺页（Page Fault）”这个中文译名容易让人误以为系统出了故障，其实绝大多数缺页都是操作系统刻意设计的正常配合机制。进到内核缺页处理入口后，内核通常面对四类情形：

1. **按需分配缺页（Demand Zero）**：程序刚用 `malloc` 拿到一片新堆空间，第一次往里写时触发缺页。内核确认地址合法，从空闲页框里拿一页填满 0（防止看到上一个进程残留的隐私字节！），填好页表放行。
2. **文件页或交换页未驻留（主要缺页）**：目标页躺在磁盘的文件或交换区里。内核向块设备下发读请求，让当前线程暂时睡去，等磁盘搬完发中断唤醒后再填好页表。
3. **写时复制缺页（COW Fault）**：父子进程正共享着标成只读的页面，其中一方尝试写入触发写保护异常。内核在内存里快速拷贝出独立新页、改为可写，原指令重试即成功（细节已在[上一篇](01_address_space_paging.md)走通）。
4. **真正的非法访问（Protection / Segmentation Fault）**：访问了压根没映射的野指针、越过栈边界，或者试图往只读代码段里写数据。内核没法也没理由替它兜底，直接送上一枚 `SIGSEGV` 信号终止程序或交由用户信号处理器处理。

把一次正常缺页的完整内核路径串起来，每一步都严丝合缝：

1. CPU 硬件停下出错指令，把引发缺页的**故障虚拟地址**、读/写/执行操作类型和错误码记在专用寄存器里，切入内核缺页入口；
2. 内核用故障地址查当前进程的虚拟内存区域账本（如 VMA 红黑树），确认它是否落在某段合法区间；
3. 核对操作类型（读/写/执行）是否被这段区域允许——不合法直接报错发信号；
4. 判定属于哪类合法缺页（按需清零、COW、文件读入还是交换区换入）；
5. 分配空闲页框；若需要从磁盘读数据，发起 I/O 并让线程阻塞等待；
6. 填好页表项，同步更新物理页的反向映射和统计计数；
7. 必要时使旧的失效 TLB 项作废；
8. 退出内核返回用户态，**重新执行刚才引发缺页的那一条指令**——这一次翻译顺畅命中，程序毫无察觉地继续向前。

这里藏着内核编程里一个极易踩死锁的细节：处理缺页的内核代码自己访问的核心元数据（比如页表本身、进程控制块、虚拟区域描述结构）必须常驻物理内存、绝不允许再触发可睡眠的缺页，否则就会掉进“缺页处理器自己又缺页”的无限递归深渊。

## 从物理页倒查虚拟页：为什么还需要“反向映射”？

正向看，页表让我们能飞快回答：“进程 A 的虚拟页 3 住在哪个物理页框？”

可很快到了下一篇，当物理内存爆满、内核决定把**物理页框 20** 回收腾出来给别人用时，一个让人挠头的问题出现了：**怎么知道全机器几百个进程里，到底有哪几张页表正指着物理页框 20？** 总不能把几百个进程动辄几百万行的页表全遍历一遍吧！

为了能瞬间撤销指向某物理页框的所有映射（或者安全地把这页搬家到另一个 NUMA 节点），内核专门维护了一套**反向映射**（reverse mapping）元数据，记录每个物理页框正被哪些进程的哪几条页表项引用。这也道出了一个深刻事实：一旦某个共享页被几百个进程同时映射，将来想改权限或回收它，内核就得同步更新几百张页表并向多颗核心发送 TLB Shootdown——虚拟内存的复杂性与性能开销，往往就藏在这些跨进程、跨核的隐秘联结里。

## 大页的进阶实践：透明大页（THP）的双刃剑

在多级页表里实现大页其实格外自然：只要在四级页表的第 3 级目录项里打上一个“到此为止，直接指向 2 MiB 连续物理大块”的标记，硬件查到第 3 级就提前收工，既少查一层内存，又让 1 条 TLB 顶过去 512 条！

为了让应用程序一行代码不改就能蹭上大页的红利，Linux 引入了**透明大页**（transparent huge page，THP），由内核在后台默默把相邻的 512 个 4 KiB 小页凑齐拼成 2 MiB 大页，需要局部修改或写时复制时再拆分回来。听起来像免费的自动加速，可在延迟敏感的数据库（如 Redis、PostgreSQL）上却常常踩雷：当内存碎片较多时，一次普通缺页可能突然触发内核同步整理拼凑 2 MiB 连续大块，或者一次小小的写时复制被迫拷贝整整 2 MiB，导致 P99 尾延迟瞬间飙出一个尖峰！因此，大页和 THP 永远要结合业务访问特征实测开关，切忌盲目迷信“自动优化”。

## 页表守卫着整台机器的安全底线

因为硬件每次访存只认页表，页表一旦出一点差错，整台机器的隔离大厦就会瞬间坍塌。内核工程师必须在页表代码上死守五道红线：
- 绝不能让普通用户态页表项映射到受保护的内核物理页；
- 绝不能让可写数据页意外同时拥有特权可执行权限；
- 物理页释放还给空闲池之前，必须确保指向它的所有旧页表项已经彻底撤销；
- 收紧某页权限或解除映射后，必须确保所有核心上的旧 TLB 条目已经失效（防止残留缓存绕过新权限）；
- 针对现代 CPU 推测执行带来的硬件侧信道漏洞（如熔断 Meltdown 攻击），内核甚至不得不采取**内核页表隔离（KPTI）**等重手段，在用户态运行时干脆把绝大部分内核映射从页表里撤掉，宁可牺牲一点系统调用性能也要守住机密。

## 线上观测：看到“缺页率很高”该怎么往下查？

用 `vmstat`、`pidstat` 或 `perf` 看到进程的缺页计数飙升时，先别急着喊“内存不够了，快加内存条！”按下面五个问题逐一剥皮：

1. **是一次性脉冲，还是持续居高不下？** 进程刚启动时把代码和共享库按需拉进来，飙一波缺页完全正常；
2. **是次要缺页还是主要缺页？** 如果 `minflt/s` 很高但 `majflt/s` 接近 0，说明压根没碰磁盘，可能是频繁创建销毁映射、写时复制或大块内存反复初始化；只有 `majflt/s` 持续偏高，才指向真正的磁盘换入或工作集溢出；
3. **程序的工作集是不是已经撑爆了物理内存或容器内存上限？**
4. **如果 CPU 周期白白耗在访存等待上、但缺页并不高**，用 `perf stat` 看一眼 `dTLB-load-misses`，说不定瓶颈出在随机访问超大哈希表导致 TLB 疯狂未命中；
5. **数据布局、预取或大页设置**是不是和当前访问模式唱了反调？

到这里，我们把地址翻译的“空间账”（多级页表）、“时间账”（TLB）和“异常处理账”（缺页）全都算清了。可悬在头顶的最后一朵乌云始终没散开：**物理内存条的页框总数终究是有限的！** 当机器里跑着几十个进程，所有物理页框全都住满了住户，此时又一声缺页警报响起、急需腾出一个空页框——内核到底该狠心把哪一页请出门？腾出来的空白页框，又该怎么高效地切分给大小千差万别的内核对象和应用程序？带着这两个压轴问题，走进本章最后一篇：[页面置换与内存分配](03_replacement_allocation.md)。

## 自测

1. 面对 48 位或 64 位庞大的稀疏地址空间，多级页表具体是怎么把几百 GiB 的页表压回几十 KiB 的？
2. 比较一次 **TLB 未命中**、一次**次要缺页**和一次**主要缺页**，为什么它们的耗时能相差几个数量级？
3. 硬件引入 **ASID / PCID（地址空间标识）** 之后，是如何降低进程上下文切换带来的性能损耗的？
4. 在多核机器上，一个核心修改了某共享内存页的页表权限（比如把可写改成只读）之后，为什么必须大费周章地通知其他核心做 TLB 失效？
5. 合法缺页在内核补齐页表后，返回用户态时为什么要**重新执行刚才出错的那条指令**，而不是像系统调用那样执行下一条指令？

??? note "参考思路"

    1. 多级页表把虚拟页号分层索引，成片未映射的虚拟地址空洞只需在上层目录表记为“无效”，完全不必为其分配下级子表，只为真正使用的少数分支分配小页表即可。
    2. TLB 未命中通常由硬件走几趟内存页表即可完成（几十纳秒），不进内核；次要缺页虽然陷入内核，但在纯内存里分配零页、做 COW 或挂接已有页缓存即可解决（微秒级）；主要缺页必须发起真实的存储设备读取并阻塞等待磁盘 I/O（数百微秒至毫秒级）。
    3. 有了 ASID 标记每个进程的身份后，不同进程的 TLB 翻译可以安全共存于同一张 TLB 里互不串味，切换进程时不必把整张 TLB 暴力清空，切回老进程时还能直接命中先前留下的热翻译。
    4. 因为每颗核心都有自己私有的 TLB 缓存；不向其他核心发失效通知（TLB Shootdown），运行在其他核心上的同进程线程就会继续凭旧 TLB 里的“可写”缓存绕过新权限，酿成严重数据一致性或安全漏洞。
    5. 系统调用本身是一条已主动完成的请求指令，返回后自然接着跑下一条；而缺页意味着刚才那条访存指令因为缺映射根本**还没成功执行完**，内核把缺失的物理页和映射补齐后，必须回去重试那条指令才能真正拿到数据。
