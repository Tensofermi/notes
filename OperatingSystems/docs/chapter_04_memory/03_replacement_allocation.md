# 页面置换与内存分配

## 只有两个页框，新住户来了该把谁请出门？

设想一台小得可怜的机器，物理内存里总共只放得下 **2 个页框**，一开始空空如也。现在程序依次访问页面 `A -> B -> A -> C -> A`：

- 访问 `A`：缺页，住进第 1 个页框（内存：`[A]`）；
- 访问 `B`：缺页，住进第 2 个页框（内存：`[A, B]`）；
- 访问 `A`：命中！不用挪窝；
- 访问 `C`：缺页！可两个页框已经住满了，**到底该踢走 A 还是踢走 B？**

就在这一念之差，两条规则走出了截然不同的命运：
- 如果按**先进先出**（first in, first out，**FIFO**）——谁最早搬进来就请谁先走：A 是最早住进来的，于是踢走 A、换进 C（内存：`[C, B]`）；结果紧接着下一步又要访问 `A`，刚刚被赶出门的 A 只能狼狈地再触发一次缺页搬回来！
- 如果按**最近最少使用**（least recently used，**LRU**）——谁最久没露过面就请谁先走：刚才第 3 步还热乎地用过 A，B 已经冷落更久了，于是踢走 B、换进 C（内存：`[A, C]`）；紧接着末尾访问 `A`，稳稳命中！

??? question "既然 LRU 比 FIFO 聪明这么多，为什么真实操作系统内核几乎从不用“精确 LRU”，而偏爱各种近似算法？"

    因为维护“绝对精确的最近使用顺序”代价太吓人了！CPU 每执行一条访存指令（每秒几十亿次），你都得把对应的页号从双向链表中间摘出来挪到表头，还得在多核间抢锁同步——光记账就把整台机器拖垮了。真实系统于是退而求其次，借硬件页表项里自带的“访问位”配合周期性扫描和活跃/非活跃分组来**近似估计**冷热程度，用极低成本换回接近 LRU 的效果。

当物理内存被塞满、新的缺页又急着要页框时，决定把哪一页换出去的学问叫作**页面置换**（page replacement）。回头对照第 1 章的黄金原则：硬件提供的“访问位”“脏位”和缺页异常是**机制**，而决定踢谁留谁的置换算法正是操作系统大显身手的**策略**。

## 为什么绝不能等到最后一字节内存耗尽才动手回收？

你可能会想：“既然内存还没满，就一直敞开用，等到空闲页框刚好变成 `0` 的那一刻再开始腾地方不行吗？”

真这么干，系统随时会把自己憋死！因为**回收内存这件事本身就需要先申请一点内存**——想把一页脏数据写回磁盘，文件系统和块设备驱动得先分配一点 I/O 请求结构体和缓冲区；触发缺页路径的内核代码也可能需要零星临时页。如果真拖到空闲页彻底归零才动手，就会陷入“为了腾内存需要先分内存，但已经没内存可分”的死结。

因此，成熟内核普遍设了多条**内存水位线（Watermark）**：当空闲页跌破“低水位”时，后台回收线程（如 Linux 的 `kswapd`）就悄悄苏醒，趁着机器还不算太急，提前把冷页和干净文件页陆续腾出来补回“高水位”；只有当内存分配实在太猛、连后台都追不上跌破警戒线时，前台申请内存的线程才会被迫暂停业务，亲自下场做**直接同步回收**。

## 算法凭什么猜未来？局部性与工作集

页面置换本质上是在玩一场“预测未来”的游戏：谁在遥远的未来才会被再次用到（甚至再也不用），就最该被请出去。可操作系统没有水晶球，它凭什么敢猜？

它押注的是几乎所有真实程序共同遵守的两条统计规律，合称**局部性**（locality）：
- **时间局部性**（temporal locality）：刚刚摸过的一页数据，待会儿大概率还会再摸（比如循环计数器、高频热点函数）；
- **空间局部性**（spatial locality）：刚刚摸了地址 `x`，紧挨着它的 `x + 1`、`x + 2` 很快也会被摸到（比如顺序遍历数组、顺序执行指令）。

把程序在最近一段长度 $\Delta$ 的时间窗口里，实际访问过的全部虚拟页收集成一个集合，这就是它的**工作集**（working set）：

$$
W(t,\Delta)=\{p\mid p\text{ 在 }(t-\Delta,t]\text{ 内被访问}\}.
$$

工作集刻画了程序“当下为了顺畅干活，至少需要常驻在内存里的那批热页”。只要全机所有活跃进程的工作集加起来塞得进物理内存，大家就相安无事；一旦总工作集长期超出了物理内存容量，灾难就会接踵而至——系统陷入疯狂换入换出的**抖动**（thrashing）。

## 四大经典置换算法巡礼

围绕“如何逼近神谕、同时把记账开销压到最低”，置换策略演化出了四位著名选手：

### 1. OPT（最优置换）：理论天花板

**最优置换**（optimal replacement，OPT）拥有上帝视角：每次需要腾位子时，直接看穿未来，把**下一次再次被访问距离现在最远**（或者干脆永不再用）的那一页踢出去。真实在线系统当然不可能预知未来，但 OPT 依然极其宝贵——它为我们提供了一条绝对的理论下界，任何实用算法都能拿它当标尺，量一量自己离完美还差多少。

### 2. FIFO（先进先出）：最省事，却藏着反直觉的 Belady 异常

只记谁最早搬进内存，队头直接出队。实现只需要一条最朴素的队列，却完全无视这一页是不是天天被频繁访问的热门常客。更讽刺的是，FIFO 还会触发著名的 **Belady 异常**（Belady's anomaly）——对某些特定访问序列，给进程**加了更多物理页框，缺页次数反而莫名其妙变得更多了！**（比如把页框从 3 个加到 4 个，只因为旧页留得更久、恰好打乱了原有的替换节奏。）

### 3. LRU（最近最少使用）：以过去赌未来

利用时间局部性，把“最长时间没人碰过”的那一页踢出去。LRU 不会出现 Belady 异常，在大多数程序上效果逼近 OPT；唯一硬伤就是前面说过的——每次访存都精确维护全序链表，软硬件开销高到不可接受。

### 4. Clock / Second Chance（时钟算法）：工程界的性价比之王

既然精确排序太贵，何不借硬件页表项里顺手自动置 `1` 的**访问位（accessed bit）**打个折中？**时钟算法**（clock algorithm，又称第二次机会算法）把所有候选页排成一个圆环，配一根像表针一样转动的扫描指针：

```text
指针指向当前候选页：
  -> 如果 accessed == 0：说明转了一大圈都没人碰过它，果断选中淘汰！
  -> 如果 accessed == 1：说明近期有人用过，把 accessed 清零，放它一马（给“第二次机会”），指针前移一格继续找！
```

只需 1 个硬件比特位，不用在每次访存时动任何链表，就能以极低开销漂亮地近似 LRU。现代真实内核（如 Linux）在时钟和近似 LRU 之上进一步细分出“活跃链表（active）”与“非活跃链表（inactive）”，还把文件页和匿名页分开权衡，避免一次顺序扫描大文件把所有热页面全洗刷干净。

## 动手走查一遍：3 个页框下的 FIFO vs LRU

光说不练假把式，拿访问序列 `1, 2, 3, 1, 4, 1, 2, 5` 在 **3 个物理页框**下把 FIFO 和 LRU 逐拍推演一遍（标 `*` 表示发生缺页）：

| 步数 | 访问页 | FIFO 内存状态（最旧在左） | FIFO 决策 | LRU 内存状态（最久未用在左） | LRU 决策 |
| ---: | :---: | :--- | :--- | :--- | :--- |
| 1 | `1` | `[1]` | `*` 缺页装入 | `[1]` | `*` 缺页装入 |
| 2 | `2` | `[1, 2]` | `*` 缺页装入 | `[1, 2]` | `*` 缺页装入 |
| 3 | `3` | `[1, 2, 3]` | `*` 缺页装入 | `[1, 2, 3]` | `*` 缺页装入 |
| 4 | `1` | `[1, 2, 3]` | 命中（顺序不变） | `[2, 3, 1]` | 命中（`1` 移至最新） |
| 5 | `4` | `[2, 3, 4]` | `*` 踢掉最早的 `1` | `[3, 1, 4]` | `*` 踢掉最冷的 `2` |
| 6 | `1` | `[3, 4, 1]` | `*` 刚踢走又缺页！踢 `2` | `[3, 4, 1]` | **命中！**（`1` 移至最新） |
| 7 | `2` | `[4, 1, 2]` | `*` 刚踢走又缺页！踢 `3` | `[4, 1, 2]` | `*` 踢掉最冷的 `3` |
| 8 | `5` | `[1, 2, 5]` | `*` 踢掉 `4` | `[1, 2, 5]` | `*` 踢掉最冷的 `4` |

看第 5、6 步的分水岭多么传神：第 4 步明明刚用过热乎的页面 `1`，可 FIFO 死脑筋只认入住资历，第 5 步一刀把 `1` 赶出了门，第 6 步立刻吞下一次冤枉缺页；LRU 则记住了 `1` 刚刚活跃过，保住了 `1`、省下一次缺页（总缺页 6 次 vs FIFO 的 7 次）。

## 踢谁不光看冷热：干净页、脏页与匿名页的回收成本

现实里挑选牺牲页，绝不是只看“谁最冷”那么简单——**把不同种类的页请出门，付出的搬家费天差地别：**

- **干净文件页（Clean File Page）**：来自磁盘文件且进来后从未改过，硬盘上本来就躺着一模一样的原件！回收它几乎零成本——直接撤掉页表映射、瞬间收回页框，下次真要用再从文件读回来就行；
- **脏文件页（Dirty File Page）**：对应磁盘文件，但进来后被程序修改过（页表脏位为 1）。绝不能直接丢弃，必须先把它**写回磁盘**变成干净页才能释放；
- **匿名页（Anonymous Page）**：存放进程堆、栈等运行时临时数据的页面，硬盘上压根没有对应的原始文件。想腾出它的页框，系统必须把它写进专门划分的磁盘**交换空间**（swap space）；如果机器根本没开 swap，这些匿名页就彻底“请不出去”了！

这引出一个微妙的权衡：如果回收器为了偷懒永远只挑免费的“干净文件页”踢，结果就会把宝贵的内存全塞满没人用的冷脏页；反过来，如果前台急着要页框时同步等待把脏页刷盘，用户请求的延迟又会瞬间暴涨。因此真实内核会把**周期性后台异步刷脏页**和**回收算法**紧密配合，平时悄悄把冷脏页提前洗干净。

## 局部置换 vs 全局置换：隔离与效率的拉锯

当进程 A 缺页需要腾位子时，内核应该只在**进程 A 自己名下的页框**里挑牺牲品（**局部置换**），还是可以放眼**全系统所有进程**一起挑最冷的页（**全局置换**）？

- **局部置换**隔离感强，进程 A 自己内存用猛了只会折腾自己，不会把安分守己的进程 B 的热页挤出门；但缺点是不够灵活，万一 B 手里闲着一大堆冷页不用，也没法借给急需的 A；
- **全局置换**让内存像活水一样自动流向最活跃的进程，整体吞吐高；但隐患也大——只要一个低优先级的日志扫描程序突然顺序读一遍 50 GB 大文件，就可能把全机核心数据库的宝贵工作集全挤出内存！

现代操作系统（如 Linux 结合 `cgroup` 内存控制器）走的是折中路线：平时允许全局弹性流转，同时允许给关键服务或容器设定**内存保护下限**与**使用上限**，不让坏邻居掀翻整台宿主机。

## 抖动：当“越努力加任务，机器反而越慢”

假设一台 8 GB 内存的机器上，每个进程的工作集都是 3 GB。跑 2 个进程时，总工作集 6 GB 稳稳装在内存里，CPU 欢快地跑到 95%。管理员觉得“再多塞两个任务应该能多干点活吧”，于是又开了 2 个同类进程（总工作集暴涨到 12 GB > 8 GB）。

诡异的一幕发生了：CPU 利用率不仅没涨，反而一路雪崩跌到 **5%**，硬盘灯狂闪不停，连敲一个 `ls` 都要卡十几秒！这就是操作系统里最骇人的**抖动**（thrashing）恶性循环：

```text
所有进程的总工作集 > 可用物理内存
  -> 进程 A 缺页，从磁盘换入页面
  -> 为了腾空位，踢掉了进程 B 马上就要用的活跃热页
  -> 切到进程 B 刚跑两行立刻缺页，又去等磁盘
  -> 换入时又踢掉了进程 A 的热页……
  -> 全体进程轮流卡死在磁盘换入换出上，CPU 几乎无活可干！
```

遇到抖动，往机器里塞更多并发任务只会火上浇油。真正治本的招数只有几条：**果断削减并发度**（暂停或迁移一部分任务，让剩余活跃工作集重新塞回物理内存）、**加物理内存**、**优化代码访问局部性**、给核心服务加内存隔离保护，或者揪出正在悄悄吞噬内存的泄漏与无界缓存。

## 预取与按需的博弈

按需分页虽然不浪费一页无用内存，但每次用到新页才慢吞吞触发缺页读盘，延迟吃亏。于是操作系统常常配合**预取 / 预读（Prefetching / Read-Ahead）**：一看你顺序读了文件的第 1 页、第 2 页、第 3 页，内核顺手就把第 4 到第 16 页一并提前读进内存，等你真读到第 4 页时直接内存命中！

可预读是一把双刃剑：顺序看电影、扫大日志时预读大显神威；换成数据库里东一榔头西一棒子的随机索引查询，盲目预读只会白白浪费宝贵的磁盘带宽，还把真正有用的热页从缓存里挤出去。因此成熟的预读算法都是自适应的——猜中就放大窗口，猜错立刻收手。

## 物理内存大管家：伙伴系统与 slab 分配器

前面我们一直在操心“腾出页框”。现在换个视角：内核自己手里攥着几百万个空闲物理页框，一会儿驱动程序急着要 **16 个物理连续的页框**（64 KiB）来做硬件传输，一会儿进程创建急着要 **1 个只有 256 字节的小结构体**。内核该怎么高效打理这笔家当？

### 1. 整页与连续大块分配：伙伴系统（Buddy System）

为了既能飞快分出连续的 $2^k$ 个物理页框，又能在归还时迅速拼回大块减少外部碎片，Linux 等内核采用了经典的**伙伴系统**（buddy system）：

1. 按 $2^0, 2^1, 2^2, \dots$ 页（即 1 页、2 页、4 页、8 页……称为不同的“阶”）分别维护空闲块链表；
2. 来了一个需要 3 页的请求，向上取整到最近的 2 的幂——4 页（2 阶）。若 2 阶链表空着，就去 3 阶摘下一块 8 页大块，从正中间一劈为二变成一对地址相邻的 4 页“伙伴”，一块交出去，另一块挂进 2 阶链表；
3. 将来这块 4 页释放时，内核只需用简单的位运算瞬间算出它“伙伴”的地址——如果伙伴此刻恰好也空闲，立刻合并回一块完整的 8 页放回 3 阶，甚至一路连锁合并上去！

伙伴系统拆分合并飞快、天然地址对齐；代价则是“向上取整到 2 的幂”会造成内部碎片（要 5 页得给 8 页），且机器跑久了内存被零星钉子户占住后，依然可能很难凑出高阶连续大块。

### 2. 零碎小对象分配：slab 分配器

伙伴系统最小也只能给 1 整页（4 KiB）。可内核每秒要创建销毁成千上万个只有几十到几百字节的小对象（进程控制块、打开文件描述、目录项缓存、网络包头），要是每个 128 字节的小对象都独占一整页，97% 的内存全浪费了！

**slab 分配器**（以及 Linux 后续演进的 SLUB 等变体）站在伙伴系统肩膀上当起了“精细零售商”：
- 向伙伴系统批发整页，把每一页严丝合缝地切成几十个等大小的对象槽位，专门只存同一类内核结构体；
- 释放对象时不必彻底拆毁重来，可以把已初始化好的对象骨架留在缓存里，下次申请直接拎起来就用；
- 为每颗 CPU 核心配备本地小缓存，绝大部分小对象分配连全局大锁都不用抢！

付出的代价则是每类专属对象缓存都会占着一些半满的页，在对象类型繁多而利用率偏低时，会留下一定内部碎片。

### 3. 用户态分配器：为什么 `free()` 之后，监控里的内存占用却纹丝不动？

排查线上内存问题时，新手最常发懵的一幕是：“我明明在代码里把几十万个对象全 `free()` 掉了，为什么 `top` 里看到的进程物理内存占用（**RSS**，Resident Set Size，常驻内存集）一动不动，是不是内存泄漏了？”

未必！回头看看用户态 `malloc`（如 glibc `ptmalloc`、jemalloc、tcmalloc）的运作方式就明白了：
- 为了避免每次 `malloc`/`free` 都陷入内核，用户态分配器按大小类和线程本地缓存（Thread Cache）把从内核批发来的内存切分管理；
- 当你 `free()` 掉一个小对象时，分配器只是把它挂回自己的空闲链表或线程缓存里留着下次快速复用——**“还给了 `malloc`”绝不等于“还给了操作系统内核”！**
- 哪怕你想把整块堆尾归还内核，只要堆顶附近还零星钉着一个没释放的存活小对象，整段地址空间就被死死卡住没法缩回去（用户态外部碎片）。只有大块独立 `mmap` 映射，或者分配器主动通过 `madvise(MADV_DONTNEED)` 告知内核可以收回物理页，RSS 才会真正掉下来。

## 内存超量承诺与 OOM 杀手

现实里还有一件颠覆直觉的事：在一台只有 8 GB 物理内存且没开交换区的 Linux 机器上，一个程序调用 `malloc(12 GB)` 竟然可能**返回成功**！

为什么操作系统敢开这种“空头支票”？因为受按需分页启发，许多进程（比如 `fork` 之后的大进程或大号稀疏数组）虽然名义上申请了海量虚拟地址，实际一辈子都不会把每一页都写满。默认开启的**内存超量承诺（Memory Overcommit）**机制选择先痛快答应申请，等程序真摸到某一页时再去兑现物理页框，大幅提升了整机内存利用率。

可万一所有进程真的同时把开出去的支票全拿来兑现，物理内存和交换空间瞬间见底，回收和刷脏页全救不了场，系统就会坠入**内存用尽**（out of memory，**OOM**）绝境。此时，内核里的 **OOM 杀手（OOM Killer）** 被迫出动——它给所有进程挨个打分（综合考量谁吃的内存最多、谁优先级最低、谁受了保护），然后手起刀落直接发 `SIGKILL` 强行杀掉得分最高的倒霉进程，瞬间释放大片页框以保住整台宿主机不至于彻底冻死。

这条教训在生产架构里极其值钱：**`malloc` 返回非空指针，绝不保证将来写入每一页时都不会被 OOM 杀手一刀带走。** 关键数据库与核心服务必须配合合理的内存限额、预留或显式锁页来兜底。

## 别忘了物理地形：NUMA 上的内存放置

第 2 章我们认识了多路服务器上的 **NUMA**（非一致内存访问）架构——每颗处理器插槽访问自己脚边的本地内存飞快，跨越插槽访问远端内存则变慢。Linux 在物理页分配上默认遵循一条非常聪明的**首次触碰（First-Touch）策略**：虚拟地址 `malloc` 出来时还不绑定任何 NUMA 节点，而是**谁第一个写入这一页触发按需缺页，内核就把物理页框分配在那个写入线程所在的本地 NUMA 节点上！**

这藏着一个经典的并行性能陷阱：如果你在程序启动时，偷懒只用**主线程单线程**把一个 64 GB 的大数组全初始化清零，结果 64 GB 物理内存全堆在了 0 号插槽的脚边；随后你兴冲冲地拉起 64 条工作线程分布到所有插槽去并行计算，其他插槽上的线程全得千里迢迢跨节点抢 0 号节点的内存带宽，性能直接腰斩！正确做法是让**将来负责算哪一块的工作线程，自己去初始化那一块内存**。当然，内核也提供跨节点页面迁移机制，但迁移意味着拷贝整页数据、改页表并做跨核 TLB 失效，如果线程本身频繁在节点间跳来跳去，盲目追着迁页反而会越迁越慢。

## 线上内存压力快速诊断对照表

| 你在监控里看到的现象 | 优先排查的候选真相 |
| --- | --- |
| 主要缺页（`majflt`）持续飙高 | 工作集撑爆物理内存、疯狂随机读文件、或陷入交换区抖动 |
| RSS 很高，但缺页极低、延迟稳健 | 热工作集安稳常驻在内存里，属于健康吃内存，未必有压力 |
| 代码释放了大把对象，RSS 却死活不降 | 用户态分配器留着复用、堆碎片卡住堆顶，或共享映射仍被他处引用 |
| 空闲总内存还剩不少，却报高阶连续页分配失败 | 物理内存长期碎片化，凑不出连续的 $2^k$ 大块 |
| CPU 利用率极低，但机器卡顿、磁盘 I/O 拉满 | 严重抖动（频繁换入换出）或阻塞在同步文件/脏页回写 |

看内存指标永远要把数字放回时间线上看：刚启动那三秒飙出的缺页波峰，和深夜持续半小时拉不下来的缺页高原，背后的故事完全不同。

到这里，第 5 章关于虚拟内存与内存压力的旅程圆满落幕：我们亲手算通了分页翻译，见识了多级页表和 TLB 如何撑起 64 位地址空间，也摸清了内存爆满时的置换、抖动、伙伴/slab 分配与 OOM。

然而，内存条里的一切风光都有一块致命软肋——**只要断电，里面的电信号瞬间烟消云散。** 你的文档、照片、代码仓库、数据库账本，全都要比进程活得长久，必须稳稳落到硬盘、固态硬盘等持久化存储设备上，还要经得起千奇百怪的外设速度鸿沟。操作系统究竟怎样把冰冷的磁盘扇区塑造成井井有条的文件与目录，又怎样靠设备驱动、中断与 DMA 让飞快的 CPU 不被慢吞吞的外设拖垮？让我们推开[第 6 章 文件、文件系统与设备 I/O](../chapter_05_storage_io/index.md)的大门！

## 自测

1. 最优置换算法（OPT）在真实操作系统里根本无法实现，为什么教材和研究者依然离不开它？
2. 时钟算法（Clock / Second Chance）如何只凭硬件页表项里的 1 个访问位，就漂亮地近似了 LRU？
3. 物理内存吃紧需要腾位子时，为什么回收一页“干净文件页”比回收一页“匿名页”便宜得多？
4. 内核的伙伴系统（Buddy System）解决了什么分配痛点？它又会留下哪种类型的碎片？
5. C/C++ 程序调用 `free()` 释放了大块堆内存，为什么在 `top` 里看到的进程 RSS 往往不会立刻掉下来？

??? note "参考思路"

    1. OPT 需要预知未来访问序列，无法在线实现；但它给出了任意给定访问序列的理论最少缺页次数下界，可以用来客观评估 FIFO、LRU、Clock 等实用算法离理论极限有多近。
    2. 时钟算法把候选页连成环、指针顺次扫描：遇到访问位为 `1`（近期用过）就把它清零放过一次机会，继续往后转；等转一圈回来如果某页访问位仍是 `0`（整圈没人碰过），就淘汰它。这避免了维护精确全局访问顺序的高昂代价。
    3. 干净文件页的内容与磁盘原文件完全一致，回收时只需撤销映射直接丢弃，零磁盘写入；匿名页没有对应原始文件，要腾出它的物理页框必须先把它写进磁盘交换空间（无交换区时甚至根本无法换出）。
    4. 伙伴系统能以极快速度分配与合并地址对齐的 $2^k$ 连续物理页框，大幅缓解页框级外部碎片；但它把请求大小向上取整到 2 的幂（如申请 5 页分给 8 页），会造成明显的内部碎片。
    5. `free()` 只是把内存块归还给了用户态内存分配器的空闲链表或线程本地缓存，方便后续快速复用；除非分配器主动缩减堆顶、解除大块 `mmap` 映射或显式告知内核回收物理页，否则这些物理页仍算在进程的 RSS 里。
