# 文件、目录与 inode

## 文件都改名甚至删掉了，打开它的程序为什么还能接着读？

不妨想象一个初看很违背直觉的场景：程序 A 打开了 `report.txt`，刚读完第一行；这时你在另一个终端里把 `report.txt` 改名成了 `old.txt`——甚至更狠一点，直接执行了 `rm report.txt` 把它删掉了！可切回程序 A 一看，它居然面不改色地把剩下的几千行内容完完整整读了出来！

这并不是文件系统出了 bug，而是 Unix 风格文件系统最精妙的一刀设计——**把“文件的名字”和“文件的本体”彻底拆开了**。

程序 A 打开文件时，内核发给它一个小整数句柄，叫作**文件描述符**（file descriptor，`fd`）。在底层，文件夹（目录）里存的只是一张“名字 $\rightarrow$ 编号”的通讯录；文件真正的身家档案——大小、所有者、权限、时间戳、以及数据到底躺在哪几个磁盘块上——单独存在一份叫作 **inode**（index node，索引节点）的结构里。当你把 `report.txt` 改名或删除时，动的只是目录里的那条通讯录；而程序 A 手里的 `fd` 早已在打开那一刻绕过名字、直接拴在了内核的打开文件对象与 inode 本体上！哪怕最后一个名字都被抹掉了，只要还有进程紧紧攥着它的打开引用，内核就会等最后一个引用关闭后，才真正把这份 inode 和数据块回收释放。

??? question "既然如此，如果在 `report.txt` 被改名为 `old.txt` 之后，另一个新进程 B 此时也去 `open("report.txt")`，它会读到旧内容吗？"

    不会。新进程 B 手里没有现成的 `fd`，它必须从头按名字去翻目录通讯录：如果原名已经空了，打开直接报错“文件不存在”；如果这期间有人恰好又新建了一个同名 `report.txt`，B 打开的就是那个全新的 inode，和 A 正在读的旧本体毫无关系。

摸透了“名字、打开状态、文件本体”这几层对象的分离，所有看似怪异的现象——`dup` 共享读写位置、删了大日志硬盘空间却不涨、硬链接与符号链接的差别——都会瞬间豁然开朗。

## 文件抽象究竟帮我们扛了哪些脏活？

面对一块刚拆封的裸硬盘，硬件只提供一个冷冰冰的线性数组接口：“读写第 $N$ 号 4 KiB 块”。它不懂什么是文件名，不懂谁有权读，也不懂写了一半怎么记下文件长度。文件系统在裸块之上，实打实为我们筑起了五层服务：

- **人类友好的层次命名**：用树状目录把成千上万份数据整理得井井有条；
- **灵活的字节流抽象**：让程序可以随心所欲读 3 个字节或跳到第 10 万字节处写入，底层自己操心怎么对齐磁盘块；
- **丰富的元数据档案**：记录权限、所有者、修改时间和文件类型；
- **动态空间管家**：像物理内存分配器一样管理海量空闲磁盘块的分配与回收，尽量减少磁盘碎片；
- **崩溃一致性保障**：确保更新到一半突然断电，重启后整棵目录树不至于碎成乱码（第 7 章专门深挖）。

当然，每多一层便利就多一分开销——路径解析、元数据记账、缓存维护和日志写入都要耗费 CPU 与磁盘带宽，但正是这层抽象把千千万万应用程序从繁琐的扇区编号里彻底解放了出来。

## 掰开四类最容易张冠李戴的内核对象

读懂整个文件子系统，只需把下面这四个对象各自的位置和职责刻在脑海里：

### 1. 文件描述符（fd） { #file-descriptors }

**文件描述符**（file descriptor）是**进程私有的一个小整数**（Linux 上 `0`、`1`、`2` 默认分别是标准输入、标准输出和标准错误），本质上是当前进程“打开文件描述符表”里的数组下标。妙在它不只是普通文件的专属——管道、网络套接字、终端设备、甚至定时器和事件通知对象，在 Unix 里全都统一发一个 `fd`，用同一套 `read`/`write`/`close` 接口操纵。

### 2. 打开文件对象（Open File Object）

每当进程成功调用一次 `open()`，内核就在系统全局创建一份**打开文件对象**（open file object，在 Linux 内核里叫 `struct file`），专门记录**这次打开会话的动态状态**：当前读/写游标停在文件的第几个字节（文件偏移）、这次打开用的是只读还是追加标志，以及指向底层文件本体的指针。如果进程调用 `dup()` 复制描述符，或者 `fork()` 生出子进程继承描述符，新旧两个 `fd` 会指向**同一个打开文件对象**——因此它们共享同一个读写游标！

### 3. 索引节点（inode）

**inode** 是文件真正的**本体档案**，每个文件在所属文件系统里独享一份唯一的 inode 编号。它存着文件类型、字节长度、读写权限、属主 UID/GID、时间戳、硬链接计数，以及指向实际数据块位置的索引。特别注意：**文件名通常并不存在 inode 里！** 这样同一个文件才能同时拥有多个名字。

### 4. 目录项（Directory Entry / dentry）

**目录项**（directory entry，内核内存缓存里常简称 **dentry**）只干一件事——**把一个可读名字映射到对应的 inode 编号**。为了避免每次敲 `open("/usr/lib/...")` 都重新去硬盘翻好几层目录，内核会在内存里维护一张高速的目录项缓存（dentry cache），把近期解析过的路径碎片留在内存里。

把这四层串成一张关系图，全篇最核心的骨架就定格在这里：

```text
进程私有的 fd 表
  fd 3 ─┐
  fd 7 ─┴─> 打开文件对象（记录：当前偏移量、读写标志）
                │
                ▼
              inode（记录：文件本体元数据、硬链接计数、数据块位置）
                ▲                 ▲
                │                 │
         目录项 name_a       目录项 name_b
```

## 慢镜头回放：一行 `open("report.txt")` 背后走了几步？

你在 C 代码里轻轻写下一句 `int fd = open("report.txt", O_RDONLY);`，内核拿到请求后默默干完六件事：

1. 看路径是不是 `/` 开头，决定从根目录还是当前工作目录起步；
2. 沿着路径逐级查找目录项，每跨过一级目录都要核对搜索权限，并检查有没有撞上别的挂载文件系统；
3. 摸到终点目标 inode，核对当前进程身份是否具备所请求的读/写权限；
4. 在内核里分配并初始化一个新的**打开文件对象**（把初始偏移设为 `0`），让它指向目标 inode；
5. 在当前进程的 `fd` 表里挑一个最小的空闲下标（比如 `3`），填入指向刚才那个打开文件对象的指针；
6. 把小整数 `3` 返回给用户程序。

所以返回值 `3` 绝不代表“硬盘上的第 3 号文件”，它纯粹是你这个进程自己表格里的第 3 号抽屉——旁边另一个进程里的 `fd 3`，完全可能指向一个八竿子打不着的网络连接。

## 亲眼看懂共享偏移：`dup()` 与两次 `open()` 的差别

盯着下面这六行 C 代码，猜猜 `a` 和 `b` 各自读到了文件里的哪几个字节：

```c
int fd1 = open("data.txt", O_RDONLY);
int fd2 = dup(fd1);

char a[4], b[4];
read(fd1, a, sizeof(a));
read(fd2, b, sizeof(b));
```

假设 `data.txt` 内容是 `abcdefgh`。因为 `fd2` 是通过 `dup(fd1)` 变出来的，它俩在上面那张关系图里指着**同一个打开文件对象**！`read(fd1, a, 4)` 读走了 `abcd` 并把共享游标推进到了第 `4` 字节；紧接着 `read(fd2, b, 4)` 从第 `4` 字节接着读，拿到的是 `efgh`！（顺便一提，你在 Shell 里写的 `cmd > out.log 2>&1` 把标准错误和标准输出合并到同一个文件且不互相覆盖，靠的正是 `dup2` 共享同一个打开文件对象的偏移量！）

相反，如果你分别调用了两次独立的 `open("data.txt", O_RDONLY)`，内核会建出**两个独立的打开文件对象**，各自攥着各自的游标，于是 `a` 和 `b` 都会从头读到 `abcd`。在多线程并发读写同一个文件时，如果想彻底摆脱共享游标带来的互相踩踏，可以直接改用带显式偏移量的 `pread` / `pwrite` 接口。

## 路径解析里的隐形暗礁：性能与 TOCTOU 安全竞态

当你打开 `/home/alice/report.txt` 时，内核并不是做一次全局哈希查找，而像走迷宫一样逐级剥洋葱：

```text
根目录 inode (/)
  -> 查目录项 "home" -> 拿到 home 的 inode
  -> 查目录项 "alice" -> 拿到 alice 的 inode
  -> 查目录项 "report.txt" -> 拿到最终文件的 inode
```

每跨一层都要检查目录权限、查看缓存、处理挂载点跳转。如果路径里的每一级都在内存 dentry 缓存里命中，全程飞快零磁盘 I/O；可一旦缓存变冷，或者跑在跨网络的远程文件系统（如 NFS）上，一层层来回打听的延迟甚至可能超过真正读文件内容的时间！

路径解析还藏着一类极其著名的安全漏洞：由于路径里可以夹杂 `..` 返回上级目录，也可以夹杂随时能被调包的[符号链接](#symbolic-links)，如果一个高权限程序傻乎乎地先用 `access("/tmp/user_file", ...)` 检查这个路径安不安全，过了两微秒再调用 `open("/tmp/user_file", ...)` 去打开它——攻击者完全可以在这两步的微小缝隙里，闪电般把 `/tmp/user_file` 删掉并换成一个指向 `/etc/shadow` 密码文件的符号链接！结果检查时看的是无害文件，真正打开的却是系统机密。这种“检查时看的是 A，使用时已被换成 B”的漏洞叫作[检查时与使用时竞态（TOCTOU）](../chapter_06_protection_virtualization/01_protection_security.md#toctou)。现代安全编程提倡先打开目录拿到稳定的目录 `fd`，再用 `openat(dirfd, ...)` 配合禁止跟随符号链接标志，大幅压缩甚至闭合竞态窗口。

## 硬链接与符号链接：同一个文件，两种“起别名”的姿势

既然名字和 inode 本体分家了，给文件起别名自然演化出了两套风格迥异的玩法。

### 硬链接（Hard Link）：平起平坐的双胞胎名字

**硬链接**（hard link）极其纯粹——在目录里再添一条新的目录项，直接指向**同一个 inode 编号**，同时把 inode 里的**硬链接计数**加 1：

```text
目录项 name_a ──┐
                ├──> inode 42（链接计数 = 2，指向同一份磁盘数据）
目录项 name_b ──┘
```

`name_a` 和 `name_b` 地位完全平等，不存在谁是“原件”、谁是“快捷方式”！删掉 `name_a`，只是抹掉了左边那条目录项、把计数从 `2` 减到 `1`，`name_b` 照常安稳读出全部数据。

不过硬链接有两条天然禁令：第一，**不能跨文件系统创建**，因为不同磁盘分区各自维护一套独立的 inode 编号，1 号分区的 `inode 42` 在 2 号分区里压根是另一份风马牛不相及的文件；第二，**普通用户不允许给目录随便建硬链接**，否则一不小心把子目录链接回祖先目录，整棵目录树就会长出一个无限死循环的环，把遍历目录和空间回收全搞崩。

### 符号链接（Symbolic Link） { #symbolic-links }

硬链接既不能跨磁盘分区、又不能指目录，那想跨盘指个文件夹怎么办？**符号链接**（symbolic link，又称软链接 `symlink`）换了一条巧路：它本身是一个**独立的特殊小文件**（有自己的独立 inode），文件内容不是普通数据，而是一行纯文本路径字符串，像贴在门上的一张纸条：“你要找的东西不在这儿，请去 `/mnt/data/report.txt` 找！”

当内核解析路径撞上符号链接时，会读出纸条上的目标路径继续顺藤摸瓜。正因为只是一张写着路径的纸条，它极其灵活：
- 可以轻松**跨文件系统**；
- 可以自由**指向目录**；
- 哪怕目标文件此刻根本还没创建出来，也能先把纸条贴好。

相应的代价也一目了然：如果原文件搬家或被删了，这张纸条就成了指向空气的**悬空链接（dangling symlink）**；而且万一纸条 A 指着纸条 B、纸条 B 又指回纸条 A，内核还必须限制最大递归深度（否则解析器当场死循环）。

## 彻底解开“删了文件，硬盘空间却没释放”的悬案

在 Linux 里，“删除文件”的系统调用其实不叫 `delete`，而叫 **`unlink`（取消链接）**——这个名字精准得让人拍案叫绝！调用 `unlink` 时，内核只做两件事：抹掉对应的目录项，并把该 inode 的**硬链接计数减 1**。

内核什么时候才真正把文件占的磁盘块还给空闲池？**必须同时满足两个条件：硬链接计数归零（磁盘上再也没人叫得出它的名字），并且内存里指向它的打开文件对象引用计数也归零（再也没有活着的进程攥着它的 `fd`）。**

这条规则既能玩出极优雅的技巧，也制造过无数线上告警：
- **绝不留垃圾的临时文件**：程序刚 `open` 创建一个临时文件，立刻就对它调用 `unlink` 抹掉名字！程序自己还能顺着 `fd` 欢快地读写它；哪怕程序下一秒突然崩溃被强杀，内核自动关闭所有 `fd`、引用归零，磁盘空间瞬间干干净净回收，绝不会在 `/tmp` 里留下一堆孤儿临时文件；
- **线上磁盘 100% 悬案**：运维看到一个 50 GB 的日志把磁盘撑爆了，顺手 `rm app.log`，结果一查 `df -h` 发现可用空间一字节都没涨！原因正是那个服务进程还一直开着 `app.log` 的 `fd` 拼命往里写呢。此时必须用 `lsof | grep deleted` 揪出依然占着已删 inode 的进程，通知它重新打开日志或重启，那 50 GB 空间才会瞬间哗啦啦地吐出来。

## 目录本身到底长什么样？

聊了一路“目录存名字”，其实目录本身在文件系统眼里也是一个特殊的“文件”（拥有自己的 inode 和数据块），只不过它的数据块里存的是“文件名 $\leftrightarrow$ inode 编号”的映射表（小目录用线性列表，现代文件系统面对百万文件大目录则普遍用哈希 B 树加速查找）。应用程序绝不能直接用 `write()` 往目录字节里乱写，必须通过 `mkdir`、`rename`、`unlink` 等受控系统调用，由内核严密维护目录结构不变量。

顺手记牢一个最容易搞反的权限常识——**目录的 `r / w / x` 权限和普通文件截然不同**：
- 读权限（`r`）：允许**列出**这个目录里有哪些文件名（比如 `ls`）；
- 写权限（`w`）：允许在这个目录里**新增、删除或重命名**文件（注意：能不能删一个文件，看的是你对它**所在目录**有没有写权限，而不是对文件本身有没有写权限！）；
- 执行/搜索权限（`x`）：允许**穿过**这个目录去访问里面的某个已知路径。

## inode 里怎么指路？数据块布局与稀疏文件

最后一块拼图：一个 10 GB 的大视频文件占了几百万个 4 KiB 磁盘块，一个只有几百字节的 inode 总不能把几百万个块号全塞进自己肚子里吧？历史上文件系统演化出了三代块索引招数：

- **直接 / 多级间接块指针（经典 Unix / ext2/3）**：inode 里留十几个“直接指针”直指前十几个数据块（小文件零跳转瞬间读完）；文件变大了，就用一级、二级、三级“间接指针”指向专门存块号列表的索引块，像树一样层层展开；
- **区段（Extent，现代 ext4 / XFS 等主流）**：与其傻傻地把连续的 1000 个块号一条条写一千遍，不如只记一行“从第 `5000` 号物理块起，连续 `1000` 个块都归我”！这种用**（起始块号 + 连续长度）**压缩大片连续空间的记录叫作**区段**（extent），极大地瘦身了大文件元数据，也天然利好顺序读写（代价是长期反复删改后磁盘碎片增多，依然需要预分配与整理）；
- **B+ 树索引**：把海量区段或稀疏块映射组织成平衡搜索树，就算文件大到几十 TB 也能几步精准定位。

顺着这块映射表，还能顺手变出一个省空间的戏法——**稀疏文件**（sparse file）。如果你新建一个空文件，直接把写入游标 `lseek` 跳到 `1 GB` 的位置只写下 `1` 个字节，硬盘真的要为你白白分配 `1 GB` 的全零数据块吗？完全不用！文件系统只在映射表里记下末尾那 1 块，中间那 1 GB 根本不分配任何物理磁盘块，留成一个逻辑“空洞”：

```text
程序看到的逻辑文件：  [头部数据][....... 1 GB 逻辑空洞 .......][尾部 1 字节]
磁盘上实际占用的块：  [头部数据]                              [尾部 1 字节]
```

当程序去读空洞区域时，文件系统直接递回全零字节；只有真往空洞里写非零数据时，才按需补分物理块（虚拟机的动态磁盘镜像就极爱用这招）。只是拷贝稀疏文件时留个心眼：老老实实逐字节 `read` 再 `write` 的普通复制会把空洞硬生生填成实打实的 1 GB 零块，需要用支持稀疏感知的工具（如 `cp --sparse=auto`）才能保住空洞。

## 一台机器插着五花八门的盘：VFS 虚拟文件系统 { #vfs }

一台现代 Linux 服务器上可能同时挂着本地 ext4 硬盘、XFS 数据盘、U 盘上的 FAT32、内存里的 `tmpfs`、远程网络 NFS，甚至还有把内核状态伪装成文件的 `/proc` 伪文件系统。每种文件系统的磁盘格式和数据结构风马牛不相及，可应用程序为什么不管读哪一种，全都能统一调用完全相同的 `open()` 和 `read()`？

奥秘在于内核在具体文件系统前面架起了一层面向对象风格的统一抽象层——**虚拟文件系统**（Virtual File System，**VFS**）。VFS 规定了一组标准操作接口（“怎么查目录项”“怎么读一页”“怎么改属性”），每个具体文件系统只需向 VFS 注册自己的函数实现表；上层系统调用一律只和 VFS 打交道，由 VFS 自动分派给脚下对应的真实实现。

统一接口让应用程序几乎实现了“一套代码通吃天下”，但切忌把抽象当成绝对等价——VFS 藏不住底层实现之间的真实语义鸿沟：比如本地 ext4 能保证同目录下 `rename` 严格原子，某些网络文件系统在缓存一致性、文件锁、大小写敏感度甚至断电持久化保证上，却有着截然不同的脾气。

## 页缓存与文件能力的最后一瞥

普通文件的读写绝大多数时候并不会直接撞向冰冷的硬盘，而是先落在内存里的**页缓存**（page cache）里：读操作命中页缓存直接内存拷贝返回，零设备等待；写操作通常也是先改内存里的页缓存并把页标“脏”，系统调用立刻痛快返回，脏页留待后台择机刷回磁盘。而且，上一章学的 `mmap` 文件映射和普通 `read`/`write` 共享的往往正是**同一批页缓存页**。当然，这立刻引出了一个要命的裂痕——**`write()` 返回成功，绝不等于数据已经安全焊死在硬盘上！** 断电时该如何用 `fsync` 和日志保命，我们在[第 7 章 持久化与崩溃恢复](02_journaling_crash_disk.md)里会彻底算清这笔账。

另外，回头再品一眼 `fd` 的安全含义：文件系统权限检查通常只在 `open` 解析路径那一刻执行，一旦你手里拿到了合法打开的 `fd`，这个 `fd` 本身就成了一枚沉甸甸的**访问能力凭证**——即便随后目录权限被收紧、甚至文件被改名隐藏，持有这枚 `fd` 的进程依然能继续读写，甚至还能通过 Unix 域套接字把这枚 `fd` 隔空传给另一个原本无权访问该路径的进程！所以做安全审计时，绝不能只盯着路径字符串看，必须一并追踪 `fd` 的打开、继承与传递。

至此，沿着“文件名 $\rightarrow$ 目录项 $\rightarrow$ inode $\rightarrow$ VFS $\rightarrow$ 页缓存”这条文件系统主线我们已经完全打通。接下来把镜头转向另一条交织前行的铁轨：当数据压根不在页缓存里、或者程序面对成千上万条慢吞吞的外部网络与磁盘连接时，线程究竟该用什么姿势“等待”才不浪费 CPU？而内核又该怎样透过千奇百怪的**设备驱动**，向底层硬件下达真正的读写命令？让我们走进[下一篇：I/O 模型与设备驱动](03_io_models_drivers.md)。

## 自测

1. 文件描述符（`fd`）、打开文件对象（open file object）和 inode 这三者各自存着什么核心信息？
2. 用 `dup(fd1)` 复制出 `fd2` 后，为什么对 `fd1` 读取会连带推动 `fd2` 的读取位置；而对同一个路径调两次 `open()` 却不会？
3. 硬链接和符号链接在底层指向的目标、能否跨文件系统、以及删除原名后的表现上有什么根本区别？
4. 为什么运维在 Linux 上用 `rm` 删除了一个几十 GB 的大日志文件后，磁盘可用空间有时依然纹丝不动？该怎么真正释放它？
5. 当一次普通 `read()` 在页缓存中稳稳命中时，还需要向磁盘发起硬件 I/O 吗？

??? note "参考思路"

    1. `fd` 是进程局部的文件描述符表下标索引；打开文件对象记录本次打开会话的动态状态（当前文件偏移量、打开模式标志与底层对象指针）；inode 保存文件本体的元数据（权限、大小、时间戳、硬链接计数）以及数据块映射位置。
    2. `dup()` 让两个 `fd` 指向内核里的**同一个打开文件对象**，因此共享同一份偏移游标；调用两次 `open()` 则会新建两个相互独立的打开文件对象，各自维护独立偏移。
    3. 硬链接是直接指向同一 inode 的平行目录项，不可跨文件系统，删掉一个名字只要计数未归零内容丝毫不受影响；符号链接是内容为“目标路径文本”的独立小文件，可以跨文件系统和指向目录，但原名被删或移走后会变成无法访问的悬空链接。
    4. 因为有运行中的进程依然打开着该文件，内存里对它 inode 的打开引用计数尚未归零；`unlink` 只抹掉了目录名。找到并重启（或通知关闭重新打开日志）占用该已删文件的进程，待最后一个引用关闭后空间才会释放。
    5. 不需要。内核直接把页缓存中的文件数据拷贝到用户缓冲区并更新偏移即可返回，全程零块设备读取。
