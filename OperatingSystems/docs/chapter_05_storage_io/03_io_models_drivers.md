# I/O 模型与设备驱动

## 同时来了四份输入，线程到底该在哪儿等、怎么等？

CPU 执行一条加法只要不到 1 纳秒，而等一块机械硬盘转过来或等大洋彼岸发回一个网络包，轻轻松松就是几毫秒到几十毫秒——两者速度差着几百万倍！

设想你的服务器同时连着四个客户端，随时都可能有数据送来。面对慢吞吞的外部设备，程序有三种截然不同的“等法”：
- **干脆原地睡等（阻塞）**：线程喊一声 `read()`，没货就安心睡觉把 CPU 让给别人，等数据齐了再醒来继续；
- **问一眼就撤（非阻塞）**：线程问一句“有数据吗？”内核答“还没”，线程扭头立刻干别的，等会儿再来问，或者干脆请内核替自己盯着所有连接、哪个有货了通知一声；
- **甩手掌柜（异步完成）**：线程把空盘子递给内核说“帮我把这 4096 字节读到这个缓冲区里，读完了发消息叫我”，然后自己转身忙其他活儿，直到收到“已经彻底搬进缓冲区了”的完工通知！

这几种做法的核心差别，就藏在两个问题里：**等待期间谁被卡住了？内核最后拍你肩膀时，通知的是“现在可以试着去读了（就绪）”，还是“数据已经帮你读进盘子里了（完成）”？**

??? question "非阻塞 `read()` 立刻返回了“暂时没有数据”（例如 `EAGAIN` / `EWOULDBLOCK`），能把它当成“文件或连接已经结束（EOF）”直接关闭连接吗？"

    千万不能！这是写网络程序最常栽的一个跟头。返回 `0` 才代表对端正常关闭或到达文件末尾（EOF）；而返回 `-1` 且错误码为 `EAGAIN`/`EWOULDBLOCK`，仅仅表示“此刻缓冲区刚好空着，对方待会儿还会继续发数据”。一旦把两者混为一谈，你就会把一条活得好好的连接提前咔嚓剪断。

这一篇，我们就从上到下打通两条链路：上半场把五花八门的 **I/O 模型**与缓冲策略理成清清爽爽的坐标系；下半场推开内核最底层的门，看看**设备驱动**怎样把统一的 `read`/`write` 翻译成千奇百怪的硬件电信号。

## 先拆开两组最容易搅浑的坐标轴

技术讨论里，人们常常随口把“非阻塞”和“异步”混着喊。其实它们描述的是两个完全正交的维度：

### 维度一：阻塞（Blocking）vs 非阻塞（Non-blocking）

盯的是**单次函数调用当下有没有立刻返回**：
- **阻塞**：如果眼下没数据可读（或写缓冲已满），当前线程直接被内核挂起睡眠，直到条件满足才从函数里返回；
- **非阻塞**：如果眼下干不了，函数绝不让线程睡觉，**当场返回一个“暂不可用”的状态码**，把下一步决定权交还给调用者。

### 维度二：同步（Synchronous）vs 异步（Asynchronous）

盯的是**实际数据搬运和结果拿取到底是谁主动推进的**：
- **同步 I/O**：最终还是由调用线程自己在某个时刻主动发起并等待读写调用把数据搬到用户缓冲区、在返回时亲手拿到结果；
- **异步 I/O**：调用者把“要读哪里、读多少、放进哪块缓冲区”打包成一张委托单提交给内核就撒手不管；内核与硬件在后台默默把数据搬进目标缓冲区，**全部完工后**再通过完成队列、回调或事件向调用者报喜。

把这两根坐标轴一画，常见迷思瞬间破灭：**“非阻塞”绝不自动等于“异步”！** 一个 `while` 循环不停调用非阻塞 `read()`，虽然每次调用都不睡觉，但依然是调用者自己在苦哈哈地一遍遍亲自试探、亲自执行同步读取。

## 五种经典 I/O 等待姿势演进

跟着“要伺候的连接数从 1 个涨到 10 万个”的真实压力，你会看到各种 I/O 模型是如何一步步被逼出来的。

### 1. 阻塞 I/O：最直观，可一万条连接配一万条线程吃不消

最自然好写的模型，控制流从头到尾一条直线：

```text
应用调用 read()
  -> 内核发现数据还没到 -> 当前线程阻塞睡眠，CPU 切去干别的
  -> 磁盘或网卡把数据送来 -> 硬件中断唤醒线程
  -> 内核把数据拷贝到用户缓冲区 -> read() 带着字节数返回
```

千万别瞧不起阻塞 I/O！对于连接数可控（几十到几百）、业务逻辑复杂的程序，**阻塞 I/O 配上一个大小合理的线程池**代码最干净、排错最轻松，性能也往往相当出色。它真正的天花板出现在“十万条并发网络连接（著名的 C10K / C100K 问题）”：给十万条大多时间都在发呆的连接各配一条内核线程，光线程栈就要吃掉好几个 GB 内存，调度器也被撑得喘不过气。

### 2. 非阻塞 + 忙轮询：不睡觉了，却把 CPU 烧冒烟

为了不让一条线程卡死在一条连接上，把描述符设为非阻塞模式。可如果你直接写个死循环一遍遍问内核“有货没？有货没？”：

```c
for (;;) {
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n > 0) consume(buf, n);
}
```

哪怕一整分钟一个字节都没来，这颗 CPU 核心照样被你跑成 **100% 满载烧电**！纯忙轮询只有在高频交易、DPDK 专用收包核心这类“宁可独占一颗核烧电，也要把微秒级唤醒延迟榨干”的极端场合才派得上用场；普通服务绝不能这么干。

### 3. I/O 多路复用：一位管家盯住一万扇门

既然“一扇门配一个保安（阻塞线程）”太费人手，“一个保安跑断腿一遍遍敲一万扇门（忙轮询）”又太费体力，最优解呼之欲出——**给一万扇门都装上门铃，全都连到同一张值班总台！** 只要留一位管家（一条事件循环线程）安静守在总台睡觉，哪几扇门响了铃，内核就一次性把响铃名单递给他，他再去逐个敲开那几扇门把数据非阻塞读走！

这就是撑起现代高并发网络服务器半壁江山的**I/O 多路复用**（I/O multiplexing）：

```text
应用把关心的成千上万个 fd 注册给内核
  -> 单条线程调用等待接口睡眠，同时守望所有 fd
  -> 只要任意一个或多个 fd 变为可读/可写，内核立刻返回这份“就绪名单”
  -> 应用只对名单上的就绪 fd 执行非阻塞读写，绝不空跑！
```

这条路线自身也经历了两代进化：
- **第一代：`select` / `poll`**：每次调用都得把整张几千个 fd 的名单从用户态重新拷进内核，内核再从头到尾全盘扫描一遍；哪怕 10,000 条连接里此刻只有 3 条活跃，每轮也要傻傻地把 10,000 个全扫一遍，开销随连接总数线性膨胀。
- **第二代：`epoll`（Linux）/ `kqueue`（BSD/macOS）**：把你关心的 fd 名单直接**常驻记在内核数据结构里**（如红黑树），当某个网卡中断到来激活某条连接时，内核顺手把它塞进一条“就绪链表”；应用程序调用等待时，内核只需把那 3 条真正活跃的 fd 递出来，复杂度从“看总连接数”骤降为“只看活跃连接数”！

使用 `epoll` 时，一定要摸透它两种触发脾气：
- **水平触发**（level-triggered，LT，默认）：只要接收缓冲区里**还有**没读完的数据，你下次来问，内核依然会贴心地再提醒你一次——宽容、不容易漏数据；
- **边缘触发**（edge-triggered，ET）：内核只在状态“从无数据变成有数据”的**那一瞬跳变边缘**通知你一次！如果这次你只读了一半留着另一半在缓冲区里，内核可不会再喊你第二遍——因此边缘触发模式通常要求你必须把非阻塞 fd **一口气循环读到返回 `EAGAIN` 为止**，才能安心回去等下一轮。

### 4. 就绪模型 vs 完成模型：异步 I/O 登场

仔细看一眼刚才的 `epoll`：它本质上属于**就绪模型（Readiness）**——内核喊你“3 号连接有数据了，快去读吧”，但实际把数据从内核搬进你用户缓冲区的那次 `read()` 系统调用，依然得由你的应用线程亲自跑一趟。而且对于本地磁盘普通文件，传统 `epoll` 往往直接告诉你“永远可读”，没法像网络套接字那样优雅地做异步等待。

彻底解放应用线程的是**完成模型（Completion）**——也就是真正的**异步 I/O**（例如 Linux 现代的 `io_uring`、Windows 的 IOCP）：

```text
就绪模型（epoll）：内核通知“fd 可读了”   -> 应用自己调 read() 搬数据
完成模型（异步 I/O）：应用提交“帮我读 4KB 到 buf” -> 内核和 DMA 搬完后通知“已读完！”
```

一个典型的异步 I/O 生命周期长这样：
1. 应用提前分配好一块缓冲区和请求上下文（并确保在完工前绝不释放它！）；
2. 把一个——甚至一整批几十个——读写请求塞进共享提交队列，一次敲门交由内核批量处理；
3. 应用线程头也不回地继续干别的计算；
4. 稍后从完成队列里成批收割已经搬好数据的结果；
5. 处理短读、错误、超时取消与后续状态机推进。

异步 I/O 既省掉了海量等待线程，又借批量提交把第 1 章算过的系统调用过门费摊得极薄；代价则是业务逻辑被切成了零碎的状态机和回调，对象生命周期变得棘手，出了错调用栈也不再直白。顺便提个醒：许多编程语言里写起来像同步代码一样丝滑的 `async/await` 语法糖，底层实现的可能是网络事件循环（就绪模型）、可能是原生内核异步接口，也可能是背后藏着一个阻塞线程池悄悄代劳——**语法上是异步的，并不保证底层磁盘路径就一定是原生无阻塞异步的。**

## 要不要过页缓存？缓冲 I/O 与直接 I/O

确定了“怎么等”，还有一道关乎性能和一致性的关键开关：读写本地文件时，数据到底要不要经过内核的页缓存？

### 缓冲 I/O（Buffered I/O，默认）

绝大多数普通程序走的都是这条路：数据在用户缓冲区和磁盘之间，多了一站内核页缓存。重复读取热文件时瞬间内存命中，零碎小写入被内核合并攒批再落盘，顺序读还能免费蹭到内核自动预读。代价则是多了一趟“页缓存 $\leftrightarrow$ 用户缓冲区”的内存拷贝、吃掉系统空闲内存，且 `write()` 返回时数据还没真落盘。

### 直接 I/O（Direct I/O） { #direct-io }

像 PostgreSQL、MySQL InnoDB 或 RocksDB 这类专业存储引擎，自己手里本来就维护着一套更懂查询规律的巨型用户态缓冲池（Buffer Pool）。如果数据读进来先在内核页缓存存一份、再拷进数据库缓冲池存第二份，白白浪费一半宝贵内存不说，内核不懂数据库规律乱做预读和淘汰还会帮倒忙！

于是操作系统提供了**直接 I/O**（例如打开文件时传入 `O_DIRECT` 标志），请求绕过普通页缓存，尽量让数据在用户态缓冲区和存储设备之间直来直去。使用它必须清醒认识三条现实限制：
- **严格的对齐纪律**：用户缓冲区起始地址、读写长度和文件偏移量通常都必须严丝合缝对齐到磁盘扇区或块大小（如 512 字节或 4096 字节），否则内核直接报错拒绝；
- **并没有绕过整个内核**：直接 I/O 省掉的只是页缓存这一站，请求照样要穿过 VFS、块层队列、设备驱动以及下一篇要讲的[直接内存访问（DMA）](04_interrupts_dma_cache.md)；
- **绝不保证天生更快**：对于缺乏成熟自建缓存的应用、或者高频重复读取的小随机文件，绕过页缓存反而会让性能暴跌；而且如果同一个文件一边用缓冲 I/O 写、一边用直接 I/O 读，还极易闹出两边数据不一致的乱子。

## 为什么转发一个文件要拷贝两遍？零拷贝的巧思

设想一个静态文件服务器（如 Nginx）把硬盘上的一个 1 GB 视频发送给远端浏览器。走传统 `read()` + `write()` 代码时，数据像坐过山车一样被折腾得够呛：

```text
磁盘 --(DMA)--> 内核页缓存 --(CPU拷贝1)--> 用户态 buf --(CPU拷贝2)--> 内核网络缓冲 --(DMA)--> 网卡
```

仔细看中间那两趟 CPU 拷贝——应用程序压根没打算看、更没打算改视频里的任何一个字节，数据却白白跨过用户/内核边界往返抄了两整遍，顺手把 CPU 缓存洗刷得一干二净！

为了砍掉这笔冤枉账，操作系统推出了**零拷贝**（zero-copy）接口（如 Linux 的 `sendfile`、`splice`）：应用程序只递给内核一句话——“把文件 `in_fd` 里的 1 GB 直接发给网络 `out_fd`！”数据干脆留在内核空间里（甚至直接把页缓存页的物理地址交给网卡 DMA 聚合发送），彻底免去了往返用户态的软件拷贝和多余的上下文切换。

不过别被名字里的“零”字骗了：**“零拷贝”指的是消除多余的 CPU 软件内存拷贝**，并不意味着底层没有设备 DMA 传输、没有描述符构建，也不代表所有文件系统和网卡硬件都支持完全同一条路径。

## 推开最底层的门：设备驱动怎样替内核说“硬件方言”？

聊了这么多上层模型，所有请求落到最底端都要面对一个冰冷的现实：市面上有成千上万种网卡、固态硬盘、显卡、声卡和鼠标，每家厂商给硬件芯片设计的寄存器地址、命令格式和时序规矩全都不一样。内核总不能把一万家厂商的暗号全硬编码在文件系统里吧？

负责在“统一的内核抽象”和“五花八门的硬件方言”之间当翻译官的，正是**设备驱动**（device driver）：

```text
通用子系统（文件系统 / 网络栈）发出标准请求
  -> 设备驱动核对参数，把请求翻译成硬件听得懂的命令描述符
  -> 写硬件寄存器或推入共享提交队列，按门铃通知设备干活
  -> 硬件设备默默执行任务
  -> 完工后触发硬件中断（或被轮询察觉）
  -> 设备驱动回收描述符、检查错误码，并向上层汇报完工
```

一个完整设备驱动日常要扛的远不只是读写数据：通电探测硬件型号与初始化、管理休眠节能状态、配置寄存器和 DMA 传输队列、处理中断与异常超时、在设备卡死或 U 盘突然被热拔出时优雅地重置和收拾残局，统统都是它的分内事。

为了方便归类管理，类 Unix 内核通常把外设划成三大阵营：
- **字符设备（Character Device）**：像键盘、串口、终端、随机数发生器，按字节流依次收发，不支持跳到任意块位置随机读写；
- **块设备（Block Device）**：像机械硬盘、NVMe 固态硬盘，以固定块为单位支持随机寻址，上面可以架起页缓存、块层调度器和完整文件系统；
- **网络设备（Network Device）**：像以太网卡、Wi-Fi 芯片，收发的是一帧帧离散数据包，直接接入协议栈和套接字，而不是塞进 `/dev` 下的传统文件偏移模型。

### CPU 到底怎么给硬件下命令？内存映射 I/O（MMIO）

驱动代码也是 C 语言写的，CPU 究竟靠什么把命令送到硬盘或网卡芯片的耳朵里？现代计算机最普遍的手法叫**内存映射 I/O**（memory-mapped I/O，**MMIO**）：主板芯片组把设备硬件上的控制寄存器、状态寄存器，悄悄映射到 CPU 物理地址空间的一小片特殊保留区里。

驱动把这片物理地址映射进内核页表后，往那个地址写一个整数，硬件电路就会自动把这次“写内存”截获并路由成“往网卡控制寄存器发一条开机指令”！可千万别真把 MMIO 当成普通内存变量随便读写——写驱动时必须严守内核专用的 I/O 访问原语（如 `readl`/`writel`）并配齐内存屏障：
- 必须严格按硬件要求的字节宽度（如 32 位/64 位）和大小端序访问；
- 必须把这段映射标成**禁止 CPU 缓存**（否则你写的“启动设备”命令还捂在 CPU Cache 里没发出去，或者反复读到的全是缓存里的陈旧设备状态！）；
- 防止编译器和 CPU 乱序重排——绝不能把“按门铃启动 DMA”重排到“填好数据地址”之前！普通 C 语言的 `volatile` 根本拦不住 CPU 硬件级乱序，绝不能拿它替代真正的内核 I/O 屏障原语；
- 还得防着热插拔设备半途被拔走引发的总线异常。

## 真实世界的铁律：短读写、错误重试与背压

新手写 I/O 代码最容易犯的乐观病，是以为“我让 `write(fd, buf, 4096)` 写 4096 字节，它只要不报错就一定一次性写完了 4096 字节”。真实系统里，网络缓冲只剩 1200 字节空位、管道半满、或者半路撞上一个操作系统信号，都可能让 `write`/`read` 合法地只搬完一部分就提前返回（所谓**短读 / 短写**）。因此，稳健的流式代码必须循环推进直到全部搬完或遇到明确终点：

```c
while (done < length) {
    ssize_t n = write(fd, buffer + done, length - done);
    if (n > 0) done += (size_t)n;
    else handle_error_or_retry();
}
```

遇到失败要分清“可重试的暂时错误”（如 `EINTR` 被信号打断、`EAGAIN` 暂不可用）和“不可恢复的硬错误”（如对端断开 `EPIPE`、硬盘坏道 `EIO`），绝不能对着永久错误死循环重试把 CPU 烧爆。同时牢记：**即便用上 `epoll` 或 `io_uring` 能同时接住十万条连接，你的内存和下游数据库容量依然是有限的！** 必须给每条连接的缓冲和未完成队列设好硬上限，一旦下游堵车立刻暂停读取、放缓接收新请求，把**背压**稳稳传回去。

### I/O 策略选型速查表

| 业务场景 | 顺手的起点选择 |
| --- | --- |
| 连接数不多、业务逻辑复杂 | 阻塞 I/O + 合理规模线程池 |
| 成千上万并发网络连接、每次处理快 | 非阻塞 I/O + 多路复用（`epoll`/`kqueue`） |
| 高并发、高队列深度的存储与混合读写 | 完成式异步 I/O（如 `io_uring`/IOCP） |
| 拥有成熟自建缓冲池的专业数据库 | 经过严格对齐与实测的直接 I/O |
| 极致低延迟、愿意烧独占核心的专网 | 受控忙轮询或中断—轮询混合模式 |

到现在为止，我们已经摸清了应用程序怎样向内核交托读写任务、设备驱动又怎样借 MMIO 向硬件发号施令。可还有一个核心问题悬在半空：当高速固态硬盘或万兆网卡每秒吐出几个 GB 的海量数据时，真的是靠昂贵的 CPU 一条指令接一条指令地把几十亿个字节逐一搬进内存的吗？如果交给设备自己搬，万一一个流氓硬件顺手把内核内存写坏了又该怎么拦？带着这两个问题，我们立刻深入硬件传输的腹地——[下一篇：中断、DMA 与缓存层次](04_interrupts_dma_cache.md)。

## 自测

1. 很多人把“非阻塞 I/O”和“异步 I/O”混为一谈，用两句话说清它们的本质分界线。
2. 使用 `epoll` 的**边缘触发（ET）**模式时，为什么几乎总是要求把非阻塞 `fd` 一直循环读到返回 `EAGAIN` 为止？
3. 启用**直接 I/O（`O_DIRECT`）**后，一次文件读取究竟绕过了哪一层，又依然必须经过哪些层？
4. 编写设备驱动读写 MMIO 设备寄存器时，为什么不能直接拿一个普通指针（哪怕加了 `volatile`）当普通内存读写？
5. 既然 `epoll` 已经能让单线程轻松扛住十万并发连接，为什么高并发服务里依然必须严格设计背压？

??? note "参考思路"

    1. **非阻塞**说的是“单次调用当下没数据时不让线程睡眠，立刻返回暂不可用”，后续仍由应用自己主动再次读取；**异步**说的是“把整个读取请求和目标缓冲区委托给内核就继续干活，等内核与硬件彻底把数据搬完后发来完工通知”。
    2. 边缘触发只在缓冲区状态发生“从空变有”等跳变瞬间通知一次；如果你只读了一半，剩下的旧数据不会再触发第二次边缘通知，不一次性读到 `EAGAIN` 就会把残留数据一直闷在缓冲区里饿死。
    3. 直接 I/O 主要绕过了内核的**页缓存**；但它依然要经过系统调用、VFS、权限与文件块映射、块层队列、设备驱动、DMA 传输以及硬件中断完成路径。
    4. 硬件寄存器对访问宽度、大小端、禁止 CPU 缓存以及跨指令内存屏障顺序有严格要求；普通指针甚至 `volatile` 既挡不住 CPU 乱序执行，也无法保证缓存一致性与平台特定的总线访问语义。
    5. 多路复用只是省掉了线程空等的开销，并没有把内存条或下游数据库变成无限大；如果上游源源不断涌入请求而下游消化不掉，没有背压限流就会迅速把接收队列和内存撑爆、拖垮尾延迟直至 OOM 崩溃。
