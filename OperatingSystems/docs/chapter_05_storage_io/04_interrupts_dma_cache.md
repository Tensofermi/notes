# 中断、DMA 与缓存层次

## 每秒几个 GB 的数据，难道要 CPU 一字节一字节亲手搬吗？

插上一块高速 NVMe 固态硬盘或者万兆网卡，每秒钟涌入内存的数据轻轻松松达到几个 GB。如果按照最老实的办法，让每颗造价昂贵、主频数 GHz 的 CPU 核心一条指令接一条指令地从设备寄存器里读出 4 字节、再存进内存、再读 4 字节……整颗处理器几乎什么正经业务都干不了，全沦为了一个只顾低头搬砖的廉价搬运工！

硬件设计师给出了一个漂亮的“外包方案”：CPU 只当包工头——通过设备驱动提前在内存里划好一片**接收缓冲区**，写好一张清单告诉设备控制器“要读磁盘哪一块、搬完放到内存的哪个地址、一共多少字节”，然后拍拍手转身去跑别的应用程序！真正把几兆字节从硬件搬进内存条的苦力活，全权外包给设备自带的控制器芯片绕开 CPU 自己走总线完成。这套硬件直接读写主存的机制，就是**直接内存访问**（direct memory access，**DMA**）。等设备干完活，再拉响中断（或写好完工回执）通知 CPU 上场收尾。

??? question "CPU 刚刚把 DMA 读取清单交给了硬盘，能不能下一行代码立刻就去读接收缓冲区里的数据？"

    绝对不行！下单成功只代表“搬运工刚刚领到任务单”，此时磁盘里的字节可能还在半路上，接收缓冲区里躺着的还是上次剩下的旧垃圾，或者刚写了一半的残缺内容。程序必须乖乖等到设备发出完工通知，并完成驱动与平台规定的缓存同步后，才能安全读取缓冲区里的最新数据。

记住一个清醒的认知：**DMA 帮 CPU 省掉的是逐字节拷贝的体力活，绝不是让 I/O 变成零 CPU 消耗**——准备缓冲区、填写描述符、做地址映射、响中断后回收资源以及走上层协议栈，依然样样都要花 CPU 力气。这一篇，我们就顺着“怎么搬、怎么报信、怎么防设备乱写内存、数据中途停过几层缓存”四站，把软硬件交界处彻底照亮。

## 数据搬运的三代演进：从 PIO 到 DMA

回顾计算机外设接口的历史，数据从设备进内存走过了三个台阶：

1. **程序控制 I/O（Programmed I/O，PIO）**：CPU 亲自循环读写设备状态寄存器和数据寄存器，一个字节或一个字地亲手搬。电路最简单，适合敲一下只传几个字节的老式串口或极少量控制命令，一碰大文件立刻把 CPU 拖死。
2. **中断驱动 I/O**：CPU 不再死盯着设备状态空转，发出命令就先去干别的，等设备准备好一小批数据发来硬件中断再回来搬。虽然省了盲等，但每搬几十字节就得打断一次 CPU，高吞吐下照样会引发灾难性的中断风暴。
3. **DMA（直接内存访问）**：驱动提前备好内存缓冲区和任务清单，设备控制器化身“总线主设备”亲自批量搬运成千上万字节，整批搬完才只通知 CPU 一次：

```text
CPU 驱动准备好内存缓冲，在队列里写好任务描述符
  -> 敲一下设备寄存器（按“门铃”）通知设备开工
  -> 设备控制器自己读取描述符
  -> 设备走 DMA 直接把海量数据搬进主存
  -> 设备写回“已完工”状态
  -> 发硬件中断（或等 CPU 轮询发现）
  -> CPU 驱动回收描述符，唤醒上层等待线程
```

## 驱动和硬件如何默契交接？描述符环

高速网卡和 NVMe 固态硬盘每秒要吞吐几十万甚至上百万次读写请求，CPU 和硬件芯片之间怎么交接这么多任务单，才不会为了抢一把锁堵成一团？

工业界通用的优雅数据结构叫作**描述符环**（descriptor ring）——一块位于主存中、由驱动和设备共同读写的环形队列（通常成对出现：一条“提交环”加一条“完成环”）：

- **提交阶段**：驱动把空闲接收缓冲区的物理/总线地址、长度和控制标志填进提交环的下一个空槽里，随后更新“尾指针（tail）”并按一下设备的 MMIO 门铃寄存器；
- **执行阶段**：硬件控制器看到尾指针前进了，顺次取出描述符执行 DMA，把数据搬进对应内存后，在完成环里记下“第几号任务成功/出错、实际搬了多少字节”；
- **回收阶段**：驱动批量读出完成环里的回执，把数据递给上层协议栈或文件系统，再把空出来的槽位补充上新的缓冲区。

这里藏着驱动开发里最致命的内存序暗礁：**驱动必须先通过内存写屏障确保描述符里的地址和长度全部稳稳落进内存，最后一步才能更新尾指针并按门铃！** 只要编译器或 CPU 乱序把“按门铃”提前了半步，硬件控制器就会兴冲冲地读出一张只填了一半地址的半成品描述符，一头把 DMA 数据写到莫名其妙的非法内存地址里，当场掀翻整台机器！

## 中断风暴怎么治？分层处理、中断合并与轮询混合

假设一块万兆网卡每秒涌进 50 万个小数据包。如果每收到 1 个包就拉响 1 次硬件中断，设每秒事件率为 $r$，每次进出中断的固定耗时为 $c_i$，光应付“敲门进内核再退出”这一项固定开销就要吞掉：

$$
CPU_{interrupt}=r c_i.
$$

就算每次中断只花 2 微秒，$500{,}000 \times 2\ \mu\text{s} = 1\ \text{秒}$——**一整颗 CPU 核心 100% 的时间全花在应付敲门上了，一个正经数据包都来不及处理！** 系统彻底陷入“活锁式中断风暴”。

为了治服高吞吐设备的疯狂敲门，现代操作系统联手硬件使出了三记组合拳：

1. **快慢分层处理**：中断响起后的快速上半部只干最急的几件事——确认来源、记下状态、暂时屏蔽该设备后续中断、把后续繁重工作排进延后队列然后立刻撤退；真正成批拆包、走协议栈、唤醒线程全留给延后下半部在允许调度的环境下从容处理。
2. **中断合并（Interrupt Coalescing）**：告诉网卡或硬盘控制器“别每搬完 1 个包就急着响铃，**攒够 32 个包或者等满 50 微秒**再统一拉一次铃！”。这么一攒，中断次数瞬间砍掉几十倍，吞吐飙升；老规矩——代价是排在批次最前面的第 1 个包得多等几十微秒才被处理。因此现代网卡大多支持自适应合并：低流量时来一个就响保低延迟，高流量时自动攒批保吞吐。
3. **中断与轮询混合模式（如 Linux 网络的 NAPI）**：低负载时靠中断静静待命，省电不空转；一旦流量涌来触发第一声中断，内核果断**临时关掉这个设备的中断**，自己转入高效轮询循环一口气从完成环里连续收割几百个包，直到把环里的存货全清干净，再重新把中断打开！你看，中断和轮询从不是“谁先进谁落伍”，而是按事件到达频率动态切换的最优解。

## DMA 缓冲区的五大铁律与缓存一致性

把一块内存地址交给硬件设备做 DMA，比交给普通 C 函数苛刻得多。驱动必须通过操作系统专用的 DMA 映射 API 严守五条铁律：

1. **绝不能传普通用户虚拟地址**：设备挂在 PCIe 总线上，看不懂 CPU 进程页表里的虚拟地址，它只认总线地址或 I/O 虚拟地址；
2. **页面必须牢牢钉死在物理内存里（Pinned）**：传输期间绝对不许被虚拟内存子系统换出到磁盘，也不许被内存整理搬到别的物理页框——否则设备还在往老地址狂写数据时，那块物理页早已易主了；
3. **生命周期必须覆盖整个传输**：绝不能把函数里一个随时会销毁的局部栈变量地址扔给设备做异步 DMA；
4. **对齐与长度符合硬件胃口**；
5. **妥善处理 CPU 缓存一致性**。

第 5 条在嵌入式与 ARM 平台上尤其容易踩雷！在 x86 服务器上，硬件电路大多自动保证 DMA 与 CPU 缓存一致（Cache-Coherent），驱动只需管好内存屏障顺序；但在不少非硬件一致的 ARM/嵌入式板上，设备直接读写主存绕过了 CPU 的 L1/L2 Cache：
- CPU 刚往发送缓冲区写完数据、准备交给网卡发走前，如果数据还捂在 CPU 脏缓存里没冲回主存，网卡就会把主存里的陈年旧数据发出去——驱动必须先**把脏缓存刷回主存（Clean / Flush）**；
- 网卡通过 DMA 把新收到的网络包写进主存后，CPU 缓存里可能还留着这块地址的旧值——驱动在读新包前必须先**把旧缓存行作废（Invalidate）**，逼 CPU 从主存读最新字节！

## 给硬件设备戴上“手铐”：IOMMU 安全围栏 { #iommu }

想一个细思极恐的安全问题：前面我们费尽心思用 CPU 特权级和 MMU 页表把普通进程关得死死的，可 **DMA 允许外设绕开 CPU 直接读写物理内存**！万一电脑上插了一块有 bug 的廉价网卡、一根伪装成扩展坞的恶意雷电（Thunderbolt）外设，或者虚拟机里直通了一块物理设备——它只要瞎填一个 DMA 目标地址，岂不是能轻轻松松把整台宿主机内核的密码全偷走、把内核代码篡改个底朝天？

为了给外设也装上一道像 CPU MMU 一样的硬件门禁，现代平台在设备总线和主存之间架起了一颗专用守护芯片——**输入输出内存管理单元**（Input-Output Memory Management Unit，**IOMMU**）：

- 设备发出的不再是赤裸裸的物理地址，而是**I/O 虚拟地址（IOVA）**；
- 只有操作系统内核有权配置 IOMMU 里的设备页表，严格规定“这块网卡此刻只准读写这 4 个获批的物理页框”；
- 一旦故障或恶意设备敢伸手越界碰哪怕 1 字节未授权的物理内存，IOMMU 当场拦截封杀并向内核报警！

IOMMU 一举带来三大红利：**DMA 安全隔离**、**安全地把物理显卡/网卡直通给虚拟机**（第 9 章会再次见到它），以及**把物理上零碎分散的内存页拼成设备眼里连续的一整块虚拟区**。当然，IOMMU 自己也是页表翻译，同样配有硬件翻译缓存——**IOTLB**；内核在解除 DMA 映射后也得刷新 IOTLB，因此高性能驱动往往通过批量映射、复用缓冲区池或大页来压低 IOMMU 的管理开销。

## 别再把所有“缓存”混为一谈：五层缓存全景图

读到这里，你已经在整本书里见过太多次“缓存”这个词了。把它们从 CPU 芯片一路排到硬盘介质底端，五层分工瞬间一清二楚：

| 缓存层次 | 缓存的究竟是什么 | 谁在管它 | 断电后还在吗 |
| --- | --- | --- | --- |
| **CPU Cache（L1/L2/L3）** | 最近访问的内存缓存行 | CPU 硬件 | 否（易失） |
| **TLB / IOTLB** | 虚拟地址到物理地址的翻译项 | CPU/IOMMU 硬件 + 内核 | 否（易失） |
| **操作系统页缓存** | 磁盘文件的热点数据页 | 操作系统内核 | 否（易失） |
| **设备控制器缓存** | 磁盘控制器暂存的待写/热块 | 硬件控制器固件 | 除非自带掉电电容，否则否 |
| **存储介质内部缓存** | 固态盘闪存映射表、SLC 写缓存等 | 磁盘主控固件 | 视介质与掉电保护设计而定 |

扫一眼最右边那一列，你就能彻底明白为什么写持久化存储那么棘手：应用程序调用 `write()` 返回时，数据大概率只停在**第 3 层（页缓存）**；就算内核把它发给了硬盘，硬盘控制器为了显得自己写得飞快，常常刚把数据收进**第 4 层（易失板载写缓存）**就抢先给内核回了“写完了”！真要保证拔掉电源数据也不丢，持久化刷盘指令（如 `fsync` + 磁盘 Flush Cache）必须穿透上面所有易失层，直达最底端的非易失介质。

## 榨干流水线的两招经典硬件技巧

### 1. 双缓冲（Double Buffering）

如果只有一块缓冲区，设备往里 DMA 搬数据时 CPU 只能干瞪眼等，CPU 算数据时设备又只能闲着发呆。备上 A、B 两块缓冲区，两条产线立刻就能严丝合缝地并行起来：

```text
第 1 拍：设备 DMA 填满 buffer A   ||  CPU 正在处理上一轮的 buffer B
第 2 拍：设备 DMA 填满 buffer B   ||  CPU 正在处理刚填好的 buffer A
```

在稳态流水线下，整条系统的理论最大吞吐由两个环节里较慢的那一只木桶短板决定：

$$
throughput\le\min(throughput_{device},throughput_{cpu}).
$$

继续多加几块缓冲（变成环形多缓冲）确实能更好吸收瞬时抖动，但缓冲越深，单条数据在队列里干等的时间越长、占的内存越多，最终还是得靠背压封顶。

### 2. 分散—聚集 I/O（Scatter-Gather DMA）

还记得第 5 章分页吗？程序眼里连续的 64 KiB 大缓冲区，落到物理内存条上往往散落在 16 个互不相邻的 4 KiB 页框里！早年老式 DMA 笨得只能搬物理连续的一整块，逼得内核每次传输前还得先把 16 个零碎页先拷贝拼进一块连续临时内存里，白白浪费带宽。

现代硬件普遍支持**分散—聚集**（scatter-gather）DMA：驱动只需把这 16 个零碎页各自的物理地址和长度串成一张“段列表”递给设备，硬件控制器自己就能在一次 DMA 请求里顺着清单挨个扫完 16 块零散内存（读进来时自动“分散”填进各页，写出去时自动“聚集”拼成完整流），一字节都不用预先拼接拷贝！代价则是描述符更长、硬件对单次请求最大段数有限制、IOMMU 映射更琐碎。

## 真实硬件从不完美：驱动错误恢复与安全防线

教科书里的硬件总是乖巧听话，可真实机房里的硬盘会突然卡死不回中断、PCIe 总线会爆出校验错、U 盘会在 DMA 传到一半时被人一把拔走、固件偶尔会彻底失去响应。设备驱动最考验功力、也最容易藏并发死锁的地方，往往不在顺风顺水的正常读写，而在**错误恢复与热拔出重置路径**：必须立刻截停新请求、安全撤消或等待在途 DMA 结束、避免同一个描述符被正常中断和超时定时器重复回收两次，再把清晰的错误码传给上层。

安全上同样不能天真：绝不能假设硬件发回来的数据就一定可信。恶意或受损的固件、云环境里的半虚拟化设备完全可能往共享环里填入越界长度或伪造状态码；缺乏 IOMMU 防护时，失控设备更可能直接越界篡改内核内存。因此，驱动在解析设备吐出来的每一个长度和索引时，都要像校验用户输入一样保持警惕。

### 硬件 I/O 调优的核心权衡一眼看清

- **小批次 vs 大批次**：小批次延迟低，但每次都要付门铃寄存器写和中断的固定过门费；大批次吞吐爆表，却拉长队头等待延迟。
- **拷贝缓冲 vs 零拷贝固定页**：拷贝一份进内部缓冲生命周期最省心，却吃掉宝贵内存带宽；零拷贝直接把用户页钉死交给 DMA 省了拷贝，但内存固定、回收与并发修改的风险陡增。
- **纯中断 vs 纯轮询**：低负载下中断最省电优雅，高负载下容易引发中断风暴；轮询延迟极度稳健可控，闲着时却一直在烧核心耗电。

5. 应用程序调用普通 `write()` 成功返回后，数据在真正落盘前可能还停留在哪些易失性缓存层里？

??? note "参考思路"

    1. DMA 只省掉了 CPU 逐字节搬运数据的体力活；构造与回收描述符环、维护 DMA/IOMMU 地址映射、处理中断或轮询完成队列、拷贝到用户缓冲区、运行文件系统与网络协议栈，全都需要消耗 CPU。
    2. 外设挂在硬件总线上看不懂进程私有的 CPU 虚拟地址，它需要经过内核 DMA 接口映射出来的物理/总线地址或 IOVA；此外普通用户页在传输中途可能被换出或回收，且缺乏必要的缓存一致性与安全权限约束。
    3. 中断合并把多次完成攒成一次中断，大幅摊薄中断进入与退出开销，从而**提高高负载下的吞吐量**；但批次里先到达的包必须等待凑够数量或定时器到期才被处理，因此会**略微增加单包延迟**。
    4. 两者核心原理相同——都借助页表和硬件翻译缓存（TLB / IOTLB）把虚拟地址翻译成物理地址并实施严格权限拦截；区别在于 CPU MMU 管束的是**处理器核上运行的程序**，而 IOMMU 管束的是**发起 DMA 访问的外设硬件**。
    5. 依次可能停留在：用户态标准库缓冲区（若用了 `stdio`）、操作系统内核的页缓存、存储设备控制器的板载易失写缓存，以及部分介质内部的易失缓存中。
