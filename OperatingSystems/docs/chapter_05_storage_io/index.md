# 文件、文件系统与设备 I/O { #5-io }

## 从 `report.txt` 到磁盘磁道，中间隔着几重山？

打开电脑里的 `report.txt` 时，你只消给出一个好记的名字，就能像翻书一样从第 0 字节读到末尾。可硬盘和固态硬盘硬件其实根本听不懂什么叫“文件名”、什么叫“文件夹”，它们只认冰冷的数字编号——“请把第 1048576 号数据块里的 4096 个字节交出来”。

在“人好用的文件名”和“硬件只认的块编号”之间搭起整座桥梁的，就是**文件系统**（file system）；而程序与磁盘、键盘、网卡等外部设备之间交换数据的全套动作，统称为**输入/输出**（input/output，**I/O**）。为了不让飞快的 CPU 每次都苦等慢吞吞的存储设备，内核还会在内存里辟出一片区域缓存最近读过或写过的文件数据——这就是前文预告过的**页缓存**（page cache）。

本章的四篇文章像两条交织前行的铁轨，最终在收官篇合二为一：

```text
铁轨一（按名字找数据）：路径字符串 -> 目录项（名字到编号） -> inode（文件档案） -> 磁盘数据块
铁轨二（向设备搬数据）：系统调用 -> 检查页缓存 -> 块层排队 -> 设备驱动 -> DMA 与硬件中断
```

第一篇先把“名字、目录、文件档案与链接”这一整套文件系统骨架立起来；第二篇把目光转向应用程序与内核之间千姿百态的 I/O 等待姿势与设备驱动；第三篇钻进硬件底层，看清设备如何靠 DMA 自己把数据搬进内存并向 CPU 报信；最后在第四篇，我们用一行平平无奇的 `read(fd, buf, 4096)` 作为导游，把前几章学过的系统调用、调度睡眠、虚拟内存页缓存和本章的 VFS、驱动、DMA 与中断**串成一条从用户代码直达硬盘再凯旋而归的完整旅程**！

## 读完本章，试着自己回答

- 为什么说“文件描述符”只是当前进程里的一个小整数索引，而不是磁盘文件本身？
- 删除一个正被其他程序打开着的大日志文件，为什么 `df` 看到的磁盘空间半天没有释放？
- “阻塞 / 非阻塞”和“同步 / 异步”为什么是两组完全独立的维度？
- DMA 帮 CPU 省掉了逐字节搬运，可为什么高吞吐 I/O 依然会消耗不少 CPU？
- 同样是一行 `read(fd, buf, 4096)`，为什么第一次可能花掉几毫秒，紧接着第二次却只需几微秒？

## 排查性能前的一句忠告

线上遇到慢请求，最偷懒也最容易误判的结论就是脱口而出“肯定是硬盘太慢了”。一次 I/O 变慢，病根可能藏在冷缓存导致的多级路径解析、目录锁竞争、页缓存未命中、脏页回写积压、块层队列过深、驱动中断风暴，甚至应用程序自己每次只读 1 字节的糟糕访问模式里。顺着本章的层次逐站取证，才能一针见血揪出真正的瓶颈。
