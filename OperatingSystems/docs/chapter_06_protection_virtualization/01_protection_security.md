# 保护机制与系统安全

## 怎么让一个图片处理程序，眼里只看得见这一张图？

设想你的服务器每天要接收用户上传的几十万张图片，后台跑着一个开源缩略图程序把它们压缩存档。仔细想想：这个程序真正需要做的事简单到极致——从指定输入路径读入原图，算完后把缩略图写进指定输出目录。

可如果运维图省事，直接用全能管理员（`root`）账号把它跑起来，灾难的引信就已经点燃了：图片解码代码充斥着复杂的二进制字节解析，历史上最容易藏着缓冲区溢出漏洞。只要黑客上传一张暗藏杀机的特制图片打穿了解码器，攻击者瞬间就能顺着管理员身份把整台机器的数据库密码、私钥和系统配置搜刮一空！

反过来，按最小权限思路给它套上牢笼：先给它分配一个毫无特权的独立低权限用户身份；文件系统上只给输入目录开只读权、输出目录开写入权，其余目录一律大门紧锁；再问一句——它压根不需要连外网、也不需要碰磁盘设备，干脆把网络和设备访问权一并剥夺！从此操作系统会在每一次打开文件、发起系统调用的关口，死死核对它的身份与权限。

??? question "既然用户 A 自己拥有登录提交这个图片任务的权限，那平台干脆把用户 A 的全部账户凭据直接转交给这个任务进程，方便吗？安全吗？"

    方便确实方便，却极其危险！“谁有权提交任务”和“任务跑起来后需要碰哪些数据”是两回事。如果把用户 A 的全套凭据塞给一个跑着第三方解码库的任务，一旦解码库失守或代码写错路径，用户 A 名下所有无关项目的机密文件都会跟着遭殃。给具体任务签发独立的、范围收窄的最小运行身份，才能把爆炸半径牢牢锁死。

在系统领域，**保护机制**（protection）和**安全**（security）常并肩出现，但分工并不相同：保护机制决定“合法的参与者按什么规矩访问系统里的对象”，就像装在房门上精密的机械门锁；安全则是要在代码 bug、配置失误和蓄意攻击夹击下守住整套系统的承诺，就像守护整栋大楼的完整安保体系——门锁固然关键，可钥匙怎么保管、窗户关没关、监控录像有没有防篡改、出了盗窃怎么应急止损，缺一不可。这一篇，我们就从“门锁的结构”一步步讲到“整栋建筑的防线”。

## 先别问“安不安全”，先问“在防谁”：威胁模型与 CIA 三要素

工程师评审方案时，最无力的问题就是笼统地问“这系统安全吗？”没有前提就没有答案。动笔设计任何防线之前，必须先把**威胁模型**写清楚：
- 最核心要守住哪些资产（用户密码、财务账本、模型权重，还是服务不中断）？
- 假设攻击者站在哪条起跑线上（门外毫无权限的匿名网友、同一台服务器上的另一个租户、还是已经攻陷了某个前端进程的入侵者）？
- 哪些底层组件我们选择信任（比如 CPU 硬件、主板固件、宿主机内核）？
- 出了事最坏能承受什么代价，什么红线绝对不能破？

围绕威胁模型，信息安全通常守望三大目标（经典的 CIA 三元组）：
- **机密性**（confidentiality）：绝不让未获授权的人偷看到秘密内容；
- **完整性**（integrity）：绝不让未获授权的人偷偷篡改数据或劫持程序执行流；
- **可用性**（availability）：绝不让攻击者通过耗尽资源或搞垮服务，把合法用户挡在门外。

看清三者的边界能帮你避开很多幻觉：定期做异地备份能救回**完整性**和**可用性**，却救不回已经被黑客拷贝走的**机密性**；把硬盘全盘加密能防住偷硬盘的人，却防不住一个本就拥有解密权限、却被攻破的运行中服务把明文直接吐出去。

## 把“谁能碰什么”摊在桌面上：访问控制矩阵、ACL 与 Capability

要把五花八门的权限规则统一到一个清晰模型里，只需记住三个角色：发起操作的人或进程叫**主体**（subject），被操作的文件、端口或设备叫**客体**（object），某个主体当下握有的那整套权限集合叫作它的**保护域**（protection domain）。

把所有主体排成行、所有客体排成列，画成一张大表格，这就是经典的**访问控制矩阵**（access control matrix）：

| 主体（谁） | 配置文件 | 日志文件 | 网络端口 |
| --- | --- | --- | --- |
| Web 服务进程 | 只读 | 只写 | 监听 443 |
| 运维工具 | 读写 | 只读 | 管理端口 |
| 普通用户 | 无权限 | 只读自己的 | 无权限 |

真在操作系统里存这么一张几十万行乘以几百万列的巨型稀疏二维表，内存立刻爆炸。于是现实系统把这张矩阵按“列”或按“行”劈开，长出了两种截然不同的权限实现流派：

### 按“列”切：访问控制列表（ACL）

站在**客体（文件）**这一边，在每个文件旁边挂一张小名单，写明“谁能对我做什么”——比如 `config.yaml` 旁挂着 `Web服务: 读; 运维工具: 读写`。这就是**访问控制列表**（Access Control List，**ACL**；传统 Unix 的 `rwx` 属主/属组/其他人九个权限位，就是一种极度精简的 ACL）。
- **好在哪儿**：查“到底有哪些人能看这份机密文件”一眼看穿，给文件改权限也直观；
- **难在哪儿**：一旦某位员工离职，想“彻底收回他在全系统里的所有权限”，就得满磁盘把成千上万个文件的名单翻个底朝天。

### 按“行”切：能力凭证（Capability）

反过来，站在**主体（进程）**这一边，给进程发一串不可伪造的专属通行证（类似带印章的房卡），每张卡上同时写着“指向哪个对象”和“允许什么操作”——例如发给 Web 服务一张“只读 `config.yaml`”的凭证。这种把对象引用与访问权合二为一的凭证叫作 **capability**。
- **好在哪儿**：天然契合最小权限与组件化——父进程只把具体哪两张卡递给子进程，子进程连其他文件的存在都摸不着；而且可以安全地委托权限，天然免疫“糊涂的代理人（Confused Deputy）”攻击；
- **难在哪儿**：凭证绝不能让用户伪造（通常由内核代管），而且一旦凭证被进程转手传了出去，将来想精准追踪并中途吊销它会比改 ACL 棘手得多。

回头看看第 6 章学过的**文件描述符（`fd`）**，你会有种豁然开朗的惊喜：`open()` 查路径权限时走的是 **ACL** 风格，可一旦打开拿到 `fd`，这枚 `fd` 本身就成了一枚由内核代管的 **capability**——哪怕文件随后换了路径甚至删了名字，拿着 `fd` 的进程依然能按当初打开时的只读/只写权限继续访问，还能通过 Unix 套接字把它转交给另一个进程！

## 自主访问控制（DAC）与强制访问控制（MAC） { #mac }

传统桌面和 Linux 上，如果你建了一个属于自己的文件，你就可以随手执行 `chmod 777 secret.txt` 把它向全机器敞开大门——这种“由对象所有者自己说了算”的模型叫作**自主访问控制**（Discretionary Access Control，**DAC**）。DAC 灵活顺手，却有一个致命软肋：只要进程以你的身份运行、或者你不小心配宽了权限，哪怕是一个不怀好意的第三方小工具，也能凭着你的身份把你的私密文件全读走甚至改权限外泄！

为了堵住这条口子，高安全系统在 DAC 之上叠加了第二道铁闸——**强制访问控制**（Mandatory Access Control，**MAC**，如 Linux 里的 SELinux、AppArmor）。在 MAC 之下，**全系统由管理员统一制定凌驾于普通用户之上的铁律**：即便某个目录对所有用户都是可读的，MAC 策略依然可以死死规定“标记为 `thumbnail_worker` 的图片处理程序，绝对禁止触碰 `/etc/` 和用户主目录里的任何文件！”

DAC 管得宽容灵活，MAC 画得边界森严但策略编写与排错成本高得多——现代生产服务器往往让两者叠罗汉：先过 DAC，再过 MAC，缺一不可。

## 落地最小权限：把一个服务拆成“启动器 + 受限工人”

设想一个只提供静态网页、需要监听 443 端口的 Web 服务器。按旧习惯，因为传统 Unix 规定绑定 1024 以下的特权端口需要 `root`，整个服务器干脆一直顶着 `root` 跑——结果哪怕解析 HTTP 头的一个小函数出了漏洞，整台机器就沦陷了。

遵循最小权限的现代拆法干净利落：

```text
特权启动器（极简代码，只干初始化）
  -> 绑定 443 端口拿到监听 socket fd，打开必要日志与证书
  -> 立刻永久降权：切换为低权限普通用户、彻底丢弃所有管理能力
  -> 拉起受限工作进程（只读网页目录、只写日志 fd、只能操作已打开的 socket）
  -> 叠加系统调用白名单过滤与资源配额上限
```

这么一来，即使面向公网的复杂协议解析代码不幸被黑客打穿，攻击者落脚的也只是一个既改不了文件、又提不了权、连新建无关连接都做不到的逼仄小黑屋。落地最小权限真正的工程难点不在懂不懂道理，而在**精准盘点依赖**：权限收得太紧导致服务起不来时，千万别偷懒一键改成全权限，而应该在测试环境借助审计日志逐项放行真正必需的最小清单。

## 进大楼的三个独立关卡：认证、授权与审计

安全设计里常把下面三个词（常称 AAA）混为一谈，其实它们各守一道门：

- **认证（Authentication）**：“证明你确实是你宣称的那个人。”（靠密码、SSH 私钥、短期令牌或硬件安全密钥）
- **授权（Authorization）**：“就算确认你是张三，你到底有没有权打开这间机房？”
- **审计（Auditing）**：“把谁在什么时候、尝试或完成了什么敏感动作原原本本记进防篡改账本里。”

一定要牢记：**认证通过绝不等于获得全部授权！** 此外，存用户密码绝不能明文存放，也不能用 MD5/SHA-256 这类为了飞快而设计的普通哈希直接算（显卡每秒能暴力撞几十亿次），而必须用**带独立随机盐（Salt）的专用慢哈希算法**（如 Argon2、scrypt、bcrypt）。审计日志同样不能只记“谁成功进来了”，更要记清权限变更、关键配置修改与连续失败的试探，并且把日志实时送往被审计机器自己无法篡改的远端存储。

## 拆碎全能的 `root`：Linux Capabilities 与高危 SUID

早期 Unix 的权限模型过于非黑即白：要么是受尽约束的普通用户，要么是无所不能的超级用户 `root`。一个小小的 `ping` 命令仅仅需要发原始网络包，却不得不靠设置用户 ID 位（SUID）临时拿到整台机器的 `root` 最高神权——一旦 `ping` 解析命令行参数时出了缓冲区溢出，普通用户立刻原地变身 `root`！

现代 Linux 把全能的 `root` 神权像切蛋糕一样拆成了几十项细粒度的独立特权，同样命名为 **Linux capabilities**（注意区分：它指拆碎的管理员特权位，比如 `CAP_NET_BIND_SERVICE` 仅允许绑定低位端口，而前面讲的对象 capability 是指向具体对象的权限凭证）。现在一个 Web 服务只需领走 `CAP_NET_BIND_SERVICE` 这一小块蛋糕，再也不必顶着全能 `root` 裸奔了。至于历史遗留的 SUID 程序，因其极易被环境变量、符号链接和参数注入攻破，现代架构应尽量用拆细的 capabilities 或独立低权守护进程取而代之。

## 把唯一的大门收窄：系统调用过滤与沙箱

回想第 1 章我们反复强调的那句话：**用户态程序要想碰文件、连网络、建进程，系统调用是通往内核的唯一正门！**

既然所有请求都得过这道门，那如果我们给一个纯计算或纯文本解析进程在门口架上一道“安检白名单”——只允许它调用 `read`、`write`、`exit` 和申请内存这寥寥几个系统调用，一旦它敢偷偷调用 `execve` 起 Shell 或 `socket` 连外网，内核当场拦截击毙它！这就是 Linux `seccomp` 等系统调用过滤技术的威力。

把多道收紧措施组合在一起，为一个程序量身定制出的受限隔离牢笼，就叫作**沙箱**（sandbox，比如浏览器为每个不可信网页标签页建的渲染沙箱）。一个扎实的沙箱通常多层联防：
- 独立且极简的用户与文件系统视图；
- 页表隔离、只读映射与不可执行内存（W^X）；
- 借助下一章要细讲的[控制组（cgroup）](02_virtual_machines_containers.md#cgroup)锁死 CPU、内存与进程数上限；
- 精细的系统调用号与参数过滤（`seccomp`）；
- 强制访问控制（MAC）标签与严格网络出入口策略。

但务必清醒：**套上沙箱绝不是一劳永逸的免死金牌**——白名单开得太宽、不小心把宿主机敏感目录挂进了沙箱，或者共享的底层内核本身存在提权漏洞，都可能成为攻击者“沙箱逃逸”的密道。

## 内存攻防战：常见漏洞缓解与纵深防御

由于 C/C++ 等底层语言允许直接操控原始指针，内存越界、释放后使用（Use-After-Free）几十年来一直是系统漏洞的头号来源。现代操作系统、编译器和硬件联手在漏洞被触发后的“利用链”上埋下了层层绊马索：

- **不可执行页（NX / DEP）**：第 5 章见过的 W^X 原则，让栈和堆只能存数据不能当指令跑，直接废掉了“往缓冲区塞一段机器码再跳过去执行”的古典招数（不过高阶攻击者随后发明了拼凑程序里现有代码片段的 ROP 攻击，因此仍需配合后续防线）；
- **地址空间布局随机化（ASLR）**：每次启动随机打乱代码、库、堆和栈的地址，让攻击者找不到跳转坐标（但一旦遭遇信息泄漏漏洞吐出地址就可能被绕过）；
- **栈哨兵（Stack Canary）与控制流完整性（CFI）**：编译器在函数栈帧的返回地址前面偷偷埋一个随机秘密数值（像矿井里的金丝雀），函数返回前核对它有没有被缓冲区溢出踩脏，一脏立刻自杀终止进程；CFI 则进一步核查每一次间接函数跳转是不是落在合法目标集合里；
- **内存安全语言与边界检查**：从源头上改用 Rust、Go、Java 等内存安全语言，能成片消灭越界写和释放后使用——但别忘掉跨语言调用（FFI）、逻辑越权漏洞和资源耗尽攻击依然需要系统边界兜底。

这正是安全工程里著名的**纵深防御（Defense in Depth）**：绝不指望哪一道银弹百毒不侵，而是把防线一层层叠起来，就算外墙被捅破，内墙依然能把攻击者挡死。

## 安全边界上的并发幽灵：TOCTOU { #toctou }

还记得第 4 章的竞态条件和[第 6 章文件一章](../chapter_05_storage_io/01_files_directories_inodes.md)埋下的伏笔吗？安全检查和业务使用如果不原子，就会裂开一条极其凶险的漏洞——**检查时与使用时竞态**（Time-of-Check to Time-of-Use，**TOCTOU**）：

```text
第 1 步（检查时）：特权程序检查路径 /tmp/upload/a.txt -> 确认它是普通用户文件，安全！
第 2 步（抢占窗口）：攻击者闪电般删掉 a.txt，换成指向 /etc/shadow 的符号链接！
第 3 步（使用时）：特权程序按路径 open("/tmp/upload/a.txt") -> 实际打开了系统密码文件！
```

只要你的代码在“检查”和“使用”之间依赖了**随时可能被别人偷梁换柱的可变名字（路径字符串）**，TOCTOU 就永远阴魂不散。治本之策是把操作锚定到**不可掉包的内核对象句柄**上：先打开受控目录拿到稳定的目录 `fd`，随后用 `openat`、`fstat` 等基于 `fd` 的接口配合 `O_NOFOLLOW`（禁止跟随符号链接），把检查和使用严丝合缝地锁在同一个稳定对象上。

## 启动信任链与看不见的暗道：侧信道

把视野往底层硬件再探一步，还会遇到两类极具分量的安全议题。

第一是**从通电那一秒开始的信任链**：第 1 章提到的安全启动（Secure Boot）让主板固件用固化公钥验证引导程序签名，引导程序再验证内核签名，环环相扣防止有人离线往硬盘里偷偷塞进木马内核（Bootkit）。但要分清签名能证什么、不能证什么：**数字签名只证明“这段代码确实出自可信签发者且没在半路被篡改”，绝不证明“这段代码里没有安全漏洞”！** 签了名的软件照样需要运行期最小权限和及时打补丁。

第二是防不胜防的**侧信道**（side channel）攻击：哪怕你把页表隔离、文件权限、沙箱过滤全都锁到了极致，不许攻击者走任何一道正门去读秘密数据，攻击者依然可能贴在墙外“听墙根”——通过精准测量共享 CPU 缓存访问快了 20 纳秒还是慢了 20 纳秒、探测分支预测器的历史残留、甚至分析芯片功耗和电磁波动，一点点把同一颗处理器上另一个进程正在使用的加密密钥反推出来！这就是近年来震动整个计算机界的熔断（Meltdown）与幽灵（Spectre）类微架构攻击。堵住侧信道（例如核心隔离、刷缓存、写常数时间密码算法、敏感负载不与陌生租户共驻同一物理机）往往伴随着高昂的性能代价，因此同样需要严格对照威胁模型做权衡。

## 守住“可用性”与生命周期：资源控制与持续运维

安全绝不只是防偷看和防篡改——如果一个恶意请求连发一万次 `fork()`（著名的 Fork Bomb）把机器的进程表打满，或者上传一张解压后膨胀成 100 GB 的“压缩炸弹”吃光全部内存，整台机器陷入死机，你的**可用性**防线就已经彻底失守了。

因此，一套完整的安全防线必须同时框死所有共享资源瓶颈：最大进程数、打开文件数上限、内存硬上限、CPU 与 I/O 带宽份额、有界请求队列和超时熔断，并且为关键的运维控制面预留救命容量。

最后，请接受一条冰冷但务实的工程真理：**这世界上不存在永远零漏洞的完美系统。** 可维护性与快速响应能力本身就是核心安全属性——清晰的软件资产清单、能迅速上线且支持一键回滚的补丁机制、定期轮换密钥与快速吊销凭证、完善的防篡改告警审计，以及定期真实演练的离线备份恢复，共同决定了被攻破时是一场虚惊，还是一场毁灭性灾难。

到现在为止，我们已经学会了在同一台操作系统内部，怎样用身份、权限、MAC、能力拆分与沙箱过滤，把单个程序能做的事情一步步收紧。

可有时候，这种“大家住在同一栋大楼、靠门锁和规矩互不侵犯”的做法还是让人不放心——尤其是当两个完全独立的团队、甚至两个互不信任的付费租户要共用同一台昂贵的物理服务器时，有人还想自己装一套完全不同的操作系统内核、自由重启自己的机器！此时，我们想做得更彻底：**干脆把一台物理服务器，在逻辑上切分出好几台“看起来完全独立的电脑”！** 硬件和操作系统究竟如何做到让客体系统深信自己独占裸机（虚拟机），又如何在共享同一套内核的前提下切出轻盈的隔离视图（容器）？带着这些问题，进入[第 9 章 从裸机到虚拟机](02_virtual_machines_containers.md)！

## 自测

1. 访问控制列表（ACL）和能力凭证（Capability）各自是从哪个维度切分“访问控制矩阵”的？二者在“查谁能访问某文件”和“撤销某用户全部权限”上各有什么优劣？
2. 为什么说“用户登录认证成功”，绝不自动意味着他被授权读取服务器上的任意文件？
3. 不可执行页（NX）和地址空间布局随机化（ASLR）都极大地提升了系统安全性，为什么它们只能称为“漏洞缓解措施”而不能算“漏洞修复”？
4. 安全启动（Secure Boot）的逐级签名验证能向你证明什么？又绝对不能向你证明什么？
5. 回到开篇的图片缩略图服务，实施“最小权限原则”具体是怎样缩小解码库内存漏洞的破坏半径的？

??? note "参考思路"

    1. ACL 按客体（列）组织，记录在文件旁，查询“谁能碰这个文件”非常快，但撤销某个主体在全系统的权限需要遍查所有客体；Capability 按主体（行）组织，由主体持有指向对象的凭证，天然契合最小权限与受控委托，但追踪和跨进程撤销已分发出去的凭证更复杂。
    2. 认证只回答“你是谁”，授权是独立的下一步判断——回答“这个身份允许对哪个对象执行什么操作”。两者混为一谈会直接摧毁最小权限边界。
    3. 它们并没有消除源代码里的越界写、释放后使用等根本缺陷，只是提高了攻击者稳定利用漏洞执行恶意代码的门槛；一旦遇到信息泄漏或代码复用（ROP）技巧，漏洞仍可能被绕过利用。
    4. 它能证明每一棒加载的引导程序和内核来自受信任的签发者且未经离线篡改；但不能证明这些已签名的代码本身没有 bug 或安全漏洞，也不能替代运行期的权限隔离与及时打补丁。
    5. 通过剥夺管理员身份、只开放输入目录只读和输出目录只写权限、关闭无关网络与系统调用，即使黑客利用畸形图片打穿解码进程，也只能受困在这个极小沙箱里，无法读取其他项目的机密数据或篡改系统配置。
