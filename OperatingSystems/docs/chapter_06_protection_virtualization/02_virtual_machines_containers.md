# 虚拟机与容器

## 同一台服务器、同一个 8000 端口，两个团队怎么互不干扰地共存？

假设机房里只有一台空闲的 64 核 Linux 服务器，却同时来了两个团队要资源：甲组要上线新版 Python 网页服务，乙组则要测试一套老旧操作系统的内核升级。两组都希望各自独占一套互不相干的磁盘文件、互不冲突的系统依赖库，而且偏偏都要在编号 **8000** 的网络入口等待客户端发来请求（让程序守在某个端口编号上接听外部连接，叫作**监听端口**，listen on a port）。

最土豪的办法当然是给每组各买一台独立物理机——既烧钱，又经常出现两台机器的 CPU 大半天都在 10% 以下打盹的巨大浪费。于是，**虚拟化**（virtualization）登场了：它把一套共享物理硬件，切分出多个彼此隔离、仿佛独立存在的运行环境。

但“切蛋糕”有粗有细，两条截然不同的路线就摆在眼前：
- 乙组需要自己安装、配置甚至随时重启一整套独立的操作系统内核，于是给它切出一台**虚拟机**（virtual machine，**VM**）——底层替它变出一套完整的虚拟 CPU、虚拟内存和虚拟硬盘；
- 甲组只需要跑在现成的 Linux 内核上，只要文件视图、端口视野和资源配额彼此隔离就够了，于是给它装进一个轻盈的**容器**（container）——直接共享宿主机同一个内核，却让里面的程序以为自己独占了一台主机！

为了把两条路线的本质差异彻底看透，下面我们拿着同一个网页服务发出的同一行 `read("/app/index.html")`，放到裸机、容器、虚拟机三种环境里挨个照镜子。

## 跟着一次 `read()`，看清“第一道内核边界”落在谁手里

先认清三个贯穿全篇的角色名：插着真实 CPU 和内存条的物理服务器叫**宿主机**（host）；直接在物理机上运行系统、没有虚拟化夹层的环境叫**裸机**（bare metal）；跑在虚拟机里、以为自己独占硬件的那套独立操作系统叫**客体**（guest）。

现在，网页服务调用 `read()` 读取 `/app/index.html`：

| 程序跑在哪种环境 | 谁第一个接住 `read()` 系统调用 | 谁最终指挥物理硬盘干活 |
| --- | --- | --- |
| **裸机上的普通进程** | 本机唯一 Linux 内核 | 本机内核里的真实磁盘驱动 |
| **Linux 容器** | **同一个宿主机 Linux 内核**（只是按容器的文件视图和权限规则校验） | 宿主机内核里的真实磁盘驱动 |
| **虚拟机** | **客体自己的独立内核**；如果客体页缓存里没有，客体内核向自己看到的“虚拟磁盘”发读请求 | 宿主机侧的**设备后端**（device backend）截获虚拟盘请求，再替它向宿主机真实硬盘发起读取 |

盯紧中间那一列，整篇最核心的分水岭已经一目了然：**容器里的进程发出的系统调用，一脚就踩进了宿主机内核里；而虚拟机里的进程发出的系统调用，先踩进的是客体自己独立的内核！**（当然，只要对应的内核[页缓存](../chapter_05_storage_io/01_files_directories_inodes.md)里还留着热数据，两种环境照样都能省去真实磁盘读取。）

正因虚拟化带来了服务器合并提效、强租户隔离、环境打包迁移、运行异构老内核与一致部署等巨大红利，它才成了整个云计算时代的基石。但老规矩——**隔离越彻底，付出的内存、转换和仿真账单往往越高；共享越多，启动越快密度越高，但共享同一个故障域的风险也越大。**

## 拆开一台虚拟机：谁在幕后“扮演”物理硬件？

虚拟机里的客体操作系统从按下“虚拟电源键”那一刻起，就深信自己运行在一块真实主板上：它会像第 1 章那样跑固件引导、建自己的页表、初始化自己的中断表和设备驱动。可这一切究竟是谁在幕后演给它看的？

```text
+------------------------------------------+
|            客体里的应用程序               |
+------------------------------------------+
|           客体操作系统内核                |
+------------------------------------------+
|   虚拟 CPU (vCPU) / 虚拟内存 / 虚拟设备    |
+------------------------------------------+
|   虚拟机监控器（VMM / Hypervisor）        |
+------------------------------------------+
|            宿主机物理硬件                 |
+------------------------------------------+
```

居间扮演“虚拟主板”并掌管底层物理硬件分配的软件核心，叫作**虚拟机监控器**（Virtual Machine Monitor，**VMM**，也常称 **Hypervisor**）。客体眼里看到的处理器叫**虚拟 CPU（vCPU）**——在宿主机视角里，vCPU 就像一条普通线程，宿主机调度器可以让它在一颗物理核心上跑几毫秒，再把同一颗物理核心换给另一台虚拟机的 vCPU。

从启动过程就能直观感受到虚拟机与容器的体量差别：拉起一台虚拟机，宿主机得先为它划出一片专属内存、配好虚拟盘，然后客体老老实实走完一遍完整的固件引导、内核初始化和系统服务拉起；而拉起一个容器，宿主机内核早已醒着，几乎只需建好隔离视图就能直接执行应用进程！

按部署位置，传统教材把 Hypervisor 分为直接裸跑在物理硬件上的 **Type 1**（如 Xen、VMware ESXi）和作为普通软件跑在宿主操作系统之上的 **Type 2**（如 VirtualBox）。但在现代架构里（最典型的是 Linux **KVM**——把 Linux 内核自己直接变成了一个高权限 Hypervisor），两类界线早已交融；比起纠结标签，更值得弄清的是 **CPU、内存和设备这三座大山究竟是怎么被虚拟出来的。**

## 第一座大山：CPU 虚拟化——“直接跑，遇到敏感动作就交棒”

最傻的虚拟化方式是用软件逐条解释执行客体的每一条机器指令——慢上几十上百倍，根本没法用。现代虚拟机之所以能跑出接近裸机 95% 以上的计算速度，靠的是硬件辅助的**陷入与模拟**（trap-and-emulate）：

- **绝大多数普通计算指令（加减乘除、循环、访存）直接扔给物理 CPU 原生全速执行！** 一丁点解释开销都没有；
- 只有当客体试图执行**敏感或特权操作**（比如读写宿主机仿真的虚拟网卡寄存器、关掉整机物理中断、修改某些全局硬件控制位）时，CPU 硬件瞬间把客体暂停，把控制权从客体切回宿主机 VMM——这一次强制切出叫作 **VM exit**；VMM 查清客体想干什么，替它模拟出符合预期的结果，再通过 **VM entry** 把客体恢复运行！

举个具体例子：客体里的应用程序算一个整数加法，物理 CPU 直接全速算完，VMM 压根不用露面；应用程序发起普通 `read()`，CPU 先陷入**客体自己的内核**，若数据恰好在客体页缓存里命中，全程甚至一次 VM exit 都不会发生！只有当客体内核需要操作虚拟硬盘控制器寄存器、把请求发给宿主机设备后端时，才会触发一次 VM exit 惊动 VMM。

历史上，早期 x86 架构曾有个著名尴尬：有十几条敏感指令在低权限下执行时居然默默失败而不触发陷入（没法靠 trap-and-emulate 截获），逼得早年 VMware 等先驱硬是在运行期把客体内核的机器码动态扫描改写成安全指令序列（即**二进制翻译**）。后来 Intel（VT-x）和 AMD（AMD-V）干脆在芯片电路里新增了专门运行客体的“非根模式（Non-root mode）”并支持精准配置拦截清单，彻底终结了这个历史难题。

### 压低 VM exit 成本的三板斧

尽管硬件辅助让普通指令飞快，但每一次 **VM exit** 都要保存一整套 vCPU 硬件现场、切到 VMM 处理再恢复，耗时远超一次普通系统调用。如果客体驱动每发一个网络包都要读写十次虚拟寄存器、触发十次 VM exit，I/O 性能就会瞬间雪崩。工程上靠三招大幅削减退出频率：
1. **半虚拟化队列攒批**：改用知道自己身处虚拟机里的驱动，把几十个请求一起塞进共享环，只按一次门铃触发 1 次 VM exit；
2. **设备直通**：把物理网卡/显卡干脆直接交给客体自己管，彻底绕开 VMM 模拟；
3. **硬件虚拟中断直投**：让芯片硬件允许客体自己处理部分安全控制操作，减少无谓拦截。

## 第二座大山：内存虚拟化——套娃般的两阶段页表翻译

第 5 章我们算通了单机的一级翻译：应用发出的**虚拟地址**，经进程页表翻译成内存条上的**物理地址**。

可到了虚拟机里，客体操作系统自己也在煞有介事地维护页表！它以为自己分给客体应用的“物理页框 5”就是内存条上的第 5 号格子——可实际上，宿主机上同时跑着十台虚拟机，十个客体内核都宣称自己霸占了“物理页框 5”！

怎么让它们不撞车？答案非常优雅——**再叠一层翻译！** 现代 CPU 硬件支持两阶段地址翻译（如 Intel EPT / AMD NPT，统称**嵌套页表**，nested page table）：

```text
客体应用程序发出的虚拟地址（GVA）
  ──[查客体内核维护的页表]──> 客体眼里的“物理地址”（GPA）
  ──[查宿主机 VMM 维护的嵌套页表]──> 宿主机内存条上真正的物理地址（HPA）
```

把第 5 章[16 字节迷你小页](../chapter_04_memory/01_address_space_paging.md)请回来，亲手算一遍两阶段翻译，瞬间就通透了！假设：
- 客体内核的页表记录：`客体虚拟页 1 -> 客体页框 5`；
- 宿主机 VMM 的嵌套页表记录：`客体页框 5 -> 宿主机真实页框 12`。

现在客体应用读取虚拟地址 `26`：
1. 第一阶段（客体视角）：`26 = 1 × 16 + 10`，查客体页表把页 1 换成客体页框 5，算出客体以为的物理地址 $5 \times 16 + 10 = 90$；
2. 第二阶段（宿主机视角）：硬件接着查嵌套页表，把客体页框 5 换成宿主机真实页框 12，偏移 `10` 依然纹丝不动，最终稳稳落在宿主机内存条的 $12 \times 16 + 10 = 202$ 号字节！

一旦翻译结果放进 TLB，后续访存直接一次命中 `GVA -> HPA`，快如闪电。可一旦发生 [TLB 未命中](../chapter_04_memory/02_page_tables_tlb_faults.md#tlb)，代价就会被两层页表剧烈放大——因为硬件在走客体 4 级页表的**每一步**时，客体页表自己也住在客体物理内存里，每读一层客体页表都得再走一遍宿主机 4 级嵌套页表！最坏情况下，一次普通的 TLB 未命中可能引发 $4 \times 4 + 4 + 4 = 24$ 次内存访问！这正是为什么云虚拟机极其偏爱给宿主机开启 2 MiB 大页来压低嵌套遍历层数。

此外，为了在多台虚拟机之间灵活腾挪物理内存，宿主机常配合两项高级技巧：**内存超配**（向多台客体承诺的内存总额大于宿主机物理内存条，赌它们不会同时用满）和**气球驱动**（Balloon Driver——宿主机在客体内核里安插一个小驱动，当宿主机吃紧时，指挥空闲客体里的气球“吹大”向客体内核申请一大片内存再悄悄交还给宿主机；等客体忙起来再给气球放气归还）。当然，一旦所有超配的虚拟机同时跑满内存，宿主机被迫疯狂回收交换，尾延迟照样会剧烈抖动。

## 第三座大山：设备虚拟化的三条演进路线

虚拟机里看不到真实主板，那网卡、硬盘和显卡怎么接进来？三种方式把“兼容性、性能、灵活迁移”扯成了经典三角：

1. **全设备模拟（Full Emulation）**：VMM 纯靠软件硬“装”出一块古老经典的真实网卡或 IDE 硬盘（比如模拟 Intel e1000 网卡）。好处是客体操作系统一行代码不用改，哪怕装个二十年前的老系统都能无缝认出来；代价是客体驱动每次读写硬件寄存器都触发 VM exit，性能极差。
2. **半虚拟化设备（Paravirtualization，如 Virtio）**：何必装模作样演一块笨重的老硬件呢？让客体操作系统装上专门的半虚拟化驱动，直接和宿主机 VMM 坦诚相见——双方共用一块共享内存里的环形队列（类似第 6 章的描述符环），客体驱动把一大批网络包或磁盘请求攒进环里，只敲一次门铃交给宿主机设备后端批量干完！兼顾了极高的吞吐和方便的跨机迁移，唯一要求是客体里装上对应的半虚拟化驱动（现代 Linux/Windows 几乎默认内置）。
3. **设备直通（Device Passthrough，如 VFIO / SR-IOV）**：遇到大模型训练用 GPU 加速卡、或追求极致低延迟的万兆网卡，干脆绕开 VMM 模拟，把整块物理 PCIe 设备（或支持硬件切分的单个虚拟功能 VF）直接穿透交给这台虚拟机独占！性能几乎 100% 追平裸机。此时，第 6 章讲过的[IOMMU 安全围栏](../chapter_05_storage_io/04_interrupts_dma_cache.md#iommu)成了绝对救命绳——把这块直通设备的 DMA 范围死死锁在该虚拟机专属的宿主机物理页内，绝不许它越界染指宿主机或其他租户内存！代价则是直通设备与单台物理机强绑定，想做在线热迁移或灵活共享给其他客体立刻变得异常棘手。

## 换一条轻盈赛道：容器如何在共享内核下画边界？

看完了厚重的虚拟机，再回头看开篇的甲组——他们只需要在宿主机现成的 Linux 内核上跑一个 Python 网页服务，根本不想为每个微服务再多养一套客体内核、多等几十秒开机引导。

于是 **Linux 容器**走了一条截然不同的巧路：**不造假硬件，也不起新内核；直接把进程留在宿主机内核里跑，但用内核自带的三套隔离机制把它团团包住！**

### 1. Namespace（命名空间）：改变你“看得见”的世界

**命名空间**（namespace）像给每个容器戴上了一副特制 VR 眼镜，让容器里的进程只能看见自己屋里的那一片天地：
- **PID namespace**：容器里第一个启动的进程以为自己是威风凛凛的 `PID 1`，敲 `ps` 看不到宿主机和其他容器里的任何进程（但在宿主机视角里，它不过是个普普通通的 `PID 28419`！）；
- **NET namespace**：拥有独立的虚拟网卡、路由表和端口账本——这正是开篇甲组两个容器都能各自安心监听 `8000` 端口而互不打架的秘密；
- **MNT namespace**：拥有独立的文件系统挂载树，看不到宿主机根目录里的其他敏感文件；
- **UTS / IPC / User namespace**：分别隔离开主机名、进程间消息队列/共享内存对象，以及把容器里看似全能的 `root (UID 0)` 悄悄映射成宿主机上毫无特权的普通用户（如 `UID 100000`）。

一句话概括：**namespace 管的是“你看得见哪些名字和对象”。**

### 2. cgroup（控制组）：锁死你“用得掉”的配额 { #cgroup }

光戴上 VR 眼镜看不见邻居远远不够——如果容器里的代码写了死循环或内存泄漏，它照样能把宿主机 64 颗 CPU 和 256 GB 内存吃干抹净，把同机所有邻居拖死！

**控制组**（control group，**cgroup**）负责把容器里的主进程连同它生出来的全部子进程捆成一组，统一记账并死死卡住它们的资源天花板：CPU 时间配额、内存硬上限、磁盘 I/O 读写速率、最大进程数（防 Fork Bomb）。

**namespace 管“可见性”，cgroup 管“资源用量”**——少了前者没有独立视图，少了后者会闹出“坏邻居掀翻整台机器”的资源雪崩，两者缺一不可。

### 3. 联合分层文件系统、写时复制与容器安全加固

为了秒级拉起成百上千个容器而不把硬盘撑爆，容器把程序和依赖打包成只读的**镜像**（image），并按层叠放（底层是基础系统库、中层是 Python 解释器、顶层是你的业务代码）。同一台机器上跑 50 个基于同一镜像的容器，它们在硬盘和页缓存里**共享同一份只读镜像层**；每个容器启动时，只在最顶上盖一层薄薄的专属可写层——只有当某个容器试图修改基础文件时，才按**写时复制**把那个文件拷进自己的可写层改写，其他 49 个容器毫不知情！同时牢记：临时可写层往往随容器销毁灰飞烟灭，需要长期留存的数据库文件或训练权重必须放进独立挂载进来的**持久卷**（详见[下一章：从镜像到进程](03_image_to_process.md)）。

最后，为了尽量弥补“共享同一个宿主机内核”的天然短板，生产级容器还会叠加第 8 章的全套安全武装：
- 剥离不需要的 Linux **capabilities**（丢掉改网卡、挂文件系统等管理特权）；
- 配置 `seccomp` 系统调用白名单收窄内核攻击面；
- 叠加上 SELinux / AppArmor 这类[强制访问控制（MAC）](01_protection_security.md#mac)策略；
- 把根文件系统或配置目录设为只读挂载，并尽量以非 `root` 用户或 User Namespace 运行。

但无论武装到多严实，一条底线始终摆在那里：**所有容器共享同一个宿主机内核。** 一旦宿主机内核出现提权漏洞，攻击者就可能击穿容器逃逸到宿主机。因此，公有云里跑互不信任的陌生代码或强安全多租户场景时，架构师往往把两者强强联手——**外面套一层轻量虚拟机做硬件级强边界，里面跑容器享受敏捷部署！**

## 一张表看清虚拟机与容器的本质差异

| 对比维度 | 虚拟机（VM） | Linux 容器（Container） |
| --- | --- | --- |
| **操作系统内核** | 每台客体跑自己完整独立的内核 | 与宿主机及同机所有容器共享同一个内核 |
| **启动速度** | 通常较慢（秒级至数十秒，需走内核引导） | 极快（毫秒至亚秒级，直接拉起进程） |
| **内存底噪** | 较高（每台需额外承载一份客体内核与系统服务） | 极低（几乎只有应用本身，且共享只读镜像页） |
| **能否跨操作系统** | 可以（Linux 宿主机上轻松跑 Windows 或旧版 Linux） | 通常不行（必须兼容宿主机内核 ABI） |
| **隔离防线** | CPU 硬件虚拟化、嵌套页表、VMM 与 IOMMU | 宿主内核内的 namespace、cgroup、capabilities、seccomp 与 MAC |
| **设备访问方式** | 软件模拟、半虚拟化（Virtio）或 PCIe 直通 | 直接经宿主机内核设备接口与权限过滤 |

## 细算一个极易踩坑的容器配额例子：CPU 节流与 OOM

假设你给一个容器设置了两个 cgroup 限制：**每 100 ms 周期最多消耗 100 ms 的 CPU 时间**（俗称 `1 核配额`），以及 **512 MiB 内存硬上限**。

注意一个让无数线上工程师困惑的诡异现象：容器里的服务只开了 2 条并发线程，机器上明明还有十几颗完全空闲的 CPU 核心，可监控却显示服务每隔几十毫秒就被狠狠卡顿一次！怎么回事？

算笔账就豁然开朗了：cgroup 限制的是这组线程在每 100 ms 墙钟周期里的**累计 CPU 时间总量**。当 2 条线程在 2 颗物理核心上同时满载跑了 **50 ms** 墙钟时间后，两颗核合计已经用掉了 $2 \times 50 = 100\ \text{ms}$ 的 CPU 时间——配额瞬间归零！于是剩下的整整 50 ms 墙钟时间里，就算宿主机核心闲得发慌，cgroup 也会铁面无私地把这组线程全部强行**节流挂起（CPU Throttling）**，直到下一个 100 ms 周期开始才放行！如果你想让它独占固定某颗物理核而不被切碎，那需要的是第 2 章讲过的 **CPU 亲和性**（如 `cpuset` 绑定），和总时间配额是两码事。

内存上限同样如此：一旦容器内进程触碰 512 MiB 红线，内核会先疯狂回收该容器自己的页缓存，回收不动时立刻在**该 cgroup 内部触发 OOM 杀手**直接枪毙容器进程（而不连累宿主机其他服务）。千万别把容器限额当成透明的物理硬件——应用程序自身必须清楚容器的真实额度（例如 JVM 或 Go 运行时若傻傻按宿主机 64 核、256 GB 去开线程池和堆大小，一上线就会撞墙节流或被 OOM 秒杀！）。

## 虚拟机的王牌绝活：快照与在线热迁移

正因为虚拟机把一整台“电脑”的状态全装进了宿主机手里可控的内存和虚拟磁盘文件里，它玩出了物理机想都不敢想的两项绝技：

- **整机快照（Snapshot）**：瞬间把虚拟机某一刻的 vCPU 寄存器、内存影像和虚拟磁盘状态一并定格保存。最难的考验在于**一致性**——如果内存截的是第 10 秒、磁盘截的是第 10.5 秒，或者客体页缓存里还有没刷盘的脏数据，恢复出来照样对不上号，往往需要借助客体代理先短暂冻结文件系统刷盘，再同步抓快照；外部网络长连接和远端数据库更是没法靠单机快照时光倒流。
- **在线热迁移（Live Migration）**：不停机把一台正在跑业务的虚拟机，从 A 物理机活生生搬到 B 物理机！经典**预复制（Pre-copy）**做法极其巧妙：先让虚拟机在 A 上照常跑着，后台一轮轮把它的内存页拷给 B；第一轮拷完后，只补拷期间被客体改脏的那一小批**脏页**；反复迭代几轮直到剩余脏页少到微不足道，此时把虚拟机极短暂地暂停几十毫秒，把最后一点脏页和 vCPU 寄存器状态一把同步过去，B 机器立刻无缝接棒继续跑，用户甚至察觉不到服务换了台物理机！（不过，如果虚拟机正在疯狂满速改内存、脏页产生速度压过了网络拷贝带宽，预复制就会永远收不了尾，不得不主动限速客体或改用先迁核心状态再按需拉页的后复制策略。）

## 打破两个常见错觉与可观察性陷阱

1. **“拉个镜像跑起来 = 安全容器”？错！** 镜像只是一包打包好的只读文件系统和启动元数据；真正撑起隔离的，是运行期创建的 namespace、cgroup、权限裁剪和网络策略。直接把镜像解压在宿主机上跑，一丁点安全隔离都没有。
2. **“容器 = 微服务”？错！** 容器只是交付和运行边界，你可以把笨重的单体应用塞进容器，也可以把精致的微服务直接跑在裸机或虚拟机里。
3. **虚拟化让监控指标多了一层迷雾**：虚拟机里看到的“CPU 占用高”，说不定是被宿主机 VMM 抢走物理核造成的“被偷时间（Steal Time）”；容器里敲 `free -h` 看到的可能是宿主机总内存而不是自己可怜的 512 MiB cgroup 上限；一次磁盘慢延迟，可能堵在客体队列、VMM 后端、宿主机块层或真实物理盘任意一层。排错时切记**把客体/容器内部视角与宿主机外部视角对照着看**！

## 选型权衡与通往实战的最后一问

什么时候选虚拟机？需要跑不同操作系统内核、面向陌生租户要求硬件级强隔离、需要完整设备兼容和热迁移时，虚拟机不可替代。什么时候选容器？应用能共享宿主机 Linux 内核、追求秒级扩缩容、高部署密度和一致的交付环境，且团队能扎实做好权限裁剪与限额时，容器所向披靡。在云原生生产环境里，最稳健的组合常常是“**租户间用虚拟机隔开，租户内用容器高效排布**”。

理论已经全部铺平，光说不练总隔着一层纸。现在，我们把开篇那个监听 8000 端口的 Python 小网页服务真正端上实验台，先问自己三个直击灵魂的问题：它靠谁的内核处理系统调用？它眼里能看见哪些进程和端口？它写出去的数据落在哪里、重启容器后还在不在？带着这三问，走进[第 10 章：从镜像到进程](03_image_to_process.md)，亲手把一份静态镜像一步步跑成受限容器进程！

## 自测

1. CPU 虚拟化的 **Trap-and-emulate（陷入与模拟）** 机制，为什么能让虚拟机里绝大多数普通计算指令跑出接近裸机的原生速度？
2. 在内存虚拟化的两阶段地址翻译中，第一阶段页表和第二阶段嵌套页表分别由谁负责维护？为什么这种结构在 TLB 未命中时开销特别大？
3. 在 Linux 容器中，**namespace** 和 **cgroup** 各自解决什么问题？为什么少掉其中任意一个都不完整？
4. 为什么说“容器镜像本身只是一套只读分层文件，绝不等于完整的运行期安全隔离”？
5. 给虚拟机做 **PCIe 设备直通** 换来了近乎裸机的 I/O 性能，它同时牺牲了哪些原本很宝贵的能力，又必须依赖哪项硬件来保住安全？

??? note "参考思路"

    1. 非敏感的普通算术、逻辑和常规访存指令无需软件解释，直接交由物理 CPU 硬件原生全速执行；只有在客体触发配置好需要拦截的敏感操作、虚拟设备访问或外部中断时，才会触发 VM exit 交由 VMM 模拟处理。
    2. 第一阶段（GVA $\rightarrow$ GPA）由**客体操作系统内核**维护，第二阶段嵌套页表（GPA $\rightarrow$ HPA）由**宿主机 VMM** 维护。TLB 未命中时，走客体多级页表的每一级读取自身都需要再走一遍宿主机嵌套页表，导致内存访问次数呈乘积式放大。
    3. `namespace` 负责改变进程“看得见”的资源视图（进程号、端口、挂载点、主机名等）；`cgroup` 负责统计并卡死一组进程“用得掉”的资源上限（CPU、内存、I/O）。缺前者就没有独立命名空间视图，缺后者容器就能吃光宿主机资源拖垮所有邻居。
    4. 镜像只是静态文件和启动元数据包；真正的运行期隔离是在启动进程那一刻，由容器运行时调用宿主机内核创建 namespace、挂入 cgroup、裁剪 Linux capabilities、加载 `seccomp`/MAC 规则与只读挂载共同建立的。
    5. 牺牲了在多台虚拟机之间灵活共享同一硬件设备的能力，也极大增加了在线热迁移和整机快照的难度；同时必须依赖 **IOMMU** 限制直通设备的 DMA 物理内存边界，防止虚拟机借设备越界读写宿主机或其他租户内存。
