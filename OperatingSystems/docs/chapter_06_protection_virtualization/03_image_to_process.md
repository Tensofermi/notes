# 从镜像到进程：一次可重复的容器运行

**先修**：[进程](../chapter_02_processes/01_process_thread_context.md)、[权限](01_protection_security.md)、[虚拟机与容器](02_virtual_machines_containers.md)。

**读完能做**：跟踪一个服务从镜像引用到运行，区分它在文件、进程、网络和权限上的边界。

## 同一个程序，三种运行环境

先在一个空目录里运行<a href="../../ComputerNetworks/chapter_02_application/04_socket_and_listening.html">本机 Python HTTP 服务</a>。这时它能读取当前用户有权访问的目录，也会占用 CPU 和内存。它还会**监听** 8000 端口，即等客户端向这个编号对应的入口发请求。现在要让同一台机器再跑一份服务，两个团队各自管理文件、端口和资源。可以先问三个独立的问题。

| 我想控制什么 | 在 Linux 容器里的例子 | 对应机制 |
| --- | --- | --- |
| 它能看到哪些资源？ | 给两份服务分开网络视图，各自在内部监听 8000 | 命名空间（namespace）改变进程看到的资源 |
| 它能用多少资源？ | 给一份服务设置内存上限，避免它吃掉整台机器的内存 | 控制组（cgroup）一起限制和统计一组进程用掉的资源 |
| 它被允许做什么？ | 服务需要读取网页目录，但无需管理员权限 | 按进程的用户编号（UID）检查文件权限 |

把进程放进虚拟机时，客体有自己的内核和虚拟设备。放进 Linux 容器时，宿主机内核仍执行系统调用，只是进程看到的资源、能用的份额和权限可以被分别设置。比如两个容器在自己的网络视图里都可监听 8000，但如果都想把它映射到宿主机同一个 IP 的 8000 端口，入口会冲突。

程序需要的网页目录可以通过**挂载**接入容器的文件树，并设为只读。若要运行别人提交的代码，还要决定容器可访问哪些数据、可连接哪些网络服务。这样的风险假设叫**威胁模型**，据此配置的一组限制构成**沙箱**。例如，为防程序读到其他项目的文件，可以只接入当前项目的输入目录。内存上限处理的是另一件事，即一份任务用尽共享内存。

## 镜像怎样变成进程

镜像可以先理解为一份可重复使用的文件与启动配置。镜像里面有 Python 和程序依赖，也可以写明启动时执行哪个命令。提供镜像下载的服务叫**镜像仓库**（Registry）。负责把镜像变成运行环境的一组程序称为**容器运行时**。它先取到镜像，把文件准备好，为进程设置可见范围和资源限制，再启动一条实际执行的命令。镜像仍在，进程可以已经退出；同一份镜像也可以启动多个实例，其运行时文件和状态各自变化。

| 阶段 | 问题 | 输出 |
| --- | --- | --- |
| 构建 | 用哪些文件和启动配置 | 镜像文件及说明怎样启动的配置 |
| 分发 | 到哪里找这一版内容 | 可从仓库下载的镜像及其名称 |
| 准备 | 进程看到哪套文件、网络和资源约束 | 容器的文件树、另行接入的目录、可见资源及使用上限 |
| 启动 | 执行什么程序，结束后怎样知道结果 | 在宿主机上运行的进程及它返回的退出状态 |

镜像引用 `python:3-slim` 里的 `3-slim` 是**标签**，便于阅读，将来可指向新内容。想锁定这次实际下载的版本，可以同时记录镜像**摘要**，它用内容计算并标识这一份镜像。不同镜像还可以复用相同的文件内容，例如一层相同的 Python 安装文件。新容器运行时会为自己的更改加一层可写文件。若希望容器重建后仍能找到这些更改，应写到容器外并重新挂载进来。

这里用 **Docker** 发送构建和运行命令。在常见配置里，后台服务 **containerd** 管理镜像下载和容器生命周期；更靠近内核的运行程序，例如 **runc**，接收已经准备好的文件和运行配置，再创建隔离环境、启动首个进程。**开放容器倡议（OCI）**约定镜像如何表示和传送，以及底层程序拿到怎样的一份文件和配置后应当运行它，便于不同工具交接。

## 观察一个只在本机开放的服务

具备 Docker 环境时，在空目录里运行如下命令。这个教学例子采用可读标签，复现实验记录时可以额外记下实际镜像摘要。

```sh
docker run --rm -d --name notes-http-demo \
  -p 127.0.0.1:8000:8000 --memory=128m --cap-drop=ALL \
  --security-opt=no-new-privileges=true \
  python:3-slim python -m http.server 8000 --directory /tmp
curl -i http://127.0.0.1:8000/
docker exec notes-http-demo sh -c 'echo "$$"; cat /proc/self/cgroup'
docker logs notes-http-demo
docker stop notes-http-demo
```

镜像需可下载，本机 8000 端口需空闲。先预测：应用已在容器监听时，去掉 `-p` 是否还会通过上述宿主机端口访问？再分别观察进程、端口和日志。应用的挂载目录、对外访问范围和凭据应根据实际任务分别决定。

| 命令或参数 | 用来验证什么 |
| --- | --- |
| `-p 127.0.0.1:8000:8000` | `127.0.0.1` 是宿主机只供自己访问的回环地址。这里把这个地址的 8000 端口接到容器的 8000。`curl` 是从命令行发网页请求的工具，本机运行它应收到 HTTP 响应。 |
| `--memory=128m` | 请求运行时给这组进程配置内存上限；与端口转发无关。 |
| `docker exec ...` | 在容器内另外启动一个解释命令的程序（shell）。`$$` 打印这个程序在容器内的进程编号（PID），`/proc/self/cgroup` 显示读取它的进程看到的控制组信息。 |
| `docker logs ...` | 看服务是否记下刚才的请求，与客户端观察互相印证。 |

没有 Docker 时也能先做两道预测：两个容器都在内部用 8000 时，宿主机应给它们分配哪两个入口端口？若要重建其中一个容器仍保留网页修改，应把文件写到镜像、容器临时层，还是持久挂载的目录？

## 自测

设训练程序保存了一份可供下一次继续计算的恢复点（checkpoint）。如果只把恢复点写进容器自己的可写层，再从同一个镜像新建容器时会发生什么？

??? note "参考思路"
    新容器从镜像与新的可写层开始，原容器产生的 checkpoint 不随镜像出现。应把需要恢复的数据持久化到独立位置，并记录对应版本和路径。

参考 [OCI 三份规范的分工](https://opencontainers.org/about/overview/)与 [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)。
