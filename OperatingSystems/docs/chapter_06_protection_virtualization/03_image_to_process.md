# 从镜像到进程：一次可重复的容器运行

**先修**：[进程、线程与上下文切换](../chapter_02_processes/01_process_thread_context.md)、[保护机制与系统安全](01_protection_security.md)、[虚拟机与容器](02_virtual_machines_containers.md)。

**读完能做**：亲手跟踪一个网页服务从静态镜像一步步变成宿主机上的受限容器进程，并能清晰区分它在文件系统、进程视图、网络端口、资源限额与安全沙箱五个维度上的真实边界。

## 同一个网页服务，套上容器外衣后究竟变了什么？

在终端的一个空目录里，你只要一行命令就能拉起一个<a href="../../ComputerNetworks/chapter_02_application/04_socket_and_listening.html">本机 Python HTTP 服务</a>，让它监听 `8000` 端口对外提供网页文件。作为裸跑在宿主机上的普通进程，它的默认视野极其宽广：能读你当前账户有权触碰的所有目录，能毫无节制地吃光机器的 CPU 和内存，而且一旦它占住了 `8000` 端口，同机第二个服务再想监听 `8000` 就会当场撞车报错。

现在，我们要在同一台 Linux 服务器上，同时给两个互不干扰的团队各跑一份这样的网页服务。把上一章学过的隔离机制全部拧成实操问题，恰好对应着四道彼此独立的控制闸门：

| 你想把什么关进笼子 | 放到 Linux 容器里的具体画面 | 底层撑腰的内核机制 |
| --- | --- | --- |
| **它能看见哪些资源？** | 两份服务各自独享一套网络与进程视图，都在自己屋里安心监听 `8000` 端口，互看不见对方的进程 | **命名空间（namespace）**：重写进程的视野边界 |
| **它最多用掉多少资源？** | 给每个服务锁死 `128 MiB` 内存天花板和 CPU 配额，哪怕写死循环泄漏内存也不连累邻居 | **控制组（cgroup）**：统一记账并强制封顶资源消耗 |
| **它被允许干哪些事？** | 它只需读网页目录和收发 HTTP，彻底剥夺所有管理员特权、禁止提权并过滤危险系统调用 | **UID 降权、Capabilities 裁剪、seccomp 与 MAC** |
| **它写的数据能留多久？** | 静态网页目录只读挂入，真正要持久化的日志或业务数据写到容器外挂进来的独立目录 | **分层联合文件系统（OverlayFS）与持久卷挂载** |

留意一对极易踩坑的端口边界：**两个容器在各自独立的网络命名空间里，完全可以同时监听内部 `8000` 端口；但如果它们都想把内部 `8000` 映射到宿主机同一个 IP 的外部 `8000` 端口，在宿主机入口处依然会撞车！** 容器改变的是“屋子里面的门牌号”，宿主机大门上的门牌号永远全机唯一。

再往前推一步：如果这个容器里跑的不是你自己写的可靠代码，而是陌生用户提交的一段待评测代码或不可信插件，你立刻要掏出第 8 章的**威胁模型**来搭**沙箱**——防它偷窥别家项目文件，就绝不把无关宿主机目录挂进去，必要输入目录也加 `:ro` 只读挂载；防它扫描内网或把数据传出去，就直接彻底断开外网出口（如 `--network=none`）；防它吃光内存和进程数，就配齐 `--memory` 与 `--pids-limit` 上限。每一条参数对应一道具体风险，彼此不能互相替代。

## 静态压缩包如何“活”成一条进程？从镜像到容器运行时的四棒交接

很多人第一次敲下 `docker run` 时，感觉像对着一个黑盒子念了一句咒语，一秒钟后服务就在屏幕里跑起来了。把黑盒子撬开，一份冰冷的静态文件包究竟是怎么变成宿主机内核里一条活生生的进程的？整条流水线清清楚楚分成四个阶段：

| 阶段 | 这一步在回答什么问题 | 产出的核心物件 |
| --- | --- | --- |
| **1. 构建（Build）** | 应用运行需要哪些系统库、解释器、代码文件，以及默认启动命令是什么？ | 分层打包的只读**镜像（Image）**与 JSON 启动配置清单 |
| **2. 分发（Distribute）** | 另一台机器去哪里拉取完全一模一样的这一版环境？ | 托管在**镜像仓库（Registry）**里、带有可读标签与唯一内容摘要的镜像引用 |
| **3. 准备（Prepare）** | 进程醒来前，该给它拼出怎样的文件树、挂载哪些目录、套上哪些隔离与限额？ | 合并好的只读底层 + 专属可写上层、建好的 namespace/cgroup 与安全配置包 |
| **4. 启动（Execute）** | 真正调用内核拉起首个进程，并在它退出时回收退出码 | 宿主机内核里一条被套牢隔离边界的真实进程（在容器内显示为 `PID 1`） |

这里面藏着三个在生产运维里极其关键的工程细节：

### 细节一：别盲信可读标签（Tag），生产复现要锁死内容摘要（Digest）

你每天看到的 `python:3-slim` 里，冒号后面的 `3-slim` 只是一个方便人眼阅读的**标签**（tag）——它就像一支随时可以挪位置的书签，下个月官方发布安全更新后，`python:3-slim` 指向的底层内容可能已经悄然换代！要想保证今天在开发机跑通的实验、半年后在生产集群上分毫不差地复现出同一个字节，必须记录并锁定镜像的**内容摘要**（digest，形如 `sha256:9f86d0...`）——它由镜像内容经密码学哈希算出，内容改掉一个比特摘要就会彻底改变，天然具备不可篡改的内容寻址保证。

### 细节二：只读层共享 + 写时复制可写层，为何容器删除数据就丢？

镜像不是一坨铁板一块的大压缩包，而是像千层蛋糕一样一层层叠起来的只读文件系统（例如底层是极简 Debian 基础文件，中层是 Python 3 运行时，顶层是你自己的应用脚本）。当你在同一台机器上同时用 `python:3-slim` 启动 10 个容器时，底层只读文件在硬盘上**只存一份**，被所有容器共享。

启动每个容器时，存储驱动（Linux 上常见为 OverlayFS）会在只读镜像最顶上盖一层薄薄的**容器专属可写层**，通过联合挂载把它们融合成一棵完整的目录树：
- 容器读基础文件时，直接穿透读取底层只读镜像；
- 容器第一次试图修改某个基础文件时，存储驱动按**写时复制（Copy-on-Write）**把它先拷一份到自己的可写层再改写，丝毫不影响其他 9 个容器；
- 容器停止并删除时，这层临时可写层也随之灰飞烟灭！因此，镜像的寿命、容器进程的寿命和业务数据的寿命是**三条彻底独立的生命线**——凡是希望容器删掉重建后依然安然无恙的数据（数据库文件、网页上传物、模型训练检查点），一律必须写到容器外部通过**绑定挂载或持久卷**接进来的持久化存储中。

### 细节三：一条命令背后的三层接力——Docker、containerd、runc 与 OCI

你在命令行里只敲了一个 `docker run`，幕后其实经过了职责分明的三层标准化交接：

```text
用户敲下 docker run（Docker CLI / Daemon：面向用户的交互与编排入口）
  -> containerd（高层容器运行时：管镜像拉取、层解压、镜像仓库认证与容器生命周期）
  -> runc（底层容器运行时：按配置调用 Linux clone/unshare/pivot_root/cgroup/seccomp 系统调用）
  -> 宿主机 Linux 内核（真正创建出套牢隔离边界的新进程！）
```

之所以不同厂商的工具（Docker、Podman、Kubernetes CRI-O）能无缝互相接力，全赖行业共同制定的**开放容器倡议**（Open Container Initiative，**OCI**）标准：它用白纸黑字统一规定了“镜像怎么打包”“仓库怎么拉取”以及“高层运行时把解压好的根文件系统和 `config.json` 交给底层运行时后，底层该如何启动进程”。从此，换掉上层工具，同一份标准镜像照样在任何兼容运行时上原样跑通。

## 动手实战：把受限 HTTP 容器拉起来逐项验身

如果你的机器装好了 Docker（且本机 `8000` 端口空闲、可以访问镜像仓库），打开终端跑一遍下面这组精炼的只读安全实验。为了便于教学这里用了可读标签，做正式实验记录时建议顺手用 `docker inspect` 记下它的 `sha256` 摘要：

```sh
docker run --rm -d --name notes-http-demo \
  -p 127.0.0.1:8000:8000 --memory=128m --cap-drop=ALL \
  --security-opt=no-new-privileges=true \
  python:3-slim python -m http.server 8000 --directory /tmp
curl -i http://127.0.0.1:8000/
docker exec notes-http-demo sh -c 'echo "$$"; cat /proc/self/cgroup'
docker logs notes-http-demo
docker stop notes-http-demo
```

别急着复制粘贴回车就完事——先停下来做一次**事前预测**：容器里的 Python 服务明明已经在监听 `8000` 端口了，如果我把命令行里的 `-p 127.0.0.1:8000:8000` 删掉，在宿主机上运行 `curl http://127.0.0.1:8000/` 还能连得上吗？（答案：连不上！因为容器的 `8000` 端口关在它自己的网络命名空间里，没做端口转发，宿主机根本找不到入口。）

接着，把上面命令行里每一个参数和观测动作逐一拆开验明正身：

| 命令或参数 | 它在系统底层拧紧了哪颗螺丝、验证了什么 |
| --- | --- |
| `--rm -d` | `-d` 让容器在后台运行；`--rm` 约定进程一停止就自动清理临时可写层与容器元信息，不留垃圾。 |
| `-p 127.0.0.1:8000:8000` | `127.0.0.1` 是宿主机仅限本机访问的回环地址。这条规则把宿主机本机 `8000` 端口精准转发给容器网络命名空间里的 `8000`（故意不写 `0.0.0.0` 以免意外暴露到局域网！）。随后用 `curl` 发起 HTTP 请求即可收到响应。 |
| `--memory=128m` | 通知运行时把该容器放进内存硬上限为 `128 MiB` 的 **cgroup** 里；它管的是内存用量，和端口映射完全独立。 |
| `--cap-drop=ALL` | 贯彻最小权限原则，一口气剥光所有 Linux 管理特权（capabilities）——只服务静态文件的 Python 进程一项特权都不需要！ |
| `--security-opt=no-new-privileges=true` | 彻底堵死通过 SUID 程序或文件能力在容器内中途提权的后门。 |
| `docker exec ... 'echo "$$"; cat /proc/self/cgroup'` | 在同一个容器的命名空间与控制组里拉起一个临时 shell：打印当前 shell 在容器 PID namespace 里极小的进程号（注意 Python 主进程在这里正是 `PID 1`！），并读取 `/proc/self/cgroup` 亲眼确认它正受控于宿主机为其新建的专属控制组路径。 |
| `docker logs notes-http-demo` | 查看容器标准输出/错误流记录下的访问日志，和前面 `curl` 收到的响应互相印证。 |

> 手头暂时没有 Docker 环境也没关系，试着在脑海里完成这两道推演检验自己是否真懂了：
> 1. 如果要在同一台宿主机上同时跑起两个都在内部监听 `8000` 的网页容器，宿主机侧该怎样映射端口？（例如分别映射为 `127.0.0.1:8001:8000` 与 `127.0.0.1:8002:8000`。）
> 2. 如果希望删除并重建其中一个容器后，刚才上传保存的网页文件依然完好无损，应该把文件存进“镜像本身”“容器可写层”还是“宿主机挂载进来的持久目录”？（显然是外部挂载的持久目录或持久卷！）

## 再多追问一层：当普通容器沙箱依然不够保险时

经过上面这番加固（`--cap-drop=ALL`、`no-new-privileges`、`seccomp` 过滤、只读挂载、非 `root` 用户、内存与进程数限额），普通 Linux 容器对绝大多数自家微服务和可控研发环境来说已经足够结实。

可如果你的平台要运行**完全不可信的第三方代码**（例如在线评测机 OJ、多租户无服务器函数 FaaS、或陌生外部用户提交的 AI 训练脚本），威胁模型陡然升级——所有容器依然共用着同一个动辄三千万行 C 代码的宿主机 Linux 内核，万一对方利用一个零日内核提权漏洞直接穿墙，整台宿主机上的所有租户数据都会暴露无遗！

于是，现代云原生底座在“传统重量级虚拟机”和“普通共享内核容器”的夹缝中，长出了两类**强沙箱容器运行时**：
- **微虚拟机（MicroVM，如 AWS Firecracker、Kata Containers）**：把传统虚拟机的多余老旧设备模拟全砍掉，只留极简半虚拟化 Virtio 接口和瘦身内核，几百毫秒就能拉起一台真正拥有硬件级独立内核边界的迷你虚拟机来包住容器；
- **用户态拦截内核沙箱（如 Google gVisor）**：在容器进程和宿主机内核之间插一层用内存安全语言（Go）写的轻量级用户态“代办内核”，把容器发出的绝大部分系统调用就地拦截模拟，只让极少数高度受限的系统调用真正触碰宿主机内核，大幅砍小共享内核的攻击面。

两者都印证了前两章反复强调的铁律：**强隔离永远是用额外的性能与内存开销换来的，最终选型永远取决于你的威胁模型。**

## 自测

1. 设一个深度学习训练程序在容器里运行了三小时，保存了一份可供断点续训的恢复点（checkpoint）。如果不小心只把这个 checkpoint 写进了**容器自己的临时可写层**，随后因为故障删掉旧容器、再用同一个镜像拉起一个新容器，会发生什么？正确的做法是什么？
2. 为什么在生产环境里部署容器时，强烈建议记录并锁定镜像的**内容摘要（digest）**，而不是仅仅依赖 `python:3-slim` 这样的可读标签（tag）？
3. 解释下面这条命令中三个安全与隔离参数各自独立管着哪一摊事：`--memory=128m`、`--cap-drop=ALL`、`-p 127.0.0.1:8000:8000`。

??? note "参考思路"

    1. 新容器会从干净的只读镜像加一层全新的空可写层起步，旧容器临时可写层里的 checkpoint 早已随旧容器删除而彻底丢失，根本不会跟着镜像自动出现。正确做法是将 checkpoint 持久化写到容器外部独立挂载的持久存储（本地持久卷或共享分布式存储）中，并按原子发布协议记录完整版本清单与路径。
    2. 可读标签只是可变指针，镜像仓库随时可能把同一个标签指向更新后的新版本内容，导致不同时刻拉取跑出不一致的环境；而内容摘要由镜像内容哈希算得，唯一锁定不可变版本，保证部署与排错完全可复现。
    3. `--memory=128m` 通过 cgroup 限制这组进程的内存消耗硬上限；`--cap-drop=ALL` 剥夺所有 Linux 管理特权位以贯彻最小权限原则；`-p 127.0.0.1:8000:8000` 仅把宿主机本机回环地址的 `8000` 端口转发到容器独立网络命名空间的 `8000` 端口，既打通本机访问又避免意外向外部网络暴露端口。

延伸阅读：[OCI 三份规范的分工](https://opencontainers.org/about/overview/) · [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)。
