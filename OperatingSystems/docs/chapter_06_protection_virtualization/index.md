# 保护、安全与虚拟化 { #6 }

## 给同一个服务换一种运行环境

先决定[图片处理程序需要读写哪些文件](01_protection_security.md)。再想象两组人共用一台机器，希望各管各的服务。虚拟机提供一套虚拟硬件，让里面的操作系统启动自己的内核。容器内的程序继续使用宿主机的内核，由它限制可见资源和用量。跟着[同一次文件读取](02_virtual_machines_containers.md)比较两种路径，最后用[打包好的文件和启动设置](03_image_to_process.md)运行一个服务。

## 从最小权限出发

如果一个文本解析器只需要读取一个输入文件，它就不应同时拥有修改系统配置、监听任意端口和读取所有用户密钥的能力。万一它被恶意输入攻陷，多余的权限就全成了攻击者的战利品。所以稳妥的做法是只给完成工作必需的权限，这叫**最小权限原则**（principle of least privilege）。实施时可以先问：程序以谁的身份运行、只能读哪些目录、要不要打开网络端口。

保护与虚拟化可以从两类边界理解：

| 边界 | 主要问题 | 代表机制 |
| --- | --- | --- |
| 访问边界 | 这个程序能打开或改写目标文件吗？ | [文件权限和授权记录](01_protection_security.md) |
| 资源视图边界 | 程序能看见哪些资源，可以用多少？ | [命名空间（namespace）和控制组（cgroup）](02_virtual_machines_containers.md) |

边界越多并不自动越安全。如果不同层策略互相矛盾、默认权限过宽或共享内核存在漏洞，攻击路径仍可能贯穿多个层次。设计时可以先写下要保护哪些数据、担心什么操作、对方能接触哪些资源——这些假设组成**威胁模型**（threat model），再按具体风险选择隔离措施。

## 与前面章节的联系

页表权限隔离地址空间，调度器和 cgroup 控制 CPU 份额，文件系统权限保护持久化对象，系统调用入口实施参数检查，namespace 改变进程看到的资源视图。虚拟化不是独立附加层，而是对前面机制的重新组合。

阅读时可以持续追问三件事：谁在实施检查、检查所依据的身份和策略存在哪里、检查通过后获得的是一次操作还是可继续传递的对象引用。这样能把零散的权限位、文件描述符和容器配置放进同一模型。

学完后可做[从镜像到进程](03_image_to_process.md)的实验，通过一个 HTTP 服务对照可见进程、资源限制、文件视图和监听端口。
