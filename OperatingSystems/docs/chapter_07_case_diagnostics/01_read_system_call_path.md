# 一次 `read` 系统调用的完整旅程

## 同样读这 4096 字节，为什么第一次慢如蜗牛、第二次快如闪电？

不妨先做一个简单的思维实验：程序打开一个本地普通文件，从开头第 0 字节读入 4096 字节；接着把读写游标拨回 0，再一模一样读一次这 4096 字节。

两次执行，你的 C 代码一字未改，最终拿到缓冲区里的 4096 个字节也分毫不差。可打开底层监测就会发现：第一次耗时可能高达几毫秒、硬盘指示灯跟着闪了一下；紧接着第二次却可能在几微秒内瞬间返回，硬盘静悄悄纹丝不动！

秘密就藏在我们前面铺垫了一路的**页缓存**（page cache）里：第一次读取时，内核翻遍页缓存找不到这页数据，只好老老实实向硬盘下达读取请求、把当前线程送去睡觉，等磁盘用 DMA 把数据搬进页缓存后再醒来交货；而第二次读取时，那页热乎的数据依然安稳躺在内存页缓存里，内核连块设备层的门都不用敲，直接内存拷贝交差！

??? question "如果实测发现第二次读取只比第一次快了一丁点，能直接断定页缓存没命中吗？"

    不能单凭一次墙钟耗时草率下结论！说不定这个文件本来就热乎地留在页缓存里（第一次其实已经命中了），两次测出来的全都是系统调用、内存拷贝和调度噪声。真正靠谱的判据，是去核对块设备层和内核计数器——看看这两次调用背后到底有没有真的提交磁盘 I/O 请求。

把镜头聚焦回你在概述页第一眼就见过的那行代码：

```c
char buffer[4096];
ssize_t n = read(fd, buffer, sizeof(buffer));
```

源码短得不能再短，可只要你按下回车，它就会像一列穿过整座操作系统城堡的观光列车，把前六章学过的**系统调用、特权级切换、进程调度与睡眠唤醒、虚拟内存缺页、VFS、页缓存、块层、设备驱动、DMA、IOMMU 和硬件中断**统统串成一条活生生的全链路！先记住这趟旅程最重要的一句清醒口诀：**调用 `read()`，绝不等于一定会去读物理磁盘。**

## 搭好干净舞台：先明确本次旅程的假设

真实操作系统的 `read()` 既可以读本地文件，也可以读管道、网卡、键盘甚至远程网络盘。为了把主线看清而不被旁枝末节淹没，我们先设定一个最干净的基准场景：

- `fd` 是先前打开本地普通文件拿到的[文件描述符](../chapter_05_storage_io/01_files_directories_inodes.md#file-descriptors)；
- 从当前文件偏移往后，至少还有 4096 字节可读（没撞到文件尾）；
- `buffer` 是用户进程栈或堆上一块合法可写的内存地址；
- 走默认的缓冲读取路径（绕过页缓存的[直接 I/O](../chapter_05_storage_io/03_io_models_drivers.md#direct-io)和 `mmap` 我们留在后半段对照比较）；
- 暂不叠加密、压缩或网络文件系统。

## 全景路线图：先看整条铁轨，再逐站停车

站到高空俯瞰，整趟旅程分为“前半程进站”、“页缓存分叉口”和“后半程出站”三段。其中 **VFS** 是把请求分派给具体文件系统的[统一抽象层](../chapter_05_storage_io/01_files_directories_inodes.md#vfs)，**DMA** 则是[设备绕开 CPU 直接把数据搬进内存的引擎](../chapter_05_storage_io/04_interrupts_dma_cache.md)：

```text
用户代码调用 read(fd, buffer, 4096)
  -> 第 1 站：C 库包装，按 ABI 装填寄存器并执行系统调用指令
  -> 第 2 站：CPU 提权进入内核总入口，保存用户现场并核查基本参数
  -> 第 3 站：查进程 fd 表 -> 取出打开文件对象（含偏移、标志）
  -> 第 4 站：经 VFS 分派给具体本地文件系统，定位 inode 与目标文件页号
  -> 分叉口：查询页缓存（Page Cache）
       ├─ 【快车道 · 分支 A 命中】：锁定缓存页 -> 安全拷贝到用户 buffer
       └─ 【慢车道 · 分支 B 未命中】：分配页缓存槽位 -> 查 inode 块映射
             -> 提交块层合并/调度 -> 驱动建 DMA 描述符并按硬件门铃
             -> 当前线程主动睡眠让出 CPU（调度器切换去跑其他任务）
             -> 磁盘控制器走 DMA 把数据写入页缓存（经 IOMMU 校验）
             -> 硬件中断响起，回收描述符、标记缓存页就绪、唤醒等待线程
             -> 线程重回就绪队列 -> 调度器再次选中恢复运行 -> 拷贝到用户 buffer
  -> 推进文件偏移量、设置返回值（实际读取字节数）
  -> 专用返回指令降回用户态，继续执行下一行用户代码
```

这是一张跨越 Linux、BSD、macOS 等主流类 Unix 系统都稳固成立的概念路线图。下面，我们一节一节车厢逐站停车细看！

## 第 1 站：用户态 C 库包装（过门前的打包）

C 代码里的 `read(...)` 并不是直接跳进内核，它先调用标准 C 库里的一小段包装函数。包装函数严格遵守[应用二进制接口（ABI）](../chapter_01_foundations/02_kernel_user_syscalls_interrupts.md)的寄存器约定：把代表 `read` 的系统调用号放进指定编号寄存器，把 `fd`、`buffer`、`4096` 依次放进参数寄存器，然后干脆利落地执行一条硬件系统调用指令（如 x86-64 的 `syscall`）。

记住此刻三个状态：`buffer` 还只是一个用户态虚拟地址，`fd` 还只是你进程自己的一个小整数，而内核此刻对它们**一个字都不敢轻信**。顺带一提，等会儿内核若返回负错误码（如 `-EBADF`），也是由这层 C 库包装在返回前贴心地把它转成返回值 `-1`、并把正错误码塞进当前线程私有的 `errno` 里。

## 第 2 站：受控跨门入核（权限变了，人没换）

系统调用指令一响，CPU 硬件原子地完成三件事：保存用户态下一条指令地址与标志位、把特权级从用户态拔高到内核态、跳转到内核唯一受控入口并切到当前线程的内核栈。

回顾第 1 章那条黄金定律：**此刻发生了“用户态 $\rightarrow$ 内核态”的权限转换，但 CPU 上跑的依然是刚才那条线程，压根还没发生进程切换！** 内核通用入口先查系统调用号是否合法，接着核查 `fd` 有没有越界、请求长度会不会整数溢出、用户提供的 `buffer` 范围是不是完全落在合法用户空间内。不过内核心里清楚：就算此刻范围合法，用户页等会儿真正写入时依然可能缺页，所以真正拷贝字节时照样要走带有异常兜底的安全跨界拷贝例程。

## 第 3 站：顺着 `fd` 摸到“打开文件对象”

内核拿小整数 `fd` 去翻当前进程的“文件描述符表”，取出对应的**打开文件对象**（`struct file`）。这张会话档案里清清楚楚记着：
- 指向底层 inode 的指针；
- 上一次读完停下来的**当前文件偏移（offset）**；
- 当初 `open` 时的访问模式（只读、只写还是可读可写）与标志（是否非阻塞、是否直接 I/O）；
- 这类对象专属的操作函数表。

如果 `fd` 压根没打开、当初是以只写方式打开的，或者指向一个不支持普通读的对象，列车就在这一站直接亮红灯返回错误（如 `EBADF`）。另外，如果多个描述符（经 `dup` 或 `fork`）共享着这同一个打开文件对象，内核还要小心协调并发修改共享偏移的同步规则。

## 第 4 站：VFS 分派与算出目标文件页号

打开文件对象把请求交给 **VFS**（虚拟文件系统），VFS 再按对象底层的真实类型分派给具体文件系统（比如 ext4 或 XFS）的读例程。

对于普通本地文件，具体文件系统拿出当前文件偏移 `offset`，用第 5 章最熟悉的一行整除，瞬间算出本次读取落在文件的第几号 4 KiB 页面上：

$$
page\ index=\left\lfloor\frac{offset}{page\ size}\right\rfloor.
$$

如果一次读取跨过了两个相邻页面（比如从偏移 `3000` 读 4096 字节），就顺次把涉及的多个文件页都排上日程；如果快到文件末尾、剩不下 4096 字节，则自动把读取长度截短到实际剩余长度。接下来，列车驶入决定快慢生死的**分叉口——查页缓存！**

## 分支 A（快车道）：页缓存命中！

内核拿着 `(inode, page index)` 去页缓存索引树里一查——运气真好，目标页已经稳稳躺在物理内存里，而且内容是最新的！列车直接驶入微秒级快车道：

1. 给这页缓存加上临时引用或页锁，防止拷贝到一半被后台内存回收器突然踢走；
2. 算出页内起始偏移和能拷多少字节；
3. 调用安全拷贝函数（`copy_to_user`），把数据从内核页缓存抄进用户的 `buffer`；
4. 把打开文件对象的偏移量往前推进 `4096`，更新文件访问统计；
5. 放开缓存页引用，带着返回值 `4096` 优雅退回用户态。

```text
内核页缓存页（已在物理内存） ──(copy_to_user)──> 用户态 buffer
```

全程零磁盘 I/O、零 DMA、零中断、零睡眠调度！耗时只剩系统调用过门、树查找、4 KiB 内存拷贝以及可能的一点点锁开销。

### 藏在快车道里的暗坑：页缓存命中，怎么还是触发了缺页？

老练的工程师在这里会多留一个心眼：**就算文件源页稳稳命中了页缓存，你的用户目标 `buffer` 却可能还没分配物理页框！**（比如 `buffer` 是刚 `malloc` 出来、第一次写入的栈/堆新页，或者刚 `fork` 完还处在[写时复制（COW）](../chapter_04_memory/01_address_space_paging.md)只读状态。）

这时，当内核里的 `copy_to_user` 往 `buffer` 写下第一个字节时，硬件立刻啪地触发一次**用户页次要缺页异常**：
1. 拷贝临时暂停，嵌套进入内核缺页处理器；
2. 为 `buffer` 分配一个崭新的匿名物理页（或完成 COW 复制）并补齐用户页表；
3. 回到刚才暂停的那条拷贝指令，把剩下的字节顺畅拷完！

记住这个精彩细节：**“文件页缓存命中”不等于“本次 `read` 零缺页”**——因为读操作同时牵扯着“文件源页”和“用户目标页”两端的内存。

## 分支 B（慢车道）：页缓存未命中，奔赴磁盘！

如果页缓存里扑了个空，列车就不得不切入漫长而精密的磁盘远征。把下面八步连起来读，前六章的所有核心机制将在此刻完美合拢：

### 1. 占好缓存槽位、查块映射并顺手“预读”

内核先从伙伴系统要一个空闲物理页框插进页缓存树里占好坑，给它打上“正在从盘读入（尚未就绪）”的锁标志（这样要是有另一条线程也同时来读同一页，不会傻傻发两次重复磁盘读，而是乖乖跟着一起等）。接着，文件系统去查该 inode 的区段（extent）或块指针树，把逻辑文件页号翻译成硬盘上真实的物理块号。

如果内核察觉你正在顺着文件一页接一页地顺序读取，**预读（readahead）**机制还会顺手把后面相邻的 8 页、16 页一并塞进这次请求里提前搬进页缓存，赌你下一次 `read` 直接躺赢快车道！当然，如果是数据库东一枪西一枪的纯随机读，过度预读就成了浪费磁盘带宽、挤走热页的帮凶。

### 2. 进入块层：合并、拆分与排队调度

文件系统把读取任务包装成通用块请求结构体（如 Linux 里的 `bio`），递交给内核的**块层（Block Layer）**。块层像一位老练的物流调度员：
- 发现有好几个请求读的是紧挨着的相邻扇区？干脆**合并**成一次大传输，摊薄硬盘寻道和命令开销；
- 单次请求太大超出了硬件控制器胃口？按上限整齐**拆分**；
- 按优先级、公平配额（如 `cgroup` 磁盘 I/O 权重）排好队，送入对应的硬件提交队列。对于多队列并发能力强悍的 NVMe 固态盘，块层尽量零阻塞并行分发；对于机械硬盘，调度器则还会尽量按磁道顺序排排站减少磁头来回折腾（第 7 章的[崩溃一致性、日志与磁盘调度](../chapter_05_storage_io/02_journaling_crash_disk.md)会专门比较不同存储介质的调度逻辑）。

### 3. 设备驱动构造 DMA 描述符并按门铃

块请求落到具体的**存储设备驱动**手里。驱动调用内核 DMA 映射 API，把刚才占好坑的页缓存物理页映射成硬件看得懂的总线/I/O 地址；如果机器开启了[IOMMU](../chapter_05_storage_io/04_interrupts_dma_cache.md#iommu)，还会同步向 IOMMU 写入放行规则，严防硬件越界乱写。随后驱动把地址、长度与读命令填进**描述符环**的提交槽，做好内存写屏障，往硬盘控制器的 MMIO 门铃寄存器轻轻一写——发车！

### 4. 当前线程果断睡眠，把 CPU 让给有用的人

硬盘接到命令还要几十微秒（SSD）甚至几毫秒（HDD）才能交货，让飞快的 CPU 原地干等简直暴殄天物。于是内核把当前正在执行 `read` 的线程状态从 `Running` 改成 `Blocked`（等待该页缓存解锁），挂进这页缓存的等待队列，随后果断调用第 2 章学的**调度器**，把上下文切换给就绪队列里另一条正嗷嗷待哺的线程：

```text
当前 read 线程：运行（Running） -> 阻塞等 I/O（Blocked）
同机其他线程：  就绪（Ready）   -> 上台运行（Running）
```

看，这就是操作系统借并发完美隐藏慢速 I/O 延迟的经典一幕：从用户程序眼里看 `read()` 卡住了，可机器里的 CPU 一毫秒都没闲着！

### 5. 硬件默默发力：DMA 直写页缓存

在 CPU 专心跑别的应用程序的同时，硬盘主控芯片从闪存颗粒或旋转盘片上读出那 4096 字节，化身总线主设备走 **DMA**（穿过 IOMMU 的地址翻译与权限把关），直接把数据原封不动地写进刚才占好坑的那一页内核页缓存里。CPU 全程没搬一个字节！

### 6. 硬盘敲铃报喜：硬件中断与延后收尾

数据稳稳落进内存后，硬盘往完成环里写下“成功”回执，并拉响一条**硬件中断**（或在高负载轮询模式下被内核查到）。

CPU 暂停手里正在跑的某个倒霉路人线程切进内核中断入口：快速上半部迅速确认硬盘中断、安排延后处理后撤离；延后完成路径接着检查回执无误、解除临时 DMA/IOMMU 映射、把那页页缓存的标志正式改成“数据最新可用”，最后顺着等待队列拍醒刚才睡着的 `read` 线程！（万一硬盘撞上坏道返回错误，内核也会把错误状态标在页上，让醒来的线程收到 `-EIO` 报错。）

### 7. 醒来不是立刻飞奔：重回就绪队列等调度

请格外留神这极其容易被忽略的一拍：**硬盘中断唤醒线程，只是把它的状态从“等待”改回“就绪”，绝不代表它这一微秒就立刻霸占了 CPU！**

```text
磁盘中断完工 -> 唤醒线程（Blocked -> Ready）-> 等待调度器点名 -> 恢复现场（Running）
```

如果此时机器上正挤着几十个满载的 CPU 密集型任务，哪怕高速 NVMe 固态盘只花 50 微秒就把数据搬进了内存，你的 `read` 线程照样可能在就绪队列里干排几毫秒才轮到上台收尾！

### 8. 恢复内核现场、拷贝字节、圆满返程

调度器终于点中了 `read` 线程，恢复它的内核栈和寄存器，让它从当初第 4 步睡下的那一行无缝醒来！它确认页缓存已经就绪，走上和快车道完全相同的收尾动作：安全拷贝 4096 字节到用户 `buffer`，把文件偏移加 `4096`，最后执行返回指令降回用户态，把返回值 `4096` 稳稳交到你的 C 代码手里。

## 为什么 `read(fd, buffer, 4096)` 有时只返回了 `1200`？

很多新手看到 `read` 返回了小于 `4096` 的正数，以为一定出了 bug。其实**短读（Short Read）**在系统编程里完全合法且常见：
- 文件总共就剩 `1200` 字节就到末尾了；
- 你读的是管道、终端或网络套接字，此刻缓冲区里恰好只到了 `1200` 字节；
- 漫长的阻塞期间飞来一个操作系统信号，刚好已经搬了一部分字节于是提前返回；
- 某些特殊字符设备按自身的记录帧边界返回。

记住三条返回值铁律：**返回正数 $n$** 表示成功搬了 $n$ 字节（未必等于请求上限）；**返回 `0`** 在普通文件和流式连接里表示到达终点（EOF，别再傻傻死循环读下去了）；**返回 `-1`** 才是真的报错（需查 `errno` 区分是被信号打断 `EINTR`/暂不可读 `EAGAIN`，还是真故障）。因此读固定长度的稳健代码永远写成循环：

```c
size_t done = 0;
while (done < sizeof(buffer)) {
    ssize_t n = read(fd, buffer + done, sizeof(buffer) - done);
    if (n > 0) done += (size_t)n;
    else if (n == 0) break;
    else handle_error_or_retry();
}
```

当然，对于交互式聊天或网络流，收到先到的 `1200` 字节往往应该立刻解析处理，不必死磕凑满 `4096` 平白拉长交互延迟。

## 这趟旅程里，锁都埋在哪些暗处？

别忘了，同一台多核机器上可能有上百条线程在同时读同一个文件或同一个目录！沿着刚才那条路线，内核悄悄布满了多层精细同步：
- 进程 `fd` 表的引用计数与并发关闭保护；
- 共享打开文件对象里偏移游标的同步；
- inode 元数据与数据块映射表的读写锁；
- 页缓存树及单个缓存页的“正在读入”页锁与等待队列；
- 块层提交队列与驱动描述符环的每核锁/原子尾指针；
- 拷贝到用户缓冲区缺页时的进程页表锁。

这里有一条极其重要的内核设计哲学：**绝不抱着高层全局大锁去等慢吞吞的磁盘 I/O！** 内核会先在锁内拿到稳定引用、把单页标上“正在读入”标志，立刻放开所有目录和树级大锁，再去从容提交块请求并睡觉，绝不连累其他读取别的文件页的线程。

## 换两种姿势读同一个文件：`mmap` 与直接 I/O

把普通 `read()` 走透之后，拿它和前两篇学过的两种替代方案一比，优劣高下立判：

- **换用 `mmap` 文件映射**：进程直接把文件映射进虚拟地址空间。首次读那个指针地址时触发缺页，内核直接把**同一页内核页缓存**挂进进程页表——从此 CPU 直接读内存，省掉了 `copy_to_user` 的整页拷贝和频繁系统调用！代价则是缺页等待隐身在了普通内存加载指令里，面对文件突然被别人截断（可能触发 `SIGBUS` 崩溃）和映射生命周期管理更棘手；而且对于小块顺序读，现代 `read()` 配合内核自适应预读未必会输。注意：`mmap` 和 `read` 共享的是**同一份页缓存**，绝不是两套平行副本。
- **换用直接 I/O（`O_DIRECT`）**：绕开内核页缓存，让磁盘 DMA 直接把数据写进用户态对齐且钉死的缓冲区（或临时内核映射），专治专业数据库“内核缓存 + 数据库缓冲池”双重占用内存的浪费。但它省掉的只是页缓存这一站，系统调用、权限检查、块映射、块层、驱动、DMA、IOMMU 和中断一步都没少！

## 把延迟劈开看：性能分解与安全红线

当你在线上抱怨“怎么一次 `read()` 花了 15 毫秒？”时，心里应该立刻弹出两道账单公式：

- **若命中页缓存**：
$$
T_{hit}=T_{syscall}+T_{lookup}+T_{copy}+T_{return}.
$$
- **若未命中页缓存**：
$$
T_{miss}=T_{submit}+T_{queue}+T_{device}+T_{completion}+T_{schedule}+T_{copy}.
$$

如果只看总耗时 15 毫秒，你根本分不清是硬盘真的慢了 14.9 毫秒（$T_{device}$），还是块队列排了长龙（$T_{queue}$），抑或硬盘 0.1 毫秒就读完了、可你的线程在就绪队列里被抢占干等了 14.9 毫秒（$T_{schedule}$）！要想逐项拿到真凭实据，就需要联合系统调用跟踪、主要缺页统计、块设备延迟和 off-CPU 火焰图——我们在第 13 章的[诊断工具、实验方法与自测](02_diagnostics_self_test.md)里会亲手演练整套抓证手法。

同时，整条路径横跨了“用户程序 $\leftrightarrow$ 内核 $\leftrightarrow$ 外部硬件”多重信任边界，每一站都埋着安全红线：打开与读取全程严格校验 `fd` 权限；用户指针必须安全跨界拷贝；偏移加长度必须严防整数溢出；文件系统解析磁盘上的元数据时不能轻信损坏甚至恶意篡改的 U 盘镜像；DMA 必须靠 IOMMU 牢牢锁死在授权物理页内。

## 刻进骨子里的四条反直觉真相

合上这趟 `read()` 旅程，再回头默念四条最常被初学甚至资深开发者搞错的结论：

1. **进入内核态 $\neq$ 切换进程**：页缓存命中时，进出内核全程都是同一条线程一气呵成。
2. **调用 `read()` $\neq$ 读取物理硬盘**：绝大多数热文件读取在页缓存这一站就凯旋返回了。
3. **磁盘中断完工 $\neq$ 线程立刻继续跑**：中断只是把线程唤醒放回就绪队列，何时上台还得听调度器排班。
4. **读到新数据或 `write()` 返回 $\neq$ 数据已安全落盘**：页缓存里的字节随时可能随断电灰飞烟灭！

等等——盯住上面第 4 条！这一整章，我们把“读数据”和“硬件搬运”走得无比丝滑。可现在反过来问一个让人脊背发凉的问题：**写文件呢？** 往文件里追加一段数据，往往要同时改写“空闲块位图”“inode 大小与指针”“目录项”以及“数据块本身”好几个分散在磁盘不同角落的块。如果写完一半、刚改好目录项还没来得及写完数据块，机房突然断电跳闸——明天重启电脑时，整个文件系统岂不是乱成一锅谁也修不好、甚至把旧垃圾暴露给新用户的废墟？

操作系统究竟靠什么精巧机制（**日志 Journaling** 与 **写时复制 CoW**），让一块随时可能断电的硬盘在重启后依然纹丝不乱？让我们立刻推开下一章的大门——[第 7 章 持久化与崩溃恢复](../chapter_05_storage_io/02_journaling_crash_disk.md)！

## 自测

1. 既然目标文件数据已经在页缓存稳稳命中了，为什么这次 `read()` 在拷贝阶段依然有可能触发缺页异常？
2. 当页缓存未命中、驱动把读请求发给硬盘之后，内核为什么要立刻让当前线程睡眠，而不是原地等硬盘读完？
3. 既然 DMA 已经替 CPU 把 4096 字节直接搬进了内存页缓存，传输完成后为什么依然需要 CPU 来处理中断或完成队列？
4. 硬盘发来中断宣告数据搬运完成，为什么原 `read` 线程在那一微秒不一定马上就能恢复执行？
5. 用 `mmap` 映射文件并用指针读取，和直接调用 `read()` 读同一个文件，两者在内核底层维护的是两份独立的缓存吗？
6. 对于普通本地文件，`read()` 返回 `0` 和返回 `-1` 各自传达了什么截然不同的信号？

??? note "参考思路"

    1. 文件源页虽在页缓存里，但用户程序提供的目标 `buffer` 虚拟页可能尚未分配物理页框（按需分配）或正处于写时复制（COW）只读状态，因此内核执行 `copy_to_user` 往里写数据时仍可能触发用户页的次要缺页。
    2. 磁盘读取通常耗时数十微秒至数毫秒，远慢于 CPU 指令周期；让当前线程阻塞睡眠把 CPU 让给其他就绪线程，能用并发隐藏漫长的 I/O 延迟、维持整机高吞吐。
    3. CPU 仍需响应中断、检查硬件回执是否出错、解除 DMA/IOMMU 映射、回收描述符槽位、将页缓存页标记为“最新可用”，并把等待队列里睡着的线程唤醒。
    4. 中断完成路径只是把线程状态从“等待”改回“就绪”，它还必须进入就绪队列，等待调度器按优先级和时间片算法重新选中并切换上下文后才能恢复执行。
    5. 不是。现代主流操作系统采用统一页缓存设计，`mmap` 和 `read`/`write` 通常直接共享同一批内核页缓存页，从而保证基本视图一致并省去双份内存浪费。
    6. 返回 `0` 表示正常到达文件末尾（EOF），没有更多字节可读；返回 `-1` 表示本次读取发生错误或被中断，具体原因必须读取线程局部错误码 `errno`（如 `EAGAIN`、`EINTR`、`EBADF`、`EIO` 等）来区分。
