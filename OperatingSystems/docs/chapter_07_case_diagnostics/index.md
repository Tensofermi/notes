# 诊断案例概览 { #7 }

## 排障最忌“盲人摸象”：每次只验证一个可证伪假设

顺着前面十二章一路走来，我们已经逐层拆开了一台现代计算机（乃至一整座集群）里的每一台齿轮：特权边界与系统调用、进程线程与调度、锁与死锁、虚拟内存页表、文件系统与块设备 DMA、权限沙箱与容器虚拟化，以及集群编排与恢复。

可到了真实线上故障现场，bug 和性能瓶颈从来不会礼貌地举着牌子告诉你“你好，我是第 5 章的缺页问题”。举个最典型的例子：一个进程在日志里打印完“开始读取数据”之后，足足卡死了整整 10 秒钟才吐出下一行！

面对这沉默的 10 秒，新手往往一拍脑袋开始瞎猜：“一定是硬盘太慢了！”或者“快加 CPU 核数吧！”可只要把前面学过的机制摆在脑海里一对照，立刻就能列出一串截然不同、修法南辕北辙的候选真相：
- 它可能真的在**阻塞等磁盘**把冷数据搬进页缓存；
- 也有可能磁盘 0.2 毫秒就读完了，可这台机器 CPU 严重过载，线程醒来后在**就绪队列里干等了 9.9 秒**才被调度器重新选中；
- 还有可能数据早就在内存里了，但它被卡在一把别人没放开的**内核或用户态锁**门口！

怎么一眼把它们区分开？别靠猜——为每一个假设写下一条**能把它彻底证伪的可观测证据**（比如同时记录“块设备请求完成时间”和“线程重新上 CPU 的时间”），一次只核实一个变量，把不符合证据的解释一条条划掉！这就是最后这一部分要锤炼给你的核心工程内功。

## 为什么必须学会“跨层串联诊断”？

单拎出一章来背诵“`read` 是系统调用”“页缓存加速读取”“DMA 减少 CPU 拷贝”轻而易举；可真实系统里，一次简单的文件读取既可能瞬间命中页缓存却在拷贝到用户缓冲时触发次要缺页，也可能在提交块设备请求后让线程睡眠、被中断唤醒后又在就绪队列里排队，返回前还要撞上短读或信号打断；而放在容器与集群里，还要叠加 cgroup CPU 节流、内存上限回收和共享存储网络抖动！

只有脑子里装着一整张跨层条件分支图，看到任何一个孤立监控数字时，你才不会被表面假象带偏。

## 科学的系统诊断闭环

每当你接手一台“变慢”或“卡死”的机器时，按这七步闭环推进，稳准狠：

```text
1. 精准描述现象（谁慢？何时起？平均慢还是 P99 尾延迟慢？）
   -> 2. 对照架构分层，列出 2–3 个互相排斥的候选假设
   -> 3. 挑选对线上扰动最低的第一轮聚合观测证据
   -> 4. 把不同层次的时间线与计数器对齐比较
   -> 5. 用硬证据毫不留情地排除不成立的假设
   -> 6. 构造最小可复现实验，实施针对性修复
   -> 7. 复测验证：确认问题真正消退，而不是把瓶颈悄悄转移到了下一层队列！
```

## 走完收官篇，你将具备的能力

- 面对任意一次 `read`/写盘异常，迅速画出页缓存命中与未命中的分叉证据链；
- 熟练区分线程处于 **on-CPU（正在算）**、**runnable（排队等核）**、**sleeping（阻塞等事件）** 三种状态，不再盲目乱抓火焰图；
- 为高 CPU、频繁上下文切换、持续主要缺页、高 I/O 延迟和锁竞争各自挑出最精准的第一批只读观测命令；
- 警觉工具本身的“观测者效应”与指标陷阱（如 `free` 内存列、多队列 NVMe 的 `%util`），绝不把时间上的相关性草率当成因果关系；
- 真正用操作系统底层的机制与权衡推理未知故障，而不是靠背诵零散名词碰运气。
