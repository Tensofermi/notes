# 集群编排：提交、准入、放置与执行

**先修**：[单机调度](../chapter_02_processes/03_cpu_scheduler_lab.md)、[从镜像到进程](../chapter_06_protection_virtualization/03_image_to_process.md)。

**读完能做**：拿任务状态解释它在等谁，分清平台、集群和节点的职责。

## 先写一份最小任务请求

设任务需要两张 GPU，在同一台机器运行，输入为数据集 D 的第 3 版，使用镜像摘要 I。提交接口把**期望**存下来；任务的**实际状态**来自控制器、调度器、节点以及程序的观测。只返回「接收成功」时，平台可能还没拿到资源，也可能还没开始启动容器。

| 阶段 | 谁作决定 | 一个常见等待原因 |
| --- | --- | --- |
| 提交 | API 校验任务、身份、配置，并记录用户意图 | 数据集引用或权限校验未通过 |
| 生成执行对象 | 控制器根据意图协调实际对象 | 依赖配置尚未就绪 |
| 准入 | 批任务队列根据配额及就绪条件决定是否放行 | 项目配额不足 |
| 放置 | 调度器根据资源和约束选择可行节点 | 两台节点分别只有一张空闲 GPU |
| 启动与执行 | 节点组件、运行时和内核使进程运行 | 拉镜像失败、设备初始化失败或进程退出 |

这是一组职责；不同任务集成方式的对象创建和状态更新时间可以不同。教学上允许把阶段画成「已提交 → 等待准入 → 等待放置 → 启动中 → 运行中 → 终止」，把失败、取消与重试明确画成分支。

## 为什么控制器要重复对账

控制器读取期望和实际状态，然后做一次使两者更接近的操作。若控制器在创建执行对象后立即退出，下次醒来应该先查询并复用已经创建的对象。用可重复的标识、明确的归属关系和状态核对，能降低重复执行的风险。API 里的状态只是观察到的结果，更新可能滞后，排查时还需要看事件时间、运行尝试编号和节点观察值。

Kubernetes 的自定义资源定义（CRD）可以扩充 API 所支持的资源类型。MatrixInfra 的 API/CLI 接收任务配置，Recipe 描述运行需要的环境和入口等约定，控制器再将任务转换成相应执行对象。对接 Kueue 的批任务可通过准入控制项目资源，Kubernetes 调度器负责给 Pod 选择节点。节点上的设备插件等机制使 GPU 等设备资源能被发现并提供给工作负载。K3s 提供 Kubernetes 发行版这一层的承载。

## 配额、拓扑与使用率

两台机器各剩一张卡，项目还有两张卡配额。一个要求同机双卡的任务可以通过简单配额检查，却没有可行放置。若项目只剩一张卡配额，则应先研究队列与配额。支持拓扑感知的准入也可以更早发现某些容量约束。公平共享、优先级和抢占会影响长时间等待、资源空闲和中断成本。

任务占用两张卡 30 分钟，记录 1 GPU·小时的分配量。计算活动、显存占用和有效吞吐要另外观察。计费或内部成本分摊时，明确用的是分配时间、实际执行时间还是其他指标。
