# 集群编排：提交、准入、放置与执行

**先修**：[调度实验：就绪、运行与等待](../chapter_02_processes/03_cpu_scheduler_lab.md)、[从镜像到进程](../chapter_06_protection_virtualization/03_image_to_process.md)。

**读完能做**：拿到一条集群任务的状态卡住时，一眼判别它究竟卡在配额排队、物理选机还是单机启动，并理清平台 API、控制器、集群调度器与单机节点各自的分工。

## 一台机器变成一组机器后，为什么不能直接“一键启动”？

在[第 3 章单机调度实验](../chapter_02_processes/03_cpu_scheduler_lab.md)里，世界简单得多：进程已经在本机内存里了，内核调度器只需每隔几毫秒问一句“这颗 CPU 下一步交给谁跑？”。

现在把机房门推开：两个研发团队共享着由两台物理服务器组成的小型**集群**（cluster），其中每一台独立服务器称为一个**节点**（node）。两台节点各自插着 2 张适合大规模矩阵并行计算的 **GPU 加速卡**（全集群共 4 张卡），每个团队在平台里都被划定了各自可用的资源预算上限，即**配额**（quota）。更麻烦的是，有些训练作业因为卡间高速通信要求，必须拿到**同一台节点上的 2 张卡**，而且不同节点上预装的驱动版本、挂载的数据存储也可能各不相同。

面对这么多跨机约束，平台不可能像单机敲一条命令那样直接拉起进程，而是必须把决定拆成环环相扣的四道关卡：
1. **提交（Submission）**：校验用户身份与参数，把用户的意图原原本本持久化记下来；
2. **准入（Admission）**：按团队配额、队列优先级与公平规则，裁决“现在能不能把这份预算划给它”；
3. **放置（Placement）**：在满足算力、内存与硬件拓扑约束的候选机器里，挑出最合适的一台（或多台）物理节点；
4. **执行（Execution）**：被选中的节点拉取容器镜像、挂载数据、配置设备与 cgroup，最终交给单机操作系统内核拉起进程！

把这一整套跨机器的状态流转、资源分配与故障兜底有序组织起来的系统工程，就是**编排**（orchestration）。

## 先写一份最小任务请求：接口返回“成功”意味着什么？

设想用户向平台提交一个作业：需要同机 2 张 GPU，读取“数据集 D 的第 3 版”，运行环境指定一份精确锁定了**内容摘要（digest）**的[容器镜像](../chapter_06_protection_virtualization/03_image_to_process.md)。

当平台 **API** 返回 `200 OK：接收成功` 时，很多初学者会误以为“太好了，我的训练已经在 GPU 上跑起来了！”其实远远不是——API 做的第一件事只是把你这份**期望状态（Desired State）**稳稳写进平台数据库。接下来，幕后有一组分工明确的系统组件接力推动它：
- **控制器**（controller）：不知疲倦的“对账管家”，反复比对数据库里的“期望状态”和集群里的“实际现状”，替你的作业生成具体落地用的**执行对象**（写明要起哪个容器、传什么启动命令、申请多少卡与内存）；
- **集群调度器**：根据全集群各节点此刻的剩余资源和亲和/拓扑约束，为执行对象挑选落脚的物理节点——请注意区分：**它和第 2 章的单机 CPU 调度器虽然同名，却身处完全不同的层次——一个以秒/分钟为尺度“给作业挑机器”，另一个以毫秒为尺度“给线程分 CPU 时间片”！**

把每一关的决策者和最常见的卡顿原因排成一张表，以后看集群状态就再也不会一头雾水：

| 所处阶段 | 谁在拍板做决定 | 卡在这一步最常见的真实原因 |
| --- | --- | --- |
| **1. 提交** | 平台 API 校验身份、权限与参数格式 | 镜像名写错、数据集不存在、或无权访问该项目 |
| **2. 生成执行对象** | 控制器把业务作业翻译成底层容器规格 | 依赖的密钥、配置或前置任务尚未就绪 |
| **3. 准入** | 队列与配额管理器核对预算与优先级 | 团队配额已耗尽，正排在同团队或全局队列里等额度 |
| **4. 放置** | 集群调度器按资源与拓扑筛选物理节点 | 集群总空闲卡数看似够，但没有任何**单台节点**凑得出同机双卡 |
| **5. 启动与执行** | 目标节点拉镜像、挂目录、分设备并交给内核 | 镜像仓库拉取超时、存储卷挂载失败、GPU 驱动异常或代码启动即崩溃 |

在教学和运维看板里，可以清晰地把这条主干画成状态机：`已提交 -> 等待准入 -> 等待放置 -> 启动中 -> 运行中 -> 已终止`，再把失败、取消与重试作为明确分支挂在旁边。

## 慢镜头走查：跟着双卡任务 `J` 熬过 8 个时刻

为了彻底摸清“配额不够”和“机器放不下”的微妙差别，我们跟着任务 `J` 走一遍时间线。

**初始舞台**：集群有节点 `N1` 和 `N2`，每台各装 2 张 GPU，一开始两台机器上各跑着一个单卡老任务（所以 `N1` 剩 1 张空闲卡、`N2` 剩 1 张空闲卡）。任务 `J` 需要**同机 2 张卡**，它所属的团队起初只剩 1 张卡的配额。注意：这里的**空闲卡**指的是尚未在账本上分配给任何任务的卡——哪怕某张已分配出去的卡此刻刚好处于 0% 算力空闲，也绝不能偷偷一卡两卖！节点准备环境时，还需把数据目录[挂载](../chapter_06_protection_virtualization/03_image_to_process.md)进容器文件树。

下面每个时刻我们只变动一个条件，仔细盯着 `J` 究竟被什么拦住：

| 时刻 | 集群里发生了什么变化 | `J` 此刻的真实处境与下一步 |
| ---: | --- | --- |
| **0** | API 校验通过，将任务 `J` 持久化记入数据库 | 提交成功，进入**等待准入** |
| **1** | 准入检查：团队剩余配额仅 `1` 张，而 `J` 需要 `2` 张 | 预算不够！继续**等待准入**（连选机器的门都没进） |
| **2** | 同团队另一个旧任务结束，团队可用配额涨到 `2` 张 | 预算过关！平台预留额度、`J` 获准放行；**但 `N1`、`N2` 各自只有 `1` 张空闲卡，均不满足同机双卡约束**，于是 `J` 卡在**等待放置**！ |
| **5** | `N1` 上占着卡的旧任务跑完释放，`N1` 空闲卡变成 `2` 张 | 终于有单台节点凑齐 2 张卡！调度器果断选中 `N1` 绑定 `J` |
| **6** | `N1` 领命开工，但本地还没缓存这个大镜像，正从仓库下载 | 节点已定，处于**启动中**（等待拉取镜像与挂载数据） |
| **8** | 镜像拉完、数据卷挂妥、容器进程在 `N1` 内核中成功启动 | 正式进入**运行中**，开始输出训练日志并消耗算力 |

请狠狠盯住**时刻 2**——这是集群运维里最容易把人绕晕的一幕！如果你粗略地把整个集群的空闲 GPU 加在一起算总账：$1 + 1 = 2$ 张，明明够任务 `J` 用啊，怎么还死死卡在“等待放置”呢？

原因正是你在第 5 章虚拟内存里早就打过交道的老熟人——**资源碎片**（resource fragmentation）！内存里两块不连续的 8 MB 空隙装不下一个要求 12 MB 连续内存的程序；集群里分属两台节点的各 1 张空闲 GPU，同样装不下一个要求**同机 2 卡**的作业！在更庞大的真实集群里，准入系统有时还会把机架、高速互联网络等**拓扑（Topology）**信息一并纳入早期检查，防止作业早早占住了配额却迟迟找不到满足拓扑的节点。把“配额准入”和“物理放置”拆开观察，你一眼就能分辨此刻该找管理员申请涨预算，还是该去排查集群碎片。

??? question "趁热打铁做个预测：如果时刻 5 空出那张卡的不是 `N1`，而是 `N2`，接下来会发生什么？又假如时刻 6 镜像拉取一直报错超时，给团队再追加 10 张 GPU 配额能救活任务 `J` 吗？"

    若时刻 5 释放的是 `N2`，那么 `N2` 就从 1 张空闲变为 2 张空闲，调度器自然选中 `N2`（要是两台同时满足，调度器还会按负载均衡或凑整防碎片的打分策略挑出更优者）。至于时刻 6 镜像拉取失败，任务早过了准入和放置两关，卡死在节点启动环境阶段——此时给团队再多配额也毫无用处，必须直接去查 `N1` 节点上的拉取错误事件、仓库网络或认证密钥！

??? example "不用搭集群，用 12 行 Python 重放上面四个关键时刻"

    下面把同机双卡任务的推进逻辑浓缩成三个顺序判断：`team_free` 表示团队剩余配额，`free_by_node` 记录各节点空闲卡数，`ready` 代表镜像与挂载等节点准备动作是否完成。试着改一改输入，观察任务最早会在哪一道闸门停住：

    ```python
    def observe(needed, team_free, free_by_node, ready):
        if team_free < needed:
            return "waiting for quota"
        eligible = [name for name, free in free_by_node.items() if free >= needed]
        if not eligible:
            return "waiting for node"
        return "running" if ready else "starting"

    print(observe(2, 1, {"N1": 1, "N2": 1}, False))  # waiting for quota
    print(observe(2, 2, {"N1": 1, "N2": 1}, False))  # waiting for node
    print(observe(2, 2, {"N1": 2, "N2": 1}, False))  # starting
    print(observe(2, 2, {"N1": 2, "N2": 1}, True))   # running
    ```

    这段迷你脚本展示的是“放置前静态快照”的核心判别逻辑；真实生产平台还会原子记录已预留的配额、已绑定的节点名，并妥善处理多任务并发抢卡与重试。

## 为什么集群控制器偏爱“反复对账”而不是“发完命令就忘”？

设想一下：控制器刚刚替任务 `J` 在集群里建好了底层执行对象，还没来得及回数据库把状态更新成“已创建”，控制器所在的进程突然崩溃重启了！等它 3 秒后重新醒来，如果按传统“一次性命令脚本”的思路傻傻重跑一遍流程，它就会再建出**第二个一模一样的重复执行对象**，把同样的昂贵 GPU 训练跑上两份！

为了在随时可能宕机、丢包、重启的分布式集群里站稳脚跟，现代编排系统普遍采用**声明式控制循环**——不断重复的**协调**（reconcile）机制：

```text
循环：
  1. 读取“期望状态”（例如：数据库说“任务 J 应当存在 1 个执行对象”）
  2. 观测“实际现状”（去集群里查一查：属于 J 的执行对象现在究竟有没有、处于什么状态？）
  3. 计算两者差异，只做一步把现状推向期望的幂等动作！
```

看看刚才那个崩溃场景怎么瞬间被化解：控制器重启醒来后，**先查现状再动手**——它凭着任务 `J` 稳定的唯一标识和归属标签，一眼看到属于 `J` 的执行对象其实已经建好了，于是绝不重复新建，只需顺手把缺失的状态记录补写完整即可！集群世界的可靠性，从来不是靠祈祷“每次流程都顺顺当当跑完最后一行”，而是靠**稳定身份 + 反复观测现状 + 幂等纠偏**炼出来的。

### 对照真实工业底座：Kubernetes、Kueue 与 MatrixInfra

把上面抽象出来的每一块拼图，严丝合缝地贴回今天最主流的开源集群编排生态 **Kubernetes**（及其轻量发行版 **K3s**），你会发现所有晦涩术语瞬间都有了家：
- **Pod**：Kubernetes 调度的最小部署单元——把必须同生共死、安排在同一台节点上运行的一个或多个紧密协作容器打包在一起；
- **设备插件（Device Plugin）**：跑在各个物理节点上的硬件上报员，负责探查本机插着几张健康的 GPU 并把可分配数量汇报给集群；
- **Kueue**：专为“提交后跑完即止”的批处理与训练作业打造的**队列与准入管家**，掌管多团队配额、公平共享与抢占；
- **kube-scheduler**：真正的**集群放置调度器**，为已经通过 Kueue 准入的 Pod 逐台筛选并打分，拍板把它绑定到最合适的物理节点；
- **kubelet**：驻守在每台物理节点（如 `N1`）上的本地大管家，一看到集群账本把某个 Pod 绑定给了自己，立刻指挥本机的[容器运行时](../chapter_06_protection_virtualization/03_image_to_process.md)拉镜像、挂存储、配 cgroup 与 GPU，最终交给宿主机 Linux 内核把进程跑起来！

而在第 13 章即将实操的 **MatrixInfra** 训练平台案例中，用户只需通过命令行或 API 提交一份写明运行环境与启动指令的 **Recipe** 配置；平台借助 Kubernetes 的**自定义资源定义**（Custom Resource Definition，**CRD**）把训练作业声明为原生集群对象，再由专用控制器持续 `reconcile`，一路护送这份意图落地成节点上飞速运转的 GPU 进程。

## 集群排班的三难困境：利用率、公平与防饥饿

单机调度里我们见识过短任务和长任务的博弈；到了动辄数万元一张加速卡的集群里，排班策略的每一次取舍都直接关系到真金白银：

1. **填缝（Backfilling）还是死守队头？** 设想需要 8 张卡的大模型训练排在队头，眼下集群里刚好零散空着 2 张卡，而排在后面的小任务只要 1 张卡。如果放小任务插队先跑（填缝），眼前集群利用率立刻漂亮了许多；可要是源源不断的小任务一直插队把卡占零碎，队头那个 8 卡大作业就会**永远凑不齐整机、活活饥饿！** 反过来，为了保护大作业强行把空出来的卡先“预留干晾着”等其他旧任务陆续结束凑齐 8 张，短期内又得忍受昂贵的 GPU 闲置空转。
2. **公平共享、优先级与抢占**：高优先级紧急任务或欠了额度的团队，有时必须直接**抢占**正在跑的低优先级任务强行把卡腾出来——被半路踢下场的任务，就只能指望从上一次保存好的恢复点（[checkpoint](02_retries_and_artifacts.md)）重新接续，避免前面几小时算力全部打水漂！（想亲手拨弄到达顺序、亲眼对比先来先服务、填缝和抢占的差距，不妨顺手玩一玩<a href="../../DataStructuresAndAlgorithms/chapter_task_scheduling/index.html">任务调度模拟</a>。）
3. **分配量 $\neq$ 真实有效算力**：任务霸占着 2 张 GPU 跑了 30 分钟，平台计费账本上记的是实打实的 **1 GPU·小时** 的分配量；可在这 30 分钟里，GPU 核心到底是一直在高速做矩阵乘、还是因为单机 CPU 数据预处理太慢/硬盘读太慢而 80% 的时间都在空转等数据？显存用了多少、每秒吞吐多少样本？计费核算和性能优化必须把“占着卡的时间”和“卡真正在算的时间”分开量！

---

到这里，我们已经把任务从“用户敲下提交”一路护送到了“在节点 GPU 上顺利跑起来”。可分布式集群的真正考验，往往从**出意外的那一刻**才刚刚开始——如果点击提交时网络突然抖了一下报了超时，重发一次会不会跑出两份任务？如果训练跑了三个小时，节点 `N1` 突然断网失联、检查点刚写到一半，平台怎么知道它究竟是死了还是只是卡了一下？重启的新尝试又该如何避免和假死复活的旧尝试把同一个结果目录写乱？

带着这些惊心动魄的分布式可靠性拷问，让我们迈进[第 12 章 任务生命周期与可靠性](02_retries_and_artifacts.md)！

## 自测

1. 团队同时提交了两个都需要同机 2 张 GPU 的训练任务：任务 A 状态显示“等待准入”，任务 B 显示“已获准，但等待节点放置”。作为平台排障人员，你应该分别去查哪两套完全不同的证据？
2. 为什么集群控制器不能采取“创建完执行对象就立刻记完事，不再回头核对”的一次性脚本模式，而必须围绕稳定标识做反复协调（`reconcile`）？

??? note "参考思路"

    1. 对任务 A（卡在准入），应优先检查所属队列、团队剩余配额、任务优先级与准入规则（比如是不是被高优队列或其他在跑任务占光了预算）；对任务 B（已准入但无节点），预算已经不是瓶颈，应立刻去查集群调度器的打分失败事件、各物理节点剩余空闲卡数（是不是遭遇了跨机资源碎片）、节点硬件标签与拓扑约束。如果已经成功绑定到节点却迟迟没跑起来，再去查该节点上的镜像拉取、存储挂载与设备启动事件。
    2. 因为分布式环境里控制器随时可能在“发出创建请求后、写回自身状态前”崩溃重启，或遭遇网络超时导致结果未知。只有借助稳定标识反复观测集群实际现状并执行幂等纠偏，才能既不遗漏未建好的对象，也不重复拉起双份昂贵任务。
