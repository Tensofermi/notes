# 任务失败以后：幂等、产物和恢复

**先修**：[文件崩溃一致性](../chapter_05_storage_io/02_journaling_crash_disk.md)、[任务状态](01_jobs_and_admission.md)。

**读完能做**：区分提交重试、运行重试和 checkpoint 恢复，知道每一步要保留什么证据。

## 超时意味着结果未知

客户端提交任务 POST，请求可能未到达，也可能任务已创建、回应丢了。重发相同请求如果会创建新 ID，就可能启动两份工作。一个常见设计是为同一次业务操作复用幂等键，让服务端原子地记录键与任务 ID；遇到同键同内容返回已有结果，同键不同内容报告冲突。客户端先查询进度，再带退避地重试暂时性错误。

接收端记录幂等键需要存储和过期策略。保留时间短于客户端可能重试的窗口，仍可能出现重复。运行层重试也需要独立的尝试编号，以便把各次日志、退出码和产物对应到同一任务。

## 从部分故障恢复

| 看到的现象 | 先问什么 | 恢复时要保留什么 |
| --- | --- | --- |
| 心跳超时 | 进程真停了，还是暂时失联 | 签发的租约、身份和状态时间 |
| 进程退出 | 是暂时性故障还是可重复的配置错误 | 退出码、最近事件与尝试编号 |
| 文件只写了一半 | 有无可识别的完整版本 | 完成标记、文件校验和上一份完整 checkpoint |

心跳是带超时假设的一条信号。需要避免旧任务在失联后恢复并覆盖新任务的结果，可以给每次尝试独立输出位置，且只允许当前授权尝试发布最终引用。健康检查应区分服务能否接收流量与进程是否要重启。

## 目录记录和数据位置

一个产物记录可以含任务与尝试编号、数据集版本、代码版本、镜像摘要、生成时间、存储位置和内容校验值。实际字节可仍在受控的机器存储，登记一条记录不会搬运文件。使用前验证读权限和完整性。

| 存储 | 提交结果时关注 |
| --- | --- |
| 本地文件系统 | 同一文件系统内的提交步骤，以及主机故障后是否还能访问 |
| 共享文件系统 | 共享可见性、故障域、并发写入与挂载权限 |
| 对象存储 | 对象版本、提交清单、校验与多对象产物的发布条件 |

单文件可用临时文件、刷盘和同目录重命名来组织发布，并根据文件系统要求处理目录项持久化。多文件 checkpoint 可先写各分片并验证，再发布指向完整版本的清单。恢复时读最近一个完整版本，根据程序需要恢复参数、优化器状态和训练进度。日志、指标与追踪可以关联诊断，但重启后还需要可恢复的任务和产物状态。

## 自测

发送方提交超时，后来看到两个容器都打印了同一任务名。你先查什么？

??? note "参考思路"
    查任务 ID、幂等键和尝试编号，区分重复提交、正常重试或旧尝试未退出。再查哪一次被允许发布产物，避免仅看日志文本就选择 checkpoint。
