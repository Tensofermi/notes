# 任务失败以后：幂等、产物和恢复

**先修**：[崩溃一致性、日志与磁盘调度](../chapter_05_storage_io/02_journaling_crash_disk.md)、[集群编排：提交、准入、放置与执行](01_jobs_and_admission.md)。

**读完能做**：清晰分辨“重发提交请求”“整次重新运行任务”和“从最近一份完整检查点接续运行”三种恢复动作，并能说出每一步必须留存哪些防错证据。

## 客户端只看到了“超时”，服务端却可能早就干成了！

先按时间线放慢一次再常见不过的远程任务提交：
- **时刻 0**：客户端向集群平台发起一次 HTTP `POST` 请求，请求创建一个昂贵的 8 卡训练任务，并在请求头里附上自己为这次操作生成的唯一标记 `demo-42`；
- **时刻 1**：服务端顺利收到了请求，通过校验，在持久化数据库里把 `demo-42` 和新生成的任务编号 `J7` 原子地绑在一起存了下来，随后准备把 `J7` 写进回包；
- **时刻 2**：就在回包刚飞出服务端网卡的那半毫秒，中间一台交换机闪断了一瞬间——回包凭空蒸发了！

现在切到客户端的视角：它干等了 10 秒钟，只收到冰冷的一句 `Timeout（请求超时）`。客户端完全被蒙在鼓里——**那个请求究竟是半路丢了压根没送到服务端，还是服务端其实已经建好了 `J7`、只是回包丢了？**

如果客户端贸然重新发一次完全不带标记的 `POST`，服务端会乖乖再建一个全新的 `J8`，瞬间把你宝贵的 8 卡训练平白无故跑出两份！破局的关键，在于前面附上的那个小标记 `demo-42`：客户端重试时原封不动带着 `demo-42` 重发；服务端一查数据库，发现 `demo-42` 早就登记过、对应 `J7`，于是绝不重复创建，直接把现成的 `J7` 安稳返回给客户端！

这种“同一个操作执行一次，和因为重试重复执行十次，最终产生的系统状态完全一致”的黄金性质，叫作**幂等**（idempotence）；那个专门用来帮服务端认出“这只是上一次请求的重复敲门”的唯一标识，叫作**幂等键**（idempotency key）。

??? question "如果客户端在第二次重试时，复用了同一个幂等键 `demo-42`，却悄悄把里面的学习率或模型参数改掉了，服务端该怎么处理？"

    服务端绝不能睁一只眼闭一只眼直接返回旧任务 `J7`！幂等键的契约只适用于**完全相同的业务意图**。规范的服务端会在记录幂等键时一并存下请求参数的哈希指纹；一旦发现“键相同，但请求内容变了”，必须立刻返回明确冲突错误（如 HTTP `409 Conflict`），防止把用户的新意图悄悄张冠李戴到旧任务上。

在单机世界里，函数调用要么成功返回、要么当场抛错；可一旦跨过网络走向集群，故障的画风彻底变了——超时、失联、假死、半截文件无处不在。这一章，我们就围绕**提交防重（幂等）**、**运行防乱（租约与尝试隔离）**和**落盘防残（产物与原子检查点）**三道防线，把分布式任务的可靠性讲透。

## 为什么“超时 $\neq$ 失败”？提交层重试的工程纪律

把刚才那幕背后的教训再压实一点：在网络通信里，**超时只代表“结果未知”，绝不代表“对方没干活”**。围绕这个残酷现实，靠谱的提交协议通常由四颗螺丝拧紧：

1. **客户端先查再重发，且携带稳定幂等键**：遇到超时或 5xx 临时故障时，优先拿着幂等键去查任务是不是已经建成了；重发时坚持带同一个幂等键。
2. **服务端原子落账 + 参数指纹比对**：把“记录幂等键”和“创建任务 ID”包在同一个数据库事务里，保证要么同时成功、要么同时回滚——绝不能任务建好了却漏记幂等键。
3. **带随机抖动的指数退避（Exponential Backoff）**：遇到临时过载时，重试间隔逐步拉长（如 1s $\rightarrow$ 2s $\rightarrow$ 4s $\rightarrow$ 8s），并混入一点随机抖动，防止成千上万个同时超时的客户端整齐划一地每 2 秒发起一次“同步重试海啸”把刚喘过气的服务端再次打趴！这种逐步放慢重试节奏的策略叫作**退避**（backoff）。
4. **合理的幂等键保留窗口**：服务端存下的幂等键记录终究要过期清理，但它的**保留时长必须严格大于客户端允许重试的最大时间窗口**——否则刚过 1 小时服务端把键删了，客户端第 61 分钟发来一条迟到的重试，依然会漏防重复！

此外，把目光往下一层挪：就算提交只建了唯一一个任务 `J7`，任务在漫长运行中如果因为机器坏了而重启重试了 3 次，平台必须为每一次运行分别发一个单调递增的**尝试编号（Attempt ID，如 `J7-attempt-1`、`J7-attempt-2`）**，把各次尝试的日志、退出码和临时输出彻底隔开，免得查故障时把三次运行的碎片混成一锅粥。

## 集群里最凶险的幽灵：部分故障、心跳与租约

单机时代的世界很干脆：断电了，整台电脑连同内存里的所有进程一起瞬死，干净利落。可到了由上百台服务器组成的集群，冒出了第三种让人抓狂的灰色地带——**部分故障**（partial failure）：节点 `N1` 上的训练进程其实还活蹦乱跳地在算梯度，只不过机柜交换机松动丢包了 30 秒，或者 `N1` 遭遇严重内存抖动卡顿了 20 秒，控制面死活收不到它的消息！

站在控制面视角，你根本分不清 `N1` 是**已经彻底断电阵亡**，还是**仅仅暂时失联、10 秒后又会生龙活虎地冒出来**！如果控制面等了 30 秒判定它死了，赶紧在 `N2` 上拉起第 2 次尝试 `attempt-2`；结果第 35 秒网络恢复，满血复活的 `attempt-1` 居然还自以为是主角，顺手把一份过时的旧权重直接写进共享目录，把 `attempt-2` 辛辛苦苦刚算好的新结果一把覆盖掉了！（分布式系统里管这种“两个自以为是主角的进程互相乱写”叫**脑裂 / 僵尸写入**。）

为了在灰色迷雾里既能及时发现故障、又绝不让复活的旧幽灵污染新结果，集群平台联手请出了两位守门神：

- **心跳（Heartbeat）**：运行中的任务或节点每隔几秒向控制面发一条“我还活着”的报平安消息。它回答的是——**“我最近还听得见它的声音吗？”**
- **租约（Lease）**：控制面发给当前合法尝试的一张**带明确到期时间戳的授权凭证**（类似限时门禁卡）。它回答的是——**“此时此刻，究竟谁才有合法权力提交最终结果？”**

把心跳和租约配合起来，再加上**独立尝试输出目录**，就能把“假死复活覆写”彻底封死：
- 每次尝试（`attempt-1`、`attempt-2`）各自往自己带尝试编号的专属临时目录里写中间文件，绝不直接互相覆盖；
- 控制面只有在旧租约彻底过期失效之后，才给 `attempt-2` 签发带有更高代号（Epoch / Fencing Token）的新租约；
- 哪怕 `attempt-1` 后来苏醒冲回来试图发布最终结果，存储层或平台账本一眼核对它的租约已过期或代号低于当前最新尝试，当场拒绝它的发布请求！

遇到常见异常信号时，先按下面这张排查表稳住阵脚：

| 平台捕捉到的异常现象 | 第一时间该问什么 | 恢复与排错必须留住的证据 |
| --- | --- | --- |
| **心跳超时失联** | 进程/机器真挂了，还是网络闪断或单机卡顿假死？ | 签发的租约期限、最后一次心跳时间戳、节点健康事件 |
| **容器进程非零退出** | 是一过性的偶发硬件错（值得重试），还是代码/配置硬伤（重试一百遍也白搭）？ | 进程退出码（如 `137` 常指向 OOM 强杀）、末尾日志、尝试编号 |
| **检查点文件写了一半** | 上一份带校验的完整版本还在不在、还能不能安全回退？ | 完整发布清单、内容校验值（checksum）、上一份可用 checkpoint 指针 |

顺手区分两类最容易配混的健康探针：**就绪检查（Readiness）**问的是“你现在能不能接新流量？”（不通过只摘流不杀进程）；**存活检查（Liveness）**问的是“你是不是已经彻底死锁没救了？”（不通过会强行重启容器）。把慢启动或短暂过载错配成激进的存活检查，反而会把正在努力干活的服务反复误杀！

## 产物目录、血缘追踪与跨存储层的原子发布

跑完一天一夜的百卡训练，如果最后拿去上线的模型文件根本说不清是用哪一版数据集、哪一版代码、哪一次重试跑出来的——甚至里面有几个字节在传输中静默损坏了——那整整一天的昂贵算力就彻底白费了。

训练产出的模型权重、评估报告、检查点统称为**产物**（artifact）。成熟的平台绝不只是把文件随手扔进某个文件夹，而是会维护一本严谨的**产物目录与血缘账本**：
- **可追溯血缘**：绑定任务 ID、尝试编号、数据集版本、代码提交哈希、容器镜像摘要（digest）与生成时间；
- **完整性指纹**：计算并登记内容的**校验值**（checksum，如 SHA-256），读取使用前可随时验身，防住存储静默位翻转或半截截断；
- **账本与数据分离**：记住目录登记的只是一条指向真实文件的轻巧元数据指针，并不会替你搬运几百 GB 的大文件，真正读取时依然要检查底层存储的访问权限和故障域。

把[第 7 章单机崩溃一致性](../chapter_05_storage_io/02_journaling_crash_disk.md)学过的黄金发布法则，平移到集群常见的三类存储介质上，看看“怎样才算真正安全交卷”：

| 底层存储类型 | 发布完整产物或 Checkpoint 时必须盯紧的生死线 |
| --- | --- |
| **节点本地文件系统** | 走完“写临时文件 $\rightarrow$ `fsync` 刷盘 $\rightarrow$ 同目录原子 `rename` $\rightarrow$ `fsync` 目录”；但务必清醒——**如果这台物理机彻底宕机，本地盘上的检查点就跟着一起失联了！** |
| **共享文件系统（如 NFS / Lustre）** | 多节点同时看见同一目录树，重点防不同尝试并发写同一路径、核对跨客户端缓存可见性延迟、挂载权限与共享存储自身的故障域 |
| **对象存储（如 S3 兼容存储）** | 按完整对象名整体写入（天然没有原地半覆盖，但不支持传统目录原子重命名）；面对由几十个分片组成的大模型检查点，必须先写完并校验所有分片对象，**最后一步再写入一份列全所有分片路径与校验值的“版本清单（Manifest）”**宣告正式生效！ |

回头看看最后一条**多片检查点原子清单发布**：哪怕第 18 分钟写到第 37 个权重分片时节点突然断电，因为最终那份 `checkpoint-2/MANIFEST.json` 压根还没写出来，重启恢复的新尝试一扫目录，就会毫不犹豫地跳过这个半成品，稳稳加载上一份已经签发完整清单的 `checkpoint-1`——按程序要求精准还原模型权重、优化器状态（如 Adam 动量）、学习率调度步数以及数据读取偏移，无缝接着往下算！

## 分清三种“重来”：别把它们混为一谈

读到这里，你已经彻底有能力把日常运维嘴里笼统喊作“重试”的三件事剥得干干净净：
1. **重发提交请求**：解决的是“客户端超时不知道建没建成”，靠**幂等键 + 退避**避免跑出双份任务；
2. **整次重新运行（Job Retry）**：任务遇到临时性故障退出了，平台分配一个新的**尝试编号**和**新租约**，换台健康机器拉起全新容器；
3. **断点续算（Checkpoint Resume）**：新尝试启动后，不从第 0 步傻傻重头算起，而是读入最近一份带完整清单与校验值的 **checkpoint**，从中断前的进度接力奔跑！

日志、监控指标与分布式追踪帮你事后还原“刚才到底发生了什么”，但真正能让系统在惊涛骇浪里毫发无伤地站起来继续跑的，是今天这三样扎扎实实的可恢复状态——**幂等提交账本、带代号的尝试租约，以及原子发布的完整产物清单**。

## 自测

1. 客户端提交任务时网络超时，几分钟后运维却在集群里发现有两个容器居然都在打印同一个任务名。拿到这个现场，你第一时间会查哪三样核心证据来破案？
2. 为什么仅仅靠“每隔 5 秒发一次心跳”，还不足以防止一个网络闪断后复活的旧尝试把新尝试的检查点覆盖掉？需要加什么机制才能彻底兜底？
3. 分布式训练要保存一份包含 16 个权重分片文件的 Checkpoint 到对象存储里，怎样设计发布顺序，才能保证任意时刻宕机都不会让后续恢复读到“一半旧、一半新”的残次模型？

??? note "参考思路"

    1. 第一时间核对 **任务 ID、幂等键、尝试编号（Attempt ID）**：先看两个容器属于两个不同任务 ID（说明是客户端超时重发时没用好幂等键导致的重复提交），还是同一个任务 ID 下的两个尝试编号（说明是失败重试，或旧尝试在失联恢复后尚未及时退出）。接着核对哪一次尝试持有当前有效租约与产物发布权，绝不能光凭日志里打印的任务名就随便挑检查点。
    2. 因为心跳只能证明“过去几秒没收到消息”，无法区分“真死”和“短暂失联假死”。必须搭配**带有效期的租约（Lease）与单调递增代号**，并给每次尝试分配独立的临时输出路径，由存储或控制面拒绝过期租约的最终发布请求。
    3. 先把 16 个分片全部写入带当前尝试编号和版本号的独立路径，逐一核对上传完整性与校验值；直到 16 个分片全部确认就绪落盘后，最后一步才原子写入一份列出全部 16 个分片路径与校验值的**版本清单（Manifest）**或更新最新指针。恢复时只认存在完整清单的最新版本，从而自动屏蔽任何写到一半的残缺分片。
