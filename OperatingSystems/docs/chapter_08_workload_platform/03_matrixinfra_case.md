# 综合练习：跟完一次 MatrixInfra 任务

前两章我们拆解了集群的提交、准入、放置、控制循环对账，以及面对超时与部分故障时的幂等、租约与原子检查点。现在，把这些分散的机制全部拼回一台真实的训练平台里，接受一场端到端的总检验：**当用户甩过来一句“我的任务怎么磨蹭了这么久才跑起来”，或者“节点半夜掉线了，我现在该从哪份权重接着训”，你能不能像老练的系统侦探一样，顺着时间线一步不落地追查到底？**

本篇以 **MatrixInfra** 训练平台作为实战案例——先把它抽象成一个职责清晰的服务：对外接下用户声明的“要跑什么代码、用哪版数据、要几张卡”请求，对内按配额和拓扑把作业派发到物理机器上，并在运行和故障恢复中严密登记产物。动手之前，建议先把[集群编排路径](01_jobs_and_admission.md)和[失败恢复与产物协议](02_retries_and_artifacts.md)放在手边随时对照。

**目标**：学会用可观测的事件时间戳把笼统的“慢”和“挂了”精准切分到具体层级，并针对不同 AI 工作负载选对真正有意义的指标与告警。整套练习既可以在纸面推演，也可以在本地模拟完成。

## 排障第一课：把“等了 14 分钟”切回事件时间线

用户跑来抱怨：“我的训练任务等了整整 14 分钟才开始跑，集群太慢了！”

这句话本身几乎没法直接修——因为“14 分钟”把**预算排队、物理选机、节点拉镜像启动**三段归不同子系统管的时间全糊成了一团！专业排障的第一步，永远是先拉出任务 `J7` 的结构化事件时间表：

```text
10:00  任务 J7 提交成功（API 持久化期望状态）
10:05  通过准入检查，获得团队配额预留          -> 等配额：5 分钟
10:12  集群调度器选中物理节点，完成放置绑定      -> 等节点：7 分钟
10:14  节点拉完镜像、挂好数据卷，容器进程启动    -> 节点启动：2 分钟
10:40  训练进程写出第一份完整检查点（checkpoint）-> 已在运行阶段！
```

把五个时间戳抄成一行，迷雾瞬间散开：
- 从 `10:00` 到 `10:14` 这 14 分钟，清清楚楚拆成了 **5 分钟等准入（配额/队列）+ 7 分钟等放置（找同机空卡）+ 2 分钟节点启动（拉大镜像与挂载数据）**；
- 至于 `10:40` 的 **检查点（checkpoint）**，那是进程早已启动跑了 26 分钟之后的业务产出，和启动前的 14 分钟排队八竿子打不着！

看到切分结果，优化方向立刻精准了十倍：最大的 7 分钟卡在“等放置”，说明真正该查的是集群 GPU 碎片或大任务等待队列，而不是盲目去折腾镜像加速器（就算把拉镜像压成 0 秒，也只救回 2 分钟）。

??? question "如果任务 `J7` 后来故障重启了，第二次尝试居然在存储目录里写出了同名文件 `checkpoint_step_1000`，你怎么确认两份文件谁属于谁、哪份才是真正能用的？"

    千万不能只看显示文件名！必须用 **`任务 ID + 尝试编号（Attempt ID）`** 串联日志、租约与产物目录路径——每次尝试都把产出写进带自己尝试编号的独立子目录；如果一份恢复点由多个权重分片组成，更必须对照[原子发布清单（Manifest）](02_retries_and_artifacts.md)核验所有分片路径与内容校验值是否全部齐备。

## 实战演练：手把手跟踪一次 26 分钟的微调训练全周期

现在，把时间拉长、把故障放进来，完整跟完一次真实的大模型**微调**（fine-tuning，用一批新领域数据在已有预训练模型基础上继续训练）任务。

**作业声明**：申请**同机 2 张 GPU**，指定明确版本的代码提交号、基础模型版本与训练数据集版本，用一份 [Recipe](01_jobs_and_admission.md) 写死容器镜像内容摘要（digest）与启动命令。（如果对准入、放置、挂载还有一丁点生疏，可以随时回翻[任务 J 的时间线](01_jobs_and_admission.md)逐项核对。）

下面这张表记录了从时刻 `0` 提交到时刻 `26` 重试圆满收工的七个关键瞬间——请把每一行右侧的“下一步核对证据”当成你的随身排障清单：

| 时刻 | 平台观测到的状态 | 你下一步应该立刻核对哪组证据 |
| ---: | --- | --- |
| **0** | API 返回任务 ID（如 `J9`） | 核对持久化的期望配置、幂等键、提交者身份与数据集/模型引用是否合法 |
| **2** | 仍停在“等待准入” | 查所属队列、团队配额余额、作业优先级，以及有没有高优作业插队 |
| **4** | 已通过准入，却停在“等待节点” | 查全集群各节点空闲 GPU 分布（是否碎片化）、同机拓扑约束与节点健康标签 |
| **6** | 节点已绑定，容器进程拉起 | 核对实际拉取的**镜像摘要**、数据卷只读/读写挂载、GPU 设备透传与应用启动日志 |
| **15** | 成功发布 `checkpoint 1` | 核对发布清单与内容校验值（checksum）、写入权限、当前尝试 ID 与可恢复状态完整性 |
| **19** | 所在节点突发断网失联！ | 查最后心跳时间戳、旧尝试租约是否过期、是否满足自动重试条件，以及确认**最后一份完整 checkpoint 是哪一份** |
| **26** | 平台拉起新尝试并运行完毕 | 核对最终产出模型版本、尝试血缘、校验值、评估指标与产物目录正式登记 |

走完这张表，请特别留意两条在大型 AI 平台里极易混淆的路径分离：
1. **控制面 vs 数据面分离**：API、控制器、数据库里流转的只是轻巧的 JSON 控制元数据；几十 GB 的数据集和模型权重字节绝不经过控制面，而是由被选中的计算节点直接通过高速内网向共享文件系统或对象存储吞吐。任务记录里“引用了数据集 V3”，并不保证计算节点本身一定拥有读取存储网络的权限和带宽！
2. **GPU 闲着 $\neq$ 集群调度坏了**：容器在时刻 6 跑起来后，如果监控发现 2 张昂贵的 GPU 算力利用率只有 15%，别急着怪调度器——此刻问题已经沉进了**单机操作系统内部**！它可能卡在单机 CPU 数据预处理跟不上（查单机 CPU 调度）、可能卡在本地/网络磁盘读数据太慢（查第 6 章页缓存与块 I/O）、可能卡在主机内存向显存的 PCIe DMA 拷贝带宽，也可能是多卡集合通信（AllReduce）撞上了网络抖动。

## 换一种活干，尺子全得换：五大 AI 工作负载对比

训练任务好不容易跑稳了，平台很快又涌进了五花八门的新需求：在线聊天机器人要实时吐字、强化学习要批量生成几十万条采样轨迹、评测团队要跑严格可复现的性能基准测试、智能体（Agent）还要一边调用模型一边在沙箱里执行代码工具！

这时候如果还拿同一套“GPU 利用率越高越好”的尺子去量所有工作负载，立刻会闹出大笑话。

先认清几把最核心的新标尺：
- **训练（Training）vs 推理（Inference）**：训练是用海量数据反复更新模型参数，最怕白算、最在乎多卡整体吞吐与断电续训；**推理**（inference）则是拿着训好的固定模型响应外部输入生成结果。
- **词元（Token）与尾延迟（Tail Latency）**：大语言模型把文本切成一小段一小段的**词元**（token，可能是一个汉字、一个英文词或词根）逐个吐出。用户坐在屏幕前等回复时，对两件事最敏感——发出问题后多久看到**第一个字蹦出来（首字延迟 TTFT）**，以及最倒霉那 1% 的请求到底卡了多久（P99 **尾延迟**）。
- **负载均衡（Load Balancing）与批处理（Batching）**：面对蜂拥而至的在线请求，平台一方面靠**负载均衡**把流量分散到多份推理副本上，另一方面把几乎同时到达的多个用户请求凑成一批喂给 GPU 一起做矩阵乘（**批处理**）以榨干硬件吞吐——老规矩，批凑得越大吞吐越高，可排在队头的用户多等的排队延迟也会跟着水涨船高！

把平台常见的五类工作负载摊在一张表上，它们的“命门”一目了然：

| 工作负载类型 | 平台最优先保住什么 | 排障与评估必须记录的核心指标 |
| --- | --- | --- |
| **训练 / 微调** | 多卡协同同时就绪（防碎片与死锁）、稳定推进与断点续训恢复 | 每步耗时、分配 GPU·小时、有效算力占比、checkpoint 间隔与恢复耗时 |
| **在线推理服务** | 服务高可用、弹性扩缩、负载均衡与“批处理吞吐 vs 响应延迟”平衡 | 首字延迟（TTFT）、单字生成速率、P95/P99 尾延迟、错误率与超时率 |
| **Rollout 离线采样**（批量生成海量样本） | 高并发吞吐、容忍局部失败重试、每批样本精准归属模型版本 | 每秒生成样本数、丢弃/重试比例、输入数据集与生成模型版本血缘 |
| **Benchmark 基准评测** | 输入数据、随机种子与软件环境 100% 可复现，横向对比公平 | 锁定镜像摘要、完整配置快照、固定样本集与可比性能分布指标 |
| **Agent 工具执行**（模型自主调工具/写代码） | 长驻会话状态维护、严格最小权限沙箱隔离（防越权执行恶意代码） | 会话与任务 ID、工具授权清单、每步操作审计日志、超时熔断与恢复点 |

对比“在线推理”和“离线 Rollout 采样”就能把架构权衡看个透：在线推理背后坐着一个急切盯着屏幕的真实人类，哪怕牺牲一点 GPU 利用率也绝不能让 P99 尾延迟爆掉；离线采样没人实时盯着等下一秒出字，平台就可以大胆开大批量、允许插队利用闲时低价卡甚至接受偶尔抢占重试，一心把每单位算力的总产出榨到极致！

## 动手思考练习（检验是否真正融会贯通）

合上表格，拿一张草稿纸亲手回答下面四道直击真实工程的综合题：

1. **拆分延迟**：用户反馈“提交了一个训练任务，足足等了 20 分钟才看到第一条训练 loss 日志”。请把它拆成**准入等待、放置等待、节点启动准备、应用初始化**四段；如果监控面板目前只记了一个“提交到首条日志总耗时 = 20 分钟”，还缺哪几个关键事件时间戳才能把四段劈开？
2. **断电恢复判决**：回到上面的微调时间线，假设任务在时刻 `15` 完整发布了 `checkpoint 1`，时刻 `18` 正在往对象存储写 `checkpoint 2` 的第 7 个分片，结果时刻 `19` 节点彻底失联！新尝试在时刻 `21` 拉起时，应该恢复到哪一份 checkpoint？假如有人坚持说“我觉得 `checkpoint 2` 说不定已经写完了”，你必须看到哪几条铁证才敢采用 `checkpoint 2`？
3. **差异化告警设计**：分别为“面向用户的在线对话推理服务”和“夜间跑的离线 Rollout 采样作业”各设计一条最关键的运维告警规则，并解释为什么这两条告警长得截然不同。
4. **最小权限与审计**：一个自动化评测任务在运行期间需要做三件事——读取公司内部私有模型权重、把公开基准分数写进公共报告库、以及调用一个外部 HTTP 评分接口。请按第 8 章最小权限与第 10 章容器沙箱思路，分别写出这三件事各自该配怎样的授权范围、网络策略与审计记录。
