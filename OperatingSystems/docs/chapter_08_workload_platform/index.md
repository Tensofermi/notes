# 从单机调度到集群编排

## 当任务不再只跑在一台电脑上，多出了哪几道全新的关卡？

前十章里，无论我们讨论 CPU 时间片轮转、虚拟内存页表、文件系统崩溃恢复，还是 Linux 容器的命名空间与控制组，故事全都发生在一台物理机内部。一旦进程在宿主机上拉起来，单机操作系统内核就能井井有条地替它安排好一切。

可今天真正的 AI 模型训练、大数据分析与云原生后台服务，早就不止跑在一台服务器上——几十台、几百台插满多张加速卡的服务器通过高速网络连成一片，作为一个整体对外提供算力，这就是**集群**（cluster）。

把一个已经打包成标准容器镜像的任务交给一整座集群时，单机时代从没见过的新问题扑面而来：
- **谁有资格现在进场？** 两个团队共用四张加速卡，预算配额不够时任务该在哪里排队？
- **到底把任务塞进哪台机器？** 两台机器各剩 1 张空闲卡，加起来明明有 2 张，可需要“同机双卡”的任务为什么依然跑不起来？
- **中途断网或宕机了怎么收场？** 客户端提交请求超时了、到底建没建成功？训练跑了三小时突然有一台机器失联、半截检查点写了一半，重启后怎么精准接续而不把数据写坏？

从这一章开始，全书最后的三大章节（第 11、12、13 章）将把前面练就的[单机调度](../chapter_02_processes/03_cpu_scheduler_lab.md)、[文件持久化](../chapter_05_storage_io/02_journaling_crash_disk.md)与[容器运行时](../chapter_06_protection_virtualization/03_image_to_process.md)内功全部放大到集群尺度：

- **第 11 章 · [集群中的提交、准入、放置与执行](01_jobs_and_admission.md)**：跟着一个需要同机双卡的任务 `J`，走通“提交 $\rightarrow$ 准入 $\rightarrow$ 放置 $\rightarrow$ 节点启动”四道关卡，理解资源碎片、控制循环对账（reconcile）以及 Kubernetes + Kueue 的真实分层。
- **第 12 章 · [任务失败以后：幂等、产物和恢复](02_retries_and_artifacts.md)**：直面客户端超时、部分故障和半写入检查点（**checkpoint**——记录任务重启后继续计算所需的完整状态），用幂等键、租约与原子清单发布筑起可靠性防线。
- **第 13 章 · [MatrixInfra 综合练习](03_matrixinfra_case.md) 与 [诊断工具全景](../chapter_07_case_diagnostics/index.md)**：把单机与集群全部机制拼进一次完整的微调训练任务，并对照推理、采样、Agent 等不同负载，练成一套从集群事件一路下钻到单机系统调用的分层诊断硬功夫。
