# 操作系统笔记

你现在正看着这篇笔记，或许同时还开着音乐播放器，后台也在默默下载着一个大文件。它们似乎各自独占着一台电脑，互不干扰。可打开机箱看看，里面只有一颗（或几颗）处理器（CPU）、几根内存条、一块硬盘和一张网卡。那么多程序挤在同一套有限的硬件上，既没有把彼此的数据踩成一团乱麻，也没有谁霸占着屏幕让其他程序彻底冻住——背后默默分配资源、划清边界并替大家打理硬件杂务的，正是**操作系统**（Operating System，OS）。

想体会它有多不可或缺，不妨反过来设想一个“没有操作系统”的世界：你的每一个程序都必须亲自和硬件打交道——得知道当前插的是哪家厂商的硬盘，得自己算清楚数据该写在第几个扇区，得盯着键盘芯片有没有来电脉冲，还得时刻提防旁边另一个程序把自己的内存盖掉。一旦机器上要同时跑两个程序，它们就会立刻为了同一块磁盘、同一段内存打得不可开交。所以，操作系统要回答的绝不只是“怎样把硬件包成几个顺手的函数”，而是一个更根本的系统难题：

> 如何在共享而有限的硬件上，为许多程序提供方便、高效、可靠并且彼此隔离的运行环境？

整份笔记都围绕这个问题展开。如果你是第一次系统地学操作系统，不妨先带着三个具体的小实验上路：先在两个终端里[跑起同一段程序](chapter_02_processes/01_process_thread_context.md)，亲眼看看它们怎样互不耽误地轮流等待与推进；接着拿[两张地址对照表](chapter_04_memory/01_address_space_paging.md)手算一遍，弄明白两个程序里的“同一个内存编号”为何能指向两块互不相干的物理内存；等这两件事想通了，再去把[同一个网页服务分别放进普通进程和容器](chapter_06_protection_virtualization/03_image_to_process.md)里跑一遍，你会发现“隔离”这件事其实一点也不神秘。

## 操作系统扮演的三个角色

为了在混乱的共享硬件上建立秩序，操作系统通常同时扛起三副担子：

| 角色 | 面临的麻烦 | 给出的典型抽象 |
| --- | --- | --- |
| 抽象机器 | 硬件接口琐碎繁杂，不同型号差异巨大 | 用[进程](chapter_02_processes/01_process_thread_context.md)代表程序的一次运行，用[文件](chapter_05_storage_io/01_files_directories_inodes.md)给磁盘上零散的数据块一个可按名查找的外壳 |
| 资源管理器 | 多个任务争抢有限的 CPU、内存与设备 | 用[调度](chapter_02_processes/03_cpu_scheduler_lab.md)裁决谁先用处理器，用队列为设备请求排好次序 |
| 隔离与保护者 | 程序可能写错代码，甚至怀有恶意 | 用[地址翻译](chapter_04_memory/01_address_space_paging.md)为每个程序造出彼此看不见的内存空间，用[权限检查](chapter_06_protection_virtualization/01_protection_security.md)拦住越界动作 |

这三个目标听起来都很美好，可在真实的工程里，它们常常互相拉扯。举个随处可见的例子：磁盘读写很慢，系统可以把十个零散的读请求攒成一批，按磁盘磁头或闪存块最顺手的顺序一次处理完。这样做下来，每秒能完成的请求总数确实变多了，但排在最前面那个早就提交的请求，却不得不干等着后面九个凑齐。

为了精准讨论这类取舍，系统领域有两个出场率极高的标尺：单位时间内完成的工作总量叫**吞吐量**（throughput），而单件工作从发出到拿到结果所花的时间叫**延迟**（latency）。攒批往往能拉高吞吐量，却可能拉长单个请求的延迟；为了隔离而多加一层安全检查，能让系统更稳，却也会多花掉一点时间。读完整份笔记你会发现，操作系统里几乎没有“全都要”的免费午餐，大量精巧设计的本质，都是在这些相互牵制的目标之间找到恰当的平衡点。

## 从一行代码窥见冰山之下

在应用程序里，把文件里的一段数据读进内存，写出来常常只有轻描淡写的一行：

```c
ssize_t n = read(fd, buf, 4096);
```

这里的 `fd` 是程序先前打开文件时领到的一个数字编号，`buf` 是程序准备用来装数据的一小块内存，`4096` 表示想读的字节数，返回值 `n` 则告诉程序实际读到了多少字节。

猛一看，它和你自己写的普通函数调用没什么两样。可只要往深处追一步，就会发现这行代码跨过了一道极深的鸿沟：操作系统里真正掌管全机硬件、拥有最高权限的核心部分叫**内核**（kernel）。普通程序绝不允许直接跳进内核里随便调用函数、改写数据结构，否则一个写坏了指针的小工具就能把整台机器拖垮。因此，硬件和操作系统联手架起了一道严格受控的“办事窗口”——应用想要读写文件、申请内存或收发网络数据，必须通过这道门向内核递交请求，这就是**系统调用**（system call）。

当你执行上面那一行 `read` 时，水下悄悄展开了一连串精密配合：

```text
应用调用 read，跨过边界进入内核
  -> 内核查表，把数字编号 fd 对应到已打开的具体文件
  -> 先翻一翻内存里有没有现成留着的文件数据副本
  -> 若没有，就向存储设备下达读取指令，顺便让 CPU 先去忙别的程序
  -> 等设备把数据搬进内存后，再把字节拷贝到应用提供的 buf 中并返回
```

注意第三步里藏着一个耐人寻味的细节：内核常常会把刚刚读过的文件数据顺手在内存里留一份副本（第 6 章的[文件系统与设备 I/O](chapter_05_storage_io/index.md)会正式介绍这套叫页缓存的机制）。不妨先留一个悬念：如果程序紧接着把同一段文件再读一遍，第二次会发生什么？要是内核直接把内存里的副本递给它，整趟耗时的磁盘读取就彻底省掉了，耗时可能从几毫秒骤降到几微秒。如果你想提前把这一行 `read` 背后从用户代码一直到硬盘中断的每一站都走通，[跟踪一次 read 系统调用](chapter_07_case_diagnostics/01_read_system_call_path.md)会给你一份完整的路线图。

## 把内核看作一台事件驱动的状态机

初学操作系统时，很多人脑海里会浮现这样一个画面：内核像一个永不停歇的大管家，始终占着一颗 CPU 核心，在死循环里到处巡逻、发号施令。这个想象其实错得挺离谱——要是内核自己一直占着 CPU 转圈，你的程序还怎么跑呢？

更贴近真相的心智模型，是把内核看作一台由事件驱动的**状态机**（state machine）：它把机器当前的处境（谁在运行、谁在等键盘、哪块内存归谁管）记在一组核心数据结构里，平时把 CPU 安心交给应用程序去跑；直到某个事件敲响了门，内核才短暂接过控制权，依照规则更新状态，再把 CPU 交出去。

什么事件会敲响内核的门？无非几类：应用主动递来系统调用，时钟芯片每隔几毫秒滴答一声提醒该检查轮换，硬盘或网卡干完活发来完工通知，或者程序访问了一个还没准备好的内存地址触发硬件报警。不管哪一种，内核处理的节拍都高度一致：

```text
外部或内部事件到达
  -> 保存被打断程序的执行现场
  -> 切入内核，识别究竟发生了什么事
  -> 核对身份、权限与参数是否合法
  -> 更新内核里的对象状态与等待队列
  -> 视情况让当前任务暂停、唤醒别的任务，或重新做调度
  -> 恢复选中的执行流，把 CPU 交还给程序
```

没有应用干活也没有设备来消息时，内核并没有自己的“业务”要忙，CPU 干脆进入省电的空闲等待。这套“事件到达 -> 切入内核 -> 更新状态 -> 恢复执行”的节拍，是贯穿全书的骨架，我们在[第 1 章的入口机制](chapter_01_foundations/02_kernel_user_syscalls_interrupts.md)里就会亲手把它拆解清楚。

## 读这份笔记的方法

操作系统最忌讳把概念背成飘在空中的名词表。几乎每一个机制，都能在真实机器上找到可观测的证据：听说“把 CPU 从一个程序换给另一个程序需要开销”，就顺手追问系统到底忙着保存了哪几份现场数据；看到一次文件读取慢得出奇，别急着怪硬盘坏了，先问问数据是不是根本没在内存副本里、这次调用究竟有没有真的去等设备。

遇到任何新机制，都可以习惯性地做三层追问：

1. **抽象层**：它向上给程序员承诺了怎样一个简单、稳定的使用方式？
2. **机制层**：为了兑现这份承诺，内核和硬件在底层实打实地维护了哪些数据结构与规则？
3. **策略层**：当存在多种合理做法时（比如先让谁跑、内存满了该踢掉谁），系统依据什么标准做权衡？

这三层里，把**机制**和**策略**分开尤其关键。机制回答“能不能做到”，策略回答“应该怎么选”：硬件定时器和保存现场的动作是机制，决定先挑哪个任务上 CPU 的算法是策略；把虚拟地址映射成物理地址的表结构是机制，物理内存吃紧时决定把哪一页换出去的算法是策略。先把“能力”和“选择”拆开，原本缠成一团的知识点往往瞬间就明朗了。

## 实验与观测边界

笔记中出现的命令行工具（如 `strace`、`ps`、`vmstat`、`iostat`、`perf stat`）一律优先采用只读观测方式，用来帮你把书本上的模型和机器里的真实数字对上号。这些工具是否可用、能看到多少细节，取决于具体的操作系统、内核配置和当前账户权限；动手前请先确认目标进程和所在环境，切勿在承载真实业务的生产机器上贸然开启高开销的跟踪采样。

合上这一页、正式迈进[第 1 章](chapter_01_foundations/index.md)之前，不妨把下面三个问题揣在兜里：

- 为什么普通函数调用不能直接替代系统调用？
- 为什么一个任务卡着等硬盘时，另一个任务还能顺畅地用着 CPU？
- 为什么程序里写出来的内存地址，通常并不是内存条上那个真实的物理编号？
